# Action Hub operations

Every write below except `todos ack`, `questions done` and `approvals add` is `python <kit>/tools/hub.py <verb> ... --from <your session key>`, one per call; the MCP tools `hub_ask`, `hub_todo_add`, `hub_todo_ack`, `hub_page_publish` and `hub_approval_request` do the same, each taking `from` exactly where its verb takes `--from` (so neither `hub_todo_ack` nor `hub_approval_request` takes one). The key is the `hub key:` line of your session-start context; the hub refuses any other, and when that line says unknown, ask the PM.

1. Question: `python <kit>/tools/hub.py questions add --title "<restates its subject>" --context-file <F> --option "label::description" [--option ...] --recommended <N> [--refs <ID> ...] --from <key>`. Each carries its context, options and a recommendation (`N` counts from 0). A question about one record: add `--record <repo>:<ID>` (the kit's own records are repo `pm`) and park the record on it (skill backlog-ops, `set-status <ID> parked --q <Q-id>`), then move on: no relay to the PM and no wait. Read one question with its options, answer and note: `python <kit>/tools/hub.py questions show <Q-id>` (`questions` alone lists every one). Withdraw an open one you asked: `questions withdraw <Q-id> --from <key> --if-version <V>`.
2. Pending and push: read `python <kit>/tools/hub.py pending --for <key>` once at session start and act on what it lists. Run no background hub wait: the hub pushes each answer and done to-do for your key to your session as a `[hub push] <kind> <id> <status> ...` message with one line of what to do (<kit>/docs/action-hub.md "Push notifications"). On a push, read `pending --for <key>` (it hands the item to you and ends the push), then act. An answer stays pending until it is logged or marked done ("For the PM"), so after a compaction or restart check before acting on an id `pending` lists again. A bound answer returns in its record: the hub files it there (an `## Owner answer` section; the park ends when no other bound question is open; status `filed`, <kit>/docs/action-hub.md "Filing the answer") and its push names the record. Read it with `backlog.py show <ID>`, take the item up again, then end the question with `python <kit>/tools/hub.py questions done <Q-id> --why "<what you did>" --if-version <V>` (V from `pending`). One the owner made a standing rule is the PM's to log (done is refused), and one whose filing failed stays `answered` and is the PM's.
3. To-do, a command the owner runs for your own work: `python <kit>/tools/hub.py todos add --title "<T>" --command "<C>" [--command ...] [--detail "<D>"] [--steps <F.json>] [--repo <repo>] --from <key>`. Withdraw an open one: `todos withdraw <T-id> --from <key> --if-version <V>`. When the hub pushes it done, act on it and `python <kit>/tools/hub.py todos ack <id>`; one not acked within 30 minutes falls to the PM (<kit>/docs/action-hub.md "Who handles a pending item").
4. Page: one UTF-8 HTML file, no script, no `on*` attribute, no remote URL, no <meta> but charset utf-8 or name viewport/color-scheme/description/author/generator, <title> plain text only, at most 512 KiB (<kit>/docs/action-hub.md "pages/<id> and page_html/<id>"). Draw each diagram as inline `<svg>`: Mermaid is refused ("render it to svg first"). Publish with `python <kit>/tools/hub.py pages publish <page-id> --title "<T>" --html-file <F> [--summary "<S>"] --from <key>`; republishing needs `--if-version <V>` from its card. A page id is refused if it contains anything shaped like an id (a letter from Q M T P S A R, a dash, digits, any case: `design-T-3`). Cite the page id in the `--refs` of the question or to-do that asks about it. No shell: write the file to your scratch folder and name it in your report; your caller publishes it.
5. Owner approval, when your role's rule says a change needs one: write each file's whole new content to a file outside the checkout, then `python <kit>/tools/hub.py approvals add --checkout <checkout> --title "<T>" --file <repo path> <content file> [--file ...] [--reason "<R>"]`. Each base is the file at the checkout's HEAD (`--head <commit>` for another), the content is the file's exact bytes, and it prints `REQUESTED <id>`; it takes no `--from`, and cannot ask for a delete (<kit>/docs/action-hub.md "approvals/A-NNN"). It only asks: the owner decides on the hub. Once approved, the author commits with `commit.py --owner-approval hub:<id> --model "<model name>"` with the file still at its base; commit.py writes the approved content.
