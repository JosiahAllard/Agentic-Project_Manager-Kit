# Land a branch

Landings go through the machine-lock queue as one entry each. The coordinator submits each LAND verdict at once (`land.py --submit`) and keeps a background `gate.py wait-result` running; the lander role (optional) does the same for one branch and reports; its steps are the one copy of the lander procedure. Landings go ahead of every ordinary waiting run on their own and merge onto whatever main is at their turn; nothing aligns them.

## Coordinator: queueing a landing

- Submit every LAND verdict as soon as you give it, from the main checkout: `python <kit>/tools/land.py -C <main checkout> <branch> --expect-tip <reviewed tip> --reviewed-by <reviewer id> --submit`, naming the `reviewer_id` of the verdict you queued, one `--reviewed-by` per branch in `--expect-tip`'s order, always before `--submit` (a batch only where the profile's **Landing** section allows, up to the repo's `"landing".batch_max`; never a high-risk branch). It prints a `REVIEW ...` line for each verdict queued at a tip submitted, then one `SUBMITTED ...` line last. A missing or miscounted `--reviewed-by` is a USAGE error whose `Instead:` line is the command to run; a wrong id, or no usable verdict at the tip, is REFUSED (<kit>/docs/gate.md "Submitting a landing"). Start the `gate.py wait-result <branch> --tip <sha> --kind land -C <main checkout>` command it prints as a background command, one per submission, and act when the host wakes you on its exit; do not poll, loop or sleep. No go to anyone, no expected-main hash: submitted landings queue and merge in ticket order, each onto the main it finds. A lander role (optional) may do the submit, wait and report for you.
- Read the `RESULT <verdict> land ...: <line>` it prints (the verdicts: the lander role's step 6). `pass` -> close records (below) and send the notices (the after-landing bullet); the landing posts itself to the Action Hub's Landings feed (<kit>/docs/gate.md "Landing feed"), so a plain pass is no message to the PM: message the PM only for an action (a `stuck` landing, a record close that failed, a deploy step). A `WARNING: the landing of <branch> was not posted to the hub feed` line changes nothing: the landing stands. A branch whose landing needs a deploy step carries a `Deploy: <what to do>` trailer on its tip, which the feed shows. `fail` with `CONFLICT ...: the author merges main` -> send the branch back to its author to merge main and re-gate (the final gate of the bullet below), re-review the change, resubmit with the new tip. `fail` with `NOT LANDED: ...` -> nothing landed: send it back with the failing lines, as for any red gate. `refused`, `busy`, `not-run` -> report the line and fix its cause. `stuck` -> report the lines verbatim; it leaves the lock held for the owner. `error` -> read `land.py --queue` and the log before anything else.
- Every landing needs its verdict queued first: `python <kit>/tools/verdict.py add -C <main checkout> --branch <branch> --tip <full sha> --verdict LAND --risk High --reviewer <type> --reviewer-model <model> --reviewer-id <id> --author "<commit author> / <author agent type>" --range <base>..<tip> --session <session>` (`<kit>/docs/gate.md` "Strict paths"). A strict landing (a changed path matches `STRICT_DEFAULTS` in `<kit>/kitlib/gate/strict_defaults.py`) lands alone.
- After a main sync of a reviewed branch, run `python <kit>/tools/verdict.py carry -C <main checkout> --branch <branch>` before submitting the new tip: `CARRIED ...` moves the queued verdict to it (only conflict-free main merges since the review, the branch's own diff unchanged); `NOT CARRIED: ...` means review and queue the new tip (`<kit>/docs/gate.md` "Carrying a verdict forward").
- A branch lands only with your verdict and its final gate green on that exact tip: `gate.py --full` for a strict branch (it lands alone; its merged gate runs `--full --fresh`); `--full` too, smoke steps or not, for a branch that changes a gate config file once the base's `.kit.json` sets `"landing".shared_paths` or `"landing".gate_once`, or a shared path under `"landing".shared_paths` without `"landing".gate_once`; for any other, the optimized default gate once the base's gate config names smoke steps or its `.kit.json` sets `"landing".shared_paths` or `"landing".gate_once` (the scoped gate; under gate_once the merged gate runs `--full`), `--full` otherwise; never bounce a scoped final gate that rule allows (`land.py` refuses any other record; `<kit>/docs/gate.md` "Landing", step 4, "Shared paths", "Gate once at landing"). `land.py` aborts any conflict, docs too: the author merges main and re-gates the same way; the brief carries no conflict rules.
- A test pinning files outside its module is mapped to them in the gate's selector (`--find gate`), or main goes red at the next landing.
- Before a record closes, move what must survive (owner decisions, quoted and dated, to the decisions log; constraints beside the code or the owning doc); open follow-ups become their own records.
- After a landing, take `<merge>` from its `LANDED <branch> on <main> at <merge>` line and `<base>` from the `"base"` field of the JSON line `wait-result` prints after `RESULT` (the main the landing, a batch too, started from); tell an open workstream on branch `<W>` only when `git diff --name-only --no-renames <merge>...<W>` shares a file with `git diff --name-only --no-renames <base> <merge>`, and every open workstream when one of the landing's files matches a `.kit.json` `"landing".shared_paths` glob; name the merge commit (skill branch-sync); the PM hears of it only by the coordinator role's rule.
- Cleanup of what a landing left (its `kept` lines), only after the push is verified: the repo's command (`python <kit>/tools/doc_index.py -C <main checkout> --find cleanup`), else `python <kit>/tools/worktree_remove.py -C <main checkout> <worktree>`. "Filename too long" or "Permission denied": leave it and report. Absolute paths only.
- A fresh or successor session reads `land.py --queue` and the land result records first (skill session-handoff), and never resubmits a branch already queued.

## Never

Edit code; close or amend a backlog record; force-push; `git add -A`; `reset --hard`; `branch -D` or `--force`; `git worktree remove` or `git branch -d` from a worktree; chain a write with other commands; land without a verdict or a branch whose tip moved after review, unless `verdict.py carry` recorded it; wait in a loop, jump the queue, override or break a lock; kill a process by name; remove a worktree or untracked file the brief did not name. Refusals: skill backlog-ops, "Refusals".

Details: `<kit>/docs/gate.md` ("Commands", "Exit codes", "Landing", "Branch cleanup"); `<kit>/docs/worktree-remove.md`.
