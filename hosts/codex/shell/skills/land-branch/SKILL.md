# Land a branch

Landings go through the machine-lock queue as one entry each. The coordinator submits each LAND verdict at once (`land.py --submit`) and keeps a background `gate.py wait-result` running; a lander is an optional wrapper that does the same for one branch and reports. Landings go ahead of every ordinary waiting run on their own and merge onto whatever main is at their turn; nothing aligns them.

## Lander (optional)

Prerequisites, all from the coordinator: the branch, its reviewed tip sha (full), the verdict in words (LAND, or LAND WITH FOLLOW-UP and where it is recorded), and any extra gate. Missing one: say what you need, do nothing. Read the repo profile's Landing and Shared resources sections (`python <kit>/tools/doc_index.py -C <main checkout> --find landing`); a repo whose profile names another landing command uses it, and these rules still hold.

1. Work from the main checkout on the main branch, never inside a worktree you will remove; `git status` clean; logs go to your scratch folder.
2. Run the brief's extra gate first, under the lock the profile names, and release it: the landing books its own lock. Pure pass/fail: dispatch the test-runner role.
3. Run `python <kit>/tools/backlog.py -C <main checkout> landable <branch>` first (exit 0 LANDABLE, with one `closes <ID>` or `releases <ID>` line per pull the branch holds: what its landing does to that record; a `closes` line that ends `a slice branch needs a Part-of: <ID> line` closes the whole record, so for a slice branch report it and do not submit; 2 NOT LANDABLE, the branch holds a pull its landing leaves dead; 1 CANNOT TELL, a bad branch name or unreadable ref, records or Closes and Part-of lines: report either, never widen scope at landing). Scope is widened at fold-in, not at landing: `python <kit>/tools/backlog.py -C <worktree> set <ID> --scope <path>` (widening a pulled record into a live pull needs the PM's ruling, `<kit>/docs/backlog.md` "Owner gates"). Then submit as one bare call: `python <kit>/tools/land.py -C <main checkout> <branch> --expect-tip <sha> --submit`. A detached process books one machine-lock entry, takes the landing lock, merges the main it finds `--no-ff`, gates the merged tree, pushes only when green, and drops a red merge; main is untouched. The call prints a `REVIEW <branch> <tip>: ...` line when a verdict is queued at that tip (a carried one names the commit reviewed), then one `SUBMITTED ... wait: ...` line last, and exits 0; no `SUBMITTED` line: report the output.
4. Start the `gate.py wait-result ... --kind land -C <main checkout>` command that line prints, as printed, in the background with output to a log (never a pipe, polling loop or Monitor), and wait for its notification. `python <kit>/tools/land.py -C <main checkout> --queue` shows who holds and who waits.
5. Read the line the wait prints, `RESULT <verdict> land <branch> at <tip>: <line> (<log>)`. `pass`, `LANDED ...`: landed. `fail`, `CONFLICT <branch> with main <sha>: the author merges main`: nothing left behind; report it, the author merges main (never resolve it yourself). `fail` with `NOT LANDED: ...` (a red merged gate, a refused push), or `refused`, `busy`, `not-run`, `usage` (`REFUSED:`, `BUSY:`, `NOT RUN:`, `USAGE:`): nothing left behind; report the line and the log's failing lines (a stray in the main checkout: also the safe restore, `python <kit>/tools/stray_restore.py -C <main checkout>`), the coordinator decides. `stuck`, `STUCK: ...`: the lock stays held; report it and the log's `left:` lines verbatim and do nothing else. `error`: the landing stopped on an exception, or its process died (`the landing process died: ...`); report it with `land.py --queue`.
6. Only a flake on the repo's known-flake list gets one rerun; any other failing run is real (the list: `python <kit>/tools/doc_index.py -C <main checkout> --find flakes`).
7. Size check: the lander role's step 3.
8. Verify read-only, whatever the verdict: `git ls-remote <remote> <main>` equals `git rev-parse <main>`, then one `git merge-base --is-ancestor <tip> <remote>/<main>` per branch (exit 0). Not verified: report.
9. Records: the branch names its own in its last commit's message, on its own line (`Closes: <ID>`), and land.py closes it at landing; one the brief names still open at the pushed main is reported, never closed by you.
10. Cleanup, only after step 8: `land.py` removes the landed branch, worktree and remote branch itself. For any part its `kept` lines name: the repo's command (`python <kit>/tools/doc_index.py -C <main checkout> --find cleanup`), else `python <kit>/tools/land.py -C <main checkout> --sweep-landed` (a dry run; read it) then `python <kit>/tools/land.py -C <main checkout> --sweep-landed --apply`, or `python <kit>/tools/worktree_remove.py -C <main checkout> <worktree>`. "Filename too long" or "Permission denied": leave it, report. Absolute paths only.
11. Report one block: branch; old and new main sha; merge commit; test counts; extra gate; pushed yes/no with both shas; worktree removed; any record still open; any judgement you made.

## Coordinator: queueing a landing

- Submit every LAND verdict as soon as you give it, from the main checkout: `python <kit>/tools/land.py -C <main checkout> <branch> --expect-tip <reviewed tip> --submit` (a batch only where the profile's **Landing** section allows, up to the repo's `"landing".batch_max`; never a high-risk branch). It prints a `REVIEW ...` line for each verdict queued at a tip submitted, then one `SUBMITTED ...` line last. Start the `gate.py wait-result <branch> --tip <sha> --kind land -C <main checkout>` command it prints as a background command, one per submission, and act when the host wakes you on its exit; do not poll, loop or sleep. No go to anyone, no expected-main hash: submitted landings queue and merge in ticket order, each onto the main it finds. A lander role (optional) may do the submit, wait and report for you.
- Read the `RESULT <verdict> land ...: <line>` it prints (the verdicts: lander step 5). `pass` -> close records (below) and send the notices (last bullet). `fail` with `CONFLICT ...: the author merges main` -> send the branch back to its author to merge main and re-gate (the final gate of the bullet below), re-review the change, resubmit with the new tip. `fail` with `NOT LANDED: ...` -> nothing landed: send it back with the failing lines, as for any red gate. `refused`, `busy`, `not-run` -> report the line and fix its cause. `stuck` -> report the lines verbatim; it leaves the lock held for the owner. `error` -> read `land.py --queue` and the log before anything else.
- Every landing needs its verdict queued first: `python <kit>/tools/verdict.py add -C <main checkout> --branch <branch> --tip <full sha> --verdict LAND --risk High --reviewer <type> --reviewer-model <model> --reviewer-id <id> --author "<commit author> / <author agent type>" --range <base>..<tip> --session <session>` (`<kit>/docs/gate.md` "Strict paths"). A strict landing (a changed path matches `STRICT_DEFAULTS` in `<kit>/kitlib/gate/strict_defaults.py`) lands alone.
- After a main sync of a reviewed branch, run `python <kit>/tools/verdict.py carry -C <main checkout> --branch <branch>` before submitting the new tip: `CARRIED ...` moves the queued verdict to it (only conflict-free main merges since the review, the branch's own diff unchanged); `NOT CARRIED: ...` means review and queue the new tip (`<kit>/docs/gate.md` "Carrying a verdict forward").
- A branch lands only with your verdict and its final gate green on that exact tip: `gate.py --full` for a strict branch (it lands alone; its merged gate runs `--full --fresh`); `--full` too, smoke steps or not, for a branch that changes a shared path or a gate config file once the base's `.kit.json` sets `"landing".shared_paths`; for any other, the optimized default gate once the base's gate config names smoke steps or its `.kit.json` sets `"landing".shared_paths` (the scoped gate), `--full` otherwise; never bounce a scoped final gate that rule allows (`land.py` refuses any other record; `<kit>/docs/gate.md` "Landing", step 4, "Shared paths"). `land.py` aborts any conflict, docs too: the author merges main and re-gates the same way; the brief carries no conflict rules.
- A test pinning files outside its module is mapped to them in the gate's selector (`--find gate`), or main goes red at the next landing.
- Before a record closes, move what must survive (owner decisions, quoted and dated, to the decisions log; constraints beside the code or the owning doc); open follow-ups become their own records.
- After a landing, take `<merge>` from its `LANDED <branch> on <main> at <merge>` line and tell a workstream only when `git diff --name-only --no-renames <merge>...<branch>` shares a file with `git diff --name-only --no-renames <merge>^1 <merge>`, and every open workstream when one of those files matches a `.kit.json` `"landing".shared_paths` glob; name the merge commit (skill branch-sync); the PM hears of it only by the coordinator role's rule.
- A fresh or successor session reads `land.py --queue` and the land result records first (skill session-handoff), and never resubmits a branch already queued.

## Never

Edit code; close or amend a backlog record; force-push; `git add -A`; `reset --hard`; `branch -D` or `--force`; `git worktree remove` or `git branch -d` from a worktree; chain a write with other commands; land without a verdict or a branch whose tip moved after review, unless `verdict.py carry` recorded it; wait in a loop, jump the queue, override or break a lock; kill a process by name; remove a worktree or untracked file the brief did not name. Refusals: skill backlog-ops, "Refusals".

Details: `<kit>/docs/gate.md` ("Commands", "Exit codes", "Landing", "Branch cleanup"); `<kit>/docs/worktree-remove.md`.
