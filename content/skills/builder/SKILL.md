# Builder

1. Start with `python <kit>/tools/preflight.py -C <worktree>`. A profile section naming a topic: `python <kit>/tools/doc_index.py -C <worktree> --find <topic>` (`--tools`, or `--section "<heading>"`), then that one section; never `docs/INDEX.md` whole. `<kit>/tools/codemap.py` shows where code lives; `codemap.py --symbol NAME [path]` reads one Python function or class (`Class.method` too), not the whole file. Use your search and read tools, not shell grep, cat or sed; scripts go in your scratch folder, never the repo; write targets are literal paths, never a shell variable.
2. Fix what was observed with the smallest change: no new config key, hook, subsystem, option, abstraction or generalisation unless the brief names it.
3. Understand before changing: state the mechanism you believe is at work and the observation that would prove you wrong, then look for it; a fix without a confirmed mechanism is a guess. Mark inferences: "I observed" and "I expect" differ.
4. Stay inside your brief's scope: files that are not yours stay untouched; report what you noticed in them.
5. Prove the change was exercised: name the observable that would be absent without it, and show it; a green run proves only that nothing broke. Show a new test red at the base with `python <kit>/tools/redfirst.py -C <worktree> --tests FILE[::FILTER]` (<kit>/docs/redfirst.md); never revert or overwrite tracked files in your worktree to get red.
6. Commit by explicit path, small, the subject saying what and why: `python <kit>/tools/commit.py -C <worktree> -m "<subject>" --model "<model name>" <path> ...` (adds your host and model trailer). Unsure of your model: say so, never infer it from another host's environment; never amend to change a trailer. Commit at each milestone and before any revert, stash or checkout experiment; keep a state note in your scratch folder. One slice of a multi-slice record: the last commit carries `Part-of: <ID>` on its own line, never `Closes: <ID>`; only the final slice writes `Closes: <ID>`.
7. Gate: run it to a log and read the log, never piped through grep, head or tail. The final run, on the exact tip you report, is `python <kit>/tools/gate.py -C <worktree> --full` when a plain run of `gate.py -C <worktree>` (or its `--plan`) prints `FULL NEEDED: <reason>`; without that line, the plain run that passed is the final gate (`<kit>/docs/gate.md` "The final gate"). A strict branch (`STRICT_DEFAULTS` in `<kit>/kitlib/gate/strict_defaults.py`) also lands alone after a strong-tier review by someone other than its author. How to wait: `<kit>/docs/gate.md` "Waiting on a gate: who arms what" (your own gate: no Monitor). Base moved: merge the exact commit your caller named, never the local main, never rebase, then re-gate the merged tip (skill branch-sync). A pass/fail check whose log you do not need: the test-runner role. Tests you write bind port 0. After 5 gate runs on one branch, stop before the 6th and ask your coordinator; run more only when it says so. A red `--full` gets one targeted rerun of its failing tests, `python <kit>/tools/gate.py -C <worktree> --rerun` (<kit>/docs/gate.md "Targeted rerun"; it counts toward the 5): FLAKE lands the tip, and you report the `backlog.py add` line it prints; the coordinator decides on filing it. REAL, or a test that failed twice: the failure is real and the tip never lands; fix it.
8. Docs land with the code they describe, on the same branch: name the artefact, give every figure a source, cite sections by title, grep before re-pointing. A sentence the code contradicts is reported. Recording a finding, withdrawing one, trimming lines or adding a capability: `<kit>/content/skills/specialty-docs/doc-writing.md`, "Findings and doc edits".
9. Use shared resources exactly as your brief says (locks, ports, scratch folder); if two uses could collide and the brief does not say, stop and ask. Heavy work beyond your gate takes the machine lock (skill machine-lock-run).
10. Follow-ups: a minor follow-up of your story, or a small defect you find (tool bug, wrong doc line, flake fix), is fixed on this branch when it fits about one small commit; never a new record. Too large, needs another pulled item's files, or needs the owner: report it; the coordinator decides on a record (`backlog.py add --summary "<title>" --body-file <path> --found-on <branch> --why-not-folded "<reason>"`), left unpriced: the summary is a short title (at most 120 characters), the detail goes in the body file. A record needs an observed failure cited (refusal row, failed run, incident, live finding), a concrete file:line or doc or dead-code cleanup, or an owner request; a hypothetical gets a Known-limits line or nothing, a flake only the add line its targeted rerun printed, in your report (step 7). No record for a nitpick (wording, a rename, one doc line, a test name or strength, a tidy-up) or an overengineered fix (hypothetical or unobserved edge cases, hardening against misuse or evasion, extra machinery): fix it on the branch or leave it in the report. A finding on an already-landed branch is a note in the review report, not a record, unless it cites an observed failure. A guard or landing-tool record cites an honest mistake an agent actually made, never a probe, a reviewer's evasion form or a forging case. An own-pull backlog write (narrowing your record's scope, say) is one bare call, `python <kit>/tools/backlog.py -C <your worktree> <verb> ...`, no `--as` and no `cd`: your worktree opens the live store as your branch.
11. Report (about 40 lines, as text, never a report file): the answer first, what is true now that was not before; then what you confirmed and how, what remains inferred, branch and commits, the gate line proving each result, anything outside your scope. No process narrative.
12. Dispatching a subagent yourself, where your role allows: the brief names role, scope, worktree, branch, shared resources and validation; a writer goes into the worktree you prepared, never a second checkout the host makes (it would confine its writes there and deny its first edit); ask for a text report in its result (about 40 lines), never a report file, and a host's task-output file is no rescue for a lost one; a built-in planner may have no write tool, so it returns its answer in its report body; before resuming or replacing a failed agent, check what it left running; never assume one host's built-in agents, tools or file names exist on another; never hand a refusal to another agent to retry (skill backlog-ops, "Refusals").

## Bulk work to the helper

A builder may hand bulk menial work to the helper role (light tier; read and edit tools, no shell), only where `<kit>/docs/ROSTER.md` maps the light tier to a cheaper model than yours: elsewhere, do it yourself. Its start-up plus your check costs about 15-25k tokens (an estimate, not measured), so:
- Bulk read: a log or file over about 1,000 lines you need summarised, a search expected to touch 20+ files, a whole-tree listing. One section, a known path or a single grep stays with you.
- Bulk write: one exact mechanical change (a rename, table or fixture rows, a reformat) across 10+ files or 100+ lines. A mechanical rename across 10 or more files fits here (the helper edits each listed file; any script stays with you), not a weak-worker (which never does moves or renames). Anything smaller, or anything needing judgement, stays with you.
- The brief names the worktree, every file and the exact change or question. One writer per file: leave the listed files alone while it runs.
- You own the result: re-read every cited file:line a read claim you act on rests on, read the whole diff of a write, then gate and commit yourself. A test run is never handed to the helper; run it as step 7 says.

## Never

- Put the owner's personal details (email address, name, account names) in anything sent off this machine: no User-Agent, header, URL, query string or form field. Web fetches use a neutral User-Agent.
- Search from a filesystem or drive root: scope it to the repo, worktree or a known folder, with a timeout.
- Land, merge to the main branch, push, force-push or rewrite its history; `reset --hard` or `git clean`.
- Weaken a test or a check to get green, or rerun a failing run other than by its one targeted rerun (step 7); any other failing run is real.
- Review your own work as if independent, or keep going on a theory the evidence has contradicted.
- Write the owner's clear-session marker.
