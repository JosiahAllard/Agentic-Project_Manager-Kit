# Action Hub operations

Every write below except `todos ack`, `questions done`, `approvals add` and `skill-edit` is `python <kit>/tools/hub.py <verb> ... --from <your session key>`, one per call; the MCP tools `hub_ask`, `hub_todo_add`, `hub_todo_ack`, `hub_page_publish` and `hub_approval_request` do the same, each taking `from` exactly where its verb takes `--from` (so neither `hub_todo_ack` nor `hub_approval_request` takes one). The key is the `hub key:` line of your session-start context; the hub refuses any other, and when that line says unknown, ask the PM.

1. Question: `python <kit>/tools/hub.py questions add --title "<restates its subject>" --context-file <F> --option "label::description" [--option ...] --recommended <N> [--refs <ID> ...] --from <key> (--record <repo>:<ID> | --class <C>)`. Each carries its context, options and a recommendation (`N` counts from 0), and a record or a class, never neither (the hub refuses it; `hub_ask` takes `record` or `class`). Class `C` is `rule` (a standing rule or a delegation run line), `machine`, `cross-repo` or `go` (a one-off landing or archive go). A question about one record: `--record <repo>:<ID>` (the kit's own records are bound under the PM repository's folder name, as the hub lists its repositories, which `hub_view` view `repos` gives: `<pm-folder>:<ID>`, not `pm:<ID>` or `kit:<ID>`) and park the record on it (skill backlog-ops, `set-status <ID> parked --q <Q-id>`), then move on: no relay to the PM and no wait. Read one question with its options, answer and note: `python <kit>/tools/hub.py questions show <Q-id>` (`questions` alone lists every one). Withdraw an open one you asked: `questions withdraw <Q-id> --from <key> --if-version <V>`.
2. Pending and push: read `python <kit>/tools/hub.py pending --for <key>` once at session start and act on what it lists. Run no background hub wait: the hub pushes each answer and done to-do for your key to your session as a `[hub push] <kind> <id> <status> ...` message with one line of what to do (<kit>/docs/action-hub.md "Push notifications"). On a push, read `pending --for <key>` (it hands the item to you and ends the push), then act. An answer stays pending until it is logged or marked done ("For the PM"), so after a compaction or restart check before acting on an id `pending` lists again. A bound answer returns in its record: the hub files it there (an `## Owner answer` section; the park ends when no other bound question is open; status `filed`, <kit>/docs/action-hub.md "Filing the answer") and its push names the record. Read it with `backlog.py show <ID>`, take the item up again. That is all: once you have it (your `pending` read), the hub marks the question done itself (`done_by` `hub`, <kit>/docs/action-hub.md "Done by the hub"), so do nothing more, no `questions log` and no `questions done`. When `pending --for <key>` still lists it after that, the hub did not mark it done, for one of these reasons: the owner made it a standing rule (the PM's to log; your done is refused); it carries a delegation run line (it waits for its log step, as the delegation says); its filing failed (it stays `answered` and is the PM's); it is bound to no record (a classed answer, the PM's to log); or the hub could not tell what the filing did to the record (listed ` (filed)` with no other reason: end it yourself with `python <kit>/tools/hub.py questions done <Q-id> --why "<what you did>" --if-version <V>`, V from `pending`).
3. To-do, a command the owner runs for your own work: `python <kit>/tools/hub.py todos add --title "<T>" --command "<C>" [--command ...] [--detail "<D>"] [--steps <F.json>] [--repo <repo>] --from <key>`. Withdraw an open one: `todos withdraw <T-id> --from <key> --if-version <V>`. When the hub pushes it done, act on it and `python <kit>/tools/hub.py todos ack <id>`; one not acked within 30 minutes falls to the PM (<kit>/docs/action-hub.md "Who handles a pending item").
4. Page: one UTF-8 HTML file, no script, no `on*` attribute, no remote URL, no <meta> but charset utf-8 or name viewport/color-scheme/description/author/generator, <title> plain text only, at most 512 KiB (<kit>/docs/action-hub.md "pages/<id> and page_html/<id>"). Draw each diagram as inline `<svg>`: Mermaid is refused ("render it to svg first"). Publish with `python <kit>/tools/hub.py pages publish <page-id> --title "<T>" --html-file <F> [--summary "<S>"] --from <key>`; republishing needs `--if-version <V>` from its card. A page id is refused if it contains anything shaped like an id (a letter from Q M T P S A R E, a dash, digits, any case: `design-T-3`; or `H-<name>-<digits>`). Cite the page id in the `--refs` of the question or to-do that asks about it. No shell: write the file to your scratch folder and name it in your report; your caller publishes it.
5. Owner approval, when your role's rule says a change needs one: write each file's whole new content to a file outside the checkout, then `python <kit>/tools/hub.py approvals add --checkout <checkout> --title "<T>" --file <repo path> <content file> [--file ...] [--reason "<R>"]`. Each base is the file at the checkout's HEAD (`--head <commit>` for another), the content is the file's exact bytes, and it prints `REQUESTED <id>`; it takes no `--from`, and cannot ask for a delete (<kit>/docs/action-hub.md "approvals/A-NNN"). It only asks: the owner decides on the hub. Take back one still pending (a superseded draft): `approvals withdraw <A-id> --from pm --if-version <V>` (approvals store no `from`, so the key is `pm`; V from `approvals --json`), which prints `WITHDRAWN <A-id>`; a decided or expired one is refused. Once approved, the author commits with `commit.py -m "<subject>" --model "<model name>" --owner-approval hub:<id> <path> ...` with the file still at its base; commit.py writes the approved content.
6. Skill edits: the owner writes a kit skill's new text on the hub, and the push `skill_edit <E-id> submitted` goes to the kit's coordinator, which has a worker commit it; the text is the owner's, so commit it unchanged and never write or edit one on the hub yourself (agents are refused). The worker: `python <kit>/tools/hub.py skill-edit show <E-id>` gives the skill, base blob and version V; `skill-edit show <E-id> --out <F>` writes the text byte for byte. In a worktree from main, when `git rev-parse main:content/skills/<name>/SKILL.md` is not the base blob, stop with `skill-edit fail <E-id> --why "the skill changed on main" --at main --checkout <worktree> --if-version <V>` (the owner re-applies it). Else copy F over `content/skills/<name>/SKILL.md` (only the source: commit.py renders the copies) and commit it with `python <kit>/tools/commit.py -C <worktree> -m "Skill <name>: owner edit" -b "Text by the owner, hub edit <E-id>" --model "<model name>" content/skills/<name>/SKILL.md`, then `skill-edit done <E-id> --branch <branch> --checkout <worktree> --if-version <V>` (the hub checks the branch's blob against the text). A commit that cannot be made: `skill-edit fail <E-id> --why "<W>" --if-version <V>`. The branch is reviewed and landed as any other (<kit>/docs/action-hub.md "skill_edits/E-NNN").
