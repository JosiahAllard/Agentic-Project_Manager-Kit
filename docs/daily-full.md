# daily_full

`tools/daily_full.py [-C DIR] [--plan | --summary] [--force] [--out DIR]` runs every non-manual gate step in full (each step's `daily_cmd` when it has one, else its `full_cmd`, else its `cmd`; docs/gate.md "Steps"), on `"daily_full".ref` (default `<remote>/<main branch>`), in a detached worktree of its own (default `<worktrees_dir>/daily-full`). Logic: `kitlib/dailyfull`.

- Opt-in: it refuses (exit 2) unless `.kit.json` "daily_full".enabled is true. The kit never schedules it. A repository that wants it daily registers the schedule itself.
- It moves only a clean linked worktree of its own. A worktree of `.` or the main checkout, a folder that is not a registered linked worktree, or a tree with uncommitted files is recorded red `infra` with the reason (for a dirty tree, the file names). Nothing is cleaned, reset or switched.
- One run at a time per tree. Before it fetches, a run takes the tree's lock (`kitlib/fs/treelock.py`), an OS byte-range lock on `<git common dir>/kit-tree-<name>-<hash>.lock`, and it holds the lock until its result is written, on every exit. A second run finds the lock held and exits 5 with `daily: busy: held by pid N since T`. It does not touch the tree and records nothing. The system drops the lock of a holder that exits or is killed, so the next run takes over and says `took over`.
- The fetch and switch come before the machine-lock booking, not inside it. `runner.gated` takes the planned steps and loads the hook checks before it books, and both come from the tree at the ref. Only a run holding the tree's lock moves the tree, so a run waiting for its slot never moves a tree another run is gating.
- Each run fetches, puts the worktree at the ref, and loads the gate from the ref's own `.kit.json`. All steps then run in one slot of `"daily_full".kind` (default `daily-full`) through `kitlib.gate.runner.gated`, waiting up to `"daily_full".max_wait` seconds. A failing step does not stop the run.
- Every run writes `<out>/<stamp>/result.json`, where `<out>` defaults to `<gate log dir>/daily`. The fields are `verdict`, which is green, red or skipped; `sha`; `steps`; `red`, which lists the failing step names plus `infra` when the run could not start; `skipped`, the steps that did not run; `error`; and, for a skip, `reason` and `cause`. A run in which no step ran (every one SKIP) is red `infra`, never green.
- Unchanged commit: after the fetch, if the latest run that ran (skips do not count) is green at the ref's commit, the run is a recorded skip with cause `unchanged`, prints `daily: SKIPPED (unchanged) - ...` and exits 0. The recorded results under `<out>` are the state; there is no other file. A red latest run, or a green one at another commit, runs. `--force` runs regardless. `--summary` shows these skips as `skipped (unchanged since the last green run)`, not as a problem.
- A lock refusal is a recorded skip, not a red. The cause is one of busy, timeout, lock-unavailable, reserved or hold.
- `--summary` prints the status lines from the recorded runs:
  - the last verdict, with its failing steps;
  - the skips in a row;
  - STALE, when the newest attempt is over `"daily_full".stale_hours` old.

  As a preflight report hook it is `daily_full:summary_lines`.
- Exit codes: 0 green or skipped, 1 a step red, 2 usage or off, 4 the tree or its gate could not be readied (recorded red), 5 another run holds the tree (nothing recorded). A lock usage refusal, such as an unknown kind, is exit 2 and recorded red.

## The schedule

The kit registers no task for it (above); the repository's owner does. A task whose program is `python.exe` is a console program started by a process that has no console, and Windows gives such a program a new console and shows its window (`kitlib/proc/job.py`, "No console window from a parent without a console"); for a task that runs as the signed-in user, that window is on the desktop. For no window, the task's program is `pythonw.exe` and its first argument the carrier, `tools/no_window.py`:

```powershell
$py = python -c "import os, sys; print(os.path.join(sys.base_prefix, 'pythonw.exe'))"
if (-not $py -or $py -match '\\WindowsApps\\' -or -not (Test-Path -LiteralPath $py)) { throw "no pythonw.exe outside WindowsApps: $py" }
Register-ScheduledTask -TaskName '<task name>' -Trigger (New-ScheduledTaskTrigger -Daily -At <HH:mm>) -Action (New-ScheduledTaskAction -Execute $py -Argument '"<kit>\tools\no_window.py" python "<kit>\tools\daily_full.py" -C "<main checkout>"' -WorkingDirectory '<main checkout>') -Settings (New-ScheduledTaskSettingsSet -StartWhenAvailable) -User $env:USERNAME -RunLevel Limited
```

A task that is already registered keeps its trigger and settings and gets only the new action:

```powershell
$py = python -c "import os, sys; print(os.path.join(sys.base_prefix, 'pythonw.exe'))"
if (-not $py -or $py -match '\\WindowsApps\\' -or -not (Test-Path -LiteralPath $py)) { throw "no pythonw.exe outside WindowsApps: $py" }
Set-ScheduledTask -TaskName '<task name>' -Action (New-ScheduledTaskAction -Execute $py -Argument '"<kit>\tools\no_window.py" python "<kit>\tools\daily_full.py" -C "<main checkout>"' -WorkingDirectory '<main checkout>')
```

- `tools/no_window.py PROGRAM [ARGS...]` starts PROGRAM, waits for it and exits with its exit code (`kitlib.proc.spawn.carry`). The code is PROGRAM's whole 32-bit one: 0 to 0x7FFFFFFF as it is, and a code above that, as a crash gives (0xC0000005), through `kitlib.proc.spawn.exit_code` as the negative number with the same bits (one that fits a C long, so it does not rest on how the interpreter converts a larger one), so the carrier ends with those bits and whoever started it reads 0xC0000005 again (`tests/proc/test_no_window.py` `CarrierTest.test_an_exit_code_above_the_signed_range_comes_back_whole` measures that with a real `pythonw.exe`). The task's last result is the code its program ended with, so it is `daily_full.py`'s; a crash shows there as the same eight hex digits (not measured in Task Scheduler itself: the test reads the code as the carrier's starter gets it). Its own exit codes: 2 when no PROGRAM is named, 127 when PROGRAM cannot be started. It prints one thing, `USAGE: pythonw no_window.py PROGRAM [ARGS...]` on stderr when no PROGRAM is named, and only when its starter gave it a stderr; a scheduled task gives none, so there it prints nothing. So that a start that fails is not silent, an exit of 127 and an exception out of the carry each append one JSON line to the kit's console incident log, `kit-console-incidents.log` in the kit's work temp folder, in the shape of the console incident lines (`kitlib.lock.detach.note_carrier_failure`: `{"time"` (UTC), `"how": "carrier-fail"`, `"pid"` (the carrier's), `"exe"` (PROGRAM's file name, never its arguments), `"why"}` (the exit code, or an exception's type only, since its message can echo the arguments); `KIT_CONSOLE_INCIDENT_LOG` names another file, which the tests use). When the work temp folder cannot be worked out, or the line cannot be written, there is no line, and the exit code or the exception is unchanged. A PROGRAM that itself exits 127 gets the line too: the exit code cannot tell the two apart.
- `python` as PROGRAM is the `python.exe` in the folder of the `pythonw.exe` that runs the carrier; any other PROGRAM is started as named.
- `pythonw.exe` has no console, so the carrier starts PROGRAM with `CREATE_NO_WINDOW`: a console with no window. Everything PROGRAM starts in turn shares that console, so the whole run opens none. Run from a console (`python tools/no_window.py ...`) it adds nothing and PROGRAM shares that console.
- `$py` is the `pythonw.exe` of the base install of the `python` the line runs (`sys.base_prefix`), never a path lookup: `Get-Command pythonw` gives the Microsoft Store or Python install manager alias under `WindowsApps` when that folder is first on `PATH`, and a task must not run that. The second line throws, so nothing is registered, when `$py` is empty, is under `WindowsApps` or is not a file (checked in a scratch script on 2026-10-14 against a `WindowsApps` path, a missing path and an empty one, with nothing registered; with `python` itself the install manager's alias under `WindowsApps`, the first line gave the base install's `pythonw.exe`). The kit's own task lines do the same in Python (`kitlib/launcher/pythonw.py`, used by `kitlib/worktree/task.py` and `kitlib/launcher/autostart.py`).
- The kit's own scheduled tasks use the same carrier: the worktree sweep (docs/worktree-remove.md "The scheduled task"), the agent temp sweep and the procwatch task (docs/machine-setup.md "Extras") and the launcher's sign-in task (docs/launcher.md "Autostart").

Every start in the kit's own code follows one rule, so a kit program run with no console (a hook under `pythonw.exe`, a task without the carrier) opens no window for what it starts: it goes through `kitlib.proc.spawn` (`run`, `call`, `popen`) or `kitlib.proc.job` `Job.start`, which add `CREATE_NO_WINDOW` only when the process has no console and the caller chose no console of its own, or it passes `creationflags=` itself. `tests/proc/test_spawn_sites.py` reads the source and fails on a start that does neither and has no row, with its reason, in that test's `EXEMPT` table.

The backstop for every other start in a process that has imported `kitlib` (a bare `subprocess` call, a `multiprocessing` child, a test): `import kitlib` installs `kitlib.proc.console`'s hook on `_winapi.CreateProcess`, which `subprocess` and `multiprocessing` both start through. The first start whose flags make no console choice, in a process with no console, first gives the process a console with no window (`AllocConsoleWithOptions` with its no-window mode; where Windows does not export it, attach to the console of a helper started with `CREATE_NO_WINDOW`). That child and every later one share it, so none opens a window. When no console can be had, each such start gets `CREATE_NO_WINDOW` instead. A start that names a console choice is passed on as it is, and after the first start the hook costs one check of a cached flag. The import loads no `ctypes`. Each console it makes is logged as one JSON line (time, how, pid, exe, argv, the child's command line, the parent's pid and exe; both command lines redacted by `kitlib.proc.console.redact_command`: the program and its first six words, each cut to 120 characters, with secrets masked, erring toward masking: the values of token, key and password flags (any name holding `pass` or `pw`, but for a few words such as `-PassThru` and `/passive`) and of `-p`, `-P`, `/p` and a glued `-PVALUE` once a word starting `-u` or `--user` (or `sshpass`) came before them, and of `/RP`; every glued `-pVALUE`; all after the first `:` of a user flag's value (`-u`, `-sSu`, `-uuser:password`, `--proxy-user`, `/u`; `user:***`, `DOMAIN\user:***`, `https:***`), or the whole value when it ends at that `:`, but for a drive path (`python -u` and a script); the value gets every other mask too, and is never a following flag; secret `name=value`, `name = value`, `"name": value`, `'name': value` and `{name: value` pairs within a word or across words (a quoted value up to its closing quote); the word after `Bearer` or `Basic`; a URL's user info (to the last `@` when a `:` follows `://`, else the authority's); and token-shaped words. Each mask is linear in its word; it never raises) in `kit-console-incidents.log` in the kit temp folder (docs/test-tools.md "Temp folders"), so a kit process that ran with no console can be found; a log that cannot be written never stops the start. `tests/__init__.py` imports `kitlib` first, so every test process has the hook. A console with no window takes no typed Ctrl+C, and no kit code sends one (`GenerateConsoleCtrlEvent`, `os.kill`), but a child on it could: a `pythonw.exe` process given a console this way would be ended at once by it (exit `0xC000013A`; Python's SIGINT handling does not run under pythonw), where before it had no console and got none. So the hook also registers a console control handler that takes Ctrl+C and Ctrl+Break for that process only; its children on the console get them as before.

Tests: `tests/proc/test_spawn.py` (the flags and the carrier's logic), `tests/proc/test_no_window.py` (`SpawnWindowTest` and `CarrierTest` start a real `pythonw.exe` and read the child's `GetConsoleWindow()`), `tests/proc/test_spawn_sites.py`, `tests/proc/test_console.py` (the hook: a real `pythonw.exe` parent starts children by bare `subprocess.run`, `Popen`, `check_output` and `multiprocessing`, by both ways of getting a console, with console choices of its own, from eight threads at once, when started with no std handles, and with a child sending Ctrl+C and Ctrl+Break to the console).

Not ported: per-piece red mapping and the hold after two reds, a custom step list, deferred steps, and owner-reservation reads beyond the lock's own exit 11. Tests: `tests/dailyfull`.
