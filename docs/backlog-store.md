# Backlog store (design)

## Goal

A backlog add, edit, pull or close is one tool call that takes seconds. No work branch, gate, review, lander, batch or 18:00 wait.

## Where records live

- Each repo keeps its own backlog, in its own repo: no extra repo, nothing shared between projects.
- Records are `backlog/<ID>.md` on the ref `refs/backlog/main`.
- The ref has no shared history with main. It never merges, rebases or fast-forwards with main; the two move independently.
- `.kit.json` `"backlog": {"store": "ref" | "branch" | "main"}`, default `ref`, which a write must name: the default alone is read-only (docs/backlog.md "Stores").
  - `ref`: hidden from branch lists and PR menus, not fetched by a default clone (the tool adds the fetch refspec, only once a fetch found the store on the remote: kitlib/backlog/store.py `RefBackend.load`; a refspec for a ref the remote lacks fails every plain `git fetch`).
  - `branch`: the same on a visible `backlog` branch, browsable on GitHub.
  - `main`: records are files under `docs/backlog` (or the folder named) in the checkout, written in a linked worktree and carried to main by landings, or committed on the PM data branch (docs/backlog.md "Stores").

## Write path (kitlib/backlog/store.py)

One call, for a `ref` or `branch` store:
1. Fetch the store ref (no checkout; the working tree and main are never touched).
2. Plan the change against the fetched store and validate it (schema, ids, scope, role gates).
3. Build the new tree with a temporary index (`GIT_INDEX_FILE`), `commit-tree` on the fetched tip.
4. Push with `--force-with-lease=<ref>:<fetched tip>`, a compare-and-swap. On a lost race: refetch, re-plan, retry (bounded). A repo with no remote uses `update-ref` with the old value.

The commit message names the verb, id, session and any ruling, so `git log refs/backlog/main` is the audit trail; undo is a revert on the ref. The `main` backend's write path is in docs/backlog.md "Stores". Writes to a `ref` or `branch` store never touch a checkout; the `main` backend refuses in a main checkout.

## Reads

`next`, `show`, `list`, `check`, the guards and the hub's backlog view (`kitlib.hubbacklog`, `kitlib.hubsite.backlog`) read the store after a fetch. Checks that need code (scope paths exist) read main's tree directly; nothing is copied between the two.

## Lifecycle changes

- `pull` and `release` write at once, so claims are visible to every coordinator immediately. `pull` records the branch: `--as <branch>`, else the branch checked out in `-C`. A pull that would record the configured main branch (made in the main checkout, or `--as <main>`) is refused, and in the PM data worktree, whose configured main is its data branch, the code repository's main too (the main checkout's configured mains, `main` and `master` when that cannot be read; pull_branch.py `code_mains`), after the record's own refusals, with how to pull it instead (`--as <branch>` first, with the record's own `session:` as `--session` when it has one and no `--session` when it has none, then from the branch's worktree; pull_branch.py `refusal`): the main branch never lands, so no landing would close the record.
- Taking over a dead pull: `pull` of a pulled record refuses "already in flight", except when the record's `session:` is the caller's `--session` and the pull is dead by the test `next` uses for its "DEAD PULL" line (kitlib/backlog/offer.py `in_flight_split`: git answered, and no local branch, remote-tracking branch or worktree is named by `pulled_by`). Then it moves the pull to the caller's branch with no `release --reason`: `pulled_by` and `pulled_at` are rewritten, pre-emption lines are kept, and the output says "took over a dead pull from <old branch>", with the "warning: scope collides with ..." lines a pre-empting pull prints for live pulls. It takes no `--reason` or `--blocker`. A takeover whose scope collides with a live pull on another branch is the `pull-collision` row, as a pull is, refused unless the caller's role may take it (docs/backlog.md "Owner gates"). Another session, a record with no `session:`, a live `pulled_by` or a git probe that fails still refuses. A `pulled_by` that already landed (a merge with the subject `Merge <branch>` or `Merge <branch>: ...`, as kitlib/gate/land.py writes it, on the configured main branch, committed on or after the `pulled_at` day so an older landing of a reused branch name does not count; plan.py `landing_merge`) is refused with "close the record"; a history git cannot read fails.
- Closing at landing: after `gate.py land` verifies the push, it closes every record still pulled by the landed branch ("landed <merge sha>"), unless a commit of the branch carries a `Part-of: <ID>` line: then the landing is one part of a record, and it closes only the records its `Closes:` lines name and releases every other record the branch holds pulled (below). A failure prints a WARNING with the command; the landing stands. Builders `release` what they did not finish. `backlog.py landable` says ahead of the landing which records it will close and which it will release (docs/backlog.md "Commands").
  - A branch commit may name records on its own line (`Closes: <ID>[, <ID>...]`) anywhere in its message, not only in git's trailer block, since tools/commit.py writes the attribution as a last paragraph of its own: the line starts with `Closes:` (that case only), each following line that starts with a space or tab continues its value, and the first word of each comma-separated value is the id. Prose (`closes D2`, or `Closes: D2` inside a sentence) names nothing (at_landing `closes_values`, `closes_trailers`). The landing closes each one that is pulled, whoever pulled it, and its `closed` line says it was named by the trailer and who had pulled it. Read from `<tip> --not <the main it merged onto>` for each branch of a batch, so a trailer already on main closes nothing. A record closed this way while a live branch holds it that is neither main (the code repository's, in the PM data store too) nor a branch of the same batch (a local, remote-tracking or worktree branch by its `pulled_by`: offer.py `live_branches`; a probe that fails counts as live) also prints a WARNING to tell that branch's builder. A named record that is not pulled, or one the store refuses to close (owner-held), is a WARNING with the `close` command; the ids no store holds are one NOTE line (a typo, or a case that differs from the file name), printed only when every store taking part was read; trailers git cannot read are a WARNING and the branch's own pulls still close. In the PM data branch's folder store (below), for a named record: after a close that was refused and put back, the WARNING gives the close command while anyone still holds the record pulled, and names that holder (`at_landing._after_put_back`); a close left uncommitted, or committed with a stale index, still prints the WARNING to tell a live holder's builder (`_close_in`).
  - The implicit default store (`refs/backlog/main` while `.kit.json` names no `"backlog".store`, which refuses every write: store.py `default_store_refusal`) is only read at a landing: the remote's ref, fetched into the local `refs/backlog/main` as every fetching read of a ref store is, or, when the remote has none, the local ref as it is, with no fetch (at_landing `_close_in`, `_read_default`). Nothing is closed or released there. A record it holds that a `Closes:` line names, or that the branch holds pulled, and that no other store read holds (the PM data store, below) is one WARNING per record: it is stranded there, so add it to the live store, or, if `refs/backlog/main` is the live store, name it in `.kit.json` (`"backlog": {"store": "ref"}`) and close it with the printed command (`_Stranded.warning`). Such an id is not in the typo NOTE. No such WARNING is printed when a store taking part was not read, and a repository whose `.kit.json` names a store never reads the default ref. `backlog.py check` on the default store adds a `default store` line with one WARN per record when it holds any; it is never red (check.py `check_default_store`). When the remote has no `refs/backlog/main` and the local ref holds a store, the fetching read refuses (it would start a new store without those records), so `check` reads the local ref instead and says so (check.py `load_for_check`).
  - A branch that lands one part of a record a later branch finishes writes `Part-of: <ID>[, <ID>...]` on its own line, read by the `Closes:` line's rules (`trailer_values` with `PART_KEY`), from the same `<tip> --not <base>` for each branch of a batch, so a `Part-of:` line already on main, or in another branch of the batch, changes nothing. Any such line, even one whose value holds no plain id, makes the landing one part: each record the branch holds pulled that no `Closes:` line names is released, not closed: `state: open`, its pull and pre-emption lines cleared (`plan.py` `plan_release`, as the branch itself, so no liveness probe), so `next` offers it again. The reason is `part landed <merge sha> (a Part-of line of <branch>); the rest is not done`, the store commit's subject `releases <ID>: <reason>` and its line `released <ID> in the backlog store ...` (at_landing `release_reason`, `_release_plan`). So a mistyped `Part-of:` id releases rather than closes. A record another branch holds is never released: a `Part-of:` id the branch holds pulled in no store read (a typo, or another branch's record) is one NOTE line, nothing written, printed only when every store taking part was read; an id both a `Closes:` and a `Part-of:` line name is closed, never released, with a NOTE line. Each NOTE says only what the landing did (at_landing `_Seen`). Since the part's landing leaves the record open and unpulled, the branch that finishes it pulls it again before it lands with `Closes: <ID>`; a `Closes:` line naming a record that is not pulled closes nothing and is a WARNING (above). A release goes through the same per-store steps as a close (`_close_in`: the clean check, the index lock, put back when overtaken, uncommitted, stale index), and its WARNINGs say released and give `backlog.py --as <branch> release <ID> --reason "<reason>"` in place of the close command (`_Act`, `_after_put_back`); a record the branch no longer holds pulled is left as it is. No `Part-of:` line: exactly the closes above. When the lines cannot be read, `Part-of:` lines are not read either and the branch's own pulls close, as the WARNING says (`close_landed`).
  - kitlib/backlog/at_landing.py `close_landed` runs after the lock is released (docs/gate.md "Landing", step 9). Records are looked up by file name, in two stores (`_close_in` for each):
    - The configured store, when it is a `ref` or `branch` store: one store commit per record. A configured `main` store, or a remote with no store, gets nothing written and no refspec added.
    - The PM data branch's store (`pm_data_store`: the store that worktree's own config names, in the worktree that has the PM data branch checked out, unless it is the configured store or the main checkout itself). A `main` (folder) store there: the record file is deleted in that worktree and the deletion is committed on the PM data branch, as every write there is (docs/backlog.md "Stores"; `MainBackend._commit`), and the close line names the commit. The close opens that store with `clean` (`open_backend(..., clean=True)`): before it writes anything, every path the close would write (the record, and each record it unblocks) must match HEAD in that worktree and its index (`MainBackend._require_clean`, a `git status` read with `--no-optional-locks`). One that does not (a hand edit, a staged change, or a record file never committed there) stops that record's close with nothing written (`errors.Dirty`): a WARNING that names the paths, the command to compare them with HEAD first (`git -C "<worktree>" diff HEAD -- "<path>"...`, or `git -C "<worktree>" status --short -- "<path>"...` when one is not in HEAD, which a diff would not show), and the close command to run once that change is committed or put back; the landing's exit code is unchanged. When only that worktree's index differs (its files hold HEAD's content: an `IndexStale` left unrepaired, or HEAD moved by plumbing), the WARNING gives the index repair (`errors.Dirty.repair`, `git -C "<worktree>" reset -q -- "<path>"...`) in place of the compare, then the close command. A `backlog.py` write there does not use `clean`, so it still writes over such a change. The close, like every write there, holds git's index lock in that worktree from before it reads HEAD's commit or checks the files until its index update (`MainBackend._lock_index`, docs/backlog.md "Stores"), so a `git commit` there in the middle of it fails instead of committing an index that would revert the close. When another git command holds that lock for `INDEX_WAIT` (2 s), the close stops with nothing written (`errors.Busy`): a WARNING that says it was not closed, with the error, which names the lock file, and the close command; the landing's exit code is unchanged. A close whose commit fails for any other reason leaves the file deleted and uncommitted, and is a WARNING whose command is `catch-up --apply` with every path the close wrote, each in double quotes, the records it unblocked included (`errors.Uncommitted.paths`). A close stopped because another commit changed one of its paths on HEAD (`errors.Overtaken`) puts each file it wrote back (`MainBackend._put_back`: a path that commit changed to HEAD's content, any other to what it held before the close) and is a WARNING that says the close was refused and, from the store read again (`at_landing._after_put_back`), one of five things: the record is still pulled by the branch (for a record a `Closes:` line names, by anyone, naming the holder), with the close command; the store no longer holds it (that commit closed or removed it), with no command; it is in another state and no longer pulled by the branch (for a named record, by anyone), with the `show` command and no close command; its file cannot be read as that commit left it, with the `show` command; or the store could not be read again (a `Refusal` or an `OSError`), with the `show` command. For a file left (`Overtaken.left`) the WARNING says not to commit over that commit and gives `git -C "<worktree>" diff HEAD -- "<path>"...` to compare first. None gives a ready-made `catch-up --apply` command. A close committed with that worktree's index left stale (its update, or the move of the updated copy over it, failed) is a WARNING that says it was closed and gives the `git reset -q -- "<path>"...` repair (`git reset -q` with no paths when it has no index file), never a close command (`errors.IndexStale`). A `branch` store there (`ref` is refused for the data branch, docs/pm-data-branch.md "Layout"): one store commit per record, as above; a remote with no store gets nothing written.
  - A record the branch no longer holds (one a trailer names: that is no longer pulled) is left as it is. An owner-held record is the `close-held` row, which a landing never takes (it runs no role check), so it is a WARNING whose command is the plain `close ID --reason "landed <sha>"`, for the owner or the PM to run.
- `close` and `retire` stay as verbs for work that never lands.

## Merge safety

- Plain git refuses unrelated histories; GitHub cannot open a PR between them.
- Records sit under `backlog/`, so even a forced merge overwrites nothing.
- `gate.py land` refuses a branch whose history contains the store's root commit (kitlib/backlog/at_landing.py `ancestry_refusal`, the last locked check). It reads the store's tip from the remote (`ls-remote`, objects fetched with an empty `--refmap`, so no ref moves) and the local copy. A store it cannot read, remote or local, refuses the landing.

## Guards and hooks

The kit's push_block skips its gate-OK check for the store ref and for any non-main branch; its leak and secrets checks run on every pushed ref (kitlib/guard/prepush.py).

## Migration

A repo moves to a ref or branch store at go-live (docs/go-live.md): land or port every in-flight records branch first; then one normal branch deletes `docs/backlog`, sets `.kit.json` `backlog.store` and updates hooks. Old record history stays in main's git log. A record not written since its store's migration ages from that commit (docs/backlog.md `stale`).

## Hub filing

The Action Hub files a story at once, unpriced, through `add` with a `review:` mark, which a coordinator clears after reading (docs/backlog.md "Records"). Its backlog writes go through `kitlib/hubsite/recordwrite.py` with the role check passed (`role_checked`). Its timed job `unblock-conditions` writes there too: a hold whose `until` condition is met is unblocked from that one member in one store commit under `Session: hub-condition`, reason `condition met: <condition>` (`recordwrite.condition_met`; docs/backlog.md "block --until"). Like the owner's hub writes, it adds no audit log line, and the audit check counts it as by design.

## Hub store-commits job

A `backlog.py` write in the PM data worktree commits its own record paths (docs/backlog.md "Stores", `MainBackend._commit`). What is left uncommitted there is a write whose commit failed (`errors.Uncommitted`) or a hand edit. The hub server's timed job `store-commits` (`kitlib/hubjobs/store_commits.py`, every 3600 s; docs/action-hub.md "Timed jobs") commits those once an hour, in place of the PM's hand commit:

- It commits only the record paths `MainBackend.pending` lists, through `MainBackend.commit_paths`, which is the `catch-up --apply` path. That path holds the store's index lock (`_IndexLock`) from the file read to the index update, commits those literal paths by compare-and-swap, and stages nothing else. A held lock (`errors.Busy`) is a skip, and the job retries next hour.
- It leaves out any record that may be half-written. A file changed in the last 60 s waits for a later pass. A file that does not parse as a record, or whose `id:` is not its file name, is left out, and the pass fails naming it. A file there that is not a record is never committed.
- It never pushes. The hub's git sync (`kitlib/hubsite/gitsync.py`) pushes the PM data branch whenever it differs from the remote, these commits included, and a second pusher of that ref would race it.
- Any other store error is a job failure, shown in hub health, and the third failure in a row pushes `failing` to the PM. A commit that fails with Overtaken, Uncommitted or IndexStale also stops the job at once, on that first failure: every later pass fails (`StoreStuck`) and commits nothing while one of that failure's paths is still uncommitted. A bare `Failure` (git did not answer) does not stop it; the next pass tries again.
