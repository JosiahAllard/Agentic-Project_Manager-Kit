# Launcher

`tools/launch.py` starts, hands off and stops the PM's long-running Claude sessions, each in its own minimized window. Logic: `kitlib/launcher` (no argparse, print or exit); the machine-facing calls (process list, registry with `REG_EXPAND_SZ` values expanded as .NET did, window, stopping a process) sit in `kitlib/launcher/host.py` so tests fake them (`tests/launcher/fakes.py`).

```
launch.py start (--repo NAME | --repo-path DIR | --session KEY) (--account N | --org N) [--agent A | --no-agent] [--brief F] [--prompt P] [--name N] [--predecessor N] [--model M] [--effort E] [--autocompact T] [--what-if] [--home-worktree] [--no-remote-control]
launch.py deep --repo-path DIR (--brief FILE | --brief-text TEXT) --requester NAME --slug SLUG [--account N|auto] [--model M] [--effort E] [--autocompact T] [--force] [--plan] [--home-worktree]
launch.py consultant --repo-path DIR [--repo SLUG] [--account N|auto] [--model M] [--effort E] [--autocompact T] [--notes-path P] [--force] [--replace] [--plan] [--home-worktree]
launch.py homes (--repo NAME | --repo-path DIR) [--remove NAME] [--what-if]
launch.py stop --name NAME [--successor NAME] [--pid N] [--dry-run]
launch.py handoff (--session KEY | --all) [--account N|auto] [--recycle] [--stem NEW] [--state FILE] [--what-if] [--home-worktree]
launch.py pick-account [--limit 95] [--explain]
launch.py usage
launch.py after-reboot [--test] [--dry-run]
launch.py pm-relaunch --name NEW
launch.py install-autostart [--what-if]          (retired: refuses)
```

Exit codes: 0 done; 1 refused or failed (the reason on stderr); 2 a stop refused (`REFUSED: ...` on stdout) or a usage error; 130 Ctrl+C.

## Settings

The machine config (docs/kit-json.md "Machine config keys"), key `launcher` (checked by `kitlib/launcher/settings.py`; an unknown key or a relative path is a config error naming the key):

```json
{"launcher": {
  "state_dir": "<pm repo>/launcher",
  "repos": {"app": "<app repo>"},
  "accounts": {"1": ["~/.claude"], "2": ["<second config dir>"]},
  "orgs": {"1": "~/.claude-org1"},
  "coordinator_agent": "coordinator"
}}
```

| Key | Meaning | Unset |
|---|---|---|
| `state_dir` | absolute folder of the state files and logs | an error when a command needs it |
| `repos` | name: absolute repo folder, for `--repo` and a sessions.json `repo` | `--repo` refused; `--repo-path` works |
| `accounts` | `"<n>"`: config folders, first choice first; absolute or `~/...` | one account, `1`, in `~/.claude` |
| `orgs` | `"<n>"`: an organization sign-in's config folder, for `--org n` | `--org` refused |
| `coordinator_agent` | the agent file a coordinator runs as | `coordinator` |
| `pm_resume_beside_desktop` | `true`: `after-reboot` resumes the PM session even while the desktop app or an unnamed session runs | `false`: it skips |
| `terminal` | Linux: the terminal command a window opens in, a list of words, with `/bin/bash -c <script>` appended (`["xterm", "-e"]`; "The window") | a detached tmux session |

`repos` keys match case-sensitively and must equal the `repo` values in sessions.json.

The default folder `~/.claude` launches with `CLAUDE_CONFIG_DIR` removed, never set to it: setting it moves where Claude keeps `.claude.json`.

## Accounts

An account is signed in when one of its folders holds `.credentials.json`; a launch uses the first such folder, and an account with none is refused. An org is signed in when its `.claude.json` names an `oauthAccount`. Each session's status line writes `usage-status.json` into its account folder.

`pick-account` chooses among signed-in accounts the one under `--limit`% (default 95) of its seven-day window whose week resets soonest, so the allowance that expires first is used first; when every account is over, the soonest reset anyway. A passed reset reads 0%. `deep` and `consultant` with `--account auto` pick the same way, then refuse an account at or over 90% of either window unless `--force`: the last 10% is the PM's headroom.

## Usage

`launch.py usage` prints one line per account (`account N: five_hour=X% (resets ddd HH:mm)  seven_day=Y% (...)  [updated M min ago]`, or `no usage file`), `current account: N` for the file written in the last 15 minutes, and Codex's weekly window from its newest session log. A window whose reset has passed reads `reset`; one the file does not give (null, no reset time, no percentage) reads `?`. `kitlib/pmwatch` parses these lines; `pm_watch.py` reads them in-process (docs/pm-watch.md).

A usage file refreshes only while a session on that account runs, so a reading can be hours or days old. A stale or missing reading is shown as such, never as 0%: `kitlib.pmwatch.parse_usage` keeps `?` and `no usage file` as unknown (None, `missing` for no file), gives each reading its `age` in minutes, and marks it `stale` when it is older than `STALE_MINUTES` (60 minutes) or of unknown age; the hub page uses the same 60. Percentages are rounded half to even (`accounts.whole`), so 94.6 reads as 95 where it used to read as 94. The watcher skips an unknown window in its band and reset events and keeps the last known figure. The hub's Usage tab dates each account by its own reading, not by when the hub read it, shows `?` for unknown and marks stale and missing accounts. `pick-account --explain` prints `week unknown` for an account with no seven-day reading; `pick` still counts it as under the limit, resetting a week from now.

## Lookup

A launched session is a `claude.exe` that is not the Store app (under `WindowsApps`); its name is the `--remote-control` argument, matched exactly as a whole token (`x-a1` never matches `x-a1-r2`). `kitlib/launcher/lookup.py` reuses `kitlib.pmstart`'s parser. A session launched with `start --no-remote-control` (no `--remote-control` on its command line; the flag exists to measure what Remote Control costs, and `--session` refuses it) is found by its `-n` argument instead; `--remote-control` wins when both are present, and `stop` accepts either in the window's script. Nothing without one of them has a name (tests/launcher/test_lookup_stop.py `RcOff`).

## The window

`kitlib/launcher/window.py` `script()` writes the window's PowerShell: the title (the session name), the user's registry environment (but Path, TEMP, TMP), every inherited `CLAUDE*`/`ANTHROPIC*` variable cleared, then `CLAUDE_CODE_FORCE_SESSION_PERSISTENCE=1`, the session mark, `CLAUDE_CONFIG_DIR`, when the launcher sees `AGENT_TEMP`, that variable set again with TEMP/TMP pointed at it (the PM resume too), the folder, and the `claude` command with `--permission-mode auto --remote-control '<name>' -n '<name>'` (after `--add-dir '<main checkout>'` when the session starts in its home worktree, "The home worktree"). It opens minimized and unfocused through `conhost.exe powershell.exe -NoExit -EncodedCommand`.

On Linux (`kitlib.platform.NAME`) `script()` is `kitlib/launcher/linuxwin.py`'s bash, one step a line in the same order: the title, `CLAUDE*`/`ANTHROPIC*` unset, the persistence variable, `export PM_KIT_ROLE=...` and `PM_KIT_SESSION_NAME=...`, `CLAUDE_CONFIG_DIR` (unset for the default folder), `AGENT_TEMP` made and set with `TMPDIR`, `TEMP` and `TMP`, `cd -- '<folder>' && claude ...`, then `exec /bin/bash -i` so the window stays open; every value is single-quoted. It runs as `/bin/bash -c <script>` in a new detached tmux session, `tmux new-session -d -s <name>` with the arguments as a list (tmux 3.0 or later; `tmux attach -t <name>` shows it), or, when `launcher.terminal` is set, as that command with `/bin/bash -c <script>` appended, in its own session. The tmux name is the session name with anything but `A-Za-z0-9_-` made `_`; a name tmux already has, two names made the same tmux name among them, is refused and nothing is started or ended. A session name holding whitespace, a quote or a backslash is refused on Linux, at `start` (a name made from a folder such as `My Project` too) and at `stop`: `/proc` joins a process's arguments with spaces and keeps no quoting, so `my project-a1` would read as `my`. Known limits on Linux: there is no registry environment step, so the session has the tmux server's (or the terminal's) environment plus the exports; and if Claude Code sets `process.title`, `/proc/<pid>/cmdline` loses `--remote-control`, so lookup and `stop` cannot find the session (`tests/launcher/test_linux_live.py` `ProcessTitle`, the first check on a Linux machine, with `PM_KIT_LIVE_CLAUDE=1`). Tests: tests/launcher/test_window_linux.py.

Every window sets `PM_KIT_ROLE` (docs/guard.md "Session mark") and `PM_KIT_SESSION_NAME`; `script()` refuses an empty role, since an unmarked session counts as the owner's.

| Session kind | `PM_KIT_ROLE` |
|---|---|
| `start` with the coordinator agent | `coordinator` |
| `deep` | `deep-worker` |
| `consultant` | `consultant` |
| `start --no-agent`, a plain sessions.json entry, `after-reboot --test` | `plain` |
| the PM session `after-reboot` resumes | `pm` |
| `start --agent <other>` | the agent's own name |

An agent name (`--agent`, `coordinator_agent`, a sessions.json `agent`) may carry the kit plugin's prefix, `<plugin>:<name>` (`kitlib.agentname.PREFIX`; docs/guard.md "Agent names"); `window.AGENT` and `settings.check` accept it and no other colon. `role_for` compares the names without it, so `<plugin>:coordinator` is the coordinator, and the mark never carries it. The default session name (below) and the `ROLE_AUTOCOMPACT` lookup use the name without it too. The plugin registers its agents only under the prefix, so the launcher passes a bare kit agent name (`start.KIT_AGENTS`, the roles in `content/roles/`, rendered as `hosts/claude/shell/agents/`) to `--agent` as `pm-kit:<name>` (`start.run_as`): the default `coordinator` starts `--agent pm-kit:coordinator`. A renamed agent's former name (`start.AGENT_ALIASES`: `opus-worker`, now `senior-worker`) starts as its new one. A prefixed name and any other name (a repo's own agent) pass as given (tests/launcher/test_start.py). There is no bare fallback: a configured `coordinator_agent` of `coordinator` is qualified too, so a repo's own file named after a kit agent is never started by the launcher, and on an account without the plugin the only ways round it are `start --no-agent` or an agent name that is not a kit agent's.

Only the launcher's PM resume carries the `pm` mark; no settings file sets `PM_KIT_ROLE`, so a PM session opened by hand or in the desktop app is unmarked. The consultant is not marked `coordinator`: it never dispatches or lands, and the coordinator start hook should not fire for it; under the guard it is held like any non-owner session.

## Start

`start` opens one session in `--repo`'s folder (or `--repo-path`) on `--account` or `--org`. The default name is `<repo>-<agent>-a<N>` (`<repo>-session-a<N>` with `--no-agent`). `--brief` makes the first message read that brief first; `--predecessor` names the session this one succeeds. `--session KEY` starts a sessions.json entry with its repo, agent and brief, under the entry's recorded `name` (a recycle's `<stem>-a<N>-r<k>` too) on its own account, or `<stem>-a<N>` on another `--account`; `--account` there is a number, `current` (the account this process runs on: `CLAUDE_CONFIG_DIR`, or `~/.claude` when unset, matched against `launcher.accounts`; when no account lists the folder it picks like `pick-account` and says "current account not identified; picked N") or `auto` (`pick-account`'s choice); with none signed in it is refused (`accounts.resolve_current`, tests `tests/launcher/test_start_current.py`); it refuses while any session of that stem runs, and refuses the flags the entry sets (`--org`, `--brief`, `--name`, `--agent`, `--no-agent`, `--model`, `--effort`, `--autocompact`, `--predecessor`). Every `start` (a coordinator, another agent or a plain session, and so every hand-off and after-reboot start) passes `--autocompact 200000` unless `--autocompact` says otherwise (`kitlib.launcher.start.DEFAULT_AUTOCOMPACT`; 0 leaves the CLI's own window); the owner's per-role compact windows are 200k for coordinators and other launched sessions, 350k for the consultant, 500k for a deep-worker; the light subagent roles carry their own 170k ceiling in their agent files (docs/content.md "Role front matter", `compact`). A sessions.json entry whose agent is `consultant` or `deep-worker` starts with that role's window, 350k or 500k (`start.ROLE_AUTOCOMPACT`), on `--session`, hand-off and after-reboot alike. The PM resume and `autostart-test` pass none.

`deep` starts `deep-<slug>` as the `pm-kit:deep-worker` agent (model `opus[1m]`, effort xhigh, auto-compact 500k), reporting to `--requester`; `--brief-text` is written to `<AGENT_TEMP or TEMP>/deep-briefs/` and removed again if the launch fails. `consultant` starts `consultant-<repo>` (auto-compact 100k..500k, default 350k), one per repo unless `--replace`; it warns when the repo has no `docs/conventions-digest.md` or git does not ignore a notes file given inside the repo. Both refuse a name already running, and print the `stop` line to use afterwards. `--what-if`/`--plan` print the window script and start nothing.

The consultant's notes file is `<agent temp>/<repo>-consultant/notes.md` unless `--notes-path` names another (`start.consultant_notes_path`; the agent temp folder is `AGENT_TEMP`, else `TEMP`, else the home folder, `start.agent_temp`), outside the repository, so a consultant in a home worktree can write it. The agent-temp sweep never removes a `<name>-consultant` or `<name>-coordinator` folder (`optional/agenttemp/agent_temp_sweep.py` `BUILT_IN_KEEP`). The old default, `docs/ops/consultant-notes.local.md` in the repo, is never changed or deleted: when `--notes-path` is left out, the old file exists and the new one does not, the launcher copies it to the new path just before the window opens ("Copied the old notes file ..."; with `--plan` "Would copy ...", nothing written), and removes that copy again if the launch then fails; when both exist it copies nothing and warns that the old file is no longer read. With `--replace` beside a running consultant that still writes the old file, a warning says that what it writes after the copy stays in the old file (`start._copy_old_notes`; tests/launcher/test_consultant_notes.py). The old file can be deleted by hand once the new one has what it needs.

`--home-worktree` (parsed on `start`, `deep`, `consultant` and `handoff`; off by default, so without it every session starts in its repo folder as before) starts a deep-worker or consultant session in its home worktree instead; any other agent session is refused ("The home worktree").

## The home worktree

A session started in a repository's main checkout resolves every relative path there: a .NET or other relative write the guard cannot place (docs/guard.md), and every subagent it dispatches, which starts in the session's folder (Claude Code docs, page sub-agents, section "Write subagent files"). With `--home-worktree` a deep-worker or consultant session whose folder is a main checkout starts instead in `<main>/<worktrees folder>/home-<name>`, where the worktrees folder is the default host's `worktrees_directory` in `hosts.json` (`kitlib/launcher/home.py` `folder()`, read when a home is wanted and never at import, so `stop` and `after-reboot` run with a broken `hosts.json`; a launch that wants a home and cannot read it is refused with "--home-worktree: ... nothing was started.", not a traceback):

- Deep-worker and consultant sessions only (`start.HOME_ROLES`): a session started in a linked worktree may write only that worktree and temp (docs/guard.md "Write jail"). A consultant's notes file is in agent temp ("Start"); a `--notes-path` inside the main checkout is refused with `--home-worktree` before anything starts ("the notes file ... is in the main checkout ..."). A coordinator's state note is not in the main checkout (it is `<agent temp>/<repo>-coordinator/state-<session>.md`), so the note is not why a coordinator is refused: only a deep-worker or consultant is given a home, so `start` with any other agent (the coordinator agent too) and a `handoff` whose successor is not a deep-worker or consultant (`--all`: any one of them) are refused with `start.HOME_REFUSED` before anything starts; a plain session (`--no-agent`) keeps its folder.
- `<name>` is the full session name, lowercased with anything but `a-z0-9._-` made `-` (`home.home_path`): one home per session name, so `deep-<slug>` gets `home-deep-<slug>`, and a successor under a new name (`-a<N>`, `-r<k>`) gets its own home, never its predecessor's. Homes are removed only by `launch.py homes --remove` ("Listing and removing homes"), so they accumulate, one per name started with the flag.
- It is a linked worktree of the same repository, detached at the main checkout's HEAD and held with `git worktree lock` (reason `launcher home worktree of home-<name>: ...`). `home.ensure` makes it when missing, locks it when unlocked, and moves it to the main checkout's HEAD only when `git status` shows nothing uncommitted or untracked; a dirty home is named in a warning and left as it is (a stray write may have landed there), and a failed move is a warning. Refused, nothing started: the folder exists but is not a worktree of this repository, is registered with no folder, or is on a branch (a work branch, not a home).
- A home is never moved under a running session: before anything is made, a running session whose home path is this one's is refused (`start.home_folder`, "already running ... in its home worktree"); the paths are compared, not the names, so `Deep-X` and `deep-x-` are refused while `deep-x` runs, so `home.ensure` moves only a home whose session is not running. Two launches of one name at the same moment are not locked against each other: the second either fails on git's refusal of its `worktree add`, whose message says to wait for the other launch, or finds the home already at HEAD and leaves it.
- The window `Set-Location`s the home and passes `--add-dir '<main checkout>'`, so file tools may read the main checkout by absolute path (an added directory grants file access, not configuration: Claude Code docs, page permissions, section "Additional directories grant file access, not configuration"); writes there are still refused by the guard's write jail, so a deep-worker's branch work goes in its own worktree. The first message ends with `start.HOME_NOTE`, which names both folders and says not to write in the home.
- The tracked `CLAUDE.md`, `AGENTS.md` and `.claude/` files are in the worktree at the same commit, so the session loads the same instructions (Claude Code docs, page memory, section "How CLAUDE.md files load"); auto memory is keyed by the git repository, so worktrees of one repository share it (the same page, section "Auto memory"). The untracked `.claude/settings.local.json` is not in the worktree: when the main checkout has one the launcher warns that the session runs without it. Transcripts are stored per start folder, so a session started in its home resumes from there (Claude Code docs, page sessions, sections "Where transcripts are stored" and "Resume by session ID or name").
- Refused before any window and before any folder is made in the main checkout: git cannot place the folder (`repo.classify` UNKNOWN), or git does not ignore the home's path (an untracked folder in the main checkout stops a landing; the kit's own `.gitignore` ignores `.claude/worktrees/`). git answers the ignore check for a path that does not exist yet (tests/launcher/test_home.py `RealHome`), so it runs first. A folder that is already a linked worktree, or outside git, is used as given, with a line saying so. `--what-if`/`--plan` create nothing and say what would be made or moved.

Nothing else removes a home: the nightly sweep skips it (`kitlib.worktree.sweep` `sweep_skip`: "detached HEAD: no branch, never swept"), `worktree_remove --check` lists no leftover or merged line for it, `worktree_remove home-<name>` fails on git's own refusal to remove a locked worktree (tests/launcher/test_home.py `RealHome`); `next` reads only worktree branches (`kitlib/backlog/offer.py`), and a home has none. `after-reboot` does not pass the flag: its sessions start in their repo folders as before. Tests: tests/launcher/test_home.py, tests/launcher/test_start_home.py.

### Listing and removing homes

`launch.py homes --repo NAME` (or `--repo-path DIR`, a main checkout; anything else is refused, "is not a main checkout ... Nothing was changed.") lists each `home-<name>` worktree in the host's worktrees folder (`home.list_homes`): its HEAD, whether it is locked, whether it is clean or which files it has (uncommitted, untracked or git-ignored: a stray write is often ignored), "folder missing" for one registered without a folder, and the running session whose home it is. `--remove NAME` (a session name or `home-<name>`, any case) unlocks the home and runs `git worktree remove` without `--force` (`home.remove`); `--what-if` says what it would do and writes nothing. `NAME` is first read as a session name; only when that session has no home is a leading `home-` dropped, so a session named `home-automation` keeps its own home `home-home-automation` (`start.homes`). Refused, nothing removed: an empty name or a bare `home-`, a session whose home it is is running (stop it first), the folder is not a worktree of this repository, not a `home-<name>` in the worktrees folder, on a branch, registered with its folder missing (the message gives the `git worktree unlock` and `git worktree prune` steps), it has any uncommitted, untracked or ignored file, which the refusal names (move or delete them yourself; the launcher deletes no file), or its HEAD is a commit that no branch, tag or other ref contains and that the main checkout's HEAD does not have (a commit made in the home: `git worktree remove` checks only files, so it would be orphaned; put a branch on it first; `home._reachable`). A failed unlock removes nothing; a failed remove locks the home again with the lock reason it had, and when git has already dropped the worktree, the message names the loose folder left for you to check and delete. An unreadable hosts.json is refused as `launch.py homes: ...; nothing was listed or removed.` Tests: tests/launcher/test_homes.py (`RealRemove` on real git; `Verb` drives `launch.main` for the exit codes).

### Known limits

- `home._reachable` checks only the home's current HEAD against refs/heads, refs/tags, refs/remotes and the like: a commit made in the home and then left by a checkout survives only in the home's reflog, and refs/worktree/* and refs/bisect/* are not seen, so `home.remove` does not refuse for it.
- `home.remove` checks for ignored files with `git status --ignored`, then runs `git worktree remove`, which does not count ignored files: an ignored file written between the two calls is deleted with the folder.
- The default consultant notes file is under `start.agent_temp`, `AGENT_TEMP` else `TEMP`: a launch that sees a different one of the two reads a different notes file.
- The old notes file is copied whenever the new one is missing, with no marker that it was copied before, so deleting the new file brings the old copy back at the next launch; and a launch that fails removes its copy even if a concurrent launch that started meanwhile is using it (`start.consultant`).

## Stop

`stop --name` stops one session's `claude.exe`, then its window only when that window's script carries the same name, then the window's `conhost.exe` when the window was its only child. Each process is stopped by pid and creation time, and the session's command line is read again at that time, so a reused pid is never hit. Refused (nothing stopped): a name or successor naming the PM session (`pm-session` or `Project Manager`, any case, or coordinators.json's `pm_name`, "PM relaunch"), a name with surrounding spaces, a successor equal to the name or not running, no match, several matches unless `--pid` picks one, the PM session (by name or by `pm_session_id` in coordinators.json), and the caller's own ancestor. An unreadable coordinators.json does not refuse a stop: the `pm_session_id` check is then skipped. Each stop is logged to `stop.log`; a log write that fails is said on stderr, and the stop stands. The stopped session's `pipes.json` entry is then dropped ("Pipe addresses"); a failure there is said the same way.

On Linux the session is a `claude` process (the claude host's Linux `process_names` in hosts.json: `claude`, `node`; a `node` only when its program or script is the CLI, hosts.json `cli_program`, or a script in the `cli_package` directly under `node_modules`, so `node app.js -n x` is never one, and the claude's command line is read again at its creation time before it is stopped and must still be the CLI's) and its window is its parent only when that parent is `bash` running the window's script with exactly the name in both its `PM_KIT_SESSION_NAME` line and its `claude` line, quoted (`pm` never takes `pm-session`'s window). `stop` ends the window by killing that shell by pid and creation time, never through tmux: the shell's command line is read again at its creation time before the claude is stopped, the shell is left alone when it no longer carries the name, and tmux closes the session once the shell has gone. There is no conhost, and nothing above the shell (the tmux server, a terminal) is ever stopped (tests/launcher/test_stop_linux.py).

## Pipe addresses

Every live Claude Code session publishes a registry record, `<config folder>/sessions/<pid>.json`, with its pid, `sessionId`, `startedAt` (epoch ms), its creation time (`procStart` or `procStartFt`), `entrypoint`, `messagingSocketPath` (its peer pipe) and its name; a secret key file sits beside it, which the launcher never opens (`kitlib/launcher/pipes.py` docstring). The hub's push notifications send to that pipe (docs/action-hub.md "Push notifications").

- After `start` opens a window it polls the registry folders of the default config folder and of every configured account and org (`pipes.registry_dirs`, each folder once) for a record of the new session's name started at or after the moment before the window opened, once a second for up to 20 s (`pipes.TRIES`, `pipes.POLL_S`), and writes its entry to `pipes.json` (`pipes.record`, through `Host.record_pipe`). Not found in time, it says `pipe not recorded yet: the hub resolves it at send time`; a fault says `pipe not recorded (...)`. Either way the start stands. With no `launcher.state_dir` nothing is polled or written.
- A record alone is never proof that a session runs: `launch.py stop` leaves its record behind, and the pipe changes on every restart. A record counts only while its pid runs with the record's creation time (`pipes.is_live`).
- `pipes.json` is a hint and an audit, never the truth: a sender resolves the live record at send time and uses `pipes.json` only to choose between two live sessions of one name. No token is ever written to it. Two launchers writing at once can drop one entry (the last write wins); the sender's registry scan still finds that session.

Tests: tests/launcher/test_pipes.py.

## Hand-off

`handoff --session KEY --account N|auto` starts the successor `<stem>-a<N>` once the session has replied "ready to hand off"; `--recycle` starts `<stem>-a<N>-r<k>` on the same account and prints the `stop` line for the old one. `--all` hands off every entry, agent sessions first, skipping one already on the target. `--stem NEW` (one `--session` only; letters, digits, `_` and `-`) hands off under a new stem: the successor is `NEW-a<N>`, with no `-r<k>` even on a recycle, and sessions.json's `stem` becomes `NEW`; it is how a running session moves to a new stem. `--state FILE` (one `--session` only; an existing file) names the note the successor is told to read, in place of the entry's `state`: the path the session gave in its ready reply. The predecessor lands nothing after it replies ready: the successor's first message (`start.predecessor_text`) tells it to queue each LAND verdict the state note lists that the owner or a ledger ruling has cleared, to hold the rest until the owner gives the go, and never to wait on the old session; there is no landing order between the two. A not-signed-in account, and without `--recycle` the account the session is already on, is refused, and so is an unreadable sessions.json or coordinators.json (both are read before anything starts). sessions.json (and coordinators.json for a repo's main coordinator) is rewritten only after the start succeeds; the old window stays open until the PM stops it.

## After a reboot

`after-reboot` waits 60 s, then starts every plain sessions.json entry (`agent` false) on the account `pick-account` chooses, skipping `_` keys, `"autostart": false`, and any entry whose stem is already running; an agent entry (a coordinator) is logged `<key> a coordinator: the hub restarts it (coord-restart), skipped`, since the hub's coord-restart job starts it ("Hub restart"). The hub runs `after-reboot` once after a boot ("Hub restart"); nothing else starts it but the owner by hand. An entry's brief is passed whenever it has one, and a start that fails in any way is logged `FAILED` and the run goes on. It then resumes the PM session (`claude --resume <pm_session_id> --agent pm-kit:pm` as `pm-session`, the kit's PM agent, content/roles/pm.md) unless it is running (`pm-session`, the id, or coordinators.json's `pm_name`; a resume that starts drops `pm_name`, since the PM is `pm-session` again), the desktop app is running (resuming there too would fork the conversation; with `pm_resume_beside_desktop` true it resumes anyway and logs so), or, more than 15 minutes after boot, its transcript was written in the last 15 minutes. Lines go to `after-reboot.log`. It runs with no console, so nothing it hits escapes as a traceback: no signed-in account or a missing or bad sessions.json (no entry started), a bad coordinators.json (no PM resume), a failed sessions.json write, and a PM account not signed in are each logged `FAILED`, and the run goes on to what it still can. `--test` starts only a plain `autostart-test` session in the home folder; `--dry-run` says what it would start, runs the PM resume checks and says their outcome, and opens and writes nothing.

## Hub restart

The hub server's timed job `coord-restart` (`kitlib/hubjobs/coord_restart.py`; docs/action-hub.md "Timed jobs") restarts a stopped coordinator on its last account, every 300 s, the first run 120 s after the hub starts. It looks only at agent entries of sessions.json that the PM checklist lists as not running (`kitlib.pmstart` `down_entries`: a name, `autostart` not false); plain sessions are left alone. A start runs `launch.py start --session KEY --account N` as a windowless child, the line the checklist prints, at most one per run. The last account is the one the job last saw a session of the stem running on (the `-a<N>` of its name), else the entry's `account`. The decision is `coord_restart.decide`, which reads nothing itself. It holds, starting nothing, when:

- any session of the stem runs (the test `start --session` refuses on), so there is never a second copy;
- stop.log has a line with no successor (`successor '-'`) for a session of the stem that is newer than the last time the job saw it running (a stamp within 1 s before the sighting counts as newer: stamps are whole seconds), or the job never saw it running;
- it has been seen down on fewer than 2 runs in a row, which gives a hand-off time to start it first;
- it has had 3 starts in 24 hours (pushed `gave-up`), or the last start was less than 10 minutes (after the first) or 30 minutes (after the second) ago;
- no account is known, the account is not signed in (`not-signed-in`), or it is at or over `accounts.HEADROOM_LIMIT` (90%) of a window that has not reset (`over-limit`).

A start is pushed as `restarted`, or as `restarted-unchecked` when the account has no usage file, so its limit was not checked (as `check_headroom` does for other launches). A push's detail is `KEY:aN`, and each word goes out once per down spell. The hub keeps one owed push per job and a newer one replaces it, so a run pushes at most one event: one word (a start first, then `gave-up`, `over-limit`, `not-signed-in`), its detail every `KEY:aN` of that word that fits the 64-character field, joined by `.`. Only what that event carries counts as sent; the rest goes out on a later run. A start that ends a failing streak (3 failures in a row) pushes its `restarted` on the next run, since the hub pushes `recovered` straight after that run and it would replace the start's push. A child that exits non-zero or runs past 180 s is a job failure (hub health) and still counts toward the cap. `coord-restart.json` in `launcher.state_dir` keeps `{key: {seen_at, account, starts}}`, so a hub restart keeps the cap. Hub health's `note` lists every entry's state.

To keep a coordinator down for good, stop it with `launch.py stop --name <name>` and no `--successor` (the PM's step on `ready to stop:`), or set `"autostart": false` on its entry. The PM checklist line is unchanged.

The hub is the only thing that restarts agents: the launcher's sign-in task is retired ("Autostart"), and the hub itself starts at sign-in from its own task (`hub.py setup --autostart`, docs/action-hub.md). After a boot the job also runs `launch.py after-reboot` once per boot, as a windowless child it does not wait for; `after-reboot` then starts the plain sessions and resumes the PM ("After a reboot"), and the coordinators come back through this job. The boot is `now - uptime`; the one it ran for is kept in `coord-restart.json` (`_after_reboot`), and the job runs it on the hub process's first run whose boot is more than 120 s (`BOOT_SAME_S`) from the kept one, at any uptime, so an owner who signs in hours after the boot still gets it and a hub restart in the same boot does not. With no boot kept at all (a first install, or a lost file) and the machine up 30 minutes (`BOOT_S`) or more, the boot is only kept, not run: that hub start is not a boot's. It runs before sessions.json is read, so a bad sessions.json still lets the PM resume, and a `coord-restart.json` that cannot be read counts as no boot kept: the one-shot still runs, nothing is written, and the run is then a failure as before. A child that cannot start is a job failure, tried on the next run. Restarting a coordinator that stopped on `ready to stop:` once its repository has startable backlog work is not yet built: the PM still does that by hand.

Known limits:

- Windows Fast Startup's "Shut down" may not reset the uptime (`GetTickCount64`), so it may not count as a new boot and `after-reboot` may not run (inferred, not checked); a restart does reset it.
- A wall-clock step of more than 120 s (`BOOT_SAME_S`) between runs moves `now - uptime` and can run the one-shot again; `after-reboot` skips running stems and a running PM, so it starts nothing twice.
- After a reboot the coordinators come back one per run, about 5 minutes apart (the first about 7 minutes after the hub starts), and each of those starts counts toward the 3 starts in 24 hours.
- A window closed by hand writes no stop.log line, so it reads as a crash and is restarted, within the cap.
- An event still owed when the next run pushes is replaced: the PM gets only the newer one. Hub health's `note` shows the newer run's current state of every entry, not the replaced push.
- The last account prefers the account the job last saw running over sessions.json `account`, so after a hand-off to another account a start goes to the old account until the job sees the new session run.
- A stop.log stamp in the repeated hour when daylight saving ends is read as the later of its two instants, so the stop can read up to 1 hour later than it happened. A sighting that really came after it then still counts as older: a coordinator restarted by hand in that hour that then crashes is left down.

## PM relaunch

`pm-relaunch --name NEW [--wait SECONDS]` is for a PM that still runs but can no longer be reached, such as one whose Remote Control link died in an outage, so the web app no longer lists it; `after-reboot` skips a running PM and `stop` refuses it. It opens a new window as the after-reboot resume does (the `pm` session mark, coordinators.json's `pm_folder` and the config folder of its `pm_account`) running `claude --resume '<pm_session_id>' --fork-session --agent pm-kit:pm --remote-control 'NEW' -n 'NEW' '<prompt>'`; `--fork-session` (the CLI's `claude --help`) resumes the conversation under a new session id. The fork's id is learned from its registry record ("Pipe addresses"), polled once a second until its `sessionId` differs from the old one, for up to `--wait` seconds (default 120, `relaunch.WAIT_S`: a long transcript resumes slowly), then written to `pipes.json`. Once it is known, the old PM is sent a stand-down through the hub's push delivery while coordinators.json still names it, then coordinators.json's `pm_session_id` becomes the fork's and `pm_name` becomes `NEW`. That write is tried 3 times, each waiting out a reader holding the file (`kitlib/fs/replace.py`); if it still fails, every line so far stands and the last but one gives the manual step (`set pm_session_id to <id> and pm_name to NEW in <path>`). The fork's first message has it act as the PM only once coordinators.json's `pm_session_id` is its own session id; until then it does nothing, and after 10 minutes asks the owner, so an unconfirmed fork is never a second PM. A fork not confirmed within the wait changes nothing and sends nothing, and says so with the manual step. The hub's peer resolution counts `pm_name` as a PM sender and reaches the fork by its session id; its name fallback stays `Project Manager` and `pm-session`, so a stale `pm_name` is never a delivery target (docs/action-hub.md "Push notifications"). Every session `start` opens afterwards is told `pm_name` first wherever its first message names the PM (`start.pm_ref`), and the roles message the PM session their start context names. A session started before the relaunch keeps its old context: the owner tells a long-running coordinator the new name, or recycles it. After-reboot drops `pm_name` when it resumes the PM as `pm-session`. The old session is never stopped: closing its window is the owner's step, and the last line says so. Refused, nothing started: no PM in coordinators.json, the recorded PM not running (no live registry record with its id, no process carrying its id or `pm-session`), and a `NEW` that is empty or spaced, a PM name (holding `pm-session` or `project manager`, any case: stop's test), or names a running session, a live registry record or a sessions.json entry (`kitlib/launcher/relaunch.py`; tests/launcher/test_pm_relaunch.py).

## Autostart

`install-autostart` is retired: it registers nothing and exits 1 with `install-autostart is retired: ...`, naming the line that removes a task installed before (`kitlib/launcher/autostart.py` `install`). The task `Claude coordinators after reboot` ran `launch.py after-reboot` at sign-in; the hub now does that once after a boot ("Hub restart"), so the hub is the only thing that restarts agents. A task still installed would run `after-reboot` beside the hub's run, which starts nothing twice (a running stem is skipped); remove it with `Unregister-ScheduledTask -TaskName 'Claude coordinators after reboot'` (on Linux, the pm-kit job `coordinators-after-reboot`). The name stays in `autostart.TASK_NAME` so the PM start's task check still knows it as the kit's. `after-reboot --test` starts a minimized, unfocused `autostart-test` window after the same 60 s wait, to check the run by hand; `kitlib/launcher/reboot.py` `run` takes a `say` that gets each line as it happens, and `tools/launch.py` prints it.

## State files

In `launcher.state_dir`, machine state outside git; copy the examples to start:

- `sessions.json` (`docs/launcher.sessions.example.json`): `{key: {repo, agent, stem, state, brief?, account, name, autostart?}}`. `agent` true runs the coordinator agent, a string that agent, false a plain session. A `_` key is a note.
- `coordinators.json` (`docs/launcher.coordinators.example.json`): `{repo: account, pm_session_id, pm_folder, pm_account, pm_name?}`; `pm_name` is the name `pm-relaunch` gave the PM. A value starting with `<` is a placeholder and is ignored.
- `stop.log`, `after-reboot.log`: one timestamped line per action.
- `coord-restart.json`: the hub's coordinator restart job's sightings and starts, and the boot it last ran `after-reboot` for ("Hub restart").
- `pipes.json`: `{name: {pid, session_id, pipe, proc_start, entrypoint, recorded_at}}`, written by `start` and trimmed by `stop` ("Pipe addresses").
- `push-outbox.json`, `push-undelivered.jsonl`: the hub's push notifications, written by the hub server, never by the launcher (docs/action-hub.md "Push notifications").

JSON is read with or without a BOM and written UTF-8 without one.
