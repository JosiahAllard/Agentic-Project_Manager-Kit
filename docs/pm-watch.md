# PM watcher

`tools/pm_watch.py` stays silent until something needs the PM and prints one line per event. The PM runs it in the background without `--stream`: it exits after the first events, and the PM starts it again at once, before it handles them, so the heartbeat stays fresh and the hub's `watcher down` push (docs/action-hub.md "Push notifications") does not fire while the PM works. With `--stream` it keeps polling after an event and never exits, so a background run of it reports nothing; the PM start check warns on it (docs/pm-start.md "Watcher"). Logic: `kitlib/pmwatch` (checks and the `Watcher` poll), with the Claude-only parts (`~/.claude*/projects` transcripts, the `custom-title` record, the `~/.claude/machine-lock/alerts` default) in `hosts/claude/adapter/claude_host.py`, the seam the host split (ARCHITECTURE "Host split") lifts out. The tool's docstring lists the events and options; the state keys (`branches`, `usage`, `bg_alerts`, `lock_notices`, `idle`, `idle_nolog`, `plugin_main`, `hub_stale`, `rc_lost`, `limit_stalled`) live in `kitlib.pmwatch`.

## Stopped sessions

A session that `launch.py stop` ended with no successor reads `STOPPED <name> at <iso>`, once per stop, and never `IDLE` (a stopped session keeps its `sessions.json` entry, so the idle check would otherwise report it as a quiet one). The watcher reads the launcher's `stop.log` in the folder of the sessions file (`kitlib.pmwatch` `stop_log_reader`; the line `kitlib.launcher.stop` writes, `successor '-'`). The newest stop of the name counts, and only while it is not older than the session's newest transcript activity: activity after the stop means the session was started again, and a quiet one then reads `IDLE` as before. A stop with a successor, a missing `stop.log` and a stop of another name leave the idle check as it was. The first run records a stopped session in the `idle` baseline as `[time, "stopped"]`, silently. Code: `kitlib.pmwatch` `idle_events`, `idle_baseline`.

## Remote Control link

A running session can lose its Remote Control link (a network outage) and go on working locally: nothing in it says so, and the owner, who is remote, loses it from the web app. The `REMOTE` check reads Claude's session registry, `<config folder>/sessions/<pid>.json` (the folder `kitlib.launcher.pipes` reads), whose `bridgeSessionId` holds the Remote Control session id and is null while the link is down. It watches the names in `sessions.json` (as the idle check does) and the PM's own, `pm-session` (`kitlib.launcher.stop.PM_RC_NAME`). For each name it takes the newest record whose pid runs with the recorded creation time. It gives `REMOTE <name> link lost: the session runs, its Remote Control link is down (pid N)` once per episode when that record's `bridgeSessionId` is null, the session started more than 3 minutes ago (`RC_GRACE_S`: a new session is null until it connects), and the process was started with `--remote-control` under that name (a `--no-remote-control` session has no link to lose; the process list is read only when some session looks unlinked). `REMOTE <name> link back` follows once when the field holds an id again. A record without the field (an older CLI) and a session inside the grace period leave the state as it was; a session that is gone, or now runs as another process (stopped and started again under the same name), drops out, so the new one starts clean. A record whose name is not text is skipped. Unlike the idle check it keeps no baseline: a link already down when the watcher first runs is reported then. State key `rc_lost`: one `<name> <pid> <creation time>` entry per session reported lost. The check runs on the idle cadence (`--idle-poll`, 300 seconds). The PM tells the owner through the hub; the watcher posts nothing itself.

Known limit: the CLI rewrites the record when the session's status changes, so a null is fresh, but an id can be stale. A quiet session that has written nothing since its link dropped still shows the old id, so it is reported late, when it next writes its record, or not at all while it stays quiet. A busy session, and the PM, are reported within one pass of their next write. Inferred, not observed: a session whose Remote Control the owner turned off from inside it (`/remote-control`) most likely also reads null and is reported as `link lost`; the field does not say why the link is down. Code: `kitlib.pmwatch` `rc_events`, `rc_check`; the reader `hosts/claude/adapter/claude_host.py` `rc_records`. Tests: tests/pmwatch/test_rc.py.

## Usage-limit stall

A session that reaches its account's weekly limit stops with its process still running: it looks like an idle one. `LIMIT <name> account <n> stalled at the weekly limit until <iso> (pid <p>)` tells the two apart, once per stall. A session is stalled when all three hold:

- Its process is live: the newest registry record of the name whose pid runs with the recorded creation time, as in "Remote Control link". The names are the same too: sessions.json's and the PM's.
- Its account's stored reading is at the limit: `seven_day` at 100%, or at 99% and stale (`kitlib.pmwatch` `at_limit`; a reading refreshes only while a session works, so it can stop short of 100). The account is the one whose `launcher.accounts` folder holds the record's registry folder (`registry_accounts`); a folder of no account, such as an org's, has no reading and no LIMIT.
- The newest thing the session did is the CLI's usage-limit API error, and its reset still lies ahead.

The reader goes by the entry's structured fields, never its display text: `isApiErrorMessage` true, `apiError` `usage_limit_reached`, and `rateLimitType` `seven_day` in `apiErrorParams.rate_limit_info` (else `quotaLimits`), with `resetsAt` from the same place. `apiErrorStatus` is not asked for: a subagent's entry has none. The tests' fixture, tests/pmwatch/usage_limit_entry.jsonl, is two real entries, one of each kind. Only the weekly window counts (the owner's rule), so any other `rateLimitType`, an unknown one included, reads as no stall. No real five-hour entry has been seen, so its value is not known.

A subagent's entries live in its own file, `<id>/subagents/agent-<agent id>.jsonl`, not in the main transcript, so a main session waiting on a stalled subagent shows nothing in its own file. Such a session counts as stalled. The reader takes the newest conversation entry (type `user` or `assistant`) of the main transcript and of the subagent file written last, and the later of the two by timestamp decides, the main one on a tie. So an older limit entry followed by anything newer, in the main transcript or another subagent, is no stall: the session recovered or moved on. A `resetsAt` in the past is no stall either. Records of other types after the entry (a title, say) are passed over. Inferred, not observed: which of them the CLI writes after a limit entry. A tail line that does not parse reads as no stall until the next pass.

The check runs on the idle cadence and reads no registry or transcript unless some account is at the limit; then only the last 64 KB of each file (`TAIL_BYTES`). Like `REMOTE` it keeps no baseline: a session stalled when the watcher first runs is reported then, by the hub job's first run too. State key `limit_stalled`: one `<name> <pid> <creation time> <reset>` entry per session reported, dropped when it no longer reads stalled, so a later stall fires again. The usage reading can be one `--usage-poll` old (600 seconds), so LIMIT can come that much after the stall. No early trigger on the burn slope is built: the owner keeps it off until the slope is measured.

`rc_check` hands the check to the `Watcher` as its `limit` attribute, so pm_watch and the hub job both run it. Code: `kitlib.pmwatch` `at_limit`, `limit_events`, `limit_check`, `Watcher`; the readers `hosts/claude/adapter/claude_host.py` `newest_entry`, `weekly_reset`, `weekly_stop`, `rc_records`. Tests: tests/pmwatch/test_limit.py.

## Config

The machine config (docs/kit-json.md "Machine config keys"), key `pm_watch`; a flag of the same meaning wins:

```json
{"pm_watch": {
  "sessions_file": "<launcher state_dir>/sessions.json",
  "state_file": "<local-app-data>/pm_watch/state.json",
  "alerts_dir": "<home>/.claude/machine-lock/alerts"
}}
```

`<home>`, `<local-app-data>`, `<pm-repo>` and `<kit>` stand for absolute paths: the user's home, `%LOCALAPPDATA%`, the PM repository and this kit's checkout.

`sessions_file` (`--sessions`) is required: neither flag nor key exits 2. Usage is read in-process by `kitlib.pmwatch.usage` from `kitlib.launcher.usage` (`launch.py usage`, docs/launcher.md "Usage") with the machine config's `launcher` settings; without a `launcher` key it exits 2 (`kitlib.pmwatch.launcher_configured`), since the default would watch only `~/.claude`. The flag `--usage-script` and the key `pm_watch.usage_script` are refused with exit 2. `state_file` (`--state`) defaults to `%LOCALAPPDATA%\pm_watch\state.json`; `alerts_dir` (`--alerts-dir`) defaults to `~/.claude/machine-lock/alerts`.

Kit-only additions: `--state`, `--stream`, the heartbeat below, and `--once` (one poll, print any events, exit 0) for checks. `--stream` and `--once` exclude each other (exit 2).

## Stream mode and heartbeat

Every pass except a `--once` run writes `<state file>.beat`, holding `{"pid", "beat", "stream", "started", "yielded"}`: the watcher's process id, the time of the pass in epoch seconds, whether it streams, when the process started in epoch seconds (`kitlib.pmwatch` `own_start_time`, null when Windows does not report it), so a reused pid is not taken for the watcher, and whether that pass stepped aside for the hub's session-watch job ("Hub session-watch job"). The heartbeat is a separate file because the state file's keys are shared with the PM's copy. A heartbeat write that fails (an `OSError`, such as a `PermissionError` while another process holds the file) is skipped and tried again on the next pass, so it never stops the watcher; the heartbeat then goes stale. A pass sleeps 60 seconds (`kitlib.pmwatch` `POLL_SLEEP`), so a new alert or lock notice shows up to a minute late. The PM session-start check reads the heartbeat beside the configured `state_file` (docs/pm-start.md): a heartbeat more than 5 minutes old, one whose pid is not a running `pm_watch.py` that started at the recorded time, or one that says it streams, gives a line to start the watcher again in the background, unless the hub's session-watch job covers ("Hub session-watch job"). Code: `kitlib.pmwatch` `run`, `write_heartbeat`, `read_heartbeat`, `own_start_time`.

## Plugin export

Kit-only: the `PLUGIN` event, when the pm-kit plugin export is behind the kit's `refs/remotes/<remote>/main`, once per main sha (state key `plugin_main`), and with the machine config's `plugin.auto_refresh` on, the detached start of `tools/plugin_refresh.py --apply` (docs/plugin-source.md "Behind warnings"). The hub server's `plugin-refresh` job refreshes on the same switch (docs/plugin-source.md "Hub refresh") and is the one owner while it is up: when the hub's GET health `jobs` names `plugin-refresh`, the event is the behind line alone and pm_watch starts nothing; with the hub down (or no token file or pointer) pm_watch starts the refresh itself as before, and both still take `refresh.pid` (`kitlib.pmwatch` `hub_plugin_job_up`). With no export, or an account folder not migrated, the event names `python tools/plugin_refresh.py --migrate --apply` and starts nothing. A tracking ref or export state that cannot be read is a failed check. Also the `HUB` event, once per stale episode (state key `hub_stale`), when the hub server's GET health `code` says hub code newer than the running server has landed: it carries the owner's restart step (`python <kit>/tools/hub.py restart`, or `hub.py stop` then `hub.py serve` with no autostart task; docs/action-hub.md "Stale code"). A hub that is down, has no token file or no pointer is no event; any other failure is a failed check. Both checks ask at most once per `branch_poll` (300 seconds). Code: `kitlib.pmwatch` `hub_check`, `plugin_check` and `Watcher`; `tools/pm_watch.py` `main(plugin=False)` and `main(hub=False)` run without them, for tests. `Watcher` calls `kitlib.pmwatch` `preload` when built, which imports the modules the checks would otherwise load on their first pass (`kitlib.pluginsource`, `kitlib.pmstart.consoletasks`, `kitlib.machinesetup.extras`, `kitlib.launcher.settings`, `kitlib.launcher.usage`, `kitlib.hubsite.codestale`, `kitlib.hubsite.serve`, and the host's own, on Claude its plugin source module), so a landing that writes the checkout cannot give the running watcher a mix of old and new code.

## Hub session-watch job

The hub server's `session-watch` job (`kitlib/hubjobs/session_watch.py`; docs/action-hub.md "Push notifications", its push shape) runs the same `Watcher` on the code the hub loaded: BGFAIL, LOCKNOTICE, USAGE and RESET, IDLE and STOPPED, REMOTE, LIMIT and ERROR, from the same `pm_watch` config keys. It leaves PLUGIN (the `plugin-refresh` job owns the refresh), HUB and BRANCH (whose refs are only `--branch` arguments) to pm_watch. Its state is its own file, `<state_file>.hub.json`, never pm_watch's: a fresh one is a silent baseline, and a hub restart repeats nothing. pm_watch steps aside for the job: at the start of each pass it reads the hub's GET health `jobs` (`kitlib.pmwatch` `hub_session_job_up`), and while that names `session-watch` with no failure since its last success and a run (`last_at`, a skip's too) at most 3 periods (`SESSION_JOB_LIVE_RUNS` times `every_s`, 180 s) old (`session_job_live`), its session checks still run and save their state but print nothing, their ERROR lines too; BRANCH, PLUGIN and HUB stay pm_watch's and print as before. One failure ends the step-aside, since a job failing before it polls would lose those events; a stale `last_at` ends it too, since a hung job thread keeps its failures at 0. A job that has not run yet (30 s after the hub starts) has no `last_at`, so pm_watch keeps its checks until then. It steps aside only when its sessions file, alerts folder and notice folder (`--sessions`, `--alerts-dir`, `--notice-dir`) are the ones the job reads: the config's `sessions_file`, its `alerts_dir` or the host's default, and `machine_lock.notice.dir` (`job_inputs`, `session_yield`); otherwise its own events would reach no one. A hub that is down, has no token file or pointer, or answers anything else is no job: pm_watch acts alone. A recent success is not asked for: the job skips every run while a live pm_watch has not stepped aside, so it has no success to show.

pm_watch keeps writing its heartbeat while stepped aside, with `"yielded": true`. The job waits only on a fresh heartbeat that has not stepped aside: while pm_watch's heartbeat is at most 300 s old (`session_watch.LIVE_S`) and its `yielded` is not true, the job still polls and saves its state but pushes nothing, so pm_watch alone tells the PM; it pushes once the heartbeat is older or says `yielded`. A heartbeat with no `yielded` field (a pm_watch from before it) holds the job as before. So, when both run this code, the two do not both go silent: pm_watch yields only to a job that has run lately without failing, and the job holds back only for a pm_watch that has not yielded. A hub still running the code from before this (it reads a yielded heartbeat as live) holds back while pm_watch yields, so both stay silent until that hub restarts; a hand-started hub does not restart on a code change (pm_watch's own HUB event, which stays on, names the restart step once the hub's code is stale). At the hand-over an event can reach neither: one pm_watch drops after it stepped aside that the job had already taken in while it still held back for the heartbeat (the job reads the `yielded` heartbeat at its next run, up to 60 s later).

The hub push worker's `watcher down` push and the PM session-start watcher check (docs/pm-start.md) count the watcher as up when the job covers, not only when pm_watch's heartbeat is fresh: its health block has fewer than 3 failures and a success (`ok_at`) at most 300 s old (`kitlib.pmwatch` `session_job_healthy`; docs/action-hub.md "Push notifications"). A job that only skips has no recent success, so it never covers on its own. pm_watch stays in place.

## Switch-over for the PM repo

The PM repository keeps no watcher code. It sets `pm_watch.sessions_file` to the launcher's sessions.json and points `pm_start.pm_watch_cmd` at `python -u <kit>/tools/pm_watch.py`, without `--stream` (docs/pm-start.md "Config"), or leaves it unset for the kit's own command; `kitlib/pmstart` finds it as a `pm_watch.py` process whose heartbeat is fresh.
