# Test tools

Three tools for a checkout's own test runs: `tools/testlist.py`, `tools/tool_deps.py` and `tools/pytests.py`. All three are not live. Each one takes `-C DIR`, the checkout, default here. Each exits 2 on USAGE or on a refused configuration or checkout. Their keys are `.kit.json` "testlist" and "tool_tests"; the defaults are in `kitlib/config/schema.py`, and docs/kit-json.md lists them.

## testlist

`tools/testlist.py` (kitlib/testlist) lists the test names in a tree's result files, so that a move or rename that loses a test shows.

- `--save FILE` before the change, then `--diff FILE` after it. The diff lists removed (`  - `) and added (`  + `) names.
- `--against NEW` diffs two saved lists.
- `--status` adds passed, failed or skipped to each line.
- Result globs: "testlist" `junit` and `trx`.
- Exit codes: 0 same, listed or saved; 1 the names differ; 2 nothing found, or no result newer than the saved list.

## tool_deps

`tools/tool_deps.py` (kitlib/tooldeps) works out which tools test modules a change can break.

- `PATH ...` prints the selected modules, or ALL.
- `--graph` prints every tools module and its direct edges.
- `--check` audits the "tool_tests" tables and exits 1 on a problem.

The tables are read from "tool_tests": `extra`, `pinned`, `patterns`, `whole_tree`, `untested`, `dynamic_imports`, `always_run`, `selector_files`, `ignore`, and the rest of that section. A `{"piece": ...}` or `{"solution": true}` pin needs a pieces table that the entry point does not pass, so it is refused when it is read.

## kit_tests

`tools/kit_tests.py` (kitlib/tooldeps/selftree.py) runs the kit's own suite, whole or only the test packages a branch's change can reach. Kit build agents run their branch with `--select`, and kit landings gate with `--select` too; `--full` runs the whole suite by hand. `gate.py --full` and `daily_full.py` run the whole suite once the kit-suite gate step has a `full_cmd` running `--full` (docs/gate.md "Steps") and `daily_full` is enabled in `.kit.json`; the owner schedules daily_full.py. A `daily_cmd` running `--full --both-tiers` makes the daily run also run `tiers.REAL_GIT_MODULES` on real git ("Fake git" below). Every `--select` and `--full` run also runs the test modules the change adds or changes on real git, as a second pass (below). Wrap either in the machine lock, booking 2 cores (the test size, `medium_cores`: 2 on the default layout, and `--cores` above it exits 2; 4 logical processors, so 4 modules at once); `<repo>` is `repo.name` in `.kit.json`:

```
python <kit>/tools/machine_lock.py run --repo <repo> --slug <slug> --kind test --cores 2 -- python tools/kit_tests.py --select
```

To gate a worktree from another directory, run that worktree's own gate.py with an absolute `-C`: `python <worktree>/tools/gate.py -C <worktree> --full`. With no `-C` or a relative one, a gate.py run on another checkout of its repository is refused (docs/gate.md "The caller's checkout").

- `--select` diffs against the merge-base with `--base` (default: gate.md "Default base"), the work tree and untracked files included. `--changed PATH ...` takes the list instead. `--full` takes `--base` too, for its real-git pass (below).
- It prints each selected `tests/<pkg>` with the reasons it was picked, then runs those packages' test modules.
- `--full` runs every module `python -m unittest discover -s tests -t .` would load. `--plan` prints the selection and runs nothing.
- `--select --smoke` adds the table's `smoke` modules to the selection, unless every changed path is `prose`; a line names them (`kit_tests: --smoke: ...`). A `smoke` entry naming no test module exits 2 and runs nothing. It is meant as the kit-suite step's cmd once the kit's gate config names that step in `gate.smoke_steps` (docs/gate.md "Smoke steps"); the kit's `.kit.json` is owner-only.
- `--scrub` runs only `tests/scrub`, in one pass with the same isolation, and takes no change list (`--changed`, `--base`, `--both-tiers` are usage errors). The kit's gate sets no `docs_only`, so no kit gate step runs it: a docs change runs the default `--select`, which keeps the scrub and the doc tests the change maps to (docs/gate.md "Docs-only changes").
- `--list` (kitlib/tooldeps/selflist.py) runs nothing and takes none of the run flags (`--jobs`, `--plan`, `--real-git`, `--both-tiers`, `--pid-hold`, `--changed`, `--base`). It loads every module of the suite in one child process and prints each test id, one per line, sorted; then `kit_tests: list: N test(s) in M module(s), K static skip(s) (runtime skips not counted), J module(s) failed to import`; then one `kit_tests: skip: <id> (<reason>)` line per skipped test and one `kit_tests: import failed: <id>` line per module that did not import. K counts tests whose class or method carries a `unittest.skip`, `skipIf` or `skipUnless` decorator; a `self.skipTest()` inside a test body is a runtime skip and is not found, so K is a lower bound. Two runs of the same tree print the same lines, so the output of a base and a tip diffs cleanly (the Moves and renames equivalence check's test-id and skip-count comparison).
- Tests run on the fake git ("Fake git" below); `--real-git` runs every test on real git instead, and `--both-tiers` runs the selection on the fake, then `tiers.REAL_GIT_MODULES` of it and the added or changed test modules on real git.
- On the fake, `--select` and `--full` then run the test modules the change adds or changes on real git, as a second pass, with no flag (tools/kit_tests.py, kitlib/tooldeps/tiers.py `changed_test_modules`). `--select` takes them from its change list. `--full` diffs against `--base` or the default base the way `--select` does, says it in a line (`kit_tests: --full: the real-git pass's change list against the merge-base with <base>: N changed path(s)`), and exits 2 with `kit_tests: refused: ... - no test ran` when git cannot list the change. A line names them before the run (`kit_tests: real-git pass: N added or changed test module(s): ...`, under `--plan` too). The two passes print as `--both-tiers`' do, and only `kit_tests: OK, both tiers green (fake git, real git)` is the run's OK. A change that adds or changes no test module, such as the daily run on main, runs one pass after the line `kit_tests: real-git pass: no added or changed test module`, which is not a verdict. A deleted module, a helper, or a path outside the tree's test modules gives none. There is no second pass under `--real-git`, or when the environment already sets `KIT_FAKE_GIT` to anything other than 1. With `--pid-hold` the hold covers only the fake pass.
- No test child (a unit, the count child, `--list`'s loader) gets the session's kit binding: `child_env` (kitlib/tooldeps/childenv.py, which kit_tests imports) drops `PM_KIT_ROOT`, `PM_KIT_RELEASE_ID`, `KIT_LIVE_ROOT`, `KIT_PINNED`, `PM_KIT_ROLE`, `PM_KIT_HOST` and `PM_KIT_SESSION_NAME` (`KIT_SESSION_ENV`), each host's `session_env` variable (hosts.json) and every `PM_KIT_<HOST>_` prefixed variable (`session_env_names`) from the environment it copies, so a session's env cannot steer the suite. A test that needs one sets it itself (tests/gate/fixtures.py `test_env` sets `KIT_PINNED=live`).
- Nothing selected (a docs-only change) prints `kit_tests: OK, nothing selected (N changed path(s))`, so a gate whose pass pattern is `kit_tests: OK` passes; `--plan` prints the same line.
- Exit codes: 0 passed, nothing selected or `--plan`; 1 a test failed; 2 USAGE, git could not list the change, or `--select` with a malformed table; 130 Ctrl+C. On 2 no test ran.
- `--full` is the escape hatch: with a malformed table it prints a warning, treats `serial` as empty and runs every module. Only `--select` refuses.

Parallel runs (kitlib/tooldeps/selfrun.py):

- One unit is one test module, or one test class of a split module, run as `python -m unittest <unit>` would run it. A unit past its timeout is killed and reported TIMEOUT, and a unit that ran no test is a FAIL.
- Units run in a pool of long-lived interpreters, one per job (kitlib/tooldeps/pool.py, pool_worker.py), so a run starts about one interpreter per job, not one per unit. Each worker has its own kill-on-close job. Each worker imports the units' top-level packages once, before its first unit (selfrun `unit_packages`), so their import code, audit hooks included, does not run again per unit.
- Between units a worker puts back cwd, os.environ (TEMP and TMP included), sys.path, sys.argv, the modules the unit imported and the module globals it changed (pool_worker.py lists the rest).
- A worker is replaced when its unit times out, crashes, is interrupted, or leaves a thread or a process running, and when it ended while idle. Ending a worker returns once every process its job held has ended (pool.py `GONE_WAIT`, 5 s at most). A unit that leaves a non-daemon thread running FAILS, since its own process would never have exited. The log's `kit_tests: interpreters:` line counts the workers, the replacements and why; a `kit_tests: pool worker replaced after` line names the unit behind each replacement.
- A test module with a `KIT_TESTS_OWN_PROCESS = '<why>'` line runs in its own `python -m unittest` process (kitlib.pytests.runner.run_unit), and the log says why.
- `--jobs N` units run at once. The default is the logical processors the lock run holds (`MACHINE_LOCK_CPUMASK`); outside a lock run it is 2, and the tool says which.
- Units start longest first by the seconds each took when last run, recorded in `kit-tests-times.json` in the git common dir (shared by work trees, never a work-tree file). Units with no record start first: the table's `long` modules in order, then the largest source.
- A module expected to take more than half the ideal wall time (expected seconds summed over jobs; at least 60 s) runs one unit per test class, so it cannot floor the wall time; with no record, the `long` modules are split. A module with a `load_tests` hook, or with tests from classes it does not hold by name, is never split. The log names each split module.
- Each unit gets its own TEMP and TMP folder, removed when it ends, so scratch files and scratch lock stores never meet.
- The run folder that holds them is a `kit-tests-*` folder in the kit temp folder (see "Temp folders"), so fixture repositories stay on the checkout's drive and out of the sessions' TEMP. When that folder cannot be made, the run uses the kit's default temp folder (`kitlib.config.user.default_work_temp`), else the process's temp folder, and its log says why (`make_temp`). A run that made its folder in the kit temp folder, outside the tests, first removes the `kit-tests-*` and `kit-direct-*` folders there that are over a day old, left by a killed run, and says how many (`kitlib.tooldeps.selfrun.prune_stale`).
- When `git` on PATH is Git for Windows' `cmd\git.exe` launcher (as from PowerShell), units get its `mingw64\bin` first on PATH, so each git call is one process, not two; the log says so. Git Bash already does this.
- The table's `serial` modules run after the pool, one at a time.
- Once every pooled unit has started, each unit that ends gives back the cpu slots the units still running do not use, the highest slots first (`kitlib.lock.giveback.drainer`, docs/lock-api.md "Giving back slots"), so a queued run starts on them before this run ends. Only when the lock run offers it (`machine_lock.py run` from this kit, or a gate's last step) and no `serial` module is still to run; the log says what was given back. Units never get the offer. A run under the installed monolith wrapper (the installed `machine_lock.py`) gives back nothing, because only kit-wrapped runs offer slots back; with no offer the log says `kit_tests: give back: no offer ...` once. In a two-pass run one drainer serves both passes, and since a slot given back is never taken again, the fake pass gives back only down to the threads the real-git pass's units can use at once (kitlib/tooldeps/tiers.py `unit_bound` from one count of those modules, at most `--jobs`; `keep_for_next`), said in a line `kit_tests: give back: the fake-git pass keeps N thread(s) for the real-git pass ...`; the real-git pass, the last, gives back the rest.
- One child process first asks unittest's loader how many tests each module holds. A module with none (a helper `test*.py` matches) is listed and not run. A module whose tests come from an import still counts.
- Ctrl+C starts no new unit, waits for the running ones to end, removes the temp folders, prints the summary and exits 130.
- The log has a line per unit as it ends, the full output of every unit that did not pass, a table per test package, then one summary line. A unit that skipped tests says `[3/170] OK 12s 25 tests, 2 skipped <module>` (the count is unittest's `skipped=N`, runtime `skipTest()` included); the package row and the summary end add the sum, only when it is above 0.
- A gate test built on tests/gate/fixtures.py `GateRepoCase` (the landing tests among them) that is still running `DUMP_S` (120 s, well inside the pool's 300 s `UNIT_TIMEOUT`) after its setUp ends writes every thread's stack to fd 2, and again every 120 s until it ends (`arm_dump`). In the pool, fd 2 is the unit's `unit-<n>.out` in the run folder; the log shows that output for a unit that does not pass, and a killed run leaves the file behind.
- `--jobs 1` runs the single `python -m unittest` process instead.
- `--pid-hold` (opt-in, off by default) first starts the pid hold (section "The pid shield"), so no process a test starts can be given a pid that a stale taskkill still names.

The import graph is derived on each run, never written by hand. A changed path selects as follows:

- `kitlib/<m>/...` selects `tests/<m>`, the tests of every kitlib package that imports `m` transitively, the test packages that use any of them (`from kitlib import X` counts), and the test packages naming a tool that imports them.
- `tools/<x>.py` selects the tests of the kitlib packages `x` imports, leaving out the shared core, and the test packages naming `x` or a tool that imports it. A deleted tool still selects the tests of the tools that import it and of the packages that run it.
- A kitlib package whose code holds a string naming `<x>.py` runs that tool, so a change reaching `x` also selects that package and what imports it. A shared-core package that runs it adds only its own tests.

Known limits: a run is seen only as a string literal naming `<x>.py`, so a path built at run time is missed; and a shared-core package that runs a reached tool selects only its own tests, not its importers.
- `tests/<t>/...` selects `t` and the test packages importing `tests.<t>`.

`tests/selection.json` holds the table; a change to it runs the full suite.

- `shared_core`: kitlib packages whose change runs everything. Default git, config, proc, lock.
- `full`: globs that run everything. These are the test helpers (`tests/*.py`), any file directly in `kitlib/`, the selector and the gate.
- `paths`: `[glob, [packages]]`, added on top of any rule. It is for a test that reads another folder, such as a scrub test, or `tests/skills`, which checks that every tool, kitlib and optional path a skill names exists.
- `by_name`: globs selecting the test packages that name the file. If none names it, everything runs.
- `prose`: the same, but a file no test names selects nothing and is listed as `(no test)`.
- `always`: test packages that read every tracked file (`scrub`: no ruling id, no machine path in any file `git ls-files` lists). Any non-empty change that does not run everything adds them, so a doc edit cannot reach main unscanned.
- `serial`: `[module, why]` pairs for test modules that cannot run beside others; each runs alone after the parallel phase.
- `long`: test modules known to run long; with no recorded time they start first and run split by class.
- `smoke`: the test modules `--smoke` adds: guard, landing, lock and commit approval (tests.commit.test_commit is left out until it is split by class).
- `skip_fails`: `[module, why]` pairs for proof modules. A listed module whose unit skipped any test (a decorator or a runtime `skipTest()`) is FAILED and the log says why, because a skip would void the proof. An entry naming a module the tree does not hold prints a `kit_tests: WARNING: skip_fails names ...` line.

Any other path is unmapped and runs the full suite: unmapped never means skip.

## Fake git

kitlib/git/fake answers git inside the test process (`fake.run(args, cwd, stdin, env)`), reading and writing the real on-disk repository (objects, packs, refs, index, config), so real git can carry on in a repository it touched. It exists to cut the suite's process starts, most of which were git: the full suite at 12 jobs went from 24848 process starts (24021 git) in 278 s to 1972 (1131 git) in 89 s (two machine-lock runs, before and after the fake git, each start logged by a sitecustomize audit hook).

- It is on while `KIT_FAKE_GIT=1` (kitlib.git.cmd `fake_active`). kit_tests gives the units 1 unless the environment sets it (`--real-git` gives 0); tests/__init__.py does the same for a direct `python -m unittest` run. Production never sets it.
- Routed to it: `cmd.call` and `cmd.run`, `cmd.spawner()`, `cmd.subprocess_run` (kit code that starts git itself) and kitlib.git.batch's cat-file. A test that swapped `cmd._run` or `subprocess.Popen` keeps its stub. `cmd.genuine()` is false under the fake, so kitlib.git.cache keeps none of its answers.
- Commands (`fake.COMMANDS`): add branch cat-file check-ref-format checkout clone commit commit-tree config diff diff-tree fetch for-each-ref hash-object init log ls-files ls-remote ls-tree merge merge-base merge-tree mv push read-tree remote reset rev-list rev-parse revert rm show status switch symbolic-ref tag update-index update-ref var worktree write-tree.
- Anything else, or an option it does not know, raises `Unsupported` ("unsupported in fake git: <what>"). It never falls back to real git. Unsupported is a BaseException, so `except Exception` around a git call cannot take it for an answer.
- Unreadable files: an open of a ref or a loose object that Windows denies for a moment (another holder excludes readers) is retried for about half a second, then raised; a lock whose write or rename fails is removed (kitlib/git/fake/refs.py `_read_file`, `RefLock.commit`; objects.py `_read_loose`). A tree object that is missing ends the command with git's "fatal: unable to read tree (<oid>)" instead of reading as empty (revs.py `tree_entries`), so `read-tree` cannot write an index that silently lacks the paths under it. Tests: tests/git/test_fake_tier.py `FakeRefReadRace`, `FakeUnreadableObjects`.
- History simplification: `log` with paths prunes like git's default mode (a merge TREESAME to a parent follows only that parent). `--full-history` follows every parent and shows a merge unless it is TREESAME to all of them, git's mode without parent rewriting; with `--diff-filter` (and no `-m`/`-c`/`--cc`) it shows no merge, as git shows a merge no diff to filter; `--simplify-merges` stays Unsupported (kitlib/git/fake/history.py `Walker.run`). Tests: tests/git/test_fake_full_history.py, with a real-git twin.
- Ref sets: `--all`, `--branches`, `--tags` and `--remotes` after an odd number of `--not` are subtracted, as git does (`rev-list X --not --branches --remotes --tags` is the commits X reaches that no branch, remote-tracking branch or tag does); a set given once on each side of a `--not` is Unsupported (kitlib/git/fake/history.py `REFSETS`). Before, the fake added them whatever came before, so that form counted every commit.
- Worktree config: when the repository's own config sets `extensions.worktreeConfig` (under any `core.repositoryformatversion`), the current worktree's `config.worktree` (`<gitdir>/config.worktree`; the main worktree's is in the common dir) is read after the repository config and before `GIT_CONFIG_COUNT` and `-c`; a missing file reads as empty (kitlib/git/fake/repo.py `Repo.config`). `git config --worktree`, `--show-origin` and `--show-scope`, and a `worktree add` from a worktree whose `config.worktree` exists (git copies it) stay Unsupported. So does a `config.worktree` that sets `core.worktree` or `core.bare` at any value (git honours both there; kitlib/git/fake/repo.py `Repo._check_format`), and `core.bare` true in the repository config when the repository is reached through a `.git` file (git then treats the worktree as bare; repo.py `discover`). Tests: tests/git/test_fake_differential.py `test_worktree_config`, with a real-git twin; the refusals in tests/git/test_fake_tier.py `FakeRefusesWhatWorktreeConfigLeavesUnmodelled`.
- Line-ending attributes: a `.gitattributes` at the root of the work tree is read (kitlib/git/fake/wt.py `Attributes`, `Convert`), as convert.c does for `text`, `-text`, `!text`, `text=auto`, `eol=lf` and `eol=crlf`: on hashing (add, commit -a, status, diff, `hash-object --path`) from the work tree's file, and on a checkout (`checkout -- <paths>`, switch, checkout, reset, clone, worktree add, merge --abort) from the result index's, as git reads them. A path no line rules follows `core.autocrlf` as before, and its CRLF check reads the index's stage 0 blob, else stage 2 on an unmerged path, as convert.c `has_crlf_in_index` does; `text` or `text=auto` with no `eol` follows `core.autocrlf` (`true` CRLF, `input` LF) and is Unsupported when it is unset or false (`core.eol` would decide). A ruled path that a checkout would write as other bytes is rewritten on a stat change alone, in whole seconds as Git for Windows compares them, and its size shortcut holds as in git (status shows ` M` for a changed size that hashes equal; diff does not). Unsupported: another attribute or a macro, a pattern with `/`, `\`, `[`, a leading `!` or `"`, a nested `.gitattributes` or a case variant of the name (tracked, on disk, or one a checkout would write: it is refused before the checkout writes anything), a root one that is not a regular file or is tracked but missing, `$GIT_DIR/info/attributes`, a global or `attr.tree`/`GIT_ATTR_SOURCE` file, and `core.safecrlf` other than warn on a converted path. A file is read only when a path is hashed or written, as git does. Tests: tests/git/test_fake_differential.py `test_gitattributes_line_endings`, `test_gitattributes_under_core_autocrlf`, `test_a_binary_index_blob_with_a_cr_leaves_conversion_on`, `test_an_unmerged_path_reads_its_stage_2_blob_for_a_crlf`, with a real-git twin; tests/git/test_fake_tier.py `FakeHashObjectPath`, `FakeRefusesWhatAttributesLeaveUnmodelled`.
- Stat data: like git, it trusts the index's stat data for an entry that is not racily clean, and compares ctime only under `core.trustctime` (tests.gitfixture sets it false). It ignores `core.checkStat`, except for the checkout of a path a `.gitattributes` line rules (above), where `minimal` drops ctime and any other value but `default` is Unsupported.
- Guard: while `KIT_FAKE_GIT` is 1, tests/__init__.py's audit hook raises when a test process starts git.
- The integration tier: a class marked `@real_git('<what the fake lacks>')` (tests/realgit.py) runs on real git. The integration tier covers hooks, the reflog, blame, `git grep`, `@{-N}` branch shorthand, shallow clones, combined diffs, directory rename detection, a broken loose ref, the git process itself (its environment, a timed-out call's process tree, counts of git children, a prune from another process) and checks of the fixture and of the guard's filesystem places against git. `kit_tests --real-git` runs every test on real git.
- The differential test: tests/git/test_fake_differential.py runs one script of the kit's git forms on two copies of one fixture, the fake answering on one and real git on the other, with author and committer dates pinned. It compares each command's exit code, stdout and `fatal:`/`error:` stderr. Then real git reads both end states, and `git fsck` checks what the fake wrote. A difference names the step and its argv. It is an integration-tier class, so every run that selects tests/git runs it: any change under kitlib/git runs the full suite. About 8 s for its 6 scenarios (a run at the branch, 6 tests in 8.0 s).
- Neither the landing gate nor the daily run runs the whole suite on real git. The landing gate's `--select` and a `--full` run the test modules the change adds or changes on real git as a second pass ("kit_tests" above), so a new or changed test cannot reach main having run only on the fake. A gate step's `daily_cmd` (docs/gate.md "Steps") running `kit_tests --full --both-tiers` runs the fake pass, then the real-git pass. That pass runs only the git, worktree and landing test modules (tests.git, tests.worktree, tests.gate.test_land*) and the daily-only `tests/stubs/test_new_repo.py`, which skips unless `KIT_FAKE_GIT` is 0 (`tiers.REAL_GIT_MODULES`), plus any test module the change adds or changes (none on main). `kit_tests: OK, both tiers green (fake git, real git)` is printed only when both pass. Each pass's own lines read `kit_tests [fake git]: ` or `kit_tests [real git]: `, so a pass verdict never matches the step's `kit_tests: OK` pattern. Only the last pass may give cpu slots back to the lock, and only the fake pass records unit times (kitlib/tooldeps/tiers.py). `--both-tiers` with `--real-git` or `--pid-hold` is a usage error.

## Temp folders

The kit temp folder for a checkout is `kitlib.config.user.work_temp`. It holds kit_tests' run folders, the default gate log base (docs/gate.md) and `kit-console-incidents.log` (`kitlib.proc.console`, docs/daily-full.md "The schedule"). A gate makes thousands of files a second there, so it keeps out of every folder sessions use as TEMP (`session_temps`). On Windows it is the first of these that is not a session temp, inside one or holding one:

- the machine config's `temp_dir` (docs/kit-json.md), when set;
- `kit-temp` (`kitlib.config.user.TEMP_DIR_NAME`, the kit's default), then `kit-work` (`WORK_DIR_NAME`), at the root of the checkout's drive, when the checkout is not on the drive of the user's temp folder (a Dev Drive, say);
- the system temp folder (`system_temp`: `%LOCALAPPDATA%/Temp`), then `kit-work` beside it (`%LOCALAPPDATA%/kit-work`).

When every one of them overlaps a session temp it is the first, so a gate is slow, never broken. Elsewhere than Windows it is `temp_dir`, else the system temp folder.

The shared temp folder (`kitlib.config.user.shared_temp`) holds the kit's few small files every process must find whatever TEMP it inherited: the gate's fallback log base, the worktree sweep log and private index folders (`kitlib.config.user.mkdtemp`). It is `temp_dir` when set and its drive (or share) is there, even when that is a session temp, made if missing (asking for the shared temp folder, even only to read from it, makes that folder); else, or when it cannot be made, the system temp folder. The tests never see this machine's `temp_dir` there: under the home fence with no `home` it is the system temp folder.

The session temps (`kitlib.config.user.session_temps`) are the machine config's `agent_temp_sweep` `dir` (the agents' temp folder, docs/machine-setup.md "Extras") and the user environment's `AGENT_TEMP`, `TEMP` and `TMP` (HKCU\Environment, expanded). With `temp_dir` set to the agents' temp folder, the kit temp folder is `kit-temp` at the drive root; on a machine whose agents' temp folder is that `kit-temp` (machine setup's default), it is `kit-work`. Where the user environment's `TEMP` is the system temp folder (Windows' default), a checkout on the system drive gets `%LOCALAPPDATA%/kit-work`.

It never reads the process's TEMP, TMP or AGENT_TEMP, so every process and shell gets the same folder. Folders that cannot be made, or a machine config that cannot be read, fall back with a note: run folders to `default_work_temp` (the same rule without `temp_dir`) when that is another folder, else to the process's temp folder; gate logs to `fallback_log_base`.

Tests that use `tempfile` follow their unit's TEMP, so they land in the run folder. tests/gitfixture.py's repositories and copies, and tests/tooldeps/test_pool.py's folders, go in `fixture_parent()`: the unit's TEMP under kit_tests; under a plain `python -m unittest`, one `kit-direct-*` folder per process in `default_work_temp`, kept out of that process's TEMP and AGENT_TEMP too, and removed at exit. Other `tempfile` use in a plain `python -m unittest` stays in the caller's TEMP.

Run folders a killed run leaves are removed by the next run on the machine (`kitlib.tooldeps.selfrun.prune_stale`, called by `run` outside the tests): only `kit-tests-*` and `kit-direct-*` folders directly in the run folder's parent, a day old by their own modification time, each claimed first by a rename that Windows refuses while a file in it is open. Links and junctions, as the entry or inside it, are never followed. Tests: tests/config/test_temp_on_z.py, tests/tooldeps/test_stale_runs.py.

Known limits: a launch that sets a custom `AGENT_TEMP` for its session only (not in the user environment or the machine config) is not a session temp, so the kit temp folder may be that folder. A `kit-direct-*` folder a killed direct run left is removed only when `default_work_temp` is also the parent of kit_tests' run folders (no `temp_dir`, or one that is a session temp).

## Home fence

A test must never read or write the real home folder: the machine config, the `~/.claude*` account folders, pm_watch's state. tests/__init__.py calls `kitlib.config.user.fence_home()` on import, which records the home folder the process starts with. From then on `kitlib.config.user.home_dir()` raises `HomeFenced` whenever the home resolves to that folder, so a test that forgets to give a home fails instead of reading the real one. `HomeFenced` is a BaseException, so `except Exception` around a home lookup cannot swallow it. Production never calls `fence_home()` and never sets the marker below, so a real run is unfenced: there `home_dir()` reads one environment variable more and asks Windows nothing (tests/config/test_home_fence.py `RealRunTest`).

- Covered: every lookup through `home_dir()`, which includes `locate`, `user_config` and every other machine config read with no `home`. The machine-path check's `kitlib.machinepaths.load_config` (and so `check`, `scan` and `scan_staged` with no `cfg`) reads `machine_path_folders` through it, so a test of those runs under a temp home (tests/machinepaths/test_machinepaths.py `PlantedTree`). The launcher's `current_account`, the coordinator start's `machine` check, pm_watch's `default_state_file` (when LOCALAPPDATA is unset) and the plugin refresh's `account_folders` and `Runner` also look up the home through it. So does the guard's shell reader when it is given no `home`: `kitlib.guard.shell.home_folder`, which `resolve_path` reads for `~`, `home_text` for `~` and a home variable, and `cd_target` for a bare `cd` (tests/guard/test_shell.py `HomeFolder`). A plain `os.path.expanduser('~')` elsewhere is not fenced.
- The processes a test starts: a kit tool started by a test is fenced too, through a marker in its environment. The marker is `KIT_HOME_FENCE` (`kitlib.config.user.FENCE_ENV`), and its value is the home folder the test run started with. Only `kitlib.config.user.fence_env` sets it, and it keeps a marker that is already there, so a nested run under a temp home keeps the outer run's home. tools/kit_tests.py marks the units' environment (`run_pass`, and the import that `--list` does), because a pool worker (kitlib/tooldeps/pool_worker.py) replaces its environment for each unit. tests/__init__.py marks a direct `python -m unittest` run. `home_dir()` reads the marker at each call, so a process that never imports the tests package refuses the real home as the test process does.
- What is refused: in a fenced or marked process `home_dir()` refuses the folder `fence_home()` recorded, the folder the marker names, and the profile folder Windows itself reports (`kitlib.config.user.real_profile`: SHGetKnownFolderPath, never USERPROFILE or HOME). A marker that names some other folder therefore cannot unfence the real profile. Each folder is compared as spelled and as the folder it really is (`os.path.realpath`), so a junction, a symlink or a short (8.3) name of a real home is refused. The extended-length prefix (`\\?\`, or `\\?\UNC\` before a share) is dropped before comparing (`kitlib.config.user._home_key`), because `os.path.abspath` and `os.path.realpath` keep it. When Windows does not name the profile folder, every lookup is refused (`UNPROVEN_MESSAGE`): no home can then be shown to be a temp one.
- The machine's lock store: kitlib/lock/store.py finds the profile folder from Windows itself (`profile_dir`), so no temp home moves the store and `home_dir()` never sees it. It has a fence of its own, `kitlib.lock.store.fence`: in a fenced or marked process (`kitlib.config.user.fenced()`, which asks Windows nothing) `Store.path` and `Store.mutex_name` raise `HomeFenced` for the machine's store, so nothing under it is read, written or locked, and `kitlib.lock.site.load` refuses the machine config's lock settings (`kitlib.lock.store.machine_home`). Building `Store()` and reading its `root` stay legal: they open nothing. A test uses a scratch store, `Store(root=<a temp folder>)` (tests/lock/helpers.py `StoreCase`), which is not fenced. Limits: a root that reaches the machine's folder by another spelling (a junction, a short name, the extended-length prefix, a share) counts as a scratch store, because `Store.__init__` compares the two absolute paths without resolving them (`os.path.normcase` only); and two modules work on a path the environment names, with no `Store`: `kitlib.lock.giveback.Offer` on the one `MACHINE_LOCK_GIVE_BACK` names, and kitlib/lock/bg_client.py, which only reads the `control.json` that `MACHINE_LOCK_BG_CONTROL` or `MACHINE_LOCK_BG_ROOT` names. Tests: tests/lock/test_store_fence.py, tests/lock/test_site.py `Fenced` and `MachineHome`, tests/config/test_fenced.py.
- Not fenced: a child whose environment a test built without the marker, and a child that is not the kit's Python code. A known limit: a real home spelled as a network share of this machine (the administrative share of its drive, for one) is not refused. `os.path.realpath` leaves a share path as spelled, and `_home_key` resolves no share to the folder behind it.
- Giving a test a home: pass `home` (or the folders themselves) where the code takes one, or use tests/home.py. `temp_home(case)` points USERPROFILE and HOME at a new empty temp folder for the rest of the test, and `TempHomeCase` does that for every test of a class (a subclass with its own setUp calls `super().setUp()` first). The code under test keeps its real path; only where the home resolves changes, so it reads an empty machine config.
- Giving a child a home: a kit tool that a test starts needs the temp home as well. A child started with this process's environment, or with `gitfixture.fixture_env()` (a copy of it), gets what `temp_home` set. A test that builds the child's environment passes USERPROFILE and HOME in it: tests/landed/test_landed.py `Fixture.cli` does, for tools/landed.py, which looks up the kit temp. hosts/claude/shell/hooks/guard.py blocks with exit 2 on any failure, the fence's refusal included, so a test that expects a block from a guard with the real home passes without reaching its own reason; tests/guard/test_entry.py `Entry.setUp` gives every guard it starts a temp home. kitlib/gate/runner.py `_run_check` logs any exception a check raises and reports the check as failed, so a refusal in a gate that a test starts would pass a test that expects a failing check. tests/gate/fixtures.py `test_env` therefore carries a temp home for the gate and landing processes the gate tests start, and tests/guard/test_prepush.py `PrePushCase.push` passes one to the pre-push hook. Both use `tests.home.child_home()`: one temp folder for each test process, removed at exit, for a helper that has no test case to clean up with. A child that must run as a real run does gets `tests.home.unmarked_env()`, the environment without the marker. A temp home does not lift the lock store's fence: a marked child that uses the machine's lock store raises `HomeFenced` whatever its home (a guard child then exits 2), so the test gives it a scratch store: `store=` in process, the hidden `--test-root` of tools/machine_lock.py and tools/lock_release_check.py for a child.
- The machine config: a temp home has no PM repo pointer, since under the tests the pointer is the environment's `KIT_PM_REPO_FENCE` (`kitlib.config.pointer.FENCE_ENV`, tests/home.py `PM_REPO_FENCE_ENV`) and the registry is never read; `tests/home.py` `machine_config(home, body, case=)` makes a PM repository for the temp home and points it there. The session-start machine config check (`kitlib.pmstart.configcheck.lines`) is stubbed to print nothing by `tests.pmstart.stub_config_lines`, which the `__init__.py` of tests/pmstart, tests/coordinatorstart and tests/hoststart call on import. The stub replaces the module attribute for the whole process and is never undone, so once one of those packages is imported it holds for every later module that process runs (a kit_tests pool worker runs many), not only those three packages; its own tests (tests/pmstart/test_config_check.py, tests/coordinatorstart/test_machine_config.py, tests/hoststart/test_machine_config_check.py) put the real one back on a temp home or pass their own.
- Testing the fence itself: `fence_decoy(case)` makes a temp home and records it as the fenced one, so the same test without the fence would read an empty temp folder, not the real home. Tests: tests/config/test_home_fence.py and the `test_home_fence` modules of tests/coordinatorstart, tests/pluginsource and tests/pmwatch. In tests/config/test_home_fence.py, `ChildFenceTest` covers a marked child and a kit tool, `SpellingTest` the junction, the short name (the short-name test skips on a volume that gives no short names) and the extended-length prefix, `HelperHomeTest` the temp home of `child_home` and `test_env`, `FailClosedTest` the refusal when Windows does not answer, `MarkerTest` and `FenceEnvTest` the marker, and `ProfileTest` the profile folder. tests/tooldeps/test_kit_tests_base.py `HomeFenceEnvironment` shows that kit_tests marks the units.
- The one exception: `tests.real_install_config()`. The scrub tests check the kit's files against this install's own names, which only the real machine config holds. These are tests/shipped.py `install_patterns`, `forbidden` and `violations` with no `home`, and tests/scrub/test_generic.py `install_names`. tests/__init__.py records the real home before it calls `fence_home()`. `real_install_config()` reads the machine config file under that home explicitly and returns only its install-name keys (`tests.install_config`): `scrub_patterns`, `machine_path_folders`, pm_start's `sessions_file`, `repos` and `hub_url`, and the `cap` of coordinator_start, else of its old-name key (kitlib/config/user.py SCHEMA). When there is no config file, the calling test raises `unittest.SkipTest` with the reason (tests/shipped.py `NO_INSTALL_NAMES`), so the test shows as skipped and does not pass without the names. `install_patterns()` does the same when the config sets no `scrub_patterns`. The folders of `machine_path_folders` are refused as "machine path" by tests/shipped.py `machine_patterns`, which never skips, and tests/scrub/test_builtin.py `configured_folders` passes them to the built-in scrub; while the key is unset, tests/shipped.py `real_machine_folders` prints the machine-path check's NOTE (kitlib/machinepaths `UNSET_NOTE`) once per test process. The base patterns (ruling ids and user-profile paths: tests/shipped.py `BASE_FORBIDDEN`) and `machine_patterns` run first in any case: tests/shipped.py `scan` and `violations` return a finding of theirs, so the test fails on it, and raise the skip only when that scan is clean. A malformed config fails the test (ConfigError). Tests: tests/agents/test_install_patterns.py `RealScrubPatternsTest`, which also shows that it opens only the machine config file and returns no other key.

## Platform markers and the ratchet

The Linux port (docs/linux-support-plan.md, section 4) runs the suite where much of it cannot pass yet. Two pieces hold it to a list that only shrinks.

- Markers, tests/platforms.py: `@windows_only(reason)` and `@posix_only(reason)` mark a test class or method that runs on one platform only. Each applies `unittest.skipUnless` with the reason as the skip text, so the test carries `__unittest_skip__` as a hand-written skip does (`--list` counts it the same), and records `(platform, reason)` in `REASONS` under `module.qualname`. A marker with no reason raises `ValueError`. The platform is read when the marker is applied (`platforms.WINDOWS`, `platforms.POSIX`; a test patches those). The module imports no kitlib, so a test module can name its markers where kitlib does not import. A test under tests/ never skips by hand on `os.name`, `sys.platform` or `WINDOWS` (a `skipUnless`, a `skipIf`, or a `unittest.skip` under such an `if`); it uses a marker. Another condition stays a `skipUnless` of its own under the marker. Tests: tests/ci/test_platforms.py, tests/ci/test_platform_skips.py.
- The ratchet, tools/ci_ratchet.py (kitlib/ci/ratchet.py): `ci_ratchet.py [-C ROOT] [--baseline PATH]` runs the whole suite in one child, `python -c` running `unittest discover -s tests -t .` under ROOT, which prints one result line (`kit-ci-ratchet: ` and JSON): the failing ids, the import failures among them, the number run and the marker counts by reason. Failing means a failure, an error, an unexpected success or a module that does not import (`unittest.loader._FailedTest.<module>`); a subtest's failure counts as its test's. The child's environment is the caller's without the session's kit binding (kitlib/tooldeps/childenv.py `scrubbed`); the tests package sets its own fences.
- The baseline: one test id per line, sorted, none twice, no tab and no space at either end; blank lines and `#` lines are skipped. The default is tests/linux-baseline.txt on Linux and tests/windows-baseline.txt on Windows, where no file means an empty list; `--baseline` names another, which must exist. A branch that makes a listed test pass takes it out in the same branch.
- Exit codes: 0 green (the failing ids are exactly the baseline), 1 a difference (`NEW FAILURE: <id>`, or `STALE: <id>` for a listed test that passes or is gone), 2 a usage error, a malformed baseline (`refused:`) or a broken run (`BROKEN RUN: <why>` and the output's last lines). A run is broken when the tests package does not import, the child dies, times out (`RUN_TIMEOUT`, 3600 s) or prints no result line, or no test runs: never green, whatever the baseline says.
- Until slice 2 of the plan, every Linux run is a broken run: the tests package fails to import (tests/__init__ imports kitlib.config.pointer, which loads kitlib.git, then kitlib.proc.win32 and `ctypes.WinDLL`). tests/linux-baseline.txt is empty until then. The ratchet itself loads no kitlib.proc beyond kitlib/__init__'s console hook, and no kitlib.config or kitlib.git; it starts its child with an explicit `creationflags=`.
- On Windows the gate (`gate.py --full`) runs the suite; the ratchet is not run there on the whole suite. Tests: tests/ci/test_ratchet.py, each case on a small test tree in a temp folder with a real child.

## pytests

`tools/pytests.py` (kitlib/pytests) is the parallel tools-test runner.

```
pytests.py [-C DIR] [--audit] [--jobs N] [--unit-timeout S] <module|module.Class> ...
pytests.py [-C DIR] --all ...
pytests.py [-C DIR] --select [--base B] [--merged] [--changed PATH ...] [--plan] [--audit]
add --pid-hold to any run: the opt-in pid hold (section "The pid shield")
```

- **Units.** Each unit (a module, a shard of one, or a class with `split_classes`) runs in a fresh child `python <kit>/tools/pytests.py --child`. The child's cwd is the checkout root, and the checkout's tools folder is first on sys.path.
- **Order.** Up to `jobs` units run at once. `serial` units run afterwards, one at a time.
- **The log's last lines** (kitlib/pytests/runner.py `run`):
  - `pysel floor N`: the static `def test_` count of what was named;
  - `Ran N tests in Xs`;
  - `OK` or `FAILED (units: ...)`.
- **Exit codes.** 0 for all passed, nothing selected, or `--plan`; 1 when a unit failed or timed out.
- **Refusals (exit 2).** A checkout without its tools folder. A `--select` whose change list git could not read: no test runs, and the last line is `pytests FAILED | no test ran: git could not read the change list`.
- **`--select`.** Takes `git diff --name-only --no-renames` from the merge-base with `--base` (default: gate.md "Default base"), plus untracked files, or the `--changed` list. These go through kitlib.tooldeps' selection.
- **`--audit`.** Fails a unit (`[FAIL] audit:` lines) for any read under the checkout that the tool_tests tables do not map to its module.

Keys, all in "tool_tests":

| Key | Default | Meaning |
|---|---|---|
| `shards` | `{}` | module -> number of class-shards |
| `serial` | `[]` | modules or `module.Class` run alone, after the pool |
| `split_classes` | false | one unit per TestCase class |
| `jobs_max`, `jobs_divisor` | 6, 4 | default jobs = min(jobs_max, max(2, cpus // jobs_divisor)) |
| `jobs_env` | none | an environment variable whose integer overrides the default job count; kept only as the source used it (no env override of root or config) |
| `unit_timeout` | 3600 | seconds before a unit is killed and reported TIMEOUT |

### Running it from the gate

`python_tests` and `python_tests_floor` are no gate keys: a `.kit.json` that sets one fails to load (unknown key, kitlib/config/schema.py `SECTIONS`; docs/gate.md "Not ported", the `python_tests` row). Write the run as an ordinary step instead, and put the floor in its `pass` patterns:

```json
{"name": "tools-tests",
 "globs": ["tools/**"],
 "cmd": ["{python}", "{here}/pytests.py", "-C", "{root}", "--select", "--base", "{base}"],
 "merged_args": ["--merged"],
 "pass": ["^OK$", "^Ran ([5-9]\d|\d{3,}) tests in "]}
```

- `{here}` is the kit's tools folder (kitlib/gate/steps.py `mapping`).
- The second `pass` pattern is a floor of 50 tests. Set it to the repository's own count.
- A run that selects nothing prints no `Ran` line. With a floor, that run fails the step, so give the step `globs` that match only when tests would be selected.

### What was not ported

- The PM kit's `-C` hand-off (chdir_main, KIT_CALLER_CWD, OWN_COPY), the repo guard, and the KIT_REPO_ROOT / KIT_CONFIG overrides. The root is always `-C`.
- The POSIX kill branch. The kit is Windows only.
- The `_kit_module` loader. The child imports kitlib.

## The pid shield

kitlib/proc/shield.py (`shield`, `release`, `process_dacl`) adds one entry to a child process's DACL that denies PROCESS_TERMINATE to Everyone. A stale `taskkill /PID <n> /T /F` aimed at a dead shell then cannot end the child, while a job's TerminateJobObject still can.

- Call it while the child is still suspended (kitlib.proc.job `Job.start`'s `before_resume`).
- A process with a NULL DACL is left as it is (OSError).
- It is not wired into the gate.
- Its users are kitlib.pytests and kit_tests' pool. `runner.shield_unit` shields each unit's own process and each pool worker (kitlib/tooldeps/pool.py), and never the processes a unit starts.
- A unit that cannot be shielded runs unshielded, with a `pytests: could not shield ...` note.
- On Linux there is no shield (a process has no DACL): `shield_unit` raises PlatformUnsupported, so every unit and worker runs unshielded with that note, and its job's cgroup ends it.
- Never end a unit by its pid. End the runner: KILL_ON_JOB_CLOSE ends its units.

The pid hold covers the processes a unit starts. A test's git can be given the pid of a shell that has just died, and the second stale taskkill then ends it with exit 1 and no output. That is the same shape as a real exit-1 answer, such as `merge-base --is-ancestor`'s NO.

Without the hold, the ancestry question is still read safely. kitlib/git/refs.py `is_ancestor` asks `git rev-list -n 1 <descendant>^{commit}..<ancestor>^{commit}`, whose YES (nothing printed) and NO (one commit) both exit 0, so a killed git gives no answer (None) rather than a NO. Each NO is then confirmed with `git merge-base --independent`, because rev-list's walk can stop early under skewed commit dates and print a commit the descendant does reach. A confirmation that fails is also no answer. The kit's former raw `merge-base --is-ancestor` callers in kitlib/worktree, kitlib/pmdata, kitlib/redfirst and kitlib/preflight/board.py now call it.

- **Opt-in, never in the gate.** `--pid-hold` on `tools/kit_tests.py` or `tools/pytests.py` turns it on; without it no hold is made. It is for agent test runs. The gate refuses `--pid-hold` in `setup`, in a step's `cmd`, `full_cmd`, `daily_cmd` or `merged_args` (kitlib/gate/steps.py `unsupported`, `build`). There is no environment switch, so nothing can leak it into a gate step.
- kitlib/pytests/runner.py `PidHoldRun.start` starts this process's `PidHold` (kitlib/proc/shield.py `hold()`). It warms the hold for `WARM` (3 s), then publishes it. kit_tests starts it before it copies the units' environment, so the published hold reaches pooled and `--jobs 1` units alike.
- The hold keeps every pid of the user's processes unused until 3 s after its process exits. A stale kill then names an exited process and ends nothing.
- A run that inherits a running hold (`shield.inherited()`) makes no hold of its own.
- **Reporting.** The run prints `pid hold: on (...)` before the first unit and `pid hold: held to the end of the run` before its summary (pytests: before `pysel floor`, so the last line stays `OK` or `FAILED`). A hold that cannot be made, for any reason, prints `pid hold: FAILED, this run is NOT held (<error>)` at the start and `pid hold: FAILED at the start, this run was NOT held (<error>)` at the end; the tests still run. A hold that stops during the run prints `pid hold: FAILED during the run, units after it stopped were NOT held (<error>)` at the end. Unlike the shield's messages these say FAILED: the gate never runs them.
- The gate starts no hold of its own.

Other reads whose "no" was exit 1 with no output now ask in a form that exits 0 either way:

- kitlib/git/refs.py `ref_commit` asks `for-each-ref <ref>`, so a missing ref is exit 0 with no line. A broken loose ref (a file holding garbage) is also exit 0 with no line, but git warns "ignoring broken ref <ref>" on stderr, so no line with a stderr line naming the ref is no answer (tests/git/test_git.py `_Parity.test_a_broken_loose_ref_is_no_answer_and_its_siblings_still_answer`). Other stderr is not about the ref: "no ref" then stands once `resolve(known=True)` confirms it. A ref whose name differs only in case (`refs/heads/Main` against a loose `refs/heads/main`, one file on a case-insensitive file system) is no answer, never "no ref". The fake git imitates the broken-ref warning in for-each-ref and in `rev-parse --verify` (kitlib/git/fake/refs.py `BrokenRef`). The backlog store (kitlib/backlog/store.py, at_landing.py), kitlib/pmdata/init.py and kitlib/worktree/remove.py `pulled_by` read refs this way.
- `refs.current_branch` asks `branch --show-current`, which prints nothing on a detached HEAD.
- `refs.merge_base` confirms a "no common commit" by comparing the root commits each side reaches (`rev-list --max-parents=0`). In a shallow clone the cut-off commits read as roots, so there "none" is no answer (tests/reviewpack/test_base.py `ShallowClone`).
- kitlib/pmdata/init.py reads config with `config --list -z` and filters it in Python.
- `refs.resolve` asks `rev-parse --verify` without `--quiet`, so "no such rev" is exit 128 with `refs.NO_SUCH_REV` as the last stderr line, and a silent exit 1 is no answer. A stray stderr line before it (a config deprecation warning, "unable to access") leaves the answer standing; one that names the rev, or a ref ending in `/<rev>`, does not: git 2.55 prints "warning: ignoring broken ref <ref>" before NO_SUCH_REV for a broken loose ref (tests/git/test_git.py `_Parity.test_a_broken_loose_ref_is_no_answer_from_resolve_either`). GIT_TRACE output names the rev in the traced command line, so under GIT_TRACE the answer is no answer (it fails closed). By default both still return None, with different whys, so every caller's "missing" path is unchanged; `known=True` returns `('', None)` for "no such rev". kitlib/worktree/remove.py `tag_tip` and `branch_tip` use `known=True`: a killed tag read refuses the abandon ("cannot read tag") instead of taking the name for free.
- A second pass moved the `rev-parse --verify --quiet` reads and the `refs.resolve` callers that read a no-answer None as "missing" onto `known=True`, `ref_commit` or `merge_in_progress`. kitlib/forbidden `default_base` (a kill picked master), kitlib/syncbase (the target read, and the MERGE_HEAD reads through `refs.merge_in_progress`: after a clean `merge --no-commit` a kill read as a fast-forward, which left the merge uncommitted and reported it merged; and a MERGE_MSG path that cannot be read, which reached `open('')` and now refuses with the merge left in progress, tests/syncbase/test_sync.py `test_a_killed_merge_msg_path_read_is_refused_and_the_merge_left_as_is`), kitlib/worktree/new.py, kitlib/docs/budget.py and kitlib/reviewpack/trailers.py all refuse on no answer. kitlib/gate/cleanup.py reports the branch `kept` with the reason. kitlib/backlog/landable.py says "cannot read refs/heads/<branch>" where it used to say "no local branch of that name". kitlib/redfirst/run.py `rev` says "whether <rev> names a commit in <dir> could not be read" where it used to say "does not name a commit". kitlib/landed prints UNKNOWN for the local main and for an ancestry read that gives no answer (`contains` no longer turns `is_ancestor`'s None into "no"). When `remote get-url` gives no answer, landed answers CANNOT ANSWER. The local main decides only on exit 2, git's "No such remote", and only in a clone with no remotes at all. If the remote is missing but others exist, landed answers CANNOT ANSWER and names them. kitlib/preflight/settings.py drops `--quiet`, and a missing or unread base still shows as `?`. Each refusal has a test that stubs `cmd._run` with `(1, b'', b'')` (redfirst's also stubs `cmd.subprocess_run`). Two sites have no red test, because a kill gave the right outcome before too: syncbase `arm_merge_msg` (not armed) and preflight settings (`?`).

Reads that still take a quiet exit 1 as an answer include kitlib/guard/prepush.py (`config --get-regexp`, `rev-parse --quiet --verify`), kitlib/commit `rev-parse -q --verify` and kitlib/hubbacklog `rev-parse --verify -q`. Default-mode `refs.resolve` callers that drop the why remain, such as kitlib/gate/runner.py, kitlib/gate/land.py and kitlib/records/landing.py.

### What the hold costs

`PidHold._pass` measured 11.5-14.8% of one core while the hold runs (kitlib/proc/shield.py, comment on `_pass`).

The whole kit suite, measured 2026-10-10 on the development machine (12 physical cores, other agents' runs sharing it). Every run was `python tools/kit_tests.py --full [--pid-hold]` booked through the machine lock with `--kind engine-test --cores 4` (8 logical processors, 8 jobs; the lock now caps engine-test, renamed `test`, at `medium_cores`, 2 on the default layout, so a rerun books `--kind test --cores 2`), 3794 tests in 170 modules, all passing. "Suite" is kit_tests' own `OK in Ns`; "wall" is the whole lock run, booking and the hold's warm-up included.

| Runs | Hold | Suite (s) | Wall (s) |
|---|---|---|---|
| solo | off | 95, 83 | 96, 84 |
| solo | on | 88, 86 | 92, 90 |
| 2 at once | off | 112, 106 | 113 |
| 2 at once | on | 115, 107 | 118 |

- The steady cost does not show above run-to-run noise: two solo runs without the hold differed by 12 s.
- The fixed cost is the 3 s warm-up, paid once per run before the first unit.
- Two holds at once (one per run) added 1-3 s per run and 5 s to the pair's wall time, inside the same noise.
- Whether the gate should ever use the hold is open (docs/go-live.md).
