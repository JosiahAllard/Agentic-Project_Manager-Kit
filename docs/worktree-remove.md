# Worktree remove

Remove a workstream's worktree only when its work has landed and nothing holds it, abandon unlanded work under a tag, and sweep landed idle worktrees nightly. On Windows `git worktree remove` destroys the worktree's registration when it fails partway, so every check runs before git is called.

## Tools

- `tools/worktree_remove.py [-C DIR] <path or slug> [--keep-branch]`: check, remove, then `git branch -d` (never `-D`).
- `... <path or slug> --abandon "<why>" [--keep-branch]`: for UNLANDED work. Tags the tip `archive/<slug>`, then removes the tree and the branch.
  - A LANDED tree that holds uncommitted or untracked work (the plain verb refuses it) is abandoned too (`kitlib.worktree.remove._abandon_landed_dirty`). The plain verb's checks run first. Then the work, tracked changes and untracked files that are not ignored, is saved as a commit on the tip, written through a throwaway index (`snapshot_tree`), under the annotated tag `archive/<slug>`. The line is `saved     uncommitted work (<n>) of <path> as <commit> under tag archive/<slug> ...`, with the `git diff` that shows it. The tree is read again and must still match the saved commit, with HEAD unmoved. Then it is reset to its HEAD (`git reset --hard`, `git clean -d`, never `-x`), removed through `git_remove`, and the branch goes with `git branch -d`. A rerun reuses a tag that already holds exactly this work on this tip. A tag on anything else refuses, nothing changed. A file written between that last match and the reset is lost: the window is narrowed, not closed. A landed, clean tree is still refused (`nothing to abandon`).
- Both verbs also take, by its PATH only, a registered DETACHED worktree outside every worktree folder (an agent's red-run tree): the same checks, then removed with no branch to delete; `--abandon` tags its HEAD `archive/<folder name>`. Refused, nothing changed: the main checkout, a path inside it or holding it, a link or junction on the way (the path and each folder above it, checked one by one with `holders.linked`, so an 8.3 short name or another spelling of the same folders is the same tree, not a link: `link_on_the_way`), an exempt folder, an unregistered folder, a tree holding another registered worktree, a locked tree and no HEAD; `--abandon` also refuses a tree on a branch (a workstream's, under the worktree folder), which only the plain verb takes, as below; a missing folder is `nothing` (exit 0) (`kitlib.worktree.remove.outside_target`). A relative path is taken against the caller's directory.
  - The plain verb alone (`remove`; the owner's rule: only that deliberate by-path call clears one) also takes such a tree on a BRANCH, named by its path, registered and unlocked, unless that branch is the main branch (`is on the main branch`, refused in `outside_target`, before the merge check; `same_name`, so any case): every later check still runs (the merge check judges the branch, then the reflog, holders, work, links and `last_look`), and `git branch -d` deletes the branch after the removal (`--keep-branch` keeps it). `--abandon`, the slug form, the landing cleanup and `--classify --apply` (both call `_remove` without `branch_ok`) refuse it (`only a detached tree is removed here`).
  - Its HEAD reflog (`<git dir>/logs/HEAD`) and per-worktree refs, all deleted with the tree, are checked before any git write, as `--scratch` checks them (`kept_reflog`, with `kitlib.worktree.scratch` `reflog` and `reachable`): a commit no ref reaches is the owner's call, never this tool's. The plain verb refuses when HEAD or any of those commits is in no branch, remote-tracking branch or tag (`which no ref reaches`), even when HEAD itself is in the base. `--abandon` refuses too, naming each such commit that the tag on HEAD would not keep either; it tags nothing. A reflog or ref list that cannot be read, or a reach that cannot be told, refuses. The HEAD held to all this is the one the merge check found in the base (`merge_check`'s `seen`), and just before `git worktree remove` both verbs read HEAD, the reflog and the per-worktree refs again (`scratch.unmoved`) and refuse when any moved (`HEAD moved after it was checked`, `its HEAD reflog or a per-worktree ref changed after it was checked`).
  - A SLUG never names such a tree: with no folder under the worktree folder but an outside tree of that name, it is refused (exit 1) with each path-form command (`slug_redirect`): `"<path>" --scratch`, `"<path>"` and `"<path>" --abandon "<why>"`. For an agent's red-run tree under a temp folder use `--scratch`: it needs only HEAD and the reflog in some ref, and it restores uncommitted files git already holds, where the plain verb needs HEAD in the base and refuses any uncommitted file. The plain verb is for a tree whose HEAD has landed, `--abandon` for unlanded work worth a tag. A worktree list that cannot be read for a missing slug is still `nothing` (exit 0), after a `note` line saying an outside tree of that name could not be looked for.
  - Printed reruns name an outside tree by its quoted path (`handle`). The landing cleanup (`kitlib/gate/cleanup.py`) removes a landed branch's tree, and an outside tree on a branch is refused (its refusal names the plain verb by path).
- A DETACHED tree in a worktree folder gets the same HEAD reflog and per-worktree ref check as an outside tree, and the same second read just before git (`kept_reflog`, `unmoved`), from both verbs and so from the landing cleanup and `--classify --apply`: a commit made there and left by a checkout lives only in that reflog, which `git worktree remove` deletes. A tree on a branch in a worktree folder is not checked this way by either verb or the landing cleanup, though a commit it made detached and left by checking its branch out again is only in that reflog too: only `--classify --apply` checks that case (`classify.reflog_skip`).
- `.kit.json` `worktree_remove.branch_template` is one `{slug}` template or a list of them (`phase/{slug}` plus `records/{slug}`): a slug-form removal is refused unless the worktree is on the branch one entry makes from its folder name (the refusal lists every candidate). A DETACHED tree has no branch, so the template is not asked of it: both verbs take it by its slug, and the HEAD reflog check above still holds it. An empty list, a non-string entry or an entry without exactly one `{slug}` is a configuration error (exit 2), never an allow.
- `... <branch> --branch`: a LANDED local branch with no worktree, deleted with `git branch -d` (never `-D`). Refused, with nothing changed: the main branch, a branch any worktree has checked out (use the slug form), a tip not in `<remote>/<main_branch>` as it stands (the refusal names `--branch --abandon`), and a backlog record still pulled by the branch (an open claim, as the sweep reads it). A missing branch is `nothing` (exit 0). The remote branch is not touched.
- `... <branch> --branch --abandon "<why>"`: for an UNLANDED local branch with no worktree. Tags the tip `archive/<name>` (`<name>` is the branch with the prefix and suffix of the first `branch_template` entry it fits cut off, else the whole branch name), then deletes the branch with `git update-ref -d` held to the tagged tip. Refuses the main branch, a missing branch, a branch any worktree has checked out (use the slug form), and a branch already in the pushed base (the refusal names `<branch> --branch`, or the landing cleanup `land.py --sweep-landed`). The remote branch is not touched, as in `--abandon`. `--keep-branch` is a usage error here.
- `... <branch> --mark-stale "<why>"`: marks the worktree of an UNLANDED branch stale, so the nightly sweep abandons it (see "Stale marks"). The branch is taken exactly, as by `--branch`, and must have a worktree under a worktree folder. Refused, nothing written: anything `--abandon` would refuse (the main branch, an exempt, missing or locked tree, the template, work already in the base, uncommitted or untracked files, ignored files that are not build output, a link inside), a `disposable_untracked` file (the sweep counts it as dirt, so the mark would never be acted on), an open claim on the branch, a live tree (`--classify`'s L rule), an empty reason, a marks file that cannot be read, and a branch with no worktree (the refusal names `--branch --abandon`). A rerun replaces the mark (`remarked`) (`kitlib.worktree.marks.mark`).
- `... <branch> --unmark-stale`: clears that mark (`cleared`). No mark is `nothing` (exit 0) (`marks.unmark`).
- `--tag archive/<name>`, with either `--abandon` form: the tag a ruling names, in place of `archive/<slug>` (for one, an earlier tag `archive/api-<slug>` already held the work). It is taken as named, never the next free one: made when absent, reused when it already holds the tip (for a landed tree with uncommitted work, this saved work), refused on any other commit, with nothing changed. A name that does not start `archive/`, or that `git check-ref-format` refuses, is refused (exit 1, `kitlib.worktree.remove.tag_name_refusal`). `--tag` without `--abandon`, given twice or with no name is a usage error (exit 2, `split_tag` in `tools/worktree_remove.py`).
- The UNLANDED refusals (`merge_check`, and `_remove_branch` for `--branch`) name `--abandon "<why>"` first, as the supported route, run on the owner's or the PM's ruling, keeping the commits under an `archive/` tag. The tree form then still prints the owner's raw `git worktree remove` and `git branch -D`, labelled for the owner's own terminal only: the Action Hub refuses them as a to-do (docs/action-hub.md "todos/T-NNN (or a generated id for the owner's own items)"). Neither verb has an override. The guard's `git-worktree-remove` rule has two exceptions for a raw `git worktree remove`: it passes any tree under a temp root (`jail.temp_roots`, a scratch tree) before any check, and an unlanded tree whose stale mark holds (see "Stale marks").
- Both `--branch` forms take the name exactly: one `git check-ref-format --branch` does not echo back (`main~1`, `main^`, `main@{1}`, `@{-1}`) or one differing from a branch only in case (`Main`) is refused, and the main-branch and checked-out checks ignore case (`kitlib.worktree.remove.local_branch`).
- `... <path> --scratch`: a SCRATCH worktree, a detached tree an agent made under its temp folder (red evidence against an older commit). It takes exactly one path and no other option. It removes the tree only when every one of these holds (`kitlib.worktree.scratch`):
  - The path is under a scratch root: `AGENT_TEMP`, `TEMP`, `TMP` or the system temp folder, `%LOCALAPPDATA%\Temp` (`kitlib.config.user.system_temp`, never the machine config's `temp_dir`), read from the environment. A root that is not an existing absolute folder, is reached through a link, or is a drive root, the home folder or above it, or holds the main checkout is no root. A path inside the main checkout or a worktree folder (`homes_of`, junctions resolved) is a workstream worktree: use the slug form. The roots come from the caller's environment, so they are a scope hint, not protection: the reachability and content checks below are what protect the tree.
  - No link or junction is on the way. The tree is registered, not locked, detached, and holds no other registered worktree. Its HEAD, every commit in its HEAD reflog (`<git dir>/logs/HEAD`, deleted with the tree) and the tip of each of its per-worktree refs (`refs/worktree`, `refs/bisect`, `refs/rewritten`, deleted with it too; one that is not a commit refuses: `scratch.reflog`) are in a branch, remote-tracking branch or tag; a commit no ref reaches is the owner's call, never this tool's. Among the branch, remote-tracking and tag refs asked, one that is a blob or tree is skipped (a tag object is peeled), and a failed `merge-base` proves nothing: it refuses only when no other ref proves the commit reachable.
  - Nothing holds it, no link is inside it, and its ignored files are build output only (the rules above).
  - Every uncommitted file, and its staged blob, equals `<ref>:<path>` for some ref under `refs/heads` or `refs/remotes`: the same path only. A rename, copy, conflict, type change, quoted path or nested repository is refused.
  - It then checks each file once more, resets the index, checks tracked files out of HEAD (`GIT_LITERAL_PATHSPECS=1`), deletes untracked ones, each re-hashed with no link on its way just before (`restored  N file(s) found in git at their paths`), reads HEAD, the reflog and the per-worktree refs again (`HEAD moved after it was checked`, `its HEAD reflog or a per-worktree ref changed after it was checked`) and removes the tree through `git_remove` (see "The last status read"), never with `--force`. A status, worktree list, reflog or hash that cannot be read refuses. An unregistered folder is never deleted (`refused ... not a registered worktree`), and a missing one is `nothing` (exit 0). A file rewritten after its check is kept: `changed after it was checked`. The window from that check to git is narrowed, not closed. So is the one from the last HEAD and reflog read to `git worktree remove`: a commit made inside it is removed with the tree. The reflog is read from `logs/HEAD`, so a repository whose ref format is not `files` (reftable) is refused.
  - To make red evidence without leaving such a tree, use `tools/redfirst.py` (docs/redfirst.md).
- `... --check`: lists stumps and orphans (exit 1 if any) and, for information, landed worktrees.
- `... --sweep-merged [--apply]`: the nightly sweep. Without `--apply` it is a dry run. It refuses anywhere but the main checkout. It first fetches the base (`git fetch --no-tags <remote> +refs/heads/<base>:<tracking ref>`, 300 s, no prompt: `sweep.fetch_base`), so the base reads as it stands on the remote; a failed fetch removes nothing (exit 1). A held or unreadable landing lock, or a machine lock that cannot be read, defers it the same way. It also abandons each UNLANDED worktree marked stale that every sweep check but the landed one lets through (see "Stale marks").
- `... --classify [--json]`: read-only. Sorts every registered worktree but the main checkout into one class (A, B, C, E, L or O; see "Classify"). `--json` prints the data instead of the lines. It takes no other flag but `--apply`, which removes the A and E trees and drops the stale registration of each O tree (see "Classify").
- `tools/worktree_sweep_task.py [-C <main checkout>] [--register --owner-confirmed]`: prints the scheduled-task line. With both flags it runs it in PowerShell. A bare `--register` is refused, and agents never type `--owner-confirmed`.

Exit codes: 0 done, 1 refused or failed (or the sweep deferred, or `--classify` found a tree in A, B, C, E or O), 2 usage or a refused `.kit.json`, 130 Ctrl+C.

## Stale marks

- The owner's rule: among unlanded work, only branches with a stale mark recorded by `--mark-stale` are pruned.
- The guard (docs/guard.md, the `git-worktree-remove` row) lets a raw `git worktree remove` of an unlanded tree through when the tree is clean, git says its HEAD is not in main, and its branch has a stale mark recorded by `worktree_remove.py --mark-stale` that names this path and this tip, with nothing newer than the mark in the tree, in its git dir (apart from `index`, `index.lock` and the folder's own time), in the branch's reflog or in the tip's commit date (`sweep.last_activity`). It skips the sweep's other checks: the 24 h idle bar, `git worktree lock`, the exemption (`remove.exemption`), the worktree-folder placement (`remove.is_workstream`), a branch checked out elsewhere, holders, the open-claim check, the machine-lock holder and the landing hold. `--mark-stale` makes all of them when it marks (`marks.mark`, with `--classify`'s L rule, `classify.live_reason`) but the holder probe's DELETE-access test of each entry (`holders.blockers`): of holders it checks only processes' current folders, through the L rule. So what the guard leaves open is that test and what changes after the mark. The idle bar: the mark is the decision that the tree is idle, and any activity after it voids the mark. `git worktree lock`: one made before the mark is refused when marking, and one made after writes `locked` into the worktree's git dir, which voids the mark while the lock is held, as activity after the mark does (an unlock leaves no trace; the guard reads no `--force`, so a doubled `--force` is no cover). A mark naming another path is void, so the placement holds. Known limits: a process holding a file open in the tree other than as its current folder is seen by neither the mark nor the guard, which do not run `holders.blockers`; an exemption or a second checkout added after the mark, and a holder process (the guard runs no process probe, so one that moves in after the mark), an open claim, a machine-lock run or a landing that starts after the mark, are not seen unless they write in the tree or its git dir; the branch and its commits stay, since the remove deletes only the tree. It refuses, saying why, a void mark and a marks file, branch, last activity or git common dir that cannot be read. A HEAD whose merge git cannot tell is refused as unmerged before any mark is read, and so is a detached HEAD, which names no branch to mark. Unlike the sweep, it tags nothing and leaves the branch and the mark, which the sweep later names for `--unmark-stale` (`kitlib.guard.rules.stale_mark_word`; tests in `tests/guard/test_stale_mark_rule.py`).
- One marks file per repository, `<git common dir>/kit-stale-marks.json` (`{"version": 1, "marks": [...]}`; each mark holds `branch`, `tip`, `path`, `why`, `at` and `by`). It is written under its own lock (`kit-stale-marks.lock`) through a temp file and a replace. A file of any other shape cannot be read.
- The sweep abandons a marked tree under `archive/<slug>` only when every sweep check but the landed one holds: idle 24 h, the machine lock, git locks, holders, no open claim, the landing hold and a clean status. A mark is void (the tree kept as UNLANDED, the mark kept) when the tree is not the one it names, its tip moved, or anything in the tree, in its git dir (apart from `index`, `index.lock` and the folder's own time), in the branch's reflog or in the tip's commit date is newer than the mark. A mark has no age limit.
- The abandon runs under the marks lock, only while the mark is still the one the sweep read, held to the checked tip (`remove._abandon` `expect`, which also refuses work already in the base); the tag message names who marked it and why, and the mark is dropped once the abandon is done. A marks file that cannot be read abandons nothing: the landed sweep goes on and exits 1.
- Last, under `--apply` the marks of gone branches are dropped (`would drop` in a dry run), and a mark on a branch with no worktree is named for `--unmark-stale`.
- `--classify` shows each mark, void or not (`mark:`), and gives a B or C tree under a worktree folder a `next` line: `--unmark-stale` when its mark holds, else `--mark-stale`, but only when `--mark-stale` would take the tree. A dirty tree, one whose tip is in the base (landed, or nothing of its own) and one a claim shown still pulls get a `note ... takes no --mark-stale` line saying why instead (`classify.mark_bar`).

## Classify

`kitlib/worktree/classify.py` `classify` without `--apply` deletes, moves, fetches and writes nothing. Every git call is a read, and the status is read with `--no-optional-locks`. The base (`origin/main`) is read as it stands and never fetched, so the header says `(as it stands, not fetched)`. The backlog store is opened with `fetch=False`. Each tree gets the first class that matches, in this order:

| Class | Rule | Next step the output names |
|---|---|---|
| L live or kept | Locked with `git worktree lock`; exempt; the landing tree (`_landing`); or held. Held means one of: the landing lock names its branch; a machine lock record names it (`sweep.machine_lock_holder`); a process has its current directory in it; or its last activity is newer than the dead bar. A tree whose status or last activity cannot be read is L too. | reported only |
| O orphan | Registered, its folder missing, and not locked, exempt or the landing tree (decided before the held probes, which need the folder). Its `note` says whether its admin folder (`<git common dir>/worktrees/<id>`, which `git worktree remove` deletes) keeps a commit no branch, remote-tracking branch or tag reaches: its HEAD reflog, a per-worktree ref or a pseudo-ref such as ORIG_HEAD (`remove.orphan_unsaved`; `unsaved` in `--json`). | `--apply` drops the registration and keeps the branch; one that keeps an unsaved commit, cannot be read, or lies outside every worktree folder and scratch root (`remove.orphan_outside`: an unmounted or remapped drive looks the same) is left for the owner |
| A landed | The tip is in the base and off its first-parent chain (`merged_worktrees`' rule), the tree is clean, and a tree on a branch has a commit of its own in the branch's reflog (`own_commit`). Also an empty tree: clean, tip in the base, nothing of its own, no backlog record claims it and its reflogs hold no unsaved commit (`empty_keep`, below). | `worktree_remove.py <slug>` |
| E evidence | A detached tree outside every worktree folder; or the folder name matches `EVIDENCE_GLOBS` (`agent-*`, `*-red`, `redcheck`, `mutant*`) and the tree is clean and, on a branch, the live backlog stores can be read and none claims the branch (`evidence_keep`). A name alone proves nothing about the work in a tree: one that fails this goes on to B or C, its note `an evidence name, kept from E: <dirty files, the claim, or why the claims are unknown>`. | `--scratch` or `--abandon "evidence"` |
| B finished | Clean, ahead of the base, and its tip has a `--full` gate-OK record git still agrees with (`gate_ok.verify_full`). | land it or record why not |
| C half-done | Anything else: dirty, no gate-OK record, a record that cannot be read, or an empty tree that is claimed, whose claims cannot be read, or whose reflogs hold an unsaved commit. | take it up, or block or release its record; then `--abandon` |

- The dead bar is `DEAD_AFTER_S`, 24 h. Last activity is `sweep.last_activity` for a tree on a branch. For a detached tree it is the newest of: the tree, its git dir (the index left out) and the HEAD commit's date.
- A run-wide probe that cannot be read makes every tree L, and a `note` line says why. The run-wide probes are the landing lock, the machine lock and the process list. A process the scan cannot open (another user's, or a protected one) is counted on the `processes` line and not searched. On Linux the holder probes read /proc (`kitlib.platform.linux.paths.process_paths`) and see this user's processes only: `holders.blockers` names each path in the tree that one of them uses (its current folder, root, program, an open or mapped file) as held, gives the tree as unread when one of them cannot be read in full or a process's user cannot be told, and as not searched when /proc cannot be listed, lists no process or does not list the scan's own; each refuses, so an empty answer means every process of this user was read and none uses the tree. A process is this user's when any of the four users of its status `Uid:` line (real, effective, saved, file system) or its /proc folder's owner says so; the folder's owner is the effective user only (observed on Linux 7.0, Ubuntu 26.04: it stays so for a not-dumpable process, whose entries inside go to root), so it alone would miss a setuid program this user ran. Two kinds of process of this user whose links the kernel refuses (EACCES or EPERM on its `ns/mnt`) are this login's own and are counted, as another user's are, without making the tree unread (`paths._login_process`): one in this user's manager's own scope (its cgroup v2 path ends `/user@<uid>.service/init.scope`: `systemd --user`, which holds CAP_WAKE_ALARM, and its `(sd-pam)`), and one not exec'd since its fork (`PF_FORKNOEXEC` in its stat flags) whose parent, not PID 1, is another user's (a root daemon's child that dropped to this user, running the daemon's code: the ssh login's `sshd-session`). Every other process of this user that cannot be read keeps the tree unread, and `describe` names each one (`unread   pid <n>  <name>`) so it can be ended or waited out. Each other thread of a live process gives its own current folder and root too (/proc/<pid>/task); a zombie leader's still-running threads give every kind. A process or thread of this user in another mount namespace (`ns/mnt` unlike the scan's own: a devcontainer, rootless podman), or whose namespace cannot be read, makes the tree unread, since its paths name another tree; in the scan's own mount table (mountinfo), a tree whose device is mounted again where that mount's root and the tree's place in the file system overlap (a bind mount of the tree, of a folder above it or of one in it), a tree with any other mount at or under it (a folder bound into it) or a later mount at or above the one holding it (which hides it), or one no mount there holds (a chroot), is unread, since a process standing in the other path uses the tree under a path not under it; a /proc with `hidepid=2`, `hidepid=invisible` (or 4, ptraceable) or `subset=pid` on any proc mount there hides processes of this user, so the tree is not searched, as when /proc's mount options or the scan's own namespace cannot be read, or the scan runs in any PID namespace but the first (its `ns/pid` link is not `pid:[4026531836]`, the first one's fixed inode: inside docker, podman, a devcontainer or a WSL2 distro, whose own /proc shows one id on the status `NSpid:` line all the same) or that link cannot be read, since such a /proc lists none of the processes outside it, which may use a tree bound in. Known limits: one process of this user that cannot be read and is not this login's own (ssh-agent, gpg-agent, a desktop's gcr ssh agent, an agent host that marks itself not dumpable, a process under a sudo parent, an AppArmor or snap confinement) makes every removal unread until it ends, and the removal then falls to the owner. The login's own are trusted unread: the current folder and open files of the user manager, its `(sd-pam)` and `sshd-session` are inferred to be outside any tree (the manager runs with no `WorkingDirectory`), never read; a process deliberately moved into the manager's `init.scope` would be hidden, and so would a never-exec'd fork of a not-dumpable program of this user adopted by a root subreaper other than PID 1. A thread's own open-file table (a thread that unshared CLONE_FILES) is not read; another user's processes are not seen; each of those mount cases makes every removal it covers unread, and the removal then falls to the owner; a view of the same files the table does not show as that device (a FUSE or overlay mount) is not seen as another path, and a mount in another namespace (a container's volume) is that namespace's, seen only through its processes (unread). A WSL2 distro runs in a PID namespace of its own, so there every removal is not searched and falls to the owner. /proc is listed once: a process that forks and exits while the scan runs can leave a child, started after the listing, that inherits its current folder unseen. On Linux `held_folder` answers not searched (no open shows a held folder there). On Windows, when a process could not be read, a tree no other rule holds is L unless every folder in it opens for delete (`holders.held_folder`: Windows refuses that open on a process's current directory), so L can also mean "a process we could not read may hold it"; a folder that refuses, a walk error or a tree past `WALK_MAX` entries makes it L. A git HEAD of forty zeros (an unborn or missing branch) is L. A landed tree on a branch is A when the branch's reflog shows a commit made on it (`own_commit`); a reflog that is missing, expired or cannot be read is C. B's record must come from a `--full` gate (`gate_ok.verify_full`); a record from a gate without it shows as `gate: not full: ...` (C). The backlog's `block` and `release` of another branch's pull ask `branch_liveness`, the same L rule for the one tree on that branch (docs/backlog.md "Stopping a pull").
- An empty tree (clean, tip in the base, nothing of its own: a branch made at a base commit and never worked on, or a detached tree in a worktree folder) is A only when "no claim" is evidence (`live_claims`): the claims are read from the store this repository's `.kit.json` names (as the sweep reads it) and from the PM data worktree's named store (`store.pm_data_live_store`, read as `backlog.py -C <PM data worktree>` reads it). Otherwise it is C, and its note says why (`nothing of its own; kept: ...`): neither names a store (the implicit default `ref` store is read-only, so no pull is ever written there), a named store or a record in it cannot be read, a record pulled by its branch claims it, its branch reflog shows a commit of its own or cannot be read, its HEAD or branch reflog holds a commit no ref and not its tip reaches (`unsaved_reflog`: removing the tree and branch deletes both reflogs), or it is the PM data worktree itself.
- Each tree's line shows the backlog records its branch pulled (`claim:`), or `unknown: <why>`.
- Each B and C tree gets a `next` line per claim, `backlog.py -C <checkout of that store> release <ID> --reason "<why>"` (or `block` to keep the branch); a claim in a main or folder store named in `.kit.json` gets no command, since that store takes no write in the main checkout, only an instruction to run it from a worktree whose branch holds the record. Claims match `pulled_by` without regard to case, as backlog.py does. Then a `next` line with its `--abandon "<why>"` command. The `--abandon` line is for after the tree has been taken up or recorded.
- Exit codes: 0 when every tree is L, 1 when any tree is A, B, C, E or O (or a run-wide read failed: `failed ... nothing was classified`), 2 for a refused `.kit.json`.

`--classify --apply` (with or without `--json`) classifies as above, then removes each A and E tree through the existing remove paths and drops each O tree's stale registration (`apply_tree`): A by the plain verb; E by `--scratch` when it is detached under a scratch root and every commit its HEAD and HEAD reflog hold is reached by a ref (`scratch_route`), by the plain verb when its tip is in the base, else by `--abandon "evidence"` (tag `archive/<slug>`). An A tree, and an E tree that does not go to `--scratch`, is first checked the same way: when its HEAD reflog holds a commit no branch, remote-tracking branch or tag, and not its tip, reaches, it is `skipped` (`reflog holds unsaved commits`) and left for the owner (also when the reflog cannot be read), because the remove deletes that reflog, the tag holds only the tip, and the remove path checks the reflog only for a tree outside the worktree folders or a detached one. Each path makes its own checks again, so a tree held, dirtied or moved since it was classified is refused there. An O tree goes to `kitlib.worktree.remove.prune_orphan` only when its row says nothing only its registration keeps (`unsaved` 0); one whose admin folder keeps a commit no ref reaches, or could not be read, is `skipped` and left for the owner. `prune_orphan` runs `git worktree remove <registered path>` for that one entry, never `--force` and never `git worktree prune` (which drops every stale entry), and keeps the branch (`removed   <path>: its stale registration (the folder was already gone); branch <b> kept`). It refuses, nothing changed, a path that exists (`its registration is not stale`), a path outside every worktree folder and scratch root (`reported only`; `--apply` skips such a row before calling it), an exempt folder, the main checkout, a locked tree, an admin folder that keeps a commit no ref reaches or cannot be read, and a folder that appeared or an admin folder that changed when both are read once more just before git; a path no longer registered is `nothing` (exit 0). B, C and L trees are never touched, nothing is fetched and no remote branch is touched.

- It runs on the main checkout only, as the sweep does. A held landing lock (`sweep.landing_hold`) refuses the run before anything is read: `refused   ...; nothing was classified or removed`. The lock is read again before each tree; taken mid-run, that tree and the rest are `skipped`. The machine lock is read again before each tree too (as the sweep does): a tree a record now names, or every tree while the lock cannot be read, is `skipped`.
- One line per A or E tree, `removed|failed|skipped <path>: <class>, <path taken>[, tag archive/<slug>]` and, for a failure, the path's first refusal. A tree whose worktree was removed but whose path then refused (its branch kept by `git branch -d`, say) is `failed`: `the worktree was removed, but <refusal>`. The B, C and L blocks, `next` lines and `summary` follow, then `applied   removed N, failed N, skipped N`. In `--json`, each such tree has `apply` (`result`, `why`, and the path's own `lines`) and the data has `applied`.
- Exit codes: 0 when every A, E and O tree was removed and no B or C tree is left; 1 when the run was refused, a tree failed or was skipped, or a B or C tree is left; 2 for usage or a refused `.kit.json`. `--apply` without `--classify` is still the sweep's (`--sweep-merged --apply`).

## The last status read

`kitlib.worktree.remove.git_remove` calls `last_look` first: one more read of `dirty`, just before `git worktree remove`. git's own refusal names modified and untracked files and never an ignored one, which it deletes with the tree, so this read is what keeps an ignored file written after the caller's own checks. Every removal goes through `git_remove`, so every caller gets it: the remove and abandon verbs (after `clear_disposable`), the sweep (after its second `sweep_status`), the landing cleanup (through `_remove`), `--scratch` (after `restore` and `clear_disposable`) and redfirst's cleanup (`kitlib/redfirst/run.py` `remove_tree`).

- It refuses on anything `dirty` lists: a modified or untracked file (one `disposable_untracked` names too: the verbs have cleared those by then), an ignored file outside `build_output`, a keeper inside it. The line is `failed    <path> changed after it was checked - <what>; git was NOT run`. A status that cannot be read gives `failed    <path>: its status could not be read again (<why>); git was NOT run`. The tree stays registered and intact, `--abandon` keeps its tag and the branch, and the sweep counts the worktree under `failed` (exit 1).
- A folder that vanishes between the caller's checks and `git_remove` is refused the same way: no status can be read where it was, so git is not run, and the registration and the branch stay, and later runs report the entry: `--check` lists it as an `orphan`, `--classify` as O (and `--apply` drops that registration, as above), the sweep skips it (`its directory is missing`), the landing cleanup (`kitlib/gate/cleanup.py` `clean_branch`) keeps it as `registered, and its folder is gone`, and the remove verb answers `nothing   <path> does not exist`.
- The window is narrowed, not closed. An ignored file written after `last_look` returns and before git deletes its folder is still deleted, without a word from git.
- `last_look` does not repeat the link check (`holders.link_reason`): a link or junction made inside build output after the verb's link check is not seen. One outside build output is refused when the status lists it or what it leads to (`??`, or `!!` when ignored).

Tests: `tests/worktree/test_remove_snapshot.py` (`IgnoredAfterTheLastStatusRead`; after `clear_disposable`, a tracked edit and delete in `FileAppearsInTheWindow`, a `disposable_untracked` file in `DisposableInTheWindow`, a junction in `JunctionAppearsInTheWindow`, a vanished folder in `FolderGoneInTheWindow`) and `tests/worktree/test_worktree_sweep.py` (`Sweep.test_an_ignored_file_written_after_the_sweeps_second_status_read_survives`).

## The scheduled task

`kitlib/worktree/task.py` `command` writes the one PowerShell line `tools/worktree_sweep_task.py` prints or, with `--register --owner-confirmed`, runs. The task `<repo name>-worktree-sweep` runs daily at 03:00 as the registering user (`-RunLevel Limited`, `-StartWhenAvailable`), its working directory the main checkout. On Linux the same name is a systemd user timer daily at 03:00 (persistent, so a missed run is made up), else a crontab line, running this python and the tool in the main checkout (`kitlib.platform.linux.schedule`, `task.linux_job`); the same flags print it or install it, and the `pythonw.exe` and carrier text below does not apply.

- Registration is the owner's `tools/machine_setup.py --apply`, which by default registers this task for every repository in the machine config's `launcher.repos` after one dry run of the sweep, running the kit's live main checkout, and registers it again when it runs a removed plugin export (`--no-worktree-sweep` opts out; docs/machine-setup.md "Extras", "Worktree sweep tasks"). pm-start flags a repository whose task is missing or stale. `tools/worktree_sweep_task.py` stays the one-repository form.

- No console window opens. The task's program is the `pythonw.exe` of the base install of the python that runs the tool (`sys.base_prefix`; `kitlib/launcher/pythonw.py` `base_pythonw`), named in the line itself (`PYTHONW_IS`), never a `Get-Command` lookup, which gives the `WindowsApps` alias when that folder is first on `PATH`, and its arguments are `"<kit>\tools\no_window.py" python "<kit>\tools\worktree_remove.py" -C "<main checkout>" --sweep-merged --apply` (`argument`). `tools/no_window.py` is the carrier (docs/daily-full.md "The schedule"): it starts the `python.exe` beside that `pythonw.exe` with a console that has no window and exits with the sweep's exit code.
- The tool refuses (exit 1, nothing printed or registered: `refused   ...; nothing was registered`) when that `pythonw.exe` is under a `WindowsApps` folder or is not a file (`kitlib/launcher/pythonw.py` `refusal`); the line itself still throws, registering nothing, when `$py` is empty or under `WindowsApps` (`NOT_THE_STORE_ALIAS`).
- The line does not replace a task: PowerShell refuses to register a name that exists. A task registered before the carrier runs `python` directly, with a window, until the owner removes it (`Unregister-ScheduledTask -TaskName '<repo name>-worktree-sweep' -Confirm:$false`) and registers it again (machine setup's `-Force` re-registration covers only a task that runs a removed plugin export).

## How it reads state

- `-C` is a plain path option; the kit has one copy of the tool. A relative path argument resolves against the process's own directory.
- Landing lock: read through `kitlib.records.landing.LandingLock` (`<common dir>/kit-landing.lock`). A file there that is no lock record counts as held.
- Open claim (sweep) and pulled warnings (abandon) read the backlog store backend: a record with `state: pulled` and `pulled_by: <branch>`. A `ref` or `branch` store is read at its local ref as it stands (not fetched, not per revision); an absent ref holds no records. A store that cannot be read skips the worktree (sweep) or prints a note (abandon).
- Machine lock: read through the kit's own `<kit>/tools/machine_lock.py status --json` only (the tool read beside the kit, `kitroot.lock_tool`). Two shapes are accepted: `lock.held/waiting/background` and the kit snapshot (`runs` plus `queue.entries`); anything else defers the sweep.
- Sweep task: it runs this kit's `tools/worktree_remove.py` by absolute path with `-C <main checkout>`, and the tool must sit in a main checkout (not a branch worktree's copy).
- `<branch> --branch` without `--abandon` removes a landed branch without its worktree. Its checks are the plain verb's merge check and the sweep's open-claim check.
- Output is collected and printed when the verb ends, not streamed. The `--apply` log (`<shared temp>/<repo name>-worktree-sweep.log`; `<shared temp>` is `kitlib.config.user.shared_temp`: the machine config's `temp_dir`, else the system temp folder) is written from the same lines.
