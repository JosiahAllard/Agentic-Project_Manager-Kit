# gate.py

The universal gate: `tools/gate.py` (entry) over `kitlib/gate` (library). ARCHITECTURE.md "Contracts" (Booking, Kinds, Gate-OK record, Landing) is the design; this page is the behaviour. Keys: docs/kit-json.md "gate" and "landing".

## Commands

| Command | Does |
|---|---|
| `gate.py [-C DIR] [--base REV] [--full \| --only STEP ... \| --rerun] [--plan] [--slug S] [--log-dir D]` | (`--rerun`: Targeted rerun.) Gates the checkout under `book(<gate.kind>)` (default `test`), booked as a gate run: the build daemons it leaves that serve nothing outside its job are stopped at its end (Build daemons). The base is the default base (Default base); the merge base with HEAD is what is compared. A landing takes a branch tip only with the gate-OK record of a `--full` pass, or of a default-mode or docs-only pass the base's config takes, which neither `--base` naming another commit nor `--only` writes (Gate-OK record; Landing, step 4). |
| `land.py BRANCH [BRANCH ...] --expect-tip SHA [--expect-tip SHA ...] [--expect-main SHA] [-C DIR] [--summary T] [--full] [--fresh] [--wait S] [--log-dir D] [--keep-branch] [--reviewed-by ID ... [--wait-result] --submit]` | The landing tool (tools/land.py): lands BRANCH, or a batch, from the main checkout onto `<remote>/<main>` as it is at the landing's turn (see Landing). One `--expect-tip` per branch, in the same order. `--expect-main` is optional: the main the landing was planned on, compared and never refused for (Landing, step 4). `--wait` defaults to `"landing".wait_s`. `--submit` starts the landing detached and returns at once, and needs one `--reviewed-by` per branch, the reviewer id of its queued verdict (Submitting a landing); `--wait-result` before it waits in the same call and ends with the landing's result (Submitting a landing, "Waiting in the same call"). Landed, each branch is cleaned up unless `--keep-branch` (see Branch cleanup). |
| `land.py --sweep-landed [--apply] [-C DIR]` | The branch cleanup for every branch main already contains (`kitlib.gate.cleanup.sweep`; see Branch cleanup). Without `--apply` a dry run: it changes nothing and names what would go. |
| `land.py --queue [-C DIR]` | Read-only: the landing lock file's holder, then the landings in the machine lock's queue (its entries of priority `land`), holding first, then waiting in turn order, a landing of another repository marked so (`kitlib.gate.land.queue`; see The landing queue). |
| `land.py BRANCH [BRANCH ...] --check-strict [-C DIR]` | Read-only, no lock, no verdict: whether each branch changes a strict path, `STRICT <branch>: <paths> ...` or `NOT STRICT <branch>: ...` (`kitlib.gate.land.check_strict`; see Strict paths). |
| `gate.py land BRANCH --expect-tip SHA [--expect-main SHA] [-C DIR] [--summary T] [--full] [--fresh] [--wait S] [--log-dir D] [--keep-branch] [--reviewed-by ID --submit]` | The same landing for one branch, with `--wait` defaulting to 0, or to `"landing".wait_s` with `--submit` (see Landing). |
| `gate.py wait-result BRANCH --tip SHA [--kind gate\|land] [--timeout S] [-C DIR]` | Reads only, except that it finishes a running record whose process died as `error`. Waits until BRANCH's final result record names a tip starting with SHA (7 to 40 hex digits), prints `RESULT ... at <tip>` (the tip cut to 10 characters) and exits 0 when its verdict is `pass`, 1 for any other verdict, 7 when no such record appears within S seconds (default: no limit). See Result record. |
| `gate.py stop RUN [-C DIR]` | Ends one gate run by its machine-lock run id (`r-...`, on the gate's held line and in `machine_lock.py status`): that run's process tree and lock only. A landing's is refused, but a load node's land gate shows as a plain gate on the node (Stopping a gate, Known limits). Exits 0 stopped or already gone, 1 it could not be ended, 2 USAGE, 4 refused (`tools/gate.py` `do_stop`, over `kitlib/gate/stop.py`; see Stopping a gate). |
| `gate.py --measure --out PATH [--days N]` | Writes a proposed kinds table from the lock's run history (kitlib/gate/measure.py). It never writes the live kitlib/lock/kinds.json. Every kind's cpu in the proposal is a whole number 1..the layout's agent_cap: the p90 peak busy cpu slots rounded up, or agent_cap when the runs fill what they booked (pinned runs cannot show more). The lock measures a run's job object only, so a finished run counts as a cpu sample only when its history line shows work in the job (kitlib/gate/measure.py `skip_reason`): not `partial`, held `MIN_HELD_S` (10 s) or more, with `cpu_s` and a peak above 0, and `cpu_s` at least `MIN_BUSY_THREADS` (0.1) x `held_s`. A kind with too few runs or too few cpu samples is kept whole, warn_min included, written as the size it books on this layout now. It prints one line per kind; the line counts the skipped runs by reason. Not caught: a wrapper that itself keeps a tenth of a thread busy while its work runs outside the job. |
| `gate.py allow BRANCH --runs N --why TEXT [-C DIR]` | The coordinator's call (`tools/gate.py` `do_allow`, over `kitlib/gate/budget.py` `allow`): allows BRANCH N gate runs in all, past the branch gate budget (The branch gate budget). N is a whole number above 5; `--why` is required, and an N not above 5 or an empty `--why` is `USAGE: ...` (exit 2). Prints `ALLOWED <branch>: N gate runs (<used> used); <file>`; `REFUSED: <reason>; nothing written` (exit `G.REFUSED`) when BRANCH is not a branch of the repository or the file cannot be written. |

## Default base

`kitlib.git.refs.default_base` is the one rule every kit tool uses when no `--base` is given: `refs/remotes/<remote>/<main>` (as last fetched) when it resolves, else the local `<main>`. A local main lags whenever nobody pulls into the main checkout, and measuring against it counts the remote's newer commits as the branch's work. When the local main is at another commit the tool prints `base: local main <hash> is N behind <remote>/<main> <hash>; measuring against <ref>` (or ahead, or both). An explicit `--base` is always used as given. Users: gate.py, doc_budget.py, review_pack.py, forbidden.py, kit_tests.py and pytests.py `--select`; preflight.py `--board` measures its rows against `<remote>/<base>` when the two differ.

Every kit `git fetch` and `git ls-remote` runs with `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never` and `GIT_HTTP_LOW_SPEED_LIMIT=1000`/`GIT_HTTP_LOW_SPEED_TIME=60` (`kitlib.git.cmd.NETWORK_ENV`): a remote that wants credentials, or a transfer stalled below 1000 bytes/s for 60 s, fails instead of hanging. An ssh passphrase prompt is not covered (forcing `ssh -o BatchMode=yes` would override the user's `core.sshCommand`, `GIT_SSH` and ssh config; see the `kitlib.git.cmd` docstring). A push keeps the user's credential prompts.

## Exit codes

From kitlib/gate/__init__.py. The machine lock's refusal codes pass through unchanged (kitlib/lock/store.py: 6 busy, 8 timeout, 10 require-lock, 11 reserved, 12 hold). Ctrl+C is 130.

| Code | Name | First line printed |
|---|---|---|
| 0 | OK | `GATE OK[ (warned: ..; skipped: ..)]` (or `GATE OK (auto-detected: no stack found, so NO checks ran; ...)`, see Auto-detected gate), `LANDED <branch> on <main> at <merge> (pushed and verified on <remote>)` (followed by a scope-check `WARNING: ...; the landing went ahead: the scope check only warns for now (kitlib.gate.land SCOPE_REFUSES)` for a branch that changes paths outside its records' scopes while `land.SCOPE_REFUSES` is False (Landing, step 4); and by `WARNING: the landing lock could not be released: ...` and the command to break it when only the release failed), or `proposal written: <path>` |
| 1 | FAILED | `GATE FAILED: <steps> (<first>: <reason>)`, or `NOT LANDED: ...` (a red merge dropped, a step that changed the landing tree, a push refused because `<remote>/<main>` moved on, a push git refused (exit 1 with git's own `! [rejected]` or `! [remote rejected]` line) while `<remote>/<main>` is still the base, an exception, SystemExit or Ctrl+C after the merge and before the push), or for a merge that conflicted (aborted, the batch's earlier merges dropped) `<branch> does not merge cleanly into <main>: ...; the merge was aborted` and the verdict line `CONFLICT <branch> with main <base>: the author merges main` |
| 2 | USAGE | `USAGE: ...`: bad arguments, an `--only` name no step has, a `--base` that does not resolve, a machine-lock usage error such as an unknown `"gate".kind`. Never worded as a refusal (refusal-log P10). |
| 3 | STUCK | `STUCK: landing <branch> stopped in phase <phase>: ...`, then what is left and the steps to clear it (see Landing); the landing lock stays held at phase `stuck`. Only a push that may have landed and cannot be told is STUCK, an exception, SystemExit or Ctrl+C during the push included, and a push that timed out, died (exit 128), exited 1 without git's refusal line or exited 0 while `<remote>/<main>` is still the base |
| 4 | REFUSED | `REFUSED: ...; nothing was changed` or `... nothing was merged` (a config error before the merge is one); `REFUSED: no gate step selected: ...` when the steps cover none of the changed paths, or under `--full` and in the merged gate when every step is manual, or when each step left is dropped by another selected step's `skip_if_selected` (`runner.NO_STEP`, `runner.NO_STEP_FULL`); `REFUSED: no gate step ran: ...` when every selected step was skipped for a missing `requires` (it names each one and what it requires). In both, no record is written and a landing drops its merge. `REFUSED: the stash stack is not empty (refs/stash is at <sha>): ...` while the repository's stash stack holds an entry (The stash guard). `REFUSED: this gate's output file ...` when a branch gate's stdout is a file another gate run is writing (Whose run a log is). A scope-check miss is `REFUSED: <branch> changes <n> path(s) outside the scopes of the records it holds ...; nothing was merged` only once `land.SCOPE_REFUSES` is True; until then it is a WARNING after `LANDED` (Landing, step 4). |
| 5 | BUSY | `BUSY: landing lock: HELD ...; nothing was changed` (the landing lock file not had within what is left of `--wait` once the turn was given), or `BUSY: ... not broken, because ...` at once for a gone holder that left something unpushed. A turn the machine lock does not give is its own code, not BUSY (below) |
| 9 | LANDED_UNGATED | Retired: no landing gives it. The code and the `landed-ungated` verdict are kept so old result records still read (`G.LANDED_UNGATED`) |
| 16 | STOPPED | `STOPPED: gate run <id> was stopped; no verdict and no gate-OK record`, or `STOPPED: the gate was stopped while it waited for the machine lock; ...`: the exit of a stopped gate (Stopping a gate), not of `gate.py stop` |

`gate.py wait-result` has its own codes: 0 (the record's verdict is `pass`), 1 (any other verdict, `stopped` and an old record's `landed-ungated` included), 2 (USAGE), 7 (TIMEOUT: no final record at that tip in time).

Any other machine lock refusal prints `NOT RUN: the machine lock refused the gate: ...`; for a landing's turn (Landing, step 3), `NOT RUN: the machine lock did not give the landing its turn: ...; nothing was changed`, with the lock's code (6 when `--wait` is 0 and the lock cannot give it at once, 8 when `--wait` ran out; kitlib/lock/run.py `book`). Ctrl+C is 130 only when nothing is left: before the merge, or after it and before the push, once the merge was dropped and the lock released. During the push it is STUCK.

A landing's verdict is its exit code, and in text its first line starting `LANDED `, `NOT LANDED:`, `CONFLICT `, `STUCK:`, `REFUSED:`, `BUSY:`, `USAGE:` or `NOT RUN:`. Key on that line, not on `^GATE (OK|FAILED)`, which is the merged gate's own verdict (`kitlib.gate.runner.verdict`). A `GATE OK` line appears only in a landing that LANDED; a green merged gate that is then not landed prints it as `merged gate passed ...`, so no `GATE OK` line stands beside a `NOT LANDED`.

## Steps

kitlib/gate/steps.py. A step has a `cmd` (argv with `{python} {root} {base} {here} {tools}` substituted) or a `check` (a function in the repo hook module's `GATE_CHECKS`).

- **Full command.** A `cmd` step may also have `full_cmd`, an argv substituted the same way. A full run (`gate.py --full`, `land.py --full`, `daily_full.py`) runs `full_cmd` instead of `cmd` (`steps.build(full=True)`); every other run, a landing without `--full` included, runs `cmd`. `merged_args` are appended to whichever runs. Use it for a step whose `cmd` selects tests by the change: on an unchanged tree such a `cmd` selects nothing and passes without running a test.
- **Daily command.** A `cmd` step may also have `daily_cmd`, substituted and validated like `full_cmd`. The daily full run (`daily_full.py`) runs a step's `daily_cmd` when it has one, else its `full_cmd`, else its `cmd` (`steps.argv_of`, `steps.build(daily=True)`). No other run reads it, so a tier too slow for every full gate, such as the kit's `kit_tests --full --both-tiers`, can run only daily.

- **Selection.** In diff mode a step runs when it is `always`, or when a changed path (tracked diff from the merge base, plus untracked files git does not ignore) matches its `globs` and none of its `exclude`, or when its `content` regex is in a changed file. `--full` runs every step that is not `manual`. `--only` runs exactly the named steps. `skip_if_selected` drops a step. Diff mode then adds the `"gate".smoke_steps` (Smoke steps), and a docs-only change runs only the `"gate".docs_only` steps (Docs-only changes). Order: `setup`, then stages `first`, `main`, `last`, then `defer`.
- **Judging.** A step passes only when its exit code is in `ok_exits`, every `pass` pattern matches, no `fail` pattern matches, a cmd step's log is not empty, and it did not run zero tests (`Ran 0 tests` or a `zero_tests` pattern). The `errors` policy must also find no unexplained line. A `warn` step that fails, or a `warn_lines` hit, is WARN. A FAIL stops the rest unless the step has `continue`. A `requires` entry is a command name (looked up on PATH) or an argv probe that must exit 0 within 60 s (`PROBE_TIMEOUT`; on timeout its whole process tree is ended). One that is missing is SKIP, or FAIL with `requires_strict`. A gate whose selected steps were all skipped did not run anything, so it is REFUSED, not OK.
- **Zero-count warning.** Before its steps run, a branch gate (`gate.py`; a landing's merged-tree gate does not) prints a `WARNING:` line for each `pass` pattern a zero-test run also matches, in every configured step, including steps this run does not select (`steps.zero_count_passes`: it matches `Ran 0 tests` or a `zero_tests` line, or its own first count may be 0, as `\d+`). Put a floor in such a pattern, as `[1-9]\d*`. The warning never fails the gate or changes its exit code; a check that raises prints one `WARNING:` line saying so instead, a `pass` that is no string is skipped, and each line is escaped to ASCII (`runner.zero_count_warnings`).
- **Reuse.** A cmd step with `reuse` (`true`, or a group name: a group is reused whole or not at all) and declared inputs (`globs` or `content`.globs) may be counted as passed without running, in a branch-gate rerun or a landing, when a pass of the same inputs, argv, config and kit is in the gate cache (see Gate reuse). A check step never is.
- **Check contract.** `GATE_CHECKS[name](ctx)`; ctx has `root base merged changed options name log run`. `run(argv, cwd=None)` runs in the slot's job and returns the exit code. A check returns 0/True to pass. Raising fails the check, and the traceback goes in the log. Calling `sys.exit` (any code, 0 included) also fails it, and the code goes in the log. Ctrl+C is not caught: it stops the gate.
- **Tested tree.** A gate's machine-lock run records the git tree it tests as `tree`, kept in its history line (`runner.tested_tree`; `book(..., tree=)`, `Slot.note_tree` for the slot a landing holds): a branch gate's HEAD tree when the work tree is clean (none otherwise), a landing's merge tree, the daily full run's commit's tree. It is a note, never a reason to refuse.

### Smoke steps

`"gate".smoke_steps` (docs/kit-json.md) names steps that a default-mode (not `--full`) branch gate runs whatever changed: after diff selection and `skip_if_selected`, each one not already selected is added with the reason `smoke`, a manual one included, and never dropped (`steps.select`). A name no step has is a config error (`steps.unknown_names`). The gate-OK record of such a gate has `mode` `select` (Gate-OK record), and a landing takes it for a tip when the base's config allows it (Landing, step 4). The merged gate does not run the smoke steps again unless `--full` selects them: a manual smoke step runs in the branch gate only.

For the kit, `kit_tests.py --select --smoke` adds `tests/selection.json`'s `smoke` modules unless every changed path is prose (docs/test-tools.md). The kit's `.kit.json` is owner-only. Its gate config sets `smoke_steps` to `["kit-suite"]` and `docs_only` (Docs-only changes); its `"landing"` section sets `shared_paths` (`kitlib/*`, `boot/*`, `hosts/*`, `githooks/*`, `kit.json`, `hosts.json`; Shared paths) and `self_review_max_lines` 150. So the kit's gates split by strict paths (Strict paths): a branch that changes one ends on `gate.py --full` on its tip, lands alone with a strong-tier verdict from a reviewer who is not its author, and its merged gate runs `--full --fresh`; every other branch ends on the optimized gate, the default mode `gate.py -C <worktree>` (diff selection and the smoke steps, plus Gate reuse for `kit-suite`, which sets `reuse: true` and `globs: ["*"]`), whose `select` record the landing takes (Landing, step 4).

### Shared paths

`"landing".shared_paths` (docs/kit-json.md) is a non-empty list of globs: a repo's shared code, which each repo names for itself. While it is unset nothing changes. When it is set, a non-strict branch that changes none of the listed paths may end on the scoped gate: the default mode `gate.py -C <worktree>`, with no smoke steps needed. Its `select` record lands its tip (Landing, step 4; `Lander.select_refusal`, `Lander.shared_refusal`, read from the base's config only). A tip still needs a `--full` record when its landing diff (merge base with the base..tip) changes a shared path (`the tip changes shared path <paths> ("landing".shared_paths), which only a --full record lands`), a strict path (`the tip changes strict path <paths>, which only a --full record lands under "landing".shared_paths`; Strict paths) or a gate config file (`reuse.config_hits`). The same holds whatever `"gate".smoke_steps` or `"gate".docs_only` say: a smoke `select` record, or a `docs` record of a change that is docs-only, is refused too when the change touches a shared or strict path; the shared check runs before the docs-only route. Entries are whole-path globs, matched as step globs are (`steps._match`: lowercased, `fnmatch`, `*` crosses `/`): `api/*` covers everything under `api/`, while `api` would match only a file named `api`. An entry ending in `/` or `\` matches nothing and is a config error: write `api/*`. The record's diff must still cover the landing diff. The key lives in `"landing"`, not `"gate"`, so it stays out of the gate config hash (`runner.gate_config`) and setting it voids no record. The merged gate is unchanged: it runs every step that is not manual, as `--full` selects them, and a strict landing still escalates to `--full --fresh`.

### Gate once at landing

`"landing".gate_once` (docs/kit-json.md; a bool, default false) moves the one `--full` run of a non-strict branch from the branch to the landing. While it is false or unset nothing changes. When the base sets it true, a branch that changes no strict path and no gate config file may end on the default-mode gate `gate.py -C <worktree>`, shared paths included (Shared paths), and its `select` record lands its tip whatever `"gate".smoke_steps` and `"landing".shared_paths` say (Landing, step 4; `Lander.select_refusal`, `Lander.strict_refusal`, read from the base's config only). A tip still needs a `--full` record when its landing diff changes a strict path (`the tip changes strict path <paths>, which only a --full record lands under "landing".gate_once`; Strict paths, checked before the docs-only route) or a gate config file (`reuse.config_hits`). The record's diff must still cover the landing diff. After the merge, the merged gate (Landing, step 6) of such a base runs `--full` on the merged or batched tree (`Lander.once_escalate`): each step's `full_cmd`, no reuse, said once as `GATE ONCE: the base <base> sets "landing".gate_once: the merged gate runs --full on the merged tree`, and the merge's record is a `full` one. A merge whose base..merge diff is docs-only under the base (Docs-only changes) stays on the docs-only route. A strict landing escalates to `--full --fresh` as before. `tools/review_pack.py` says such a tip's record as `scoped gate OK (the base sets "landing".gate_once)`, and `worktree_remove.py --classify` counts it green. The key lives in `"landing"`, so setting it voids no record.

### The final gate

The gate a branch ends on, run on the exact tip it reports (builder, branch-sync, review): `gate.py -C <worktree> --full` when the branch changes a strict path (Strict paths); `--full` too, smoke steps or not, when `.kit.json` sets `"landing".shared_paths` or `"landing".gate_once` and the branch changes a gate config file, or sets `"landing".shared_paths` without `"landing".gate_once` and the branch changes a shared path (Shared paths). Otherwise the optimized default gate, the same command without `--full` (diff selection and the smoke steps, plus Gate reuse for a step that asks for it), once the gate config names smoke steps (Smoke steps) or `.kit.json` sets `"landing".shared_paths` or `"landing".gate_once` (the scoped gate; under `"landing".gate_once` shared paths included, and the merged gate runs `--full`: Gate once at landing); `--full` until then. Landing refuses a tip without the matching record. A reviewer never sends back a scoped final gate this rule allows.

A plain branch gate (no `--full`, `--only` or other `--base`), and its `--plan`, says which applies: when the tip must end on `--full`, its last line but one is `FULL NEEDED: <reason>; so this tip's final gate is gate.py -C <worktree> --full (docs/gate.md "The final gate")` (`runner.full_hint`, `land.full_needed`). The reason is the one the landing's tip check would refuse its record for, read from the base's config as a landing reads it (`Lander.diff_refusal`, the checks of `Lander.select_refusal` that depend only on the landing diff), or a changed strict path, since a strict branch ends on `--full` whatever the record check takes. Without that line, the plain run that passed is the final gate. When the base's config or strict list cannot be read, the line is `NOTE: cannot tell whether this tip needs a final --full gate: <why>`; the hint never changes what the gate selects, its verdict, its record or its exit code.

### Docs-only changes

`"gate".docs_only` is `{globs, exclude, steps}` (docs/kit-json.md). A change is docs-only when it changes something and every changed path matches `globs` and none of `exclude`, and none is `.kit.json`, a config section file, the hook module, a `"landing".reuse_never` path or a strict path (`steps.docs_only`, `reuse.docs_only_change`). A docs-only branch gate (not `--full`, not `--only`) runs exactly the `docs_only` steps, plus `setup`, says `a docs-only change: only the "docs_only" steps run`, and writes its record with `mode` `docs`. `docs_only.steps` must not be empty: a `docs_only` with empty or missing `steps` is a config error (`steps.unknown_names`), since its gate would run nothing yet write a record. A branch decides this from its own config; a landing decides it from the base's (Landing, steps 4 and 6). The kit sets `docs_only` to `docs/*.md` with the step `kit-suite`, so a docs-only kit change runs `kit_tests.py --select --smoke` (docs/test-tools.md).

## Auto-detected gate

With no `"gate"` section in `.kit.json` (neither inline nor in the file it names, such as `tools/gate.json`), the gate detects the stack from the checkout's files and runs its usual test and lint steps (`kitlib/gate/detect.py`; docs/multi-host-plan.md decision 24). A configured `"gate"` section always wins, even an empty one: no detected step is ever added to it, and a section with no step that covers the change refuses as before. Every gate takes its steps from `detect.effective`: the branch gate (from the checkout), a landing's merged-tree gate and its check of commits on top (from the merged tree), and the daily full run (from its worktree).

The files are the ones git lists (tracked, plus untracked files it does not ignore that are under none of the build folders below); where git cannot list them, a walk that skips `node_modules`, `.venv`, `target`, `bin`, `obj` and other build folders, and any folder with a `.git` of its own. Detection only reads files: it installs, fetches and runs nothing, and looks nothing up on PATH. Each detected step is `always`, and names its tool in `requires` (Steps, Judging). A test step is `requires_strict`, so a missing test runner FAILs: a gate never passes without the tests it found. A lint step is not, so a missing linter is SKIP, named in the verdict line. `{python}` is the interpreter running the gate, not a project virtualenv; a project that needs its own interpreter, an install step or other arguments writes a `"gate"` section.

| Stack | Detected by | Steps |
|---|---|---|
| Python | a test file (`test*.py` or `*_test.py`) | `python-tests`: `{python} -m pytest` when the repository uses pytest (`pytest.ini`; a `conftest.py`; a `[tool.pytest...]`, `[tool:pytest]` or `[pytest]` section; `pytest` or a `pytest-*` plugin named in `pyproject.toml`, `setup.cfg`, `setup.py`, `tox.ini`, `Pipfile` or `requirements*.txt`; or a test file that imports it), requiring `import pytest` to work; else `{python} -m unittest discover`, with `-s tests` (or `-s test`) when the tests are in that folder |

| | `.flake8`, or `[flake8]` in `setup.cfg` or `tox.ini` | `python-flake8`: `flake8` |
| Node | `package.json` at the root | `node-test`, `node-lint`, `node-typecheck`: `<pm> run <script>` for each of the scripts `test`, `lint`, `typecheck` it has (npm init's `no test specified` placeholder is not a test). `<pm>` by lockfile: `pnpm-lock.yaml` pnpm, `yarn.lock` yarn, `bun.lockb` or `bun.lock` bun, else npm (npm, pnpm and yarn run as their `.cmd` shims). | Go | `go.mod` at the root | `go-test`: `go test ./...`; `go-vet`: `go vet ./...` |
| .NET | a `*.sln` or `*.slnx` at the root, else a test project (`*.csproj`, `*.fsproj` or `*.vbproj` named `*test*`, or referencing `Microsoft.NET.Test.Sdk`) | `dotnet-test`: `dotnet test <solution or project> -nodeReuse:false -p:UseSharedCompilation=false`, one step per solution (or per test project when there is no solution), each named `dotnet-test-<name>` when there are several (`-2`, `-3` ... when two share a name). A path starting with `-` or holding `{` is never passed |

Several stacks in one checkout run every one's steps, in the table's order. Python with no test file and no linter config, and a `package.json` with none of the three scripts, detect nothing. Only root-level manifests count: a monorepo whose `go.mod`, `Cargo.toml` or `package.json` live only in subfolders detects nothing for that stack, and writes a `"gate"` section.

**What the base owes.** The branch gate and a landing's merged-tree gate also detect over their base commit's tree (the branch gate: the merge base; a landing: its base, `<remote>/<main>` at its turn (Landing, step 4), read with `git ls-tree` and `git cat-file`), and keep every step the base detects that the tree under test does not (`detect.owed`; the `dotnet-test` steps count as one). So a branch that deletes its test files, its `test` script or its manifest still runs those tests, with the base's command, and they fail. A kept lint step (`python-ruff`, `python-flake8`, `node-lint`, `node-typecheck`, `rust-fmt`, `go-vet`) is `warn`: its failure is a WARN named in the verdict. The source line names what was kept (`kept from the base, which detects them and this tree does not: ...`). Dropping a check on purpose takes a `"gate"` section. When git cannot read the base the gate is REFUSED. The daily full run, which has no base, detects over its worktree alone. Detection does not stop a branch from changing what a detected step runs (a `test` script edited to `exit 0`, a `conftest.py` that skips everything): that is a change to the tests themselves, which review sees as it would under a configured gate.

**The label.** An auto-detected gate says `source: auto (auto-detected gate: <stacks>; ...)` before it starts, and the same line is the last line of its report (`source: gate.json` for a configured gate). `gate.py --plan` ends with it too. The result record and the gate-OK record carry `source` (`auto` or `gate.json`; see Gate-OK record and Result record), so the PM sees an auto-detected gate in the record a waiting session reads, not only in the console.

**Nothing detected.** When neither the tree under test nor its base detects a stack, the gate runs no step and PASSES, saying so: `GATE OK (auto-detected: no stack found, so NO checks ran; ...)`, then `source: auto (auto-detected gate: no stack found, so it ran NO checks; ...)`. A branch gate writes the gate-OK record as usual (its `steps` empty, `source` `auto`), and a landing lands. It passes rather than refuses because an auto-detected gate exists so that a repository with nothing committed for the kit (a docs-only repository, or a stack no detector knows) can run a worker-to-landing cycle; a refusal there could only be cleared by committing a gate section, which is what auto-detection avoids. The checks it did not run are not hidden: the verdict line, the source line and both records' `source` say so wherever a pass is read. A configured gate with no step selected is still REFUSED (Exit codes), and an auto-detected gate whose detected steps were all skipped is REFUSED as any gate is (`no gate step ran`). The daily full run refuses a gate with no step either way.

**The record's hash.** `gate_config` (Gate-OK record) is still the configured section over its defaults, not the detected steps: they follow from the commit's tree, which the record names, its base's tree (`base`), and the kit, which its `kit` names, so the hash and the record still fix what the gate ran. `steps` lists them by name.

## Build daemons

At the release of a gate run that ended "done", `kitlib/lock/run.py` `Slot.stop_daemons` stops the build daemons the gate's commands left in its job (policy: `machine_lock.daemons`, default `gates`, in `kitlib/lock/site.py`). A daemon is shared: any build on the machine may reuse one this gate started, so `kitlib/proc/daemons.py` `stop` ends one only when it is shown to serve the gate's job alone:

- MSBuild nodes and the C#/VB compiler server (VBCSCompiler) are always left running: their clients reach them over named pipes, and which process holds the other end cannot be read from outside.
- A Gradle or Kotlin daemon is stopped, with its children, only when the other end of every established TCP connection on this machine (`kitlib/proc/tcp.py` `peers`) of every process in its tree is in the gate's job (`kitlib/proc/job.py` `Job.contains`), in that same tree, or a process that has gone.
- Anything else is left running, never killed: a client outside the job or whose job Windows will not tell, a local connection whose other end the table does not show, a connection table or process tree that cannot be read. A daemon in the tree of a daemon left running, or serving a process in that tree, is left too.

Each daemon is said, as `run <id>: stopped the <label> (pid N) it left: <result>` or `run <id>: left the <label> (pid N) running: <why>`, and listed in the run's ended record under `daemons` (`pid`, `what`, `result`; a left one's result is `left: <why>`). A gate nested in another run says them and records none. The tree and the table are read once, before any daemon is ended, so a client that connects between that read and the kill is not seen; exactly the (pid, creation time) pairs judged are ended, children first, each by `terminate_verified`.

The kill path spares a shared daemon too. A run cancelled by `stop`, interrupted by Ctrl+C or ended in error, and a `Launcher.kill`, ends its job through `Slot.end_tree`, which calls `end_sparing`; so does a background run's `kitlib/lock/background.py` `end_child` (a stop past `bg_stop_grace_s`, a yield-late, Ctrl+C). This holds for any run booked by `book()`, not only a gate. Sparing a daemon makes the kill take up to about 2 s longer (`END_PASSES` x `END_PASS_S`, then `END_WAIT_S`), so a background run's stop frees its slots that much later. `machine_lock.daemons` is not read here: a daemon that serves only the run's job is ended, and one the rules above leave is spared with its tree.

- Nothing found, or no daemon left, or the job's processes or the daemons cannot be read: TerminateJobObject.
- `stop` raised: each daemon found is recorded and said as `not judged (<error>)`, never as left, and each one still running at its creation time is spared with its tree.
- Otherwise every process in the job outside the spared trees is ended by `terminate_verified`, oldest first, in up to `END_PASSES` (10) passes `END_PASS_S` (0.1 s) apart (`_end_others`). A target created at or after the pass's time stamp may hold a reused pid and is not ended in that pass; the next pass sees it again. A process still running after the last pass and up to `END_WAIT_S` (1 s) more is said (`WARNING: run <id>: pid N in its job could not be ended; it runs on, unpinned`); the job is then closed without a kill and the spared daemons run on. A job or process table that cannot be read part way ends the job whole, the spared daemons with it, and that is said.
- An interrupt inside `end_tree` goes up with the kill marked not done, so the release that follows judges and ends the tree again. One that interrupts the release's own `end_tree` ends the whole job, the spared daemons with it.

Known limits:

- While a run lives its job is kill-on-close, so a wrapper that dies closes it and Windows ends every process in it, a shared daemon included; no code runs then.
- An MSBuild node or the compiler server in the job is left whoever its clients are (`PIPE_LABELS`), so a cancelled `dotnet` run does not end them or what they started. Nothing in the lock ends them later: they run until they exit or are ended by hand. `python optional/procwatch/procwatch.py --kill --only msbuild-node` ends an idle MSBuild node with no living parent that is at least 5 minutes old (15 with `/nodereuse:true`); it matches only a node started with `/nodemode:`, and it reports compiler servers (rule `roslyn-server`) and never ends one. The .NET stack template's gate steps run with `-nodeReuse:false -p:UseSharedCompilation=false` (`templates/stacks/dotnet/tools/dotnet_each.py` `NO_REUSE`) so they leave no build server behind; the template's `stack.json` `BUILD_COMMAND` has only `-nodeReuse:false` and its `TEST_COMMAND` neither, so a run of those commands can leave build servers.
- A spared daemon inside a nested kill-on-close job made by a process the kill ends can die with that job although the record says it was left running (inferred from how Windows jobs behave, not tested).
- A descendant of a spared daemon whose own parent has exited no longer shows as its descendant, so it is ended. A process started after the last pass by one being ended runs on, unpinned.
- A left daemon whose creation time cannot be read and whose pid another user's or a protected process takes during the passes counts as alive, so that pid and its orphaned workers are spared and run on, unpinned. Processes can leak this way; nothing shared is killed.
- The pid-reuse test rests on Windows stamping creation times from the clock `GetSystemTimeAsFileTime` reads (inferred, not measured); a clock set back during the passes voids it.

## Console windows

Every gate run's lock run watches for console windows while its steps run: `kitlib/lock/run.py` `Slot.start` starts a `kitlib/proc/winwatch.py` `Monitor` before the first step, and `kitlib/gate/runner.py` `window_results` stops it (`Slot.watch_stop`) after the last step and says the report, before the verdict:

```
windows opened: 1 - WARNING: a console window opened (the verdict does not count it)
  12:20:05 window pid 56324 python.exe via windowsterminal.exe CASCADIA_HOSTING_WINDOW_CLASS title "<python folder>\python.exe" [this run]
    cmd: "<python folder>\python.exe" -c "import sys; sys.stdin.read()"
    parent: pid 4410: python -m unittest tests.proc.test_x
```

- `cmd:` and `parent:` say what spawned the window: the program's command line, its parent pid and the parent's command line, read when the window's event arrives (`winwatch.proc_info`). A process gone or unreadable by then shows `(unreadable)`.

- N counts the windows the run opened (`[this run]`: the program was in the run's job, `Slot.window_owner`) and those it cannot place (`[run unknown]`: the program had exited, or could not be opened, when the window was read). A window whose program is outside the job is listed under `also seen, another run's: M` and not counted. A console host window shown and gone before it could be read is listed under `also seen: K console host window(s) ...` and not counted.
- A window warns: the verdict, the exit code and the gate-OK record do not change. `WINDOWS_FAIL = True` in `kitlib/gate/runner.py` is the one change that makes a counted window fail the gate: `window_results` then adds a FAIL result named `windows` (`GATE FAILED: windows (windows: N console window(s) opened)`), the report line reads `- FAILED: a console window opened`, and the lock run records code 1. `windows` is a reserved step name (`kitlib/gate/steps.py` `RESERVED`), so no configured step shares that result's name.
- Every gate run is watched, not only `--full`: a branch gate, a landing's merged-tree gate and the daily full run. The branch and merged-tree gates also return the windows as the outcome fact `windows` (each `Window.as_dict()`; None when no step ran).
- A monitor that cannot run, or that raises as it starts (`Slot.watch_start`), says `windows opened: unknown (the window monitor did not run: <why>)`, and the gate goes on.
- What it sees and misses (Windows Terminal hosting, the title heuristic for new tabs, other programs' windows, session 0, the events still queued when it stops): the `kitlib/proc/winwatch.py` module docstring. The tests show no window the user can see (docs/test-tools.md "Window tests").

## Gate-OK record

The branch gate writes `<dev_drive>\pm-kit\kit-gate-ok\<repo key>\<sha>.json` (kitlib/records/gate_ok.py, `gate_ok.record_dir`; the repo key is the result folder's, Result record) only when all of these hold:

- at least one step was selected, every selected step passed, warned or was skipped, and at least one passed or warned; or the gate is an auto-detected one that found no stack (Auto-detected gate), which selects and runs nothing, passes with `GATE OK (auto-detected: no stack found, so NO checks ran; ...)` (`runner.NO_CHECKS`) and writes the record with `source` `auto` and `steps` empty;
- no `--only` was given;
- the base is the default base (`--base` naming another commit makes the gate partial);
- the work tree was clean (no tracked change, no untracked file) at the start and at the end;
- HEAD did not move;
- the repository's stash stack was empty when the gate started (else the gate is REFUSED) and when it ended (The stash guard).

**Where the records are.** The record folder is outside every checkout and every agent's temp folder, like the result folder, so no agent's own file writes reach it; the git common dir, where records were before, is writable by any session that can write `.git`. With a `dev_drive` the record folder is the only place a record is written or read: no .git copy is written, and one found in `<git common dir>/kit-gate-ok/` is not read (`gate_ok.write`, `gate_ok.read`). With no `dev_drive` there is no record folder: the gate writes the record to `<git common dir>/kit-gate-ok/<sha>.json` (`gate_ok.legacy_dir`) instead, says `warning: the gate-OK record could not be written to the record folder: ...` and still passes (a landing is refused earlier, with no result folder), and every reader (a landing's tip check, the guard's `git-push-main` rule, the pre-push hook, the worktree, review-pack and landed tools) reads it there. That path is kept for load nodes set up without a `dev_drive` (docs/load-nodes.md "Gating a branch on a node").

With no step selected, or every selected step skipped, it is REFUSED (exit 4), except in that auto-detected gate with no stack. Otherwise a missed condition prints `no gate-OK record: <why>` and still exits 0 when the gate passed. `gate_config` is `.kit.json` "gate" over its defaults (`kitlib.gate.runner.gate_config`); guard.py and pre-push verify with the same value. A landing writes the record for its merge commit after the merged gate passes, after the checkout is checked unchanged, and before the push.

`source` (an added key, `gate_ok.ADDED_KEYS`) is where the gate's steps came from: `gate.json` (the configured "gate" section) or `auto` (Auto-detected gate). A record written before the key has none; `gate_ok.source_of(record)` reads it as `gate.json`, and `verify` neither requires nor checks it.

`full` (an added key, `gate_ok.ADDED_KEYS`) is true when the gate ran `--full`, false for a default-mode run. A landing's record says whether the landing was `--full` (its merged gate ran each step's `full_cmd`, where a step has one; Landing, step 6); its merged gate selects every step but the manual ones either way. Only the JSON true counts (`gate_ok.full_of`). A record written before the key has none, and nothing else in it tells the two modes apart: the steps carry names only, and a step with a `full_cmd` has the same name in both. `gate_ok.verify_full(root, commit)` takes a record only when `verify` does and it is a `--full` one; a record without the key does not count. A landing requires that of every branch tip unless the base's config takes its `select` or `docs` record (`mode`, below; Landing, step 4), and review_pack.py prints it (docs/review-pack.md).

`mode` (an added key, `gate_ok.ADDED_KEYS`) is what the gate selected (`gate_ok.MODES`): `full` (`--full`, exactly when `full` is true), `select` (a default-mode run: the steps the change selects plus the smoke steps; Smoke steps) or `docs` (only the docs-only steps ran; Docs-only changes). `gate_ok.mode_of` reads a record without the key as `full` when `full_of` says so, else as unknown, and a mode that disagrees with `full` as unknown; a landing takes an unknown mode only as `--full`. The gate config hash leaves out `smoke_steps` and `docs_only` while they are unset (`runner.HASH_IF_SET`), so records written before the keys still verify. A removed gate key keeps its old default in the hash (`runner.HASH_REMOVED`: `python_tests`, `python_tests_floor`, `trailers`), so records written while it was a key still verify; it is in no config and builds no step.

`input_keys` (an added key, `gate_ok.ADDED_KEYS`) is `{"schema": 1, "steps": {<step>: {<part>: <sha256>}}}`, or null: a branch gate's key for each step a landing may serve from this record when main moved on (`reuse.record_keys`; Gate reuse, "The input tree"). `gate_ok.build` refuses any other shape. A landing's own record holds none.

`ran_on` is only on a record a load node's `gate.py --full` wrote and main took in (`gate_ok.import_record`: every `verify` check with main's own config at the commit, which must be its `config_rev`, a `--full` pass of the same repository): `{"node", "host_key", "job"}` from main's registry, with `input_keys` set to null; `verify` neither requires nor checks it (docs/load-nodes.md "Gating a branch on a node"). A landing whose merged gate ran on a node and passed main's checks writes its own record with it too (`gate_ok.record_pass(ran_on=...)`, which refuses `input_keys` beside it; docs/load-nodes.md "A landing's merged gate on a node").

`config_rev` (an added key, `gate_ok.ADDED_KEYS`) is the commit the gate config was read from: HEAD for a branch gate, the base for a landing (Landing, step 4). `gate_ok.verify(root, commit, config_at=...)` requires it to be in the commit's history and compares the record's `gate_config` with the config that commit holds; `kitlib.gate.runner.verify_record(root, commit)` does that with `.kit.json` read by `kitlib.config.load_at`. `verify(root, commit[, gate_config])` without `config_at` is unchanged.

## Result record

kitlib/gate/result.py. `<dev_drive>\pm-kit\kit-gate-result\<repo key>\<stem>.<kind>.json` (`result.result_dir`), where `dev_drive` is the machine config's Dev Drive root (docs/kit-json.md "Machine config keys"): one folder per repository, shared by every worktree and the main checkout, outside every checkout and every agent's temp folder, so no agent's own file writes reach it. The repo key is the repository folder's name (the folder a `.git` common dir is in; a bare repository's own folder), lowercased with every character outside `[a-z0-9_-]` dropped and cut to 40 (`repo` when nothing is left), then `-` and the first 12 hex digits of the SHA-256 of the git common dir's real path, case-folded (`result.repo_key`): two repositories never share a folder. The kind is `gate` (`kitlib.gate.runner.branch_gate`) or `land` (`kitlib.gate.land.Lander.run`).

**No result folder.** With no `dev_drive` set, or a machine config that cannot be read, there is no result folder and nothing is written anywhere else: a branch gate says `WARNING: the result record could not be written: the machine config sets no dev_drive ...` and its outcome stands; a direct landing is REFUSED before anything was changed, `REFUSED: no result folder for the land records: ...` (`Lander.preconditions`), and a submission is REFUSED the same way, `REFUSED: the machine config sets no dev_drive ...; nothing was changed`, starting nothing. The owner sets `dev_drive`.

**The old folder.** `<git common dir>/kit-gate-result/` (`result.legacy_dir`), where an older kit wrote, is read, and written only when `result.finish_dead` finishes a dead old-folder record in place (under that file's lock, which it makes there). `wait-result` and a submission's check for a landing already running or a tip already landed (`submit.blocked`) take a record there when the result folder has none of that branch and kind, or when it started strictly later than the result folder's (`result.pick`; a record the result folder holds but cannot read is never covered by an old one); a dead run's `running` record there is finished `error` where it is, under its own lock (`result.finish_dead`). Gate reuse counts the old folder's records too (`result.record_dirs`). What a landing trusts reads the result folder only: the submission's claim, the records a submission replaces, and the detached landing's check of its own records (`submit.restore`), so a record put in the old folder never starts or steers a landing.

**Writes.** A run writes the file twice, each time atomically (temp file, then `os.replace`): a `running` record when it starts, then its final record with the same `run_id` and `started_at`. The `running` record replaces any earlier record of that branch and kind, at that tip or another. Every write takes the record's lock first, an OS lock on `.<record file name>.lock` beside it (`result._held`); `submit.claim`'s timeout write, `submit.abandon` and `result.finish_dead` re-read the record under it and leave a record another writer changed; a lock not had within 10 s (`result.LOCK_WAIT_S`) is a failed write. The lock files stay in the folder, one per branch and kind, empty, never pruned. A branch gate starts the record before anything else; a landing starts it once its locked checks pass, just before the merge, and a submitted landing when it is submitted (Submitting a landing). A landing's `started_at` is when it joined the landing queue either way: a direct landing takes the time just before it books its turn (`Lander._run`, before `Lander.book_turn`), and a submitted one at the submission. The time the machine lock gave it its turn is not recorded. Each write is said as a progress line, `result record: <path>`, before the outcome's own lines, so the verdict line stays last; a write that fails says `WARNING: the result record could not be written: ...` instead, and the outcome, exit code and verdict line stand. The outcome's `result_record` fact is the final record's path, or None. An exception or Ctrl+C that escapes the run is written as verdict `error` and raised again unchanged.

**No record** (the file keeps whatever it held): `--plan`; a detached HEAD; `gate.py` failing to open the machine lock store before the gate starts; a landing that ends before its locked checks pass (USAGE, REFUSED before anything was changed, NOT RUN when the machine lock does not give its turn, BUSY on the landing lock: a duplicate or retry overwrites nothing). A submitted landing is the exception: its records are written `running` at the submission and every outcome finishes them, refusals included; a `--submit` that is USAGE writes none. A process killed outright leaves its `running` record with no final one.

**Land ledger.** `<result folder>\land-ledger.jsonl` (`result.ledger_path`): each final or `error` land record `Lander.run` writes is also appended there as one JSON line (`result.append_ledger`) with the keys `branch`, `tip`, `run_id`, `started_at`, `finished_at`, `verdict`, `code`, `summary`, `gate_once` and `escalated`, as the record has them. A batch appends one line per branch, all sharing one `run_id`, so a counter of gate runs dedupes on `run_id`. A direct landing appends only once its locked checks pass; a submitted landing's records were written running at the submission, so it also appends for USAGE, REFUSED, BUSY and NOT RUN. `summary` tells apart the outcomes a `fail` covers: a merged-gate red is `verdict` `fail` with a `summary` starting `NOT LANDED: the merge of <branch> was undone; ` (a batch names its branches joined with `, `), while a conflict's starts `CONFLICT `, and an exception before the merge, a failed push, a tip that changed while the gate ran or a cancelled NOT RUN each say something else. The file is only ever appended to, so a red landing's line stays after a retry replaces its land record. Each line is one write call, made after the landing lock is released, so the lines of two landings are not ordered by the lock; a reader skips a line that does not parse. A landing with no record (No record) appends nothing, nor do a submission's own `refused` finish (`submit.abandon`) and `wait-result`'s dead-process `error`. A line that cannot be appended is said as `WARNING: the land ledger line could not be appended: ...; the outcome stands`, and a land record that was never built as `WARNING: no land record was built, so no ledger line for <branch>; the outcome stands`; either way the outcome, exit code and verdict line stand. Nothing prunes the file.

**File name.** The stem is the branch with every character outside `[a-z0-9._-]` written `%XX` (its UTF-8 bytes, capital hex), capital letters included, so `kit/A` is `kit%2F%41`: two branches never share a file, even where file names ignore case. A stem whose first part is a Windows device name (`con`, `nul`, `com1`, ...) has its first letter encoded too. A stem over 120 characters (`result.MAX_STEM`) is cut and ends `~` and a hash of the branch.

| `gate_once` | a landing's final and `error` records: whether the base's config sets `"landing".gate_once` (`Lander.gate_once`; Gate once at landing); null for a branch gate, a `running` record, a landing that ended before it read the base's config, a record a submission or `wait-result` finished (`submit.abandon`, `result.finish_dead`), and a record written before the key. Added within schema 1, like `source` |
| `escalated` | the same records: whether `"landing".gate_once` made the merged gate run `--full` (`Lander.once_escalate`, which says `GATE ONCE: ...`); false when it was `--full` already (`--full`, a strict branch) or the merge is docs-only. Null where `gate_once` is |

A pass is not a gate-OK record: a gate that passes a dirty tree is `pass` with `gate_ok_record` null. A waiting session that treats `pass` as ready to land checks `gate_ok_record` too, and that the gate ran `--full`, or that the base's config takes its `select` or `docs` record (Landing, step 4).

**Waking a waiting session.** The gating session runs the gate as usual (`gate.py`, or `gate.py land`) and tells the waiting session the branch and the tip it is gating (`git rev-parse HEAD`) once the gate has said its first `result record:` line. The waiting session arms after that: before it, an earlier run's record at the same tip would answer at once. `wait-result` writes one thing: a `running` record at that tip whose process has died (`pid` and `ctime` name a process that is surely gone, `process.alive`) is finished `error`, summary `the <landing|gate> process died: pid <n> ended without finishing its record`, with the run's `run_id` and `started_at` (`result.finish_dead`), so a killed run is never waited on forever. A `running` record with no `pid` (one written before the key) is waited past. It blocks until the file holds the final record of that branch and kind at that tip (`branch` and `kind` equal, `tip` starting with `--tip`, any case; a `running` record does not count), then prints two lines, `RESULT <verdict> <kind> <branch> at <tip>: <summary> (<log>)` and the record as one line of JSON, and exits. Example for a branch gate of `kit/x` at tip `<sha>` in the repository at `<repo>`:

```
Monitor({description: "gate result kit/x", timeout_ms: 1800000,
         command: 'python <kit>/tools/gate.py wait-result kit/x --tip <sha> --timeout 1740 -C <repo>'})
```

`<kit>` is the kit checkout (`<tools_dir>` in docs/guard.md), `<repo>` any checkout of the gated repository. Wait for a landing with `--kind land`, or submit it with `land.py --wait-result --submit`, which prints these same two lines when it ends (Submitting a landing, "Waiting in the same call"). The Monitor caps `timeout_ms` at 30 minutes, so `--timeout 1740` ends first. Exit 7 with a `TIMEOUT:` line means no final record at that tip yet: the run is still going, has not started, or ended without one (see No record); arm it again, and look at the gating session when it keeps timing out. The exit code is the verdict (0 pass, 1 anything else, `error` included); the printed record says which. A `--tip` that is not 7 to 40 hex digits, or a `--timeout` that is negative, `nan` or infinite, is USAGE (2). Do not pipe it into another command: guard.py's `wrapped-gate` rule (docs/guard.md) refuses `gate.py` piped.

### Waiting on a gate: who arms what

Your own gate: run it in the foreground with `timeout` 600000 when it fits; otherwise `run_in_background` (the kit's background mode, never a stray `&`) and end the turn. Give each run its own log, named for the branch and tip, in your own scratch folder: a shared log let a worker report GATE OK from another branch's lines. The exit notice wakes you. No Monitor, no polling the log, no sleep. Never `tail -f` or `-F` a log in Monitor or a background call: on Windows the tail outlives its Monitor and keeps reading the file every second. A gate another session runs: `gate.py wait-result` (above); a run of your own: `run_in_background` and its exit notice. A branch gate stays attached until its verdict, waiting for the machine lock included (`runner.branch_gate`), so its exit code is the verdict. The exit notice is a message the host sends you, never text in your own turn. While the log holds only its `result record:` line, the gate is still queued or running; `gate.py wait-result <branch> --tip <sha> --timeout 0 -C <repo>` says whether a final record exists yet. Monitor with `wait-result` is only for a gate another session runs: one arm at `timeout_ms` 1800000, re-armed only on exit 7. One wait or sleep call stays under the cache TTL of your own role: about 4.5 min on the 5-minute cache, about 55 min on the 1-hour cache (`cacheTtl: 1h` in the role's `experimental:` block in `hosts/claude/shell/agents/<role>.md`; no such line means 5 minutes); a call that idles past it re-writes the cache. Wait with wait-result calls, never sleep loops. Never re-arm a wait because a turn ended with nothing new: each Monitor fire wakes the session for a full cache read.

### The branch gate budget

`kitlib/gate/budget.py`, asked by `runner.gated` just before the session gate cap, for a branch gate only (`capped=True`, with `budget_branch` the checked-out branch). Skill builder, step 7, tells the worker the rule: after 5 gate runs on one branch, stop before the 6th, report to the coordinator and ask.

- A run counted: a history line of the machine lock with `gate` true, a priority other than `land`, the gated repository (case aside) and the branch, that ended at or after the branch was made (the first entry of its reflog, so a branch made again under an old name starts at 0). A fully reused gate books nothing and counts nothing. A landing, the daily full run and redfirst never ask. History lines written before they kept `gate` never count.
- The branch is the line's `branch` (case aside), which the branch gate books with, never its slug: two branches of one slug (`kit/a`, `kit-a`) each get 5, and a gate under `gate.py --slug` still counts. A null `branch` never counts. A line written before history lines kept `branch` counts by the branch's default slug (`runner.slug_of`).
- At the limit (`budget.RUNS`, 5) a branch gate prints `REFUSED: the branch gate budget: ...` naming the counted run ids, with an `Instead:` line, and runs nothing. Below it the gate says `gate budget: run <k> of <n> on <branch>`.
- `gate.py allow BRANCH --runs N --why TEXT` is the coordinator's: it writes `<dev_drive>\pm-kit\kit-gate-budget\<repo key>\<branch stem>.json` (`budget.allow_path`; `branch`, `runs` the new total, `why`, `at`, `by`), replacing any earlier one, outside every checkout like the gate-OK record folder. The limit is the larger of 5 and `runs`. An allowance written before the branch was last made is not read. With no `dev_drive` it writes `<git common dir>/kit-gate-budget/<branch stem>.json` (`budget.legacy_path`) instead, and the budget reads that file only then (`budget.allowance`); with a `dev_drive` no .git copy is written or read.
- The owner is never refused. Anything the check cannot read (reflog, history, allowance) is one `WARNING: the branch gate budget is not applied: ...` and the gate runs (fail open).
- Known limit: a new branch made at the same tip is another branch, with a budget of its own.

### The session gate cap

`kitlib/gate/gatecap.py` `wait_turn`, called by `runner.gated` just before it books a branch gate's run (`capped=True`, which only `runner._gate_checkout` passes), in the store it books in. Off unless the machine config sets it: `"coordinator_start".gate_cap`, `{repo name: n}`, the name as the lock records it (`.kit.json` `"repo".name`, else the checkout's folder name), matched exactly, else lower case. Unset, 0 or null: no cap. A value that is not a whole number 0 or more, or a machine config that cannot be read, is said as one `WARNING: the session gate cap is not applied: ...` and caps nothing.

- Counted: live gate runs (booked, waiting or held) of that repository, matched without case, whose recorded ancestors hold the caller's nearest agent host (`kitlib.lock.store.owns`): one coordinator and its in-process subagents count together. Not counted: a landing's runs (priority `land`), another session's, the run this process is inside. An agent whose host cannot be read (`kitlib.lock.store.caller` gives role agent with no host: a detached run, or a process tree or host registry it could not read) cannot tell its session's runs from another's, so every gate run of the repository counts (fail closed), less the same exceptions bar another session's.
- At n, the gate says one line, `the gate waits for the session gate cap: <k> of <n> gate runs of this session in <repo> are in flight (<run ids>); it books when one ends` (for an agent with no readable host, `of this session` reads `(all counted: this agent's host cannot be read)`), counts again every `POLL_S` (5 s, never under the lock's `queue_poll_s`) and says nothing more, then books as usual. A fully reused gate books nothing and never waits.
- Never waits: a landing (`merged_gate` books through `gated()` without `capped`, or runs in the slot it holds), the daily full run (`kitlib.dailyfull` calls `gated()` without `capped`) and the owner (role owner, no agent host above the caller, so no run is the owner's session's). The caller and the cap are read only while some gate run of the repository is live.
- Known limit: the count and the booking are not one step, so gates of one session started together can each count below n and all book, going past it.

### Whose run a log is

A branch gate's log is its stdout, saved by the caller (`gate.py ... > <log> 2>&1`). Its header line, `gate <branch> at <tip>, base ...`, names the run: match that branch and tip to the result record its `result record:` line names (the record's `branch` and `tip`), or to the branch and `git rev-parse HEAD` you gated. A log whose header names another branch or tip is not that run's log.

Two gates writing one file at once (seen twice: two workers of one session, one `gate-full.log` name in the session's shared scratch folder) each write at their own file position: the second shell's `>` truncates the file, its header lines land at the start, then NUL bytes, then the first run's own later lines. So a branch gate (`--plan` included) whose stdout is a disk file first takes an exclusive OS lock on one byte far past any log's end, through that handle (kitlib/gate/outfile.py `claim`, from tools/gate.py `main`). A second gate on the same file is `REFUSED: this gate's output file <path> is the output of another gate run that is still running; ...; nothing ran`, exit 4, with an `Instead:` line (give each run its own log, named after the branch and tip), and says nothing else, no header. The lock ends with the process. A lock Windows refuses for another reason is one `WARNING: the gate could not claim its output file ...` and the gate runs.

Not caught: the second shell's `>` still truncates the file, so the first run's lines from before it are gone (its later lines, `result record:` and verdict included, still name its branch); a stdout that is not a disk file (a console, a pipe; PowerShell 5.1's `>` writes the file itself, through a pipe) claims nothing; a gate from an older kit takes no claim.

## Stopping a gate

`gate.py stop RUN [-C DIR]` (kitlib/gate/stop.py `stop_run`) ends one gate run that hung or is no longer wanted. RUN is the machine lock's run id, `r-...`, printed on the gate's held line and by `machine_lock.py status`; the result record's `run_id` is another id and is not taken. What the run is comes from its lock record alone.

| The run | What `gate.py stop` does |
|---|---|
| no lock record, or a record without `gate` | `REFUSED: ...; nothing was stopped`, exit 4. Only a gate's own bookings set `gate`, so nothing else can be ended here |
| a landing's | Refused the same way, live or ended: its own lock run (priority `land`, a `resource`, a `landing:` note), a run under a landing's process (the record's `ancestors` or `parent`), a run under a running land record's process, or the holder of the landing lock of `-C`'s repository. A landing lock that cannot be read counts as held. The landing lock is only ever read. These are checks of this machine: a load node's land gate shows none of them on the node (Known limits) |
| another session's | The lock's own rule (`kitlib.lock.api.end_run`): the owner, or the agent session the record's `ancestors` show it belongs to; anyone else is refused with the lock's message. A run with no agent host above it is the owner's alone |
| already ended, or its process gone | `ALREADY GONE: ...; nothing was stopped`, exit 0. A dead run's lock record goes the way any booking moves it (`store.live_runs(prune=True)`, ended `reaped`); a `running` result record is finished `error` (`result.finish_dead`), or `stopped` when a stop is what ended the run. The lines say what was left and where it went |
| live | Stopped, below: `STOPPED: gate run <id> (<repo>/<slug>): ...`, exit 0, then a `result record:` line |

**A live run.** The stop goes through `api.end_run`, the lock's own stop request. The gate's own process sees it (`Slot.wait`, or its turn in the queue), ends the run's process tree, starts no further step (a step's `continue` does not matter), releases its lock as `cancelled` and exits 16. Its result record's verdict is `stopped`, code 16; no gate-OK record and no red-run record are written, so `gate.py --rerun` still has the tip's red run, and a waiter (`gate.py wait-result`) ends with exit 1. A gate stopped while it waited for its turn ran nothing; the lock ends that run `not acquired`, code 1, with the request's `stopped_by`, and it counts as stopped. A targeted rerun stops the same way, with no rerun record.

**A hung gate process.** A run still live after `settings.stop_s` (default 60 s) is not polling. Only then is its process ended from here, with `process.terminate_verified`, which ends a pid only when its creation time is still the lock record's, judged on the handle it kills through: never by name, never a recycled pid. A record that changed meanwhile, has no creation time, or names a process that cannot be ended is `STOP FAILED: ...`, exit 1, with nothing more ended. The job closes with the process, which ends the tree. The lock's reap then frees the run (ended `reaped`), and the result record is finished `stopped` from here (`result.finish_stopped`, which leaves any record but that run's `running` or `error` one alone).

**Known limits.** A gate waiting at the session gate cap has no lock run yet, so it has no id to stop. A process that left the run's job is named (`NOT ENDED: ...`), never ended, and a shared build daemon is spared as in any stop (Build daemons). A stop that arrives after the gate's last check of it finds the run ended by itself and says so: its verdict stands. A stopped gate counts toward the branch gate budget, as its history line does. A wrapper of an older kit reads the stop as a failure, not `stopped`. `machine_lock.py stop` of a gate run also ends it `stopped`, and is the lock's tool, with none of these gate checks. A load node's land gate (`kitlib/loadnode/landgate.py` `land_gate`) runs `runner.merged_gate` with no slot or `book_kw`, so on the node it is a plain gate run: `gate.py stop` run there ends it, and main reports `NOT LANDED` with nothing pushed.

## Targeted rerun

`gate.py [-C DIR] --rerun [--slug S] [--log-dir D]` (kitlib/gate/rerun.py `rerun_gate`) reruns only the failing tests of the tip's latest red `gate.py --full` run, to tell a flake from a real failure. It takes no `--base`, `--plan`, `--full` or `--only`. It covers kit_tests and unittest reports only: a red step of another test runner, gradle or dotnet for one, is uncovered (below), and the refusal says so.

- **The red run.** A `gate.py --full` that fails, with no `--only`, of a tree that was clean when it started and when it ended, with HEAD unmoved and the stash stack still empty, writes a red run (`runner._red_record`, `rerun.record_red`) and says `red-run record: <path>; a targeted rerun of the failing tests: gate.py --rerun ...`. It holds the commit, its tree and author, the base, the gate config's hash, and each step's status. A FAIL step also gets the test ids its log names (`rerun.parse_log`: a kit_tests report, whose ids take the `KIT_FAKE_GIT` value of the tier header above them, or a plain unittest report), each with the step's directory, or why the step is uncovered (below). A red run that cannot be written is one `WARNING: no red-run record ...`. The red run never changes the gate's verdict.
- **The rerun.** It runs on a clean tree at the commit of the red run, which must be HEAD. Under one machine-lock slot, booked as a gate run of the branch (`gate=True`, the branch, the red run's tree), it runs `python -m unittest -v <class>` once for each failing class at the tip, in the step's directory, with the mode the class failed in set in its environment. Each class is paired with the same command in a throwaway tree at the base (the control; kitlib/redfirst `make_tree`, removed afterwards). Then it runs, whole, every step the red run never reached (NOT RUN). It counts toward the branch gate budget and waits for the session gate cap like a branch gate (The branch gate budget; The session gate cap).
- **The class verdict.** A class run passes an id only when it exits 0, its summary is `OK`, it ran at least one test, and it shows that id run (`rerun.judge_class`). Under `OK (skipped=...)` or `OK (expected failures=...)` only an id shown `ok` passes. A fixture id (`setUpClass` and the like) passes when some test of its class or module passes.
- **FLAKE.** Every failing id passed at the tip, every NOT RUN step passed, warned or was skipped, and no id failed twice on the branch (Failed twice). It prints `RERUN FLAKE: ...` (exit 0), the rerun record's path, and a `backlog.py add FLAKE-<CLASS> ...` line. The builder reports that line to the coordinator, who decides on filing it.
- **REAL.** Anything else prints `RERUN REAL: ...` (exit 1): the failure is real, and the tip never lands on it. An id that already failed twice (Failed twice) is REAL before anything runs: `RERUN REAL: <ids> failed on this tip and failed twice on its branch ...; nothing was rerun` (exit 1, nothing booked, no rerun record). **VOID**: the work tree changed, or HEAD moved, while the rerun ran (exit 1). A VOID rerun still uses the red run's one rerun.
- **The control** is information only. A red control never turns a REAL into a FLAKE. A control that fails is said as `(also red at base)` on its class's line, recorded as `control: red`, and listed as `also red at base <sha>: <classes>` (a break that was there before the branch). A class the base does not have is `absent`.
- **Refused** (exit 4, nothing run, nothing booked): no red run of HEAD; a tree that is not clean, or a stash entry; the latest red run already rerun (one rerun per red run: the next step is a fix, or a new `gate.py --full`); a gate config that is not the one the red run used; a red run that is uncovered; and rerun records of the branch that cannot be read, or a branch git cannot list.
- **Uncovered.** A red run is uncovered when a FAIL step failed on more than its exit code and a missing pass pattern, when its log cannot be read or is neither a kit_tests nor a unittest report, when a kit_tests unit is not FAILED (`TIMEOUT`, a runner failure), when a test could not be loaded (`unittest.loader._FailedTest`), when the FAIL/ERROR lines do not add up to the `FAILED (...)` summary, when there is an unexpected success, when the kit_tests run was interrupted or refused, or when a step's directory is outside the tree. An uncovered tip lands only on a passing `gate.py --full`. A gradle log stays uncovered because it cannot carry a FLAKE: a failure line gives a simple class and a display name (`ApiLayeringTest > api.errand <-> api.movement ... FAILED`), not a class the rerun can name; it shows no test that passed; a failed build can show test lines and die of a Gradle error (`java.io.EOFException`); and the rerun runs `python -m unittest`, not a repository's own Gradle command.
- **Records.** `<dev_drive>\pm-kit\kit-gate-rerun\<repo key>\<commit>\`, one file per run, written once and never rewritten: `red-<ns>-<token>.json` and `rerun-<ns>-<token>.json`. Each carries the sha256 of its own canonical JSON (`hash`), and a rerun names the hash of the red run it reran (`red`). The commit's history is every file in its folder. A file whose name, schema, hash, commit or kind does not match, or that cannot be read, makes the whole folder unreadable, and that refuses (fail closed). With no `dev_drive` there is no folder, so no red run is written and nothing can be rerun.
- **Failed twice.** The rule applies to a tip that has a red run of its own. An id counts once for each red run that names it and once for each rerun whose tip run did not pass it, summed over the tip and every commit of its branch, `git rev-list <tip> ^<merge base>` (`rerun.branch_twice`; the merge base with the red run's base for `--rerun`, with the landing's base for a landing). An id that failed on the tip and counts two or more makes the tip never land, whatever other record it has (Landing, step 4). An id that failed only on earlier commits does not stop a tip that did not fail it. A tip with no red run of its own is not counted: a green `gate.py --full` of a fix lands. A record of any branch commit that cannot be read refuses, whatever the tip's own count (fail closed). Only the red runs of `gate.py --full` gates of branch commits, and their reruns, are counted: a failure seen only in a default-mode or `--only` gate, or in a red run that wrote no record (`WARNING: no red-run record ...`), is not counted.

## Landing

kitlib/gate/land.py runs from the main checkout, on main, and merges and gates in a landing tree of its own (step 5): the main checkout is never merged into, reset or gated. In this order:

1. **Usage.** Every hash is a full hash, one `--expect-tip` per branch, each branch and tip named once; `--expect-main` is optional. The config is read at the main checkout's HEAD.
2. **Refusals.** It refuses when the checkout is not main, HEAD is not on main, a branch is main or missing, or a batch has more branches than `"landing".batch_max`.
3. **Turn, fetch and lock.** Before it fetches or merges anything, the landing books its one slot in the machine lock (`Lander.book_turn`): `book(<"gate".kind>, <repo>, <branch[+branch...]>, gate=True, resource="landing:<git common dir>", priority="land", wait_s=<--wait>, no_wait=<--wait is 0>, store=...)` (kitlib/lock/run.py; docs/lock-api.md). That booking is its place in the landing queue (The landing queue), and the merged gate (step 6) runs in it and books nothing more. Just before it books, the landing chooses where the merged gate runs (`Lander.plan_route`, `kitlib.loadnode.landroute.plan`) and says `gating on load node <n>: <why>` or `gating here: <why>`, or nothing when the choice is quiet (a kit checkout, no registry, no node opted in). Routed to a load node, it books with `cores=1`: the landing's own work, while the node runs the gate (docs/load-nodes.md "A landing's merged gate on a node"). Not given within `--wait` seconds: NOT RUN with the lock's code (Exit codes), nothing changed. At its turn it fetches `<remote>`, then takes the landing lock file (kitlib/records/landing.py) with what is left of `--wait`, saying `waiting up to <s> s for the landing lock` once (`Lander.take`); not had in time is BUSY. Branch gates never take the lock file, and never book with that resource.
4. **Follow and locked checks.** It fetches again, under the lock. HEAD must still be on main (`Lander.locked_checks`: the turn can come long after step 2), or it is REFUSED with `the main checkout is on <branch>, not <main>, at the landing's turn`. The landing's base is `<remote>/<main>` as fetched, at its turn (`Lander.onto_origin`): a local main only behind it, with nothing unpushed, is fast-forwarded first (`git merge --ff-only`, only with HEAD on main, a clean checkout and no merge in progress), said as `fast-forwarded <main> from <old> to <remote>/<main> <new>`. This fast-forward stays with the landing tree: it runs only here, before the merge, and only moves a clean main checkout on main that is behind, so the checkout starts at the base the landing merges onto; the merge itself is never made there (step 5). A local main with commits the remote lacks (`<main> is at <sha>, with commits <remote>/<main> (<sha>) does not have: push them or set them aside by hand; ...`), or one the fast-forward cannot move, is REFUSED. When the base is not the commit the config was read at, the config is read again at the base (`Lander.follow`): one naming another main branch or remote, or one that no longer takes this landing (its batch size), is REFUSED; otherwise the landing tree, the merged gate, the hook module and the records all use the base and its config. When `--expect-main` was given and is not the base, it says `main moved on from <expect-main> to <base>; merging onto <base>`, and never refuses for that. Then the checks: each tip equals its `--expect-tip`; the main checkout is clean; the repository's stash stack is empty (The stash guard); no merge is in progress; no branch is already merged; in a batch, no tip contains another; for every owner-only path that landing the branch would change, every branch commit that changes it is authored by the owner ("Owner-only commits" in docs/guard.md); and, for a `ref` or `branch` backlog store, no branch's history holds a root commit of the store (kitlib/backlog/at_landing.py `ancestry_refusal`; a store that cannot be read refuses too); every tip has a gate-OK record of exactly that commit from a `gate.py --full` pass (`Lander.tip_gate_check`, `gate_ok.verify_full`; Gate-OK record), or a verified `select` or `docs` record the base's config takes (`Lander.select_refusal`, read from the base's config only, never the tip's). Such a record counts when the paths its own diff (its `base`..tip) changes cover the landing diff (merge base with the base..tip), and either the landing diff is docs-only under the base (Docs-only changes) and every base `docs_only` step passed in it (pass, warn or reused), or the record is a `select` one, the base sets `"gate".smoke_steps`, every smoke step passed in it and the landing diff changes no gate config file (`.kit.json`, a section file, the hook module; `reuse.config_hits`). Under a base that sets `"landing".shared_paths`, a `select` record also counts without smoke steps, and any `select` or `docs` record is refused when the landing diff changes a shared or strict path (Shared paths). Under a base that sets `"landing".gate_once`, a `select` record counts without smoke steps and whatever shared path it changes, and any `select` or `docs` record is refused when the landing diff changes a strict path (Gate once at landing). A base that sets none of the four keys lands only `--full` records. A tip with none of these records lands on a FLAKE targeted rerun of its latest red `--full` run (`rerun.verify_flake`; Targeted rerun): the rerun of exactly that red run, which must be the only one, said FLAKE, passed every id the red run named in the mode it failed in and every step it never reached, and the records still match git. When the tip has rerun records and they do not land it, the refusal below adds `; its targeted rerun does not land it: <why>`. Checked first for each tip, whatever record it has: a tip with a red run of its own and a test that failed on it and failed twice on its branch (Targeted rerun, "Failed twice"), or whose rerun records or its branch's cannot be read, is REFUSED as `<branch> tip <sha> does not land: <why>` (`rerun.twice_refusal`). A miss is worded `<why>, and <what the select check found>`. Before any tip is read, a base whose `.kit.json` has a "gate" section (`detect.configured`) from which `--full` selects no step (every step is `manual`, there is none, or each is dropped by another selected step's `skip_if_selected`) is REFUSED with `the "gate" section of .kit.json at <base> leaves no step for --full to select (...); no branch can land until <main> gives the gate a step that is not manual and that no other step's skip_if_selected names` (`Lander.no_full_step`): `--full` and the merged gate select every step but the manual ones, then drop each step whose `skip_if_selected` names a selected step (kitlib/gate/steps.py `select`), so both would refuse with no gate step selected and no tip could get the record. A gate whose selected steps all `require` something missing on this machine is not refused here, since only the probe can tell: the branch's `gate.py --full` gives `REFUSED: no gate step ran` with what each step requires (Exit codes). Then a default-mode run's record, a record written before the `full` key, a record of another commit (an earlier tip) or one git no longer agrees with is `<branch> tip <sha> has no full-gate OK record: <why>; gate that tip whole first: python "<gate.py>" -C "<worktree>" --full`, where `<gate.py>` is the worktree's own when the kit lands itself (its main checkout has the kit's layout, `content/roles/` and `tools/render_content.py`: `kitlib.content.oncommit.is_kit`, whether the running kit is a checkout or a plugin export; The caller's checkout) and the running kit's otherwise, and `<worktree>` the worktree that has the branch out (`Lander.full_gate_command`). When the kit lands itself and the tip's record lacks the `full` key (the record `gate_ok.verify` takes, written by a gate from before the key), the part after `<why>; ` is instead `merge <remote>/<main> (<base>) into <branch> first (...), then gate the merge whole and land that tip: python "<gate.py>" -C "<worktree>" --full` (`Lander.full_gate_advice`): the branch's own `tools/gate.py` may be from before gate-OK records had the `full` key, and such a gate.py never writes it. The record's `gate_config` is not compared with any config: a branch gate writes a record only for a clean tree, with `config_rev` the tip (`runner._gate_checkout`), so it hashes the tip's own committed config; reading that config again here would use the landing kit's defaults and schema, which differ from the branch's when a kit branch changes the gate's defaults or adds a config key; and what lands is decided by the base's config, which the merged gate (step 6) reads. And a branch that changes a strict path lands alone, with a strong-tier verdict from a reviewer who is not its author (`Lander.strict_check`; Strict paths). Every other branch, each of a batch on its own entry, lands only with a verdict queued at its tip from a reviewer who is not its author, on any model (`Lander.verdict_check`, `Lander.review_refusal`): the Strict paths bullets on the entry, its tip, a carried entry and the author hold, each refusal worded `<branch>: <why>`; only the tier rule is the strict paths' alone. No branch prefix is exempt. Any miss is REFUSED, with nothing merged.

   The last check is the scope check (`Lander.scope_check`). Every path a branch changes, from its merge base to its tip (a rename counts as a delete and an add), must fall in the scope of a record the branch holds, matched as `kitlib.backlog.scope.members_collide` matches (whole path components, casefolded). A branch holds a record that is `pulled` with `pulled_by` the branch, and a `pulled` record that a `Closes: <ID>` trailer in the branch's own commits names, whoever pulled it. A record closed early and so gone from the store counts only when a trailer names it, read at its last version, from before the commit that deleted it. Some paths need no record: those matching `land.SCOPE_ALWAYS` (`tests/**`, and `docs/INDEX.md`, where the doc-budget check makes every new doc add a line), and a folder store's own folder. The files `tools/render_content.py` writes are not exempt, because kitlib cannot import tools/ to learn which they are: a rendering change puts them in a record's scope. The records are read from the configured store and from the PM data branch's store (step 9). A `ref` or `branch` store is read as its remote holds it, without moving a ref. A folder store is read at the branch tip, which counts a record file the branch deleted at its last version. In a batch, each branch is checked on its own commits (`<tip> --not <base> <earlier tips>`), and its merge base is taken with the base and the batch's earlier tips. The check's lines:
   - a path outside every held scope: `<branch> changes <n> path(s) outside the scopes of the records it holds (<IDs>): <paths>; widen a record's scope first ...: <backlog.py set <ID> --scope ... command>; or land them on their own branch`. It names at most `land.SCOPE_SHOWN` paths and counts the rest. A path holding a comma or a glob character (`*?[]{}`) is compared literally, so a folder member covers it; one still outside is listed as `(no scope member can name it)`. A path the check cannot decide (a backslash, a drive letter, a `..` or empty component, `none`) is listed as `(undecidable: <why>)`. Both are left out of the command.
   - a store that cannot be read, or that holds a record it cannot read, while some path is not covered by the records it could read: `cannot read the backlog store to check <branch>'s paths against the scopes of the records it holds: <why>`. Such a store gives no records. When the records that could be read cover every path, the unread store is not mentioned.
   - a branch that holds no record, while a store that holds records was read: `NOTE: <branch> holds no pulled record; its paths were not checked against a scope`, right before the `LANDED` line. It never refuses.
   - a check that cannot finish: `the scope check of <branch> stopped (<why>)`.

   While `land.SCOPE_REFUSES` is False, as now, a miss does not stop the landing: it prints `WARNING: <why>; the landing went ahead: the scope check only warns for now (kitlib.gate.land SCOPE_REFUSES)` right after the `LANDED` line, and the exit is 0. With it True, a miss is `REFUSED: <why>; nothing was merged`. Either way, the fix is to widen the record's scope first with the `backlog.py set --scope` command the line names (`set` checks the new members against every live pull's scope), or to land those paths on a branch of their own.
5. **Landing tree and merge.** The merge happens in the landing tree (`Lander.prepare_tree`), never in the main checkout: a detached linked worktree the kit owns at `<main checkout>/<repo.worktrees_dir>/_landing` (`land.TREE_NAME`; docs/kit-json.md), locked with the reason `kit landing tree (kitlib.gate.land)` (`land.TREE_LOCK`). The first landing makes it (`git worktree add --detach --lock`), said as `the landing tree <path>: made`. A later landing reuses it when it is clean, checked out at the base; its ignored files, such as build caches, stay. When it is gone, not clean, mid-merge, not a work tree of its own, or cannot be put at the base, it is removed (`git worktree remove --force --force`, or a prune when the folder is gone) and made again, said as `the landing tree <path> <why>: recreated` (`Lander.add_tree`). A folder at that place that git does not list as a worktree, or a listed worktree there that is not a locked detached tree with that reason, is REFUSED (`... it was left as it is: move it aside`), and so is a place that is the main checkout or holds it; nothing is merged. Then `git merge --no-ff <tip>` runs in the landing tree, for each branch in order. A conflict is aborted there (an abort that fails is a WARNING: only the tree is left dirty, and the next landing recreates it), the batch's earlier merges are dropped with the tree's state, and it gives FAILED with the verdict line `CONFLICT <branch> with main <base>: the author merges main` (the result record's `summary`): the branch's author merges main into it and the landing is submitted again. Main is never moved.
6. **Merged gate.** It gates the landing tree once in the slot of step 3 (`runner.merged_gate(..., slot=, tree=)`), adding each step's `merged_args`. It selects every step that is not manual, as `gate.py --full` does, whatever paths the merge changes (`runner._merged_gate`): each runs its `cmd`, and only a `--full` landing its `full_cmd`: a strict one, or one under `"landing".gate_once` whose merge is not docs-only (Gate once at landing). A step gated on globs the branch never touched still runs, so the landing tree, which starts without the main checkout's ignored caches, gets what the author's full gate had, such as an asset import before the engine tests. The steps run in the landing tree, and a check step gets it as `ctx['root']`; the repository's name and its log folder are the main checkout's (`runner._merged_gate`). Check steps run the hook module as the base has it, read from that commit like the config (kitlib/gate/hookrev.py), so a branch is gated by main's checks, not its own. Step `cmd`s run the merged tree's files. A merge whose base..merge diff is docs-only under the base's config (Docs-only changes), in a landing without `--full`, runs only the `docs_only` steps (and `setup`) and says `a docs-only merge: only the "docs_only" steps run`. A step may be reused instead of run (see Gate reuse), in a one-branch landing that is not strict also from the tip's own `--full` record when the merge holds the tree it passed on (Gate reuse, "The same tree"). On red, or when no step ran, it is NOT LANDED (FAILED or REFUSED): the merge is dropped, nothing is pushed, and nothing is reset anywhere, since the merge was only ever in the landing tree. Files a step left there go with the tree: the next landing recreates a tree that is not clean.

   Routed to a load node (step 3), the merged gate runs there instead, as a land job (`Lander.node_gate`, `landroute.run_on_node` with `docs` set as here): a pass is green, with `ran on load node <n> as job <j>` among its lines; any other end is NOT LANDED, and so is any exception that is not `landroute.Fallback`. A merge the node started on is never gated again on main. The landing gates here instead when the tip's `--full` record has the merge's tree (`same_tree_why`: its steps are reused here, never on a node), when no node qualifies at its turn (`recheck`; another node that does takes it, said as `gating on load node <n2>: ...`), or when nothing ran on the node (`Fallback`). It says `gating here: <why>`, releases its 1-slot run first, then books the gate kind's full run as in step 3, with no wait limit (`Lander.rebook_here`): booked while the 1-slot run is still held, a kind of every slot, an owner whole hold or a gpu pool would wait on itself. The lock file stays held meanwhile (The landing queue). The lock refusing that run is NOT LANDED.

   Main moved on before the turn to a base whose config names another `"gate".kind` than step 3 booked (step 4, `Lander.follow`): on main, the landing says `the base <b> books "gate".kind <k>, not <k0> as this landing did: releasing the landing's <k0> run and booking a <k> run for the merged gate, waiting with no limit`, releases its run first, then books the base's kind at its own size, as the fallback above does and for the same reason (`Lander.rebook_kind`); the lock file stays held, and the lock refusing that run is NOT LANDED. Routed to a load node, it asks the nodes again for the base's kind's slots (`Lander.route_need`, `landroute.need_of`); a kind that cannot be sized gates here as above, and the node's gate keeps the 1-slot run booked at the old kind.
7. **Unchanged.** On green, the landing tree's HEAD must still be the merge, with no tracked change and no untracked file there, and the stash stack must still be empty (The stash guard; `Lander.unchanged`). Otherwise nothing is recorded or pushed and the merge is dropped (FAILED, `NOT LANDED: the merged gate passed, and <why>; ...`). The commit pushed is the commit gated: what the owner does in the main checkout meanwhile (a commit, an edit, an untracked file, a push of main) reaches neither the gated tree nor the pushed commit. A `"landing".log_dir` resolves in the main checkout (`runner.log_base`), not in the landing tree, so logs there that git does not ignore do not stop the landing: they leave the main checkout not clean, and the next landing is REFUSED until they are moved (Go-live notes).
8. **Push.** It writes the merge's gate-OK record (its `mode` `docs` when the merged gate ran only the docs-only steps, else `full` or `select` as the landing's `--full` says; its `ran_on` the node, host key and job when the merged gate ran on a load node, Gate-OK record), then runs `git push <remote> <merge>:refs/heads/<main>` from the main checkout (never forced), and `git ls-remote` must show the merge (`Lander.push`). When `<remote>/<main>` moved on to a commit without the merge while the gate ran, the push is refused: `NOT LANDED: <remote>/<main> moved on to <sha> while the merged gate ran, so the push of the merge <sha> was refused (a landing never forces); nothing landed, ...: land again` (FAILED, the lock released, the branch kept). Landing again merges onto the new `<remote>/<main>` and gates that whole. When the push may have landed and git cannot tell (the push was interrupted; `ls-remote` cannot read `<remote>/<main>`; the remote's main is a commit this checkout cannot place against the merge, even after a fetch; or the push did not land while `<remote>/<main>` is still the base or absent, unless git refused it), it is STUCK (below), unless the push never connected (below). A push git refused (exit 1 with git's own ref status line on stderr, `! [remote rejected] ...` from a hook or `! [rejected] ...` such as a non-fast-forward, `kitlib.gate.land.PUSH_REFUSED`) while `ls-remote` shows `<remote>/<main>` still at the base published nothing: `NOT LANDED: the push of the merge <sha> failed (<git's error>), and <remote>/<main> is still the base <sha>; nothing landed, ...: land again once the push can go` (FAILED, the lock released, as on a red merged gate). So is a push that never connected to the remote (`land.push_never_connected`): git exited 128 and every line on its stderr is `fatal: unable to access '<url>': <curl's error>` (`land.PUSH_NEVER_CONNECTED`), which git dies with only when its first request, the ref discovery (remote-curl.c `discover_refs`), fails before any pack is sent, with curl's error one that only a connection never made gives: `Could not resolve host: <host>` (or `proxy`), `Failed to connect to <host>:<port> after <n> ms: <reason>` (curl 8; git 2.55.0.windows.5 with libcurl 8.21.0 prints it for both a refused port and a timed-out connect, `<reason>` `Could not connect to server`) or the earlier `Failed to connect to <host> port <port>[ after <n> ms]: <reason>` (`Connection refused`, `Timed out`), and `Connection timed out after <n> milliseconds` or `Resolving timed out after <n> milliseconds` (curl's connect timeout, before any request). It is `NOT LANDED: the push of the merge <sha> never connected to <remote> (<git's error>), and <remote>/<main> <what ls-remote read>; nothing landed, ...: land again once <remote> can be reached` (FAILED, the lock released, the branch kept), whatever `ls-remote` read, unreadable included (in an outage it fails the same way), unless it shows the merge or a commit holding it. Any other curl error (`Recv failure: Connection was reset`, a TLS failure, `Operation timed out`), an `RPC failed` line (the pack's request, after the discovery connected), any further line on stderr (`the remote end hung up unexpectedly`, `send-pack: unexpected disconnect while reading sideband packet`) or any other exit stays STUCK. Otherwise a push that died (exit 128), exited 1 without that line (no message, what a git ended from outside leaves, `refs.KILLED_SHAPE`, named in the STUCK line; only a stray warning; or a bare `failed to push some refs`, which git prints for any failed push), timed out or exited 0 while the remote's main is still the base stays STUCK on purpose: a connection dropped after the upload exits 128, a git killed after the upload exits 1, and the remote may still apply the update after the `ls-remote`. Once `ls-remote` shows the merge the landing stands (`Lander.phase` `pushed`): the tracking ref is set to it, and a release of the lock that fails, or an exception or Ctrl+C before the release ends, is still LANDED (exit 0) with a WARNING. Those lines name the command to break the lock when it is still held, and, for each store that takes part in step 9, the command that shows the branch's backlog records left to close (`at_landing.landable_commands`; `Lander.landed_anyway`).

   Then the main checkout's main is brought to the merge (`Lander.sync_main`): `git merge --ff-only <merge>` there, when HEAD is on main, no merge is in progress, main has no commit the merge lacks, and no local change or untracked file is on a path the merge changes (a local edit elsewhere is carried along). Otherwise nothing in the main checkout moves, and `WARNING: <branch> landed at <merge>, and the main checkout's <main> (<sha>) was not fast-forwarded to it: <why>` names what is in the way and ends with the command, `git -C "<root>" merge --ff-only <remote>/<main>`. Commits made in the main checkout are named and kept: rebase them onto `<remote>/<main>`, or set them aside, first. A main that is not checked out (HEAD elsewhere) is not moved with `git update-ref` either: it gets the same WARNING, since `merge --ff-only` in the main checkout is the only way a landing moves the local main, and the next landing is REFUSED until HEAD is back on main (step 4). The landing stands either way.
9. **Close.** After the release, every record the branch holds pulled is closed, `landed <merge>` (`at_landing.close_landed`), and so is every pulled record a `Closes: <ID>` line in the branch's commits names, whoever pulled it, read from the branch tip down to the main it was merged onto (for a batch, the previous branch's merge; `Lander.close_pulled`; docs/backlog-store.md "Lifecycle changes"). When such a record was held by a live branch that is neither main (the code repository's, in the PM data store too) nor in the batch, a WARNING says to tell that branch's builder (`at_landing._live_holder_warning`). Both happen in two stores:
   - the configured store, when it is a `ref` or `branch` store: one store commit each (`closed <ID> in the backlog store: landed <merge> (store at <sha>)`);
   - the PM data branch's store (kitlib/pmdata; docs/pm-data-branch.md), found as the worktree of the repository that has the branch `kit-pm-data.json` records checked out (`at_landing.pm_data_root`), unless it is the configured store or the main checkout itself: the record file is deleted in that worktree and the deletion committed there (`closed <ID> in the backlog store <store>: landed <merge> (committed <sha>)`); a commit that fails is a WARNING naming the `catch-up --apply` command for every path the close wrote, a commit stopped because another commit changed one of those paths on HEAD puts the close's files back and is a WARNING that ends, from the store read again (`at_landing._after_put_back`), in one of five ways: the record is still pulled by the branch (for a record a `Closes:` line names, while anyone holds it pulled, naming that holder), with the close command; the store no longer holds it, with no command; it is in another state and no longer pulled by the branch, with the `show` command; its file cannot be read as that commit left it, with the `show` command; or the store could not be read again, with the `show` command. A file it left adds the `git diff HEAD --` compare, and none gives a ready-made `catch-up --apply` command; and a commit whose index update fails is a WARNING naming the `git reset -q --` repair (kitlib/backlog/at_landing.py `_close_in`).

   A close that fails, a store that cannot be read, and an exception or Ctrl+C here, is a WARNING with the command to finish it, or to see what is left (`backlog.py landable <branch>`, one per store, `at_landing.landable_commands`); the landing stays LANDED and is never undone. A close command for the configured store names `-C "<a worktree of this repository>"` (`at_landing.WORKTREE`), never the main checkout the landing ran in, and the repository's own `tools/backlog.py` when it has one, else the kit's (`at_landing.close_command`); an owner-held record's command carries the owner's go that ends the hold (`at_landing._close_in`, as `plan_close` needs it). A command for the PM data store names that worktree.
10. **Cleanup.** Then each branch's remote branch, worktree and local branch go, unless `--keep-branch` (see Branch cleanup). Its lines come before the `LANDED` line.
11. **Mirror refresh.** Last, once the machine-lock slot is released too and nothing is held, a landing that LANDED pushes the merge to the mirror of main on each load node that opted the repository in (`Lander.refresh_mirrors`, `kitlib.loadnode.mirror.refresh`; docs/load-nodes.md "The mirror of main"). It adds at most 65 seconds to the landing's return, and nothing with no node opted in. Its lines come before the `LANDED` line; a failure, an exception or Ctrl+C there is a WARNING, and the landing stays LANDED.

An exception, SystemExit or Ctrl+C under the lock (`Lander.recover`): before the merge, the lock is released (a config error is REFUSED). After the merge and before the push, a merge stopped part way is aborted in the landing tree (best effort, `Lander.half_merge`), the merge is dropped and the lock released (FAILED, `NOT LANDED: ...`); Ctrl+C is then raised again, so the exit is 130. During the push it is STUCK (exit 3), Ctrl+C included: the merge may be on the remote. After the verified push it is LANDED (step 8). A second failure while recovering leaves the lock held: STUCK.

STUCK is only a push that may have landed and cannot be told (step 8). Nothing is ever reset: the main checkout was never merged into, and a merge that did not land needs nothing undone. The lock stays held at phase `stuck` so that no landing stacks on top. STUCK prints a `left:` line (the branch HEAD is on in the main checkout, main, the remote's main as `git ls-remote` reads it, the tracking ref, tracked changes, untracked files), then numbered steps to clear it, in order. Each command is on its own line starting `    $ ` (`land.STEP_CMD`); no step says reset, and none makes a `kit-stuck` branch. The steps fit what is left (`Lander.clear_steps`):

- **Push unknown** (`ls-remote` failed): the push may have landed. When the tracking ref holds the merge, `git fetch` and `git rev-parse <remote>/<main>` come first, then the On the remote steps; when git cannot place the tracking ref against the merge, only the Remote's main not here step follows. Otherwise `git fetch` and `git rev-parse <remote>/<main>`: if that shows the merge, the landing is done (bring main to it with `git merge --ff-only <remote>/<main>`, then break the lock); if it shows the base, the push did not land and nothing is to be undone; if it shows anything else, `git branch -r --contains <merge>` says whether the merge is landed (the list names `<remote>/<main>`). A failed fetch means stop: what it shows is stale.
- **On the remote** (the remote's main is the merge or descends from it; `Lander.on_origin_steps`): the merge is landed. When the tracking ref is not the remote's main, `git fetch` comes first, since `break_lock` compares main with it. A merge that reached the remote without a passing merged gate is named, with `git revert -m 1 <merge>` to run by hand once the lock is broken (newest first in a batch), never as a `$` line. Then `git switch <main>` when HEAD is elsewhere, tracked changes and untracked files to keep or drop by hand, and `git merge --ff-only <remote>/<main>` when main is only behind it; when main has commits the remote lacks, they are named to push or set aside by hand. Commits on the remote's main beyond the merge that no merged gate saw are named (`<sha> <subject>`), with the full gate to run on main once the lock is broken.
- **Remote's main not here** (`ls-remote` read a commit this checkout lacks, or git cannot place it against the merge, so whether it holds the merge cannot be told; `Lander.check_first`): one step, `git fetch` and `git branch -r --contains <merge>`, then only the lock break. The step says in words what to do: if the fetch failed, the list is stale, so stop and do not move main; if the list names `<remote>/<main>` the merge is landed, so bring the checkout to `<remote>/<main>` by hand; if not, the merge is not on the remote and nothing is to be undone: settle the remote's main with whoever pushed it.
- **Not landed** (the remote's main is the base, or another commit that does not hold the merge): the merge did not land, and nothing is to be undone; only the lock break follows.
- Last, a `python -c` line that runs `LandingLock.break_lock` (it refuses while the holder is alive or main differs from the remote's tracking ref).

A gate-OK record is written for the merge before the push. When the push is refused (NOT LANDED) or did not land (cleared from STUCK), the record for that merge commit stays in the record folder (Gate-OK record, "Where the records are"). It is stale but harmless: records are keyed by commit (`gate_ok.record_path`), that commit is not on main, and a reader verifying any other commit never reads it. Only a later push of that same merge commit would find it; it can be deleted by hand (the owner's: no agent's file writes reach the record folder).

**First switch.** A repo whose base `.kit.json` still uses old key spellings (docs/kit-json.md lists the current ones) fails to load with the kit loader, and the pre-push hook, the guard's git-push-main rule, the land.py preconditions, the trailers check and review_pack's base read all refuse until main loads. The owner lands that one switch by hand: rewrite `.kit.json` to the kit spelling, check it with `python <kit>/tools/preflight.py -C <repo>` (a load error prints `preflight: refused: kit configuration: <error>` and exits 2), then push the switch commit before the kit hook is installed in that repo, or with `--no-verify` from the owner's own terminal (the guard refuses `--no-verify` pushes in agent sessions). After that, normal landings work (docs/go-live.md "Landing tool").

### Pinned tools

A landing fast-forwards the main checkout it runs from: to `<remote>/<main>` before it merges, and to the merge once it is pushed (Landing, step 8). A tool running there would import the modules it loads lazily after that against the older ones it had already loaded: a mixed generation. So `tools/land.py` and `tools/gate.py`, started from the kit's main checkout or from an export whose marker names it (the plugin's: `<kit>/tools/gate.py`; marker `checkout`, `kitlib.pluginsource` `export_checkout`, docs/plugin-source.md "Layout"), first re-run themselves from an export of the kit's remote-tracking main, `refs/remotes/<remote>/main`, with the same arguments and the same interpreter flags (`-X utf8`, `-B`, `-I`, `-W` and the rest that the private `subprocess._args_from_interpreter_flags` gives, none when Python lacks it, and `-u` when this run's stdout is write-through), and exit with its code (kitlib/gate/pin.py `run`, called before the tool's own imports):

- **Where.** `<plugin export root>/pins/<sha12>`, the export root of docs/plugin-source.md "Layout" (`plugin.export_dir`, default `%LOCALAPPDATA%\pm-kit\plugin`). The export is made once per commit by `kitlib.pluginsource` `export` (marker `made_by` `kitlib.gate.pin`), under `pins/refresh.pid`, waited for up to 60 s (`pin.LOCK_WAIT_S`).
- **Leases.** Each pinned run holds `pins/leases/<sha12>-<pid>.json` while it runs and removes it when the tool ends. Each pin, under the lock, prunes (`pin.prune`): leases whose processes are both gone, every `<sha12>` export holding the marker that no live lease holds (except the commit it runs), and every `<sha12>.tmp`. A lease file that cannot be read is removed once older than 10 s (`pluginsource.LOCK_GRACE_S`); a lease that reads but is malformed is dead (`pin._malformed`), so it never makes the pin fail open nor holds an export.
- **Environment.** The child gets `KIT_PINNED=<sha>` and `KIT_LIVE_ROOT=<the main checkout>`. Any `KIT_PINNED` value means run live, so the child, and every tool it starts, never pins again. A command the tool prints (the gate, sweep, lock-break and backlog commands) names `KIT_LIVE_ROOT`, never the export, which a later prune may remove. The gate's own `{here}` runs (`steps.KIT_TOOLS`) use the export. `gate.py`'s own-copy refusal (The caller's checkout) compares against `KIT_LIVE_ROOT`. Started from an export whose marker names the main checkout, the tool is pinned through it as from the checkout itself, so `<kit>/tools/gate.py` counts as the main checkout's own: run from a kit linked worktree with no `-C` or a relative one, it is REFUSED.
- **Runs live.** A run with `KIT_PINNED` set, a linked worktree (its `.git` is a file), an export whose marker names no main checkout, and a checkout with no remote-tracking main run the code they are in, with no line.
- **Fails open.** When the pin cannot be made (the export root refused, the tracking ref unreadable, the lock busy past its wait, the export failing, no `tools/<name>.py` in it), stderr gets `WARNING: pin: running the live checkout's code: <why>`, `KIT_PINNED=live` is set, and the tool runs from the main checkout as before. Once the child has started nothing fails open, so the tool never runs twice. Ctrl+C while pinning exits 130 with the tool not run. From just before `Popen` until the child exits, the parent ignores Ctrl+C (`pin._ignore_ctrl_c`, main thread only), so it waits for the child, exits with its code and keeps the lease until the child exits. Ctrl+C reaches the child through the shared console and stops it as it does an unpinned tool. Two limits: when the current handler cannot be read (`signal.getsignal` gives None) nothing is changed; and a Ctrl+C in the instant after the parent starts ignoring it and before the child is attached to the console is lost (press again). A shell that already ignores Ctrl+C at the console level (`SetConsoleCtrlHandler(NULL, TRUE)`, as an agent's shell does) passes it to both processes, so no Ctrl+C reaches either.
- **Identity.** Run from an export, `runner.kit_identity` (the gate-OK record's `kit`) is the marker's commit, clean. The gate cache keys on the kit's file hashes instead (`reuse.kit_identity`, Gate reuse), so an export and a checkout of the same files are one kit.

### The landing queue

A landing is ONE entry in the machine lock's queue: the booking of step 3 (`Lander.book_turn`), with `resource="landing:<git common dir>"` (`land.queue_key`) and `priority="land"` (kitlib/lock/run.py `book`; docs/lock-api.md). Every checkout of a repository makes the same key, so they share one turn: one landing of a repository holds it at a time and the others wait in the machine lock's queue, where a `land` entry goes ahead of ordinary waiting runs. Landings of different repositories share the machine's slots, not the turn. The per-repository queue in `resources.json` (kitlib/lock/resource.py) is no longer used by landings. A landing never books its slot nested inside another machine-lock run: a submitted landing's environment drops `MACHINE_LOCK_RUN` (Submitting a landing).

The entry lives as any lock run's entry does, so a landing that dies leaves an entry the machine lock drops. The slot is given up whenever the landing ends (`Lander.run`, `Lander.drop_slot`), STUCK included: the stuck lock file keeps the next landing out. The merged gate runs in that slot (kitlib/gate/runner.py `gated(slot=)`), and as its steps finish it stops the build daemons they left (`Slot.stop_daemons`, as a gate's own release does) and ends the rest of their tree (`Slot.end_tree`), so nothing the gate started runs on through the push; the slot stays held until the landing ends. `land.py --queue` prints the lock file's holder, then the `land` entries, holding first, then waiting by ticket, each with its repo, slug, kind, run id and pid, and `; another repository` when its resource is not this repository's key; it joins nothing.

At its turn the landing takes the landing lock file (kitlib/records/landing.py). The lock file stays for what the machine lock does not hold: the stuck record, a gone holder's break, and a landing of a tool outside the machine lock (a token holder):

- **Free:** taken.
- **Held at phase `stuck`:** BUSY at once; a stuck landing is cleared by hand from its STUCK report.
- **Held by a process that is gone** (pid and start time, `LandingLock.holder_state`): when nothing is unpushed, the lock is broken (`LandingLock.break_lock`), said as `broke the landing lock of a holder that is gone ...`, and taken. When main differs from the tracking ref `<remote>/<main>`, or a merge is in progress (`LandingLock.unpushed`), it is never broken: BUSY at once, naming what is unpushed and the break command. When main is only behind the tracking ref, with nothing unpushed, BUSY says so and gives the fast-forward, `git -C <root> merge --ff-only <remote>/<main>`; the next landing then breaks the lock itself. When that holder died at phase `push` and `<remote>/<main>` has moved on from its `origin_at_take` (a lander killed after its verified push, before the main checkout's fast-forward), BUSY also says `its holder is gone after its push: ... so its push most likely landed and only the main checkout's fast-forward was skipped`, then gives the fast-forward, `Then land again`, and the break command.
- **Unreadable or of an old format** (`LandingLock.read` fails): waited for like a live holder, never broken; BUSY with phase `?` when `--wait` runs out. A taker killed between its create and its write leaves an empty lock file for good, and `LandingLock.break_lock` refuses an empty, unparseable or unreadable file even with `holder_gone=True`: delete such a file by hand, and only once `land.py --queue` shows no landing running.
- **Held by a live process, or by a token holder** (a tool outside the machine lock): waited for, up to what is left of `--wait` (`Lander.poll_s`, 5 s between looks).
- **Held by a landing waiting for this repository's turn** (a node-routed landing that fell back to main and is booking its full run again, Landing step 6: it gave the turn up and this landing got it): at each look, when the machine lock's queue holds a waiting entry with this repository's landing resource and the holder's branches, the landing says `the landing holding the landing lock (<branches>) waits in the machine lock for this repository's landing turn, ...`, releases its run and books again behind the holder with what is left of `--wait`, one cpu slot again when it is node-routed itself (`Lander.yield_turn`), then looks again after `poll_s`; the line is said once per holder. That booking not given in time is NOT RUN with the machine lock's exit code, not BUSY. A queue that cannot be read is no such holder. A landing from a kit without this waits until its `--wait` runs out, and the holder waits as long.

### Submitting a landing

kitlib/gate/submit.py. `land.py --submit` and `gate.py land --submit` check the arguments (USAGE as without `--submit`, nothing written), check the review the command names (below), refuse with nothing written (`submit.blocked`, exit 4, `REFUSED: ...; nothing was changed`) when a branch's land record is `running` in a process that lives (`result.running_state` `live`; one whose process died does not count) or already says it landed at that tip (`pass`, or an old record's `landed-ungated`, so the record is left as it is), write each branch's `running` land record (Result record) with one `run_id` for the batch and no `pid` yet, start the same landing again as a detached, windowless process, wait up to 15 s (`submit.CLAIM_WAIT_S`) for it to record itself (`submit.claim`), and print one `REVIEW` line for each branch with a verdict queued at the tip submitted (`submit.review_lines`; none for a branch with no entry at that tip), then the `SUBMITTED` line last, and exit 0:

```
REVIEW <branch> <tip>: <verdict> by <reviewer>/<model> (<reviewer_id>)[, carried from <sha> over <n> main merge(s)]
SUBMITTED <branch>[+<branch>...] tip <sha>[,<sha>] wait: python <kit>/tools/gate.py wait-result <branch> --tip <sha> --kind land -C <main checkout>
```

The command names the review each branch lands on, so whoever reads it (the owner, a permission check) sees the review in it: one `--reviewed-by <reviewer id>` per branch, in `--expect-tip`'s order, placed before `--submit` (nothing may follow `--submit` in the allow rule, docs/allow-rules.md), each the `reviewer_id` of the branch's verdict queued at its tip, or one of its ids when that field lists several (`submit.reviewer_ids`; case and surrounding spaces aside). `submit.named_review` checks it, with nothing written, before the running-landing check:

- A queue that cannot be found, or a branch with no usable verdict at its tip (none queued, one marked failed, one given at another tip and not carried, an entry that cannot be read), is REFUSED by name (exit 4): queue the verdict (tools/verdict.py add) first.
- A missing `--reviewed-by`, or a count other than one per branch, is USAGE (exit 2), followed by an `Instead:` line: the same command with each branch's queued reviewer id, in forward slashes with `--reviewed-by` before `--submit`, an argument holding a space double-quoted (`submit.again_line`). For a plain `tools/land.py` submit (`-C`, the branches and `--expect-tip`, with `--expect-main`, `--wait`, a one-word `--summary` and the flags) that is the allow rule's form; other forms get the normal permission prompt: `gate.py land`, which the allow rules do not cover, a `--summary` with a space (now quoted, and the rules deny quotes), `--log-dir` (denied) and a kit folder whose path holds a space (left unquoted, so that command does not run as printed). It is USAGE, not REFUSED, so a caller with the old form runs the line given.
- An id that is not the reviewer of that verdict is REFUSED (exit 4), naming the verdict on record, with no `Instead:` line: name the review the verdict records, or queue the one meant.

`--reviewed-by` without `--submit` is USAGE. The detached landing is started without it, and the foreground landing takes no review name: its own check of the queue is unchanged (Landing, step 4). A library caller of `submit.submit` that passes no `reviewed_by` skips this check.

The `REVIEW` lines only show the review on record (a carried one names the commit reviewed: Carrying a verdict forward); they decide nothing, and a queue that cannot be read gives none. The landing's own checks decide (Landing, step 4). The `SUBMITTED` line is unchanged and always last.

The wait command names the batch's last branch and tip, because the landing writes the batch's records in batch order and that record last; `<kit>` is the kit's live folder (`pluginsource.live_root`); `-C` names the main checkout of the submitter's `-C` (`repo.main_checkout_toplevel`, that `-C` itself when git cannot place it), a checkout no branch cleanup removes; each path is in double quotes when it holds a space (`submit.wait_line`). The record is in the repository's result folder (Result record), so the command reads the same record from any working directory. The coordinator runs it, as printed, in the background and wakes on its exit (Waking a waiting session).

**Waiting in the same call.** `land.py ... --wait-result --submit` (`--wait-result` before `--submit`, so the allow rule takes it as it is: docs/allow-rules.md) submits as above, prints the `REVIEW` and `SUBMITTED` lines and flushes them, then follows the landing to its end (`submit.follow`). One background call then covers the submission and the wait, and wakes its caller when it exits; without it the caller makes the submit call and then a second, background call to `wait-result`. `--wait-result` without `--submit` is USAGE (2), and `gate.py land` has no such flag. A submission that does not give OK prints its lines and exits as it would without the flag, and waits for nothing. Once submitted it prints, in order:

- `WARNING: the landing process (pid <n>) had not exited 60 s after its result record; ...`, only when its process still runs 60 s (`submit.EXIT_WAIT_S`) after the batch's last record went final. After that record, the landing appends the land ledger, posts the Landing feed and prints its outcome lines. The wait never goes longer than that bound: what follows is what the output held at that point.
- The landing's own outcome lines from its output file, at most 60 (`submit.BLOCK_MAX`; a longer tail starts with a `... <n> earlier line(s)` line) (`submit.outcome_block`): every line after its last `result record:` line, such as the gate verdict and `logs:`, the `cleanup` lines, `LANDED ...` or `NOT LANDED: ...`, `closed <ID> ...`, the `WARNING`s and a `STUCK` landing's steps.
- For each branch in batch order, the two lines `wait-result` prints for it, byte for byte (`result.result_lines`). An earlier branch with no final record yet is a `WARNING` naming its `wait-result` command.

The exit code is the code in the batch's last record (0 pass, 1 fail or `error`, 3 stuck, 4 refused, 5 busy, a machine-lock code for `not-run`), not wait-result's 0 or 1.

The wait has no timeout of its own. The landing bounds it: its turn waits at most `"landing".wait_s`, then the landing runs. A record whose process died is finished `error`, as for `wait-result`.

The landing is detached, so stopping the wait stops only the wait:
- A host that kills the call (a foreground call past the host's 10-minute cap, or a closed session) leaves the landing running. The `SUBMITTED` line already printed holds the `wait-result` command to wait with again.
- Ctrl+C prints `Ctrl+C: the wait stopped; the landing goes on: <that command>` and exits 130.

Run it in the background, never in the foreground: it lasts as long as the landing.

The detached process is started as `machine_lock.py run --detach` starts its wrapper (docs/lock-api.md): `submit.command` builds `pythonw.exe` running the carrier `tools/no_window.py`, which starts the `python.exe` beside it running the submitting tool (`tools/land.py` or `tools/gate.py`) with `CREATE_NO_WINDOW` and waits for it; `submit.detach` refuses, starting nothing, when any of the three is not a file, else starts that command with `Win32_Process.Create` through PowerShell's CIM cmdlets (`kitlib/lock/detach.py`). WMI's process is outside the submitter's process tree and job, so it outlives the submitter, and `pythonw.exe` has no console, so the landing gets a console with no window. The pid `submit.detach` gives is the carrier's; the landing is the `python.exe` the carrier started (`detach.wrapper_pid`). The claim watches the landing and, when its wait ends first, writes the landing's pid into the records (the pid the landing then claims them with, `restore`); only when no landing was found does it record the carrier's. A carrier that cannot start the landing exits 127 and notes it in the kit's console incident log, and the claim then finds the carrier gone. Its environment is the submitter's, less `MACHINE_LOCK_RUN` (the landing books its own turn, never one nested in the submitter's run), with `MACHINE_LOCK_ORIGIN` set to the submitter's ancestry (the slot is booked `detached=True`, so the machine lock gives it the submitter's role), `PYTHONIOENCODING=utf-8` and `PYTHONUNBUFFERED=1` (`submit.child_env`). A tool run from a pinned export keeps `KIT_PINNED`, and `pin.lease_child` leases the export to the carrier and to the landing, one lease each (Pinned tools). It waits for its turn up to `--wait`, else `"landing".wait_s`.

Files, in the result folder (Result record), named by the batch's first branch and the submission's `run_id`, so no submission overwrites another's (`submit.files`): `<stem>.<run_id>.land.submit`, the payload (each branch's run id and start time, the output file, the land records the submission replaced), and `<stem>.<run_id>.land.log`, the detached landing's output, which is each record's `log` until a merged gate names its own. Every outcome of the detached landing finishes the records with the same `run_id`: OK, FAILED, CONFLICT, REFUSED, STUCK, BUSY and NOT RUN alike, and `error` for an exception. No record is left `running` when the landing cannot go on:

- A start that fails prints `REFUSED: the landing could not be started: <why>; nothing was changed` (exit 4) and finishes the records `refused`.
- The detached landing writes its own `pid` into the records as it reads its payload (`submit.restore`). One that dies before that, within the claim wait, is finished `error` by the submitter, which prints `REFUSED: the landing process died before it started: pid <n> ended without recording itself; nothing was changed; its output: <log>` (exit 4). One still starting when the wait ends gets its `pid` written by the submitter.
- One that cannot read its payload finishes the records of the `run_id` its payload is named by `refused`, `REFUSED: cannot read the submission ...; nothing was changed`, and notes it in the log (`submit.abandon`).
- One that dies later (killed outright, a crash) leaves `running` records naming a dead process: the first `wait-result` on them finishes them `error` (Waking a waiting session).

Left open: two submissions of one branch started at the same instant can both pass `submit.blocked` before either writes its records; both landings then run in turn in the landing queue, and each branch's record is the last one written.

A later submission prunes payload and log files older than 14 days (`submit.KEEP_S`), keeping every run a land record still has running, whatever its age; a file it cannot delete stays (`submit.prune`). A pruned run's final record can name a log that is gone.

A submission taken (exit 0) is also noted in the session's coordinator event log when one is on, after its lines are printed; that changes nothing the submission says or exits with (docs/coord-state.md "Who appends").

### Batch

`land.py A B --expect-tip TA --expect-tip TB` lands A and B as one landing: each passes the locked checks, they merge in the order given (`Merge A: <summary>`, then `Merge B: <summary>` on top), the merged tree is gated once against the base (log slug `A+B`), and the last merge is pushed. A conflict on any branch aborts it and drops the earlier merges; a red gate drops them all. Main never held them: they were only in the landing tree. A branch whose tip is already inside another tip of the batch is refused: land the containing branch alone. Each branch gets its own result record (`facts['result_record']` is then a list). The verdict line names the branches joined by `, `. At most `"landing".batch_max` branches (default 3). A batch holding a branch that changes a strict path is REFUSED (Strict paths). Each branch needs its own verdict queued at its tip; the first, in the order given, without one is REFUSED by name (Landing, step 4). Submitted, the batch names one `--reviewed-by` per branch in the same order (Submitting a landing).

### Landing feed

Once a landing has landed (exit 0 with a merge), its lock released and its records closed, `Lander.post_landing` posts one event per branch to this machine's Action Hub as the agent (POST `/api/v1/landings`, docs/action-hub.md "landings/L-NNN"): the branch's land record picked as its ledger line is (`result.LEDGER_FIELDS`), with the repo, the main branch, the new main (a batch's branches share it), the record ids `close_pulled` closed for the branch, the merged gate's mode (its gate-OK record on the new main) and the tip's `Deploy:` trailer values as a deploy note (`kitlib.hubsite.landings`). The post is best-effort with a 3 s timeout: a hub that is down, has no agent token here, does not answer, or is older than the route (a 404), and any other exception, Ctrl+C included, is said as `WARNING: the landing of <branch> was not posted to the hub feed (<why>); the landing stands` and the event is dropped (no pending file, no retry). The WARNING is progress, not an outcome line: the outcome, its lines, its exit code and verdict line stand. A landing that did not land posts nothing.

### Strict paths

The strict paths are the list in strict_defaults.py, which is owner-authored: the globs `STRICT_DEFAULTS` holds in kitlib/gate/strict_defaults.py (`land.STRICT_FILE`). A landing reads that file from the base, the `<remote>/<main>` it merges onto, with `git show <base>:kitlib/gate/strict_defaults.py`, and parses it with `ast` (`land.parse_strict`): it is never imported and never read from the branch, so a branch that edits the list is checked against main's. A base with no such file, a repository that is not the kit, has the running kit's list (`strict_defaults.STRICT_DEFAULTS`). `.kit.json` adds no strict path. The list covers the guard, lock, gate, process, lockmcp, hubmcp, mcpwire, commit and records code under `kitlib/`, `tools/land.py`, `tools/gate.py`, `boot/**`, each host's adapter and its shell hooks and agents (`hosts/*/adapter/**`, `hosts/*/shell/hooks/**`, `hosts/*/shell/agents/**`), and `content/roles/**` and `content/skills/**`; read the file for the exact globs. Each branch's changed paths, from its merge base with the base to its tip, are matched against the globs as step globs are (`steps._match`: lowercased, `fnmatch`). A branch with a match lands only when all of these hold (`Lander.strict_check`, a locked check of Landing step 4):

- it lands alone. A batch holding it is REFUSED: `<branch> changes strict path <paths>: a branch that changes a strict path lands alone, never in a batch`. It names at most `land.STRICT_SHOWN` paths and counts the rest.
- a verdict is queued for it (kitlib/gate/verdicts.py; `tools/verdict.py add`), read whole: an entry that is not well formed, a missing `reviewer_model` or `author` included, is `its verdict entry cannot be used: <why>`; none is `it lands only with a queued verdict (tools/verdict.py add), and none is queued for it`; one a landing marked failed is `its verdict entry is marked failed (<why>): queue it again with tools/verdict.py add`.
- the verdict is queued at the tip being landed, else `the verdict was given at <sha>, and the branch is at <sha>: review and queue the tip, or carry the verdict (tools/verdict.py carry) when a main sync is all that changed`. An entry carried to the tip (`carried`, Carrying a verdict forward) counts only when `kitlib.gate.carry.check` passes again here, from the commit reviewed to the tip against the base this landing merges onto, never on the facts the entry stores; else `the verdict was given at <sha> and carried to <sha>, but the carry does not hold against <main> <sha>: <why>; review and queue the tip`.
- its `reviewer_model` names a strong-tier model: one hosts.json gives a host's `strong` or `deep` tier and no host's `light` or `standard` tier (`land.strong_models`). On Claude that is `opus`. `land.strong_alias` accepts the model itself (`opus`, case aside) or a full model id that holds it as a word of its own and names no other model of hosts.json's tiers (`claude-opus-5-5` names `opus`). An id that names no tier model (`gpt-5`), a weaker one (`claude-sonnet-4-6`, `haiku`) or two is refused: `the reviewer ran on <model>, not a strong-tier model (...): a branch that changes a strict path lands only on a strong-tier review, whoever built it (its author is <author>)`. Codex's `account-default` is in every tier, so a Codex review never counts. The builder's agent type changes nothing here: a haiku review of a worker or weak-worker build is refused like any other. Off the strict paths there is no tier rule, so a plain branch built by worker lands on a haiku review.
- its reviewer is not the author (`land.is_author`): no id the `reviewer_id` lists (split on `/`, `,`, `;` or white space) and no agent type the reviewer names (`verdicts.reviewer_types`: `pm-kit:strong-worker` is `strong-worker`) is a whole word anywhere in `author`, case-folded, where a letter, digit, `_` or `-` beside it joins it to a longer word and anything else, `:` included, is a break (`Kit Test / strong-worker`, `Kit Test (agent) (pm-kit:strong-worker)` and `Kit Test | strong-worker` all name `strong-worker`; none names `worker`). Otherwise `the reviewer <id> (<type>) is its author (<author>): ...`. A reviewer that names no agent type (`pm-kit:`) is not a well-formed entry (`verdicts.check`), so `verdict.py add` refuses it and a landing finds it cannot be used.

The coordinator queues the verdict, for every landing and not only a strict one (Landing, step 4), with `tools/verdict.py add` (its arguments are all required, except `--record`):

`python <kit>/tools/verdict.py add -C <repo> --branch <branch> --tip <full sha> --verdict LAND --risk High --reviewer pm-kit:analyst --reviewer-model opus --reviewer-id <reviewer agent id> --author "<commit author> / <author agent type>" --range <base>..<tip> --session <coordinator session>`

- `--verdict` is `LAND` or `LAND WITH FOLLOW-UP`, `--risk` is `Low`, `Medium` or `High` (`verdicts.VERDICTS`, `verdicts.RISKS`).
- A Medium or High-risk verdict the queueing coordinator reviewed itself (an id `--reviewer-id` lists is `--session`, case aside, or a `--reviewer` type holds the word `coordinator`) is refused, nothing written, exit 2 (`verdicts.self_review_why`): `REFUSED: a <Medium or High>-risk verdict needs a reviewer other than the coordinator queueing it, and <which> ...`, then `Instead: dispatch a fresh analyst to review the branch (skill branch-review, step 3), then queue its verdict with --reviewer pm-kit:analyst --reviewer-id <its agent id>`. A Low self-read is queued, unless `.kit.json` sets `"landing".self_review_max_lines` (unset: no size check): then a Low self-read is refused the same way (`verdicts.self_review_size_why`) when it changes more lines than that, counted as the larger of `--range` and `<main as fetched>...<tip>` (added plus removed, `git diff --numstat --find-renames`, from the merge base; `verdicts.diff_lines`), or when its size cannot be told (main as fetched unread, or git gives no answer). A `.kit.json` that cannot be read is `NOT DONE` (exit 1).
- `--reviewer-model` takes the tier model hosts.json names (`opus`), or a full model id naming it as above. `add` checks it against the reviewer's transcript (the host ADAPTER's optional `agent_models()`, docs/new-host.md; on Claude, `<config folder>/projects/*/*/subagents/agent-<id>.jsonl` under CLAUDE_CONFIG_DIR and every `~/.claude*`, the union of every match, read a line at a time and no further than a second model). When a transcript names a model that `--reviewer-model` does not (an analyst dispatched with no model override runs on its role's default tier), `add` refuses and queues nothing: `REFUSED: --reviewer-model opus, but the reviewer <id> ran on claude-haiku-5-5 (its transcript): ...`, `Instead: queue it with --reviewer-model haiku, the model it ran on; a branch land.py --check-strict calls STRICT needs a review on opus: dispatch a fresh analyst with model opus (skill branch-review)`. A review whose transcripts show more than one model (a reviewer that switched models, or two reviewers on different ones) can be named by no `--reviewer-model`: its Instead: line asks for a fresh analyst on the model typed. An agent id (`a` and 16 hex digits) with no transcript found queues with `NOTE: --reviewer-model <model> is not checked: no transcript found for the reviewer id <id>`. A self-review, a reviewer id that is not an agent id (a session name) and a host with no reader (Codex) are not looked up. `land.py` does not check it again.
- `--author` names the commit author and the author's agent type, separated by `/`, `,` or `;`, bare or as `pm-kit:<type>` (`Kit Test / strong-worker`). `is_author` finds the reviewer's type or id as a word anywhere in `author`, whatever the separator.

A landing reads its branch's entry and never removes it. `tools/verdict.py list` drops each entry that waits to land no more (`verdicts.expire`) before it lists the rest, one line each: `EXPIRED <branch> <tip>: landed: ...` when the tip is an ancestor of `<remote>/<main>` as last fetched, `EXPIRED <branch> <tip>: superseded: there is no branch <branch>` when it is not and the branch is gone. An entry is kept whenever that cannot be told: main as fetched cannot be read (`KEPT ALL: ...`, nothing dropped) or git gives no answer for it. A branch that moved off its queued tip keeps its entry, for `verdict.py carry` (Carrying a verdict forward). `verdict.py drop [--tip SHA]` removes a branch's entry by hand.

Each refusal starts `<branch> changes strict path <paths>: ` and ends `; nothing was merged`. A list that cannot be read at the base (git fails, or the file does not assign `STRICT_DEFAULTS` once as a literal tuple of non-empty strings) refuses every landing: `cannot read the strict paths from <main> at <sha>: <why>`. So does hosts.json that cannot be read, and paths git cannot list.

Before a reviewer is picked, `python <kit>/tools/land.py -C <main checkout> <branch> --check-strict` (`land.check_strict`) says, read-only, with no lock and no verdict, whether a branch changes a strict path, by the same `Lander.strict_paths` the refusal uses, against `<remote>/<main>` as last fetched: `STRICT <branch>: <paths> (tip <sha>, base <ref> <sha>): its reviewer must run on a strong-tier model, and it lands alone`, or `NOT STRICT <branch>: no strict path changed (...)`.

A strict branch that passes lands automatically, as any other: its merged gate runs `--full --fresh` whatever the caller passed (it only ever tightens; so it reuses nothing, not even from the tip's record on the same tree, Gate reuse), and the landing says `STRICT: <branch> changes strict path <paths>: reviewed by <reviewer> on <model> (<reviewer_id>)[ at <sha>, carried over <n> main merge(s)]; the merged gate runs --full --fresh` before the merge (`Lander.strict_escalate`; the bracket only for a carried verdict).

NOTE: a strict tip accepts a select record (the merged gate runs --full --fresh), except under a base that sets `"landing".shared_paths` or `"landing".gate_once`, where a strict tip needs a `--full` record (Shared paths, Gate once at landing). Step 4's record check is the same for a strict branch; the escalation above is what gates it whole. The procedure asks more than the record check: a strict branch's final branch gate is `gate.py --full` on its tip (a branch gate takes no `--fresh`; `--full` reads and stores no reuse, Gate reuse), and its reviewer is never its author. The code checks the rest: a strict branch lands alone (`Lander.strict_check`), with a verdict from a strong-tier reviewer whoever built it (`Lander.review_refusal`), and every landing refuses a verdict whose reviewer the entry names as its author (`is_author`).

### Carrying a verdict forward

A reviewed branch needs no fresh review because main moved: a merge of main that git made with no conflict adds nothing of the branch's own to review. After a main sync of a branch whose verdict is queued, the coordinator moves the verdict to the branch's head with:

`python <kit>/tools/verdict.py carry -C <repo> --branch <branch>`

It checks the head against main as last fetched (`<remote>/<main_branch>`; `NOT CARRIED: main as fetched (...) cannot be read: <why>; fetch first` when there is none) with `kitlib.gate.carry.check`, read-only. The head carries the verdict given at the commit reviewed when all of these hold (its module docstring has the detail):

- every commit after the review is a merge with exactly two parents, on one first-parent line from the head down to the commit reviewed: no commit of the branch's own after the review;
- each merge's second parent is in main, and its tree is the one `git merge-tree --write-tree` makes of its parents with no conflict: no conflict resolved by hand, no merge edited before its commit;
- the branch's own diff against main is the one reviewed: the same paths, and the same `-U3` patch once the `index` lines and hunk positions are taken out (`carry.CONTEXT`). An edit of main within three lines of a branch hunk changes the patch and refuses: the fail-closed choice. A binary file counts as the same only when both sides hold the very same blobs.

A pass rewrites the entry under the queue lock (`verdicts.carry`): `tip` becomes the head, and `carried` records `{from, merges, main, diff, utc}`: the commit reviewed, the merges carried over (oldest first, the last the head), main as checked, the sha256 of the normalized patch and when. Who reviewed, `queued_utc` and `range` (still ending at the commit reviewed) stay as they were; a second sync carries again from the same commit reviewed, and `verdict.py add` (a fresh review) drops `carried`. It prints:

`CARRIED <branch> <head> from reviewed <sha>: <n> main merge(s), no conflict, the branch's own diff unchanged against <remote>/<main> <sha>; <verdict> by <reviewer>/<model> (<reviewer_id>)`

Anything else writes nothing and exits 1: `NOT CARRIED: <why>; review and queue the head instead` (a branch commit after the review, a conflict, a changed diff, an entry marked failed, one already at the head), `NOT QUEUED: <branch>` when nothing is queued. When the entry or the branch moves while the check runs (outside the lock), nothing is written either: `NOT DONE: ... run carry again`. `verdict.py list` shows `carried_from=<sha>` on a carried entry, and `land.py --submit` its `REVIEW` line (Submitting a landing).

A landing never trusts the stored facts: it runs the check again under its lock, from `carried.from` to the tip, against the base it merges onto (Strict paths), so main moving on after the carry is checked too. A queue entry holding `carried` is checked like every other key (`verdicts.check`): it is set only by `carry`, never given to `add`, and its `from` is not the tip.

### Gate reuse

kitlib/gate/reuse.py: a per-step cache of gate results, read and written by a branch gate (a rerun reuses) and by a landing's merged-tree gate, a batch landing included (`reuse.branch_plan`, `reuse.planner`). A step with `reuse` is not run when a pass of its key is stored within `"landing".reuse_max_age_h` hours and no fail or warn of that key is. It is fail-closed: any doubt or error runs the step, and its `gate: reuse:` line says why.

**The key** (`reuse.step_key`) is the sha256 of the canonical JSON of:

- the step's name, argv and cwd, with the checkout's root written `<root>` and the kit's `<kit>` (so a worktree and the main checkout make one key, and the landing's `merged_args` another);
- the sha256 of its program (`shutil.which` of argv[0]; not found: no reuse) and of every argv element that names a file relative to its cwd;
- `gate_ok.config_hash` of the gate config (`runner.gate_config`);
- the kit's identity, `reuse.kit_identity`: the hash of every file under the kit's `kitlib/` and `tools/` (bytecode left out), the interpreter's path and `sys.version`. Never the kit's commit: two commits with the same files are one kit;
- the change (`reuse.changed_list`): the sorted, distinct paths the gate selects by, a branch gate's changed paths or a landing's base..merge, since a step such as `kit_tests.py --select` picks its tests by the change without naming `{base}`. Keys stored before this part are not met again: the cache starts cold once;
- its inputs (`reuse.inputs`): every file `git ls-files -c -o --exclude-standard` shows in the work tree (tracked, or untracked and not ignored) that matches its `globs` or its `content`.globs (its `exclude` is not subtracted), by sha256; a tracked file deleted in the work tree is `absent`. An input that is a link or a folder (a nested repository or submodule) means no reuse.

**The opt-in's contract.** `reuse` is a promise that the step's result depends on nothing outside its key. A step that asks for it must therefore:

- read only files its `globs` or `content`.globs match. A file git ignores, or one an earlier step or the build generates, is never an input: a step that reads one must not ask for reuse;
- not depend on environment variables, installed SDKs, packages or tools other than its program and the files its argv names, the network or the clock: none of these is in the key;
- not depend on git state (HEAD, refs, the index, commit messages): none of it is in the key, and a pass stored on one commit serves any commit with the same input files;
- not need what it leaves behind: a reused step does not run, so nothing it would leave (a build output, a file a later step reads) exists. Give a step whose output a later step needs the same group as that step.

A reused step's `requires` probe is not run either (`runner._to_run` leaves the step out of the run): it counts as `reused` where a missing requirement would have skipped it.

**The same tree** (`reuse.same_tree`). A branch's `gate.py --full` stores nothing in the cache, so without this a landing whose merge holds the very tree the tip passed `--full` on would run every step again. In a one-branch landing that `reuse.landing_why` lets reuse (so never a strict one, nor a batch), the tip's gate-OK record serves an asking step the cache does not serve when all of these hold:

- the record is a `--full` one of the tip (`gate_ok.verify_full`, `mode` `full`), and its tree is the merge's tree;
- the record has no `ran_on`: a record a load node's gate wrote lets its tip land but serves no step, since those steps ran on another machine;
- the merge's parents are exactly the base and the tip, and the record's `base` is the landing's base;
- its `gate_config` is the landing's, its `kit` (commit, interpreter, clean) is the kit gating the landing, and it ended within `"landing".reuse_max_age_h` hours;
- the step is no check step, has no `merged_args` (its landing argv never ran at the tip), and passed in that record.

Only in this mode, a step whose command names `{base}` or holds the base commit, or that declares no input, is not barred: the tree and the base commit are the ones the tip's run had, so `{base}` and every tracked file are too, and the history differs only by the merge commit, which the opt-in already promises the step does not read. This covers tracked content only: the landing tree lacks the author worktree's ignored and generated files, and no step is checked for them, whether `plan_steps` takes the record on a miss or on a step that declares no input (the key is built from the landing tree), so a step whose result depends on an ignored or generated file must not set `reuse`. The result taken is that of the step's `--full` command (its `full_cmd` where it has one), not of the `cmd` the landing would run. Such a step gets no key and is never stored, so this never reaches the cache. Any error while reading the record means every step runs. The kit never takes this path for its own landings: it gates its branch with the worktree's own gate.py, so the record's kit commit is not the one the landing runs.

**The input tree** (`reuse.input_tree`). When main moved on since the tip's gate, the merge's tree is not the tip's, so the same tree does not serve, and a step whose command names `{base}` is never cached. A branch gate that writes a gate-OK record therefore also writes, in its `input_keys` (`reuse.record_keys`), a key for each step that asks for reuse, passed, is no check step, runs a command, declares inputs and has no `merged_args`. Each key is a set of parts (`reuse.INPUT_PARTS`), each its own sha256, so a miss names the parts that differ:

- `argv`: the step's argv and cwd as its gate ran them (`full_cmd` in a `--full` gate), with the checkout's root written `<root>`, the kit's `<kit>` and the full base commit `<base>`. A step whose `full_cmd` differs from its `cmd` misses on `argv` against a `--full` record;
- `tools`: as in the cache key (its program and every file its argv names);
- `head_inputs` and `base_inputs`: path, mode and blob of every entry `git ls-tree -r` shows at the head (the tip; the landing's merge) and at the base (the record's merge base; the landing's `--expect-main`) that matches the step's `globs` or `content`.globs, `exclude` not subtracted. A link or a gitlink among them, or no input at the head, gives the step no key;
- `changed`: the paths base..head changes (`runner.changed_between`, git on both sides);
- `kit`: `reuse.kit_identity` (the kit's files and interpreter, never its commit). A kit that changes while the gate runs gives no keys.

No keys are written for `--only`, a partial (`--base`) or docs-only gate, a gate with no detected step, or a work tree with uncommitted changes when the gate started; anything that goes wrong says `gate: reuse: no input keys in the record: <why>` and never fails the gate. In a one-branch landing that `reuse.landing_why` lets reuse and that the same tree did not serve, the record the tip check accepted (`Lander.tip_records`: a `--full` record, or a default-mode one `select_refusal` took; never a docs-only record, and none when the tip lands only on a FLAKE rerun) serves an asking step the cache does not when the record is the tip's, its input keys are of `reuse.INPUT_SCHEMA`, its mode is `full` or `select`, the merge's parents are exactly the base and the tip, its `gate_config` is the landing's, it ended within `"landing".reuse_max_age_h` hours, the step passed in it (not warned, nor was reused), and every part the landing computes for the step equals the record's. A batch never reads it.

Only on this path, and only because `base_inputs` and `changed` are equal, a step whose command names `{base}` or the base commit is not barred: what it reads of the base is the same. **A step that reads history beyond the changed list and the base side of its inputs (commit messages, the log, ancestry, its own merge-base) must not set `reuse`**; neither must one whose result depends on the environment or a toolchain, which no part holds. The inputs come from git trees while `tools` reads the work tree: this is sound only because the branch gate writes a record only for a clean tree at HEAD, and a landing reuses only in a clean landing tree. As with the same tree, this covers tracked content only: the landing tree lacks the author worktree's ignored and generated files, and no step is checked for them, so a step whose result depends on an ignored or generated file must not set `reuse`. A step served from the record gets no key and is never stored, so the relaxation never reaches the cache. Any error while reading the record or a tree means every step runs.

**Never cached**: nothing is read or stored, every asking step runs and says `NONE <step>: <why>`:

- for one step: a check step, a step with no `globs` and no `content`.globs, a step whose `cmd`, `full_cmd`, `daily_cmd` or `merged_args` names `{base}` (it reads git history), or whose argv holds the base commit (`reuse.undeclared`; the same tree or the input tree above may still serve these two); globs that match no file git shows (a mistyped glob, or one naming only ignored files, would key the step on its command alone; `reuse.step_key`), an input that is not a plain file, or a program not found (`reuse.NotCacheable`);
- for the whole gate: `--full`, a branch gate's `--only`, `"landing".reuse_max_age_h` 0, a change (the branch gate's changed paths, or a landing's `<base>..merge`) touching `.kit.json`, a config section file, the hook module or a `"landing".reuse_never` path, or a strict path (kitlib/gate/strict_defaults.py `STRICT_DEFAULTS`, imported; `reuse.strict_hits`). A branch gate's `--base X` narrows its changed paths to those since the merge base with X (`runner.changed_since`), so these checks do not see a path changed before X;
- in a landing also (`reuse.landing_why`): `--fresh`, which a branch changing a strict path always has (Strict paths); a result record that cannot be read, in the result folder or the old one, or no result folder (Result record); a `land` record of a tip (an earlier landing that did not land: its tree is gated again); a `gate` record of a tip whose verdict is not `pass`; a landing tree that is not clean;
- anything that raises while planning: `NONE <step>: <Type>: <message>`.

**The lines**, one per asking step, in order, each starting `gate: reuse: `:

- in a one-branch landing whose merge holds the tip's `--full` tree, first: `SAME TREE <tree>: <branch> at <tip> passed gate.py --full on this tree (record ended <UTC>)`, or `SAME TREE <tree>: the --full record of <branch> at <tip> is not used: <why>`;
- in a one-branch landing the same tree did not serve, when the tip's accepted record holds input keys, next: `INPUT TREE: the <mode> record of <branch> at <tip> (base <base>, ended <UTC>) serves a step whose key parts all match`, or `INPUT TREE: the <mode> record of <branch> at <tip> is not used: <why>`;
- `HIT <step>: key <first 12 hex>, stored <UTC time it was stored>`, then `REUSED <step>: passed on the same inputs (key ..., stored ...)`; or, from the same tree, `HIT <step>: the --full record of <tip> (same tree <tree>, ended <UTC>)`, then `REUSED <step>: passed in the --full gate of <tip> on the same tree (ended <UTC>)`; or, from the input tree, `HIT <step>: the input tree of the <mode> record of <tip> (ended <UTC>)`, then `REUSED <step>: passed in the <mode> gate of <tip> on the same inputs, base side and change (ended <UTC>)`;
- `MISS <step>: <why>`: `no result stored for key ...`, `no pass within "landing".reuse_max_age_h (<h>) for key ...`, `failed or warned on these inputs at <time> (key ...)`, an entry that cannot be read, or `<steps> of its group <group> runs` (a group is reused whole or not at all). When an input tree is in use, a MISS or NONE line of a step it did not serve ends `; input tree: <why>`: the parts that differ (`argv differs`, `head_inputs, base_inputs differ`), `the record says <result>`, `the record holds no input key for it`, or a bar;
- `NONE <step>: <why>` as above;
- after the run, for each step that missed: `STORED <step>: pass|fail, key ...` (PASS is stored as pass, FAIL and WARN as fail; a skipped step stores nothing), or `NOT STORED <step>: its inputs changed while the gate ran`, or `NOT STORED <step>: its key changed while the gate ran (the kit, a program or the config)` (the key is made again after the run and must be the same: a step that writes its own inputs, or a kit edited meanwhile, stores nothing), or `NOT STORED <step>: <Type>: <message>`. A failure to store never fails the gate.

The lines go to `reuse.log` in the log folder. A reused step's result is `reused` (in the verdict `reused: <steps>`, and in the gate-OK record's `steps`). When every selected step is reused, `setup` does not run and nothing is booked: a branch gate books no slot, and a landing's gate books nothing beyond the landing's own turn (Landing, step 3). A step that asks for no reuse says nothing, and no `reuse.log` is written.

**Storage.** `<git common dir>/kit-gate-cache/<key>/<YYYYmmddTHHMMSSZ>-<pid>-<hex8>.<pass|fail>.json` (`reuse.cache_dir`, `reuse.ENTRY_RE`), shared by every checkout of the repository, written to a temp file and renamed into place. An entry whose body does not match its name (schema, key, result, time) is a miss. A pass stored more than 60 s in the future (`reuse.SKEW_S`) is not counted; a fail is. After each gate that could store (one with an asking step that was keyed), entries older than 168 hours (`reuse.PRUNE_H`) are pruned (`reuse.prune`): only names matching `ENTRY_RE`, as plain files, in folders named by a key that are plain folders inside the cache; a link or junction is never followed, and other files are left. A temp file (`reuse.TMP_RE`) last written more than 168 hours ago, left by a crash between the write and the rename, is pruned the same way; a newer one stays, since another gate may be writing it. Key folders left empty are removed. A prune that fails says one `gate: reuse: prune: ...` line and the gate goes on.

In the kit's own repository `.kit.json` "gate" (owner-only) gives its one step `kit-suite` `"globs": ["*"]` and `"reuse": true`, so it asks for reuse; a change to a strict path or to the gate's config still reuses nothing (above).

### Branch cleanup

kitlib/gate/cleanup.py runs in the landing (`Lander.clean_up`) once the push is verified, the lock released and the backlog records closed: never on a landing that did not land. For each branch, three parts, each judged on its own:

- **Remote branch.** Deleted when main contains its tip: `git push --force-with-lease=refs/heads/<branch>:<tip> <remote> :refs/heads/<branch>`. The lease is a compare-and-swap, not a force: the remote deletes the branch only while it still points at the tip read just before, so a branch pushed to since is refused and kept. `git ls-remote` must then show it gone.
- **Worktree.** Removed by kitlib/worktree/remove.py, the code `worktree_remove.py` runs (docs/worktree-remove.md): under the worktrees folder, landed in `<remote>/<main>`, nothing holding it, nothing uncommitted, untracked or ignored outside build output, no link inside; then `git worktree remove`, never forced. That code then deletes the local branch with `git branch -d`.
- **Local branch** with no worktree: `git branch -d`, never `-D`.

Nothing is forced. A tip main does not contain, a worktree with work in it, a worktree in use, and anything git refuses are kept. Each kept part is named on a `  kept` line under the branch's `cleanup   <branch>: ...` line, and the landing still counts as landed. A branch never pushed has its remote branch `absent`. The result record's `cleanup`, and the landing's `facts['cleanup'][branch]`, hold `remote_branch` (`deleted`, `absent`, `kept`, `skipped`), `worktree` (`removed`, `absent`, `kept`, `skipped`), `worktree_path`, `local_branch` (`deleted`, `absent`, `kept`, `skipped`) and `kept` (one reason per kept part). A local branch git gives no answer for after its delete is `kept`, with "whether it is gone could not be read", never `deleted` (kitlib/gate/cleanup.py `_left`). `--keep-branch` skips all three (`skipped`). An exception in one branch's cleanup is a WARNING and the next branch is cleaned; Ctrl+C stops it with a WARNING. Both name the sweep command, and so does a landing stopped after its verified push (`Lander.landed_anyway`).

`land.py --sweep-landed [--apply]` applies the same rule to every branch, local or on the remote, that main already contains: it fetches `<main>`, and takes a tip in `<remote>/<main>` and off its first-parent line (a branch made from main with no commit of its own is never one). Branches main does not contain are not named. It does nothing while a landing holds the landing lock (BUSY). A dry run, the default, names what would go and ends with the `--apply` command. The landing cleanup and the sweep delete a remote branch only by the lease push above and a local branch only with `git branch -d`; guard.py gains no allowance for an agent's `git branch -D` or `git push --delete`.

## The caller's checkout

Skills and roles run the gate as `python <kit>/tools/gate.py -C <worktree>`, an absolute `-C` that names the tree, so the rule below does not stop them; the final gate before review and landing adds `--full`, because a landing takes only a tip with a gate-OK record from a `--full` pass (Landing, step 4). In the kit's own repository that command runs the plugin export's gate code (pinned through the main checkout its marker names, "Pinned tools") on the worktree's tree; `python <worktree>/tools/gate.py -C <worktree>` (AGENTS.md) runs the worktree's own.

In the kit's own repository every checkout has a real `tools/gate.py`, so `python <worktree>/tools/gate.py` run from the main checkout with no `-C`, or with a relative one such as `-C .`, would gate the main checkout with the worktree's code. For a branch gate run with no `-C` or a relative one, `tools/gate.py` applies kitlib/gate/caller.py `own_copy_refusal` to the tree it would gate (the directory it was run from, or where the relative `-C` resolves) and its own checkout: `pluginsource.live_root(KIT)` (`KIT` in tools/gate.py, the same directory as kitlib/gate/steps.py `KIT_ROOT`), so a gate.py running from an export with `KIT_LIVE_ROOT` set (a pinned run, or the plugin's export whose marker names the main checkout, "Pinned tools") counts as the main checkout's own, and `<kit>/tools/gate.py` from a kit linked worktree with no `-C` or a relative one is refused like main's own gate.py would be:

- The two are different checkouts of one repository (the same git common dir, different git dirs): `REFUSED: <gate.py> is in the checkout ...`, exit 4, nothing run. Each following line gives the documented command, `python <tree>/tools/gate.py -C <tree>`, for one tree, with a path that holds a space in double quotes. A relative `-C` names the tree meant, so only its line is given, headed `  to gate <tree>:`. With no `-C` the tree meant is ambiguous (the gate.py's path names one checkout, the directory another), so both are given, headed by intent: `  if you meant the directory you ran from:` (the checkout the directory is in) and `  if you meant the checkout this gate.py is in:`.
- An absolute `-C` names the tree on purpose and is not checked: main's gate.py with an absolute `-C <worktree>` runs main's code on the worktree.
- They are the same checkout, the gate.py is in another repository, or either is in no repository (an export with no `KIT_LIVE_ROOT`, as when its marker names no main checkout): it runs.
- git cannot place the gate.py's checkout (dubious ownership, a git timeout): REFUSED only when its path nests (one inside the other) with the gated checkout or with the folder that checkout's git common dir is in, so the two could be one repository's checkouts; the command lines follow as above. A sibling that only shares a name prefix (`main-co-x` beside `main-co`) does not nest. Otherwise it runs, as a repository's gate did before this check. A directory git cannot place is left to the gate itself.

A relative `--log-dir` resolves against the directory the gate was run from, not the gated tree, so when that directory is in another checkout the logs would be stray files there: kitlib/gate/caller.py `log_dir_refusal` makes it `USAGE: --log-dir <D> is relative ...`, exit 2, nothing run. An absolute `--log-dir`, none, or a directory in no repository passes.

The one documented way to gate a worktree from another directory is that worktree's own gate.py with an absolute `-C` naming it:

```
python <worktree>/tools/gate.py -C <worktree> --full
```

A targeted run of a few test modules, with the output in a log (no gate-OK record; it never replaces the `--full` gate): `python -m unittest discover -s <worktree>/tests/<pkg> -t <worktree> -p test_<module>.py > <log> 2>&1`, one command per module, absolute paths, then read the log. For every package a change can reach, `python <worktree>/tools/kit_tests.py -C <worktree> --select [--changed PATH ...]` (docs/test-tools.md "kit_tests"; `--changed` picks packages, not single modules). No `cmd /c` loop.

Running the worktree's own gate.py matters in the kit's repository: the gate records the identity of the kit that ran it (the gate-OK record's `kit.commit`, `runner.kit_identity`), and the code under test is the code that gates.

Landings, `wait-result` and `--measure` apply neither check.

## The stash guard

kitlib/gate/stash.py. A repository has one stash stack: `refs/stash` and its log are in the git common dir, so the main checkout and every linked worktree push to and pop from the same one. A tree that was stashed is not the tree its commit names, and an entry made in one checkout can be applied in another. So no branch gate and no landing runs while the stack holds an entry, whichever checkout made it:

- **Branch gate** (`kitlib.gate.runner._gate_checkout`, which `_branch_gate` calls): `REFUSED: the stash stack is not empty (refs/stash is at <sha>): ...`, exit 4, with `--plan`, `--only` and `--full` too. Nothing is booked, no step runs, no log folder is made and no gate-OK record is written.
- **An entry made while the branch gate ran**: the verdict and the exit code stand, and no gate-OK record is written: `no gate-OK record: the stash stack is not empty (...): an entry was made while the gate ran, ...`. The stack is read again only when no other condition of Gate-OK record already withholds the record.
- **Landing** (`Lander.locked_checks`, Landing step 4): `REFUSED: the stash stack is not empty ...; nothing was merged`, after the clean-tree check. The stack is the repository's, so an entry made in a linked worktree refuses a landing in the main checkout. A `--submit` landing is refused the same way, in its detached run: `SUBMITTED` still exits 0, and the refusal is in the landing's result record (`gate.py wait-result --kind land`).
- **An entry made while the merged gate ran** (`Lander.unchanged`, Landing step 7): `NOT LANDED: the merged gate passed, and the stash stack is not empty ...`; the merge is dropped and nothing is pushed.
- **git cannot tell** (`kitlib.git.refs.ref_commit` has no answer for `refs/stash`): the same four refusals, worded `git cannot tell whether the stash stack is empty: <why>`. No answer is never read as an empty stack.

The guard only reads the ref (`stash.tip`): it never runs `git stash` and never changes the stack. To clear a refusal, run `git stash list`; whoever made each entry commits it on a branch or drops it. No key turns the guard off.

A red run (a new test shown failing without the fix) uses `tools/redfirst.py -C <worktree> --tests <file>` (docs/redfirst.md), never a stash or a scratch copy of kitlib. The test file must be committed first. A test that only calls a symbol the fix adds is RED because the symbol is missing (an AttributeError or ImportError), which does not show the behaviour wrong: say so in the report.

Limits:

- An entry made and dropped again wholly within a run leaves nothing to read.
- A `refs/stash` set by hand with no log refuses, although `git stash list` prints nothing for it.
- The daily full run (kitlib/dailyfull, which calls `runner.gated` itself), `wait-result`, `--measure`, `land.py --queue`, `land.py --check-strict` and `land.py --sweep-landed` do not ask.
- guard.py refuses a stash before it runs in a main checkout (`git-stash`, every session) and, for an agent session, in a linked worktree when it adds an untagged entry or takes one it does not name (`git-stash-shared`; docs/guard.md "Rules"). A tagged `git stash push -m <tag>` from an agent, and any stash from the owner's own session or a `plain` one in a linked worktree, still pass, so for those this guard is what answers, after the fact.

## Known limits

- No per-step timeout. A step that hangs is ended by stopping the gate (Ctrl+C, or the machine lock's stop, which ends the slot's job).
- The hook module's module-level code runs when it is loaded, before the gate is booked. It runs outside the slot, and a `sys.exit` there is REFUSED.
- Files git ignores, and files marked assume-unchanged or skip-worktree, are outside the record. The clean-tree checks do not see them.
- The targeted rerun (Targeted rerun) runs each failing class with `python -m unittest -v <class>` in its step's directory, with only the `KIT_FAKE_GIT` mode recorded from its kit_tests tier header set. A failure that needs anything else the step's own command sets up may not happen in the class run alone; that class then passes, and the rerun says FLAKE (`rerun.judge_class`, `rerun.verify_flake`). A red run the parser does not account for is uncovered (Targeted rerun), and the rerun and land refuse it.
- A `--reviewed-by` id holding `-c` in any case (a hyphenated id such as a UUID with a `-c...` group) puts `-C` after the allow rule's prefix, which PowerShell's case-blind `-C R *-C*` deny refuses, as it does a branch named like `kit/x-check` (docs/allow-rules.md): that submission gets the normal permission prompt.
- A kit from before the result folder left the git common dir reads and writes only the old folder (Result record): its `wait-result` and its submission's check for a running landing do not see a record this kit writes.

## Not ported

General behaviour the kit gate leaves out, which a repo keeps in its steps or hook module:

- **Repo checks are `cmd` steps**, with no gate key: the doc budget over `{here}/doc_budget.py -C <root>` (docs/doc-tools.md), forbidden paths over `{here}/forbidden.py` and the trailer check over `{here}/trailers.py` (docs/repo-checks.md), machine paths over `tools/machine_paths.py -C <root>` (0 OK, 1 FAILED, 2 NOT CHECKED; docs/commit.md). A repo's Python tests are steps with a `pass` floor (docs/test-tools.md). A config that sets `python_tests`, `python_tests_floor`, `trailers` or `kill_retry` fails to load (unknown key). Repo-specific checks go in the hook module's `GATE_CHECKS`; a zero-test regex is the gate's `zero_tests`.
- **No process shield.** A stop, Ctrl+C or error ends a step's whole process tree through the slot's job, except a build daemon another job's client uses or may use ("Build daemons"). `--pid-hold` in `setup` or a step's `cmd`, `full_cmd`, `daily_cmd` or `merged_args` is refused: the pid hold is opt-in for agent test runs (docs/test-tools.md "The pid shield").
- **No merge train.** A batch landing (Landing, Batch) is merged and gated whole, never as partial landings, and every landing gates the whole merged tree.
- **No landing-time repo policy.** A review-pack precondition or records-only rule is a check step. The gate prints no machine state on failure (the lock's status shows it).
- **Worktree removal after landing** is the branch cleanup (Branch cleanup). The per-step cache key is the reuse evidence, with no log hashes or forecasts; `--fresh`, `--full` and `--only` force a run, and `merged_args` makes another key (Gate reuse).

## Go-live notes

- A repo's Python tests must be steps (no gate key runs them).
- Turn on `push_block` only after the repo lands through `land.py` (`gate.py land` is its one-branch form).
- In a landing, only the hook module's own file comes from the base (Landing, step 4); a hook module that imports sibling files from its tools folder is not supported there (kitlib/gate/hookrev.py). Its `__file__` is its path in the merged checkout, so a hook that reaches files beside itself through `__file__` reads the merged tree's copies, not the base's; its tracebacks and GATE_CHECKS errors name `<rev10>:<path>`.
- A `landing.log_dir` inside the repo must be gitignored. Otherwise the gate's logs are untracked files: a branch gate writes no record, and a landing, which writes them in the main checkout, not in its landing tree, leaves that checkout not clean, so the next landing is REFUSED (Landing, steps 4 and 7).
- Without `landing.log_dir`, gate logs go to `<kit temp>/<repo>-gate/<branch>/` (kitlib.gate.runner.log_base over kitlib.config.user.work_temp; docs/test-tools.md "Temp folders"), never an inherited TEMP, so agents and the owner's shells read the same folder. When that base cannot be made, or the machine config cannot be read, the run's logs go under `runner.fallback_log_base` (`<shared temp>/<repo>-gate`: kitlib.config.user.shared_temp, the machine config's `temp_dir`, else `%LOCALAPPDATA%/Temp`) with a `gate logs:` note on stderr (`runner.make_log_dir`, which redfirst and daily-full use too); landed.py reads it as well. A Windows process without LOCALAPPDATA and with no usable drive root stops with a RuntimeError instead of falling back to TEMP.
- The gate prints its verdict to stdout only, so landed.py finds one only where a caller saved that output under the gate log folder (docs/landed.md).
- A lander's post-merge stray check: `python <kit>/tools/checkout_guard.py --main-stray --allow-tracked <main checkout>` (exit 1 on any stray, or when git could not tell; docs/preflight.md).
- Doc budget check: `[sys.executable, <kit>/tools/doc_budget.py, -C, <repo>]`, judged with kitlib.verdict (`DOC BUDGET OK` / `DOC BUDGET FAILED`). Exit 2 means refused or a usage error; see docs/doc-tools.md.
- There is no keep-red option. A red merge never reaches main: it is only in the landing tree, and it is dropped.
