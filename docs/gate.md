# gate.py

The universal gate: `tools/gate.py` (entry) over `kitlib/gate` (library). ARCHITECTURE.md "Contracts" (Booking, Kinds, Gate-OK record, Landing) is the design; this page is the behaviour. Keys: docs/kit-json.md "gate" and "landing".

## Commands

| Command | Does |
|---|---|
| `gate.py [-C DIR] [--base REV] [--full \| --only STEP ...] [--plan] [--slug S] [--log-dir D]` | Gates the checkout under `book(<gate.kind>)` (default `engine-test`), booked as a gate run: the build daemons it leaves that serve nothing outside its job are stopped at its end (Build daemons). The base is the default base (Default base); the merge base with HEAD is what is compared. |
| `land.py BRANCH [BRANCH ...] --expect-main SHA --expect-tip SHA [--expect-tip SHA ...] [-C DIR] [--lane L] [--summary T] [--full] [--fresh] [--wait S] [--log-dir D] [--keep-branch]` | The landing tool (tools/land.py): lands BRANCH, or a batch, from the main checkout (see Landing). One `--expect-tip` per branch, in the same order. `--wait` defaults to `"landing".wait_s`. Landed, each branch is cleaned up unless `--keep-branch` (see Branch cleanup). |
| `land.py --sweep-landed [--apply] [-C DIR]` | The branch cleanup for every branch main already contains (`kitlib.gate.cleanup.sweep`; see Branch cleanup). Without `--apply` a dry run: it changes nothing and names what would go. |
| `land.py --queue [-C DIR]` | Read-only: the landing lock's holder, then the landing queue in turn order (`kitlib.gate.land.queue`). |
| `gate.py land BRANCH --expect-main SHA --expect-tip SHA [-C DIR] [--lane L] [--summary T] [--full] [--fresh] [--wait S] [--log-dir D] [--keep-branch]` | The same landing for one branch, with `--wait` defaulting to 0 (see Landing). |
| `gate.py wait-result BRANCH --tip SHA [--kind gate\|land] [--timeout S] [-C DIR]` | Read-only. Waits until BRANCH's final result record names a tip starting with SHA (7 to 40 hex digits), prints it and exits 0 when its verdict is `pass`, 1 for any other verdict, 7 when no such record appears within S seconds (default: no limit). See Result record. |
| `gate.py --measure --out PATH [--days N]` | Writes a proposed kinds table from the lock's run history (kitlib/gate/measure.py). It never writes the live kitlib/lock/kinds.json. Every kind's cpu in the proposal is a whole number 1..the layout's agent_cap: the p90 peak busy cpu slots rounded up, or agent_cap when the runs fill what they booked (pinned runs cannot show more). The lock measures a run's job object only, so a finished run counts as a cpu sample only when its history line shows work in the job (kitlib/gate/measure.py `skip_reason`): not `partial`, held `MIN_HELD_S` (10 s) or more, with `cpu_s` and a peak above 0, and `cpu_s` at least `MIN_BUSY_THREADS` (0.1) x `held_s`. A kind with too few runs or too few cpu samples is kept whole, warn_min included, written as the size it books on this layout now. It prints one line per kind; the line counts the skipped runs by reason. Not caught: a wrapper that itself keeps a tenth of a thread busy while its work runs outside the job. |

## Default base

`kitlib.git.refs.default_base` is the one rule every kit tool uses when no `--base` is given: `refs/remotes/<remote>/<main>` (as last fetched) when it resolves, else the local `<main>`. A local main lags whenever nobody pulls into the main checkout, and measuring against it counts the remote's newer commits as the branch's work. When the local main is at another commit the tool prints `base: local main <hash> is N behind <remote>/<main> <hash>; measuring against <ref>` (or ahead, or both). An explicit `--base` is always used as given. Users: gate.py, doc_budget.py, review_pack.py, ruling_cites.py, forbidden.py, kit_tests.py and pytests.py `--select`; preflight.py and board.py measure their rows against `<remote>/<base>` when the two differ.

Every kit `git fetch` and `git ls-remote` runs with `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=never` and `GIT_HTTP_LOW_SPEED_LIMIT=1000`/`GIT_HTTP_LOW_SPEED_TIME=60` (`kitlib.git.cmd.NETWORK_ENV`): a remote that wants credentials, or a transfer stalled below 1000 bytes/s for 60 s, fails instead of hanging. An ssh passphrase prompt is not covered (forcing `ssh -o BatchMode=yes` would override the user's `core.sshCommand`, `GIT_SSH` and ssh config; see the `kitlib.git.cmd` docstring). A push keeps the user's credential prompts.

## Exit codes

From kitlib/gate/__init__.py. The machine lock's refusal codes pass through unchanged (kitlib/lock/store.py: 6 busy, 8 timeout, 10 require-lock, 11 reserved, 12 hold). Ctrl+C is 130.

| Code | Name | First line printed |
|---|---|---|
| 0 | OK | `GATE OK[ (warned: ..; skipped: ..)]` (or `GATE OK (auto-detected: no stack found, so NO checks ran; ...)`, see Auto-detected gate), `LANDED <branch> on <main> at <merge> (pushed and verified on <remote>)` (followed by `WARNING: the landing lock could not be released: ...` and the command to break it when only the release failed), or `proposal written: <path>` |
| 1 | FAILED | `GATE FAILED: <steps> (<first>: <reason>)`, or `NOT LANDED: ...` (red merge undone, conflict aborted, a step left untracked files in the main checkout, an exception or SystemExit after the merge that was undone) |
| 2 | USAGE | `USAGE: ...`: bad arguments, an `--only` name no step has, a `--base` that does not resolve, an unknown `--lane`, a machine-lock usage error such as an unknown `"gate".kind`. Never worded as a refusal (refusal-log P10). |
| 3 | STUCK | `STUCK: landing <branch> stopped in phase <phase>: ...`, then what is left and the steps to clear it (see Landing); the landing lock stays held at phase `stuck`. A step that committed or changed a tracked file is STUCK, and so is a Ctrl+C or SystemExit whose undo cannot complete |
| 4 | REFUSED | `REFUSED: ...; nothing was changed` or `... nothing was merged` (a config error before the merge, `"landing".lock_file` included, is one); `REFUSED: no gate step selected: ...` when the steps cover none of the changed paths; `REFUSED: no gate step ran: ...` when every selected step was skipped for a missing `requires` (it names each one and what it requires). In both, no record is written and a landing undoes its merge. |
| 5 | BUSY | `BUSY: landing lock: HELD ...; nothing was changed` (the turn or the lock not had within `--wait`; with landings ahead in the queue, `landing queue: N ahead: ...` follows the holder), or `BUSY: ... not broken, because ...` at once for a gone holder that left something unpushed |
| 9 | LANDED_UNGATED | Landed, but main was not gated whole: `LANDED <branch> on <main> at <merge> (already on <remote>: <remote>/<main> <sha> has it, with N commit(s) on top made while the merged gate ran: ...)`, then `WARNING: <branch> landed, and main was not gated whole: <commits> change <paths>, which select <steps>; gate it with: python "<kit>/tools/gate.py" -C "<root>" --full` (see Landing, step 7) |

`gate.py wait-result` has its own codes: 0 (the record's verdict is `pass`), 1 (any other verdict, `landed-ungated` included), 2 (USAGE), 7 (TIMEOUT: no final record at that tip in time).

Any other machine lock refusal prints `NOT RUN: the machine lock refused the gate: ...`. Ctrl+C is 130 only when nothing is left: before the merge, or after it once the merge was undone and the lock released.

A landing's verdict is its exit code, and in text its first line starting `LANDED `, `NOT LANDED:`, `STUCK:`, `REFUSED:`, `BUSY:`, `USAGE:` or `NOT RUN:`. Key on that line, not on `^GATE (OK|FAILED)`, which is the merged gate's own verdict (`kitlib.gate.runner.verdict`). A `GATE OK` line appears only in a landing that LANDED; a green merged gate that is then not landed prints it as `merged gate passed ...`, so no `GATE OK` line stands beside a `NOT LANDED`.

## Steps

kitlib/gate/steps.py. A step has a `cmd` (argv with `{python} {root} {base} {here} {tools}` substituted) or a `check` (a function in the repo hook module's `GATE_CHECKS`).

- **Full command.** A `cmd` step may also have `full_cmd`, an argv substituted the same way. A full run (`gate.py --full`, `land.py --full`, `daily_full.py`) runs `full_cmd` instead of `cmd` (`steps.build(full=True)`); every other run, a landing without `--full` included, runs `cmd`. `merged_args` are appended to whichever runs. Use it for a step whose `cmd` selects tests by the change: on an unchanged tree such a `cmd` selects nothing and passes without running a test.
- **Daily command.** A `cmd` step may also have `daily_cmd`, substituted and validated like `full_cmd`. The daily full run (`daily_full.py`) runs a step's `daily_cmd` when it has one, else its `full_cmd`, else its `cmd` (`steps.argv_of`, `steps.build(daily=True)`). No other run reads it, so a tier too slow for every full gate, such as the kit's `kit_tests --full --both-tiers`, can run only daily.

- **Selection.** In diff mode a step runs when it is `always`, or when a changed path (tracked diff from the merge base, plus untracked files git does not ignore) matches its `globs` and none of its `exclude`, or when its `content` regex is in a changed file. `--full` runs every step that is not `manual`. `--only` runs exactly the named steps. `skip_if_selected` drops a step. Order: `setup`, then stages `first`, `main`, `last`, then `defer`.
- **Judging.** A step passes only when its exit code is in `ok_exits`, every `pass` pattern matches, no `fail` pattern matches, a cmd step's log is not empty, and it did not run zero tests (`Ran 0 tests` or a `zero_tests` pattern). The `errors` policy must also find no unexplained line. A `warn` step that fails, or a `warn_lines` hit, is WARN. A FAIL stops the rest unless the step has `continue`. A `requires` entry is a command name (looked up on PATH) or an argv probe that must exit 0 within 60 s (`PROBE_TIMEOUT`; on timeout its whole process tree is ended). One that is missing is SKIP, or FAIL with `requires_strict`. A gate whose selected steps were all skipped did not run anything, so it is REFUSED, not OK.
- **Reuse.** A cmd step with `reuse` (`true`, or a group name: a group is reused whole or not at all) and declared inputs (`globs` or `content`.globs) may be counted as passed without running, in a branch-gate rerun or a landing, when a pass of the same inputs, argv, config and kit is in the gate cache (see Gate reuse). A check step never is.
- **Check contract.** `GATE_CHECKS[name](ctx)`; ctx has `root base merged changed options name log run`. `run(argv, cwd=None)` runs in the slot's job and returns the exit code. A check returns 0/True to pass. Raising fails the check, and the traceback goes in the log. Calling `sys.exit` (any code, 0 included) also fails it, and the code goes in the log. Ctrl+C is not caught: it stops the gate.

## Auto-detected gate

With no `"gate"` section in `.kit.json` (neither inline nor in the file it names, such as `tools/gate.json`), the gate detects the stack from the checkout's files and runs its usual test and lint steps (`kitlib/gate/detect.py`; docs/multi-host-plan.md decision 24). A configured `"gate"` section always wins, even an empty one: no detected step is ever added to it, and a section with no step that covers the change refuses as before. Every gate takes its steps from `detect.effective`: the branch gate (from the checkout), a landing's merged-tree gate and its check of commits on top (from the merged tree), and the daily full run (from its worktree).

The files are the ones git lists (tracked, plus untracked files it does not ignore); where git cannot list them, a walk that skips `node_modules`, `.venv`, `target`, `bin`, `obj` and other build folders, and any folder with a `.git` of its own. Detection only reads files: it installs, fetches and runs nothing, and looks nothing up on PATH. Each detected step is `always`, and names its tool in `requires` (Steps, Judging). A test step is `requires_strict`, so a missing test runner FAILs: a gate never passes without the tests it found. A lint step is not, so a missing linter is SKIP, named in the verdict line. `{python}` is the interpreter running the gate, not a project virtualenv; a project that needs its own interpreter, an install step or other arguments writes a `"gate"` section.

| Stack | Detected by | Steps |
|---|---|---|
| Python | a test file (`test*.py` or `*_test.py`) | `python-tests`: `{python} -m pytest` when the repository uses pytest (`pytest.ini`; a `conftest.py`; a `[tool.pytest...]`, `[tool:pytest]` or `[pytest]` section; `pytest` or a `pytest-*` plugin named in `pyproject.toml`, `setup.cfg`, `setup.py`, `tox.ini`, `Pipfile` or `requirements*.txt`; or a test file that imports it), requiring `import pytest` to work; else `{python} -m unittest discover`, with `-s tests` (or `-s test`) when the tests are in that folder |
| | `ruff.toml`, `.ruff.toml` or `[tool.ruff]` in `pyproject.toml` | `python-ruff`: `ruff check .` |
| | `.flake8`, or `[flake8]` in `setup.cfg` or `tox.ini` | `python-flake8`: `flake8` |
| Node | `package.json` at the root | `node-test`, `node-lint`, `node-typecheck`: `<pm> run <script>` for each of the scripts `test`, `lint`, `typecheck` it has (npm init's `no test specified` placeholder is not a test). `<pm>` by lockfile: `pnpm-lock.yaml` pnpm, `yarn.lock` yarn, `bun.lockb` or `bun.lock` bun, else npm (npm, pnpm and yarn run as their `.cmd` shims). Dependencies are not installed: `node_modules` must be there |
| Rust | `Cargo.toml` at the root | `rust-test`: `cargo test`; `rust-fmt`: `cargo fmt --check` when `rustfmt.toml` or `.rustfmt.toml` is there |
| Go | `go.mod` at the root | `go-test`: `go test ./...`; `go-vet`: `go vet ./...` |
| .NET | a `*.sln` or `*.slnx` at the root, else a test project (`*.csproj`, `*.fsproj` or `*.vbproj` named `*test*`, or referencing `Microsoft.NET.Test.Sdk`) | `dotnet-test`: `dotnet test <solution or project> -nodeReuse:false -p:UseSharedCompilation=false`, one step per solution (or per test project when there is no solution), each named `dotnet-test-<name>` when there are several |

Several stacks in one checkout run every one's steps, in the table's order. Python with no test file and no linter config, and a `package.json` with none of the three scripts, detect nothing.

**The label.** An auto-detected gate says `source: auto (auto-detected gate: <stacks>; ...)` before it starts, and the same line is the last line of its report (`source: gate.json` for a configured gate). `gate.py --plan` ends with it too. The result record and the gate-OK record carry `source` (`auto` or `gate.json`; see Gate-OK record and Result record), so the PM sees an auto-detected gate in the record a waiting session reads, not only in the console.

**Nothing detected.** The gate runs no step and PASSES, saying so: `GATE OK (auto-detected: no stack found, so NO checks ran; ...)`, then `source: auto (auto-detected gate: no stack found, so it ran NO checks; ...)`. A branch gate writes the gate-OK record as usual (its `steps` empty, `source` `auto`), and a landing lands. It passes rather than refuses because an auto-detected gate exists so that a repository with nothing committed for the kit (a docs-only repository, or a stack no detector knows) can run a worker-to-landing cycle; a refusal there could only be cleared by committing a gate section, which is what auto-detection avoids. The checks it did not run are not hidden: the verdict line, the source line and both records' `source` say so wherever a pass is read. A configured gate with no step selected is still REFUSED (Exit codes), and an auto-detected gate whose detected steps were all skipped is REFUSED as any gate is (`no gate step ran`). The daily full run refuses a gate with no step either way.

**The record's hash.** `gate_config` (Gate-OK record) is still the configured section over its defaults, not the detected steps: they follow from the commit's tree, which the record names, and the kit, which its `kit` names, so the hash and the record still fix what the gate ran.

## Build daemons

At the release of a gate run that ended "done", `kitlib/lock/run.py` `Slot.stop_daemons` stops the build daemons the gate's commands left in its job (policy: `machine_lock.daemons`, default `gates`, in `kitlib/lock/site.py`). A daemon is shared: any build on the machine may reuse one this gate started, so `kitlib/proc/daemons.py` `stop` ends one only when it is shown to serve the gate's job alone:

- MSBuild nodes and the C#/VB compiler server (VBCSCompiler) are always left running. Their clients reach them over named pipes, and which process holds the other end of a pipe cannot be read from outside.
- A Gradle or Kotlin daemon is stopped, with its children, only when the other end of every established TCP connection on this machine (`kitlib/proc/tcp.py` `peers`) of every process in its tree is in the gate's job (a job nested in it counts as in), in that same tree, or a process that has gone. `kitlib/proc/tcp.py` reads the connection table and `kitlib/proc/job.py` `Job.contains` asks Windows (`IsProcessInJob`).
- Anything else leaves it running, never killed: a client outside the job, a client whose job Windows will not tell, a connection on this machine (to a loopback address, or to an address that is the local end of any row in the table) whose other end the table does not show, a connection table or process tree that cannot be read. A daemon in the tree of a daemon left running, or serving a process in that tree, is left too.

Each daemon is said, as `run <id>: stopped the <label> (pid N) it left: <result>` or `run <id>: left the <label> (pid N) running: <why>`, and listed in the run's ended record under `daemons` (`pid`, `what`, `result`; a left one's result is `left: <why>`). A gate nested in another run says them and records none. A `store.say` that raises in `Slot.stop_daemons` is dropped: the release goes on, and the record is not given these results. The tree and the table are read once, before any daemon is ended, so a client that connects between that read and the kill is not seen. Exactly the (pid, creation time) pairs judged are ended, children first, each by `terminate_verified`; the tree is not read again, so a judged child whose pid a newer process now holds is not hit, and a process a daemon starts after the read is not ended. Tests: tests/proc/test_daemons.py, tests/proc/test_tcp.py, tests/lock/test_release_daemons.py.

The kill path spares a shared daemon too. A run that is cancelled by `stop`, interrupted by Ctrl+C or ends in error (a gate's block raised), and a `Launcher.kill`, ends its job through `kitlib/lock/run.py` `Slot.end_tree`. This holds for any run booked by `book()` (`machine_lock.py run`, a gate, a `slot()`), not only a gate; a background run does not use it (see the known limits). Windows cannot take a process out of a job, so the daemons are judged before anything is ended: `kitlib/proc/daemons.py` `find` on the job's pids, then `stop` with `Job.contains`, as above. `machine_lock.daemons` is not read here: a daemon that serves only the run's job is ended, as the kill always did, and one the rules above leave (MSBuild nodes and the compiler server among them) is spared with its tree. Each is said and recorded as above.

- Nothing found, or no daemon left: TerminateJobObject, as before.
- The job's processes or the daemons cannot be read: TerminateJobObject (the run's tree surely ends).
- `stop` raised: it may have ended some daemons first, so each daemon found is recorded and said as `not judged (<error>)`, never as left, and each one still running at its creation time is spared with its tree.
- Otherwise every process in the job outside the spared trees is ended by `terminate_verified`, oldest first so a parent cannot start more, in up to `END_PASSES` (10) passes `END_PASS_S` (0.1 s) apart (`Slot._end_others`). Each pass takes a stamp of the system time (`filetime_now`), reads the job's pids, then the process table, and builds the spared trees from that table (each left daemon at its creation time, or, when its creation time cannot be read, while `process.alive` does not say it is gone, with its descendants). Reading the job first means a worker the daemon started before the pid list is in the table too, so it is spared. A target whose process was created at or after the stamp may hold a reused pid, so that pass does not end it; a new process in the job is seen again by the next pass. One still running in the job after the last pass, and up to `END_WAIT_S` (1 s) more, is said (`WARNING: run <id>: pid N in its job could not be ended; it runs on, unpinned`; `Slot._running`); a listed pid whose process has exited by then is not. The job is then closed without a kill and unpinned, and the spared daemons run on. A job or process table (`process.snapshot`) that cannot be read part way ends the job whole, the spared daemons with it, and that is said. A second `end_tree` (the release's, after a Ctrl+C) adds its results to the record's `daemons` (`Slot.tell_daemons`): a pid judged again takes its new result, the others stay. A `store.say` that raises in `Slot._end_tree` is dropped: what is ended and spared does not change. When it raises in `Slot.tell_daemons`, the results after the failed one are not said and the record is not given that judgement's results, so after a second judgement it can keep the earlier result of a pid judged again.
- An interrupt anywhere inside `end_tree` (a second Ctrl+C, or any other exception that is not an `Exception`), during the daemon judgement or the passes, goes up with the kill marked not done, so the release that follows judges and ends the tree again. One that interrupts the release's own `end_tree` ends the whole job, the spared daemons with it, and goes up.

Known limits:

- While a run lives its job is kill-on-close, so a wrapper that dies (killed or crashed) closes it and Windows ends every process in it, a shared daemon included; no code runs then.
- A background run (`kitlib/lock/background.py` `end_child`) still ends its whole job, a shared daemon included.
- An MSBuild node or the compiler server in the job is left whoever its clients are (`kitlib/proc/daemons.py` `PIPE_LABELS`), so a cancelled `dotnet` run does not end them or what they started; only the daemon itself is named in the `left the <label> (pid N) running` line.
- Nothing in the lock ends those later: `daemons.stop` leaves them at every release, whatever `machine_lock.daemons` says, so they run until they exit by themselves or are ended by hand. `python optional/procwatch/procwatch.py --kill --only msbuild-node` ends each MSBuild node that is idle, has no living parent and is at least 5 minutes old (15 with `/nodereuse:true` on its command line); its rule matches only a node started with `/nodemode:` (`kitlib/proc/daemons.py` `PATTERNS` matches `-nodemode:` too), so one started with `-nodemode:` is not ended by it. It reports compiler servers (rule `roslyn-server`) and never ends one. The .NET stack template's gate steps (`templates/stacks/dotnet/tools/gate.json`) run `dotnet build` and `dotnet test` with `-nodeReuse:false -p:UseSharedCompilation=false` (`templates/stacks/dotnet/tools/dotnet_each.py` `NO_REUSE`), meant to leave no build server behind a run; its `stack.json` `BUILD_COMMAND` has only `-nodeReuse:false` and its `TEST_COMMAND` neither.
- A spared daemon inside a nested kill-on-close job, made by a process the kill ends, can die with that job although the record says it was left running (inferred from how Windows jobs behave, not tested).
- A descendant of a spared daemon whose own parent has exited no longer shows as the daemon's descendant, so it is ended.
- A process started after the last pass by one being ended runs on, unpinned.
- A left daemon whose creation time cannot be read (`process.proc_ctime` gives None) and whose pid a process this user cannot open (another user's, or a protected one) takes during the passes still counts as alive (`process.alive` cannot tell them apart), so `Slot._end_others` spares that pid and, through `process.descendants`, the dead daemon's orphaned workers; they run on, unpinned. Processes can leak this way; nothing shared is killed.
- The stamp test rests on Windows stamping a process's creation time from the same system clock `GetSystemTimeAsFileTime` reads (inferred from the documented clocks, not measured); a clock set back during the passes voids it.

Tests: tests/lock/test_release_daemons.py (`ReleaseLeavesASharedDaemon`: the errored and cancelled gates, `Launcher.kill`, a second Ctrl+C mid-kill in wait and in release, a second kill keeping the first's record, a worker started between the reads, a reused pid, a listed pid gone by the last pass, a daemon whose creation time cannot be read, a process table that cannot be read, a judgement that raised, a result that cannot be said, a `say` that raises for every text with a survivor of the passes and on a done release, the two kill-path controls, and a control on the harness: an outside client that exited fails as the test's setup).

## Gate-OK record

The branch gate writes `<git common dir>/kit-gate-ok/<sha>.json` (kitlib/records/gate_ok.py) only when all of these hold:

- at least one step was selected, every selected step passed, warned or was skipped, and at least one passed or warned;
- no `--only` was given;
- the base is the default base (`--base` naming another commit makes the gate partial);
- the work tree was clean (no tracked change, no untracked file) at the start and at the end;
- HEAD did not move.

With no step selected, or every selected step skipped, it is REFUSED (exit 4). Otherwise a missed condition prints `no gate-OK record: <why>` and still exits 0 when the gate passed. `gate_config` is `.kit.json` "gate" over its defaults (`kitlib.gate.runner.gate_config`); guard.py and pre-push verify with the same value. A landing writes the record for its merge commit after the merged gate passes, after the checkout is checked unchanged, and before the push.

`source` (an added key, `gate_ok.ADDED_KEYS`) is where the gate's steps came from: `gate.json` (the configured "gate" section) or `auto` (Auto-detected gate). A record written before the key has none; `gate_ok.source_of(record)` reads it as `gate.json`, and `verify` neither requires nor checks it.

`config_rev` (an added key, `gate_ok.ADDED_KEYS`) is the commit the gate config was read from: HEAD for a branch gate, `--expect-main` for a landing. `gate_ok.verify(root, commit, config_at=...)` requires it to be in the commit's history and compares the record's `gate_config` with the config that commit holds; `kitlib.gate.runner.verify_record(root, commit)` does that with `.kit.json` read by `kitlib.config.load_at`. `verify(root, commit[, gate_config])` without `config_at` is unchanged.

## Result record

kitlib/gate/result.py. `<git common dir>/kit-gate-result/<stem>.<kind>.json`, beside `kit-gate-ok/`: one folder per repository, shared by every worktree and the main checkout, never tracked. The kind is `gate` (`kitlib.gate.runner.branch_gate`) or `land` (`kitlib.gate.land.Lander.run`).

**Writes.** A run writes the file twice, each time atomically (temp file, then `os.replace`): a `running` record when it starts, then its final record with the same `run_id` and `started_at`. The `running` record replaces any earlier record of that branch and kind, at that tip or another. A branch gate starts the record before anything else; a landing starts it once its locked checks pass, just before the merge. Each write is said as a progress line, `result record: <path>`, before the outcome's own lines, so the verdict line stays last; a write that fails says `WARNING: the result record could not be written: ...` instead, and the outcome, exit code and verdict line stand. The outcome's `result_record` fact is the final record's path, or None. An exception or Ctrl+C that escapes the run is written as verdict `error` and raised again unchanged.

**No record** (the file keeps whatever it held): `--plan`; a detached HEAD; `gate.py` failing to open the machine lock store before the gate starts; a landing that ends before its locked checks pass (USAGE, REFUSED before anything was changed, BUSY on the landing lock: a duplicate or retry overwrites nothing). A process killed outright leaves its `running` record with no final one.

**File name.** The stem is the branch with every character outside `[a-z0-9._-]` written `%XX` (its UTF-8 bytes, capital hex), capital letters included, so `kit/A` is `kit%2F%41`: two branches never share a file, even where file names ignore case. A stem whose first part is a Windows device name (`con`, `nul`, `com1`, ...) has its first letter encoded too. A stem over 120 characters (`result.MAX_STEM`) is cut and ends `~` and a hash of the branch.

| Key | Value |
|---|---|
| `schema` | 1 |
| `kind` | `gate` or `land` |
| `branch` | the branch name |
| `tip` | full hash: HEAD for a branch gate, `--expect-tip` for a landing |
| `base` | the merge base gated against, or `--expect-main`; null when the gate stopped before it knew one |
| `run_id` | one run's id; its `running` and final records share it |
| `started_at`, `finished_at` | UTC, `YYYY-MM-DDTHH:MM:SSZ`; `finished_at` is null while running |
| `verdict` | `running`; or final: `pass`, `fail`, `refused`, `stuck`, `busy`, `usage`, `landed-ungated` (exit 9: landed with commits on top that no gate saw), `not-run` (a machine lock refusal), `error` (an exception or Ctrl+C ended the run) |
| `code` | the exit code gate.py gives that outcome; null for `running` and `error` |
| `log` | the run's log folder, or null when no step ran |
| `summary` | the verdict line (`GATE OK ...`, `GATE FAILED: ...`, `LANDED ...`, `NOT LANDED: ...`, `REFUSED: ...`, ...), or the exception for `error` |
| `gate_ok_record` | the branch gate's gate-OK record path, or null (always null for a landing) |
| `cleanup` | a landing that landed: this branch's cleanup (see Branch cleanup); null for a branch gate, a landing that did not land, and one whose cleanup did not run |
| `source` | where the gate's steps came from: `gate.json` (the configured "gate" section) or `auto` (Auto-detected gate); null while `running`, for `error`, and when the run ended before its gate config was read (a landing: before its merged gate ran). Added within schema 1: a record written before it has no `source` key, which readers take as null (`result.source_of`) |

A pass is not a gate-OK record: a gate that passes a dirty tree is `pass` with `gate_ok_record` null. A waiting session that treats `pass` as ready to land checks `gate_ok_record` too.

**Waking a waiting session.** The gating session runs the gate as usual (`gate.py`, or `gate.py land`) and tells the waiting session the branch and the tip it is gating (`git rev-parse HEAD`) once the gate has said its first `result record:` line. The waiting session arms after that: before it, an earlier run's record at the same tip would answer at once. `wait-result` is read-only. It blocks until the file holds the final record of that branch and kind at that tip (`branch` and `kind` equal, `tip` starting with `--tip`, any case; a `running` record does not count), then prints two lines, `RESULT <verdict> <kind> <branch> at <tip>: <summary> (<log>)` and the record as one line of JSON, and exits. Example for a branch gate of `kit/x` at tip `<sha>` in the repository at `<repo>`:

```
Monitor({description: "gate result kit/x", timeout_ms: 1800000,
         command: 'python <kit>/tools/gate.py wait-result kit/x --tip <sha> --timeout 1740 -C <repo>'})
```

`<kit>` is the kit checkout (`<tools_dir>` in docs/guard.md), `<repo>` any checkout of the gated repository. Wait for a landing with `--kind land`. The Monitor caps `timeout_ms` at 30 minutes, so `--timeout 1740` ends first. Exit 7 with a `TIMEOUT:` line means no final record at that tip yet: the run is still going, has not started, or ended without one (see No record); arm it again, and look at the gating session when it keeps timing out. The exit code is the verdict (0 pass, 1 anything else, `error` included); the printed record says which. A `--tip` that is not 7 to 40 hex digits, or a `--timeout` that is negative, `nan` or infinite, is USAGE (2). Do not pipe it into another command: guard.py's `wrapped-gate` rule (docs/guard.md) refuses `gate.py` piped.

**Waiting on a gate: who arms what.** Your own gate: run it in the foreground with `timeout` 600000 when it fits; otherwise `run_in_background` and end the turn. The exit notice wakes you. No Monitor, no polling the log, no sleep. Monitor with `wait-result` is only for a gate another session runs: one arm at `timeout_ms` 1800000, re-armed only on exit 7. Never re-arm a wait because a turn ended with nothing new: each Monitor fire wakes the session for a full cache read.

## Landing

kitlib/gate/land.py runs in the main checkout, on main, in this order:

1. **Usage.** Every hash is a full hash, one `--expect-tip` per branch, each branch and tip named once. The lane is `full` or one that `.kit.json` "landing".lanes declares, read from `--expect-main`'s config.
2. **Refusals.** It refuses when the checkout is not main, HEAD is not on main, a branch is main or missing, the lane's `branch_prefix` does not match, or a batch has more branches than `"landing".batch_max`.
3. **Fetch, queue and lock.** It joins the repository's landing queue, then takes the landing lock (kitlib/records/landing.py) at its turn (see The landing queue). `--wait` seconds covers both, counted from the first look that finds either taken, when it says `waiting up to <s> s for the landing lock` once (`Lander.take`); not had in time is BUSY. Branch gates and other repos never take this lock or queue.
4. **Locked checks.** It fetches again, then checks: main equals `<remote>/<main>` equals `--expect-main`; each tip equals its `--expect-tip`; the tree is clean; no merge is in progress; no branch is already merged; in a batch, no tip contains another; in a lane, every changed path is in its `paths`; for every owner-only path that landing the branch would change, every branch commit that changes it is authored by the owner ("Owner-only commits" in docs/guard.md); and, for a `ref` or `branch` backlog store, no branch's history holds a root commit of the store (kitlib/backlog/at_landing.py `ancestry_refusal`; a store that cannot be read refuses too). Any miss is REFUSED, with nothing merged. A landing that waited (its first look found the queue turn or the lock taken, and `--wait` let it wait) follows main forward: when main and `<remote>/<main>` agree on a commit that descends from `--expect-main`, it merges onto that commit and gates and lands as usual, saying `main moved on from --expect-main <old> to <new>, which descends from it`; the lane, branch and batch checks are rerun against the new main's config. Main moved any other way (rewritten or reset), main and the remote disagreeing, or a new config that names another main, remote or lock is REFUSED. A landing that took its turn and the lock at once, or ran with `--wait 0`, keeps the exact check (`Lander.follow`).
5. **Merge.** `git merge --no-ff <tip>`, for each branch in order. A conflict is aborted, the batch's earlier merges are undone, and it gives FAILED.
6. **Merged gate.** It gates the merged tree once under `book()`, adding each step's `merged_args`, then the lane's `merged_args`. Check steps run the hook module as `--expect-main` has it, read from that commit like the config (kitlib/gate/hookrev.py), so a branch is gated by main's checks, not its own. Step `cmd`s run the merged tree's files. A step may be reused instead of run (see Gate reuse). On red, `git reset --keep <expect-main>` runs (with the merge's 300 s timeout), but only while HEAD is on main, main's first-parent line beyond `--expect-main` is exactly this landing's merges and no tracked file changed. The result is FAILED: a red merged gate never leaves its merge on main. Untracked files a step left are kept: they are named, with a line saying the main checkout needs cleaning.
7. **Unchanged.** On green, HEAD must still be on main at the merge, with no tracked change and no untracked file. Otherwise nothing is recorded or pushed and the merge is undone as on red (FAILED, `NOT LANDED`). A step that committed, changed a tracked file or switched HEAD to another branch makes that undo unsafe, so it is STUCK. A `"landing".log_dir` inside the checkout must be git-ignored: the gate's logs are untracked files there, so the landing is NOT LANDED.
   - **Commits on top, already pushed** (`Lander.adopt`). Someone committed on top of the merge in the main checkout and pushed while the gate ran. When, after a fetch, `<remote>/<main>` (as `git ls-remote` reads it) equals the tracking ref and main, no merge is in progress, HEAD is on main with no tracked change and no untracked file, and main's first-parent line beyond `--expect-main` is commits on top of exactly this landing's merges, the landing is finished instead of undone: the lock is released, then steps 9 and 10 run. The `LANDED` line says `(already on <remote>: <remote>/<main> <sha> has it, with N commit(s) on top made while the merged gate ran: <sha> <subject>; ...)`. The paths those commits change (merge to `<remote>/<main>`) are matched against `--expect-main`'s gate steps as diff-mode selection does (`Lander.unseen`; `setup` not counted). None selected: the merge's gate-OK record is written and the exit is 0. One or more selected, or the paths or the selection cannot be worked out: no record, a `WARNING: ... main was not gated whole: ...` line after the `LANDED` line names the commits, paths and steps and the full gate to run, and the exit is 9 (LANDED_UNGATED). The warning is set before the landing counts as pushed and cleared only when no step is selected, so an exception or Ctrl+C between the two still exits 9 with it. Anything short of all those conditions is undone or STUCK as above.
   - **The merge already on the remote.** No undo runs once `<remote>/<main>` is a merge of this landing or descends from one (`Lander.not_on_remote`, asked again after a fetch when the remote's commit is not here). When `ls-remote` cannot read `<remote>/<main>`, the tracking ref decides: unless it is known not to hold the merge, no undo runs either. Both are STUCK, on red and on green alike, and the report says no reset (see the STUCK steps below).
8. **Push.** It writes the record, then runs `git push <remote> <merge>:refs/heads/<main>` (never forced). `git ls-remote` must show the merge. From then on the landing stands (`Lander.phase` `pushed`, also set by an adopt in step 7): a release of the lock that fails, or an exception or Ctrl+C before the release ends, is still LANDED (exit 0, or 9 when an adopt found commits on top and had not cleared its warning that main was not gated whole) with a WARNING: the tracking ref is set to the verified commit (the merge, or for an adopt the remote's main it found), and the lines name the command to break the lock when it is still held, and, for each store that takes part in step 9, the command that shows the branch's backlog records left to close (`at_landing.landable_commands`; `Lander.landed_anyway`).
9. **Close.** After the release, every record the branch holds pulled is closed, `landed <merge>` (`at_landing.close_landed`), in two stores:
   - the configured store, when it is a `ref` or `branch` store: one store commit each (`closed <ID> in the backlog store: landed <merge> (store at <sha>)`);
   - the PM data branch's store (kitlib/pmdata; docs/pm-data-branch.md), found as the worktree of the repository that has the branch `kit-pm-data.json` records checked out (`at_landing.pm_data_root`), unless it is the configured store or the main checkout itself: the record file is deleted in that worktree and the deletion committed there (`closed <ID> in the backlog store <store>: landed <merge> (committed <sha>)`); a commit that fails is a WARNING naming the `catch-up --apply` command for every path the close wrote, a commit stopped because another commit changed one of those paths on HEAD puts the close's files back and is a WARNING naming the close command while the record is still pulled by the branch, or the `git diff HEAD --` compare for a file it left, and no ready-made `catch-up --apply` command, and a commit whose index update fails is a WARNING naming the `git reset -q --` repair (kitlib/backlog/at_landing.py `_close_in`).

   A close that fails, a store that cannot be read, and an exception or Ctrl+C here, is a WARNING with the command to finish it, or to see what is left (`backlog.py landable <branch>`, one per store, `at_landing.landable_commands`); the landing stays LANDED and is never undone. A close command for the configured store names `-C "<a worktree of this repository>"` (`at_landing.WORKTREE`), never the main checkout the landing ran in, and the repository's own `tools/backlog.py` when it has one, else the kit's (`at_landing.close_command`); an owner-held record's command carries the owner's go that ends the hold (`at_landing._close_in`, as `plan_close` needs it). A command for the PM data store names that worktree.
10. **Cleanup.** Then each branch's remote branch, worktree and local branch go, unless `--keep-branch` (see Branch cleanup). Its lines come before the `LANDED` line.

An exception, SystemExit or Ctrl+C under the lock: before the merge, the lock is released (a config error is REFUSED). After the merge, a merge stopped part way is aborted, and a finished one is undone, and the lock released (FAILED); Ctrl+C is then raised again, so the exit is 130. When that undo cannot complete, or the push had started and `ls-remote` had not yet shown the merge, the result is STUCK (exit 3), Ctrl+C included.

Anything after the merge that cannot be undone safely gives STUCK: an undo that does not verify, an interrupted or rejected or unverified push, or a git failure. The lock stays held so that no landing stacks on top. STUCK prints a `left:` line (the branch HEAD is on, main, the remote's main as `git ls-remote` reads it, the tracking ref, tracked changes, untracked files), then numbered steps to clear it, in order. Each command is on its own line starting `    $ ` (`land.STEP_CMD`). The steps fit what is left (`Lander.clear_steps`):

- **Push unknown** (`ls-remote` failed): the push may have landed. First `git fetch` and `git rev-parse <remote>/<main>`. When the tracking ref holds the merge, the steps go on as On the remote, with no reset; when git cannot place the tracking ref against the merge, only the Remote's main not here step follows. Otherwise: if that shows the merge, the landing is done and only the lock is broken; if it shows `--expect-main`, go on; if it shows anything else, `git branch -r --contains <merge>` comes before any reset (the merge is landed when it names `<remote>/<main>`). A failed fetch means stop: what it shows is stale.
- **On the remote** (the remote's main is the merge or descends from it; `Lander.on_origin_steps`): no step and no line says reset. When the tracking ref is not the remote's main, `git fetch` comes first, since `break_lock` compares main with it. A merge that reached the remote without a passing merged gate is named, with `git revert -m 1 <merge>` to run by hand once the lock is broken (newest first in a batch), never as a `$` line. Then `git switch <main>` when HEAD is elsewhere, tracked changes and untracked files to keep or drop by hand, and `git merge --ff-only <remote>/<main>` when main is only behind it; when main has commits the remote lacks, they are named to push or set aside by hand. Commits on the remote's main beyond the merge that no merged gate saw are named (`<sha> <subject>`), with the full gate to run on main once the lock is broken.
- **Remote's main not here** (`ls-remote` read a commit this checkout lacks, or git cannot place it against the merge, so whether it holds the merge cannot be told; `Lander.check_first`): one step, `git fetch` and `git branch -r --contains <merge>`, then only the lock break; no `reset` and no `kit-stuck` `$` line is printed. The step says in words what to do: if the fetch failed, the list is stale, so stop and do not move main; if the list names `<remote>/<main>` the merge is landed, so bring the checkout to `<remote>/<main>` by hand; if not, settle the remote's main with whoever pushed it and put main back at `--expect-main` by hand, keeping any commits beyond the merge on a branch first.
- **HEAD on another branch**: `git switch <main>` comes before any reset, so a reset never moves another branch.
- **Tracked changes**: keep or drop them by hand; `reset --keep` refuses to overwrite them.
- **Commits on main beyond the merge** (and beyond the branch it merged): they are named, and `git branch kit-stuck-<sha> <main>` keeps them before the reset; re-apply them after the lock is broken.
- **Unpushed**: `git -C <root> reset --keep <expect-main>`.
- Last, a `python -c` line that runs `LandingLock.break_lock` (it refuses while the holder is alive or main differs from the remote's tracking ref).

A gate-OK record is written for the merge before the push. When the merge is then undone (a push that did not land, cleared by hand from STUCK), the record for that merge commit stays in `<git common dir>/kit-gate-ok/`. It is stale but harmless: records are keyed by commit (`gate_ok.record_path`), that commit is no longer on main, and a reader verifying any other commit never reads it. Only a later push of that same merge commit would find it. Delete it by hand when clearing such a STUCK.

**First switch.** A repo's first switch from the old PM kit is landed by the owner, by hand. Its base `.kit.json` fails to load with the kit loader (old key spellings such as `gate.hook`, `doc_budget.owner_email`/`agent_emails`/`owner_only`/`owner_only_except`, and dropped keys such as `dependency_pin_check` and `python_tests_audit*`). Five sites then refuse: the pre-push hook (kitlib/guard/prepush.py), the guard's git-push-main rule (kitlib/guard/rules.py `git_push`), the land.py preconditions (kitlib/gate/land.py), the trailers check (kitlib/trailerscheck) and review_pack's base read.

1. Rewrite the base `.kit.json` to the kit spelling: rename the old keys, drop the removed ones (docs/kit-json.md). The renames (kitlib/config/schema.py `SECTIONS`; docs/kit-json.md and docs/doc-tools.md): `gate.hook` becomes the top-level `hook` (its module name is `hook.module`); `doc_budget.owner_email`, `doc_budget.agent_emails`, `doc_budget.owner_only` and `doc_budget.owner_only_except` become `owner.email`, `owner.agent_emails`, `owner.paths` and `owner.paths_except`. `python_tests_audit*` is dropped only as a `gate` key: it is still valid under `hook.options`, which is passed to the hook module unread, when the repo's hook module reads it.
2. Check that it loads with the kit loader: `python <kit>/tools/preflight.py -C <repo>` (`<repo>` is the checkout, worktree or not, that holds the rewritten `.kit.json`) loads the repo's `.kit.json` and, when it does not load, prints `preflight: refused: kit configuration: <the load error>` and exits 2. (`python -m json.tool` checks syntax only.)
3. The owner commits and pushes that switch commit. The kit's own pre-push hook refuses this push when it is installed in that repo: it reads the base `.kit.json` from the remote's main (kitlib/guard/prepush.py `_cfg`, `kitlib.config.load_at`), and the old spelling fails to load. Until main loads, pre-push refuses every branch push, not only the switch push. Push before the kit hook is installed in that repo, or push that one switch commit with `--no-verify` from the owner's own terminal (the guard refuses `--no-verify` pushes in agent sessions: rules git-push-main and git-push-pmdata), then install the hook. `gate.py land`, pre-push and the trailers check refuse until main loads.
4. After that, normal landings work (docs/go-live.md "Landing tool").

Reopen the item KIT-FIRST-SWITCH-LANDING if a repo ever has to switch from the old PM kit.

### Pinned tools

A landing merges into the main checkout it runs from. A tool running there would import the modules it loads lazily after the merge against the older ones it had already loaded: a mixed generation. So `tools/land.py` and `tools/gate.py`, started from the kit's main checkout, first re-run themselves from an export of the kit's remote-tracking main, `refs/remotes/<remote>/main`, with the same arguments and the same interpreter flags (`-X utf8`, `-B`, `-I`, `-W` and the rest that the private `subprocess._args_from_interpreter_flags` gives, none when Python lacks it, and `-u` when this run's stdout is write-through), and exit with its code (kitlib/gate/pin.py `run`, called before the tool's own imports):

- **Where.** `<plugin export root>/pins/<sha12>`, the export root of docs/plugin-source.md "Layout" (`plugin.export_dir`, default `%LOCALAPPDATA%\pm-kit\plugin`). The export is made once per commit by `kitlib.pluginsource` `export` (marker `made_by` `kitlib.gate.pin`), under `pins/refresh.pid`, waited for up to 60 s (`pin.LOCK_WAIT_S`).
- **Leases.** Each pinned run holds `pins/leases/<sha12>-<pid>.json` (`{sha, pid, ctime, child_pid, child_ctime}`) while it runs, and removes it when the tool ends. Each pin, under the lock, prunes (`pin.prune`): it removes the leases whose processes are both gone and every `<sha12>` export holding the marker that no live lease holds, except the commit it runs, and every `<sha12>.tmp`. A lease file that cannot be read is removed once older than 10 s (`pluginsource.LOCK_GRACE_S`); younger, the export its name starts with is kept. A lease that reads but is malformed (a pid or child_pid that is not a positive int a process id can be, 32 bits at most, or a ctime that is not an int; `pin._malformed`) is dead, so it never makes the pin fail open nor holds an export (tests/gate/test_live_pin.py `test_a_malformed_lease_is_dead_and_the_pin_still_made`, `test_a_lease_pid_past_a_process_id_is_dead`, `test_a_lease_with_a_malformed_child_pid_is_dead`).
- **Environment.** The child gets `KIT_PINNED=<sha>` and `KIT_LIVE_ROOT=<the main checkout>`. Any `KIT_PINNED` value means run live, so the child, and every tool it starts, never pins again. A command the tool prints (the gate, sweep, lock-break and backlog commands) names `KIT_LIVE_ROOT`, never the export, which a later prune may remove (`kitlib.pluginsource` `live_root`, honoured only when the running kit folder holds the export marker; `steps.kit_live`, `at_landing.backlog_py`, `kitlib.stubs.kit_root`). The gate's own `{here}` runs (`steps.KIT_TOOLS`) use the export; `{here}/kit_stubs.py` runs from it but checks and writes stubs against `KIT_LIVE_ROOT`. `gate.py`'s own-copy refusal (The caller's checkout) compares against `KIT_LIVE_ROOT`.
- **Runs live.** A run with `KIT_PINNED` set, a linked worktree (its `.git` is a file), an export (it has no `.git`), and a checkout with no remote-tracking main run the code they are in, with no line.
- **Fails open.** When the pin cannot be made (the export root refused, the tracking ref unreadable, the lock busy past its wait, the export failing, no `tools/<name>.py` in it), stderr gets `WARNING: pin: running the live checkout's code: <why>`, `KIT_PINNED=live` is set, and the tool runs from the main checkout as before. Once the child has started nothing fails open, so the tool never runs twice. Ctrl+C while pinning exits 130 with the tool not run. From just before `Popen` until the child exits, the parent ignores Ctrl+C (SIGINT set to SIG_IGN on the main thread and the handler before put back after, `pin._ignore_ctrl_c`; off the main thread nothing changes), so a Ctrl+C inside `Popen`, or before its result is assigned, cannot exit 130 and drop the lease while the child runs: the parent waits for the child, exits with its code and keeps the lease until it exits (tests/gate/test_pin_sigint.py `test_ctrl_c_inside_popen_after_the_child_started_waits_for_it`; a Ctrl+C raised during the rewrite of the lease, `test_ctrl_c_once_the_tool_started_waits_for_it_and_keeps_the_lease`, or as the handler comes back, `test_a_ctrl_c_as_the_handler_comes_back_keeps_the_tools_code`, is the child's too; an error putting the handler back once the child has exited keeps the child's code, `test_a_restore_that_fails_after_the_tool_ran_keeps_its_code_and_does_not_fail_open`). Two limits: when the current handler cannot be read (`signal.getsignal` gives None: one not set from Python) nothing is changed either, and that gap stays; and a Ctrl+C in the instant after the parent starts ignoring it and before the child is attached to the console is lost, so the tool runs whole (press again). Ctrl+C reaches the child through the shared console, and it stops itself as the tool does unpinned: a child does not inherit its parent's SIG_IGN, measured with a real console Ctrl+C (`test_a_child_of_a_parent_ignoring_sigint_still_gets_ctrl_c`). The console-level ignore, `SetConsoleCtrlHandler(NULL, TRUE)`, is inherited, and a test run from an agent's shell had it already (measured 2026-10-11: no child there was interrupted until the test's helper cleared it), so from such a shell no Ctrl+C reaches either process.
- **Identity.** Run from an export, `runner.kit_identity` (the gate-OK record's `kit`) is the marker's commit, clean. The gate cache keys on the kit's file hashes instead (`reuse.kit_identity`, Gate reuse), so an export and a checkout of the same files are one kit.

Tests: tests/gate/test_live_pin.py. The gate tests' environment sets `KIT_PINNED=live` (tests/gate/fixtures.py `test_env`), so a tool a test starts in a main checkout runs that tree's code, never an export under the real export root.

### The landing queue

Landings into one repository take turns through the machine lock's store: the queue is the exclusive resource `landing:<git common dir>` in `resources.json` (kitlib/lock/resource.py; docs/lock-api.md "Exclusive resources"), so every checkout of a repository shares one queue. A landing joins at the back. Only the first entry has the turn, and no later landing goes ahead of an earlier one, however often it looks (`Lander.poll_s`, 5 s). No landing is ever pre-empted. At its turn the landing takes the lock file:

- **Free:** taken.
- **Held at phase `stuck`:** BUSY at once; a stuck landing is cleared by hand from its STUCK report.
- **Held by a process that is gone** (pid and start time, `LandingLock.holder_state`): when nothing is unpushed, the lock is broken (`LandingLock.break_lock`), said as `broke the landing lock of a holder that is gone ...`, and taken. When main differs from the tracking ref `<remote>/<main>`, or a merge is in progress (`LandingLock.unpushed`), it is never broken: BUSY at once, naming what is unpushed and the break command. When main is only behind the tracking ref, with nothing unpushed, BUSY says so and gives the fast-forward, `git -C <root> merge --ff-only <remote>/<main>`; the next landing then breaks the lock itself.
- **Unreadable or of an old format** (`LandingLock.read` fails): waited for like a live holder, never broken; BUSY with lane `?` when `--wait` runs out. A taker killed between its create and its write leaves an empty lock file for good, and `LandingLock.break_lock` refuses an empty, unparseable or unreadable file even with `holder_gone=True`: delete such a file by hand, and only once `land.py --queue` shows no landing running.
- **Held by a live process, or by a token holder** (a tool outside the queue): waited for.

A queue entry lives while its process holds the entry's run mutex, as a lock run's queue entry does, so a landing that dies leaves an entry the next look drops. The turn is given up with the lock and whenever the landing ends; STUCK included, since the stuck lock file keeps the next landing out. `land.py --queue` prints the lock and the queue without joining it.

An unreadable `resources.json` (kitlib/lock/resource.py `ResourceUnreadable`) is never read as empty, so every landing in every repository is REFUSED (`the landing lock: ...`) until it is repaired: with no landing running, rename it aside (never delete it) in the machine lock store, the `.claude/machine-lock` folder of the user profile (kitlib/lock/store.py); the next landing to join writes a new one.

### Batch

`land.py A B --expect-tip TA --expect-tip TB` lands A and B as one landing: each passes the locked checks, they merge in the order given (`Merge A: <summary>`, then `Merge B: <summary>` on top), the merged tree is gated once against `--expect-main` (log slug `A+B`), and the last merge is pushed. A conflict on any branch aborts it and undoes the earlier merges; a red gate undoes them all. A branch whose tip is already inside another tip of the batch is refused: land the containing branch alone. Each branch gets its own result record (`facts['result_record']` is then a list). The verdict line names the branches joined by `, `. At most `"landing".batch_max` branches (default 3).

### Gate reuse

kitlib/gate/reuse.py: a per-step cache of gate results, read and written by a branch gate (a rerun reuses) and by a landing's merged-tree gate, a batch landing included (`reuse.branch_plan`, `reuse.planner`). The opt-in and the never-list are ported from one repo's gate reuse. A step with `reuse` is not run when a pass of its key is stored within `"landing".reuse_max_age_h` hours and no fail or warn of that key is. It is fail-closed: any doubt or error runs the step, and its `gate: reuse:` line says why.

**The key** (`reuse.step_key`) is the sha256 of the canonical JSON of:

- the step's name, argv and cwd, with the checkout's root written `<root>` and the kit's `<kit>` (so a worktree and the main checkout make one key, and the landing's `merged_args` another);
- the sha256 of its program (`shutil.which` of argv[0]; not found: no reuse) and of every argv element that names a file relative to its cwd;
- `gate_ok.config_hash` of the gate config (`runner.gate_config`);
- the kit's identity, `reuse.kit_identity`: the hash of every file under the kit's `kitlib/` and `tools/` (bytecode left out), the interpreter's path and `sys.version`. Never the kit's commit: two commits with the same files are one kit;
- its inputs (`reuse.inputs`): every file `git ls-files -c -o --exclude-standard` shows in the work tree (tracked, or untracked and not ignored) that matches its `globs` or its `content`.globs (its `exclude` is not subtracted), by sha256; a tracked file deleted in the work tree is `absent`. An input that is a link or a folder (a nested repository or submodule) means no reuse.

**The opt-in's contract.** `reuse` is a promise that the step's result depends on nothing outside its key. A step that asks for it must therefore:

- read only files its `globs` or `content`.globs match. A file git ignores, or one an earlier step or the build generates, is never an input: a step that reads one must not ask for reuse (tests/gate/test_reuse.py `test_an_ignored_file_under_the_globs_is_not_an_input` shows such a file changing and the step still reused);
- not depend on environment variables, installed SDKs, packages or tools other than its program and the files its argv names, the network or the clock: none of these is in the key;
- not depend on git state (HEAD, refs, the index, commit messages): none of it is in the key, and a pass stored on one commit serves any commit with the same input files;
- not need what it leaves behind: a reused step does not run, so nothing it would leave (a build output, a file a later step reads) exists. Give a step whose output a later step needs the same group as that step.

A reused step's `requires` probe is not run either (`runner._to_run` leaves the step out of the run): it counts as `reused` where a missing requirement would have skipped it.

**Never cached**: nothing is read or stored, every asking step runs and says `NONE <step>: <why>`:

- for one step: a check step, a step with no `globs` and no `content`.globs, a step whose `cmd`, `full_cmd`, `daily_cmd` or `merged_args` names `{base}` (it reads git history), or whose argv holds the base commit (`reuse.undeclared`); globs that match no file git shows (a mistyped glob, or one naming only ignored files, would key the step on its command alone; `reuse.step_key`), an input that is not a plain file, or a program not found (`reuse.NotCacheable`);
- for the whole gate: `--full`, a branch gate's `--only`, `"landing".reuse_max_age_h` 0, a change (the branch gate's changed paths, or a landing's `--expect-main..merge`) touching `.kit.json`, a config section file, the hook module or a `"landing".reuse_never` path, or a strict path (kitlib/gate/strict_defaults.py `STRICT_DEFAULTS`, imported; `reuse.strict_hits`). A branch gate's `--base X` narrows its changed paths to those since the merge base with X (`runner.changed_since`), so these checks do not see a path changed before X;
- in a landing also (`reuse.landing_why`): `--fresh`; a result record that cannot be read; a `land` record of a tip (an earlier landing that did not land: its tree is gated again); a `gate` record of a tip whose verdict is not `pass`; a main checkout that is not clean;
- anything that raises while planning: `NONE <step>: <Type>: <message>`.

**The lines**, one per asking step, in order, each starting `gate: reuse: `:

- `HIT <step>: key <first 12 hex>, stored <UTC time it was stored>`, then `REUSED <step>: passed on the same inputs (key ..., stored ...)`;
- `MISS <step>: <why>`: `no result stored for key ...`, `no pass within "landing".reuse_max_age_h (<h>) for key ...`, `failed or warned on these inputs at <time> (key ...)`, an entry that cannot be read, or `<steps> of its group <group> runs` (a group is reused whole or not at all);
- `NONE <step>: <why>` as above;
- after the run, for each step that missed: `STORED <step>: pass|fail, key ...` (PASS is stored as pass, FAIL and WARN as fail; a skipped step stores nothing), or `NOT STORED <step>: its inputs changed while the gate ran`, or `NOT STORED <step>: its key changed while the gate ran (the kit, a program or the config)` (the key is made again after the run and must be the same: a step that writes its own inputs, or a kit edited meanwhile, stores nothing), or `NOT STORED <step>: <Type>: <message>`. A failure to store never fails the gate.

The lines go to `reuse.log` in the log folder. A reused step's result is `reused` (in the verdict `reused: <steps>`, and in the gate-OK record's `steps`). When every selected step is reused, nothing is booked and `setup` does not run. A step that asks for no reuse says nothing, and no `reuse.log` is written.

**Storage.** `<git common dir>/kit-gate-cache/<key>/<YYYYmmddTHHMMSSZ>-<pid>-<hex8>.<pass|fail>.json` (`reuse.cache_dir`, `reuse.ENTRY_RE`), shared by every checkout of the repository, written to a temp file and renamed into place. An entry whose body does not match its name (schema, key, result, time) is a miss. A pass stored more than 60 s in the future (`reuse.SKEW_S`) is not counted; a fail is. After each gate that could store (one with an asking step that was keyed), entries older than 168 hours (`reuse.PRUNE_H`) are pruned (`reuse.prune`): only names matching `ENTRY_RE`, as plain files, in folders named by a key that are plain folders inside the cache; a link or junction is never followed, and other files are left. A temp file (`reuse.TMP_RE`) last written more than 168 hours ago, left by a crash between the write and the rename, is pruned the same way; a newer one stays, since another gate may be writing it. Key folders left empty are removed. A prune that fails says one `gate: reuse: prune: ...` line and the gate goes on.

In the kit's own repository no step asks for reuse (`.kit.json` "gate", its one step `kit-suite`, has no `globs`). Tests: tests/gate/test_reuse.py.

### Branch cleanup

kitlib/gate/cleanup.py runs in the landing (`Lander.clean_up`) once the push is verified, the lock released and the backlog records closed: never on a landing that did not land. For each branch, three parts, each judged on its own:

- **Remote branch.** Deleted when main contains its tip: `git push --force-with-lease=refs/heads/<branch>:<tip> <remote> :refs/heads/<branch>`. The lease is a compare-and-swap, not a force: the remote deletes the branch only while it still points at the tip read just before, so a branch pushed to since is refused and kept. `git ls-remote` must then show it gone.
- **Worktree.** Removed by kitlib/worktree/remove.py, the code `worktree_remove.py` runs (docs/worktree-remove.md): under the worktrees folder, landed in `<remote>/<main>`, nothing holding it, nothing uncommitted, untracked or ignored outside build output, no link inside; then `git worktree remove`, never forced. That code then deletes the local branch with `git branch -d`.
- **Local branch** with no worktree: `git branch -d`, never `-D`.

Nothing is forced. A tip main does not contain, a worktree with work in it, a worktree in use, and anything git refuses are kept. Each kept part is named on a `  kept` line under the branch's `cleanup   <branch>: ...` line, and the landing still counts as landed. A branch never pushed has its remote branch `absent`. The result record's `cleanup`, and the landing's `facts['cleanup'][branch]`, hold `remote_branch` (`deleted`, `absent`, `kept`, `skipped`), `worktree` (`removed`, `absent`, `kept`, `skipped`), `worktree_path`, `local_branch` (`deleted`, `absent`, `kept`, `skipped`) and `kept` (one reason per kept part). A local branch git gives no answer for after its delete is `kept`, with "whether it is gone could not be read", never `deleted` (kitlib/gate/cleanup.py `_left`). `--keep-branch` skips all three (`skipped`). An exception in one branch's cleanup is a WARNING and the next branch is cleaned; Ctrl+C stops it with a WARNING. Both name the sweep command, and so does a landing stopped after its verified push (`Lander.landed_anyway`).

`land.py --sweep-landed [--apply]` applies the same rule to every branch, local or on the remote, that main already contains: it fetches `<main>`, and takes a tip in `<remote>/<main>` and off its first-parent line (a branch made from main with no commit of its own is never one). Branches main does not contain are not named. It does nothing while a landing holds the landing lock (BUSY). A dry run, the default, names what would go and ends with the `--apply` command. The landing cleanup and the sweep delete a remote branch only by the lease push above and a local branch only with `git branch -d`; guard.py gains no allowance for an agent's `git branch -D` or `git push --delete`.

## The caller's checkout

A stub run from outside its checkout runs the kit tool in the stub's checkout (docs/install.md "Stubs"), so a shell in one checkout that runs another checkout's gate stub would gate that other checkout. The stub then passes `[stub checkout, caller directory]` on in `KIT_STUB_CALLER`; `tools/gate.py` removes it, so no step inherits it, and for a branch gate (`--plan` included) applies kitlib/gate/caller.py `refusal`:

- The caller's directory is in a different checkout from the gated one (their git dirs differ): `REFUSED: the caller is in the checkout ...`, exit 4, nothing run, no record.
- The caller's directory is in no repository, or is in the gated checkout: it runs.
- git cannot place the caller's directory or the gated tree, or the variable is malformed (a NUL in either path counts): REFUSED (fail closed).
- An absolute `-C` names the tree, so it runs. A relative `-C` resolves against the stub's checkout, not the caller's directory, so the rule applies to it. Without a stub the gate runs in the caller's directory and this rule never applies (the no-stub rule below does).
- A value whose stub checkout is not the gate's own directory was inherited from a stub further up, not set for this process: it is dropped and the gate runs. The two are compared as one directory (os.path.samefile), so a junction, symlink or 8.3 short name for the checkout still counts as its own.

With no stub there is a second hazard, in the kit's own repository: every checkout has a real `tools/gate.py`, so `python <worktree>/tools/gate.py` run from the main checkout with no `-C`, or with a relative one such as `-C .`, would gate the main checkout with the worktree's code. For a branch gate run with no stub and no `-C` or a relative one, `tools/gate.py` applies kitlib/gate/caller.py `own_copy_refusal` to the tree it would gate (the directory it was run from, or where the relative `-C` resolves) and its own checkout (`KIT` in tools/gate.py, the same directory as kitlib/gate/steps.py `KIT_ROOT`):

- The two are different checkouts of one repository (the same git common dir, different git dirs): `REFUSED: <gate.py> is in the checkout ...`, exit 4, nothing run. Each following line gives the documented command, `python <tree>/tools/gate.py -C <tree>`, for one tree, with a path that holds a space in double quotes. A relative `-C` names the tree meant, so only its line is given, headed `  to gate <tree>:`. With no `-C` the tree meant is ambiguous (the gate.py's path names one checkout, the directory another), so both are given, headed by intent: `  if you meant the directory you ran from:` (the checkout the directory is in) and `  if you meant the checkout this gate.py is in:`.
- An absolute `-C` names the tree on purpose and is not checked: main's gate.py with an absolute `-C <worktree>` runs main's code on the worktree.
- They are the same checkout, the gate.py is in another repository (a repository's stubs run the kit checkout written into them, kitlib/stubs `KIT_ROOT`), or either is in no repository: it runs.
- git cannot place the gate.py's checkout (dubious ownership, a git timeout): REFUSED only when its path nests (one inside the other) with the gated checkout or with the folder that checkout's git common dir is in, so the two could be one repository's checkouts; the command lines follow as above. A sibling that only shares a name prefix (`main-co-x` beside `main-co`) does not nest. Otherwise it runs, as a repository's gate did before this check. A directory git cannot place is left to the gate itself.

A relative `--log-dir` resolves against the directory the gate was run from, not the gated tree, so when that directory is in another checkout the logs would be stray files there: kitlib/gate/caller.py `log_dir_refusal` makes it `USAGE: --log-dir <D> is relative ...`, exit 2, nothing run. An absolute `--log-dir`, none, or a directory in no repository passes.

The one documented way to gate a worktree from another directory is that worktree's own gate.py with an absolute `-C` naming it:

```
python <worktree>/tools/gate.py -C <worktree> --full
```

Running the worktree's own gate.py matters in the kit's repository: the gate records the identity of the kit that ran it (the gate-OK record's `kit.commit`, `runner.kit_identity`), and the code under test is the code that gates.

Landings, `wait-result` and `--measure` apply neither rule. Tests: tests/gate/test_caller_checkout.py (`Refusal` and `ThroughAStub` for the stub rule; `OwnCopy`, `LogDir` and `RunByPath` for the no-stub rule and `--log-dir`).

## Known limits

- No per-step timeout. A step that hangs is ended by stopping the gate (Ctrl+C, or the machine lock's stop, which ends the slot's job).
- The hook module's module-level code runs when it is loaded, before the gate is booked. It runs outside the slot, and a `sys.exit` there is REFUSED.
- Files git ignores, and files marked assume-unchanged or skip-worktree, are outside the record. The clean-tree checks do not see them.

## Go-live notes

- A repo's Python tests must be steps (`python_tests: discover` is the default and runs nothing by itself).
- Turn on `push_block` only after the repo lands through `gate.py land`.
- Once switched, delete the retired tools (ARCHITECTURE.md "Details").
- In a landing, only the hook module's own file comes from `--expect-main`; a hook module that imports sibling files from its tools folder is not supported there (kitlib/gate/hookrev.py). Its `__file__` is its path in the merged checkout, so a hook that reaches files beside itself through `__file__` reads the merged tree's copies, not the base's; its tracebacks and GATE_CHECKS errors name `<rev10>:<path>`.
- A `landing.log_dir` inside the repo must be gitignored. Otherwise the gate's logs are untracked files: a branch gate writes no record, and a landing is NOT LANDED (Landing, step 7).
- Without `landing.log_dir`, gate logs go to `<kit temp>/<repo>-gate/<branch>/` (kitlib.gate.runner.log_base over kitlib.config.user.work_temp; docs/test-tools.md "Temp folders"), never an inherited TEMP, so agents and the owner's shells read the same folder. When that base cannot be made, or the machine config cannot be read, the run's logs go under `runner.fallback_log_base` (`%LOCALAPPDATA%/Temp/<repo>-gate`) with a `gate logs:` note on stderr (`runner.make_log_dir`, which redfirst and daily-full use too); landed.py reads it as well. A Windows process without LOCALAPPDATA and with no usable drive root stops with a RuntimeError instead of falling back to TEMP.
- The gate prints its verdict to stdout only, so landed.py finds one only where a caller saved that output under the gate log folder (docs/landed.md).
- A lander's post-merge stray check: `python <kit>/tools/checkout_guard.py --main-stray --allow-tracked <main checkout>` (exit 1 on any stray, or when git could not tell; docs/preflight.md).
- Doc budget check: `[sys.executable, <kit>/tools/doc_budget.py, -C, <repo>]`, judged with kitlib.verdict (`DOC BUDGET OK` / `DOC BUDGET FAILED`). Exit 2 means refused or a usage error; see docs/doc-tools.md.
- There is no keep-red option. A red merge is always undone by default.
