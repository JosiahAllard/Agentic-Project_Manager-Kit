# Machine lock API

`kitlib/lock/api.py` is the one way any UI reads or changes the machine lock. The UIs are `tools/machine_lock.py` (`status --json` prints `snapshot()`) and, for reads only, the lock MCP server, `mcp/lock_server.py` (docs/lock-mcp.md; it has no write tools, by the owner's decision). The Action Hub server reads and changes it in-process too, by the owner's decision: `kitlib/hubsite/lockdoor.py` calls `revision()`, `snapshot()`, `history()` and `stats()` for the hub's owner-only lock routes, and the owner's writes (`hold_create`, `hold_edit`, `hold_end`, `end_run`, `move_to_top`, `set_game_mode`, `set_games`, `set_division`) as the actor `hub` or `hub-tunnel`, which `who()` judges by the hub's own process (docs/action-hub.md "Machine lock routes"). `set_owner_check` stays as it is.

- Calls are plain functions. JSON-ready dicts go in and out, and there is no transport.
- The schedule window, `reserve_ui.pyw` (kit root) (logic in `kitlib/lockui/`), reads with `snapshot()` (with an empty stats range: it shows no stats) and `history()` (again only when the history files' sizes or times changed, or on Refresh) and makes every change with the write calls below. Owner writes go through only when the owner runs it (Who may, below).
- Every call takes an optional `store` (a `kitlib.lock.store.Store`). The default is the machine's store.
- `SCHEMA_VERSION` (now 1) changes only when a key changes meaning or goes away. Added keys leave it alone.
- Runs: a `docker exec` run (`run` or `background`) that holds no gpu slot gets `-e CUDA_VISIBLE_DEVICES= -e JAX_PLATFORMS=cpu` right after `exec`, unless the caller sets that variable with `-e`/`--env` itself (`kitlib.lock.run.docker_cpu_env`). A run's id (`r-<UTC second>-<6 hex>`, `kitlib.lock.store.new_id`) is claimed before any of its records is written (`kitlib.lock.run.claim_id`, called by `book` and `kitlib.lock.background.run_background`): it holds the id's run mutex, then looks for `active/<id>.json`, `active/<id>.stop`, `ended/<id>.json` and `background/<id>.d`. An id whose mutex another holds, or with any of those left, is taken. A drawn id that is taken is drawn again, up to `CLAIM_TRIES` (16) times, then exit 10 ("no free run id"). A given id (`--detached-id`, `book(rid=)`, `run_background(rid=)`) that is taken is exit 10 ("run id <id> is taken"), and one not shaped as a run id is exit 2 ("not a run id"); either way nothing is written, so a live or ended run with that id is untouched. Tests: `tests/lock/test_run.py` `RunIds`, `tests/lock/test_background.py`, `tests/lock/test_detach_cli.py`.
- Detached runs: `machine_lock.py run|background --detach` asks WMI (`Win32_Process.Create`) to start the `pythonw.exe` beside the `python.exe` (`detach.pythons`, not the hooks' helper, which falls back to a console python and would widen the lock tool's import reach) running the kit's carrier `tools/no_window.py` by its path, which starts the `python.exe` beside it running `machine_lock.py` with `--detached-id <run id>` (`kitlib/lock/detach.py` `command`, `create`). WMI's process is in neither the caller's process tree nor its job, so the run outlives the caller's shell; `pythonw.exe` has no console, so the run gets a console with no window (docs/daily-full.md "The schedule"), and nothing rests on `Win32_ProcessStartup.ShowWindow`. It prints `<run id> pid <pid>`: the pid of that `python.exe`, the run's wrapper and the run record's `pid` (`wrapper_pid`), or the carrier's pid when that python was not seen within 10 seconds. A missing `pythonw.exe`, carrier or `python.exe` is exit 1 with "could not start the command: --detach: <what> is not a file: <path>". A carrier that cannot start its `python.exe` writes one line to the kit's console incident log (`kitlib.proc.console.note_carrier_failure`). Tests: `tests/lock/test_detach.py`, `tests/proc/test_console.py` `CarrierFailureLine`, `tests/lock/test_detach_cli.py` (`DetachEndToEnd` starts a real detached run and finds no console window). The guard sees only the `machine_lock.py run --detach` call, the kit's own lock run (`tests/guard/test_kit_tool_forms.py`); the chain WMI starts is no shell call. The launcher draws the id (`machine_lock.py` `detach`) without looking at the store; the child claims it like any run (Runs, above), so an id that turns out to be taken refuses the child with exit 10 and no record, after the launcher has printed the id and exited 0.
- On Linux the store's named mutexes are flocks on files in the store (`locks/<name>.lock`; a run's liveness lock is `runs/<run>.alive`; `kitlib.platform.linux.locks`), and the store root is under the profile folder from the password database, never `$HOME` (`kitlib.lock.store.profile_dir`). A run's liveness reads from /proc (`store.wrapper_state`). `--detach` goes through `kitlib.platform.linux.detach`: a setsid trampoline, the run in a systemd user scope of its own where there is one, with no WMI and no carrier (`kitlib.lock.detach`). The Windows-only text below (WMI, `Global\` mutexes, `pythonw.exe`) does not apply there.

## Reads

| call | returns |
|---|---|
| `snapshot(store, history_days=7, since=None, until=None)` | The Snapshot below. |
| `revision(store)` | The store's revision alone (`Store.revision()`, an int that moves on every write), for a caller that only asks whether anything changed: no snapshot is built. |
| `wait_change(revision, timeout_s=30, store)` | The snapshot once the store's revision moves past `revision`, or after `timeout_s`. It polls every `settings.wait_change_poll_s`. Live use (cpu, memory) can move without a new revision. |
| `stats(store, days=7, since, until)` | The snapshot's `stats`. `since` and `until` are ISO times with their offset; a bad one raises `ApiError` (`invalid`). |
| `history(store, days=7, since=None, until=None)` | The runs that ended in `[since, until)` (default: the last `days`), oldest first, one store history line each (`held_s`, `wait_s`, `partial`, `background`). Each history line (history/YYYY-MM.jsonl, returned by api.history) also carries `session` and `role`, who started the run (null when unknown), and `stopped_by` ({by, session}, from the stop request; null when none was made). These add information only and change no permission or refusal. A bad time or a non-numeric `days` raises `ApiError` (`invalid`). |
| `run_record(id)` / `hold_record(id)` | One run or hold, live (`live: true` / `live_record: true`) or ended, or `None`. When the holds cannot be read, `hold_record` returns the write error result (`store`, below), never `None`; so does `run_record` when the run's live record is there but stays unreadable for `settings.queue_read_s` (`end_run` too, rather than "no live run"). An id must be one the lock makes (`kitlib.lock.store.ID_RE`, whole string, `r-` for a run, `h-` for a hold); any other is the `invalid` error result, since the id names a store file. |

### Snapshot

`schema_version`, `revision` (the store's write counter), `at`, `store`, plus:

- **`hardware`**: `threads`, `thread_ids`, and `groups` (processor groups; more than 64 logical processors).
  - `cores` [{threads, smt, efficiency}].
  - `ccds` [{index, threads, cpu_slots, preferred, game_pick}], one per L3 domain. `preferred` marks the domain holding the best efficiency or scheduling class. `game_pick` marks the one game mode takes.
  - `preferred_threads`.
  - `memory_mb` {total, free}.
  - `gpus` [{index, name, vendor, vendor_id, vram_mb, shared_mb, source, default_share}], any vendor, from DXGI or CIM on Windows, from sysfs on Linux.
  - `source` and `problems`.
- **`layout`**: the layout in force.
  - Its shape: `key`, `threads`, `cpu_slots`, `cpu_slot_threads`, `slots_cpu`, `gpu_slots`, `gpu_cards`, `gpus`, `half`, `agent_cap`, `medium_cores`, `l3_slots`.
  - `division` (in force), `default_division`, and `wanted_division` / `wanted_key` (the owner's machine.json division on this hardware), and `owner_division` (only the keys machine.json sets, `{}` when none; a dialog prefills from it so saving pins no derived key).
  - `source` (`config` or `default`) and `warning`.
  - `hardware_change` {changed, pending, reason} and `other_labels` (below). When `changed` is true, the wanted layout (`wanted_key`) differs from the one in force (`key`), and it is adopted once nothing is live or queued, unless it comes from a look that failed (below). `pending` is null when nothing waits; otherwise it is text that says why the layout in force is not the wanted one, or why it is not final. The rules, all in `layout.in_force`:
    - A look at the hardware that failed never replaces a layout.json written from a good look, live runs or not. `layout.detect` names what it read as a stand-in in `failed`: "groups" (Windows did not list the processor groups, `kitlib.proc.cpu.listed_groups`, so group 0 alone, its system mask, stands in without the groups being asked again, and on a machine past 64 logical processors its threads are fewer than the machine's; on Linux, `cpu/online` could not be read and the process's affinity stands in), "cores" or "gpus" (`tests/lock/test_layout.py` `DetectFailed`, `GroupsStandIn`). `pending` then starts "the <parts> could not be read", the parts joined as a list ("the gpus", "the cores and gpus", "the groups, cores and gpus"), and says no layout is adopted from that look (`tests/lock/test_layout.py` `FailedDetection`). The snapshot carries no failure flag: `hardware.problems` holds the detail, but it also holds notes that are not failures, such as "CIM used".
    - With no valid layout.json, a failed look's layout is written as before, marked `"provisional": true` in layout.json, so the runs booked on it keep their numbering. It is replaced under the ordinary rule, once nothing is live or queued, by a good look or by another failed look (a division change on a machine whose look always fails). A good look with the same key makes it final at the next call that may write, without waiting for an idle machine, since nothing is renumbered. `pending` carries the provisional text ("... is provisional: the first look that succeeds replaces it ...") when a failed look writes such a layout, or finds one with its own key. Other cases get the text of the rule that applies instead:
      - While a different layout waits for an idle machine, `pending` has the change-wait text.
      - When a failed look finds no valid layout.json under live runs, nothing is written and `pending` has the "layout.json is missing" text.
      - When a good look with the same key comes from the snapshot, which never writes, `pending` is null.
      - The tests are in `tests/lock/test_layout.py` `FailedDetection`.
    - A layout.json that is missing, unreadable or invalid to this kit version is rewritten only once nothing is live or queued (`tests/lock/test_layout_mismatch.py` `InvalidLayoutUnderLiveRuns`). Until then the wanted layout is used without being written. Limit: that unwritten layout is recomputed on each call, so a division change or a different look at the hardware applies to it at once, under live runs too: for example, a failed look and then a good one once a process's cached look expires (`layout.CACHE_S`). The runs live then may count their slots from another numbering. When the queue cannot be read, layout.json is not rewritten and `pending` starts "the layout could not be checked".
    - The snapshot's look writes nothing and does not read the queue. For an invalid layout.json it shows `changed` false, and `pending` null or, after a failed look, the provisional text.
    - `kitlib/lock/status.py` `pending_reason(pending)` reads the reason from that text: null when nothing is pending; `idle` (a changed layout waits for an idle machine); `unwritten` (layout.json missing or invalid, written once nothing is live or queued); `failed_look` (a failed look, the layout from a good look stays); `provisional` (the layout in use came from a failed look; also when that look keeps failing, so nothing waits for idle); `unchecked` (the queue or store could not be read); `other` (a text this kit does not give). `waits_for_idle` is true for `idle` and `unwritten`. It matches the `layout.PENDING_*` constants that `in_force` builds its texts from. `tests/lock/test_status_reason.py` drives each `layout.in_force` branch through it. `hardware_change.reason` and `set_division`'s `reason` carry its value (`tests/lock/test_api.py` `Division`).
    - `tools/machine_lock.py division --set` prints that `pending` text when the division is not in force, or is in use but provisional or unwritten. `machine_lock.py status` prints it as a `layout:` line when it is not a wait for an idle machine (`waits_for_idle`).
    - The schedule window says the reason, `hardware_change.reason` (or `pending_reason` of `pending` for a snapshot without one), in its warnings and the Division dialog (`kitlib/lockui/model.py` `layout_wait`): "a new division waits until nothing runs or queues" for `idle` (and for a `pending` or `changed` it has no text for), a sentence of its own for `unwritten`, `failed_look` and `provisional`, and the `pending` text itself for `unchecked` and `other` (`tests/lockui/test_model.py`, `tests/lockui/test_window.py` `test_the_division_dialog_says_a_failed_look_as_one`).
  - A run record's `layout` is `layout.slot_key`, not `key`: a label of the slot numbering only, `t<threads> g<cards> cpu <cpu slots> x <threads per slot> gpu <gpu slots> m<hash>`.
  - What the label is: `g` is the layout's `gpus`, the cards of `hardware.gpus` that `layout.derive` gives a share (the division's `gpu_share`, else each card's `default_share`). `gpu` is `gpu_slots`, which is 1 with no shared card (the placeholder slot). The hash covers the cpu slots only. `tests/lock/test_layout.py` pins the text for one card, two cards and none.
  - What it is not: nothing in this kit decides on it. `run.book` counts slots from layout.json (`layout.in_force`), and a live record with another label never refuses a booking (`tests/lock/test_layout_mismatch.py`). It does not say which cards the gpu slots are; `gpu_cards` does.
  - `other_labels`: the labels of live runs other than this layout's own, each once, sorted (`layout.other_labels`); `[]` when none. Every writer in this kit labels its runs from the one layout in force, so on one machine a label here means an older writer shares the store and counts its slots its own way. The one exception is brief: a run booked while another process adopts a new layout keeps its first-look label until it re-saves under the new one (`book` in `kitlib/lock/run.py`), and shows here until then. `status` then prints one WARNING line naming them, each label quoted and escaped (`repr`), so a label cannot break the line (`tests/lock/test_api.py`).
- **`slots`**: {cpu: [...], gpu: [...]}, one per slot.
  - {slot, holder (run id), background, hold (the hold id covering it now), hold_owner}.
  - cpu slots add `threads` and `pinned`; gpu slots add `card`.
- **`runs`**: every live run (waiting, held or background): a record in `active/` whose wrapper is live (`Store.run_live`, the same test `run_record` and `end_run` use).
  - Its pid and creation time decide when they can be checked (`store.wrapper_state`): a running process created then is live; no such pid, an exited one or another creation time is gone.
  - When they cannot (a process this user may not open, which a reused pid can name, or a record with no creation time), the run mutex decides: the wrapper holds it from before its record is written until after the record leaves `active/` (`run.claim_id`, `run.settle`), so one that does not exist (`ERROR_FILE_NOT_FOUND`), is abandoned or is unowned means gone. One that cannot be opened for any other reason (access denied, say), a failed wait on the wrapper, or a record with no valid run id counts as live. A pid alone is never proof of life (`tests/lock/test_reused_pid.py`). Hold claims are checked the same way (`holds.claim_alive`).
  - The mutex is let go even when removing the record from `active/` fails (`store.remove` ignores the OSError). The ended record is written first, so such a record left in `active/` is a run that has ended: while its wrapper process is still alive with that creation time it is still listed; once the process exits it reads as gone.
  - A booking moves every record in `active/` whose run has ended or died (gone by the test above) to `ended/`, once, after its first look at the queue (`run.acquire`, `Store.live_runs(prune=True)`): the queue's prune has by then said which dead runs it dropped, which an ended record would silence (`queue.prune`). A refused booking (busy, `--no-wait`, timeout) may still reap. A run that settled keeps the ended record it wrote; one whose wrapper died without settling gets one with how "reaped", code null and `reaped` naming what showed it gone (its wrapper process, or its run mutex). A reaped run gets no history line (`tests/lock/test_store_fence.py` DeadRecordsReaped).
  - This assumes the checker and every wrapper share the `Global\` mutex namespace (`Store.mutex_name`), so a wrapper's mutex is seen from any session on the machine.
  - The record's id, state, repo, slug, kind, note, pid, ctime, since, held_since, expect_s, expect_from, hold, parent, need, has, shares, pinned, pin, pin_note, threads, child, blocked_by, detached, session, releasing, log and moved.
  - `resource` and `priority`: the run's exclusive resource and its priority (`"land"`), or null; see Run resources and landing priority.
  - `within`: the thread list the run is confined to (`8-15`), or null; see Runs confined to a thread set.
  - `pin` is "pinned", null (no pin) or "overridden": an outer job's affinity limit won, so `pinned` is false and `threads` is what the command really runs on (`kitlib.proc.job.Job.check_pin`).
  - `cores`, `gpus` and `tree` (the pid tree).
  - `usage` {cpu_s, peak_cpu_cores, peak_mem_mb, peak_commit_mb, cpu_cores_now, mem_mb_now}.
  - `gpu_mem_mb`, from NVIDIA only; null elsewhere.
  - `expected_end` and `overrun` {s, planned_end}.
  - Waiting runs add `position`, `est_start`, `backfill` and `moved`.
- **`queue`**: `entries` in plan order [{id, position, ticket, repo, slug, kind, needs, since, expect_s, est_start, backfill, parked, blocked_by, hold, moved, resource, priority, within_slots, why}], and `error`.
  - `moved` is {by, name, at, seq} when the owner moved the entry to the top (`move_to_top`), else null.
  - `resource` and `priority` are the entry's (`kitlib.lock.queue.entry_resource`, `entry_priority`), else null.
  - `within_slots` is the sorted cpu slots the entry may take (`kitlib.lock.queue.entry_within`), else null.
  - `why` is the reason the entry waits. It names first any live run holding the resource the entry names (`resource R is held by ...`).
  - `entries` is null while the queue is unreadable. Then no run takes slots and a new run exits 10 (fail closed).
- **`holds`**: [`kitlib.lock.holds.entry`], and `holds_error`.
  - The record (without ancestors, with its `job`), `start_local`, `end_local`, `covers`, `slots_fixed` and `live`.
  - A hold file that cannot be read, or is not a hold, is never read as absent (`kitlib.lock.holds.HoldsUnreadable`): `holds` is empty and `holds_error` names the file. Until it reads, no run takes slots, a waiting run keeps its place and a new run exits 10 (fail closed).
  - Agent holds add `state` (upcoming, open or claiming) and `lapses_at`.
- **`game`**: `kitlib.lock.game.state`, with fields {enabled, games [{exe, name, pin, anti_cheat}], running, hold, slots, would_take, pinned, anti_cheat_services}.
- **`kinds`**: the kinds table, with `kinds_error`. A kind's `cpu` is a whole number of cpu slots or the alias `medium` or `heavy` (kitlib/lock/kinds.py). A whole number past the layout's `agent_cap` empties `kinds` and sets `kinds_error`.
  - Kind names are generic: `test` (a repository's test run) and `app-run` (a run of the application: a game engine, a live client) replaced `engine-test` and `engine-run`. kinds.json's top-level `aliases` maps each retired name to its kind: a run or hold that passes one books the kind (`kinds.resolve`), and a record written under one compares equal to it (`kinds.canonical`): a hold's claim, `Store.history_expect`, `gate.py --measure` and a landing's booked kind. A record keeps the name it was written with.
  - Known limit: a kit copy from before the rename (an older plugin folder still in use) has its own kinds.json with the old names only. It refuses `test` and `app-run` as unknown kinds, and cannot claim a hold made as `test`. It ends when those copies are retired.
- **`stats`**: {range {since, until}, rows [{kind, repo, runs, done, failed, interrupted, held_s {median, p90, max}, wait_s {median, max}, cpu_s, peak_cpu_cores, peak_mem_mb}]}.
  - The rows come from the history lines (`Store.history_records`) in the range.
  - `failed` means the command exited non-zero. `interrupted` means it was stopped, cancelled or killed.

## Writes

Every write takes `actor`. On the machine's store only its `name` is used: the write reads who is asking from the calling process's tree (`api.who`, below). On a scratch store (tests) `actor` is taken as given. A write never raises for a refusal, and returns one of:

```
{"ok": true,  "result": {...}, "snapshot": {...}}
{"ok": false, "error": {"code": "...", "message": "...", "field": "..." | null}, "snapshot": {...} | null}
```

Error codes:

| code | meaning | CLI exit |
|---|---|---|
| `invalid` | Bad input; `field` names the input key at fault | 2 |
| `forbidden` | `authorize` refused it | 2 |
| `not_found` | No live run or hold of that id | 1 |
| `conflict` | A hold is in the way, or (`move_to_top`) the run has started | 11 or 12 |
| `busy` | Agent holds leave an agent hold too few slots | 6 |
| `store` | The store could not be read or written | 10 |

| call | who | result |
|---|---|---|
| `set_division(actor, division)` | owner | {applied, pending, reason}; `reason` is `status.pending_reason(pending)`. `division` is a dict of `layout.DIVISION_KEYS`; null means every default. It is checked against this machine (`layout.derive`) before it is written. Keys starting with `_` are notes, not division keys: notes already in machine.json are kept (one the division also names takes its value), and machine.json is removed only when it would hold neither keys nor notes. |
| `hold_create(actor, spec)` | owner (owner holds); anyone (agent holds) | {hold, notes}. spec: `owner` (owner or agent), `scope` (owner: whole, half or slots), `start` (ISO with its offset, `Z` or `+hh:mm`; default now), `end` or `for_s`, `note`, `job` (optional: `OWNER` for an owner hold, repo/slug for an agent hold, and any other is invalid). whole names nothing more: it is the owner's, for the owner's own runs; slots adds `slots` {cpu, gpu}; agent adds `repo`, `slug`, `kind`, `gpu_share`. Game holds are game mode's. |
| `hold_edit(actor, id, changes)` | owner; an agent its own agent holds | {hold}. Owner holds take start (before the hold starts), end and note. Agent and game holds take end and note. |
| `hold_end(actor, id)` | owner; an agent its own agent holds | {hold}. A game hold comes back while the game runs, so switch game mode off instead. |
| `set_games(actor, games)` | owner | {games}. [{exe, pin?, name?}]. A missing `pin` defaults off for a title known to use Vanguard, EasyAntiCheat or BattlEye, and on otherwise. |
| `set_game_mode(actor, enabled)` | owner | {enabled}. Off ends a live game hold at once. |
| `end_run(actor, id)` | owner; an agent its own runs | {id, requested}. `id` is a run id (`ID_RE`, `r-`), else `invalid`. It writes the run's stop request and does not wait (the CLI's `stop` waits up to `settings.stop_s`). |
| `move_to_top(actor, id)` | owner | {id, moved {by, name, at, seq}, position}. Moves a waiting run to the front of the queue (`queue.plan`): only a hold's claimer or a nested run plans ahead of it, a later move goes ahead of an earlier one, and no run planned ahead of its turn (backfill) may start where it would delay it. Runs holding slots keep them: nothing is stopped or preempted. The run's record keeps `moved` once it starts. `invalid` for a bad id, `not_found` for a run that is not live (the message says how an ended one ended), `conflict` for one that holds slots. The CLI is `machine_lock.py top ID`; the lock window has a Move to top button on each waiting run. |

## Who may (the one hook)

- `authorize(actor, action, target)` decides every write. It returns None, or the reason for refusing.
- Who is asking is `api.who(actor, store)`. On the machine's store it is `store.caller()`, read from the calling process's tree: the role is agent when any ancestor is an agent host (`store.agent_hosts()`: every registered host's `process_names` in hosts.json for the running platform: claude.exe, which is both Claude Code and the Claude desktop app, node.exe and codex.exe on Windows; claude, node and codex on Linux), or when the tree or hosts.json cannot be read. A chain that ends at an exited process is an agent's: the walk (`process.ancestry`) climbs past an exited hop by the parent its handle records, and a listed parent that cannot be opened ends the walk as not exited. A chain topped by WMI's provider host (`store.DETACHED_LAUNCHERS`, WmiPrvSE.exe: in the chain, or the listed parent the walk stopped at, `store.detached_top`) is an agent's too, while that host is still running under its pid: that is where every process Win32_Process.Create starts sits (`kitlib.lock.detach`: a detached run, a submitted landing), whoever asked WMI. The host exits when idle, and a run can outlive it, so the kit's own detached starts also mark the process they start (`detach.create` sets `store.DETACHED_ENV`, MACHINE_LOCK_DETACHED, which everything under it inherits), and a marked process is an agent's whatever its chain shows. `store.tree_role`, a detached run's role from its launcher's ancestry, reads a launcher that is WMI's host or listed under it the same way; a launcher that is itself marked passes no ancestry (`detach.create` drops MACHINE_LOCK_ORIGIN), and a run with none is an agent's. The session id shown is the first set one of the profiles' `session_env` variables. A role, `force` or a session id in `actor` change nothing, nor do environment variables, except that the marker can make the role agent; it never makes it owner, so setting it gains nothing.
- So the owner's commands run from a terminal outside the Claude desktop app. A command run from the app's terminal panel has the app above it and is an agent's.
- Known limits. A run the owner submits detached (`machine_lock.py run --detach`, `land.py --submit`) is an agent's inside: `caller()` there sees the marker and WMI's host, not the owner's shell. A process started through WMI some other way (not `detach.create`), or one that drops the marker from its environment, reads as the owner once WMI's provider host has exited or its pid names another process: then neither its chain nor its environment shows WMI. A marked launcher's detached run carries no launcher ancestry, so the launcher does not own it for `stop` either. Only WMI's host is named, because a svchost.exe this user cannot open also tops the owner's own chains: the Task Scheduler's (the hub's `tools/hub.py serve`; the daily full run too, docs/daily-full.md "The schedule") and DcomLaunch's (Windows Terminal). The hub's and Windows Terminal's were seen on the kit machine. So a process an agent has started through another broker still reads as the owner: a scheduled task, explorer or ShellExecute, a DCOM activation. Inferred, not tested.
- The owner may do everything. "Owner" means `is_owner(actor)`, which calls the owner check.
- The default check is `default_owner_check`: `role == "owner"` with no agent host (`host`; an actor made before that key was renamed carries it as `claude`, which is still read, `store.actor_host`).
- `set_owner_check(fn)` replaces it, and `set_owner_check(None)` restores the default. This is the only place ownership is decided.
- An agent owns a record when its nearest agent host (its Claude Code process, from `store.caller`) is among the record's ancestors (`store.owns`). A session id, which `snapshot()` shows, grants nothing.
- Ending another session's run is the owner's; the CLI's `stop --force` gives an agent nothing. A run whose wrapper has died is reaped by the lock itself.

## Defaults the owner may swap

- **Overrun (owner decision):** a holder past its expected end is planned to end at now plus half its expected time, re-checked on every pass. The decision lives in `kitlib.lock.queue.holder_end`.
- **Expected time:** a run without `--expect` expects the median held time (at least `history_min_s`) of the runs of its repo, kind and mode that ended `done` (`Store.history_expect`, `Store.run_mode`): `land` (priority land), `branch` (a gate that names its branch) or `other` (also every history line written before a gate named its branch). A mode with fewer than `history_min_runs` finished runs has no history and uses the kind's `warn_min` (`expect_from` "guide"), never another mode's median. Only `kitlib.lock.run.book` calls it; the queue and the lock window read `expect_s` from the records.
- **Whole holds (owner decision):** every hold names its job, and a whole hold is the owner's (job `OWNER`). Only a run the owner started may run inside it: the run record's `role`, read from its process tree (`kitlib.lock.run.run_role`). The earlier open whole hold for agents' runs is gone. The one place this is decided is `kitlib.lock.holds.admits`.

## Giving back slots

A held run can hand back cpu slots its command no longer needs, while the command runs on, so a queued run starts on them at once (`kitlib/lock/giveback.py`; its docstring has the whole protocol). Booking only shrinks: nothing given back is taken again, and the queue order and pre-emption are unchanged.

- Offered to one command only: `machine_lock.py run`'s command (`kitlib.lock.run.run_command`) and a gate's last step (`kitlib.gate.runner.run_steps`), through `MACHINE_LOCK_GIVE_BACK`, the path of the request file `active/<run id>.giveback`. A nested run, a background run and every other command get no offer.
- The command asks with `giveback.Offer.give(cpu)`, or `giveback.drainer(say)` for a pool that drains; the wrapper serves it while it waits on the command (`Slot.serve_give_back`).
- Refused, changing nothing: a malformed request (a `gpu` that is not a list counts), a gpu slot, a slot the run does not hold, every slot it holds (one stays), a run that is nested or not pinned, and an asker that is not a live process in the run's job. The refusal is the record's `give_back_refused` {id, why, at}.
- Order: the job's affinity narrows to the slots kept first (`kitlib.proc.job.Job.narrow`; every process in the run's job moves, nested jobs too, but not a container that `docker exec` or `docker run` started: it keeps the cpuset it started with), then under the `queue` mutex the run record (`cores`, `slots`, `has`, pin fields), then the queue entry's `cores`, then the ack, the record's `given_back` {id, cpu, cores, cpumask, cpuset, at} (`giveback.shrink`). The ack comes last so the asker never hears "given" while the queue still holds the slots. Later commands get the narrower `MACHINE_LOCK_CPUSET`, `MACHINE_LOCK_CPUS` and `MACHINE_LOCK_CPUMASK`.
- Fail safe: a failed write that queue.json, read back, shows left the queue entry unchanged puts the record (in memory and on disk) back as it was, and the record and queue entry keep every slot booked. The job's pin is widened back (`Job.repin`), which moves its processes back onto every slot too; if Windows refuses that, the refusal says the job stays narrowed, and a later request that keeps any other slot is refused (`Job.narrow` only narrows). The queue entry, which every planner reads, is written after the record, so a wrapper that dies between the two leaves the slots counted held, never handed out twice.
- A lost ack: once the queue write lands the slots are given back, and nothing after it undoes that: not a failed ack write (widening the job again would book slots the queue has freed twice), not an interrupt, Ctrl+C included. `giveback.shrink` reads queue.json back under the mutex to tell whether the write landed (`giveback.queue_books`), and puts the record back only when the read-back says it did not. A read-back that finds queue.json unreadable counts as landed: the job stays narrow and the queue may still book the slots, which leaves them unused until the run ends but never books them twice. The wrapper writes the ack again on its next poll (`Slot.ack_due`), so the asker hears "given" late, or "timeout" if its wait ends first; `Offer.held` then shows the narrower `cores`, and `giveback.drainer` logs "no answer" with the cores the record books, never "the run keeps them". Asking again for the same slots is refused ("not this run's") and changes nothing. A wrapper that dies between the queue write and the ack ends the asker with it (the run's job is kill-on-close, `kitlib.proc.job.Job`), so no asker waits on that ack.
- A record the asker cannot read now is never "gone": on Windows an open that lands while the wrapper's `os.replace` swaps the record is refused, not answered with no such file. `kitlib.lock.store.read_record` tells the two apart; `Offer.give` reads such a record again on its next poll, `Offer.held` answers None (never no slots), and `giveback.drainer` then asks nothing that time. A timed-out `Offer.give` withdraws its request (`Offer.withdraw`), trying a request it cannot read or remove again for `giveback.WITHDRAW_S`, and says so in its "timeout" answer when it could not.
- The request file is not a `.json`, so it is never read as a run record; `Store.live_runs(prune=True)` removes an orphaned one.
- The history line keeps `given_back`.

## Run resources and landing priority

`kitlib.lock.run.book` takes two keyword arguments: `resource=None` and `priority=None`. `machine_lock.py run --resource NAME` passes `resource` through (`tools/machine_lock.py` `cmd_run`, `kitlib.lock.run.run_command`); `priority` stays for library callers (`kitlib.gate.land`). `background` takes neither: a background run does not book through `book()` (`kitlib.lock.background.run_background`). argparse refuses `--priority`, `background --resource` and an abbreviated `--res`, exit 2 (`tests/lock/test_cli.py`), and no MCP tool takes either (`tests/lockmcp/test_server.py`). The status text, `status --json` and the MCP snapshot show both (Snapshot: `runs`, `queue`).

`run --resource NAME`, for example `--resource ports:e2e-a` so a repo's e2e runs that share a port block never overlap:

- What it holds: the one name, exactly as given (one `--resource` per run; a second one replaces the first, as argparse does). The lock reads no meaning into it; two runs name the same resource only when the strings are equal, case included (`kitlib.lock.queue.resource_holders`). An empty name is usage, exit 2, before anything is booked or detached (`kitlib.lock.run.check_resource`, the rule `book()` applies).
- A name starting with `landing:` is refused by the CLI (`tools/machine_lock.py`), usage exit 2, before anything is booked or detached: landing resources belong to land.py (`kitlib.gate.land`, which calls `book()` directly and is not affected). Test: `test_a_landing_resource_is_usage_and_books_nothing`.
- For how long: from when the run holds its slots until it releases them, after its command and any `--on-release` command end, or until the lock finds its wrapper dead (below).
- A second run naming the same resource while the first is live waits for it, however many slots are free: with no limit by default, exit 8 when `--max-wait` runs out, exit 6 at once with `--no-wait` (the message says `resource NAME is held by` the holding run). A run naming another resource, or none, is not kept out. This holds for a nested run too: a repo gate inside a landing that calls `run --resource X` waits behind any run holding X, with no limit unless it passes `--max-wait` or `--no-wait`. Tests: `tests/lock/test_cli.py` (`test_run_resource_reaches_book_and_a_second_run_naming_it_waits`).

- **`resource`** is a non-empty string naming something the run holds for its whole life, for example `"landing:" + os.path.normcase(os.path.abspath(<git common dir>))`. Anything else is a usage error (`LockError`, exit 2), raised before the store is written.
  - The run record and the queue entry carry `"resource"` (`kitlib.lock.queue.join`).
  - The planner (`kitlib.lock.queue.plan`) never starts a waiting entry while an entry in state `held` or `bg` names the same resource, and never plans two entries naming it to overlap, however many slots are free. A background run's slots still yield to foreground runs; a resource it names does not.
  - The run's parent (a nested run's `parent`) holding the same resource does not keep it out. A nested run naming a resource its parent does not hold joins the queue for it, with no slots of its own when the parent covers what it needs; one whose parent holds that resource inherits as before and takes no queue entry.
  - The resource is free when the run's entry goes: on release (`settle`), and when the next look finds its wrapper dead (`queue.prune`, which says `run R died holding resource X; it is free`).
- **`priority`** is null (an ordinary run) or `"land"` (`kitlib.lock.queue.PRIORITIES`); any other value is a usage error (`LockError`, exit 2). The entry carries `"priority"`.
  - Plan order: own_turn entries (a hold's claimer, a nested run), then entries the owner moved to the top (latest move first), then `"land"` entries in ticket order, then a gpu entry whose gpu slots are free, then ticket order.
  - Backfill: a run behind a landing may start first only when it ends before the landing is planned to start, unless the landing's start was put off by its resource alone (`queue.plan`: its slots were free at an earlier time when its resource was not, and it is not parked). Such a start keeps out only the entries naming its resource; the others plan around the slots it is planned to take, so they start now on idle cores, and the landing starts no later than it would have. Example (`tests/lock/test_queue.py` `ResourceExclusion`): repo X's first landing holds a quarter of the cores for 30 more minutes and X's second waits for it; a landing of repo Y and a 60-minute ordinary run both start now, and X's third still waits for X's second. A landing whose slots are not free either stays a barrier as before. Nothing holding slots is stopped for a landing.
- An entry written before these fields existed has neither key and plans as an ordinary run with no resource; a `priority` value on disk that is not in `PRIORITIES` plans as ordinary too.
- The history line keeps `priority`, and `gate` (true for a gate's run, from `book(..., gate=True)`) (`kitlib/lock/store.py` `Store.HISTORY_KEYS`). The branch gate budget reads both, to count a branch's gate runs and leave its landings out (`kitlib/gate/budget.py`; `docs/gate.md` "The branch gate budget"). A line written before it kept them has neither. It also keeps `branch` (the branch a branch gate books for, from `book(..., branch=...)`; null when none was given), which the budget counts a branch's runs by; a line written before it kept `branch` has no such key. Tests: `tests/gate/test_gate_tree.py` (`test_the_history_line_keeps_gate_and_priority`), `tests/gate/test_gate_budget.py` (`test_the_gate_s_own_line_names_its_branch`).
- Tests: `tests/lock/test_queue.py` (LandPriority, ResourceExclusion) and `tests/lock/test_run.py` (Resources).

## Runs confined to a thread set

`machine_lock.py run --within THREADS` (and `kitlib.lock.run.book(..., within=...)`) keeps a run on the cpu slots whose threads all lie inside THREADS, a Linux cpuset list of global thread ids such as `8-15` or `0-3,8-11` (docker's `--cpuset-cpus`, so a run for a container can name the container's cpuset). `background` does not take it, and the MCP server has no tool that starts a run.

- Only whole slots count: a slot with any thread outside the list is left out (`kitlib.lock.layout.within_slots`). Which slots those are depends on the layout in force, and a run that re-reads a changed layout before it holds its slots works them out again.
- The planner (`kitlib.lock.queue.plan`) picks only from those slots and waits for them while other slots are free; a hold over slots outside them does not park the run (`kitlib.lock.holds.cover_plan`). While it waits, it bars a run behind it only from its own slots (`kitlib.lock.queue.barrier_guard`): a run that fits on slots outside them for its whole expected time starts now, and one that would need a slot inside them waits for it, as backfill always does. A run that also needs a gpu slot, or is parked, bars every slot. The status text's waiting line adds `within cpu slots X (--within)`, and a refusal or wait reason adds `it runs only within cpu slots X (--within)` (`kitlib.lock.queue.busy_text`).
- Exit 2 (usage), before the run joins the queue (`kitlib.lock.run.book`, `within_of`): a list that is not one (`kitlib.lock.layout.parse_threads`: empty, an open or backwards range, a stray comma, an id past 4095); a thread this machine does not have (a thread the owner's division leaves out of every slot, by `threads` or `cpu_slots` in machine.json, is no error: it is just not used); a list holding no whole slot; one holding fewer slots than the run takes (the message names `--cores N` that fits); `--within` with `--hold`; and a nested run that runs on its parent's cores when they are not all inside the list.
- The run record carries `within` (the list as text, normalised: `8-15`) and `within_slots` {cpu: [slot]}; the queue entry carries `within` {cpu: [slot]}. Both are set only when the run names a list. An entry or record without them, written before they existed included, may take any slot. `SCHEMA_VERSION` stays 1.
- Tests: `tests/lock/test_within.py`, and `tests/lock/test_cli.py` (`test_run_within_reaches_the_run_and_bad_syntax_is_usage`).

## Runs on a load node

`machine_lock.py run --node auto|main|NAME` (default auto) may run the command on a load node instead of here (docs/load-nodes.md "Lock runs on a node"). `kitlib.lock.run.run_command(..., route=)` asks the route (`kitlib.loadnode.dispatch.Router`) after its own checks (an empty command, a bash or script command) and before `book()`: None runs the command here as before, and a number is the run's exit code, with nothing booked, recorded or put in the history here (the node's lock holds the job). `--node main` asks no node and keeps the run here; so do `--resource`, `--cores`, `--hold`, `--gpu-share`, `--within`, `--on-release`, a library caller's own `env=`, a detached run and a run inside another lock run, and a Windows command (best effort; docs/load-nodes.md). A node runs committed HEAD from the checkout's top: untracked and git-ignored files the command needs are not there, and its outputs are removed with the job unless `--artifact GLOB` copies them back. `--node NAME` with any of those, or with `--detach`, is usage, exit 2. `--artifact GLOB` (repeatable) names the files a node job copies back; `--registry FILE` (hidden, on `run` and `status`) names another registry, for tests. `status` (text) ends with a `node:` line per registered node (docs/load-nodes.md "node.py list and status"); `status --json` and `snapshot()` are unchanged. Tests: `tests/lock/test_run.py` (the route), `tests/loadnode/test_dispatch.py`, `tests/lock/test_cli.py` `LoadNodes`.

`machine_lock.py run` exit codes: 0 or the command's own code; 1 no such record or not stopped; 2 usage or refused (with `--node NAME`, also a run a node cannot take); 6 busy (`--no-wait`; with `--node NAME`, also the node busy); 8 `--max-wait` ran out; 10 the lock cannot be had (fail closed; with `--node NAME`, the node could not be used before the job started: nothing ran); 11 a hold keeps it out; 12 the hold cannot be used. A run on a load node also: 9 the connection to the node was lost (the job runs on there; the follow and stop lines are said), 13 the job succeeded but its artifacts did not all come (none was copied in), 14 the node started the job but it ended with no exit code of its own or could not be followed, or the start request went out and no reply came back (it is never run again here), 130 Ctrl+C.

## Console windows

A run booked by `book()` (`machine_lock.py run`, a gate, a `slot()`) watches for console windows from its first command's start to its release (`kitlib/lock/run.py` `Slot.start`; `Slot.watch_stop`, which the release calls before it ends the job; `kitlib/proc/winwatch.py`). A window is the run's when its program is in the run's job (`Slot.window_owner`, `Job.contains`). The ended record gets `windows` (a list of `at cls how title pid exe host_pid host_exe ours`, at most `winwatch.RECORD_CAP`, 50, with `windows_truncated` the count left out) when any window was seen, and `windows_error` when the monitor could not run or raised as it started (`Slot.watch_start`; the run goes on); the history line carries neither (`kitlib/lock/store.py` `Store.HISTORY_KEYS`). `machine_lock.py run` (`run_command`) says the report after the release (`Slot.window_lines`; the lines are in `docs/gate.md` "Console windows"); a gate says it itself; any other run says nothing. A window warns and never changes a run's exit code. `WATCH_WINDOWS = False` in `kitlib/lock/run.py` turns the monitor off.

## App Execution Aliases

A Windows App Execution Alias, a file in `%LOCALAPPDATA%\Microsoft\WindowsApps` (or a package subfolder of it) such as `python3.exe` or `winget.exe`, starts its program outside the job of whoever starts it. That program is not pinned to the run's cores, runs on every core, and outlives the stop that ends the job.

- Refused, never swapped: a command whose first item, or the file CreateProcess finds for it, is under that folder is refused before the run books. `run` and `background` exit 1 before they detach, with no record (`kitlib.lock.run.script_command`, which calls `alias_check`; `created_program` follows CreateProcess's order: this program's folder, the current folder, the system folders, then PATH, appending only `.exe`). `Slot.start` refuses it too, as a backstop for a library caller. The message is `could not start the command: <name> is the WindowsApps App Execution Alias <path>: what it starts runs outside the run's job, on every core, and outlives a stop; ` followed by what to do instead (`alias_instead`): `run "<this interpreter>" <args> instead` for a python name (`pythonw.exe` beside it for a pythonw or pyw name); for the py launcher (`py`, `pyw`) `run "<this interpreter>" in place of py instead, with the arguments adjusted for python ...`, since py's own flags are not python's; `name the program's own path instead, not the alias` for any other program. When this interpreter is itself under WindowsApps (a Store python) and the program is a python or this interpreter, the run is still refused, and the message says `this kit itself runs under a WindowsApps python (<path>): run it under a python.org or Python install manager interpreter instead, not the Store python or its alias`. A bare `bash` is left to Git Bash (`kitlib.proc.bash`). Nothing is checked when LOCALAPPDATA is unset.
- `status` (text) warns when the first `python.exe` on PATH is the alias (`path_alias_line`): `python: first on PATH is the WindowsApps alias <path>; a non-python child's python escapes the run's job; put <this interpreter's folder> ahead of it on the user PATH`.
- A stop of a run booked by `book()` (`machine_lock.py run`, a gate, a `slot()`; `Slot.wait`) names each live process descended from the run's command, by the parent pid chain of one Toolhelp snapshot taken before the tree is ended, that is outside the run's job: `WARNING: run <id>: pid <pid> (<exe>) descends from the run's command but is outside the run's job: stop did not end it and it runs on, unpinned; ...` (`escaped`, `escape_lines`). It is a report only: the lock never ends a process outside the job. The chain is inexact: a process whose parent has exited is not found, and a reused pid can be. A `background` run's stop does not look. Measured 2026-10-29, cmd.exe in a job running the `python3` alias: the alias's stub (`python3.exe`) and the interpreter it starts are both outside the job, the stub's parent pid is cmd.exe and the interpreter's is the stub, so the walk from the run's command finds both.
- Tests: `tests/lock/test_run_alias.py`.

Known limits:

- Only the run's own command is checked. A `python` that a non-python child (a .bat, cmd or bash) finds on PATH can still reach the alias and escape the job. The fix is the real interpreter's folder on the user PATH ahead of WindowsApps, which the `status` warning names.
- A process that escaped the job is out of the lock's reach: nothing pins it and stop does not end it. The stop's report (above) finds it only while every process between it and the run's command lives: once one in between has exited (a cmd.exe or bash that started the alias and ended, for one), it is missed.
- The kit cannot run under a Store python. When this interpreter is itself a WindowsApps alias, every run of a python by it, the kit's own `[sys.executable, ...]` runs included, is refused (fail closed), and the message says to run the kit under a python.org or Python install manager interpreter.

## Exclusive resources

`kitlib/lock/resource.py` keeps a second queue in the same store, `resources.json`, for things one caller holds at a time and that take no slot. Nothing in the kit calls it now: a landing books `kitlib.lock.run.book(..., resource="landing:<git common dir>", priority="land")` instead, one entry in `queue.json` (Run resources and landing priority; docs/gate.md "The landing queue"), and only `tests/lock/test_resource.py` exercises the module. The module is not in the snapshot and has no write call here. It is separate from a run's `resource`, which lives in the run's queue entry and is held only while that run is.

- `join(store, resource, label)` puts a `Turn` at the back; `try_take()` returns `[]` when the caller holds the resource, else the live entries ahead of it, holder first; `wait(timeout_s)` repeats it for `timeout_s` from the first look that finds entries ahead; `leave()` gives the turn up and never raises. `entries(store, resource)` reads the queue without writing.
- First come, first served: the lowest ticket for a resource holds it, nothing goes ahead of an earlier entry, and nothing takes a resource from its holder.
- An entry stands while its process holds the entry's run mutex (`store.run_mutex`), as a run's queue entry does; a caller that dies leaves an entry the next look drops (`store.run_dead`).
- It is read and written only under the store mutex `resources`. A file that exists and cannot be read raises `ResourceUnreadable` after `settings.queue_read_s`; it is never read as an empty queue.

## Repository kinds

A repository may name its own run kinds in its `.kit.json` `kinds` section (docs/kit-json.md), beside the kit's (`kitlib/lock/kinds.json`), so a repository-specific heavy run (a world graph build, a model evaluation) books by its own name without a kit change. Each entry is a kinds.json entry plus a required `why`: `{"cpu": <1..agent_cap | "medium" | "heavy">, "gpu": 0 | "pool", "share": false, "warn_min": 60, "why": "..."}` (`gpu`, `share` and `warn_min` optional, with those defaults). A kind name is `[a-z][a-z0-9-]*`. The section is always inline in `.kit.json`, never a file beside it.

- Who reads it: `machine_lock.py run` and `machine_lock.py hold agent`, for the current directory (`kitlib.lock.run.book(checkout=)`, `kitlib.lock.api.hold_create(checkout=)`, `kitlib.lock.kinds.with_repo`). The library default is no checkout: kit kinds only.
- Where it is read: the working-tree `.kit.json` of the main checkout of the current directory's repository (`kitlib.git.repo.main_checkout_toplevel`), never a linked worktree's, so an agent's uncommitted edit in its worktree cannot size a run. Outside any git work tree there are no repository kinds.
- The kit wins a clash: a name that is a kit kind or a kit alias (`aliases` in kinds.json) books the kit's entry, the repository's entry of that name is ignored, and `.kit.json` is not read at all, so a broken `.kit.json` never stops a kit kind.
- Sizes: the entry is checked as a kinds.json entry is (`kinds.check_entry`); `--cores N` asks for fewer, never more. The agent cap is checked when the run or hold is booked, against the layout in force: a whole number past it is refused with exit 10, as is a `.kit.json` that does not load when a repository kind is asked for (fail closed). An unknown kind is usage, exit 2, and the message names the checkout whose main checkout `.kit.json` was looked in.
- Records: a run or hold on a repository kind is recorded under its name, as any kind is: history, `history_expect` and `stats` group by it. The section is not part of the gate's config hash (`kitlib.gate.runner.gate_config`).

Known limits:

- Only the CLI passes a checkout. `gate.py`, `land.py`, `redfirst.py`, `daily_full.py` and other library callers of `book()` book kit kinds only, so a repository kind in `.kit.json` `gate.kind` is an unknown kind there.
- Load nodes: dispatch sizes a run from the kit table only (`kitlib.loadnode.route.need_of`), declines a repository kind quietly, and the run stays on this machine.
- No aliases: a repository kind cannot be renamed while keeping its history under one name, as kinds.json's `aliases` do for kit kinds. A renamed kind starts a new history; a renamed kind used as `gate.kind` would also need a `HASH_KIND_AS` entry (`kitlib.gate.runner`).
- The snapshot's `kinds` is the kit's table only, and `gate.py --measure` proposes sizes for kit kinds only.
- Rollout: a kit from before this section refuses a `.kit.json` that has it as an unknown section, and every kit tool reads `.kit.json`. Add a `kinds` section only once every plugin folder in use has this change.
