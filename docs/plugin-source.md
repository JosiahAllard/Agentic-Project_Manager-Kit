# Plugin source

Every account folder's Claude Code installs the `pm-kit` plugin from an export of pushed kit main, never from the kit checkout. `tools/plugin_refresh.py` makes the export and runs `claude plugin` in each account folder; logic in `kitlib/pluginsource` (export, marketplace, prune, state, the refresh lock) and `kitlib/pluginsource/claude.py` (the account folders and the `claude` runner). Codex installs the plugin from the same export (`hosts/codex/adapter/plugin_copy.py`, `plugin_install.py`; "Host plugin copies"). With no `home`, `claude.account_folders` and `claude.Runner` find the user's home through `kitlib.config.user.home_dir()`, which the kit's tests fence (docs/test-tools.md "Home fence").

## Layout

The export root is the machine config's `plugin.export_dir`, by default `%LOCALAPPDATA%\pm-kit\plugin` (docs/kit-json.md "Machine config keys"; `kitlib.pluginsource` `settings`). On Linux the default is `<profile>/.local/share/pm-kit/plugin`, the profile folder from the password database (`kitlib.platform.linux.paths` `profile`), so a fresh box needs no machine config for it. It never reads `$HOME` or `$XDG_DATA_HOME`: a cron job, a systemd unit and a login shell all get the folder the managed settings name, as they all get the same PM-repo pointer. The one place that picks the default is `kitlib.pluginsource` `default_export_dir`; `kitlib.gate.pin` and `kitlib.kitcmd` read it through `settings`. A set `plugin.export_dir` wins on every platform. A root inside the kit checkout, or under the agent temp sweep root (`agent_temp_sweep.dir`, whose sweep removes unused entries), is refused (`kitlib.pluginsource` `placement_errors`, checked by `check` and `settings`). It holds:

- `<sha12>/`: the tracked files of one kit main commit, from `git ls-tree` of the commit and one `git cat-file` batch (`kitlib.pluginsource` `export`), so no worktree, `.git` or untracked file is in it. The top-level `tests/` folder is left out (`LEFT_OUT`, as `kitlib.kitrelease` leaves tests out of a release): it was half of each export, and nothing reads the kit's tests from an export, since a gate runs `tools/kit_tests.py` from its own checkout. Symlinks and submodules are skipped and listed in the marker. Each `hooks/hooks.json`, `mcp.json` and `.claude-plugin/plugin.json` with a `<name>.<platform>.json` beside it for the running platform holds that file's bytes (`kitlib.pluginsource` `platform_manifests`, `PLATFORM_FILES`; the renderers write one of each per platform, docs/content.md "Manifests"), since a plugin manifest names hooks.json alone and the host reads plugin.json and mcp.json by name; a swapped plugin.json is stamped as below. On Windows every file is the commit's own. It is written as `<sha12>.tmp` and renamed, so a folder by the final name is always whole.
- `<sha12>/.pm-kit-export`: the marker, `{sha, version, exported_at, skipped, made_by, checkout}`. Prune only removes folders that have one. `checkout` is the main checkout of the kit repository the export was made from (`kitlib.git.repo` `main_checkout_toplevel`; left out when git cannot place it), and `kitlib.pluginsource` `export_checkout` returns it while it still holds a `.git` folder. A `tools/land.py` or `tools/gate.py` started from the export pins through that checkout as a start from it would (docs/gate.md "Pinned tools"). `tools/kit_stubs.py memory` run from the export reads it too, for the kit its printed command names (`kitlib.stubs.live_kit`, docs/install.md "Agent memory folder: tools/kit_stubs.py memory"). An export made before the key existed has none: its tools run live, and the command `kit_stubs.py memory` prints names the export, until a refresh replaces it.
- `<sha12>/.claude-plugin/plugin.json`: the kit's manifest with its one `version` value stamped `<kit version>-main.<commit count>` (`kitlib.pluginsource` `stamp`, `stamped_version`), so `claude plugin update` sees a new version at every push without a commit on main. Every other byte, a BOM included, is kept.
- `<sha12>/.<host>-plugin/plugin.json`: each `hosts/<host>/shell/plugin.json` placed again at the path that host reads, stamped the same way (`kitlib.pluginsource` `host_manifests`), unless the commit already holds that path; the original stays where it is. Today that is Codex's `.codex-plugin/plugin.json`, whose paths name the export folder's own `content/skills/`, `hosts/codex/shell/hooks/hooks.json` and `hosts/codex/shell/mcp.json`.
- `.claude-plugin/marketplace.json`: the marketplace `pm-kit`, whose one plugin `pm-kit` is `./<sha12>` (`write_marketplace`). It is rewritten through a temp file and `os.replace`, with no BOM. The names never change, so agent names (`pm-kit:<agent>`) and allow entries stay the same.
- `.agents/plugins/marketplace.json`: Codex's marketplace file, the same `pm-kit` marketplace naming `./<sha12>`, written by the Codex plugin-copy step, not by `kitlib.pluginsource` ("Codex").
- `state.json`: `{sha, version, folder, exported_at, folders: {<account folder>: {rc, at, step, migrated}}}`, where each folder entry is the result of its last refresh or migrate. `migrated` is true once a migrate of that folder succeeded; a new export keeps each folder's `migrated: true` (`kitlib.pluginsource` `_carry`).
- `refresh.pid`: held while a refresh runs (`RefreshLock`). It is created exclusively and holds `{pid, ctime}`. A file whose process is gone, or whose pid now belongs to a process with another start time, is taken over. An empty or unreadable file is one a starting refresh has made but not yet written: it counts as live until its modified time is more than 10 seconds old (`LOCK_GRACE_S`), and is taken over after. A second refresh is refused with "a refresh is already running".
- `refresh.log`: the output of a refresh that `pm_watch` started (`spawn_refresh`).
- `pins/`: the exports `tools/land.py` and `tools/gate.py` run from when started from the kit's main checkout or from an export whose marker names it, `pins/<sha12>` (marker `made_by` `kitlib.gate.pin`), with their own `pins/refresh.pid` and `pins/leases/` (docs/gate.md "Pinned tools"). The plugin's marketplace never names them.
- `headers/`: one file per session or subagent, `<session_id>-<agent id or main>`, holding the export folder its kit header named (`kitlib.host.headerfollow` `note`). At a later tool event, `headerfollow` `line` compares the record with the folder the guard's alternatives name (`kitlib.guard.rules` `advice_kit`). When they differ, it returns one line naming the current kit folder and rewrites the record, so a session started before a refresh is told once per refresh. A SessionStart drops records older than 7 days (`MAX_AGE_DAYS`). Prune never touches the folder, since it is not a `<sha12>` export. `kitlib.host.hookmain` calls it: `dispatch` notes the folder at the header part of a start event, and `run` adds the line to the answer of the next tool event, whatever its verdict, through the adapter's optional `tool_context` (the Claude adapter has it: an `additionalContext` beside the verdict, so a deny's or an ask's reason keeps its format). An adapter without `tool_context` (Codex today) gets no line, and its record is not read, so the record is never spent where the agent cannot see it. `line` is called first with `write=False`, and the record is rewritten only after the answer is written. The line never changes a verdict: any exception in `note`, `line` or `tool_context` means no line.

## Refresh

`python tools/plugin_refresh.py` is a dry run. It prints the plan and writes nothing. With `--apply`, it does the following (`kitlib.pluginsource` `refresh`):

1. It reads the sha of `refs/heads/main` on the kit's remote (`plugin.remote`, default `origin`) with `git ls-remote`. This writes no ref and fetches nothing. When the kit's objects do not hold that commit, it refuses with "fetch the kit first". A local commit that has not been pushed is never exported.
2. It exports that commit and points `marketplace.json` at it, then prunes old export folders (see "Prune" below). When one of these steps (the export, the marketplace write, the state write, the prune) fails, it prints `REFUSED: the <step> failed: <error>`, runs no `claude` and exits 1 (`kitlib.pluginsource` `_apply`).
3. In each account folder (`claude.account_folders`), it runs `claude plugin marketplace update pm-kit` and then `claude plugin update pm-kit@pm-kit` (only `plugin update` is observed; the rest are inferred, see "Open questions"):
   - The folders are `~/.claude`, every other `~/.claude-*` (except the kit's own machine folders, `machinesetup.default_config_dirs`), and the folders of the machine config's `launcher.accounts` and `launcher.orgs`, each counted once.
   - `--folder DIR` (repeatable) limits the run to the folders named. A name that is not one of those folders is refused with `REFUSED: not an account folder on this machine: <names>`, and nothing runs (`kitlib.pluginsource` `pick_folders`).
   - A folder that is not migrated (its `state.json` record has no `migrated: true`) is refused with `REFUSED <folder>: not migrated to the export yet: python "<kit>/tools/plugin_refresh.py" --migrate --apply --folder "<folder>"`. The other folders still run, and the exit code is 1, in a dry run too.
   - `CLAUDE_CONFIG_DIR` is set to the folder, except for `~/.claude`, where it is removed.
   - Each folder's result goes into `state.json`. A failed folder does not stop the others, and the exit code is then 1.
   - A folder whose last refresh at the same sha succeeded is skipped. When the export, the marketplace and every folder are already current, nothing runs.
4. When every folder's update went through, it prunes the old versions in the plugins cache of each account folder updated or already current at this sha, never a refused one that is not migrated yet, as `--prune-caches --apply` does, with every rule of "Old caches" kept (`kitlib.pluginsource` `_prune_old_caches`). It prints `pruned cache <path>` for each version removed and `WARNING: could not remove <path>: <why>` for each that could not be; kept versions get no line, and the exit code does not change. A failed folder, a `--migrate` run and a run without `claude` prune no cache.
5. It runs each host's plugin-copy step with the export folder (see "Host plugin copies"), also when the account folders had nothing to do. A step never changes the exit code.

Every mode, dry runs included, first prints `WARNING: pm-kit marketplace <where> is <path>, not the export <root> (...)` for each account folder's `plugins\known_marketplaces.json` `pm-kit` `installLocation`, and the managed settings file's `extraKnownMarketplaces` `pm-kit` source path, that is not the export root (`kitlib.pluginsource` `marketplace_mismatches`; the file's path from the default host adapter's `managed_settings_path`, through `kitlib.machinesetup.extras` `Host.managed_path`). It reads only and fixes nothing. A missing file or entry gives no line, a file that cannot be read gives a `could not check` line, and neither changes the exit code. The session start runs the same check (see "Behind warnings").

Without `claude` on PATH, the export is still made, no folder is refreshed, and the exit code is 1. The tool takes no machine lock and imports nothing from `kitlib.lock` or `kitlib.gate`. `kitlib.pluginsource` `ensure_export` makes or keeps the export alone, with no `claude` call, for an installer that then adds the root as a marketplace. It keeps each folder's `migrated: true`, and when `state.json` cannot be read it raises `StateError` and writes nothing, rather than replace the state with one that has no flags.

## Prune

Before it removes anything, `tools/plugin_refresh.py --apply` reads what is in use (`kitlib.pluginsource` `read_in_use`):

- every running process's command line and program path (one `Win32_Process` read, `kitlib.pmstart` `list_processes`);
- every scheduled task's definition (`schtasks /Query /XML ONE`: program, arguments and working folder). A task that runs from an export folder breaks when the folder is removed. A non-elevated read works (observed 2026-10-19);
- the pin leases, `<root>\pins\leases\<sha12>-<pid>.json`, by file name, live or not (pluginsource imports nothing from `kitlib.gate`).

A `<sha12>` is in use when one of these names it as a whole path part (`in_use_sha12s`), followed by a separator, a quote, `;`, `,`, `)` or `&`. A read that fails is printed (`prune: what is in use could not be read whole (...)`), and the others still count. An empty process list counts as a failed read, since a real one always holds the reader itself.

Known limit: a non-elevated `Win32_Process` read returns a null `CommandLine` for elevated processes and for other users' processes, so such a process does not protect the export it runs from. The rename claim covers it only while the process holds a file there open.

Never removed (`kitlib.pluginsource` `prune`, `KEEP`):

- the folder `marketplace.json` names;
- the 3 newest export folders by their marker's `exported_at`;
- every export folder a running process, a scheduled task, a pin lease or a host plugin copy names ("Host plugin copies");
- every export folder replaced less than 1 day ago (`IN_USE_YOUNG_DAYS`), which covers every export made or current in the last 24 hours: a session whose MCP server has exited still runs hooks from its folder, and no process names it then. When any of the three reads failed, or no reader is given (`ensure_export`'s callers, `kitlib.gate` tests), this is 7 days (`YOUNG_DAYS`): what cannot be read counts as possibly in use. A folder is dated by when it was replaced, the `exported_at` of the next newer export, not by its own: one that was current for weeks and then replaced by three quick landings is kept. A folder whose own or replacing export's `exported_at` cannot be read is kept, and an unreadable date counts as the newest;
- a link or junction, which is never followed or removed;
- anything that is not a `<sha12>` folder holding the marker, so the `pins` folder is never touched; `kitlib.gate.pin` `prune` prunes it, by its leases (docs/gate.md "Pinned tools").

Every other export folder is removed by claim (`_claim_remove`): it is first renamed to `<sha12>.pruning-<pid>`. Windows refuses the rename while a file inside is open, so a folder still in use is kept whole and reported (`WARNING: could not remove ...: in use: it could not be claimed`). A claimed folder that cannot be removed whole stays claimed, and the next prune removes the rest. A `<sha12>.tmp` folder other than the current export's is a half-written export left by a run that stopped, and is removed too (prune runs under `refresh.pid`, so no export is being written then); so is a `<sha12>.pruning-<pid>` folder. Prune never touches an account folder or a plugin cache: see "Old caches".

## Migrating

`python tools/plugin_refresh.py --migrate` (a dry run; add `--apply` to run it) moves each account folder off a marketplace that was added from the kit checkout. In every folder it runs:

1. `claude plugin marketplace remove pm-kit` (a failure is tolerated: the folder may have none);
2. `claude plugin marketplace add <export root>`;
3. `claude plugin install pm-kit@pm-kit -s user`.

A folder whose three steps succeed is recorded `migrated: true`; a failed migrate records `migrated: false`. Only a migrated folder is refreshed by `--apply` (see "Refresh"). Migrate one folder first, `python tools/plugin_refresh.py --migrate --apply --folder "<folder>"`, and check that a session there starts and loads `pm-kit:coordinator`; then migrate the rest. Set the machine config's `plugin` key only after every folder is migrated, since older kit copies reject it.

A migrate never deletes an old cache. The migrate report lists, for each account folder, `<folder>\plugins\cache\pm-kit\pm-kit\<kit version>`. The path is made from names (`kitlib.pluginsource` `old_cache`) and is never looked up on disk, so a listed path may not exist. Remove old caches only after the migrate is verified, with `--prune-caches` (see "Old caches").

## Old caches

Claude Code copies each install into `<folder>\plugins\cache\pm-kit\pm-kit\<version>` (`kitlib.pluginsource` `cache_dir`), and never removes the old versions. A refresh whose updates all went through removes them itself (step 4 of "Refresh"), by the rules below. `python tools/plugin_refresh.py --prune-caches` lists them in every account folder (or those `--folder` names); it is a dry run, and with `--apply` it removes them, under the refresh lock, by claim as in "Prune". It cannot be combined with `--migrate` (exit 2). Kept (`prune_caches`):

- every version of an account, when the in-use read is not whole, the account's `plugins\installed_plugins.json` is missing, cannot be read or names no `pm-kit@pm-kit` install (`claude` `installed_path`), or a link or junction lies on the way to the cache;
- the version the install record's `installPath` names;
- the newest version, by folder modified time, and each replaced (the next newer one's modified time) less than 1 day ago, or whose time cannot be read;
- a version a running process or scheduled task names as `...\pm-kit\pm-kit\<version>`;
- a link or junction, which is never followed or removed.

Each line is `kept <path> (<why>)`, `would remove <path>`, `removed <path>` or `FAILED to remove <path> (<why>)`, then the counts. The exit code is 1 when a removal failed, else 0.

## Host plugin copies

A host that loads the kit from a plugin copy of its own gives its adapter's `ADAPTER` an optional `plugin_copy(home, environ)`, which returns a step. `tools/_host.py` `plugin_copies` collects one step from each host `hosts.json` registers that has the hook, and `tools/plugin_refresh.py` hands the list to `kitlib.pluginsource.refresh` as `copies` (none on a `--migrate` run; a host that will not load is a WARNING line and no step). `kitlib.pluginsource` names no host: it runs each step as `step(export folder, out, apply)`, in a dry run too, under the refresh lock with `--apply`, and a step that raises is a `<label>: not refreshed` line. A step may also have `in_use()`, the `<sha12>`s of the export folders its host's install came from: `refresh` adds them to what prune keeps (`with_hosts`), and a step whose read raises is a failed read, so the young-export rule keeps 7 days ("Prune"). Codex is the one host with a step today.

### Codex

Codex installs the plugin from the same export as Claude Code. The Codex home is `<--home>\.codex` when `--home` is given, else `CODEX_HOME`, else `~\.codex`. The step (`hosts/codex/adapter/plugin_copy.py` `Step`, the install in `hosts/codex/adapter/plugin_install.py`):

1. Writes `<export root>\.agents\plugins\marketplace.json`, the marketplace `pm-kit` whose one plugin `pm-kit` is `./<sha12>` (`marketplace`, `marketplace_body`), through a temp file and `os.replace`, unless the file already says that; a dry run prints `codex: would write ...`. A link or junction on the way is refused. A write that fails is a `codex: FAILED` line and nothing else runs, so Codex never installs from a marketplace naming an older folder. The file belongs to the export root, so a marked session writes it too.
2. In a session `PM_KIT_ROLE` marks, prints `codex: skipped` and does nothing more (see the hand-made copy below for who is marked, and the known limit).
3. Reads `<CODEX_HOME>\config.toml`, and never writes it. When `[marketplaces.pm-kit]` is there, its local `source` (a `\\?\` prefix dropped) must be the export root, or the step refuses and installs nothing. The export's `.codex-plugin\plugin.json` gives the version. When `[plugins."pm-kit@pm-kit"]` is there and the cache `<CODEX_HOME>\plugins\cache\pm-kit\pm-kit\` holds that version alone, it is current. Otherwise `--apply` runs `codex plugin add pm-kit@pm-kit` with `CODEX_HOME` set, using the native `codex.exe` (`hosts.codex.adapter.sessions` `native_codex`; 120 seconds, `INSTALL_TIMEOUT`), and checks that the cache then holds the version; Codex replaces the old cache version. With no `codex.exe` found, or an add that fails, it prints the command to run by hand.
4. After a first install it prints that Codex asks the owner to trust the pm-kit hooks at its next start; after every later install, that Codex asks again: Codex's trust hash for a hook covers its cache folder, which names the version, so a new version shows all four hooks as `modified` even when `hooks.json` is unchanged (observed). The stamped version changes at every push to main, so each refresh that installs means a new trust by the owner. The kit never writes hook trust: Codex runs a plugin hook only once the owner trusts it.
5. When config.toml names the old `pm-kit-local` marketplace beside `pm-kit`, warns that Codex loads both, so every hook runs twice, and names the two remove commands. When it names only `pm-kit-local`, prints the owner's switch steps (`switch_lines`: remove `pm-kit@pm-kit-local` and its marketplace, `codex plugin marketplace add "<export root>"`, `codex plugin add pm-kit@pm-kit`, start Codex and trust the four hooks) and still mirrors the old copy (below). When it names neither, prints the two commands that add the export.

The step's `in_use()` returns the `sha` of each cache version's `.pm-kit-export` marker, which Codex copies with the rest of the folder; a cache that cannot be listed, or a marker that cannot be read, raises. The export folder holds everything the plugin names, `boot\` included, so nothing is copied for Codex.

OBSERVED (Codex CLI 0.165.0-alpha.1.2, a private `CODEX_HOME`, 2026-10-29): `codex plugin marketplace add <export root>` and `codex plugin add pm-kit@pm-kit`, run by the step, install the stamped version into `plugins\cache\pm-kit\pm-kit\<version>`, the marker included; config.toml then holds `[marketplaces.pm-kit]` (`source = '\\?\<root>'`) and `[plugins."pm-kit@pm-kit"] enabled = true`; the root's `.claude-plugin\marketplace.json` does not disturb it. Codex lists the 20 `pm-kit:*` skills from `./content/skills/` and the four hooks, `${PLUGIN_ROOT}` expanded to the cache version, untrusted until trusted; it starts the hub and machine-lock MCP servers. Trust is kept in config.toml as `[hooks.state."<plugin id>:<hooks file>:<event>:0:0"]` (the plugin id `pm-kit@pm-kit`, the hooks file's path in the plugin) `trusted_hash` and `trusted_content_hash`; Codex's app-server `config/batchWrite` wrote it into the private home's config.toml only. A second install, of the next version, replaced the cache version (`0.4.0-main.5098` to `.5099`), and Codex then listed the four trusted hooks as `modified`. NOT OBSERVED: a hook running in a model turn (no signed-in session), and the desktop install's `codex.exe` (`native_codex` does not find `%LOCALAPPDATA%\OpenAI\Codex\bin\<hash>\codex.exe`, so the step prints the hand command there).

#### The hand-made pm-kit-local copy

Until the owner switches, a Codex home whose config.toml names only `pm-kit-local` keeps the hand-made copy, which the step mirrors (`plugin_copy.refresh`); it retires once the export install is proven in the owner's install. Codex installs that plugin by copying its marketplace folder into `<CODEX_HOME>\plugins\cache\pm-kit-local\pm-kit\<version>`, and copies it again from the marketplace folder later, so `--apply` writes both, or Codex would bring an old copy back (`hosts/codex/adapter/plugin_copy.py` `refresh`). The mirror:

- Reads the targets from `<CODEX_HOME>\config.toml` only, and never writes it: the `[plugins."pm-kit@pm-kit-local"]` entry; the `[marketplaces.pm-kit-local]` `source` folder (an absolute local path, resolved with `realpath`); that folder's `.agents\plugins\marketplace.json` entry for `pm-kit`, a path that starts with `./` and stays under the folder; and the cache folder of the version the marketplace copy's `plugin.json` (else `.codex-plugin\plugin.json`) gives.
- Refuses, writing nothing, when any of these is missing or malformed, when a target is not one config.toml names, or when a link or junction lies on the way below the Codex home or the marketplace folder. With no config.toml it prints that Codex is not set up and writes nothing. A missing cache folder (Codex has not installed that version) is a note, and the marketplace copy is still written.
- Mirrors the parts the export's `hosts/codex/shell` holds, `skills`, `agents`, `hooks` and `.codex-plugin`, into each target. A part already the same, byte for byte, is left alone. Each other part is copied to a sibling `<part>.pmkit-new-<pid>`; the old part is renamed aside to `<part>.pmkit-old-<pid>`; the copy is put in place with `os.replace`; then the old part is removed. Windows refuses the rename while a file in the part is open, so a part Codex holds open is left as it was, with the note `busy: ... close Codex and run the refresh again`. A replace that fails after the rename puts the old part back. A part that is a link or junction is refused, never followed. A leftover sibling from a stopped run is removed first.
- Changes no version and no other file: `plugin.json`, `mcp.json`, `boot\` and `mcp\` stay as Codex installed them.
- Runs under `refresh.pid`, and only in the owner's session: a session `PM_KIT_ROLE` marks (a PM's `pm_watch` auto refresh, which inherits it, or a hub server started from a marked session, whose "Hub refresh" child inherits it) prints `codex: skipped` and writes nothing. Known limit: the guard does not refuse `plugin_refresh.py --apply` to an agent, and a subagent of the owner's own session is unmarked, so this check does not stop one.
- Prints lines that start `codex:`, and never changes the exit code.

When `hooks\hooks.json` changes, Codex asks the owner to trust the pm-kit hook again at its next start; the refresh prints `hooks changed` then. Close Codex before the refresh, since it holds the MCP files open.

INFERENCE for the hand-made copy, not observed on a live Codex install: the `config.toml` keys, the marketplace manifest's place and entry shape, and the cache path come from the Codex plugin documentation and the owner's install notes. Where the real layout differs, the step refuses and writes nothing.

## Behind warnings

- **Session start.** The PM's session start (`kitlib.pmstart` `plugin_current`, run after `kit_sync`, which fetches) prints a line when:
  - there is no export yet;
  - `state.json`'s sha is not the kit's `refs/remotes/<remote>/main`;
  - a folder is not migrated;
  - a migrated folder's last refresh failed, or it has not been refreshed to the current export yet (`not refreshed to <sha12>`), or `state.json` cannot be read;
  - once the export is readable and the tracking ref is too, a migrated folder's `known_marketplaces.json`, or the managed settings file, points the `pm-kit` marketplace off the export root (`marketplace_mismatches`, as in "Refresh"). The check never raises: a file that cannot be read or has the wrong shape gives one `could not check the pm-kit marketplace path in <file>: ...` line per file (`kitlib.pluginsource.claude` `_check_one`), and any other failure gives one `could not check the pm-kit marketplace paths: ...` line (`kitlib.pluginsource` `_marketplace_lines`).

  With no export, or a folder not migrated, the line names `python "<kit>/tools/plugin_refresh.py" --migrate --apply` (`refresh_cmd(True)`), since `--apply` alone refuses such a folder; otherwise it names `python "<kit>/tools/plugin_refresh.py" --apply` (`refresh_cmd()`). `<kit>` is the kit's absolute path (`live_root`), since the PM reading the line works in another folder. The refresh checks read only the export root; the marketplace check reads each migrated folder's `plugins\known_marketplaces.json` and the managed settings file, never a cache. A folder's last successful refresh stands in for what it has installed: this is a proxy, not a reading of the install.
- **Watcher.** `pm_watch` (`kitlib.pmwatch` `plugin_check`, over `kitlib.pluginsource` `poll`) prints `PLUGIN pm-kit plugin behind kit main <sha12>: python "<kit>/tools/plugin_refresh.py" --apply`, or `--migrate --apply` when there is no export or a folder is not migrated. It checks on the branch cadence (`--branch-poll`) by reading one ref and `state.json`:
  - The event comes once per main sha. The sha is kept as `plugin_main` in the watcher's state file, so a relaunch does not repeat it.
  - An export that is already behind is reported on the first run.
  - A landing's push updates `refs/remotes/<remote>/main` (`kitlib/gate/land.py` `push`), so a kit landing is seen without a fetch.
  - The ref is read in the kit's source checkout: when the kit running the check is itself an export (it holds the marker), `kitlib.pluginsource` `source_kit` names the main checkout its marker records; an export whose marker names none that still exists is a failed check (pm_start prints `could not check the pm-kit plugin: ...`).
  - With no tracking ref, it prints nothing. A tracking ref that cannot be read, or a `state.json` that cannot be read, is a failed check; a check that fails three times running gives `ERROR plugin check`.
- **Auto refresh.** With `plugin.auto_refresh: true` (default false), that first event also starts `tools/plugin_refresh.py --apply` itself, detached and windowless, and appends `(auto_refresh: started)`. While a live process holds `refresh.pid`, it starts nothing and appends `(auto_refresh: a refresh is already running)`. With no export, or a folder not migrated, it starts nothing and appends `(auto_refresh: not started: no export yet)` or `(auto_refresh: not started: not migrated in <folders>)`. The hub server's job ("Hub refresh") refreshes on the same switch; the two share `refresh.pid`, so only one refresh runs at a time.

## Hub refresh

The hub server (`tools/hub.py serve`, docs/action-hub.md) runs a timed job, `plugin-refresh` (`kitlib.hubsite.plugin_job`, on the runner `kitlib.hubsite.jobs`), first 30 seconds after it starts and then every 300 seconds (`EVERY_S`). A scratch store (`--store`) runs no job. Each run:

- reads the kit's `refs/remotes/<remote>/main` and `state.json`, as the watcher's check does ("Behind warnings");
- does nothing, and says why in its note, when there is no tracking ref, no export yet, a folder not migrated, the export current at that main with every migrated folder's last refresh through (`current at <sha12>`), `plugin.auto_refresh` off (default false; the note names the `--apply` command), or a live process holding `refresh.pid` (`a refresh is already running`);
- otherwise runs `<kit>\tools\plugin_refresh.py --apply` as a child process (`--home` when the hub has one), windowless, and waits for it, at most 1800 seconds (`REFRESH_TIMEOUT_S`; past it the child and every process it started are ended, `kitlib.proc.process` `kill_tree`). A child, so a landing that changed the refresh is run by the new code, not the code the hub started with. The child does the whole refresh, the host copy steps included, so the Codex copy too, except from a marked session ("Codex"). Its output and exit code are appended to `<export root>\refresh.log` under a `hub plugin job <time>` line.

The child takes `refresh.pid` itself, so the hub never runs two, nor one beside a `pm_watch` spawn or a refresh by hand; one that finds it taken is a note. A child that exits non-zero, or overruns, is a job failure: the same main is tried again 1800 seconds (`RETRY_S`) after it failed, not sooner, and the runs between say `waiting to retry` with the failure.

A run that did nothing (every note case above, a retry not due) is a skip (`kitlib.hubsite.jobs` `Skip`): it neither counts as a failure nor resets the count. The runner keeps each job's state in GET health's `jobs` block (`every_s`, `runs`, `failures`, `running`, `last_at`, `ok_at`, `note`, `error`; null with no job), pushes `[hub push] job plugin-refresh failing` to the PM at the third real failure in a row and `... recovered` at the next real success (`current at` or `refreshed to`; `kitlib.hubsite.push` `job_event`). A child still running when the hub closes can outlast the close (the step is logged unclean): once the hub has exited nothing waits on it, and it runs to its own end, holding `refresh.pid` until then.

## Open questions

Observed on this machine (2026-10-27), then what is still inference.

OBSERVED:

- **Copied, not in place.** Each account folder holds `plugins/cache/pm-kit/pm-kit/<version>/` (about 12 MB), `installed_plugins.json` `installPath` points there, and the marketplace source is the local export root (an export folder is about 17 MB). The plugins reference (https://code.claude.com/docs/en/plugins/loading, "In-place and copied plugins") says a relative-path plugin of a local-path marketplace loads in place; here it is copied. Either way the export holds pushed main only.
- **Cache folder.** `<CLAUDE_CONFIG_DIR>/plugins/cache/pm-kit/pm-kit/<version>`, where `old_cache` points.
- **Version format.** The stamped `<kit version>-main.<n>` (for example `0.4.0-main.4607`, `kitlib.pluginsource` `stamped_version`) is accepted: `state.json` records it with `claude plugin update` rc 0.
- **`claude plugin update pm-kit@pm-kit`** works: `state.json` has rc 0 in every account folder.
- **Prune** removes old exports and keeps what a process, a scheduled task or a pin lease names (`refresh.log`).

INFERENCE:

- **The other claude subcommands.** `claude plugin marketplace update pm-kit`, `marketplace remove pm-kit`, `marketplace add <path>` and `install pm-kit@pm-kit -s user` are inferred from the end state (every `known_marketplaces.json` points at the export root, and `state.json` has `migrated: true`); no log line shows them. The tests use a fake `claude` that logs its arguments (`kitlib.pluginsource` `UPDATE_STEPS`, `migrate_steps`). To settle it, run `--migrate --apply --folder` on one folder and read its output.
- **Open files in old sessions.** That a session started before a migrate or refresh keeps its MCP server running from the folder it loaded, and holds files there open, so removing that folder before every session restarts can fail or break the session. The handle behaviour is not observed. It is why prune keeps what a process names and recent exports, and removes by claim, so a folder with an open file is kept whole. To settle it, list the open handles under an old cache while such a session runs.
