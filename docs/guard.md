# Shell guard and git hooks

`boot/hook.py <host> PreToolUse`, the kit's one hook entry (`boot/hook.py claude PreToolUse` on Claude), is the kit's one PreToolUse hook (ARCHITECTURE.md "Layers": Guards). `githooks/pre-push` is the kit's guard git hook. Both are thin entries over `kitlib/guard/` ("Hosts" below says how a hook reaches it). `githooks/` also holds `pre-commit`, the ledger check, inert unless a repository opts in (docs/ledger.md "Pre-commit check").

**Live and enforcing:** the guard is registered as the PreToolUse hook in the user settings (since plan step 14 as `boot/hook.py claude PreToolUse`; before it as `hosts/claude/shell/hooks/guard.py`, which `tools/machine_setup.py` re-points) ("Go-live", step 1), and subagent calls are refused by it (observed: rules `main-checkout` and `write-jail`). `githooks/pre-push` is live only in a repository whose `core.hooksPath` names `githooks/` ("Go-live", step 2).

## Output

- **Allow:** the hook prints nothing and exits 0.
- **Deny or ask:** it prints `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny"|"ask", "permissionDecisionReason": ...}}` and exits 0.
- **Reason format:** `<what and why> Instead: <the exact command to use> [kit guard: rule=<rule> role=<main|subagent>]`. The role is what the event said (on Claude, `agent_id` present or not; `Action.agent`). The self-test reads it. The command after `Instead:` is also the Decision's `instead`.
  - After `Instead:` comes one command, ready to run, with no prose after it. Any explanation goes in the sentence before it, which ends with `:` (tests/guard/test_rules.py `test_rows` checks this for every row).
- **Unguarded tools:** a tool no rule can refuse (any tool but Edit, Write, MultiEdit, NotebookEdit, Bash, PowerShell, Read, Grep, Glob and `mcp__*`: `hosts.json` `claude.hook.guarded_tools`) is allowed before kitlib is imported, read by `boot/hook.py` with json alone (`skips`; tests/guard/test_entry.py `Unguarded`, which also holds the list equal to the adapter's tool tables and `MATCHER`). It fails toward the guard: a payload that is not JSON or not an object, a tool name that is missing or not a string, and hook data it cannot read or of the wrong shape all go to the full guard (a missing `hosts.json` or host entry blocks the call), never to an allow.
- **Guard error:** if the guard fails on a guarded tool, it denies with rule `guard-error` (fail closed; `kitlib.host.hookmain.run`).
  - This includes a `kitlib.guard` that will not import and a payload the adapter cannot parse: hookmain imports the guard inside its `try` and has the adapter render the deny. Its `Instead:` reruns the hook on the event (`python "<kit>/boot/hook.py" claude PreToolUse < event.json`).
  - If the adapter or hookmain themselves will not import, or the answer cannot be written, the hook exits 2, which Claude Code also reads as a block.
  - Test: tests/guard/test_entry.py breaks each import.

## Rule modes

`kitlib/guard/modes.py`. Every refusal goes through `rules.refuse`, which asks the rule's mode:

- **deny:** the refusal stands, as its rule's verdict (deny or ask).
- **warn:** the call goes ahead, and the refusal's reason reaches the agent after `[kit guard warning] ` (`rules.WARNING`; the Decision is an allow with rule `warn`, `rules.WARNED`). Claude gets it as the hook's `additionalContext`, with no `permissionDecision` (`hosts/claude/adapter/host.py` `WARN_CONTEXT`); Codex shows nothing for a warned allow. The checks after a warned refusal still run, so a later deny still decides. Several warnings on one call are joined (`kitlib.host.hookmain`).
- **off:** the call goes ahead, and nothing is said.

The kit's modes are `modes.DEFAULTS`; a rule it does not name is deny:

- **warn:** `unplaced` (below), `unreadable`, `git-alias`, `heavy`, `heredoc-winpath`.
- **off:** `wrapped-gate`, `busy-wait`.
- **deny, kept:** owner-only tools and files, `hub-owner-verb` on a parsed hub tool run, the hub's secrets, the machine config, the ledger, PM data, lock state, `.kit.json`, generated files, gate results (`gate-result`), destructive git in a main checkout, `branch -D`, forcing or deleting main, `core.hooksPath`, owner identity, kill-by-name, a shell alias on the command line (`git-alias-shell`), and file-tool edits of a main checkout.

The owner sets a rule's mode in the machine config's `guard_rules` (`{"<rule>": "deny"|"warn"|"off"}`; docs/kit-json.md "Machine config keys"), and only there: never `.kit.json` or another file a branch carries, so a branch cannot loosen the rules it is judged by. A value that is not one of the three is ignored, and a config that does not read leaves the defaults (`modes.resolve`).

- **unplaced:** a write the guard cannot place (a computed or unread target, code given on the line, a git or .NET call whose directory the text does not tell, a computed `-C`, a computed `git worktree remove` target, a computed push refspec with no `--force`, `--delete`, `--no-verify` or literal `+` or `:`, git on a jailed session's unreadable line) is refused under `unplaced` instead of the placing rule (`rules.unplaced`, `rules.PLACE_RULES`: `main-checkout`, `write-jail`, `git-main-history`, `git-restore`, `git-checkout`, `git-reset-hard`, `git-clean`, `git-stash`, `git-bulk-add`, `git-commit-all`), with the same reason and alternative. Those rules still deny a write that resolves literally into a main checkout or outside an agent's folders, and so does a write git cannot place inside a `.git` folder, or git pointed elsewhere by `GIT_DIR`, `--git-dir`, `--work-tree` or an environment change the guard cannot read (`write-jail`).
- **gate-result:** an agent session's literal write into a repository's gate result folder (`<git common dir>/kit-gate-result/`, `rules.gate_result`), which only the gate writes, is denied; `Instead:` is `python "<kit>/tools/gate.py" wait-result <branch> --tip <sha>`.
- **Tests:** tests/guard/test_cheap.py (each mode, the defaults, the owner's overrides, the kept denies).

## Hosts

The guard judges a neutral `kitlib.host.Action` and answers a `kitlib.host.Decision` (ARCHITECTURE.md "Host contract"); no module under `kitlib/guard/` reads a host's payload or writes its output.

- **The hook:** `boot/hook.py claude PreToolUse` (the one entry of every host) hands Claude's adapter, `hosts.claude.adapter.host.ADAPTER` (the module `hosts.json` names), to `kitlib.host.hookmain.dispatch`, which runs `kitlib.host.hookmain.run`: the event JSON is parsed by `hosts/claude/adapter/events.py` `parse`, judged by `kitlib.guard.decide(action)`, lowered by `kitlib.host.degrade` when the host cannot show an ask, and rendered by the adapter's `render` (nothing for an allow, the JSON in "Output" for a deny or an ask). The fail-closed deny, an optional deadline (rule `guard-timeout`; Claude passes none) and the settings entry (`hookmain.command_line`, the one place a hook command line is written) are hookmain's, the same for every host.
- **What Claude's adapter reads:** `tool_name` sorts the call: a file tool (Edit, Write, MultiEdit: `file_path`; NotebookEdit: `notebook_path`) is an `edit`, Bash and PowerShell a `shell` (`command`, its dialect, `run_in_background`), Read, Grep and Glob a `read` (`events.READ_TOOLS`: Read's `file_path`; a search's `path`, absent meaning `cwd`, with `Action.params` `{search: contents, filter: <Grep's glob>}` or `{search: names, wildcard: <Glob's pattern>}`; Grep's `pattern` is not read), `mcp__*` an `mcp` call, anything else `other`. `cwd` as sent. `agent_id` is `Action.agent`; `agent_type`, for a subagent only, is `Action.agent_role` with one kit plugin prefix dropped ("Agent names"). `PM_KIT_ROLE` is read from the hook's environment, as before.
- **Host facts the rules need** arrive as Action fields or from `hosts.json`, never as host names in kitlib: the role a subagent runs as (`agent_role`), the shell dialect, whether the call is backgrounded, the host's form of the same edit at another path (`retarget`, for an `Instead:` line), and the lock MCP's tool names (the host profile's `mcp_tool_format`; "Lock MCP").
- **Paths:** every path the guard folds to compare, key or make canonical goes through `kitlib/guard/paths.py` `norm` (today's Windows rules, unchanged), so the later OS work changes one function. A command line's text (drive letters, quoting) is the shell parser's, not a path rule.
- **Tests:** the guard tests build Claude payloads and decide them through the adapter (`tests/guard/claudehost.py`); tests/guard/test_entry.py runs the hook end to end.

## Parsing

`kitlib/guard/shell.py` tokenises Bash and PowerShell, and `cmd /c` text. `commands.py` reads the result.

- **Seen as text, not commands:** quotes, here-docs and PowerShell here-strings.
- **Seen as commands:**
  - `;`, `&&`, `||` and `|` split commands;
  - `$(...)`, backticks, a PowerShell argument in `( )` (one computed word, `shell._Scan.ps_paren_arg`; "Rules") and `powershell -Command "..."` (`/Command`, `–Command`; after a switch powershell.exe does not know (any switch outside `commands.PS51_SWITCHES` and `PS51_ALIASES`, pwsh's value switches included; after `-i`, `-in` or an `-EncodedArguments` prefix the next word is read both as its value and as the command, `PS_VALUE_EITHER`; past `PS_FORKS_MAX` of them on one reading path the line is flagged `a powershell switch line with too many readings` and each further one is read as taking no value), which starts its command, both that text and a later `-Command` or standard input, each reading kept once and parsed on its own (`commands.expand`): `commands._nested_text`), `bash -c`, `cmd /c` (`//c`, `/k`, `//k` too, as Git Bash passes them) bodies are parsed again as nested commands;
  - the command after find `-exec`, `-execdir`, `-ok` or `-okdir` (up to `;` or `+`) is a nested command at find's working directory (`-execdir`/`-okdir`: at an unknown one), its words that hold `{}` computed;
  - a `trap` handler is a nested command at the trap's working directory, or at an unknown one when the line holds `cd`, `pushd`, `popd` or `Set-Location` anywhere (`commands.LINE_CD_RE`); a `mapfile`/`readarray -C` callback is a nested command;
  - `env -S <string>` is a nested command;
  - a shell (`cmd`, `bash` and the other `commands.BASH_SHELLS`, `powershell`, `pwsh`) that `Start-Process` (`saps`, `start`) starts runs its `-ArgumentList` as a nested command, at the `-WorkingDirectory` when one is given (`commands._sp_shell_text`): Start-Process hands it one command line, the elements joined with spaces, so for `cmd` the rest of that line after `/c` (`/k`, `/r`) is the text, read once with its outer quotes and once without; `bash` and `powershell` read their usual `-c`/`-Command` text from the words each element splits into (`commands._split_list`). The list is every word of an array, given by position or after `-ArgumentList` in its space or colon form (`-ArgumentList:'/c','echo x'`), up to the next unquoted, non-computed dash word (`commands._ps_param_word`; a quoted `'-NoProfile'` element is the child's), and a program given by position after `-ArgumentList` is the last word it took (`commands._start_process`). The common parameters (`-Verbose`, `-Debug`, `-ErrorAction`/`-ea` and the other `commands.PS_COMMON_VALUES`) and `-PSPath` (FilePath's alias) are parameters, never the program or a list word; a colon with nothing after it (`-FilePath: cmd`, `-WorkingDirectory: <dir>`) takes the next word. Start-Process resolves `-WorkingDirectory` as a wildcard path, and a bare `C:` or a drive-relative `C:x` against that drive's current location, so a value the guard cannot place exactly (`commands.sp_workdir_unplaceable`: those, a `*`, `?`, `[` or backtick, a device path, a Git Bash `/c/x` spelling) leaves the nested line no directory and its write is refused as one the guard cannot place. These readings follow PowerShell's binding closely, not exactly, so a parameter word they cannot place makes the line unreadable (below);
  - any other program `Start-Process` starts with a `-WorkingDirectory` (git, python, cp and the rest) runs in that folder (`commands.run_dir`, read as above): `commands.git_call` takes it as the directory git starts in, so `Start-Process git -ArgumentList 'commit',... -WorkingDirectory <main>` from a worktree is a commit in the main checkout. The shell-write rules ("Rules", `rules.shell_writes`) read git's own targets from that folder alone, and judge any other program's (the working directory a `python -c` or a script writes, cp's operands) from both that folder and the command's own directory, refused when either is a main checkout: a worktree workdir never lets a write pass that the command's own directory refuses, so `Start-Process python -ArgumentList 'x.py' -WorkingDirectory <wt>` typed in the main checkout is refused, while the same git call is not. For a main-checkout workdir typed in a worktree the `main-checkout` alternative is the same call with `-WorkingDirectory "<wt>"`. A computed workdir, or one `commands.sp_workdir_unplaceable` names, gives no folder: git there is git whose directory the text cannot tell, and the program's writes are ones the guard cannot place. A redirect and `-RedirectStandardOutput`/`-RedirectStandardError` stay placed from PowerShell's own location, which the workdir does not move (tests/guard/test_advice_workdir.py);
  - `cd`, `Set-Location`, `pushd` and `env -C <dir>` move the working directory for the commands after them.
- **Wrappers:** `env`, `command`, `exec`, `nohup`, `nice`, `time`, `timeout <n>`, `stdbuf`, `sudo` and `xargs` are skipped with their options (`time -p`, `nice -n 5`, `stdbuf -oL` and so on). The program after them is read. After `xargs -I`, `-i` or `--replace` (`commands.xargs_opts`), every later word that holds the replace string is computed (`commands.fill_words`): the program word and `sh -c` or `env -S` text too. The first `git` word in its tail is the program.
- **Redirects:** recorded per command with their targets.
- **Arguments the shell rewrites:** brace expansion (`src/{a,b}`), ANSI-C strings (`$'a\tb'`) and a bash backslash in a word are read as the words the shell produces.
- **Git spellings:** `-C`, `-c`, `--git-dir`/`--work-tree`, `--config-env` and git's place and config variables are read; long options are matched by unique prefix, and options that take a value skip it.
  - The variables (`commands.GIT_ENV_NAMES`): `GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`, `GIT_INDEX_FILE`, `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_<n>`, `GIT_CONFIG_VALUE_<n>`, `GIT_CONFIG_PARAMETERS`. One counts when set before the command (`=` or bash `+=`), through `env`, by `export` and the like (with or without a value), `$env:`/`${env:}` (`=` alone or in the same word), `Set-Item`, `Set-Content`, `Add-Content` or `New-Item -Name` on `env:`, a `Rename-Item`/`Copy-Item`/`Move-Item` to an `env:` name, or `SetEnvironmentVariable` (`commands.git_env_set`). Set anywhere in the line, nested text included (`eval`, `bash -c`, `env -S`, `Invoke-Expression`, a `source` of `/dev/stdin`), it leaves every git of the line unplaceable (`commands.mark_git_env`), whatever the order. A name is read as the shell passes it: a backslash bash drops (`export GIT_D\IR=`, `export \GIT_DIR=`, `env \GIT_DIR=`) is dropped (`commands.said`, `commands.passed`).
  - Fail closed: anything else on the line that may change the environment also leaves its git unplaceable (`commands.git_env_unsafe`). Only literal assignments are read (`NAME=v`, `export`/`declare`/`local NAME=v`, `env NAME=v`, `$env:NAME = v`, `Set-Item env:NAME`, cmd `set NAME=v`), with a name of `[A-Za-z_][A-Za-z0-9_]*` that is neither `SHELLOPTS`, `BASHOPTS`, `BASH_ENV`, `ENV` nor a `GIT_*` name outside `commands.GIT_SAFE_NAMES` (author and committer name, email and date, `GIT_TERMINAL_PROMPT`, `GIT_MERGE_AUTOEDIT`, `GIT_OPTIONAL_LOCKS`).
  - Everything else counts: a computed name (`export $V=`, `local -x $1=`, `Set-Item "env:$n"`, cmd `set %V%=`), `declare -n`, `-a`/`-o allexport` in `set`, `shopt` or a nested `bash`/`sh`, `source` of a file, `alias`, a `trap` handler other than `''` or `-` on any signal but `EXIT` or `0`, `mapfile`/`readarray -C`; git that `xargs -I`/`-i`/`--replace` runs, or that `xargs` runs with no subcommand (its input may add `--git-dir`); a PowerShell item cmdlet (`Set-Item`, `New-Item`, `Remove-Item`, `Rename-Item`, `Copy-Item`, `Move-Item`, `Set-Content`, `Add-Content`, `Clear-Item`) whose item is computed, piped in or an expression (`Set-Content` and `Add-Content` take piped input as the value, so with a path in the text they are read); a splatted argument (`@h`) on any command; `InvokeScript`, `NewScriptBlock`, `ExpandString`, `GetScriptBlock`, `AddScript`, `[scriptblock]::Create` or `[powershell]::Create` under any `System.Management.Automation.` prefix, or a static call on a computed type (`([type]'scriptblock')::Create`), outside a literal string (`git commit -m "Handle InvokeScript"` passes, `"$(...)"` counts); `Set-Location` to `env:` or a computed place; any `[Environment]::` call but a literal-name `GetEnvironmentVariable`; a static call on a variable (`$t::$m(...)`); a `::` in a `"..."` string is text (`$hits += "$b :: $f"` passes; `commands.PS_TEXT_STRING_RE`) unless the string holds an unescaped `$(`, a curly double quote, or a `${...}` holding `$`, a backtick or a quote (a `SetEnvironmentVariable` in a string with a `$` still counts); `Set-Variable` on `env:`; `Set-Alias`, `New-PSDrive`, `Import-Module`; a dot-sourced `.ps1`, cmd `call` or a `.bat`; `Start-Process -Environment`.
  - A `$env:VAR` that starts an item path (`Set-Content "$env:TEMP\x.txt"`, `Copy-Item a.txt $env:TEMP`) is a read, unless the line sets `VAR` (`$env:VAR = v`, also with the `=` starting the value's word: `$env:VAR ="v"`) or an item cmdlet names it beside an `env:` item (`Rename-Item env:FOO VAR`, `Copy-Item env:FOO env:VAR`). A line with no git is not affected (`set -a; . ./.env; set +a` passes).
  - Once one of these, `--git-dir`, `--work-tree`, `core.worktree` or `--config-env` makes git unplaceable, a `-C` before or after it does not place it again (`commands.git_call`).
  - Every git word is matched in the form the shell produces, the subcommand and options included, not only the program word.
  - A subcommand the text does not spell out (a variable, a substitution) makes the parse unclean. So does such a word in an option position that the git rules read.
  - Put `--` before a variable path, so it is not read as an option.
- **Unclean parse:** the parse is unclean when the text holds something the tokeniser does not model:
  - an unclosed quote, substitution or heredoc, a PowerShell `<#` with no `#>` (`shell._Scan.tokens`), or a `case` statement;
  - an encoded command, or a shell, `iex` or `Invoke-Expression` reading its commands from a pipe;
  - `iex`/`Invoke-Expression` of a computed value (`iex ("git " + "stash")`, or `"git $s" | iex`);
  - a shell or `source` reading a process substitution (`bash <(...)`, `source <(...)`);
  - a non-literal `bash -c`, `powershell -Command`, `cmd /c`, `eval` or `env -S` text, `trap` handler or `mapfile -C` callback;
  - a shell `Start-Process` starts with a computed `-ArgumentList` element (an `@(...)` array included) or `-WorkingDirectory`;
  - a `Start-Process` (`saps`, `start`) parameter word that names no parameter of it or names more than one (`-Bogus`, `-e`), or a switch whose `-Name:` is followed by a space (`-Wait: $true`), with or without a program (`commands._start_process`, its `unread`; with no program, a `commands.Unread` that only `commands.expand` gets, so `rolepolicy.lock_verb` still sees a call with no program);
  - an unquoted `--` in a `Start-Process` call (every later word positional), a splat (`Start-Process @p`, `Start-Process cmd @p`: `commands.PS_SPLAT_RE`), or `--%` between its words (the rest of the line passed as written; `commands.PS_STOP_PARSING_RE`), each in any of the dashes `shell.PS_DASHES` (`commands._sp_unreadable`);
  - a `cmd` word before its run switch, typed or passed by `Start-Process`, that holds `/c`, `/k` or `/r` anywhere but is not that switch alone (`/cecho`, `/q/c`, `;/c`, `,/c`, `=/c`, `x/c`, `"/c"`; `commands.CMD_RUN_HIDDEN_RE`, searched, not matched at the word's start), since cmd splits its switches at `,`, `;` and `=` as well as spaces; or a typed `cmd` word before its run switch that is computed (`commands._shell_text`);
  - a program named by a variable or a substitution;
  - a git subcommand or read option that is not literal;
  - a brace expansion, ANSI-C escape or backslash in a program name;
  - a `cmd` `if` statement or `for ... do` loop;
  - more than `commands.MAX_NESTS` (64) nested shell texts in one line (`commands._nest`): each powershell reading may be a powershell line that forks again (`pwsh -i pwsh -i pwsh ...`), so the line's total is capped; a reading is not merged with the same text under another outer command, whose chain the rules read.

  The rules still run on what was read, then "Fallback" runs.

Tests: tests/guard/test_shell.py.

## State

Every rule is a read-only check of real state. `kitlib/guard/context.py` `Ctx` gathers what the rules read, so tests can hand them a fake machine.

- **Place:** `kitlib.git.repo.classify`'s answer for the working directory or the target path: MAIN, LINKED, NONE or UNKNOWN.
  - `kitlib/guard/place.py` reads it from `.git`, gitdir and commondir files, so a call starts no git child. It reads the common config and, while that turns `extensions.worktreeConfig` on, the work tree's own `config.worktree` after it, as git does (the last `core.bare` wins). Any shape it cannot read the way git would (a bare or `core.worktree` repository, any other extension, `[include]` or `[includeIf]`, a `core.repositoryformatversion` above 1, a config line git refuses or continues onto the next, a broken gitfile, a path inside a git directory, a junction, symlink or subst drive on the way, a folder another user owns, a discovery variable such as `GIT_OBJECT_DIRECTORY`, any error while reading) goes to `repo.classify`.
  - Tests: tests/guard/test_fsplace.py asks both on real repositories; tests/guard/test_place_decisions.py decides every rule row with each and requires the same decision.
  - The PM data worktree (docs/pm-data-branch.md "Guard place and commit hooks") counts as MAIN, though git calls it LINKED: `Ctx.place` answers MAIN for a linked worktree whose top is the machine config's `pm_data.path`. Only when the machine config has no `pm_data` does the record decide: a linked worktree whose HEAD is `ref: refs/heads/<branch>` of the `kit-pm-data.json` record in its git common dir. When the strict reader refuses the machine config for another key, `pm_data` is read and checked on its own. The main-checkout rules then apply there, and a refusal names no new worktree to make (agents do not work in it). `git push` and `git worktree remove` act on the repository the data worktree shares with the kit, so from it they are judged by the kit's own `.kit.json` (refused when it does not load), and the data branch alone by the data worktree's. A main checkout is never changed. Fail closed (rule `pm-data`, subagent writes): a machine config whose `pm_data` does not read denies every one; a linked worktree whose record or HEAD does not read denies those aimed at or run from a linked worktree of that repository. Tests: tests/guard/test_rules.py `PmDataPlace`.
- **Config:** `.kit.json` of the main checkout a path belongs to, via `kitlib.config.load`. A worktree's own `.kit.json` is never read, so a branch cannot loosen its own rules. The one exception is the PM data worktree, which counts as MAIN: its own `.kit.json` is read (none there: the defaults, under which a subagent may not edit it).
- **PM data copies and aliases:** `Ctx.pm_root` reads the root commit from the record in the git common dir of the machine config's `pm_data.path` (none when the machine config names no `pm_data` or that repository has no record; a record or config that does not read, or a `pm_data.path` git cannot place, is an error, and the rules fail closed). `Ctx.gitread` (`kitlib/guard/gitread.py`) runs git for the three reads the PM-data rules need: `config --get alias.<name>`, `rev-parse --verify --quiet <root>^{commit}` with `GIT_NO_LAZY_FETCH=1` (exit 0 holds it, 1 does not; any other answer, 128 or a timeout, is an error) and `rev-parse --is-shallow-repository`. Only a non-owner session's push, send-pack, http-push or remote helper from a repository without a record, on a machine whose config names `pm_data`, and a non-builtin git subcommand in a repository with a record, or in any repository on such a machine, start them.
- **Lock:** held only when `MACHINE_LOCK_RUN` names a run that `kitlib.lock.run.nest_check` accepts: an ancestor of this process, alive, and holding. The variable alone is never proof.
- **Gate-OK record:** `kitlib.gate.runner.verify_record(root, sha)`, as the pre-push hook reads it. The record must name a `config_rev` in that commit's history, and its gate config hash must be that of the `.kit.json` "gate" the `config_rev` commit holds (docs/gate.md "Gate-OK record"). A record without `config_rev`, or made under another gate config, does not count.
- **User config:** the machine config (docs/kit-json.md "Machine config keys"), for `ledger_path`, `guard_mcp_prefix`, `guard_mcp_tools`, `guard_agent_marks` and `guard_mark_roots`, read tolerantly (a value that is not a string or a list of strings, such as `guard_mark_roots`, is dropped when the strict reader refuses the file). A file the strict reader refuses still yields an absolute `ledger_path`, so the ledger stays protected. A file that cannot be read, is not JSON or is not an object denies every subagent write (rule `ledger`, fail closed). The file is the one `kitlib.config.user.locate` names, taken once per call (`Ctx.config_location`): the new folder's, or the retired folder's while the new one has none; a location it cannot tell (`BAD`) denies every subagent write too (docs/kit-json.md "Moving the machine config folder").

**Shell writes** (`kitlib/guard/rules.py` `write_targets`):
- Redirects.
- PowerShell write cmdlets and their aliases, with parameters matched by prefix. These include `Set-ItemProperty` (`sp`), `Start-Transcript`, `[IO.File]`/`[IO.Directory]` calls and `[IO.StreamWriter]`/`[IO.FileStream]` constructors (`::new(...)`, `New-Object`, a StreamWriter cast, whose operand is a path the line computes unless it is a plain string such as `'x'` or `('x')`; what follows the `]` past spaces, `<# #>` comments and line continuations is that operand, a unary operator such as `-join` or `-not` included, unless it ends the expression (a line end, `.Name`, `)`, `,`) or is a binary operator such as `-and`, where the type is a value; a FileStream opened `Open`, `Read` writes nothing unless it names FileOptions, a sixth argument such as `DeleteOnClose`; `rules.net_writes`, `rules._net_cast`, `rules._net_ctor`). A StreamWriter constructor (`::new`, `New-Object`) whose first argument is not a plain string is judged only as a call whose path the guard does not read (below), where the line runs and where its process started, so `[IO.StreamWriter]::new($stream)` from a worktree is not refused. `\\?\<drive>:\x` and `\\.\<drive>:\x` are judged as `<drive>:\x`; a share path (`\\host\<drive>$\x`) is one the guard cannot place (`rules.NET_DEVICE_RE`, `rules.net_placed`). .NET reads a relative path against the process's directory, which `Set-Location` does not move, so such a call on a relative, driveless or computed path is refused (`main-checkout`, or `write-jail` for an agent session) with the call on the absolute path as the alternative; a literal absolute path is judged as the file written (`Copy` writes its destination, `Move` and `Replace` their paths; `rules.dotnet_unplaced`, tests/guard/test_dotnet_paths.py). `OpenRead` and `OpenText` are reads. A call whose path the guard does not read (inside a quoted word, a method named with no `(` after it, as before `.Invoke`, fewer arguments read than the ones it writes, or arguments holding a smart quote, a here-string, a `#`, a `${`, or a `$(` beside a `"`, where the parse may lose its place) is judged as a write to the directory the line runs in (`rules.net_writes`, `rules._net_lost`), and so is one on a path the guard cannot place, under the repository's roles there, for every session (`rules.write_targets`). Such a call is also judged in each directory its process may have started in, the one the event names and the location of each command it is nested in (before and after a `cd` in that command's `$( )`, `shell.Command.subs_cwd`), so a `Set-Location` from the main checkout into a worktree does not clear it (`rules.dotnet_process_dir`); a session that runs outside a worktree of its own (in the main checkout, or outside any repository) is told to give the call literal absolute paths, since a new worktree does not move where its process starts.
- cp, mv, rm, touch and tee; `sed -i`, `perl -i` and `patch`.
  - cp, mv, ln and install (`rules.CopyArgs`) write the directory `-t` names, also inside a cluster (`-rt <dir>`, `-t<dir>`) or as `--target-directory[=]<dir>` or any unique prefix of it; else the last operand. A long option that is unknown or ambiguous, or an option that is not literal, makes every operand a target. mv also writes its sources; `install -d` writes every operand; `ln <target>` alone writes the working directory.
- `curl -o` (in `--output-dir` when given), `wget -O` (not `--spider`) and `rsync` (not `-n`/`--dry-run`).
- `robocopy` and `xcopy` from any shell, and cmd copy, del and move.
- These write into the working directory, or into the folder they name:
  - `Expand-Archive`;
  - `tar -x`, from PowerShell too (Windows' own `tar.exe`), or every folder `-C` names, a relative one read from the one before it (`-C <a> -C b` is `<a>/b`; `rules._tar`). A `-C` is read in a cluster after letters that take no value (`-xvC <dir>`, `rules.TAR_FLAGS`), as `--directory` down to `--dir` and as bsdtar's `--cd` (Windows' `tar.exe`), and in an old-style first word, whose letters take their values in turn (`tar xCf <dir> a.tar`, `rules._tar_old`). A `C` that may be another option's value (`-xfC <dir>`, `-NC<dir>`, `--exclude -C<dir>`, after a letter the guard does not know) judges the working directory as well (`rules._tar_word`);
  - `unzip` (or `-d <dir>`; not `-l`/`-t`/`-v`/`-Z`/`-p`);
  - `Start-Process` redirects.
- Code given on the line counts as a write to the working directory: `python -c` or a script on stdin (any `python`, `python3.12`, `py` or `pythonw`), `node -e`/`-p`, `ruby -e` and `perl -e`. `python -c` is read in any spelling (`-Ic`, `-cCODE`, after `-X <v>`, `-W <v>` or `--check-hash-based-pycs <v>`; `rules.py_program`).
  - The one exception: a `python -c` the guard proves reads only is no write (`rules.py_reads_only`). It needs literal code, `-I` among python's own options and no option outside `-I -E -S -s -B -b -d -q -O -u -v -P` (so no `-i`, `-X`, `-W`), imports only from a short list (`rules.PY_READ_MODULES`: `json`, `sys`, `re` without `compile`, `collections`, `itertools`, `math`, and `from os.path import` of read functions), each module used only as `<module>.<name>` from its list, and `open()` called directly with a literal mode of `r`, `b`, `t` or `U` letters and no `opener`. Everything else is an allowlist too, so a shape the guard does not know stays a write:
    - Syntax (`rules.PY_NODES`): assignments, `for`, `if`, `with`, imports, calls, subscripts, literals, f-strings, operators and comprehensions. No `def`, `lambda` or `class` (names the check would have to follow), no `match` (its patterns bind names and read attributes with no name or attribute in the tree), and no `try`, `while`, `del`, `global`, `nonlocal`, `:=`, `await`, `yield` or template string; a node type a later python adds is refused as well.
    - Names: a builtin from `rules.PY_BUILTINS` (`print`, `len`, `range`, `sorted`, `reversed`, `enumerate`, `zip`, `min`, `max`, `sum`, `abs`, `round`, `any`, `all`, `str`, `int`, `float`, `bool`, `list`, `dict`, `set`, `tuple`, `repr`, `isinstance`, `map`, `filter`, `open`), a name the code imports, or a name it stores. `type` and `object` are not on it: from a value they give a class that can open a file another way. A stored name or import alias may not be a builtin's (it would hide the builtin only once the binding runs), a module's or an import's, and no two imports may bind the same name. The builtin names are a list in the code (`rules.PY_BUILTIN_NAMES`, every public builtin up to python 3.14) joined with the running python's own. A builtin a python after 3.14 adds is refused only when the guard itself runs on that python; the list does not cover it.
    - Attributes of a value that is not an imported module: only `rules.PY_VALUE_ATTRS`, the string, list, dict, match-object and file read methods (`read`, `readline`, `readlines`, `write`, `flush`, `strip`, `split`, `join`, `replace`, `format`, `items`, `keys`, `values`, `get`, `append`, `sort`, `group` and the like; the constant lists them all). A file object's `buffer`, `raw` and `name`, and any class attribute, stay out. `write` is safe there: the only files the code can hold are ones `open()` opened for reading and `sys.stdout`/`sys.stderr`. An attribute is only read, never assigned.
    - Identifiers: no name, attribute, import alias or keyword argument starts with `_`, is a frame identifier (`gi_frame`, `f_globals`; `rules.PY_FRAME_ATTR_RE`) or is one of `rules.PY_DENIED_NAMES` (`exec`, `eval`, `compile`, `open`, `getattr`, `setattr`, `delattr`, `globals`, `locals`, `vars`, `breakpoint`, `help`, `type`, `object`, `super`, `input`); `open` passes only as the read call above.
    - PowerShell: when PowerShell is anywhere on the way to python (the line's shell, or the shell around a `bash -c`), code holding a double quote or a backslash is a write, and so is the run when any word of a PowerShell command on the way (python's own, or the `bash -c` text) holds a double quote, is empty, or holds a blank and ends in a backslash (`rules.ps_native_unsure`). Windows PowerShell 5.1's native-argument quoting can hand python other text than the guard read: it passes an inner double quote unescaped, drops an empty argument (so `python -I -c '' "<code>"` runs the second word), and wraps an argument with a space in quotes without doubling a trailing backslash.
    - Start-Process (and its aliases `start`, `saps`): a python it starts is never proved. It gets one command line the guard re-splits with the quotes taken out, so the code python reads is not the word the guard read. The directory it writes is the command's own and also its `-WorkingDirectory` when one is given (`commands.run_dir`, "Parsing").
    - These two checks (the PowerShell word and Start-Process) cover every python run, a script or module too: `python tools/x.py --note ''` from PowerShell is a write of its working directory, since python may get other words than the guard read.
    - Empty or blank code is a write through any shell.
    - cmd.exe: when cmd.exe is anywhere on the way to python (`cmd /c`), every `python -c` is a write. cmd ends a quoted part at a `\"` that python reads as a quote, and keeps `print(...)` one word where the guard's cmd reading splits it at the `(`.

    Code that does not parse, or anything else, stays a write. So `python -I -c "import json,sys; print(json.load(open(sys.argv[1]))['a'])" x.json` runs in a main checkout, and the same without `-I` does not: without it python puts the working directory first on `sys.path`, where a `json.py` would be imported instead (tests/guard/test_pyreads.py; tests/guard/extra_rows.py). The `main-checkout` refusal of a `python -c` names this `python -I -c` form (`rules.PY_C_HINT`, `rules.PY_C_RUN_RE`).
- find `-delete` writes to find's paths.
- A writer that a bash find's `-exec`, `-execdir`, `-ok` or `-okdir` runs writes to find's paths too, when the guard cannot place its target (`rules.find_exec_writes`). That target is:
  - the `{}` find fills in;
  - a path the nested line computes, such as the `"$1"` of `sh -c 'rm "$1"' _ {}`;
  - a relative path at `-execdir`'s unknown place.

  Each start path of each find around the writer is judged as its target, or the directory find runs in when it names none, through any shell nested between (`rules.find_runs`). So `find <outside> -exec rm {} +` from a worktree is refused as `find <outside> -delete` is, and the alternative runs the same find on the worktree; `find <outside> -exec grep -l x {} +` still reads. A start path the guard cannot place passes from a worktree, as any target does (tests/guard/test_jail.py `ShellForms.test_find_exec_writer_is_judged_where_find_searches`).
- A writer fed by `xargs` with no literal target writes the working directory.

A write target that is not literal (a variable, a substitution) is denied when the command runs in a main checkout or a place the guard cannot tell (fail closed). Under PowerShell it is denied from every location (`rules.shell_writes`): a linked worktree or any other place git can tell, a main checkout, a place git cannot tell and an unknown location (after a computed `cd`) alike, since one `$p` or `(Join-Path ...)` can name the main checkout. The `main-checkout` rule refuses a role that may not edit one, and `write-jail` refuses any other agent session, the coordinator's mark in a main checkout included (`rules.ps_drive_jail`). The owner's session is not held. So `Set-Content $env:TEMP\x.txt` from a worktree is refused; name the temp path literally. `-Path: x`, a colon then a space, binds the next word as `-Path x` does, and `-Destination:$p` binds its computed rest to `-Destination` (`rules.ps_params`, `rules.PS_NAMED_DYN_RE`); an en dash, an em dash or a horizontal bar names a parameter as `-` does (`shell.PS_DASHES`). A PowerShell argument in `( )` (`Set-Content (Join-Path a b) x`, `-Path:(...)`, `-Destination(...)` touching its parameter, and a `( )` touching any other word, which PowerShell passes as the word and then the `( )` as the next argument: `Copy-Item a.txt(...)`, `Set-Content(...)`, `'x'(...)`, `$x(...)`, `[string](...)`) is one such word whose commands are read as nested ones (`shell._Scan.ps_paren_arg`), unless the command's first word, or the first after an assignment's `=`, is a keyword that takes one (`if`, `foreach`, `while`, `switch`; `shell.PS_PAREN_KEYWORDS`, `shell._ps_keyword_led`): `Copy-Item data (...)` passes an argument. A `(` that does not touch the word before it is an argument whatever stands between: a space, a comma, a redirection (`Set-Content -Value hi 2>&1 (...)`), a backtick line continuation or a `<#comment#>`. A redirection to a `( )` or a `{ }` (`'x' > (Join-Path a b)`, `'x' > { ... }`, which writes to the script block's text) is a target that is not literal, and the `( )`'s commands are read as nested ones (`shell._Scan.target`). A `( )` inside a word's `[ ]` index is part of that word (`$x[(...)]`, `shell._Scan.word`). A `(` touching a member access (`$s.Replace('a','b')`, `'abc'.Replace(...)`, `[IO.Path]::Combine(...)`, `(Get-Date).AddDays(1)`; `shell._PS_MEMBER_HEAD`, `shell._PS_MEMBER_TAIL`) is a method call: the `( )` stays a group and the word, the method's result, is not literal, judged where it binds like any other word. Every PowerShell writer is also held by one coarse rule that does not depend on how the scanner read a `(` or a `{` (`rules.ps_unread`): a write cmdlet, an `Export-*` cmdlet, a copier (`robocopy`, `xcopy`), and `curl`, `wget` or `tar` run from PowerShell write a target that is not literal, standing for what the guard does not read, when any argument is not one it reads. A cmdlet's argument must be a plain word or string, a variable, or a string holding variables (`rules.PS_CMDLET_ARG_RE`); a native program's a plain word or string (`rules.PS_PLAIN_ARG_RE`), since PowerShell spreads a splat, or an array in a variable, into its arguments. An `Export-*` cmdlet with no spec has every positional, word after a parameter and colon value judged as its path, bar the value of `-InputObject`, `-Depth`, `-Encoding` or a common parameter (`rules.ps_export_targets`). The one value of a parameter that names no path (`rules.PS_VALUE_PARAMS`: `-Value`, `-Encoding`, `-Filter`, `-NewName` and a few more) is passed over when it holds no command: a word, string or variable, a `( )` the scanner reads as one word, or a here-string with no `$( )`, with member calls on plain arguments after it (`-Value $s.Trim()`, `-Value (Get-Date)`, `-Value @'...'@`; `rules._ps_value_end`); a `$( )` (`-Value "at $(Get-Date)"`), and a positional `( )` or here-string, which could be the path, are not. A splat (`Set-Content @a hi`, `robocopy . @a`), a script block (`-Path { $p }`, a delay-bind `-NewName { ... }`), a type's member call (`[x]::y(...)`), a `( )` touching a group's `)` (`$a.M(1)(...)`), a word after an unquoted comma (an array binds to the parameter before it: `-Value 'a','b' x`), and a command that is split (below) or followed by a `( )` or `{ }` no value accounts for each make such a target. So `Remove-Item a.txt,b.txt` and `curl.exe -o x.txt -H $h` are refused from every location. A PowerShell redirection whose target is not one plain word, string or variable (`'x' > ` followed by a line continuation and `(...)`), or that has none the scanner read (`'x' > <#c#>(...)`), is a target that is not literal too (`rules.write_targets`). When more of the command follows a group, a method call's included, before a separator (`Set-Content -Value $s.Trim() -Path x`, `Sort-Object { $_.Length } -Descending`), the scanner has read the rest as commands of their own, so the command is marked split (`shell.Command.split`): `rules.ps_unread` stands for the arguments past the group, and the line is not clean (`commands.expand`), which `fallback.check` refuses as `unreadable` for a role subagent. A keyword's own `( )` and `{ }` (`if (...) { }`, `$r = if (...)`, `foreach`, `try`, `catch [T] { }`, `function f(...) { }`) split no command (`shell._ps_keyword_led`), which reads only a keyword or `=` spelled bare: a quoted `'if'` or `'='` is an argument. Two exceptions: `$PWD` or `${PWD}` with a literal rest (`"$PWD\x.txt"`) is read as the directory the command runs in plus that rest, and judged as a literal path, unless that directory is unknown or the write is not the line's only command (`rules.ps_pwd_path`). `$PWD` can be set under many spellings of its name (`sv PWD`, `-OutVariable ('P'+'WD')`, `[scriptblock]::Create(...).Invoke()`), and only code that runs before the target is read can do it, so a write fails closed when an operator stands before or after it (a `;`, `&&`, `||`, newline or pipeline, a script block or `( )` group it is inside, or one among its own arguments: a method call's `( )` or a script block `{ }`), or when a word of its own runs code (an argument `( )`, an index `[(...)]` or a `$( )`): `Set-Content "$PWD\x.txt" x` is judged as a path, and `Set-Content a.txt x; Set-Content "$PWD\x.txt" x` is refused. A line whose write target does not use `$PWD` is not held by this. And `$null` is no file. Under bash and cmd a target that is not literal is not denied from a linked worktree or any other place git can tell. A `cd` inside a PowerShell `$( )` or argument `( )` moves the location for the command holding it and every later one, so their directory is unknown (`shell.track`).

### Kit paths in advice

An alternative that runs a kit tool (`rules.lock_tool`, `rules.kit_tool`, the `wrapped-gate` alternative's `rules.bare_wrapper`) names it under one folder, `rules.advice_kit`: the installed export the session's kit tools run from, the folder the session header names as `<kit>`, when the guard can tell it, else the kit the guard runs from (`Ctx.kit`).

- A guard that runs from an export (`.pm-kit-export` in `Ctx.kit`) names that export.
- A guard that runs from a kit checkout names the export the machine's plugin marketplace names now (`kitlib.pluginsource.current_folder` under the `plugin` `export_dir` of the user config, default `%LOCALAPPDATA%\pm-kit\plugin`), when that folder has a 12-hex-digit name and holds `.pm-kit-export` and `kit.json` (`rolepolicy.EXPORT_NAME_RE`, `rolepolicy.EXPORT_FILES`) and its marker names this checkout (`kitlib.pluginsource.export_checkout`).
- Otherwise (no user config, no marketplace file, an export made from another checkout) it names `Ctx.kit`.

The hook is not told which folder the session's header named, so a session started on an older export is pointed at the current one. The `heavy` rule lets an interpreter run that export's `tools/gate.py` and `tools/machine_lock.py run` as it does the kit's own (`rules.kit_wrapper` through `rolepolicy.kit_export`, which takes any export folder right under the export root, the current one or not, that is neither inside nor holding a folder the session may write), so an alternative the guard gives is not itself refused as heavy (tests/guard/test_advice_workdir.py).

## Write jail

`kitlib/guard/jail.py` (roots and verdicts), `kitlib/guard/rules.py` `write_jail` and `git_jail` (rule `write-jail`). It holds agent sessions only, as `kill-by-name` does ("Session mark"): subagents and the marks in `guard_agent_marks` (default `coordinator`, its old name `conductor` (removed after the switch), `deep-worker`, `consultant` and `pm`). The owner's unmarked session and other marks (`plain`, another agent's name) are not held. Tests: tests/guard/test_jail.py.

- **Write roots** of a session running in `<cwd>` (the hook payload's `cwd`):
  - **its checkout:** the git top of `<cwd>`. In a linked worktree that worktree alone, so the main checkout is outside. A session running in a main checkout gets the whole checkout (the `main-checkout` rule still holds a subagent there). Outside git, `<cwd>` itself, unless it is a drive root or the home folder. No own root at all when that root is on, over or inside either machine config folder (`jail.own_root`, `jail.config_dirs`): a session run in `<config-dir>` would otherwise write the machine config, its guard settings and `ledger_path` among them (tests/guard/test_jail_config_move.py).
  - **its repository's worktrees:** every linked worktree of the repository `<cwd>` belongs to that lies under its main checkout (`jail.sibling`), so a session in one worktree reaches the others, as a session in the main checkout does through its checkout root. A worktree a subagent makes with `tools/new_worktree.py` from a linked worktree is therefore writable. Not the main checkout itself, not the PM data worktree (the guard places it as a main checkout; while it cannot tell which worktree that is, `Ctx.pm_data_error`, no worktree is reached this way), not a worktree on, over or inside a machine config folder, not another repository's worktree or a worktree outside the main checkout, and not a path a link carries out of its worktree (the target is compared after `realpath`). It is not a listed root: the refusal names the roots above and points at `<cwd>`'s own checkout.
  - **temp:** the system temp folder (`Ctx.tempdir`, and `TMP` when it differs), which holds Claude Code's session scratch folders; and the folder the `AGENT_TEMP` environment variable names, when it is set.
  - **data roots:** `.kit.json` `guard.data_roots` (docs/kit-json.md), read from the main checkout only, as every `.kit.json` key is. Each entry is `{path, mode, why}`: `open` (any write), `add-only` (new files only: a write, move or delete of a file that exists is denied; a copy, move or link into the existing folder is judged as `<folder>/<each source's name>`, `rules.copy_into`, when its options are only these: cp `-r -R -a -p -v -n -t`, `--recursive`, `--archive`, `--verbose`, `--no-clobber`, `--target-directory`; mv `-v -n -t` and the same long ones; ln `-s -v -t`, `--symbolic`, `--verbose`, `--target-directory`; install `-v -m -t`, `--verbose`, `--mode`, `--target-directory`. Any other option, or two target directories, is judged as the folder itself, so it is denied. cmd's copy is judged by name only for a source that is an existing file) or `read-only` (no write). A mode holds wherever the folder nests: a read-only folder inside the checkout or temp stays read-only. The kit names no folder.
  - **mark roots:** the machine config's `guard_mark_roots` (docs/kit-json.md), `{<mark>: [{path, mode, why}]}`, adds roots for the main sessions of one launcher mark, compared without case (`jail.mark_roots`, `rules.session_mark`). `path` is absolute or `~/<path>`, read from the home folder; the modes are the data roots' modes. A subagent gets none, not even one of a marked session. A root that is either machine config folder, holds it or lies inside it is dropped ("No root on a machine config folder", below), so no session is given its own guard settings, nor can create the new config file that would replace an old-only one. The schema refuses a reserved mark (`owner`, `subagent`), a relative path and an unknown mode, and a config the strict reader refuses gives no mark roots ("State": the tolerant read keeps no map). The PM's roots (its memory folder, say, or a repository's main checkout whose red landing merges it resets) are set here by the owner: the jailed PM cannot write the machine config. The intended use is folders like those, other repositories' main checkouts above all. A mark root should not cover the account folder `~/.claude` (its `settings.json` registers this hook; the live lock tool is under `tools/machine_lock`) or the kit's own checkout (`boot/hook.py`, `kitlib/guard`): a root there lets the session rewrite the guard itself. Only the machine config folders are dropped by the code. The `lock-state` and `kit-json` rules come first ("Order"), so a mark root never opens the machine lock's state or a `.kit.json`.
  - **No root on a machine config folder:** a root of any kind (checkout, temp, data, mark) that is either machine config folder, the current or the retired one (`jail.config_dirs`; docs/kit-json.md "Moving the machine config folder"), holds it or lies inside it is dropped unless it is read-only (`jail.roots`, `jail.touches_config`): a data root, `TMP`, `AGENT_TEMP` or the system temp folder at the home folder or above would otherwise let the session write the machine config. A read-only root only denies, so it is kept (tests/guard/test_jail_config_move.py).
- **Paths** compare after `os.path.realpath` and `normcase`, so `..`, symlinks and junctions are resolved: a junction in the worktree that points out of it is outside.
- **File tools:** Edit, Write, MultiEdit and NotebookEdit, by their target path.
- **Shell writes:** every literal target "Shell writes" (above) lists. Under bash, `/dev/...` is no file and passes, and `/tmp/...` stands for the folder `AGENT_TEMP` names, else the system temp folder (Git Bash's mount table is not read).
- **git:** a subcommand that writes is judged by the checkout it runs in (`-C`, a `cd` before it, else `<cwd>`), so `git -C <another repository> commit` is denied and `git -C <a worktree of the same repository> commit` passes. `update-ref` is judged from every checkout as well, by `git-shared-ref` ("Rules"): the refs it writes are shared by every worktree. The subcommand is the first word after git's global options, each in `commands.GIT_VALUE_OPTS` (`-c`, `--namespace`, `--super-prefix`, `--config-env`, `--exec-path`, `--attr-source`, `--shallow-file`) skipped with the word after it, so `git --attr-source HEAD update-ref -d refs/heads/main` is read as `update-ref`. Reads pass anywhere: `status`, `log`, `diff`, `show` and the other names in `rules.GIT_READS`; `stash list`/`show`, `worktree list`, `remote` (`show`, `get-url`), `reflog`, `notes` and `submodule` without a writing verb; `branch` and `tag` listing; `config` reads; `archive` (`rules.archive_outputs`), unless it carries `--remote` or `--exec` (they run a program), an option the guard does not know or a word that is not literal, or the line may give it a program to run (`rules.archive_filter_set`): a `-c` whose key is not on `rules.ARCHIVE_SAFE_KEY_RE` (`core.quotepath`, `core.autocrlf`, `core.eol`, `tar.umask`, `tar.<format>.remote`; another may name `tar.<format>.command`, a `filter.<driver>.smudge` or `.process`, an attributes file or an `include.path`), any `--config-env`, a word before the subcommand that is not literal, a `GIT_*` variable outside `commands.GIT_SAFE_NAMES` or a user config folder moved (`commands.HOME_ENV_NAMES`) on the line, `--exec-path=` or a `PATH` change on the line (`Command.path_env`: they say where git finds a filter's bare program name, as Git for Windows' `filter.lfs.process = git-lfs filter-process`), or a git the text cannot place (below). A change counts in every spelling `commands.line_env_names` reads: cmd's own `path` command with anything after it (`path X`, `path=X`, `path;X`, `path ;`, `@path X`, `@ path X`; a bare `path` only prints it, `commands.cmd_path_set`), cmd's `set`, `path` and `call` behind the `@` and delimiters (`,` `;` `=`) cmd drops before a command name, as a prefix or as words of their own (`@set PATH=X`, `;set HOME=X`, `@ set GIT_DIR=X`, `commands.cmd_invocation`), and a PowerShell item, content or property cmdlet (Set-Content, Add-Content, Clear-Content, Clear-Item, Remove-Item, Set-ItemProperty and their aliases) on the environment drive in any spelling (`env:X`, `Environment::X`, `Microsoft.PowerShell.Core\Environment::X`, any case, positional or `-Path`/`-LiteralPath`; `commands.ENV_DRIVE`), a wildcard or a bare drive there counting as a name computed at run time. git runs a filter in the checkout it reads (observed with git 2.55). Each word is read as bash hands it to git (`\-o` is `-o`, `-\c` is `-c`, `commands.passed`); in PowerShell a word 5.1 may split or drop for a program (a `"` in it, empty, or a blank and a trailing `\`, `rules.ps_native_unsure`, observed) fails closed, as does under cmd a word the C runtime may split apart from cmd (a `"` other than one pair around it, or no valid place in the source to read its quotes from, `rules.cmd_native_unsure`). `worktree add <path>` and `clone <url> <dir>` are also judged by the folder they make, and `archive` by the file its `-o`/`--output` names (also `-o<file>`) wherever it sits before `--` (after it, git reads a pathspec): git's first pass (builtin/archive.c `cmd_archive`) takes no value for the other options, so `--prefix -o README.md` opens README.md (`rules.archive_opened`). The guard also counts, failing closed, the forms that pass does not open (`-o` in a cluster such as `-vo`, a prefix such as `--outp=`). So `git -C <main checkout> archive HEAD | tar -x -C <temp>` passes and `archive -o <main checkout>/a.tar` is denied (tests/guard/test_archive_readonly.py). One exception (`rules.lander_check`): the lander role (agent_type `lander`, or the kit plugin's `<plugin>:lander`, "Agent names"; named in the main checkout's `.kit.json` `roles` with `edit_main_checkout: true`, Go-live step 3) may run exactly these commands in a main checkout from its worktree, with `<remote>` and `<main>` the main checkout's `.kit.json` `repo.remote` and `repo.main_branch`:
  - `git fetch <remote>`
  - `git fetch <remote> <main>`
  - `git merge --ff-only <remote>/<main>`

  Each must be alone on its line (`rules.lander_alone`, which reads the event's line again): nothing else, or one literal `cd`, `Set-Location` or `pushd` into that checkout before it, joined by `&&` or `;`. A pipe, a group, a nested shell, `||` or a third command is not alone. git may be spelt `git`, `git.exe` or PowerShell's `& git`, with `-C <main checkout>` or that `cd` before it. Anything else is denied: another option (`--prune`, `--no-ff`, `-s`, `-X`, `--squash`, ...), another ref or refspec (`main:main`, `+main`, `FETCH_HEAD`), a git option before the verb (`-c`, `--config-env`, `--git-dir`, `--work-tree`, `--no-pager`), an environment assignment or wrapper before git (`GIT_DIR=`, `env`), a word that is not literal, any other git write there, a file write there, and every other role. Any main checkout whose own `.kit.json` lets the lander in qualifies, not only the one the lander's session runs in (the PM lands kit branches from its own folder). When a lander's `git fetch` or `git merge` in a main checkout is refused (rule `write-jail`, or `git-main-history` for a merge in a repository that does not set the role), the refusal names the first test that failed, in this order: a `.kit.json` that does not load, `roles.lander.edit_main_checkout` not set (the repository's settings first, since until they allow it every form is refused), not alone, a wrapper or option, the arguments; its `Instead:` is the form to run, or `python -m json.tool "<main>/.kit.json"` when the config is the cause (`rules.lander_refusal`). The lander's own landing command (`land.py`, `gate.py land`) is a python program whose git the guard does not see ("Known limits", "write-jail reads the line, not the program"), so it needs no exception. git whose checkout the text cannot place (a variable from "Git spellings" set, `--git-dir`, `--work-tree`, `core.worktree`, `--config-env`, a computed `-C`, whatever the order of `-C`) and that writes is denied for every session the jail holds, the lander included (`rules.git_jail_unknown`): it may be a main checkout, where `symbolic-ref` or `branch -m` would re-point main's HEAD. The refusal names the cause: for a variable or option it says to drop it and run git in the worktree (`rules.git_unplaced`), for a computed `-C` to name the checkout literally. Only a plain read passes (`rules.git_reads` strict): no word that is not literal, except as `rules.strict_dyn_read` allows in bash and PowerShell (any computed word in `rev-parse`, `ls-files`, `cat-file`, `merge-base` and `for-each-ref`, which have no option that writes a file; in `log`, `show` and `diff` a computed word only when `rules.dyn_head` reads it as one argument that starts with literal text that is no option, as `"HEAD~$n"` or `"origin/$b"`, or with `--format=` or `--pretty=`, as `--format="$w %h"`; `log "$R"`, `log HEAD~$n` unquoted in bash, `"$@"` and a PowerShell array `$f` are denied, and `status`, `describe` and `branch` take no computed word), no PowerShell splat `@a` (`rules.ps_splat`), no `--output` file (abbreviated too) nor `archive -o`, no `grep -O`/`--open-files-in-pager` (it runs a pager program), and `branch`, `tag` and `config` only with options it names in full, so an abbreviation git expands (`branch --unset-up`) is denied.
- **Not judged:** a target that is not literal under bash or cmd (under PowerShell one is refused from every location, "Rules" above), a command other than git whose directory is unknown, and git whose subcommand the text does not name in a checkout the text places. These meet the rules above them (the `main-checkout` rule fails closed in a main checkout) and the fallback, whose parsed rules include the shell writes and so the jail.
- **Order:** `ledger`, `lock-state`, `kit-json`, `generated-file` and `main-checkout` are checked first, so a subagent's edit of a main checkout still reads `main-checkout`.

## Generated files

`kitlib/guard/generated.py` `source(top, rel)`; rule `generated-file` (`rules.generated_file`), checked
with the other edit rules for a file tool's target and each shell write target (decision 19 in

A repository that is not the kit, a hand-written file in a host's shell (`scripts/`, `mcp/`, the
Claude hub page) and the sources themselves pass. tests/guard/test_generated.py.

## Role policy

`kitlib/guard/rolepolicy.py`, run by `decide` on a call the shared rules allow (a call they refuse is refused as before), the same on every host (ARCHITECTURE.md "Roles"). Lifted from the Codex branch's `guard_adapter` and `kit_adapter`.

- **One switch per repository:** the policy runs only when the main checkout's `.kit.json` sets `guard.role_policy: true` (docs/kit-json.md; default false). With it off no role is held, whatever mode a role file or the `roles` table names, and every call is judged exactly as before. Which repositories turn it on is the owner's call; the kit's own repository has it on.
- **Where a mode comes from:** `roles.<role>.mode` in that `.kit.json` (a key under the role's old or new name counts: `roles.opus-worker` holds `senior-worker`, `config.policy.role_name` and `kitlib.content.names_of`), else the `mode:` line of the role's file, `content/roles/<role>.md` under the kit the guard runs from (`Ctx.kit`; docs/content.md "Role front matter"). `kitlib.content.role_mode` reads the role files once per process and reads an old name as its new one (`opus-worker` as `senior-worker`, `kitlib.content.ALIASES`, the launcher's alias table). A role with neither is not held. When the kit has no `content/roles` (a release built without it) or a role file does not parse, the roles it cannot read are not held and the guard goes on; nothing raises.
- **The kit's modes** (the role files): `controller` pm, coordinator; `write` weak-worker, worker, strong-worker, senior-worker, deep-worker, asset-smith, sound-smith, tech-artist, spec-writer, records; `read` reviewer, researcher, consultant; `test` test-runner; `lander` lander.
- **The role:** a subagent's role (`config.policy.role_name`: `Action.agent_role` when the `roles` table or a role file names it, else `subagent`); a main session's launcher mark when one of them names it; else `main`. Claude Code sends a kit subagent's type as `pm-kit:<role>`; the adapter drops exactly that prefix, so the name the policy sees is the role file's stem (another plugin's prefix names no role). The owner's own session ("Session mark") is never held, and the policy reads nothing for it.
- **Modes:** `controller` (pm, coordinator) and `write` (builders) get `role-workdir`, `role-shell` and `role-lock` alone: CLAUDE.md, `.claude/` and the other owner paths stay under the owner-approval rules (`owner.paths`, pre-push), so an owner-approved agent edit of one is still possible. `read` (reviewer, researcher, consultant) and `test` (test-runner) edit nothing in their checkout and have it read-only to shell; `lander` edits nothing in its checkout (its git landing is `rules.lander_check`'s, as before). All three keep temp and their scratch folder, and have the owner paths read-only.
- **`writes`:** a role file may name repo-relative paths or globs (`writes: [docs/ops/consultant-notes.local.md]`; a `*` stays inside one path part) that its `read`, `test` or `lander` role may still edit in its checkout with a file tool, that role alone. The consultant's notes file is the one in use (the launcher's default `--notes-path`). A shell write to such a file stays refused: the jail's roots are folders.
- **Rules:**
  - `role-edit`: a file-tool edit inside the session's checkout by a `read`, `test` or `lander` role, unless its role file's `writes` names the file. An edit outside the checkout (temp, the scratch folder) is the write jail's, as for any session. Its `Instead:` is prose (return the change in the report), the one rule whose alternative is not a command.
  - `write-jail`, with more roots for `read`, `test` and `lander`: every host's owner paths (`hosts.json` profile `owner_paths`: on Claude `CLAUDE.md` and `.claude/`) in the session's checkout are read-only, and for `read` and `test` the checkout itself (not for a file-tool edit of a `writes` file). In a main checkout an owner path that holds the host's worktrees folder (`.claude/` holds `.claude/worktrees`) is left out, so the worktrees under it stay writable. The roots are added to an in-memory view of the `.kit.json`; the file is never changed. A script in temp or the scratch folder (`python <scratch>/check.py`) and output redirected there (`gate.py --full > <temp>/gate.log`) pass. Code the jail cannot read, `python -c` and a script on standard input (`python3 - <<'EOF'`), is judged as writing the folder it runs in: refused in the read-only checkout, allowed from temp, and the refusal's alternative names temp (`jail.destination` skips a root a read-only root holds). A `python -I -c` that `rules.py_reads_only` proves reads only ("Shell writes") is no write and runs in the checkout (tests/guard/test_rolepolicy.py `test_inline_code_the_guard_proves_reads_only_runs_in_the_checkout`).
  - `role-workdir`: a shell call whose own working directory (`Action.workdir`, from a host whose shell call names one; Claude's does not) is outside the checkout the session runs in. Another drive is outside.
  - `role-shell` (`shell_gap`): an interpreter that would wait for input on the terminal, nested shells included. Only the interpreter's own options count: they end at the first operand, the script (python, bash, a PowerShell file), the word after `-c` or `-m` (python, bash), after `-Command`, `-File` or `-EncodedCommand` (`-e`, `-ec`; PowerShell) or after `/c` (cmd), so every later word is the program's (`python -m pytest -s`, `python x.py -i`, `bash -c "echo hi" -`, `pwsh -File x.ps1 -n 5` pass). Refused: bash, sh, cmd, PowerShell or python with no arguments; with `-` (bash `--` too) and nothing after it; with `-i` (python, bash), bash's `-s`, PowerShell's `-Interactive` or `-NoExit` or any prefix of it (`-noe`), or cmd's `/k` among its own options; and any of them whose own options name no script, command or informational option (`python -u`, `pwsh -NoProfile`). python's `-s` is "no user site", not standard input. When its standard input is a pipe, a heredoc, a here-string or a `<` file, bare, `-` and bash's `-s` read the script from it and pass (`python3 - <<'EOF'`, `echo x | python3`); `-i`, `/k` and `-NoExit` stay refused. `bash -c bash` is caught at the inner bash. Codex's refusal of `apply_patch` run as a shell command is Codex's own and stays in its adapter.
  - `role-lock`: `machine_lock.py` run with a verb outside the mode's list (`rolepolicy.LOCK_VERBS`), or with `--force` in any abbreviation (`--forc`; `--for`, the hold window option, is not one). The rule fails closed: any command whose words, heredoc body, here-string or `<` file name the lock CLI is a lock call (`rolepolicy._lock_seq`), and the words after the first one naming it are the lock's (`rolepolicy._lock_words`). A word names it when its base name is `machine_lock.py` in any spelling Windows opens as that file (`rules.is_lock_script`, shared with rule `owner-lock`: any case, trailing dots and spaces, a `::$DATA` stream; `tools/MACHINE_LOCK.PY`, `tools/machine_lock.py.`, `'tools/machine_lock.py::$DATA'`, each seen to open the file on Windows 11; a colon with no stream after it, `machine_lock.py:`, does not open and is not it) or it is a module name of it (`rolepolicy.LOCK_MODULE_WORD_RE`: `tools.machine_lock`, `machine_lock`). The text a command reads on standard input (`rolepolicy._fed`: a heredoc's body, a here-string's text, a `<` file's name) and every word after a python word (`-c` code, runpy's module) are read as code, naming it when they hold `machine_lock.py` or the module's name standing alone (`rolepolicy.LOCK_MODULE_CODE_RE`; `tests.lock.test_machine_lock` and `tests/lock/test_machine_lock.py` do not). Such a call is judged by its verb only when its program runs the lock CLI itself (`rolepolicy._run_words`: `machine_lock.py` is the program, python's script, or python's `-m` module whose last dotted part is `machine_lock`, `rolepolicy._lock_module`; its verb is the words after that script or module, so `python -X machine_lock -X status tools/machine_lock.py stop 42` runs `stop`), or is a launcher the guard does not unwrap (`rolepolicy.LOCK_LAUNCHERS`: `winpty`, `uv`, `setsid`, `watch`, Git Bash's `start`, `bash`, `cmd`, `pwsh` and the like) whose words name it once, as the script or `-m` module of the python it launches, with its output staying (`rolepolicy._launched`: `winpty python tools/machine_lock.py status`, `bash -c "python tools/machine_lock.py status"`, `bash <<'EOF'` with that line as its body). A python word counts only when it is the program launched (`rolepolicy._launch`, reading the launcher's own options): the words after a shell's `-c` text are its `$0`, `$1`, ..., not its command, so `bash -c 'python "$1" hold create x' python tools/machine_lock.py status` (sh, zsh, dash, ksh, `uv run sh -c` alike) and `bash script.sh python tools/machine_lock.py status` are `HANDED_ON`; in a line the guard does not read as commands (a shell a program launcher starts, `uv run sh -c '...'`) the python must open the line, and a word there holding the lock's name glued to other text (`uv run sh -c 'f=tools/machine_lock.py; python $f stop 42'`, `setsid sh -c "cat tools/machine_lock.py|python - stop 42"`) is `HANDED_ON` too (`rolepolicy._hidden_launch`, matching the name standing alone, so `uv run python -m unittest tests.lock.test_machine_lock` passes). A lock call, or an exempt read below, is `HANDED_ON` as well when a later command may read its last word back (`rolepolicy._last_words`): bash's `$_` or `${_}` (`echo tools/machine_lock.py; python "$_" stop 42`), `$!`, `${!`, a lone `_` or `BASH_COMMAND` (`rolepolicy.BASH_LAST_RE`), PowerShell's `$$`, `$^`, `$Error` or `$MyInvocation` (`gc tools/machine_lock.py; python $$ stop 42`), a `*-Variable` cmdlet given such a name or one that is not a plain name (`(gv '$').Value`), and for an exempt read PowerShell's `$_` or `$PSItem` too. A command that names no program the guard can read (`rolepolicy.NO_PROGRAM`, "in a command that names no program") is a lock call too, in every mode, when any of its words names `machine_lock.py`: an assignment alone, with or without spaces (`$c=gc tools/machine_lock.py -Raw`, `$x+=gc ...`, `${x}=gc ...`, `$global:x=gc ...`, `$x, $y = gc ...`, bash `x=$(<tools/machine_lock.py)`), a value kept for splatting (`$a = 'tools/machine_lock.py','stop','42'; python @a`) or a bash `for f in tools/machine_lock.py`, since its value may reach a program later on the line. Its words also name the lock CLI when they hold the module's name standing alone (`$m = 'tools.machine_lock'`, `'machine_lock','stop'`), a `|` beside it too, since PowerShell can split the word before python sees it (`$a = 'tools.machine_lock|hold|create|x' -split '\|'; python -m @a`, `$m = 'tools.machine_lock|x'; python -m $m.Split('|')[0] stop 42`). The one exception is a pattern only compared on a line that runs nothing (`rolepolicy._pattern_only`): the whole of a bare `Where-Object`'s (`?`, `where`; `rolepolicy.PS_FILTERS`) `{ }` block is `<left> <op> <pattern>`, `<op>` one of `rolepolicy.PS_MATCH_OPS` (`-match`, `-notmatch`, `-like`, `-notlike` and their `-i` and `-c` forms; not `-split` or `-replace`, which hand pieces on), the pattern is literal, and every other command of the line, nested ones too, is named bare from `rolepolicy.PS_TEXT_LINE` (the readers and printers below, the filters, `Format-Table`, `Format-List`, `Select-Object`, `Sort-Object`) or is git as the git reads below allow it. There the module's name next to a `|` is a regex alternative (`rolepolicy.LOCK_MODULE_TEXT_RE`), so the read-only env listing `Get-ChildItem env: | Where-Object { $_.Name -match 'MACHINE_LOCK|KIT|GATE' } | Format-Table Name, Value; git -C <worktree> status` passes, while the same block on a line that also runs python, another program or `git -c ...` is refused (tests/guard/test_rolepolicy.py `test_the_module_name_next_to_a_pipe_split_apart_is_a_lock_call`). A heredoc's or here-string's text stays read with `rolepolicy.LOCK_MODULE_CODE_RE`. Any other program given it is refused, in every mode (`rolepolicy.HANDED_ON`, "its path handed on to another program"), since it may copy, link, store or run it: `cp`, `mv`, `ln`, `install`, `rsync`, `Copy-Item`, `Move-Item`, `Rename-Item`, `New-Item -Value`, `xcopy`; `Set-Variable`, `read`, `mapfile`, `set --`, `printf -v`; `xargs`, `python -`, `python -m runpy tools.machine_lock`, `python -c "...run_module('tools.machine_lock')..."`; a script given the path (`python tools/check.py tools/machine_lock.py stop 42`); and a reader, printer or launcher whose output does not stay (`rolepolicy._output_stays`, below: an assignment, a pipe into `xargs` or anything but a bare reader, a file). So `cp tools/machine_lock.py status; python status stop 42`, `$c = echo tools/machine_lock.py status; python $c[0] stop 42`, `set -- tools/machine_lock.py status; python "$1" stop 42`, `printf '%s\n' tools/machine_lock.py status | xargs -I{} python {} stop 42`, `read a b <<< "tools/machine_lock.py status"`, `read a <<'EOF'` with the path as its body, `python - stop 42 < tools/machine_lock.py` and `$m = Write-Output tools.machine_lock; python -m $m stop 42` are refused, while `echo tools/machine_lock.py status` to the terminal and the lock CLI run itself, captured or redirected (`$s = python <kit>/tools/machine_lock.py status`), are judged by their verb. Not read, a known limit: the value of an environment assignment (on a git line any assignment is refused, above; elsewhere `PAGER='python tools/machine_lock.py stop 42' man x` is not read), git's own configuration in the repository or the user's (`diff.external`, `core.pager`, a `.gitattributes` textconv driver) and `-C` into a repository set up so, a Windows 8.3 short name (`tools/MACHIN~1.PY`), the name glued to other text in one word outside a launcher's unread line (`--file=machine_lock.py`), a transcript PowerShell keeps of the line (`Start-Transcript`), `$MyInvocation` and comments only as far as `rolepolicy.PS_LAST_RE` reaches, a glob the shell expands to the lock CLI (`python tools/machine_lock.p? stop 42`, `gc tools/machine_lock.p? -Raw | python - stop 42`: the guard matches the word's base name, `machine_lock.py`, not the files a pattern finds), and a name the shell, PowerShell or python code builds from pieces (`python "tools/machine_$('lock').py"`, `$p = 'tools/machine_' + 'lock.py'`, bash `${p}lock.py`, `-c "...'machine_' + 'lock'..."`). The one exception is a program that never runs its words (`rolepolicy._lock_path_only`): the kit's own `backlog.py`, `ledger.py` and `commit.py`, as the program or as python's script (`rolepolicy._kit_tool`, `rolepolicy.LOCK_PATH_SCRIPTS`; `backlog.py set --scope tools/machine_lock.py`, `ledger.py add --q "may machine_lock.py run stop 42?"`). The path is made absolute against the command's working directory (the session's, after any `cd` or `Set-Location` earlier on the line) and is exempt only as `<root>/tools/<name>` where `<root>` is the kit folder (`Ctx.kit`), the work-tree root of a checkout, main or linked worktree, of the repository the session works in, when that repository is the kit's (`rolepolicy.kit_checkout`: `kitlib.content.oncommit.is_kit`, `content/roles/` and `tools/render_content.py` there), or an export of the kit the machine runs from (`rolepolicy.kit_export`: a folder named by 12 hex digits, `rolepolicy.EXPORT_NAME_RE`, right under the machine's plugin export root, the machine config's `plugin.export_dir` or else `%LOCALAPPDATA%\pm-kit\plugin` as `kitlib.pluginsource.settings` reads it, holding `.pm-kit-export` and `kit.json`, `rolepolicy.EXPORT_FILES`, and neither inside nor holding a root the session may write, `rules.jail_roots` other than read-only, so a session cannot make one of its own; a pin folder, a machine config the guard cannot read or an export root it cannot name is not one). So `python <worktree>/tools/backlog.py set X --scope tools/machine_lock.py` passes, and `cd <scratch> && python tools/backlog.py tools/machine_lock.py stop 42`, the same relative path in a repository that is not the kit, and a program named bare (`backlog.py ...`, found on PATH) are runs; a reader named bare, not as a path (`rolepolicy._reader`, `rolepolicy.LOCK_PATH_READERS`: `cat`, `grep`, `rg` without `--pre`, `Get-Content`, `Select-String` and the like; `./grep` is some other program); a printer named bare (`rolepolicy.LOCK_PATH_PRINTERS`: `echo`, `printf` but not `printf -v`, `Write-Output`, `Write-Host`); and git's `rolepolicy.LOCK_PATH_GIT` subcommands (`git diff`, `git log`, `git show`, and `git commit`, which records the paths it is given and whose message is text: `git commit -m "lock: fix machine_lock.py" tools/machine_lock.py`) with the path after the subcommand, not in an option's value, and only with plain options (`rolepolicy._git_plain`, refusing rather than allow-listing as `rules.HUB_GIT_DENIED` does): no global option but `-C <path>`, `--no-pager` and `-P` (so no `-c`, `--config-env`, `--exec-path`, `--git-dir`), none of `rolepolicy.LOCK_GIT_DENIED` in any prefix before `--` (`--ext-diff`, `--textconv`, `--output`; `-o` too) nor the subcommand's own `rolepolicy.LOCK_GIT_SUB_DENIED` (commit's `--edit`, `--interactive`, `--patch`, `--reedit-message`, and `-e`, `-p`, `-c` in a short cluster: `rules.HUB_GIT_SUB_DENIED`), no alias, and no environment assignment anywhere on the line (`commands.line_env_names`: `GIT_PAGER=...`, `GIT_EXTERNAL_DIFF=...`, `export ...`, PowerShell `$env:GIT_PAGER = ...`), since an external diff, a textconv filter or a pager git starts is given the path and may run it, and a file `--output` writes is a copy a later command may run. A reader's, printer's or git's output must stay out of a program (`rolepolicy._output_stays`): it sits in no `( )` or `{ }` group or command substitution, and on the whole line every pipe ends in a bare reader and no command redirects into a file (`>`, `>>`), so `cat tools/machine_lock.py | python - stop 42` and `for f in a; do cat tools/machine_lock.py; done | python - stop 42` are still runs. Git's own `--output=<file>` and `-o` are refused (above): the diff text it writes holds the file's lines (`git diff --no-index --output=p /dev/null tools/machine_lock.py` writes every line with a `+` before it), a copy a later command can turn back into the lock CLI and run. In PowerShell a reader, printer or git is not exempt when anything else may catch its output (`rolepolicy._ps_caught`): an assignment or `&` before it, with spaces (`$c = Get-Content tools/machine_lock.py`; written without them, `$c=gc ...` is one word with no program and is refused as `NO_PROGRAM` above), a `( )` or `{ }` beside it (`python (gi tools/machine_lock.py).FullName stop 42`, a delay-bind `gci tools/machine_lock.py | Get-Content -Path { python $_.FullName stop 42 }`), a word holding `{` or `}`, or a common parameter that keeps its output or records in a variable (`rolepolicy.PS_VARIABLE_PARAMS`: `-OutVariable`, `-PipelineVariable`, and `-ErrorVariable`, `-WarningVariable`, `-InformationVariable`, whose records hold the words the command was given: `Write-Host -InformationVariable c tools/machine_lock.py`) as an abbreviation of three letters or more or as `-ov`, `-pv`, `-ev`, `-wv`, `-iv` (`rolepolicy.PS_VARIABLE_ALIASES`); nor anywhere on a line where a PowerShell command may set a variable it does not name (`rolepolicy._ps_variable_reach`): a word holding `PSDefault` (`rolepolicy.PS_DEFAULTS`: `$PSDefaultParameterValues` can give every later command an `-OutVariable`, and `Get-Variable PSDefault*` reaches it by a wildcard), `variable:` or `PSVariable` (`rolepolicy.PS_VARIABLE_WORDS`: the variable drive, `$ExecutionContext.SessionState.PSVariable`), or a `*-Variable` cmdlet (`rolepolicy.PS_VARIABLE_CMDLETS`) given a wildcard (`(gv P*s).Value[...]`); the literal words of a bare reader in no group and not caught are text it searches for or a file it reads, not a variable, so `sls PSVariable tools/machine_lock.py` passes. Not caught, a known limit: a name PowerShell computes from pieces (`Get-Variable ('PSDef'+'aultParameterValues')`). The price of failing closed, accepted: a harmless read that only looks caught is refused in every mode (its words after the name are read as a verb, often `(no verb)`), such as `(gc tools/machine_lock.py)[100..150]`, `(gc tools/machine_lock.py).Count`, `if (Test-Path tools/machine_lock.py) { 'yes' }`, `Select-String -Path tools/machine_lock.py -Pattern '\d{2}'` (a brace, even quoted), a reader on a line with an unrelated redirect or a pipe into a non-reader (`git diff -- tools/machine_lock.py; echo done > x.txt`), a run through a launcher the guard does not unwrap whose output does not stay (`winpty python tools/machine_lock.py status > out.txt`, `$s = bash -c "python tools/machine_lock.py status"`: `HANDED_ON`), a launcher that runs the lock CLI with no python word (`uv run tools/machine_lock.py status`), a heredoc naming the lock CLI that is written to a file or captured (`cat <<'EOF' > notes.md`, `git commit -m "$(cat <<'EOF' ... EOF)"`: the kit's `commit.py -m` is exempt), the module's bare name given to a program that is not a reader or one of the exempt programs above (`python -m pytest -k machine_lock`, `python <kit>/tools/doc_index.py --find machine_lock`), a git read with any environment assignment on the line or a global option but `-C`, `--no-pager` and `-P` (`git -c color.ui=never log -- tools/machine_lock.py`), `--text` (read as a prefix of `--textconv`), any line naming the lock CLI that also holds bash's `$_`, `$!`, `${!`, a lone `_` or `BASH_COMMAND`, or PowerShell's `$$`, `$^`, `$Error`, `$MyInvocation` or a `*-Variable` cmdlet given a name that is not plain (and, for an exempt read, `$_` or `$PSItem`: `gc tools/machine_lock.py | ? { $_ -match 'hold' }`; the lock CLI itself piped into such a filter passes), a launcher whose options the guard cannot place (an option of `rolepolicy.LAUNCH_PROGRAMS` it does not list that takes a value, `start` with an unquoted title, `pwsh` given a bare file), a name with a space in its middle (`python "tools/machine_lock.py. ." status`, read as two words, so its verb is misnamed), the name glued to other text in a launcher's unread line (`winpty git commit -m "fix;machine_lock.py"`), and any `NO_PROGRAM` command naming the lock CLI, such as `for f in tools/machine_lock.py` or an unspaced `$s=python <kit>/tools/machine_lock.py status` (the spaced `$s = python ...` is judged by its verb). Only verbs `tools/machine_lock.py` has are named (its parser; `status --days` gives the run history), so any other verb (`stats`, `book`, `unbook`) is refused. `write`, `controller` and `test`: `status`, `run`, `background`, `stop` and the agent rights of "Lock CLI owner writes" (`hold agent|list|end|edit`, bare `division`, `game` and `game show`). `lander`: `status`, `run`. `read`: `status`. Only the words before `--` are the lock's: `run ... -- prog --force` passes. The lock MCP's tools are held the same way, each read as the CLI verb it matches (`rolepolicy.MCP_VERBS`: `lock_snapshot`, `lock_wait_change`, `lock_stats`, `lock_run` and `lock_hold` are `status`; `lock_end_run` is `stop`, `lock_hold_end` and `lock_hold_edit` are `hold end` and `hold edit`; `lock_hold_create`, `lock_set_game_mode`, `lock_set_games` and `lock_set_division` are no mode's), named as rule `lock-mcp` names them (the lock's prefix from `guard_mcp_prefix` or the host profile's `mcp_tool_format`, or a lock tool's name under another server); a tool under the lock's prefix that the server does not have is refused. The owner-only ones meet rule `lock-mcp` first, as before.

## Fallback

`kitlib/guard/fallback.py` `check` runs only when the parse is unclean. It catches mistakes, not attackers: an unclean line is refused when it touches a main checkout, a heavy program or a protected path, and a plain line is never denied by it.

- **Modes:** the refusals below follow "Rule modes". A pattern whose rule is off (`wrapped-gate` by default) is not looked for. `unreadable`, `heavy` and `unplaced` warn by default: the warning is kept and the check goes on to the next pattern and the steps after it, so only a kept rule's deny (a re-read one, `git-push-pmdata`) stops the line.

- **Patterns:** git_guard's (one repo's `git_guard.ps1`) plus the kit's git rules.
  - When the directory is a main checkout or a place git cannot tell: bulk add, `commit -a`, `checkout`/`switch`, `reset --hard`, `clean`, `stash`, `restore` (unless it only unstages); `commit`, `merge`, `rebase`, `cherry-pick`, `revert`, `am`, `pull`, `apply`, `update-ref`.
  - Anywhere: `branch -D`, `worktree remove`, `update-ref` (only in a session `rules.shared_ref_held` holds), push to main (with no `push_block`, only a re-read deny counts: a delete or a forced push of main), push `--no-v...`, `send-pack`, `http-push`, `remote-<helper>`, `git-send-pack`, `git-http-push`, `git-remote-<helper>`, and git push or a git subcommand with a computed word (only where the repository has `kit-pm-data.json` or git cannot place the directory, and not in the owner's own session), the wrapped gate, root searches.
- **Which directory:** the main-checkout patterns are judged in the directory of the top-level command that holds the match, following a literal `cd` before it. The call's directory is not used alone. The git pattern reads a quoted `-C "<path>"`.
- **A pattern match:** the text from the match to the next `;`, `|`, `&` or newline is read again as a command and the parsed rules run on it.
  - A rule that denies gives the deny, its real `Instead:` included, after "The guard could not read this command; write the program name literally. Why: <reasons>."
  - No rule denies: rule `unreadable`. The sentence ends "Write it plainly:", and `Instead: <the line written plainly>` follows. When the guard cannot rewrite the line (a variable inside nested shell text, `bash -c "...$F..."`), or the rewrite, read again in the call's directory, is unclean too (closing an odd `'` that leaves a `"` open), the sentence instead says to make every program name and nested shell text literal or to write the commands to a script file with the Write tool, and `Instead:` names that script's run in the temp folder (`fallback.SCRIPT`, `fallback.SCRIPT_RUNS`). Every `unreadable` refusal, and the fallback's `write-jail` and `git-push-pmdata` ones, take their alternative from `fallback.plainly`, so none repeats the refused line.
- **A heavy program's name:** the same, unless the session holds the lock. A program named by a variable is refused as `heavy`, the `machine_lock.py run` form naming `<the program $X names> <args>`.
- **Anything else:** a subagent gets `unreadable`; with that warned, it is judged on as a jailed session is.
  - A session the write jail holds (a subagent, a mark in `guard_agent_marks`) gets `unplaced` when the line holds the word `git` (`fallback.GIT_WORD_RE`; `.git` and `GIT_DIR` are not it), read or write, from any place: the part the guard cannot read may point git at a checkout it cannot place. The PM data and main-checkout steps below still run.
  - Then every session (the jail's ones reach this step once the steps above warn) gets `unreadable` when a command runs in a main checkout, or a place git cannot tell, and that command runs one of:
    - a program the text does not name;
    - a shell (`bash`, `sh`, `powershell`, `pwsh`, `cmd` and the like), `eval`, `iex`/`Invoke-Expression` or `source`/`.`; this covers `-enc`/`-EncodedCommand` and a pipe into a shell;
    - git with a subcommand or read option the text does not name.
  - The same line from a worktree passes, unless the repository has `kit-pm-data.json`: then any session but the owner's own gets `git-push-pmdata` (deny) for such a line from any place in it, as the hidden program may be `git push --no-verify`.
- **`& (<subexpression>)`:** PowerShell's call operator on a subexpression leaves the line clean ("Known limits"), so the steps above do not judge it. `rules.call_subexpr_pmdata` gives the same answers on a clean line: `git-push-pmdata` in a repository with `kit-pm-data.json`, else `unplaced` (warn by default) for a session the jail holds, whether or not the line holds `git`.

Tests: tests/guard/test_rules.py ROWS, tests/guard/shell_rows.py, tests/guard/review_rows.py and tests/guard/extra_rows.py (428 rows at the time of writing); tests/guard/test_session.py for the rules that read the session mark.

### Known limits

The guard reads the command line, not the shell's state:

- **Aliases and functions** are not seen; the name is read as a program. This holds whether they are defined in an earlier call, in a profile, or earlier on the same line (`alias g=git; g push`). It also holds for git aliases in `~/.gitconfig` (only `-c alias.x=` on the command line is read: `git-alias` warns and the command it runs is judged, but a shell alias, `!`, is denied as `git-alias-shell`), except in a repository with `kit-pm-data.json`, or any repository on a machine whose config names `pm_data`, where `git-push-pmdata` expands them for every session but the owner's own. `rules.GIT_BUILTINS` is git 2.55's builtin list; on an older git a name missing from its builtins may be an alias the guard does not look up.
- **`& (Get-Command x)`** and other PowerShell calls of a computed command object are not resolved to the program they run. The parser reads `& (<anything>)` as a program the text does not name, with the subexpression's commands read as nested ones (`kitlib/guard/shell.py`), but the line stays clean (`commands.call_subexpr`): only `rules.call_subexpr_pmdata` judges that program, as `git-push-pmdata` in a repository with `kit-pm-data.json` and, anywhere else, by denying it to an agent session (`unreadable` for a subagent, `write-jail` for a marked one). For the owner and `plain` no other rule (`heavy` included) sees what it runs. A dot-source of one (`. (Get-Command x)`) is not read so.
- **Direct edits of a repository's config:** `git-remote-rewrite` reads `git remote` and `git config`. An edit of `<git common dir>/config` by a file tool or a shell write (`sed -i`, `Set-Content`) is judged only by the path rules (`main-checkout`, `write-jail`), which do not hold every session, so it can repoint a remote unseen.
- **`coproc`** is not modelled; the command after it is read as a program named `coproc` (`coproc git stash` parses clean, as one command `coproc`).
- **Pre-push config load:** when the clone has no base commit at all, neither the replaced remote main commit nor any default-branch ref, `kitlib/guard/prepush.py` falls back to the defaults: no `push_block`, main read from the git files (docs/kit-json.md "With no file"). The gate-OK check is then skipped; the fast-forward and delete refusals still apply to main, and to `main` itself whatever `<remote>/HEAD` names (read from the code; no test covers it). A base `.kit.json` that sets no `repo.main_branch` names main the same way (`test_a_base_that_names_no_main_branch_reads_origin_head`).
- **`Invoke-Expression`/`iex`, `eval` of a computed string:** the string is not evaluated; a literal argument is parsed, a computed one leaves the parse unclean.
- **`case` statements** are read as unclean (an unmatched `)`), so a subagent's `case` line is refused as `unreadable` and a jailed session's as `unplaced` when it holds `git` (both warn by default); a session the jail does not hold is not refused.
- **Known gaps, not judged (the guard is a speed bump, not a jail):** network writers (cast and rest forms and others); PowerShell `iex` with hidden env values; long hub paths folded; role-lock bypasses, PowerShell 5.1 quote splitting and the inner command of `run`; `cd` spellings; git holes (round 4) and unjudged git ref writes (a `symbolic-ref` then `update-ref`, `branch -m` of main, `tag -f`/`-d`, `replace`, `branch -f` from a linked worktree, an alias, a link made earlier on the same line); write-jail writer gaps and the jail refusal's read-only text; computed `hooksPath` keys; a PowerShell path bound from the pipeline (`$p | Remove-Item`).
- **Heavy fallback on Python 3.14:** `fnmatch.translate` ends with `\z` there, not `\Z`; `heavy_patterns` strips both, else the heavy fallback never matched.
- **Rules the fallback does not run:** `busy-wait`, `heredoc-winpath`, `git-hooks-path`, `owner-identity` and `kill-by-name` are not in `fallback.PARSED_RULES`; an unclean line meets only the fallback's own patterns.
- **busy-wait:** off by default ("Rule modes"); when on, a loop in a script file, or in the Monitor tool, is not read. A bound the rule does not know (an `-eq` count, a check inside a called script) reads as none, so that loop is denied. Any `-lt`/`-le`/`-gt`/`-ge` reads as a bound, so `while [ $(pgrep -c x) -gt 0 ]; do sleep 1; done` passes though nothing ends it. A loop behind `time` or `nohup` (`time while true; do sleep 1; done`) is read as that program's arguments and passes. The alternative for a loop on the call's own line is the bounded loop alone: what came before it on the line (`F=x;`, `cd x &&`) is not kept.
- **heredoc-winpath:** only python reading a bash heredoc as its script. A heredoc written to a `.py` file by `cat`, a PowerShell here-string, and other interpreters are not read. A drive letter followed by a single path character (`C:\x`) is not read as a path. A one-letter label, an escape, then text (`"Q:\nWhat"`) is still read as a path and refused (a warning by default).
- **git-hooks-path:** `git clone --template` and `git init --template` with hooks in the template are not seen. Abbreviated long options (`git clone --conf=core.hooksPath=x`) are not seen.
- **owner-identity:** an identity in the environment the session started with, in `GIT_CONFIG_PARAMETERS` or a `GIT_CONFIG_KEY_<n>=user.email` / `GIT_CONFIG_VALUE_<n>` pair, or set inside a script or program the line runs, is not seen. `git commit --author=<name only>` is not caught: git fills in the email from an earlier commit by that author, which can be the owner's; the rule matches the email, not the name.
- **kill-by-name:** `pkill` and `killall` that end processes by user, parent, group or terminal with no name (`pkill -u <user>`) pass.
- **Clearing the mark:** a marked session can start a child agent session with `PM_KIT_ROLE` cleared (`PM_KIT_ROLE= claude ...`, `env -u PM_KIT_ROLE claude ...`, `Remove-Item env:PM_KIT_ROLE`); the child is unmarked and counts as the owner. No rule denies it.
- **Environment changes beside a git write:** the git write of a session the write jail holds (a subagent, a mark in `guard_agent_marks`), on a line with an environment change the guard does not read, is denied even when the change is harmless (`set -a; . ./.env; set +a; git commit ...`, `Set-Content $f x; git commit ...`); run the git in its own call. Any git on a line the guard cannot read at all (`eval "$c"; git status`) is refused as `unplaced`, which warns by default ("Fallback"). The owner's unmarked session and the marks the jail does not hold (`plain`) are not jailed (`rules.git_jail` returns before `git_jail_unknown`), so their line passes.
- **Startup files:** a nested shell runs files the line does not show before its text: `bash --rcfile <f>` or `--init-file <f>`, and a login or interactive shell under a `HOME=<dir>` the line sets (`HOME=/x bash -l -c '...'`) reads that folder's profile. They are not read; git in the nested text is placed as written.
- **PATH and the exec path:** a `PATH` the line sets, or `git --exec-path=<dir>`, may make `git` or a git subcommand another program. The guard reads the word `git` as git and does not judge `PATH`.
- **Environment the line does not show:** a program the line runs that runs git itself (`python tools/commit.py`) gets the line's environment, but is not judged as git. A PowerShell `function git`, `git -c include.path=`, a .NET `ProcessStartInfo` and a variable persisted by an earlier call (`setx`, User scope) are not seen.
- **PowerShell provider items:** only a literal item of a provider-aware item or content cmdlet (`PS_PROVIDER_CMDLETS`), on a line whose every command is a plain call of such a cmdlet, a listed read-only one or git (`ps_line_plain`), skips the path rules; any other env: item (computed, given to a native program or to Out-File, Compress-Archive, Invoke-WebRequest -OutFile, or on a line with an assignment, a member or static call, `&` or a dot-source) is judged as a file path. A literal one (`PS_PROVIDER_ITEM_RE`) is then a drive or provider path the guard cannot place (next item), so `main-checkout` refuses it in a main checkout and from a worktree too, with a reason that names the PowerShell provider item and says to run the item write in a call of its own (kitlib/guard/rules.py `shell_writes`).
- **PowerShell provider and drive paths in a write:** a PowerShell `FileSystem::<abs>` (bare or `Microsoft.PowerShell.Core\FileSystem::`) is read as `<abs>` (`shell.resolve_path` with the shell, also for `cd` and the root search). Any other `Provider::` path, or a drive whose name is anything but one ASCII letter (`Main:\x` after `New-PSDrive`, `1:\x`, `_:\x`, a non-ASCII letter), cannot be placed (`shell.ps_unplaceable`), unless the provider-items skip above already let it pass. A write after a PowerShell `cd`, `Set-Location` or `Push-Location` into such a place (`cd Main:\; New-Item x.txt`) is treated the same way: `shell.track` marks the commands after it (`cwd_ps_drive`) until a cd reaches a known place; unlike other unplaceable targets it never takes the from-a-worktree skip, so `main-checkout` refuses it in a session that rule binds, and for an agent session that rule lets through (one that may edit a main checkout), `write-jail` refuses it (`rules.ps_drive_jail`). The owner's unmarked session is refused by neither. The `cwd_ps_drive` mark is lost in a nested shell and on a multi-word `cd`, so a write after either is not refused for it. Bash and cmd words and one-letter drives are read as before (kitlib/guard/shell.py, kitlib/guard/rules.py).
- **Heavy `when_args`:** an argument counts at any position, so `dotnet new console -n build` is heavy.
- **write-jail reads the line, not the program:** a script or program the agent runs (a `.py` it wrote, `python -c`, a build tool) can write anywhere; the jail judges only the targets the command line names. What such a write puts in a repository reaches main only through a commit and a push, where `tools/commit.py` (docs/commit.md) and the pre-push owner-only paths ("Owner-only commits") still check it; a write outside every repository is not checked at all. A target that is not literal goes unjudged under bash and cmd in a linked worktree or another place git can tell ("Rules"), as does a PowerShell path bound from the pipeline ("Known gaps"); a computed git subcommand is refused (`commands.git_dyn_word`).
- **BSD `xargs -S <size>`** is not read as taking a value: the size is read as the program, so the command after it (`sh -c '...'`) is not read.
- **A trap handler or `find -execdir` at an unknown place:** a relative write in it is judged as at an unknown place, so a subagent is denied `cd sub && trap 'rm -f x' EXIT` and `find . -execdir rm {} +`.
- **Both machine config folders:** with a `config.json` in both the new and the retired folder, the new one decides alone, so only its `ledger_path` is protected; a ledger only the old file names is not (docs/kit-json.md "Moving the machine config folder"; tests/guard/test_config_move.py).
- **write-jail with a git top at the home folder or above:** such a checkout holds the machine config folders, so the session gets no checkout root ("No root on a machine config folder") and the alternative a refusal names writes to temp instead (`jail.destination`).
- **write-jail temp is shared:** every session's temp root is the same folder, so one agent session may write another's scratch folder.
- **write-jail copy into an add-only folder:** only cp, mv, ln, install, `Copy-Item`, `Move-Item` and cmd copy and move are judged by the source's name. `robocopy`, `xcopy` and `rsync` into the existing folder, a source that is not literal, holds a wildcard or is drive-qualified (`D:name`), `-T`, and any option off the list in "Write jail" are judged as the folder itself, so they are denied.
- **write-jail and options that are not literal:** cp, mv, ln and install read a word that is not literal (`"$F"`) as an operand, though the shell may expand it to an option such as `-t<dir>`.
- **write-jail and a lander in the main checkout:** a lander whose `cwd` is the main checkout gets the whole checkout as its root, so the jail adds nothing there; the `main-checkout` rule and `roles.lander` decide what it may write.
- **The lander's agent type:** the exception for landing verbs matches the payload's `agent_type` `pm-kit:lander`, the kit's own lander, which the coordinator dispatches by that name (skill land-branch), and `lander`, a repo's own `.claude/agents/lander.md` (docs/ROSTER.md); nothing else does ("Agent names"), so a lander another plugin registers is held like any subagent. The `<plugin>:<name>` form is INFERRED from Claude Code's plugin naming, not observed; check one real payload after the plugin install.
- **write-jail and a session's working directory:** the roots follow the payload's `cwd`. An agent started in another repository's checkout (a subagent of a session that runs there) gets that checkout, not the worktree it was told to work in, and is denied there.

## Lock MCP

- **Which tools:** a tool named `<prefix><owner-only tool>` is caught, so is any `mcp__*__<owner-only tool>`, and so is any full name listed in the user config `guard_mcp_tools`.
- **Prefix:** the default is the asking host's: its `hosts.json` profile `mcp_tool_format` with the kit plugin (`kitlib.lockmcp.PLUGIN_NAME`) and the lock server's name filled in (`rules.host_mcp_prefix`; the same text as `kitlib.lockmcp.tool_prefix()`), and "any other server name" is the tail after the format's server separator (`__`). The Claude one is INFERRED from Claude Code's plugin MCP naming; no real PreToolUse payload has been captured, as the server is not installed. The user config `guard_mcp_prefix` replaces it and `guard_mcp_tools` adds names, so an observed name goes in config, not code (tests/guard/test_session.py `LockMcpByMark`).
- **Who is asking:** `Ctx.session_role(action)` decides (see "Session mark"); it is replaceable through `role_resolver`.
  - `subagent`, or any mark (pm, coordinator): deny.
  - Unmarked, the owner's own session: allowed. The lock's own owner check still applies.

## Session mark

`kitlib/sessionmark.py`. The launcher that starts an agent session sets `PM_KIT_ROLE` to its kind (`tools/launch.py`, docs/launcher.md "The window": `pm`, `coordinator`, `deep-worker`, `consultant`, `plain`, or another agent's name); a subagent is told apart by the hook payload's `agent_id` (`Action.agent`). `kitlib/guard/context.py` `default_session_role` gives `subagent`, else the mark, else `owner`. The mark is the hook's own environment's, unless the host's adapter hands it over as `Action.role` (Claude's does not: the hook inherits the session's environment).

- **Unmarked is the owner:** a main session nothing marks is the owner's own, exempt from `owner-lock`, `owner-setup`, `lock-mcp`, the hub rules (`hub-mcp`, `hub-browser`, `hub-owner-verb`, `hub-secrets`), `owner-identity`, `git-push-pmdata`, `kill-by-name`, `lock-state`, `kit-json` and `write-jail`. Until the kit launcher is live, sessions the old launcher starts are unmarked and count as the owner ("Go-live", step 4).
- **Reserved values:** a mark of `owner` or `subagent` reads as `marked-<value>`, never as that standing.
- **The plugin prefix:** a mark is read without the kit plugin's agent prefix, before the reserved check ("Agent names"): `<plugin>:coordinator` is held as `coordinator`, `<plugin>:owner` reads as `marked-owner`. The launcher writes bare marks (docs/launcher.md "The window").
- **Agent sessions:** `kill-by-name`, `lock-state`, `kit-json` and `write-jail` hold subagents and the marks in the user config `guard_agent_marks` (default `kitlib/guard/rules.py` `AGENT_MARKS`: `coordinator`, `conductor` (the coordinator's old mark, removed after the switch), `deep-worker`, `consultant` and `pm`; compared without case); other marks (`plain`, another agent's name) are not held to them. Setting `guard_agent_marks` replaces the default list rather than adding to it, so a value must also list every default mark it keeps holding (`ctx.user().get('guard_agent_marks') or AGENT_MARKS`). `owner-lock`, `owner-setup`, `lock-mcp`, the hub rules and `owner-identity` hold every marked session.
- **The PM's mark:** only the session the kit launcher resumes carries `pm` (docs/launcher.md "The window"); a PM session opened by hand or in the desktop app is unmarked and counts as the owner's own. The jailed PM keeps the folders it writes outside its checkout through `guard_mark_roots` ("Write jail"), which the owner sets.
- **Where it is read:** only where the session cannot change it once started: the guard hook and the lock MCP server, both started with the session's environment (INFERRED; not yet observed live). The lock CLI does not read it, since an agent sets the environment of every command it runs.
- **Lock MCP server:** `mcp/lock_server.py` `main` installs `sessionmark.owner_check` through `kitlib.lock.api.set_owner_check`. In an unmarked session a caller under the session's agent host counts as the owner (the default check sees the agent host as the caller and refuses every owner write); in a marked one only the default check passes.
- **Limits:** a session the launcher did not start is unmarked and counts as the owner. A subagent of the owner's session passes the lock server's owner check; the guard still denies it by `agent_id`. The lock's holds and tree roles do not read the mark.
- **Tests:** tests/guard/test_session.py.

## Agent names

`kitlib/agentname.py`. Claude Code names an agent a plugin bundles `<plugin>:<name>` (INFERRED from its plugin naming, not observed); the kit's plugin is `kitlib.lockmcp.PLUGIN_NAME`, and `agentname.PREFIX` is that name and a colon. Every place the guard compares an agent name accepts the bare name and that one prefixed form:

- **Agent types** (`agentname.bare`): Claude's adapter (`hosts/claude/adapter/events.py`) drops the prefix once, into `Action.agent_role`, which `kitlib/config/policy.py` `role_name` (so the `roles` table, and through it `main-checkout`, `git-main-history` and `rules.lander_check`) and `rules.lander_check` itself read. Exactly one leading `PREFIX`, in its exact case, is dropped. Any other form keeps its name, which no role names, and is held as `subagent`: another plugin's prefix, the prefix twice, another case, the prefix alone, `PREFIX` + `main`. An event without `agent_id` is `main` whatever its `agent_type`.
- **Session marks** (`agentname.bare_mark`): `kitlib/sessionmark.py` `mark`, and again `rules.agent_session` and `rules.session_mark` (a `role_resolver` that does not strip it). The prefix is dropped in any case and as often as it repeats, since a mark that names a known kind is the restrictive reading; a mark that would be left empty keeps its value, since an empty mark would be the owner's.
- **Tests:** tests/agentname, tests/config/test_policy.py, tests/guard/test_session.py, and tests/guard/test_prefix_parity.py, which runs the rule table, role policy and session tests again (its `SENTINEL_MODULES`) with each subagent's `agent_type` and each mark prefixed and expects the same decisions.

## Owner lock tools

Owner-only lock tools are run by the owner, not agents: `reserve_ui.pyw` and the lock CLI's owner writes. The lock's own owner check (`kitlib/lock/api.py` `who`, `default_owner_check`: no Claude ancestor) can be forged by a detached process, so the guard stops agents from starting them at all. That check stays as a second layer.

- **reserve_ui:** denied when a command runs it (any case, any path, with or without `.pyw`), in `kitlib/guard/rules.py` `runs_reserve_ui`:
  - as the program: a direct path, `&`, `Start-Process`, `cmd /c start`;
  - as the script of `python`, `pythonw`, `py` or `pyw`, also through `start` (`/b` and other options skipped), `Start-Process`, `nohup` or a nested `bash -c`;
  - as python's standard input, when the line names `reserve_ui` (`python < reserve_ui.pyw`, `cat reserve_ui.pyw | python`, `python -`);
  - opened by `Invoke-Item`/`ii` or `explorer`;
  - `python -c` with `reserve_ui` or the window's package (`kitlib.lockui`, `kitlib/lockui`, `from kitlib import lockui`) in its arguments, and `python -m reserve_ui` or `-m runpy`, also in a cluster of short flags (`-um runpy`, `-mrunpy`, `-Sc`) or with the module named by a variable. Other `-m` modules stay open (`python -m py_compile reserve_ui.pyw`, `python -m pytest -k reserve_ui`);
  - a program, script or opened file named by a variable, when the command's text names `reserve_ui` (`$p = "reserve_ui.pyw"; pythonw $p`).

  Reading it and git on it stay open: `cat`, `type`, `Get-Content`, `rg`, `grep`, `git add`, `diff`, `show`, `log`, `commit`, so work on the UI's own code is not blocked.
- **Lock CLI owner writes:** any word whose base name is `machine_lock.py`, run by `python`, `pythonw`, `py`, `start`, `Start-Process`, a direct path, or inside a `run` command, followed by:
  - the installed lock CLI: `reserve`, `release`, `stop --force`, `unbook --force`;
  - the kit CLI (`tools/machine_lock.py`): `hold whole|half|slots`, `division --set|--default`, `game on|off|set`, `top` (move a waiting run to the front), `stop --force`.
- **Still open:** `status`, `run`, `background`, `book`, `unbook` and `stop` without `--force`, `hold agent|list|end|edit`, bare `division` and `game`/`game show`. Ending one's own hold or run is an agent's right (`kitlib.lock.api.authorize`); the text cannot tell whose hold an id names, so the lock decides.
- **Who:** every session but the owner's own (unmarked; see "Session mark"), with no ask. A process the owner's session starts still has an agent host above it, so the lock CLI's own check refuses it there.
- **Limits:** not caught:
  - a lock CLI script named by a variable (`python $tool reserve`);
  - a glob (`pythonw reserve_u*.pyw`);
  - a variable set in an earlier call, or in an outer text that a nested shell's text does not include;
  - `reserve_ui` started by a program the guard does not know as a launcher (for example a `.py` script that runs it);
  - a lock CLI owner write passed as a `Start-Process -ArgumentList @(...)` array (`@("machine_lock.py", "reserve", "whole")`); `reserve_ui` in such an array is caught;
  - `[Diagnostics.Process]::Start(...)` and other .NET process calls;
  - copy-then-run: the UI copied or renamed to another name, then that file run;
  - a heredoc or here-string feeding python (`<<`, `<<<`): only a pipe or a `<` redirect counts as python's standard input.
- **Over-reach:** the standard-input deny fires whenever the line names `reserve_ui`, even when what feeds python is something else (`cat other.py | python; cat reserve_ui.pyw`).
- **Unreadable lines:** `kitlib/guard/fallback.py` runs this rule first when it re-reads a text-pattern match (`PARSED_RULES`). It has no text pattern of its own for these tools, so an unreadable line reaches this rule only when another rule's text pattern (wrapped gate, git, root search, heavy) matches.
- **Tests:** tests/guard/test_rules.py `OwnerLockTools`, including `test_unread_line_rereads_with_owner_lock` for the fallback.

## Owner machine setup

Machine setup's `--apply` writes the machine config, and its `owner_email` decides which commits count as the owner's (owner-only paths, `owner-identity`; docs/machine-setup.md "Owner email"). An agent that ran it could store its own address as the owner's, so the `owner-setup` rule (`kitlib/guard/rules.py` `owner_setup`, `setup_run`) denies it to every session but the owner's own:

- a word whose base name is `machine_setup.py`, `machine-setup.ps1` or `new-repo.ps1` (the program, python's script, `powershell -File`, a `Start-Process -ArgumentList` string), or `python -m <...>machine_setup`, followed by `--apply` or a prefix argparse takes for it (`--ap`, `--app`, `--appl`), or for a `.ps1` a prefix of `-Apply` (`-a`, `-App`, `-Apply:$true`), any case; words after `--` are not read;
- a `.ps1` entry point with a double quote inside an argument (Windows PowerShell 5.1 passes it on unescaped, so it can split a value into more arguments, an `--apply` among them; both scripts refuse one too);
- such an entry point followed by a word the text does not show (`python tools/machine_setup.py $f`), and on a line that names machine setup a program, or python's script, named by a variable (`$s = "...machine_setup.py"; python $s --apply`);
- `python -c` (also in a cluster, `-Sc`), or python reading its script from standard input (a pipe, `<`, a heredoc or here-string), on a line that imports `kitlib.machinesetup`.

The dry run (no `--apply`), `--help`, reads and git on its files stay open. The `--repo` mode is held the same way: it writes `.kit.json` "owner".email. An agent session's file edit or shell write of the machine config itself is the write jail's: the machine config folders are never a write root ("Write jail"). An unreadable line that names an entry point with a `-a...` word, or imports `kitlib.machinesetup`, is matched by the fallback's own pattern and re-read through this rule; the owner's own session skips it.

- **Limits:** not caught: a script of the agent's own that writes the machine config file (`python my.py`), a copy of the tool under another name, `[Diagnostics.Process]::Start(...)`. The write jail stops a file tool or shell redirect into the machine config folder, not a program's own writes.
- **Tests:** tests/guard/test_rules.py `OwnerSetup`.

## Hub secrets

The Action Hub (`kitlib/hubsite`) keeps its tokens in a folder named `hub` beside the machine config file (`kitlib/hubsite/auth.py`): `owner.token` answers as the owner, `agent.token` is every agent's, and `approval.key` signs the owner's approval decisions (`kitlib/hubsite/approvals.py` `sign`) and binds strong sessions (`kitlib/hubsite/auth.py` "The approval key"). Its store is the machine config's `hub.store`, unset: `<pm_data.path>/hub` (`kitlib/hubsite/settings.py`). Agents reach the hub only through `tools/hub.py`'s agent verbs and the hub MCP server, which read `agent.token` in their own process, and the hub server's git sync writes the store; an agent's own access to those files is owner power. Four rules hold every session but the owner's own (subagents and every mark, `plain` included, as `owner-lock` does; "Session mark"). They live in `kitlib/guard/rules.py` (section "the Action Hub"), with pure helpers in `kitlib/guard/hub.py`, which copies the hub site's names rather than importing it (tests/guard/test_rules_hub.py `Plumbing` checks they match).

- **hub-secrets, edits:** a file tool edit of a path in the token folder or a store, judged by the resolved path (`jail.real`). Both stores count, an explicit `hub.store` and `<pm_data.path>/hub`, since the hub may move to the default one. The store and port are read from the machine config's `hub` object even when the strict read refuses the file for a fault elsewhere (`rules.hub_config`).
- **hub-secrets, shell:** a command (`rules.hub_secret_shell`) with:
  - a literal word naming the token folder (`.pm-kit` then `hub`, with only separators and quotes between) or a token file's name as its last part. The words of a search or of git (`grep`, `egrep`, `fgrep`, `rg`, `findstr`, `Select-String`, `sls`, `git`; `hub.NAME_ONLY_PROGRAMS`) are patterns and messages and do not count; a word the shell computes is not read;
  - a literal path (redirect targets included, `--opt=<path>` and PowerShell's `-Opt:<path>` read; `rules.hub_path_texts`) in the token folder. A wildcard path, the word `hub` and the store are not read (a shell write into the store is the write rules'; a file tool's edit there is still hub-secrets'). A path may start with the home folder spelled as `~`, `$HOME`, `${HOME}`, `$env:USERPROFILE`, `$env:HOME`, `%USERPROFILE%`, or the drive and path pair `$env:HOMEDRIVE$env:HOMEPATH` (`${env:...}` too) or `%HOMEDRIVE%%HOMEPATH%`, read as the guard's own home and only when nothing after it is a variable (`shell.HOME_VAR_RE`, `shell.home_text`). A relative path is read from where a `cd`, `Set-Location`, `sl`, `pushd` or `Push-Location` to such a home path moved the line, and a bash or PowerShell `cd` or `Set-Location` with no place, or PowerShell's `cd $null`, counts as a move home, as bash's and PowerShell 7's do (bash cd's own options and a `--` are passed over: `cd -- ~`, `cd -P`; a bash `builtin cd` or `command cd` is the cd itself, `shell.cd_words`). That is `shell.track`'s `cwd_home` (`shell.cd_target` with `home_vars`); every other rule still treats that line's directory as unknown, so a relative `hub` run from `~/.pm-kit` counts;
  - python or node code given on the line (`-c`, `-e`, a heredoc, a here-string, the command piped in) naming a token file or the folder literally (`hub.INLINE_RE`; `rules.inline_code`). `hub.py` and `hubsite` are not secrets, so `python "<kit>/tools/hub.py" questions --json | python -c "import json,sys; print(json.load(sys.stdin))"` passes. A name the code builds or reaches through a library is not read.
- **hub-secrets, read tools** (`rules.hub_secret_read`, an Action of kind `read`): paths are resolved as the edit rule's are (`jail.real`), and only the token folder is held, so the store stays readable.
  - Read: a file in the token folder, or the folder itself.
  - Grep and Glob starting in the folder (their `path`, else `cwd`).
  - Glob from anywhere else: denied when its pattern, joined to the start (resolved and as written), can list the folder or a name in it (`hub.list_reaches`). A `**` followed by one last part, or a last part just below the folder, must match a name that is there: the token files' names (`hub.SECRET_FILES`) and everything the folder holds (`rules.hub_secret_names`; past `rules.HUB_NAMES_LIMIT` names, any pattern reaching the folder counts). So `**/*.py` from home passes unless a `.py` is in the folder. `{a,b}` is written out (`hub.expand_braces`, at most `hub.BRACE_LIMIT` forms), and a brace it cannot write out counts as reaching.
  - Grep from a parent of the folder: denied with no `glob`. With one, it is denied when any of its pieces (split on spaces and commas, braces written out, case and backslashes dropped) can take in a name in the folder or name a folder on the way there (`hub.filter_reaches`); a `!` exclusion counts as reaching. A Grep from anywhere else passes: it cannot reach the folder.
- **hub-owner-verb:** a parsed hub tool run, at any depth of the line (`rules.hub_run_args`, `rules.hub_owner_run`): python with a script whose last part is `hub.py`, or with `-m tools.hub` (`-m hub`, a flag cluster ending in `m`, `-m runpy tools.hub`), its arguments read as `tools/hub.py`'s argparse parser reads them (`hub.owner_verb`). An owner verb in the Rules table (`hub.OWNER_VERBS`, `hub.OWNER_SUBS`, `todos add --owner`) is denied; a word the guard cannot read where the verb could be counts as one, and so does a PowerShell word holding a double quote. Only a run counts: text that names the hub tool without running it (a search pattern, a file a reader reads, a quoted argument of another program, a note written with `echo`) passes, and so does an agent verb whatever follows its pipe (`python "<kit>/tools/hub.py" todos --json | ConvertFrom-Json`). A script or module word the guard cannot read is no run, and a launcher that runs the tool some other way is not read. The agent verbs stay open: `questions` (list, `add`, `log`), `todos` (list, `add`, `ack`), `stories` (list, `set`), `to-pm` (list, `reply`), `inbox` (list, `add`), `approvals` (list, `show`), `pending`, `wait`, `status`, `validate`, `serve`, `setup`, `migrate`. The owner's token is no protection here, since `kitlib/hubsite/client.py` reads `owner.token` itself (tests/guard/test_rules_hub.py `OwnerVerbs`, `ParsedRuns`).
- **hub-mcp:** an MCP tool whose last part (after the host's server separator, `__` on Claude) is in `hub.OWNER_MCP_TOOLS`, under any server name, or a hub tool (named `hub_*`, or served by a server named `hub`) whose name holds `decide` or `approve`. The list is the hub MCP server's `kitlib.hubmcp.OWNER_ONLY`, imported (`kitlib/hubmcp/__init__.py` imports nothing, so the guard never loads the server: `test_the_guard_does_not_load_the_server`).
- **hub-browser:** an MCP call to a server whose name holds `chrome`, `browser`, `playwright`, `puppeteer` or `computer-use` whose input (`Action.params`, every string up to 8 levels deep) holds `host:port` with a loopback host on a hub port (`hub.hub_origins`): 8790 and 8791 and the configured `hub.port` and `hub.tunnel_port`. Loopback is `localhost`, `*.localhost`, 127/8, `0.0.0.0`, `[::1]`, IPv4-mapped IPv6, and IPv4 in a browser's other spellings (`127.1`, `2130706433`, `0x7f.0.0.1`, percent-encoded). `Action.params` is the tool's input, which the Claude and Codex adapters now pass (`hosts/*/adapter/events.py`); it takes no part in an Action's equality or hash (`kitlib/host/__init__.py`).

- **Limits:** not caught:
  - Read, Grep and Glob in an account whose PreToolUse matcher is older than the one in "Go-live", step 1: Claude Code does not send them to the guard (the settings are the owner's to change);
  - a link or junction below a search's start that leads into the token folder: only the start and the folder are resolved, not what the search walks through;
  - Grep's other ways to pick files (`type`) are not read: a Grep from a parent with a `type` and no `glob` is denied (over-reach), not judged by its type;
  - a script the agent wrote and then runs, or any program that reads the files itself (as the write jail: "Known limits");
  - python or node code on the line that never spells a name `hub.INLINE_RE` knows: a wildcard (`glob.glob(...)`), a name built from pieces (`'own' + 'er.token'`, `chr(...)`) or read from elsewhere (an environment variable, a file). `INLINE_RE` matches the code's text, not what it does;
  - a recursive read of a parent folder (`grep -r x ~/.pm-kit`, `Copy-Item -Recurse ~\.pm-kit`), a wildcard shorter than the folder, and `Join-Path` pieces that name no token file (`Join-Path $d 'hub'`);
  - a shell command's read of the store, which is not held (its writes are the write rules'), a wildcard path into the token folder (`cat ~/.pm-kit/hub/*`), and a relative path after a `cd` the text cannot place;
  - the home folder computed rather than spelled, which no reading of the text closes: `[Environment]::GetFolderPath('UserProfile')`, `Join-Path $HOME ...`, `$HOME + '\...'`, a variable set from it (`H=$HOME; cat $H/...`), a substitution or subshell whose output is the home folder (`$(echo ~)`, `"$(cd; pwd)"/...`); and a return home the guard does not follow: `cd -`, `popd` and `Pop-Location` (the directory after them is unknown);
  - hub-owner-verb, which reads only a parsed run: a launcher that runs the tool another way (`python -c "import tools.hub ..."`, a script the agent wrote, a copy of the tool under another name), and a name built at run time (string concatenation, an encoding, a variable's value: `python -m $m answer Q-1`). The rule catches mistakes and is not an adversary boundary;
  - a machine config the guard cannot read as JSON at all: an explicit `hub.store` and configured ports are then unknown, so only `<pm_data.path>/hub` (when the guard can tell `pm_data`) and the default ports are held;
  - text the parser never reads: the hub rules run on what the parser did read of an unclean line (tests/guard/test_rules_hub.py `test_unclean_lines_are_judged_on_what_was_read`), and an encoded command (`powershell -EncodedCommand <base64>`) is not decoded, so a subagent is only warned (`unreadable`) and a marked session in a worktree passes;
  - hub-browser: a click, key or form input on a hub tab already open (its input names no origin), raw screen pixels, a host that resolves to loopback (`nip.io`, the machine's own name, a LAN address), a port the config does not name (`serve --port 0`, a one-off `--port`), an origin with no port (port 80 implied), obfuscated script text, and the tunnel's public hostname.
- **Over-reach:** denied though nothing secret is read:
  - hub-browser: a browser MCP call to a loopback origin on 8790 or 8791 (or the configured hub ports) when something other than the hub serves there;
  - a word of a program that is not a search or git whose last path part is a token file's name (`echo owner.token`), or that holds the folder's name anywhere (`echo "see ~/.pm-kit/hub"`); a word in which the name is only part of a phrase (`echo "the owner.token file"`) passes;
  - a word of any program, git's commit message included, that is itself a path into either folder (`git commit -m "~/.pm-kit/hub"`), as paths are read in every word;
  - from `~/.pm-kit`, a bare `hub` as any word, search patterns included (`grep -n hub x`), because there it names the token folder;
  - hub-owner-verb: an agent verb whose value is a variable (`--title "$t"`) or, on PowerShell, a word holding a double quote, since either may split into `--owner`;
  - a Windows PowerShell 5.1 `cd` with no place or `cd $null`, which stays where it is;
  - read tools: a Grep with no `glob` from any parent of the token folder (home, or the drive root), and a Glob whose pattern can list it; once the machine config moves into the PM repository, that repository is such a parent, so a held session's Grep over its root with no `glob` is denied.
- **Tests:** tests/guard/test_rules_hub.py (each rule, every held session, the owner's allowed, and the agent verbs passing); tests/guard/test_rules_hub_read.py (the read tools); tests/guard/test_entry.py `test_a_subagent_read_of_the_hub_owner_token_is_denied` (end to end through `boot/hook.py`).

## Pre-push

`githooks/pre-push` calls `kitlib.guard.prepush.main` with git's two arguments (the remote's name, or the URL for a push by URL, and the URL). Whoever pushes, the PM data stage below judges every ref line first; the checks after it are on a ref whose remote ref is `refs/heads/<main>`.

**PM data branch** (`prepush.leak_refusal`; docs/pm-data-branch.md "Pre-push guard"). It runs only when the git common dir of the work tree pushed from holds `kit-pm-data.json` (`kitlib.pmdata.read`: data branch, private remote, root commit); with no file nothing changes. Each ref line is judged, whatever its remote ref, and the first refusal ends the push (`--all`, `--mirror` and `--tags` included).
- **Fail closed:** a record that cannot be read or is malformed, a git common dir git cannot name, the recorded root commit missing from this clone (`cat-file -e`), or remotes that cannot be read refuse every push, the record's path or the cause named.
- **Which remote is private** (`prepush._remote_urls`, `_private`): the URL git hands the hook (its second argument, after `insteadOf` and `pushInsteadOf`) decides, not the remote's name. The push goes to the private remote only when that URL is one of the recorded remote's push URLs as git computes them (`git remote get-url --push --all <remote>`: `pushurl`, else `url`, rewritten) and no other remote has it among its URLs (push and fetch URLs as git rewrites them, and the raw `url` and `pushurl` values). Every remote URL is read with `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_<n>` and `GIT_CONFIG_VALUE_<n>` dropped from git's environment, so `git -c remote.<private>.pushurl=<public URL> push <private>` is judged as public. URLs are compared by `prepush._norm_url`: a trailing `/`, then `.git`, dropped; a remote URL (`https://`, `ssh://`, scp-like `user@host:path`) has its scheme and host case folded and keeps its path's case, so two repositories whose paths differ only in case stay two; a local path (drive, UNC, `file://`) has backslashes as slashes and is case folded whole. Everything else is public: a URL the private remote does not push to, a URL another remote also has. A remote whose URLs `get-url` cannot give for any reason but "No such remote" (then its raw config values count) refuses every push, as do remotes `git config` cannot read.
- **Public remote, by name:** the local or remote ref is `refs/heads/<data branch>`: refused, naming the one push that is allowed (`git push <private> refs/heads/<branch>:refs/heads/<branch>`).
- **Public remote, by history:** the pushed sha holds the recorded root (`refs.is_ancestor`), or git cannot tell: refused. This catches the data branch merged into any branch, and a tag (light or annotated) on a data commit.
- **Public remote, by objects:** otherwise, the objects the push may send (`rev-list --objects <local sha> --not <remote sha, when this clone has it> --remotes=<name>`) are compared with every object reachable from the root, the local data branch and `<private>/<data branch>`, less the empty tree and blob. Any shared object refuses the push, one path named. This catches a cherry-picked data commit. A file whose content is identical to a data file matches too and is refused (fail closed; the message says so); a copy changed by even one byte is not caught. The `--remotes=<name>` subtraction trusts this clone's remote-tracking refs; it is left out (nothing subtracted) when another remote's name starts with `<name>/`, whose tracking refs the pattern would also match, or the name holds a pattern character.
- **Public remote, deletions:** a deleting line sends nothing and is not judged here, so deleting a leaked `refs/heads/<data branch>` from a public remote is allowed (the main-branch rules still refuse deleting main).
- **Private remote:** it receives only `refs/heads/<data branch>`, with the root in its history. Any other ref (main, another branch, a tag), a sha without the root, and any deletion there are refused.
- **The rules after this stage** run as before for each line. For a push to the private remote their base config is the replaced remote commit's, so the data branch's own committed `.kit.json` (its `main_branch` and `push_block`) when that remote already has it; for a first push, the default branch's.
- **Not caught:** `--no-verify` skips the hook; the guard rule `git-push-pmdata` denies it outside the owner's own session ("Rules").

- **Fast-forward only, in every repo:** a push that is not a fast-forward of the remote's main is refused, and so is deleting main. A remote main sha this clone lacks cannot be an ancestor of the pushed commit, so that push is refused too ("cannot tell"; fetch first). Git hands the hook such a ref only on a forced push (`--force`, `+`, `--force-with-lease`). A branch other than main may still be rewritten.
- **Gate-OK record:** the pushed sha must have one, read as in "State". Only when `repo.push_block` is set; checked after the fast-forward rule.
- **Owner-only paths:** after the gate-OK check, and also only under `repo.push_block`, a push to main is refused when a commit it adds fails "Owner-only commits" below, record or not. A branch gate records its own tip, so without this a gated agent branch could go straight to main. "Adds" means not in the remote main it replaces when this clone has it, else not in `<remote>/<main>` as last fetched, else the whole history. Other remote-tracking refs are never subtracted: a pushed agent branch would hide its own commits.
- **Order:** the PM data stage for every line (tests/guard/test_prepush.py `test_leak_stage_runs_before_main_rules`), then per line delete or fast-forward, then gate-OK, then owner-only paths; the first that refuses is the one reported (`test_the_rules_refuse_in_order`).
- **Base config:** `push_block` and the main branch's name are read from the remote main commit being replaced when this clone has it, else from the default branch's committed `.kit.json` (the first of `<remote>/HEAD`, `<remote>/main`, `<remote>/master`, local `main`, local `master`). The working tree is never the base, and a pushed commit cannot turn the block off.
- **Broken config:** a `.kit.json` that does not load refuses the push.
- **Tests:** tests/guard/test_prepush.py pushes to a bare scratch remote with `core.hooksPath` set to the kit's githooks; `PmDataTest` adds a second bare remote as the private one, `PrivateTest` covers `_private` and `_norm_url`.

## Owner-only commits

`kitlib/guard/ownercommits.py` `violations()` judges the net change, then the commits. For each owner-only path (`kitlib/config/owner.py` `is_locked`) that the net change touches, it names every commit that changes the path and whose author email (`%ae`, never mailmapped, replace refs off) is not `"owner".email` (`is_owner`). `gate land` (docs/gate.md "Landing", step 4) and pre-push run it, so a plain `git commit` to an owner-only path does not reach main past either; `commit.py --owner-authored` was the only check before.

- **Net change:** a path counts only when landing the tip on the target main would change it: the target differs for it from the clean merge of the target and the tip (`git merge-tree --write-tree`; the tip itself for a fast-forward), or that merge conflicts on it (`net_change`). The target is the landing's base for `gate land` and `land.py` (`<remote>/<main>` as fetched at its turn; docs/gate.md "Landing", step 4), the remote main being replaced for pre-push. So an agent change a later commit undoes, a rename away and back, and an owner change the branch brought in by merging main do not count. With no target (pre-push with no remote main known), every changed path counts.
- **Rules:** the base's merged with the pushed or landed commit's (`owner.merge`): paths are the union, exceptions the intersection, the owner email the base's only. An unset owner email, or one also in `agent_emails`, refuses every owner-only change.
- **What a commit changes:** a commit with one parent or none, its diff. A two-parent merge, what differs from the clean merge of its parents (`git merge-tree --write-tree`) plus every path that merge conflicts on: a merge that only joins histories changes nothing, and an edit or conflict resolution inside a merge is judged by the merge's author. More parents: the union of the diffs against each. Renames count as a delete and an add.
- **Trailers** play no part here: the author email decides. `tools/commit.py` writes the `Owner-Approved` trailer and refuses an owner-only path without `--owner-authored` (docs/commit.md).
- **Git failure:** refuses (the landing or the push).
- **Tests:** tests/guard/test_ownercommits.py, tests/gate/test_land_owner.py, tests/guard/test_prepush.py `OwnerTest`.

Known limits:

- **The author email is what the committer says** (`git commit --author`, `GIT_AUTHOR_EMAIL`). The guard's `owner-identity` rule denies a session other than the owner's setting the owner's email on the command line; an identity in the environment the session started with is not seen. Signed commits would close it; not built.
- **Only main is checked at push**, and only under `repo.push_block`, like the gate-OK check. A push to another branch, or a merge made on the server (a pull request merged in the web UI), is not seen.
- **One net change per push:** a push to main that carries the owner's unpushed main commits together with a branch is judged as a whole. When an owner commit in it changes a path, an agent commit that touched that path and was undone counts too, and the push is refused (fail closed). Pushing the owner's commits first avoids it.

## Self-test

`hosts.claude.adapter.guard_selftest.agent_id_check(projects_dir, since)` scans subagent transcripts (`<project>/<session>/subagents/agent-*.jsonl`) for guard tags.

- **What counts:** only tags in tool results marked `is_error` (INFERRED to be where a hook deny lands).
- **Results:**
  - `role=main` in a subagent transcript is an alarm: `agent_id` has disappeared;
  - only subagent roles pass;
  - no tags is inconclusive.
- **Not live:** it is not wired to a session-start hook.

## Refusal patterns pre-empted

- **P16:** a gate wrapped as `cd <wt> && python tools/gate.py 2>&1 | tail`. Rule: `wrapped-gate`, whose alternative is `python "<kit>/tools/gate.py" -C "<wt>"` run bare in the background.
- **A repo's wrapped lander command** (same family as P16). Rule: `wrapped-gate`.
- **git_guard's main-checkout patterns:** the git rules and the fallback cover them.
