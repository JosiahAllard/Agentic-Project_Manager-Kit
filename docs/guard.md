# Shell guard and git hooks

`boot/hook.py <host> PreToolUse`, the kit's one hook entry (`boot/hook.py claude PreToolUse` on Claude), is the kit's one PreToolUse hook (ARCHITECTURE.md "Layers": Guards). `githooks/pre-push` is the kit's guard git hook. Both are thin entries over `kitlib/guard/` ("Hosts" below says how a hook reaches it). `githooks/` also holds `pre-commit`, the ledger check, inert unless a repository opts in (docs/ledger.md "Pre-commit check").

**Live and enforcing:** the guard is registered as the PreToolUse hook (`boot/hook.py claude PreToolUse`; "Go-live", step 1), and subagent calls are refused by it (observed: rules `main-checkout` and `write-jail`). `githooks/pre-push` is live only in a repository whose `core.hooksPath` names `githooks/` ("Go-live", step 2).

## Output

- **Allow:** the hook prints nothing and exits 0, except after a plugin refresh, when the folder the session's header named is gone or the session was last named a folder at least an hour ago (docs/plugin-source.md "Layout", `headers/`): then it prints the line naming the kit folder now in use (`kitlib.host.headerfollow`) as `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "additionalContext": ...}}`, with no `permissionDecision`, so Claude Code's own permission flow runs as for an empty answer (`hosts/claude/adapter/host.py` `tool_context`; Codex's adapter has none, so Codex gets no line). A warned allow ("Rule modes") carries that line after its warning, on a line of its own.
- **Deny or ask:** it prints `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny"|"ask", "permissionDecisionReason": ...}}` and exits 0. The same refresh line can ride along as an `additionalContext` beside the decision; the reason is never changed.
- **Reason format:** `<what and why> Instead: <the exact command to use> [kit guard: rule=<rule> role=<main|subagent>]`. The role is what the event said (on Claude, `agent_id` present or not; `Action.agent`). The self-test reads it. The command after `Instead:` is also the Decision's `instead`.
  - After `Instead:` comes one command, ready to run, with no prose after it. Any explanation goes in the sentence before it, which ends with `:` (tests/guard/test_rules.py `test_rows` checks this for every row).
- **Unguarded tools:** a tool no rule can refuse (any tool but Edit, Write, MultiEdit, NotebookEdit, Bash, PowerShell, Read, Grep and `mcp__*`; Glob among them, as a names search reads no token's text: `hosts.json` `claude.hook.guarded_tools`) is allowed before kitlib is imported, read by `boot/hook.py` with json alone (`skips`; tests/guard/test_entry.py `Unguarded`, which also holds the list equal to the adapter's tool tables and `MATCHER`). It fails toward the guard: a payload that is not JSON or not an object, a tool name that is missing or not a string, and hook data it cannot read or of the wrong shape all go to the full guard (a missing `hosts.json` or host entry blocks the call), never to an allow.
- **Guard error:** if the guard fails on a guarded tool, it denies with rule `guard-error` (fail closed; `kitlib.host.hookmain.run`).
  - This includes a `kitlib.guard` that will not import and a payload the adapter cannot parse: hookmain imports the guard inside its `try` and has the adapter render the deny. Its `Instead:` reruns the hook on the event (`python "<kit>/boot/hook.py" claude PreToolUse < event.json`).
  - If the adapter or hookmain themselves will not import, or the answer cannot be written, the hook exits 2, which Claude Code also reads as a block.
  - Test: tests/guard/test_entry.py breaks each import.

## Refusal log

Every deny the hook answers adds one JSON line to `<pm_data>/audit/refusals.jsonl`, `<pm_data>` being the machine config's `pm_data.path` (`kitlib/guard/refusal_log.py` `record`). This section holds the facts of the log; docs/guard-v2.md "Refusal log" keeps only design points.

- **Who writes it:** `kitlib.host.hookmain.run`, for every host's hook, after the answer text and before the hook exits, whatever made the deny (a rule, `guard-error`, `guard-timeout`, the host's own screen). On Codex the kit-tool broker writes it too (`hosts/codex/adapter/runtime.py` `evaluate_bound`), for a deny and for its own error (`host-runtime-error`); Codex has no ask, so an ask is logged there as a deny. An allow and a warning add no line, nor does an ask on a host that keeps it (Claude Code).
- **Fields,** in this order (`refusal_log.FIELDS`): `utc`, `host`, `rule` (`unknown` when the deny names none), `role` (`main` or `subagent`, as the guard judged the Action), `agent_role`, `agent`, `session` (the launcher's `PM_KIT_SESSION_NAME`), `tool`, `kind`, `repo` (the folder name of the call's main checkout, read with no git child; `-` for any other layout and for a name that is the user's profile folder or `USERNAME`), `instead_given`. An absent value is `-`. A call of several Actions is logged by its first.
- **Never in it:** the reason, the command, the path, the working directory or the Instead text.
- **Concurrent hooks:** each append holds a lock (`kitlib.fs.treelock`) on `.refusals.lock` in the audit folder, so lines never interleave; nothing on the way starts a process.
- **Best effort:** no `pm_data`, a machine config that does not read, the lock still busy after 1 s, or a failed write adds no line and never changes the verdict or the exit code. Under the kit's tests a lookup of the real home (`HomeFenced`) adds none.
- **The folder** is the backlog audit log's (docs/backlog.md "Audit log"), left untracked; `pm-data-audit` refuses agents' own edits there ("Rules"). The hook's append is not a tool call, so no rule judges it.
- **Known limits:** only the kit guard's denies are logged (not the host's own permission system or classifier, an ask the owner declines, or a kit tool's own REFUSED exit); no kit tool reads the log yet; a session the launcher did not name logs `-`; a deny's hook takes up to about 1.55 s longer (`refusal_log.BOUND`); a block before kitlib loads (`boot/hook.py`, `boot/kitboot.py`) writes no line; the `role` field is the judged Action's, so in a marked session on a host with no subagent identity it can differ from the tag in a `guard-timeout` or `guard-error` reason.
- **Tests:** tests/guard/test_refusal_log.py; tests/host/test_hookmain.py `RefusalLog`; tests/codex/test_runtime.py `BoundGuard`.

## Rule modes

`kitlib/guard/modes.py`. Every refusal goes through `rules.refuse`, which asks the rule's mode:

- **deny:** the refusal stands, as its rule's verdict (deny or ask).
- **warn:** the call goes ahead, and the refusal's reason reaches the agent after `[kit guard warning] ` (`rules.WARNING`; the Decision is an allow with rule `warn`, `rules.WARNED`). Claude gets it as the hook's `additionalContext`, with no `permissionDecision` (`hosts/claude/adapter/host.py` `WARN_CONTEXT`); Codex shows nothing for a warned allow. A warning quotes at most 120 characters of the shell command it is about (`rules.CITE_MAX`): a backtick quote of the command's text, or of a part of it, that is longer is cut there and ends ` [...]` (`rules.ELIDED`, `rules.cited`); the `Instead:` text and the rule tag stay whole, and so does a deny or an ask, which quotes the full command as before. The checks after a warned refusal still run, so a later deny still decides. Several warnings on one call are joined (`kitlib.host.hookmain`).
- **off:** the call goes ahead, and nothing is said.

The kit's modes are `modes.DEFAULTS`; a rule it does not name is deny:

- **warn:** `unplaced` (below), `unreadable`, `git-alias`, `heavy`.
- **off:** `wrapped-gate`, `busy-wait`.
- **deny, kept:** owner-only tools and files, `hub-owner-verb` on a parsed hub tool run or an unreadable line naming the hub tool, the hub's secrets, the machine config (`machine-config`), the ledger, PM data, lock state, `.kit.json`, generated files, gate results (`gate-result`), destructive git in a main checkout, `branch -D`, forcing or deleting main, `core.hooksPath`, owner identity, the owner's delegation list (`owner-delegations`), kill-by-name, an agent's shared stash in a linked worktree (`git-stash-shared`), git that python or node code on the line runs (`interpreter-git`), the backlog's roles, raw writes and audit log (`backlog-role`, `backlog-raw-write`, `pm-data-audit`), who lifts a branch's gate budget (`gate-allow`), a brace expansion the guard does not write out (`brace-limit`), file-tool edits of a main checkout, and the write jail's outer bound (`dev-drive`, "Write jail").

The owner sets a rule's mode in the machine config's `guard_rules` (`{"<rule>": "deny"|"warn"|"off"}`; docs/kit-json.md "Machine config keys"), and only there: never `.kit.json` or another file a branch carries, so a branch cannot loosen the rules it is judged by. A value that is not one of the three is ignored, and a config that does not read leaves the defaults (`modes.resolve`).

- **unplaced:** a write the guard cannot place (a computed or unread target, code given on the line, a git or .NET call whose directory the text does not tell, a computed `-C`, a computed `git worktree remove` target, a computed push refspec with no `--force`, `--delete`, `--no-verify` or literal `+` or `:`, git on a jailed session's unreadable line) is refused under `unplaced` instead of the placing rule (`rules.unplaced`, `rules.PLACE_RULES`: `main-checkout`, `write-jail`, `git-main-history`, `git-restore`, `git-checkout`, `git-reset-hard`, `git-clean`, `git-stash`, `git-bulk-add`, `git-commit-all`, `dev-drive`), with the same reason and alternative. Those rules still deny a write that resolves literally into a main checkout or outside an agent's folders, and so does a write git cannot place inside a `.git` folder, or git pointed elsewhere by `GIT_DIR`, `--git-dir`, `--work-tree` or an environment change the guard cannot read (`write-jail`).
- **gate-result:** an agent session's literal write into a repository's gate result folder (`<git common dir>/kit-gate-result/`, `rules.gate_result`), which only the gate writes, is denied; `Instead:` is `python "<kit>/tools/gate.py" wait-result <branch> --tip <sha>`.
- **Tests:** tests/guard/test_cheap.py (each mode, the defaults, the owner's overrides, the kept denies).

## Hosts

The guard judges a neutral `kitlib.host.Action` and answers a `kitlib.host.Decision` (ARCHITECTURE.md "Host contract"); no module under `kitlib/guard/` reads a host's payload or writes its output.

- **The hook:** `boot/hook.py claude PreToolUse` (the one entry of every host) hands Claude's adapter, `hosts.claude.adapter.host.ADAPTER` (the module `hosts.json` names), to `kitlib.host.hookmain.dispatch`, which runs `kitlib.host.hookmain.run`: the event JSON is parsed by `hosts/claude/adapter/events.py` `parse`, judged by `kitlib.guard.decide(action)`, lowered by `kitlib.host.degrade` when the host cannot show an ask, and rendered by the adapter's `render` (nothing for a plain allow, the warning for a warned one, the JSON in "Output" for a deny or an ask), with the refresh line added by `tool_context` when there is one ("Output"). The fail-closed deny, an optional deadline (rule `guard-timeout`; Claude passes none) and the settings entry (`hookmain.command_line`, the one place a hook command line is written) are hookmain's, the same for every host.
- **What Claude's adapter reads:** `tool_name` sorts the call: a file tool (Edit, Write, MultiEdit: `file_path`; NotebookEdit: `notebook_path`) is an `edit`, Bash and PowerShell a `shell` (`command`, its dialect, `run_in_background`), Read and Grep a `read` (`events.READ_TOOLS`: Read's `file_path`; Grep's `path`, absent meaning `cwd`, with `Action.params` `{search: contents, filter: <Grep's glob>}`; Grep's `pattern` is not read), `mcp__*` an `mcp` call, anything else, Glob included (a names search reads no token's text), `other`. `cwd` as sent. `agent_id` is `Action.agent`; `agent_type`, for a subagent only, is `Action.agent_role` with one kit plugin prefix dropped ("Agent names"). `PM_KIT_ROLE` is read from the hook's environment, as before.
- **Host facts the rules need** arrive as Action fields or from `hosts.json`, never as host names in kitlib: the role a subagent runs as (`agent_role`), the shell dialect, whether the call is backgrounded, the host's form of the same edit at another path (`retarget`, for an `Instead:` line), and the lock MCP's tool names (the host profile's `mcp_tool_format`; "Lock MCP").
- **Paths:** every path the guard folds to compare, key or make canonical goes through `kitlib/guard/paths.py` `norm` (on Windows the rules are unchanged; on Linux the case fold is per mount, "Write jail" "Paths"). A command line's text (drive letters, quoting) is the shell parser's, not a path rule: on Linux (`paths.posix`) `shell.resolve_path` reads a word starting with `/` as absolute and any other in the folder the line is in (no drive, share or `/c/x` mapping) and reads each `..` from where the links before it lead, as the kernel does (`paths.physical`: with a link `d` to `/x/src`, `d/../f` is `/x/f`; a Write or Edit tool path is read the same way), bash's `cd` is `cd`, `pushd` or `popd` by its exact name (`CD` and `chdir` move nothing, an assignment before it is passed over) and `cd /d` goes to the folder `/d`; the folder a cd moves to is kept as a real path (`shell._linux_cd`), with a flag when it was entered through a link (its text, or the folder before it, was not its real path): a cd with no `..` is the real path of its text, whether or not the folder exists yet (bash's `-L` and `-P` readings land on the same folder), so `cd d && echo x > ../f` with a link `d` to the main checkout's `src` writes the main checkout's `f`; a cd with a `..` is unknown after a cd through a link (bash folds it from a `$PWD` the guard does not keep), or when the real path of the reading bash's default `cd -L` makes (`..` folded from the text) is not the real path of the text read physically (bash falls back to the unfolded text when the folded folder is missing), and otherwise is that real path (`cd -P` is read physically, with no flag); a nested shell started in the folder keeps its flag; a folder `env -C` or Start-Process `-WorkingDirectory` names is kept as its real path too (`shell.chdir_real`), and is unknown when it is no existing folder, or when it is the starting command's own folder reached through a link (a bash started there keeps the inherited `$PWD`); a line naming `CDPATH`, `SHELLOPTS`, `BASHOPTS`, `cdable_vars`, `set -P` or `set -o physical` anywhere leaves the folder of every cd it runs unknown, in its nested shells, evals and substitutions too, unless the cd's place starts with `/` and holds no `..` (none of them redirects it), and so does a `pushd +N`/`-N`; a cd place holding `*`, `?` or `[` is unknown on both systems; a write after a cd left unknown is `unplaced` (warn by default), bash drops every unquoted backslash (`\.\./x` is `../x`), `/` is a root as a drive root is (`rules.is_root`), and a ledger path is placed when it starts with `/` (`context._placed`). The guard is declared ready on Linux (`kitlib.guard.READY_PLATFORMS`; tests/guard/test_linux_paths.py runs on Windows through the platform seam).
- **Tests:** the guard tests build Claude payloads and decide them through the adapter (`tests/guard/claudehost.py`); tests/guard/test_entry.py runs the hook end to end.

## Parsing

`kitlib/guard/shell.py` tokenises Bash and PowerShell, and `cmd /c` text. `commands.py` reads the result.

- **Seen as text, not commands:** quotes, here-docs and PowerShell here-strings.
- **Seen as commands:**
  - `;`, `&&`, `||` and `|` split commands;
  - `$(...)`, backticks, a PowerShell argument in `( )` (one computed word, `shell._Scan.ps_paren_arg`; "Rules") and `powershell -Command "..."` (`/Command`, `–Command`; after a switch powershell.exe does not know (any switch outside `commands.PS51_SWITCHES` and `PS51_ALIASES`, pwsh's value switches included; after `-i`, `-in` or an `-EncodedArguments` prefix the next word is read both as its value and as the command, `PS_VALUE_EITHER`; past `PS_FORKS_MAX` of them on one reading path the line is flagged `a powershell switch line with too many readings` and each further one is read as taking no value), which starts its command, both that text and a later `-Command` or standard input, each reading kept once and parsed on its own (`commands.expand`): `commands._nested_text`; `-File -` (any prefix of `-File`, whatever words follow it) reads its script from standard input as `-Command -` does, so text piped into it is parsed as a nested command and judged by the same rules, and a pipe the guard cannot read makes the line unreadable; after a switch powershell.exe does not know, `-File -` makes the line unreadable, as `-Command -` there does, and the words from that switch on are still judged as its command), `bash -c`, `cmd /c` (`//c`, `/k`, `//k` too, as Git Bash passes them) bodies are parsed again as nested commands;
  - the command after find `-exec`, `-execdir`, `-ok` or `-okdir` (up to `;` or `+`) is a nested command at find's working directory (`-execdir`/`-okdir`: at an unknown one), its words that hold `{}` computed;
  - a `trap` handler is a nested command at the trap's working directory, or at an unknown one when the line holds `cd`, `pushd`, `popd` or `Set-Location` anywhere (`commands.LINE_CD_RE`); a `mapfile`/`readarray -C` callback is a nested command;
  - `env -S <string>` is a nested command;
  - a shell (`cmd`, `bash` and the other `commands.BASH_SHELLS`, `powershell`, `pwsh`) that `Start-Process` (`saps`, `start`) starts runs its `-ArgumentList` as a nested command, at the `-WorkingDirectory` when one is given (`commands._sp_shell_text`): Start-Process hands it one command line, the elements joined with spaces, so for `cmd` the rest of that line after `/c` (`/k`, `/r`) is the text, read once with its outer quotes and once without; `bash` and `powershell` read their usual `-c`/`-Command` text from the words each element splits into (`commands._split_list`). The list is every word of an array, given by position or after `-ArgumentList` in its space or colon form (`-ArgumentList:'/c','echo x'`), up to the next unquoted, non-computed dash word (`commands._ps_param_word`; a quoted `'-NoProfile'` element is the child's), and a program given by position after `-ArgumentList` is the last word it took (`commands._start_process`). The common parameters (`-Verbose`, `-Debug`, `-ErrorAction`/`-ea` and the other `commands.PS_COMMON_VALUES`) and `-PSPath` (FilePath's alias) are parameters, never the program or a list word; a colon with nothing after it (`-FilePath: cmd`, `-WorkingDirectory: <dir>`) takes the next word. Start-Process resolves `-WorkingDirectory` as a wildcard path, and a bare `C:` or a drive-relative `C:x` against that drive's current location, so a value the guard cannot place exactly (`commands.sp_workdir_unplaceable`: those, a `*`, `?`, `[` or backtick, a device path, a Git Bash `/c/x` spelling), and a computed one (`$x`, `(Join-Path ...)`), leave the nested line no directory and its write is refused as one the guard cannot place. These readings follow PowerShell's binding closely, not exactly, so a parameter word they cannot place makes the line unreadable (below);
  - any other program `Start-Process` starts with a `-WorkingDirectory` (git, python, cp and the rest) runs in that folder (`commands.run_dir`, read as above): `commands.git_call` takes it as the directory git starts in, so `Start-Process git -ArgumentList 'commit',... -WorkingDirectory <main>` from a worktree is a commit in the main checkout. The shell-write rules ("Rules", `rules.shell_writes`) judge a program's own targets (the working directory a `python -c` or a script writes, cp's operands) from both that folder and the command's own directory, refused when either is a main checkout; git, and a `git-*` program, gives none there, its writes being the git rules' (tests/guard/test_start_process_workdir.py): a worktree workdir never lets a write pass that the command's own directory refuses, so `Start-Process python -ArgumentList 'x.py' -WorkingDirectory <wt>` typed in the main checkout is refused, while the same git call is not. For a main-checkout workdir typed in a worktree the `main-checkout` alternative is the same call with `-WorkingDirectory "<wt>"`. A computed workdir, or one `commands.sp_workdir_unplaceable` names, gives no folder: git there is git whose directory the text cannot tell, and the program's writes are ones the guard cannot place. A redirect and `-RedirectStandardOutput`/`-RedirectStandardError` stay placed from PowerShell's own location, which the workdir does not move (tests/guard/test_advice_workdir.py);
  - `cd`, `Set-Location`, `pushd` and `env -C <dir>` move the working directory for the commands after them.
- **Wrappers:** `env`, `command`, `exec`, `nohup`, `nice`, `time`, `timeout <n>`, `stdbuf`, `sudo` and `xargs` are skipped with their options (`time -p`, `nice -n 5`, `stdbuf -oL` and so on). The program after them is read. After `xargs -I`, `-i` or `--replace` (`commands.xargs_opts`), every later word that holds the replace string is computed (`commands.fill_words`): the program word and `sh -c` or `env -S` text too. The first `git` word in its tail is the program.
- **Redirects:** recorded per command with their targets.
- **Arguments the shell rewrites:** brace expansion, ANSI-C strings (`$'a\tb'`) and a bash backslash in a word are read as the words the shell produces. Every unquoted brace group of a bash word is written out, nested groups too, in bash's order (`{a,b}{1,2}`: a1 a2 b1 b2; `{x,{y,z}}`: x y z). A word that would give more than `shell.BRACE_LIMIT` (256) words is not written out: the parse is unclean ("Fallback"), the word is one computed word, as a variable would be, and rule `brace-limit` refuses the line ("Rules"; kitlib/guard/shell.py `_brace_group`; tests/guard/test_shell.py `BraceExpansion`, tests/guard/test_delegfile.py). Brace groups bash expands that the guard leaves as written: "Known limits".
- **Git spellings:** `-C`, `-c`, `--git-dir`/`--work-tree`, `--config-env` and git's place and config variables are read; long options are matched by unique prefix, and options that take a value skip it.
  - The variables (`commands.GIT_ENV_NAMES`): `GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`, `GIT_INDEX_FILE`, `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_<n>`, `GIT_CONFIG_VALUE_<n>`, `GIT_CONFIG_PARAMETERS`. One counts when set before the command (`=` or bash `+=`), through `env`, by `export` and the like (with or without a value; not a `-p` listing of `declare`, `typeset` or `local` such as `declare -p GIT_DIR`: `export -p` and `readonly -p` with a name still count, and not bash's or PowerShell's `set`, where `set -- GIT_DIR` sets `$1`: cmd's `set` counts, `commands.exporter_args`), `$env:`/`${env:}` (`=` alone or in the same word), `Set-Item`, `Set-Content`, `Add-Content` or `New-Item -Name` on `env:`, a `Rename-Item`/`Copy-Item`/`Move-Item` to an `env:` name, or a `SetEnvironmentVariable` call (not a string that names it, as a commit message or `Write-Host "..."`; a `$( )` in a string is a call) (`commands.git_env_set`). Set anywhere in the line, nested text included (`eval`, `bash -c`, `env -S`, `Invoke-Expression`, a `source` of `/dev/stdin`), it leaves every git of the line unplaceable (`commands.mark_git_env`), whatever the order. One exception: `GIT_INDEX_FILE` set alone before a git, as a prefix or through `env` (`GIT_INDEX_FILE=<tmp> git read-tree`), reaches only that git and the text nested in it, so the line's other git is placed as written, unless the line may define a function or an alias (`commands.git_env_prefix`). A name is read as the shell passes it: a backslash bash drops inside it (`export GIT_D\IR=`) is dropped (`commands.said`, `commands.passed`).
  - Only literal assignments are read (`commands.git_env_set`, `commands.line_env_names`, `commands.ps_env_targets`). A name the text computes (`export $V=`, `local -x $1=`, `Set-Item "env:$n"`, cmd `set %V%=`) and any other way to change the environment (`declare -n`, `set -a` with a `source` of a file, `alias`, a `trap`, `read`, a leading backslash `export \GIT_DIR=`, a splat, script text PowerShell compiles, `Start-Process -Environment`, an `env:` item renamed or copied to another name) is not read (the guard catches honest mistakes, not evasion).
  - A `$env:VAR` that starts an item path (`Set-Content "$env:TEMP\x.txt"`, `Copy-Item a.txt $env:TEMP`) is a read. A line with no git is not affected.
  - Once one of these, `--git-dir`, `--work-tree`, `core.worktree` or `--config-env` makes git unplaceable, a `-C` before or after it does not place it again (`commands.git_call`).
  - Every git word is matched in the form the shell produces, the subcommand and options included, not only the program word.
  - A subcommand the text does not spell out (a variable, a substitution) makes the parse unclean. So does such a word in an option position that the git rules read.
  - Put `--` before a variable path, so it is not read as an option.
- **Unclean parse:** the parse is unclean when the text holds something the tokeniser does not model:
  - an unclosed quote, substitution or heredoc, a PowerShell `<#` with no `#>` (`shell._Scan.tokens`), or a `case` statement;
  - an encoded command, or a shell, `iex` or `Invoke-Expression` reading its commands from a pipe;
  - `iex`/`Invoke-Expression` of a computed value (`iex ("git " + "stash")`, or `"git $s" | iex`);
  - a shell or `source` reading a process substitution (`bash <(...)`, `source <(...)`);
  - a non-literal `bash -c`, `powershell -Command`, `cmd /c`, `eval` or `env -S` text, `trap` handler or `mapfile -C` callback;
  - a shell `Start-Process` starts with a computed `-ArgumentList` element (an `@(...)` array included);
  - a `Start-Process` (`saps`, `start`) parameter word that names no parameter of it or names more than one (`-Bogus`, `-e`), or a switch whose `-Name:` is followed by a space (`-Wait: $true`), with or without a program (`commands._start_process`, its `unread`; with no program, a `commands.Unread` that only `commands.expand` gets, so `rolepolicy.lock_verb` still sees a call with no program);
  - an unquoted `--` in a `Start-Process` call (every later word positional), a splat (`Start-Process @p`, `Start-Process cmd @p`: `commands.PS_SPLAT_RE`), or `--%` between its words (the rest of the line passed as written; `commands.PS_STOP_PARSING_RE`), each in any of the dashes `shell.PS_DASHES` (`commands._sp_unreadable`);
  - a `cmd` word before its run switch, typed or passed by `Start-Process`, that holds `/c`, `/k` or `/r` anywhere but is not that switch alone (`/cecho`, `/q/c`, `;/c`, `,/c`, `=/c`, `x/c`, `"/c"`; `commands.CMD_RUN_HIDDEN_RE`, searched, not matched at the word's start), since cmd splits its switches at `,`, `;` and `=` as well as spaces; or a typed `cmd` word before its run switch that is computed (`commands._shell_text`);
  - a program named by a variable or a substitution;
  - a git subcommand or read option that is not literal;
  - a brace expansion, ANSI-C escape or backslash in a program name;
  - a `cmd` `if` statement or `for ... do` loop;
  - more than `commands.MAX_NESTS` (64) nested shell texts in one line (`commands._nest`): each powershell reading may be a powershell line that forks again (`pwsh -i pwsh -i pwsh ...`), so the line's total is capped; a reading is not merged with the same text under another outer command, whose chain the rules read.

## State

Every rule is a read-only check of real state. `kitlib/guard/context.py` `Ctx` gathers what the rules read, so tests can hand them a fake machine.

- **Place:** `kitlib.git.repo.classify`'s answer for the working directory or the target path: MAIN, LINKED, NONE or UNKNOWN.
  - `kitlib/guard/place.py` reads it from `.git`, gitdir and commondir files, so a call starts no git child. It reads the common config and, while that turns `extensions.worktreeConfig` on, the work tree's own `config.worktree` after it, as git does (the last `core.bare` wins). Any shape it cannot read the way git would (a bare or `core.worktree` repository, any other extension, `[include]` or `[includeIf]`, a `core.repositoryformatversion` above 1, a config line git refuses or continues onto the next, a broken gitfile, a path inside a git directory, a junction, symlink or subst drive on the way, a folder another user owns, a discovery variable such as `GIT_OBJECT_DIRECTORY`, any error while reading) goes to `repo.classify`.
  - Tests: tests/guard/test_fsplace.py asks both on real repositories; tests/guard/test_place_decisions.py decides every rule row with each and requires the same decision.
  - The PM data worktree (docs/pm-data-branch.md "Guard place and commit hooks") counts as MAIN, though git calls it LINKED: `Ctx.place` answers MAIN for a linked worktree whose top is the machine config's `pm_data.path`. Only when the machine config has no `pm_data` does the record decide: a linked worktree whose HEAD is `ref: refs/heads/<branch>` of the `kit-pm-data.json` record in its git common dir. When the strict reader refuses the machine config for another key, `pm_data` is read and checked on its own. The main-checkout rules then apply there, and a refusal names no new worktree to make (agents do not work in it). `git push` and `git worktree remove` act on the repository the data worktree shares with the kit, so from it they are judged by the kit's own `.kit.json` (refused when it does not load), and the data branch alone by the data worktree's. A main checkout is never changed. Fail closed (rule `pm-data`, subagent writes): a machine config whose `pm_data` does not read denies every one; a linked worktree whose record or HEAD does not read denies those aimed at or run from a linked worktree of that repository. Tests: tests/guard/test_rules.py `PmDataPlace`.
- **Config:** `.kit.json` of the main checkout a path belongs to, via `kitlib.config.load`. A worktree's own `.kit.json` is never read, so a branch cannot loosen its own rules. The one exception is the PM data worktree, which counts as MAIN: its own `.kit.json` is read (none there: the defaults, under which a subagent may not edit it).
- **PM data record:** `Ctx.pm_root` reads the root commit from the record in the git common dir of the machine config's `pm_data.path` (none when the machine config names no `pm_data` or that repository has no record; a record or config that does not read, or a `pm_data.path` git cannot place, is an error). Only `rules.data_copy` reads it, and fails closed on that error. The guard runs no git of its own for these rules: an alias in git's config is not looked up, and whether a repository is a copy of the data or shallow is not checked (the guard catches honest mistakes, not evasion).
- **Lock:** held only when `MACHINE_LOCK_RUN` names a run that `kitlib.lock.run.nest_check` accepts: an ancestor of this process, alive, and holding. The variable alone is never proof.
- **Gate-OK record:** `kitlib.gate.runner.verify_record(root, sha)`, the record in the dev drive's record folder, or, only with no `dev_drive`, its `.git` copy (docs/gate.md "Gate-OK record", "Where the records are"). The record must name a `config_rev` in that commit's history, and its gate config hash must be that of the `.kit.json` "gate" the `config_rev` commit holds (docs/gate.md "Gate-OK record"). A record without `config_rev`, or made under another gate config, does not count.
- **User config:** the machine config (docs/kit-json.md "Machine config keys"), for `ledger_path`, `ledger_dir`, `guard_mcp_prefix`, `guard_mcp_tools`, `guard_agent_marks` and `guard_mark_roots`, read tolerantly (a value that is not a string or a list of strings, such as `guard_mark_roots`, is dropped when the strict reader refuses the file). A file the strict reader refuses still yields an absolute `ledger_path` and `ledger_dir` (a relative one read against the PM repository), so the ledger and its rulebooks stay protected. A file that cannot be read, is not JSON or is not an object, or a `ledger_path` or `ledger_dir` that is not a path string or is blank (the key is then unset), or one that is not absolute once read (`C:books`), or a `ledger_dir` that exists and is not a folder (a trailing separator dropped first) (both still held as given), denies every subagent write (rule `ledger`, fail closed; `context._ledger_checked`, on the strict answer too). While such a fault leaves a ledger key unread (a blank or non-string key, a relative one with no PM repository, a file that cannot be read, or a `BAD` location whose pointer config cannot be read: `Ctx.user()` sets `ledger_unread`), the guard cannot place the ledger, so it asks the owner (ASK, rule `ledger`, `rules.ledger_unread`; a deny on a host without ask) about every edit and shell write of a main session, a target it cannot place included (one a worktree's write would pass with: `rules._write_from`, `rules.find_exec_writes`), and its git path writes (`rm`, `mv`, `restore`, `checkout-index`, `checkout` with paths; tree forms and moves only where `rules.ledger_wide_binds` binds), and denies a subagent's, git path writes included (`rules.ledger_git_unread`). The ask comes last: any other refusal of the call (a held ledger path, a protected file, `main-checkout`, `write-jail`, the git rules, the role policy's) wins over it (`edit_target`, `ledger_git`, `rules.Asked` in `shell_command`, `shell_writes` and `decide`, which still runs `rolepolicy.screen` after an ask); a ledger key that is still read keeps its paths denied for every session (tests/guard/test_ledger_dir.py `UnreadTest`). The file is the one `kitlib.config.user.locate` names, taken once per call (`Ctx.config_location`): the PM repository's `.pm-kit/config.json`, with `local.json` for the `LOCAL_KEYS`, never a home folder's file while the PM repository has one; a config still only in the home folder (`UNMOVED`), a home copy still beside the PM repository's files (`LEFTOVER`) or a location it cannot tell (`BAD`) denies every subagent write too, and an `UNMOVED` file, or for `LEFTOVER` the PM repository's `config.json`, is still read for its `ledger_path` and `ledger_dir` (`LEFTOVER`: those two keys only; for `BAD`, those two keys only, from `<pointer>/.pm-kit/config.json` when the PM-repo pointer's value is absolute (`Ctx._bad_ledger_keys`; a file there that cannot be read, is not JSON or is not an object adds nothing, and a ledger key there that is not a non-blank string is not taken; tests/guard/test_ledger_dir.py)), so the ledger, its rulebooks and its digest stay protected for every session (docs/kit-json.md "Moving the machine config folder"). The paths Copy-Item takes from the pipeline are what it reads, so for it that path is its `-Destination`.

An option the guard does not know takes no value, so the words after it count as files. awk with none of these writes nothing.

A long option that is unknown or ambiguous, or an option that is not literal, makes every operand a target. mv also writes its sources; `install -d` writes every operand; `ln <target>` alone writes the working directory.

A `-C` is read in a cluster after letters that take no value (`-xvC <dir>`, `rules.TAR_FLAGS`), as `--directory` down to `--dir` and as bsdtar's `--cd` (Windows' `tar.exe`), and in an old-style first word, whose letters take their values in turn (`tar xCf <dir> a.tar`, `rules._tar_old`). A `C` that may be another option's value (`-xfC <dir>`, `-NC<dir>`, `--exclude -C<dir>`, after a letter the guard does not know) judges the working directory as well (`rules._tar_word`). An extraction to standard output writes no file and is a read: `-O` in a cluster before any letter that takes a value or that the guard does not know (`-xOf a.tar`, `-xvOf a.tar`, `-x -O`, the old-style `xOf a.tar`), or `--to-stdout`; in `-xfO` the O is the archive's name, and `--to-command` still writes (`rules._tar_stdout`);

- Code given on the line counts as a write to the working directory: `python -c` or a script on stdin (any `python`, `python3.12`, `py` or `pythonw`), `node -e`/`-p`, `ruby -e` and `perl -e`. `python -c` is read in any spelling (`-Ic`, `-cCODE`, after `-X <v>`, `-W <v>` or `--check-hash-based-pycs <v>`; `rules.py_program`). Whatever the code is, the guard does not read what it writes: a `python -c` that only reads, `-I` or not, is a write of the directory it runs in like any other (tests/guard/test_pyreads.py; tests/guard/extra_rows.py). Run it from a worktree, or read files with the Read and Grep tools.
  - PowerShell: a python run is a write of its working directory, a script or module too, when any word of a PowerShell command on the way to python (python's own, or the text of a `bash -c` around it) holds a double quote, is empty, or holds a blank and ends in a backslash (`rules.ps_native_unsure`). Windows PowerShell 5.1's native-argument quoting can hand python other words than the guard read: it passes an inner double quote unescaped, drops an empty argument (so `python '' -c "<code>"` runs code), and wraps an argument with a space in quotes without doubling a trailing backslash. So `python tools/x.py --note ''` from PowerShell is a write of its working directory.
  - Start-Process (and its aliases `start`, `saps`): a python it starts is a write of its working directory, a script or module too. It gets one command line the guard re-splits with the quotes taken out, so the words python reads are not the ones the guard read. The directory it writes is the command's own and also its `-WorkingDirectory` when one is given (`commands.run_dir`, "Parsing").
- find `-delete` writes to find's paths.
- A writer that a bash find's `-exec`, `-execdir`, `-ok` or `-okdir` runs writes to find's paths too, when the guard cannot place its target (`rules.find_exec_writes`). That target is:
  - the `{}` find fills in;
  - a path the nested line computes, such as the `"$1"` of `sh -c 'rm "$1"' _ {}`;
  - a relative path at `-execdir`'s unknown place.

  Each start path of each find around the writer is judged as its target, or the directory find runs in when it names none, through any shell nested between (`rules.find_runs`). So `find <outside> -exec rm {} +` from a worktree is refused as `find <outside> -delete` is, and the alternative runs the same find on the worktree; `find <outside> -exec grep -l x {} +` still reads. A start path the guard cannot place passes from a worktree, as any target does (tests/guard/test_jail.py `ShellForms.test_find_exec_writer_is_judged_where_find_searches`).
- A writer fed by `xargs` with no literal target writes the working directory.

A write target that is not literal (a variable, a substitution) is denied when the command runs in a main checkout or a place the guard cannot tell (fail closed). Under PowerShell it is denied from every location (`rules.shell_writes`): a linked worktree or any other place git can tell, a main checkout, a place git cannot tell and an unknown location (after a computed `cd`) alike, since one `$p` or `(Join-Path ...)` can name the main checkout. The `main-checkout` rule refuses a role that may not edit one, and `write-jail` refuses any other agent session, the coordinator's mark in a main checkout included (`rules.ps_drive_jail`). In every shell, a relative target after a move to a location the guard cannot tell (`cd $x`) is refused the same way, as `unplaced`, for an agent session whose role may edit a main checkout (tests/guard/test_unknown_dir_jail.py). So is a write in the line a shell Start-Process starts in a computed `-WorkingDirectory`, which leaves that line no directory as an unknown `cd` does ("Parsing"). The owner's session is not held. So `Set-Content $env:TEMP\x.txt` from a worktree is refused; name the temp path literally. `-Path: x`, a colon then a space, binds the next word as `-Path x` does, and `-Destination:$p` binds its computed rest to `-Destination` (`rules.ps_params`, `rules.PS_NAMED_DYN_RE`); an en dash, an em dash or a horizontal bar names a parameter as `-` does (`shell.PS_DASHES`). A PowerShell argument in `( )` (`Set-Content (Join-Path a b) x`, `-Path:(...)`, `-Destination(...)` touching its parameter, and a `( )` touching any other word, which PowerShell passes as the word and then the `( )` as the next argument: `Copy-Item a.txt(...)`, `Set-Content(...)`, `'x'(...)`, `$x(...)`, `[string](...)`) is one such word whose commands are read as nested ones (`shell._Scan.ps_paren_arg`), unless the command's first word, or the first after an assignment's `=`, is a keyword that takes one (`if`, `foreach`, `while`, `switch`; `shell.PS_PAREN_KEYWORDS`, `shell._ps_keyword_led`): `Copy-Item data (...)` passes an argument. A `(` that does not touch the word before it is an argument whatever stands between: a space, a comma, a redirection (`Set-Content -Value hi 2>&1 (...)`), a backtick line continuation or a `<#comment#>`. A redirection to a `( )` or a `{ }` (`'x' > (Join-Path a b)`, `'x' > { ... }`, which writes to the script block's text) is a target that is not literal, and the `( )`'s commands are read as nested ones (`shell._Scan.target`). A `( )` inside a word's `[ ]` index is part of that word (`$x[(...)]`, `shell._Scan.word`). A `(` touching a member access (`$s.Replace('a','b')`, `'abc'.Replace(...)`, `[IO.Path]::Combine(...)`, `(Get-Date).AddDays(1)`; `shell._PS_MEMBER_HEAD`, `shell._PS_MEMBER_TAIL`) is a method call: the `( )` stays a group and the word, the method's result, is not literal, judged where it binds like any other word. Every PowerShell writer is also held by one coarse rule that does not depend on how the scanner read a `(` or a `{` (`rules.ps_unread`): a write cmdlet, an `Export-*` cmdlet, a copier (`robocopy`, `xcopy`), and `curl`, `wget` or `tar` run from PowerShell write a target that is not literal, standing for what the guard does not read, when any argument is not one it reads. A cmdlet's argument must be a plain word or string, a variable, or a string holding variables (`rules.PS_CMDLET_ARG_RE`); a native program's a plain word or string (`rules.PS_PLAIN_ARG_RE`), since PowerShell spreads a splat, or an array in a variable, into its arguments. An `Export-*` cmdlet with no spec has every positional, word after a parameter and colon value judged as its path, bar the value of `-InputObject`, `-Depth`, `-Encoding` or a common parameter (`rules.ps_export_targets`). The one value of a parameter that names no path (`rules.PS_VALUE_PARAMS`: `-Value`, `-Encoding`, `-Filter`, `-NewName` and a few more) is passed over when it holds no command: a word, string or variable, a `( )` the scanner reads as one word, or a here-string with no `$( )`, with member calls on plain arguments after it (`-Value $s.Trim()`, `-Value (Get-Date)`, `-Value @'...'@`; `rules._ps_value_end`); a `$( )` (`-Value "at $(Get-Date)"`), and a positional `( )` or here-string, which could be the path, are not. A splat (`Set-Content @a hi`, `robocopy . @a`), a script block (`-Path { $p }`, a delay-bind `-NewName { ... }`), a type's member call (`[x]::y(...)`), a `( )` touching a group's `)` (`$a.M(1)(...)`), a word after an unquoted comma (an array binds to the parameter before it: `-Value 'a','b' x`), and a command that is split (below) or followed by a `( )` or `{ }` no value accounts for each make such a target. So `Remove-Item a.txt,b.txt` and `curl.exe -o x.txt -H $h` are refused from every location. A PowerShell redirection whose target is not one plain word, string or variable (`'x' > ` followed by a line continuation and `(...)`), or that has none the scanner read (`'x' > <#c#>(...)`), is a target that is not literal too (`rules.write_targets`). When more of the command follows a group, a method call's included, before a separator (`Set-Content -Value $s.Trim() -Path x`, `Sort-Object { $_.Length } -Descending`), the scanner has read the rest as commands of their own, so the command is marked split (`shell.Command.split`): `rules.ps_unread` stands for the arguments past the group, and the line is not clean (`commands.expand`), which `fallback.check` refuses as `unreadable` for a role subagent. A keyword's own `( )` and `{ }` (`if (...) { }`, `$r = if (...)`, `foreach`, `try`, `catch [T] { }`, `function f(...) { }`) split no command (`shell._ps_keyword_led`), which reads only a keyword or `=` spelled bare: a quoted `'if'` or `'='` is an argument. Two exceptions: `$PWD` or `${PWD}` with a literal rest (`"$PWD\x.txt"`) is read as the directory the command runs in plus that rest, and judged as a literal path, unless that directory is unknown or the write is not the line's only command (`rules.ps_pwd_path`). `$PWD` can be set under many spellings of its name (`sv PWD`, `-OutVariable ('P'+'WD')`, `[scriptblock]::Create(...).Invoke()`), and only code that runs before the target is read can do it, so a write fails closed when an operator stands before or after it (a `;`, `&&`, `||`, newline or pipeline, a script block or `( )` group it is inside, or one among its own arguments: a method call's `( )` or a script block `{ }`), or when a word of its own runs code (an argument `( )`, an index `[(...)]` or a `$( )`): `Set-Content "$PWD\x.txt" x` is judged as a path, and `Set-Content a.txt x; Set-Content "$PWD\x.txt" x` is refused. A line whose write target does not use `$PWD` is not held by this. And `$null` is no file. Under bash and cmd a target that is not literal is not denied from a linked worktree or any other place git can tell. A `cd` inside a PowerShell `$( )` or argument `( )` moves the location for the command holding it and every later one, so their directory is unknown (`shell.track`).

### Kit paths in advice

An alternative that runs a kit tool (`rules.lock_tool`, `rules.kit_tool`, the `wrapped-gate` alternative's `rules.bare_wrapper`) names it under one folder, `rules.advice_kit`: the installed export the session's kit tools run from, the folder the session header names as `<kit>`, when the guard can tell it, else the kit the guard runs from (`Ctx.kit`).

- The guard names the export the machine's plugin marketplace names now (`kitlib.pluginsource.current_folder` under the `plugin` `export_dir` of the user config, default `%LOCALAPPDATA%\pm-kit\plugin`, on Linux `<profile>/.local/share/pm-kit/plugin`), when that folder has a 12-hex-digit name and holds `.pm-kit-export` and `kit.json` (`rolepolicy.EXPORT_NAME_RE`, `rolepolicy.EXPORT_FILES`) and its marker names the kit checkout the guard is from (`kitlib.pluginsource.export_checkout`): for a guard that runs from a kit checkout, that checkout; for one that runs from an export (`.pm-kit-export` in `Ctx.kit`), the checkout that export's own marker names.
- Otherwise (no user config, no marketplace file, an export made from another checkout, a guard's export whose marker names no main checkout) it names `Ctx.kit`.

A session's tool hook can run from another export than its start hook did, and from one a refresh has since replaced, which prune later removes. An alternative naming the hook's own export would then send the agent to a folder that may be gone. The current export is the one prune always keeps, and the one `kitlib.host.headerfollow` tells the session its header names (it compares the header's folder with `rules.advice_kit`), so the alternative and the session's current header name the same folder. Known limit: a header written under another export root (the record lives in `<root>/headers`, so a move of `export_dir` loses it) gets no header update, and the alternative names the current export under the new root.

The hook is not told which folder the session's header named, so a session started on an older export is pointed at the current one. The `heavy` rule lets an interpreter run that export's `tools/gate.py` and `tools/machine_lock.py run` as it does the kit's own (`rules.kit_wrapper` through `rolepolicy.kit_export`, which takes any export folder right under the export root, the current one or not, that is neither inside nor holding a folder the session may write), so an alternative the guard gives is not itself refused as heavy (tests/guard/test_advice_workdir.py).

## Write jail

`kitlib/guard/jail.py` (roots and verdicts), `kitlib/guard/rules.py` `write_jail` and `git_jail` (rule `write-jail`). It holds agent sessions only, as `kill-by-name` does ("Session mark"): subagents and the marks in `guard_agent_marks` (default `coordinator`, `deep-worker`, `consultant` and `pm`). The owner's unmarked session and other marks (`plain`, another agent's name) are not held. Tests: tests/guard/test_jail.py.

- **Write roots** of a session running in `<cwd>` (the hook payload's `cwd`):
  - **its checkout:** the git top of `<cwd>`. In a linked worktree that worktree alone, so the main checkout is outside. A session running in a main checkout gets the whole checkout (the `main-checkout` rule still holds a subagent there). Outside git, `<cwd>` itself, unless it is a drive root or the home folder. No own root at all when that root touches a machine config folder (`jail.own_root`, `jail.touches_config`: on, over or inside either home one, or on or inside the PM repository's `<pointer>/.pm-kit`; the PM repository's checkout, which only holds that folder, stays a root, and `machine-config` refuses the writes inside the folder): a session run in `<config-dir>` would otherwise write the machine config, its guard settings and `ledger_path` among them (tests/guard/test_jail_config_move.py).
  - **its repository's worktrees:** every linked worktree of the repository `<cwd>` belongs to that lies under its main checkout (`jail.sibling`), so a session in one worktree reaches the others, as a session in the main checkout does through its checkout root. A worktree a subagent makes with `tools/new_worktree.py` from a linked worktree is therefore writable. Not the main checkout itself, not the PM data worktree (the guard places it as a main checkout; while it cannot tell which worktree that is, `Ctx.pm_data_error`, no worktree is reached this way), not a worktree that touches a machine config folder (as above), not another repository's worktree or a worktree outside the main checkout, and not a path a link carries out of its worktree (the target is compared after `realpath`). It is not a listed root: the refusal names the roots above and points at `<cwd>`'s own checkout.
  - **temp:** the system temp folder (`Ctx.tempdir`, and `TMP` when it differs), which holds Claude Code's session scratch folders; and the folder the `AGENT_TEMP` environment variable names, when it is set.
  - **data roots:** `.kit.json` `guard.data_roots` (docs/kit-json.md), read from the main checkout only, as every `.kit.json` key is. Each entry is `{path, mode, why}`: `open` (any write), `add-only` (new files only: a write, move or delete of a file that exists is denied; a copy, move or link into the existing folder is judged as `<folder>/<each source's name>`, `rules.copy_into`, when its options are only these: cp `-r -R -a -p -v -n -t`, `--recursive`, `--archive`, `--verbose`, `--no-clobber`, `--target-directory`; mv `-v -n -t` and the same long ones; ln `-s -v -t`, `--symbolic`, `--verbose`, `--target-directory`; install `-v -m -t`, `--verbose`, `--mode`, `--target-directory`. Any other option, or two target directories, is judged as the folder itself, so it is denied. cmd's copy is judged by name only for a source that is an existing file) or `read-only` (no write). A mode holds wherever the folder nests: a read-only folder inside the checkout or temp stays read-only. The kit names no folder.
  - **mark roots:** the machine config's `guard_mark_roots` (docs/kit-json.md), `{<mark>: [{path, mode, why}]}`, adds roots for the main sessions of one launcher mark, compared without case (`jail.mark_roots`, `rules.session_mark`). `path` is absolute or `~/<path>`, read from the home folder; the modes are the data roots' modes. A subagent gets none, not even one of a marked session. A root that touches a machine config folder is dropped ("No root on a machine config folder", below), so no session is given its own guard settings, nor can create the new config file that would replace an old-only one. The schema refuses a reserved mark (`owner`, `subagent`), a relative path and an unknown mode, and a config the strict reader refuses gives no mark roots ("State": the tolerant read keeps no map). The PM's roots (its memory folder, say, or a repository's main checkout whose red landing merges it resets) are set here by the owner: the jailed PM cannot write the machine config. The intended use is folders like those, other repositories' main checkouts above all. A mark root should not cover the account folder `~/.claude` (its `settings.json` registers this hook; the live lock tool is under `tools/machine_lock`) or the kit's own checkout (`boot/hook.py`, `kitlib/guard`): a root there lets the session rewrite the guard itself. Only the machine config folders are dropped by the code. The `lock-state` and `kit-json` rules come first ("Order"), so a mark root never opens the machine lock's state or a `.kit.json`.
  - **No root on a machine config folder:** a root of any kind (checkout, temp, data, mark) that is either home machine config folder, the current or the retired one (`jail.home_config_dirs`; docs/kit-json.md "Moving the machine config folder"), holds it or lies inside it is dropped unless it is read-only (`jail.roots`, `jail.touches_config`): a data root, `TMP`, `AGENT_TEMP` or the system temp folder at the home folder or above would otherwise let the session write the machine config. So is one that is the PM repository's `<pointer>/.pm-kit` or lies inside it; one that only holds it (the PM repository's checkout, a mark root on it) is kept, and `machine-config` holds the folder ("Owner machine setup"; tests/guard/test_machine_config.py `PointerFolder`). A read-only root only denies, so it is kept (tests/guard/test_jail_config_move.py). On Linux the user's PM-repo pointer file, `<profile>/.config/pm-kit/pointer` (`jail.user_pointer_file`: `kitlib.platform.linux.paths.pointer_files`, the profile folder from the password database, never `$HOME`), is held the same way: a root that is it or holds it is dropped, so a file tool or shell write to it is a `write-jail` refusal wherever the session runs and no agent can point the kit at another PM repository (tests/guard/test_linux_pointer.py). Windows keeps the pointer in `HKLM`, and `/etc/pm-kit/pointer` is root's: only an administrator writes either, so the guard names neither.
- **Outer bound (rule `dev-drive`):** while the machine config sets `dev_drive` (docs/kit-json.md "Machine config keys") to an absolute path of an existing folder, read the guard's tolerant way (`Ctx.user`, `jail.dev_root`), a jailed session writes only on the Dev Drive, whatever root would otherwise let it write (`rules.dev_drive_bound`, `jail.on_drive`). The bound is checked last, after the jail allows a target: a file tool's target, a shell write target, a git write's checkout, the folder `worktree add` or `clone` makes, and the lander's landing verbs; git reads are not bounded. A target or root compares after `realpath`, so a junction on the drive that points off it is off the drive. A data root (`.kit.json` `guard.data_roots`) or mark root (`guard_mark_roots`) off the drive is dropped while the rule denies (`jail.roots` `dev`): config load does not refuse it, a write into it is refused as `dev-drive`, and every write the jail judges warns, naming the entry, its path and the key to move it in (`rules.jail_view`). A dropped root opens nothing on the drive: when it holds the Dev Drive (a data root `<drive>/` around a `dev_drive` of `<drive>/dev`), a target on the drive is judged by the other roots alone (`rules.in_dropped`). The refusal's `Instead:` writes to a root on the drive (`jail.destination` with `dev`). Temp, `AGENT_TEMP` and the checkout are not dropped: a write there off the drive is refused the same way. A write the guard only guesses at (the folder a program runs in standing for what its code writes, a piped write) is refused under `unplaced` instead, which warns by default (`dev-drive` is in `rules.PLACE_RULES`). With `dev_drive` unset, relative or not an existing folder (the Dev Drive unmounted, a wrong letter), or a config that does not read, the bound is off and every session start says so; the header asks the guard's own question (`jail.dev_root`), so the two always agree (`kitlib/host/header.py` `NO_DEV_DRIVE`). The owner may set `dev-drive` to `warn` or `off` in `guard_rules` ("Rule modes"); under `warn` no root is dropped and each off-drive write warns. Tests: tests/guard/test_jail.py `DevDrive`, tests/host/test_header.py.
- **Paths** compare after `os.path.realpath` and the case fold (`normcase` on Windows), so `..`, symlinks and junctions are resolved: a junction in the worktree that points out of it is outside. On Linux the fold is per mount (`paths.norm`, from `/proc/self/mountinfo`): a case-folding filesystem (vfat, exfat, cifs, hfs and the like) folds, a case-sensitive one (ext4, xfs, btrfs, tmpfs, overlay and the like) does not, and one in doubt (an fstype not listed, or no table) folds for what the guard refuses but not for what it allows: whether a root allows a target compares case-sensitively (`jail.judge`, `Root.strict`), so a case-variant sibling of an allowed root is outside, while a read-only or add-only root, the main checkout and the guarded files match either case.
- **File tools:** Edit, Write, MultiEdit and NotebookEdit, by their target path.
- **Shell writes:** every literal target "Shell writes" (above) lists. Under bash, `/dev/...` is no file and passes, and on Windows `/tmp/...` stands for the folder `AGENT_TEMP` names, else the system temp folder (Git Bash's mount table is not read). On Linux `/tmp` is itself, a temp root only when it is the system temp folder, `TMP` or `AGENT_TEMP`, and `/c/x` is a path, not drive C.
- **git:** a subcommand that writes is judged by the checkout it runs in (`-C`, a `cd` before it, else `<cwd>`), so `git -C <another repository> commit` is denied and `git -C <a worktree of the same repository> commit` passes. `update-ref`, a push into the repository itself, a `fetch` or `pull` refspec, `symbolic-ref`, `replace`, a `notes` write and the branch, tag, checkout, `worktree add`, `rebase --update-refs`, `remote`, `fast-import` and `filter-branch` forms that write a shared ref are judged from every checkout as well, by `git-shared-ref` ("Rules"): the refs they write are shared by every worktree. The subcommand is the first word after git's global options, each in `commands.GIT_VALUE_OPTS` (`-c`, `--namespace`, `--super-prefix`, `--config-env`, `--exec-path`, `--attr-source`, `--shallow-file`) skipped with the word after it, so `git --attr-source HEAD update-ref -d refs/heads/main` is read as `update-ref`. Reads pass anywhere: `status`, `log`, `diff`, `show` and the other names in `rules.GIT_READS`; `stash list`/`show` (as the first word after `stash`, `rules.stash_reads`), `worktree list`, `remote` (`show`, `get-url`), `reflog`, `notes` and `submodule` without a writing verb; `branch` and `tag` listing; `config` with a read flag (`--get` and the other `rules.CONFIG_READ_OPTS`, `-l`, `--list`) as its own option: before its first word that is not an option and before any `--`, and not as the value of `-f`/`--file`, `-t`/`--type` or another option that takes one (`rules.config_reads`; git stops reading options at the first other word, so `git config a.b --list` sets `a.b` to `--list`, observed with git 2.55); `apply` with `--check`, `--stat`, `--numstat` or `--summary` and no option before `--` but those, `-v`, `-R` and `-p<n>` (`rules.apply_checks`: each turns applying off and only `--apply` turns it on, observed); `patch-id`; `symbolic-ref` with one ref and only `-q`, `--quiet`, `--short`, `--recurse` or `--no-recurse` (`rules.SYMREF_READ_OPTS`: it prints where the ref points; a second name, `-d` or `-m` writes it); `archive` (`rules.archive_outputs`, `--remote` and `--exec` included: docs/guard-v2.md, cut), unless it carries an option the guard does not know or a word that is not literal, or the line may give it a program to run (`rules.archive_filter_set`): a `-c` whose key is not on `rules.ARCHIVE_SAFE_KEY_RE` (`core.quotepath`, `core.autocrlf`, `core.eol`, `tar.umask`, `tar.<format>.remote`; another may name `tar.<format>.command`, a `filter.<driver>.smudge` or `.process`, an attributes file or an `include.path`), any `--config-env`, a word before the subcommand that is not literal, a `commands.GIT_ENV_NAMES` variable or a user config folder (`commands.HOME_ENV_NAMES`) set on the line, `--exec-path=` or a `PATH` change on the line (`Command.path_env`: they say where git finds a filter's bare program name, as Git for Windows' `filter.lfs.process = git-lfs filter-process`), or a git the text cannot place (below). A change counts when the line sets the name literally (`commands.line_env_names`: the spellings of "Git spellings" above, and cmd's `set` behind the `@` and delimiters (`,` `;` `=`) cmd drops before a command name, as a prefix or as words of their own: `@set PATH=X`, `;set HOME=X`, `@ set GIT_DIR=X`, `commands.cmd_invocation`); cmd's own `path` command, a PowerShell cmdlet that clears or removes an `env:` item, and a name computed at run time are not read (the guard catches honest mistakes, not evasion). git runs a filter in the checkout it reads (observed with git 2.55). Each word is read as bash hands it to git (`\-o` is `-o`, `-\c` is `-c`, `commands.passed`); in PowerShell a word 5.1 may split or drop for a program (a `"` in it, empty, or a blank and a trailing `\`, `rules.ps_native_unsure`, observed) fails closed, as does under cmd a word the C runtime may split apart from cmd (a `"` other than one pair around it, or no valid place in the source to read its quotes from, `rules.cmd_native_unsure`). `worktree add <path>` and `clone <url> <dir>` are also judged by the folder they make, and `archive` by the file its `-o`/`--output` names (also `-o<file>`) wherever it sits before `--` (after it, git reads a pathspec): git's first pass (builtin/archive.c `cmd_archive`) takes no value for the other options, so `--prefix -o README.md` opens README.md (`rules.archive_opened`). The guard also counts, failing closed, the forms that pass does not open (`-o` in a cluster such as `-vo`, a prefix such as `--outp=`). So `git -C <main checkout> archive HEAD | tar -x -C <temp>` passes and `archive -o <main checkout>/a.tar` is denied (tests/guard/test_archive_readonly.py). One exception (`rules.lander_check`): the lander role (agent_type `lander`, or the kit plugin's `<plugin>:lander`, "Agent names"; named in the main checkout's `.kit.json` `roles` with `edit_main_checkout: true`, Go-live step 3) may run exactly these commands in a main checkout from its worktree, with `<remote>` and `<main>` the main checkout's `.kit.json` `repo.remote` and `repo.main_branch`:
  - `git fetch <remote>`
  - `git fetch <remote> <main>`
  - `git merge --ff-only <remote>/<main>`

  Each must be alone on its line (`rules.lander_alone`, which reads the event's line again): nothing else, or one literal `cd`, `Set-Location` or `pushd` into that checkout before it, joined by `&&` or `;`. A pipe, a group, a nested shell, `||` or a third command is not alone. git may be spelt `git`, `git.exe` or PowerShell's `& git`, with `-C <main checkout>` or that `cd` before it. Anything else is denied: another option (`--prune`, `--no-ff`, `-s`, `-X`, `--squash`, ...), another ref or refspec (`main:main`, `+main`, `FETCH_HEAD`), a git option before the verb (`-c`, `--config-env`, `--git-dir`, `--work-tree`, `--no-pager`), an environment assignment or wrapper before git (`GIT_DIR=`, `env`), a word that is not literal, any other git write there, a file write there, and every other role. Any main checkout whose own `.kit.json` lets the lander in qualifies, not only the one the lander's session runs in (the PM lands kit branches from its own folder). When a lander's `git fetch` or `git merge` in a main checkout is refused (rule `write-jail`, or `git-main-history` for a merge in a repository that does not set the role), the refusal names the first test that failed, in this order: a `.kit.json` that does not load, `roles.lander.edit_main_checkout` not set (the repository's settings first, since until they allow it every form is refused), not alone, a wrapper or option, the arguments; its `Instead:` is the form to run, or `python -m json.tool "<main>/.kit.json"` when the config is the cause (`rules.lander_refusal`). The lander's own landing command (`land.py`, `gate.py land`) is a python program whose git the guard does not see ("Known limits", "write-jail reads the line, not the program"), so it needs no exception. git whose checkout the text cannot place (a variable from "Git spellings" set, `--git-dir`, `--work-tree`, `core.worktree`, `--config-env`, a computed `-C`, whatever the order of `-C`) and that writes is denied for every session the jail holds, the lander included (`rules.git_jail_unknown`): it may be a main checkout, where `symbolic-ref` or `branch -m` would re-point main's HEAD. The refusal names the cause: for a variable or option it says to drop it and run git in the worktree (`rules.git_unplaced`), for a computed `-C` to name the checkout literally. Only a plain read passes (`rules.git_reads` strict): no word that is not literal, except as `rules.strict_dyn_read` allows in bash and PowerShell (any computed word in `rev-parse`, `ls-files`, `cat-file`, `merge-base` and `for-each-ref`, which have no option that writes a file; in `log`, `show` and `diff` a computed word only when `rules.dyn_head` reads it as one argument that starts with literal text that is no option, as `"HEAD~$n"` or `"origin/$b"`, or with `--format=` or `--pretty=`, as `--format="$w %h"`; `log "$R"`, `log HEAD~$n` unquoted in bash, `"$@"` and a PowerShell array `$f` are denied, and `status`, `describe` and `branch` take no computed word), no PowerShell splat `@a` (`rules.ps_splat`), no `--output` file (abbreviated too) nor `archive -o` (`grep -O` passes: docs/guard-v2.md, cut), and `branch`, `tag` and `config` only with options it names in full, so an abbreviation git expands (`branch --unset-up`) is denied.
- **Not judged:** a target that is not literal under bash or cmd (under PowerShell one is refused from every location, "Rules" above), a command other than git whose directory is unknown, and git whose subcommand the text does not name in a checkout the text places. These meet the rules above them (the `main-checkout` rule fails closed in a main checkout) and the fallback, whose parsed rules include the shell writes and so the jail.
- **Order:** `ledger`, `lock-state`, `hub-secrets`, `owner-delegations`, `machine-config`, `kit-json`, `generated-file` and `main-checkout` are checked first (`rules.edit_target`), so a subagent's edit of a main checkout still reads `main-checkout`.

## Role policy

`kitlib/guard/rolepolicy.py`, run by `decide` on a call the shared rules allow (a call they refuse is refused as before), the same on every host (ARCHITECTURE.md "Roles"). Lifted from the Codex branch's `guard_adapter` and `kit_adapter`.

- **One switch per repository:** the policy runs only when the main checkout's `.kit.json` sets `guard.role_policy: true` (docs/kit-json.md; default false). With it off no role is held, whatever mode a role file or the `roles` table names, and every call is judged exactly as before. Which repositories turn it on is the owner's call; the kit's own repository has it on.
- **Where a mode comes from:** `roles.<role>.mode` in that `.kit.json` (a key under the role's old or new name counts: `roles.opus-worker` holds `senior-worker`, `config.policy.role_name` and `kitlib.content.names_of`), else the `mode:` line of the role's file, `content/roles/<role>.md` under the kit the guard runs from (`Ctx.kit`; docs/content.md "Role front matter"). `kitlib.content.role_mode` reads the role files once per process and reads an old name as its new one (`opus-worker` as `senior-worker`, `kitlib.content.ALIASES`, the launcher's alias table). A role with neither is not held. When the kit has no `content/roles` (a release built without it) or a role file does not parse, the roles it cannot read are not held and the guard goes on; nothing raises.
- **The kit's modes** (the `mode:` lines of `content/roles/*.md`): `controller` pm, coordinator; `write` weak-worker, worker, strong-worker, senior-worker, deep-worker, docs-writer, helper; `read` analyst, consultant; `test` test-runner; `lander` lander.
- **The role:** a subagent's role (`config.policy.role_name`: `Action.agent_role` when the `roles` table or a role file names it, else `subagent`); a main session's launcher mark when one of them names it; else `main`. Claude Code sends a kit subagent's type as `pm-kit:<role>`; the adapter drops exactly that prefix, so the name the policy sees is the role file's stem (another plugin's prefix names no role). The owner's own session ("Session mark") is never held, and the policy reads nothing for it.
- **Modes:** `controller` (pm, coordinator) and `write` (builders) get `role-workdir`, `role-shell` and `role-lock` alone: CLAUDE.md, `.claude/` and the other owner paths stay under the owner-approval rules (`owner.paths`, pre-push), so an owner-approved agent edit of one is still possible. `read` (analyst, consultant) and `test` (test-runner) edit nothing in their checkout and have it read-only to shell; `lander` edits nothing in its checkout (its git landing is `rules.lander_check`'s, as before). All three keep temp and their scratch folder, and have the owner paths read-only.
- **`writes`:** a role file may name repo-relative paths or globs (`writes: [docs/ops/notes.local.md]`; a `*` stays inside one path part) that its `read`, `test` or `lander` role may still edit in its checkout with a file tool, that role alone. No role file uses it now: the consultant's notes file is in agent temp (the launcher's default `--notes-path`, `<agent temp>/<repo>-consultant/notes.md`), which the write jail leaves open. A shell write to such a file stays refused: the jail's roots are folders.
- **Rules:**
  - `role-edit`: a file-tool edit inside the session's checkout by a `read`, `test` or `lander` role, unless its role file's `writes` names the file. An edit outside the checkout (temp, the scratch folder) is the write jail's, as for any session. Its `Instead:` is prose (return the change in the report); with `gate-allow` ("Gate allow") one of the two rules whose alternative is not a command.
  - `write-jail`, with more roots for `read`, `test` and `lander`: every host's owner paths (`hosts.json` profile `owner_paths`: on Claude `CLAUDE.md` and `.claude/`) in the session's checkout are read-only, and for `read` and `test` the checkout itself (not for a file-tool edit of a `writes` file). In a main checkout an owner path that holds the host's worktrees folder (`.claude/` holds `.claude/worktrees`) is left out, so the worktrees under it stay writable. The roots are added to an in-memory view of the `.kit.json`; the file is never changed. A script in temp or the scratch folder (`python <scratch>/check.py`) and output redirected there (`gate.py --full > <temp>/gate.log`) pass. Code the jail cannot read, `python -c` and a script on standard input (`python3 - <<'EOF'`), is judged as writing the folder it runs in: refused in the read-only checkout, allowed from temp, and the refusal's alternative names temp (`jail.destination` skips a root a read-only root holds). A `python -c` that only reads is refused there too (tests/guard/test_rolepolicy.py `test_inline_code_that_only_reads_is_still_refused_in_the_checkout`).
  - `role-workdir`: a shell call whose own working directory (`Action.workdir`, from a host whose shell call names one; Claude's does not) is outside the checkout the session runs in. Another drive is outside.
  - `role-shell` (`shell_gap`): an interpreter that would wait for input on the terminal, nested shells included. Only the interpreter's own options count: they end at the first operand, the script (python, bash, a PowerShell file), the word after `-c` or `-m` (python, bash), after `-Command`, `-File` or `-EncodedCommand` (`-e`, `-ec`; PowerShell) or after `/c` (cmd), so every later word is the program's (`python -m pytest -s`, `python x.py -i`, `bash -c "echo hi" -`, `pwsh -File x.ps1 -n 5` pass). Refused: bash, sh, cmd, PowerShell or python with no arguments; with `-` (bash `--` too) and nothing after it; with `-i` (python, bash), bash's `-s`, PowerShell's `-Interactive` or `-NoExit` or any prefix of it (`-noe`), or cmd's `/k` among its own options; and any of them whose own options name no script, command or informational option (`python -u`, `pwsh -NoProfile`). python's `-s` is "no user site", not standard input. When its standard input is a pipe, a heredoc, a here-string or a `<` file, bare, `-` and bash's `-s` read the script from it and pass (`python3 - <<'EOF'`, `echo x | python3`); `-i`, `/k` and `-NoExit` stay refused. `bash -c bash` is caught at the inner bash. Codex's refusal of `apply_patch` run as a shell command is Codex's own and stays in its adapter.
  - `role-lock`: the lock CLI run with a verb outside the mode's list (`rolepolicy.LOCK_VERBS`), or with `--force` in any abbreviation (`--forc`; `--for`, the hold window option, is not one; `rolepolicy.lock_verb`). A lock call is a command that runs `machine_lock.py` as `rules.tool_run` reads it for `owner-tool` ("Owner lock tools"): the program, python's script, python's `-m` module whose last dotted part is `machine_lock`, or a `Start-Process -ArgumentList` string, any case; its verb is the words after the script or module, before `--`. Text that only names the lock CLI (a read, git on it, a heredoc or here-string, `python -c` code, a name held in a variable or built from pieces, a path handed to another program) is not a lock call and is not judged (the guard catches honest mistakes, not evasion). Only verbs `tools/machine_lock.py` has are named (its parser; `status --days` gives the run history), so any other verb (`stats`, `book`, `unbook`) is refused. `write`, `controller` and `test`: `status`, `run`, `background`, `stop` and the agent rights of "Lock CLI owner writes" (`hold agent|list|end|edit`, bare `division`, `game` and `game show`). `lander`: `status`, `run`. `read`: `status`. Only the words before `--` are the lock's: `run ... -- prog --force` passes. The lock MCP's tools are held the same way, each read as the CLI verb it matches (`rolepolicy.MCP_VERBS`: `lock_snapshot`, `lock_wait_change`, `lock_stats`, `lock_run` and `lock_hold` are `status`; `lock_end_run` is `stop`, `lock_hold_end` and `lock_hold_edit` are `hold end` and `hold edit`; `lock_hold_create`, `lock_set_game_mode`, `lock_set_games` and `lock_set_division` are no mode's), named as rule `lock-mcp` names them (the lock's prefix from `guard_mcp_prefix` or the host profile's `mcp_tool_format`, or a lock tool's name under another server); a tool under the lock's prefix that the server does not have is refused. The owner-only ones meet rule `lock-mcp` first, as before.
- **Tests:** tests/guard/test_rolepolicy.py, over neutral Actions (the switch, role-file modes and their precedence, the alias, Claude's prefixed subagent type, missing or broken role files, scratch edits, `writes`, stdin-fed interpreters, interpreter options against the program's, the lock verbs per mode, the lock MCP tools); tests/content/test_render.py pins the kit's own table.

## Batch files and cmd.exe

Windows runs a `.cmd` or `.bat` file in `cmd.exe /c`, which reads the whole command line again before the batch file sees it: `&`, `|`, `<` and `>` run or redirect another command, `^` escapes, a `"` toggles quoting, `%` expands a variable, `(` and `)` open and close a block, `!` expands one under delayed expansion, and a line break ends the line. PowerShell, Git Bash and Python's `subprocess` quote an argument only when it holds a blank, so `kit status 'a&whoami'` hands cmd.exe `a&whoami` bare and whoami runs. Rule `cmd-reparse` (`kitlib/guard/rules.py` `cmd_reparse`) refuses such a run. No mode names it, so it denies ("Rule modes").

- **The run:** `commands.batch_run` reads the program word from the text alone: a base name ending `.cmd` or `.bat` (any case, any path, either slash, a trailing dot or space dropped), cmd's `call <batch file>`, and the bare kit command `kit` with no extension. The kit command is the `kit.cmd` shim on the PATH, and no file is looked up, so a bare `kit` is caught even when no `kit.cmd` is on the PATH: it fails closed, as intended. PowerShell's `&`, `Start-Process -ArgumentList`, a nested `cmd /c`, `/k` or `/r` text, cmd's `start`, a `bash -c` text and `xargs` are read as for any program. In cmd's own text the program word is also read cut where cmd ends a command name (`commands.CMD_NAME_ENDS`): at `,`, `;`, `=`, `(` and `/` (OBSERVED, `cmd /c` on a scratch batch file: `args.cmd,hi x`, `args.cmd;hi`, `args.cmd=hi`, `args.cmd(hi`, `args.cmd/hi` and `args/hi` each ran it with the rest of the word as its first argument, and `call;args.cmd` and `call,args.cmd;hi` called it; `@` and `+` end no name: `args.cmd@hi` and `args.cmd+hi` were not found). So `cmd /c "kit,status x^&y"`, `call;kit` and `kit.cmd,status` are batch runs; the word is read as written as well, and a quoted one only so. A program the line computes (`& $p`) is not read.
- **Git Bash's start:** `/usr/bin/start` is a script, `"$COMSPEC" //c start "${@//&/^&}"`: it hands every word to cmd.exe's `start`, escaping only `&`. So cmd.exe reads each word before the program does, whatever the program, and a batch file it starts reads them a second time, undoing the `&` escape (OBSERVED, Git Bash `start //b //wait` on a scratch Python script and batch file that print their arguments: for the script `'50%OS%'` arrived expanded, `'a^b'` as `ab`, `'a>f'` made the file `f` and printed nothing, `'a|sort'` and `'a<f'` arrived as `a`, and `'a&ver'` arrived unchanged; for the batch file `'a&ver'` ran `ver`). `commands.bash_start` reads a Git Bash `start` (any path) for the rule: every word after `start` is judged as a batch file's argument is, the program is the first word after start's options (`//b`, `//wait`, `//d <dir>`) and a title (an empty word, or one with a blank, which Git Bash quotes and `start` takes as the title). PowerShell's `start` is `Start-Process`, read as above.
- **The arguments:** a word holding a character of `shell.CMD_REPARSE` (`shell.cmd_unsafe`): `& | < > ^ % " ( ) !`, carriage return and line feed; a computed word, whose value cmd.exe reads; an unquoted PowerShell splat (`@a`); in bash, a word with an unquoted, unescaped `*`, `?` or `[` (`commands.bash_glob`), which bash fills in with file names that cmd.exe then reads, so a file named `x&whoami` would run whoami (`'x*'`, `"x*"`, `x\*` and `$'x*'` are literal and pass; PowerShell and cmd pass a wildcard to a native program as written); and any run `xargs` makes, whose arguments come from its input. PowerShell's `--%` passes the rest of the line through unread, so the words after it are judged as written. `,`, `;`, `=` and the other delimiters only split the arguments, which the batch file's own `%1` reads, and are not refused (OBSERVED: probed on a scratch `kit.cmd`, a `,;=` word arrived unchanged).
- **What was probed** (OBSERVED, on a scratch `kit.cmd` and `gradlew.bat` that print their arguments, Windows 11, Python 3.14): from Git Bash `'-^C'` arrived as `-C`, `'50%OS%'` expanded, and `'q"r' 'a&echo INJ c'` ran `echo INJ`; from PowerShell a word with a line break lost every word after it; a Python `subprocess` list `[..., '--tests', 'a&whoami']` ran whoami. From PowerShell `!` arrived unchanged, as delayed expansion is off under `cmd /c` by default; the Command Processor `DelayedExpansion` registry value can turn it on (INFERENCE, not probed), so `!` is refused as well.
- **Order:** the rule runs last, after each command's other rules, `brace-limit`, `busy-wait` and, on an unclean line, the fallback (`rules.shell_command`, `late`), so a refusal another rule owns (`hub-owner-verb`, `owner-tool`, `backlog-role`, a write rule) answers first.
- **Who:** every session, the owner's own included: the hazard is cmd.exe's, whoever types the line.
- **Instead:** for the kit command, the same words through python and `tools/kit.py`, which no cmd.exe reads: `kit status -C <dir> 'x&y'` gets `python "<kit>/tools/kit.py" status -C <dir> 'x&y'` (each word re-quoted by `rules.shell_word`; a computed word, a splat or a word holding a line break as `<value>`; a PowerShell `--%` dropped; a bash wildcard kept as written, since through python no cmd.exe reads the names bash fills in). A Git Bash `start kit ...` gets the same line, run without `start`. Every such line runs clear of the rule. For another program the advice is prose: run it directly (python, node, the exe a batch file starts; without `start`), or give it words without cmd.exe's characters and no unquoted wildcard.
- **Allow rules:** an allow rule is matched after the guard has judged the call, so no allow rule passes a command this rule refuses. The land allow lines also deny `^`, `!` and `)` in the `kit land` spelling (docs/allow-rules.md).
- **Limits:** a program the line computes (`& $p`, `$X args`); a batch file `find -exec` runs; a batch file on the PATH named without its extension other than `kit` (`npm`, `npx` and other shims: PATHEXT is not looked up); a line the parser cannot read, which reaches this rule only for the commands it did parse; a batch file run by a tool the line starts (`gate.py`, code python runs; `machine_lock.py run` and `background` are no gap: every .bat or .cmd they start, by its path, by a bare name CreateProcess finds (the current folder included), with a trailing dot or space, or found for a name with no extension, goes through a cmd.exe line they quote themselves, so `run -- x.cmd 'a&b'` passes `a&b` literally, and an argument holding `%`, `"` or a line break is refused, kitlib/lock/run.py `script_command`); a program path that itself holds one of the characters; and a Git Bash `start` of a URL or an exe with an `&` in a word, which reaches an exe intact (OBSERVED above) but is refused all the same, as every `start` word is judged alike (`start 'https://x/?a=1&b=2'`: open it another way, or with no `&`).
- **Tests:** tests/guard/test_kit_cmd_reparse.py (`CmdReparse`: every spelling and character, cmd's cut program words under `/c`, `/k` and `/r`, Git Bash `start` of the kit and of any program, unquoted bash wildcards, other batch files, plain arguments passing, python and `.exe` spellings and PowerShell wildcards left to other rules, each `Instead:` run back through the guard clear of the rule, the words kept; `Chars`: the character set); tests/guard/test_kit_command_forms.py (`kit $t close X-1`).

## Fallback

`kitlib/guard/fallback.py` `check` runs only when the parse is unclean. It catches mistakes, not attackers: an unclean line is refused when it touches a main checkout, a heavy program or a protected path, and a plain line is never denied by it.

- **Modes:** the refusals below follow "Rule modes". A pattern whose rule is off (`wrapped-gate` by default) is not looked for. `unreadable`, `heavy` and `unplaced` warn by default: the warning is kept and the check goes on to the next pattern and the steps after it, so only a kept rule's deny (a re-read one, `git-push-pmdata`) stops the line.

- **The owner's tools by name:** first, in every session but the owner's own, a line whose text names the hub tool (`hub.py`, `tools.hub`, `-m hub`, and the kit command's `kit hub`, `kit.py hub` or `tools.kit hub`) is refused as `hub-owner-verb`, one naming the lock CLI (`machine_lock.py`, `tools.machine_lock`, `-m machine_lock`, `kit machine_lock`) as `owner-tool`, and one naming the owner's delegation list (`owner-delegations`, any case) as `owner-delegations` (`fallback.NAMED`; `-m` as the parsed rule reads it, alone or ending a flag cluster such as `-Im`, its module joined or not and maybe quoted: `-m 'hub'`, `-BIm"hub"`, `fallback.PY_M`), read verbs included: the part the guard cannot read may run an owner verb or an owner-only write. Another file whose name only holds the word (`test_rules_hub.py`, `hub.pyw`, `test_machine_lock.py`) is not the tool. The part of the line holding the name (from the last `;`, `|`, `&` or newline before it to the next) is read again first (`fallback.named_reread`): a hub owner verb there (`rules.hub_owner_run`) gives the parsed rule's own refusal, its question alternative included, a lock owner-only write gives `owner-tool`'s with its `status` line, and a write of the delegation list (`rules.owner_delegations`) gives `owner-delegations`'s with its read line. Otherwise the reason says the line names the tool and `Instead:` is `fallback.plainly`'s script-file run (tests/guard/test_rules_hub.py `test_an_unclean_line_naming_the_hub_tool_is_refused`, tests/guard/test_rules.py `OwnerLockTools`).
- **Patterns:** git_guard's (one repo's `git_guard.ps1`) plus the kit's git rules.
  - When the directory is a main checkout or a place git cannot tell: bulk add, `commit -a`, `checkout`/`switch`, `reset --hard`, `clean`, `stash`, `restore` (unless it only unstages); `commit`, `merge`, `rebase`, `cherry-pick`, `revert`, `am`, `pull`, `apply`, `update-ref`.
  - Anywhere: `branch -D`, `worktree remove`, the ref writes `git-shared-ref` judges (only in a session `rules.shared_ref_held` holds; `fallback.SHARED_REF_PATTERNS`: `update-ref`, a push whose repository is `.`, a `file:` URL, a path or `--repo`, a push whose repository is computed or starts at `~`, a `fetch` or `pull` with a `:` that is not a URL's, `--prune-tags`/`-P`, `--tags`/`-t`, `--update-head-ok`/`-u` or `--stdin` (and the starts of them git reads, `--ta`, `--std`), a forced `tag <name>` (`-f` in a cluster, or `--force` down to `--fo`), a `-c remote.<name>.fetch`, `remote.<name>.pruneTags`, `fetch.pruneTags` or `rebase.updateRefs`, `symbolic-ref` with two names or `-d`, `replace` but a listing, a `notes` write verb, `branch` with `-f`, `-m`, `-M` or `-C`, `tag` with `-f` or `-d`, `checkout -B` or `--ignore-other-worktrees`, `switch -C`, `--force-create` or `--ignore-other-worktrees`, `worktree add -B` or `-f`, `rebase --update-refs`, `remote remove`, `rm`, `rename`, `set-head` or `add --mirror`, `fast-import` and `filter-branch`), push to main (with no `push_block`, only a re-read deny counts: a delete or a forced push of main), push `--no-v...`, `send-pack`, `http-push`, `remote-<helper>`, `git-send-pack`, `git-http-push`, `git-remote-<helper>`, and git push or a git subcommand with a computed word (only where the repository has `kit-pm-data.json` or git cannot place the directory, and not in the owner's own session), the wrapped gate, root searches.
- **Which directory:** the main-checkout patterns are judged in the directory of the top-level command that holds the match, following a literal `cd` before it. The call's directory is not used alone. The git pattern reads a quoted `-C "<path>"`.
- **A pattern match:** the text from the match to the next `;`, `|`, `&` or newline is read again as a command and the parsed rules run on it. For an `owner-tool` or `wrapped-gate` match, and a name in `fallback.NAMED`, the text read again starts where the match's command starts, after the `;`, `|`, `&` or newline before it (`fallback.segment_start`, `fallback.SEGMENT_RULES`), so the program word is read with it: a match on the tool's name inside `kit machine_setup ...` reads the kit command, not its arguments alone. When that read gives no refusal, the text is read again from the match itself, as for every other pattern: a computed program or an open quote at the start of the part (`$PY tools/machine_setup.py --apply`, `echo 'x python tools/machine_setup.py --apply`) leaves the run unreadable from there, and read from the name it is the owner's tool (tests/guard/test_kit_command_forms.py `Unreadable`).
  - A rule that denies gives the deny, its real `Instead:` included, after "The guard could not read this command; write the program name literally. Why: <reasons>."
  - No rule denies: rule `unreadable`. The sentence ends by saying to make every program name and nested shell text literal or to write the commands to a script file with the Write tool, and `Instead:` names that script's run in the temp folder for the line's shell (`fallback.SCRIPT`, `fallback.SCRIPT_RUNS`). The guard never rewrites the refused line. Every `unreadable` refusal, and the fallback's `write-jail` and `git-push-pmdata` ones, take their alternative from `fallback.plainly`, so none repeats the refused line.
- **A heavy program's name:** the same, unless the session holds the lock. A program named by a variable is refused as `heavy`, the `machine_lock.py run` form naming `<the program $X names> <args>`.
- **Anything else:** a subagent gets `unreadable`; with that warned, it is judged on as a jailed session is.
  - A session the write jail holds (a subagent, a mark in `guard_agent_marks`) gets `unplaced` when the line holds the word `git` (`fallback.GIT_WORD_RE`; `.git` and `GIT_DIR` are not it), read or write, from any place: the part the guard cannot read may point git at a checkout it cannot place. The PM data and main-checkout steps below still run.
  - Then every session (the jail's ones reach this step once the steps above warn) gets `unreadable` when a command runs in a main checkout, or a place git cannot tell, and that command runs one of:
    - a program the text does not name;
    - a shell (`bash`, `sh`, `powershell`, `pwsh`, `cmd` and the like), `eval`, `iex`/`Invoke-Expression` or `source`/`.`; this covers `-enc`/`-EncodedCommand` and a pipe into a shell;
    - git with a subcommand or read option the text does not name.
  - The same line from a worktree passes, unless the repository has `kit-pm-data.json`: then any session but the owner's own gets `git-push-pmdata` (deny) for such a line from any place in it, as the hidden program may be `git push --no-verify`.
- **`& (<subexpression>)`:** PowerShell's call operator on a subexpression leaves the line clean ("Known limits"), so the steps above do not judge it. `rules.call_subexpr_pmdata` gives the same answers on a clean line: `git-push-pmdata` in a repository with `kit-pm-data.json`, else `unplaced` (warn by default) for a session the jail holds, whether or not the line holds `git`.

Tests: tests/guard/test_rules.py ROWS, tests/guard/shell_rows.py, tests/guard/review_rows.py and tests/guard/extra_rows.py (428 rows at the time of writing); tests/guard/test_session.py for the rules that read the session mark.

### Known limits

The guard reads the command line, not the shell's state:

- **Aliases and functions** are not seen; the name is read as a program. This holds whether they are defined in an earlier call, in a profile, or earlier on the same line (`alias g=git; g push`). It also holds for git aliases in `~/.gitconfig` (only `-c alias.x=` on the command line is read: `git-alias` warns and the command it runs is judged; a shell alias, `!`, ends the expansion). Aliases in git's config are not looked up (the guard catches honest mistakes, not evasion). `rules.GIT_BUILTINS` is git 2.55's builtin list, the names an inline alias cannot hide.
- **`& (Get-Command x)`** and other PowerShell calls of a computed command object are not resolved to the program they run. The parser reads `& (<anything>)` as a program the text does not name, with the subexpression's commands read as nested ones (`kitlib/guard/shell.py`), but the line stays clean (`commands.call_subexpr`): only `rules.call_subexpr_pmdata` judges that program, as `git-push-pmdata` in a repository with `kit-pm-data.json` and, anywhere else, by denying it to an agent session (`unreadable` for a subagent, `write-jail` for a marked one). For the owner and `plain` no other rule (`heavy` included) sees what it runs. A dot-source of one (`. (Get-Command x)`) is not read so.
- **Direct edits of a repository's config:** `git-remote-rewrite` reads `git remote` and `git config`. An edit of `<git common dir>/config` by a file tool or a shell write (`sed -i`, `Set-Content`) is judged only by the path rules (`main-checkout`, `write-jail`), which do not hold every session, so it can repoint a remote unseen.
- **`coproc`** is not modelled; the command after it is read as a program named `coproc` (`coproc git stash` parses clean, as one command `coproc`).
- **Pre-push config load:** when the clone has no base commit at all, neither the replaced remote main commit nor any default-branch ref, `kitlib/guard/prepush.py` falls back to the defaults: no `push_block`, main read from the git files (docs/kit-json.md "With no file"). The gate-OK check is then skipped; the fast-forward and delete refusals still apply to main, and to `main` itself whatever `<remote>/HEAD` names (read from the code; no test covers it). A base `.kit.json` that sets no `repo.main_branch` names main the same way (`test_a_base_that_names_no_main_branch_reads_origin_head`).
- **Brace groups read as written:** a bash brace group with a quoted, escaped, `$` or space alternative (`{a,"b"}`, `{a,$x}`), and a sequence (`{a..c}`, `{1..9}`), is left as written, so the words bash makes from it are not judged: a path rule sees the one word with its braces (kitlib/guard/shell.py `_brace_group`).
- **`Invoke-Expression`/`iex`, `eval` of a computed string:** the string is not evaluated; a literal argument is parsed, a computed one leaves the parse unclean.
- **`case` statements** are read as unclean (an unmatched `)`), so a subagent's `case` line is refused as `unreadable` and a jailed session's as `unplaced` when it holds `git` (both warn by default); a session the jail does not hold is not refused.
- **Known gaps, not judged (the guard is a speed bump, not a jail):** network writers (cast and rest forms and others); PowerShell `iex` with hidden env values; long hub paths folded; role-lock bypasses, PowerShell 5.1 quote splitting and the inner command of `run`; `cd` spellings; git holes (round 4) and unjudged git ref writes (a `symbolic-ref` then `update-ref`, an alias, a link made earlier on the same line); write-jail writer gaps and the jail refusal's read-only text; computed `hooksPath` keys.
- **What git-shared-ref does not read:** refspecs and remotes git takes from its config files (`remote.<name>.fetch`/`push`, `branch.<x>.remote` of `.`, `push.default`, `url.<base>.insteadOf`/`pushInsteadOf`, `remote.<name>.pushurl`, an include, `GIT_CONFIG_*`), so a named remote whose URL is this repository is judged as a remote; a push into another local repository by its path (a remote too); a symbolic ref made earlier and written through later; `GIT_NOTES_REF` and `core.notesRef`; `rebase.updateRefs`, `pull.rebase` and `branch.<x>.rebase` set in a config file (only a `-c` on the line is read; a pull with `-c rebase.updateRefs` on and no word on the line that it merges is taken to rebase); `rebase <upstream> <branch>`, which checks out and moves that branch; `git replay`, `git filter-repo` and `git history` (git 2.55: its `--update-refs` moves branches); a push to `~<user>/` (refused as unread). A refspec the shell computes whole, or one beside an option the guard does not know, is refused as unread. The coordinator's stray-ref allowance reads the session mark, which a host gives only a main session it can tell apart; on Codex, where a call the host cannot tell apart counts as a subagent's, a coordinator gets no allowance, and its stray-ref delete is refused as a worker's.
- **Rules the fallback does not run:** `busy-wait`, `git-hooks-path`, `owner-identity`, `kill-by-name`, `git-plain-commit`, `interpreter-git` and `cmd-reparse` are not in `fallback.PARSED_RULES`; an unclean line meets only the fallback's own patterns, and `cmd-reparse` judges only the commands the parser read ("Batch files and cmd.exe").
- **cmd-reparse:** its limits are in "Batch files and cmd.exe" (**Limits**).
- **busy-wait:** off by default ("Rule modes"); when on, a loop in a script file, or in the Monitor tool, is not read. A bound the rule does not know (an `-eq` count, a check inside a called script) reads as none, so that loop is denied. Any `-lt`/`-le`/`-gt`/`-ge` reads as a bound, so `while [ $(pgrep -c x) -gt 0 ]; do sleep 1; done` passes though nothing ends it. A loop behind `time` or `nohup` (`time while true; do sleep 1; done`) is read as that program's arguments and passes. The alternative for a loop on the call's own line is the bounded loop alone: what came before it on the line (`F=x;`, `cd x &&`) is not kept.
- **git-hooks-path:** `git clone --template` and `git init --template` with hooks in the template are not seen. Abbreviated long options (`git clone --conf=core.hooksPath=x`) are not seen.
- **owner-identity:** an identity in the environment the session started with, in `GIT_CONFIG_PARAMETERS` or a `GIT_CONFIG_KEY_<n>=user.email` / `GIT_CONFIG_VALUE_<n>` pair, or set inside a script or program the line runs, is not seen. `git commit --author=<name only>` is not caught: git fills in the email from an earlier commit by that author, which can be the owner's; the rule matches the email, not the name.
- **kill-by-name:** `pkill` and `killall` that end processes by user, parent, group or terminal with no name (`pkill -u <user>`) pass.
- **git-stash-shared:** a tagged `push -m <tag>` still adds an entry, and while it is there the gate's stash guard refuses every gate and landing (docs/gate.md "The stash guard"). The fallback has no pattern of its own for it, so a stash the parser cannot pick out of a line (`echo 'x; git stash`), or one after a `cd` it cannot follow, meets only `unreadable` or `unplaced`, which warn by default. A stash run by a script or program the line runs is not seen.
- **git-plain-commit:** not read (`rules.py` above `COMMIT_VERBS`): a git alias from git's config files; a verb the shell computes or a script runs; `commit-tree` and `rebase`; a computed `-C`, `--git-dir` or `--work-tree`, which the unplaced handling judges. A word the shell computes after a hold (`git cherry-pick -n $X`) is read as a commit, though it may be `--commit`, which undoes the hold. A `--continue` of a sequence started with `--no-commit` makes no commit but is refused: git keeps that mode in the sequence's state, which is not read.
- **interpreter-git:** not read (`rules.py` above `INTERPRETER_LAUNCH_RE`): a script file, one in a temp or scratch folder too, and `python -m`; a program or a git name the code builds at run time (`'g' + 'it'`, `importlib`, `getattr`); other interpreters (ruby, perl, deno) and compiled programs; PowerShell's `Start-Process` and .NET's `Process`; a library that writes the repository itself (dulwich, pygit2, `open('.git/refs/...')`); a git command that is not at the start of its string (`'cd x && git commit'`); a git name the code is given from outside its text, as an argument (`python -c "...subprocess.run(sys.argv[1:])" git commit ...`) or through an environment variable (`G=git python -c "...os.environ['G']..."`); python or node run by a launcher (`uv run python -c ...`, `npx node -e ...`), whose code is the launcher's argument and not read; an option that takes the next word as its value and that the guard does not name (python's `--check-hash-based-pycs always`, a node option outside `rules.NODE_VALUE_OPTS`), whose value is read as the script, so the code after it is not read; a line the parser cannot read. It refuses honest code in two ways, both kept: a git read (`rev-parse`, `log`) is refused like a write, and a `'git ...'` string in code whose launch runs another program is read as git.
- **Hub writer code** (`backlogrole.HUB_WRITER_RE`): names only, so code built to evade it passes: `getattr(h, 'recordwrite')`, `importlib` with a built string, `from kitlib.hubsite import *`, the `serve.py` Views wrappers, a `)` in a comment inside the import's parentheses, a backslash before a CRLF.
- **Clearing the mark:** a marked session can start a child agent session with `PM_KIT_ROLE` cleared (`PM_KIT_ROLE= claude ...`, `env -u PM_KIT_ROLE claude ...`, `Remove-Item env:PM_KIT_ROLE`); the child is unmarked and counts as the owner. No rule denies it.
- **Environment changes beside git:** a change the guard does not read leaves git where the line shows it, in every session: `set -a` or `-o allexport`, a sourced script, a nameref, an assignment or `export` whose name the shell computes (`export $n=x`), `Set-Alias git`, `Start-Process -Environment`, and a `GIT_*` name outside `commands.GIT_ENV_NAMES` (`GIT_CONFIG_GLOBAL`, `GIT_EXEC_PATH`). So `. ./env.sh; git reset --hard` from a worktree passes, though the script may point `GIT_DIR` at a main checkout (docs/guard-v2.md A4, B4, B10 to B14). A literal assignment of a `GIT_ENV_NAMES` name (`GIT_DIR=x`, `export GIT_DIR=x`, `$env:GIT_DIR = 'x'`) still leaves that git's place unknown, so its write is refused as at an unknown place. Any git on a line the guard cannot read at all (`eval "$c"; git status`) is refused as `unplaced`, which warns by default ("Fallback"). The owner's unmarked session and the marks the jail does not hold (`plain`) are not jailed (`rules.git_jail` returns before `git_jail_unknown`), so their line passes.
- **Startup files:** a nested shell runs files the line does not show before its text: `bash --rcfile <f>` or `--init-file <f>`, and a login or interactive shell under a `HOME=<dir>` the line sets (`HOME=/x bash -l -c '...'`) reads that folder's profile. They are not read; git in the nested text is placed as written.
- **PATH and the exec path:** a `PATH` the line sets, or `git --exec-path=<dir>`, may make `git` or a git subcommand another program. The guard reads the word `git` as git and does not judge `PATH`.
- **Environment the line does not show:** a program the line runs that runs git itself (`python tools/commit.py`) gets the line's environment, but is not judged as git (git that python or node code on the line runs is `interpreter-git`'s, "Rules"). A PowerShell `function git`, `git -c include.path=`, a .NET `ProcessStartInfo` and a variable persisted by an earlier call (`setx`, User scope) are not seen.
- **PowerShell provider items:** only a literal item of a provider-aware item or content cmdlet (`PS_PROVIDER_CMDLETS`), on a line whose every command is a plain call of such a cmdlet, a listed read-only one or git (`ps_line_plain`), skips the path rules; any other env: item (computed, given to a native program or to Out-File, Compress-Archive, Invoke-WebRequest -OutFile, or on a line with an assignment, a member or static call, `&` or a dot-source) is judged as a file path. A literal one (`PS_PROVIDER_ITEM_RE`) is then a drive or provider path the guard cannot place (next item): refused in a main checkout, passed from a worktree (kitlib/guard/rules.py `shell_writes`; docs/guard-v2.md B16). When a provider-aware cmdlet's literal item is refused only because of its line, the refusal says so in one sentence and its Instead is the whole line run from the worktree (`rules.whole_line`: a statement before the call that sets what it reads stays with it; a `cd`, `Set-Location` or `Push-Location` into the top of a main checkout at the start of the line and a comment after its last command are left out, and a line with any other one, or a `Pop-Location`, gives the call alone, since it would move off the worktree), not a file to write (`rules.PROVIDER_ITEM_WHY`, `rules.ps_provider_word`; tests/guard/test_provider_paths.py).
- **PowerShell provider and drive paths in a write:** a PowerShell `FileSystem::<abs>` (bare or `Microsoft.PowerShell.Core\FileSystem::`) is read as `<abs>`, after a leading separator too (`\FileSystem::<abs>`, which PowerShell takes; `shell.resolve_path` with the shell, also for `cd` and the root search). A relative `FileSystem::<rel>`, bare or after a leading `\`, is read from the location, as a relative .NET path is (`shell.ps_filesystem_relative`; PowerShell reads it from the process's directory: "The .NET process directory" below). A relative path whose first folder is `.` or `..` is no provider path: `.\x.txt::$DATA` is a stream of `x.txt` in the location, placed as that file (`shell._ps_provider`); `..\x.txt::$DATA` PowerShell reads as a provider named `..\x.txt` and refuses, writing nothing, so placing it as the stream of `x.txt` in the folder above is the stricter reading; while `x.txt::$DATA` and `sub\x.txt::$DATA`, where PowerShell reads `x.txt` as a provider's name, cannot be placed. Any other `Provider::` path, or a drive whose name is anything but one ASCII letter (`Main:\x` after `New-PSDrive`, `1:\x`, `_:\x`, a non-ASCII letter), cannot be placed (`shell.ps_unplaceable`), unless the provider-items skip above already let it pass. It is judged as any target the guard cannot place: refused in a main checkout, passed from a worktree. A `cd`, `Set-Location` or `Push-Location` into such a place leaves the directory unknown, as bash's `cd $x` does, so a relative write after it is refused as running in an unknown directory; so does one to a relative `FileSystem::<rel>` (`FileSystem::.` included), which PowerShell reads from the process's directory, not the location (`shell.cd_target`), so a git write after it is judged as one in an unknown directory. The PowerShell-drive jail that refused these from a worktree and in a session that may edit a main checkout is cut: an unusual spelling, not an honest mistake (docs/guard-v2.md B16). Bash and cmd words and one-letter drives are read as before (kitlib/guard/shell.py, kitlib/guard/rules.py; tests/guard/test_ps_drive_paths.py).
- **The .NET process directory:** .NET reads a relative or driveless path against the process's directory (`[Environment]::CurrentDirectory`), which `Set-Location` does not move. The guard cannot see that directory. It refuses an agent session's relative .NET path ("Write jail"), but judges a driveless one, an unread call and the owner's own session's relative path where the PowerShell location puts them (docs/guard-v2.md B17), so the owner's session started in the main checkout that runs `Set-Location <worktree>; [IO.File]::WriteAllText('x', ...)` is allowed and writes the main checkout.
- **A relative `FileSystem::` path and the process directory:** PowerShell reads a relative `FileSystem::<rel>` (and `\FileSystem::<rel>`) against the process's directory, as .NET does, not the location. The guard reads it from the location (`shell.ps_filesystem_relative`), so a session started in the main checkout that runs `cd <worktree>; Set-Content FileSystem::x.txt y` is allowed and writes the main checkout: a provider-path form, cut with the rest (docs/guard-v2.md B16), the same risk as the .NET one above. A `cd` to such a path is not read from the location: it leaves the directory unknown (the item above).
- **Start-Process -FilePath:** `rules.kit_script` reads the program word of a Start-Process call with a `-WorkingDirectory` from that folder, as it reads a script in `-ArgumentList`; PowerShell resolves a relative `-FilePath` from its location instead. It matters only when the program word is itself a kit tool and the repository lists it as heavy.
- **What the guard stops chasing:** the guard catches honest mistakes, not evasion, so each rule judges the form a mistake takes and names no workaround (docs/guard-v2.md "Checks this design weakens or removes", by row). Besides the items above: an owner verb reached from python code that imports the hub tool rather than a parsed run of it (A1, "Hub secrets"); a token file named in a shell word with no literal path into the token folder (A2, "Hub secrets"); the reserve UI, the lock window or machine setup started from python code, standard input or a variable (A3, "Owner lock tools" and "Owner machine setup", their Limits); a lock verb handed on by a variable, a copy or standard input in a role session (B5, "Role policy"); an alias in git's config (B1, "Aliases and functions" above); a ref reached through another symbolic ref, a link in the git directory, or a reftable (B6, B18, B19, the `git-shared-ref` row); a `[IO.StreamWriter]` cast (B7, "Shell writes"); a drive path with single backslashes in a python heredoc (B8, no rule); and, from a worktree, a PowerShell write target that is computed, a path on another provider or on a drive name longer than one letter, or a relative `FileSystem::` path, and the owner's own session's relative .NET path (B15 to B17, the items above).
- **Heavy `when_args`:** an argument counts at any position, so `dotnet new console -n build` is heavy.
- **write-jail reads the line, not the program:** a script or program the agent runs (a `.py` it wrote, `python -c`, a build tool) can write anywhere; the jail judges only the targets the command line names. What such a write puts in a repository reaches main only through a commit and a push, where `tools/commit.py` (docs/commit.md) and the pre-push owner-only paths ("Owner-only commits") still check it; a write outside every repository is not checked at all. A target that is not literal goes unjudged under bash and cmd in a linked worktree or another place git can tell ("Rules"), as does a path a PowerShell cmdlet takes from the pipeline ("Shell writes"); a computed git subcommand is refused (`commands.git_dyn_word`).
- **In-place editors the guard does not read:** an `awk -f <progfile>` whose file holds `@include "inplace"` (the guard reads no program file); `sort -o`, uniq's output operand, split and csplit, gzip, bzip2 and xz, `iconv -o` and `emacs --batch`; vim's `-i <viminfo>`, written on exit, and its `-V<n><file>` verbose log; a write named inside a `-c` command or an ed command (`w <other path>`); the editor names view, rvim, vimdiff, gvim and red; and awk, gawk, ruby -i, the editors, dos2unix and sponge run from PowerShell, as sed and perl there (`rules.write_targets`).
- **BSD `xargs -S <size>`** is not read as taking a value: the size is read as the program, so the command after it (`sh -c '...'`) is not read.
- **A trap handler or `find -execdir` at an unknown place:** a relative write in it is judged as at an unknown place, so a subagent is denied `cd sub && trap 'rm -f x' EXIT` and `find . -execdir rm {} +`.
- **What the ledger rule does not read:** a recursive wildcard that does not pass through the ledger's folders (`del /s *.md`), since a wildcard is matched only at its own depth or above (`rules.ledger_glob`); a second hard-link name of the ledger, a rulebook or the digest; and shell wildcard syntax that `fnmatch` does not share (`[^x]`, `[[:alpha:]]`, cmd's trailing `?` and trailing dot), which is matched as `fnmatch` reads it. Git that rewrites the work tree but is none of the forms the Rules table names is not this rule's; `rebase`, `cherry-pick`, `revert` and `am` are among them. Other rules refuse them only in a main checkout or a place git cannot tell (`rules.git_main_rules`: `git-checkout`, `git-main-history`), and in a linked worktree or outside git none of them is refused for the ledger's sake.
- **Both machine config folders:** with a `config.json` in both the new and the retired folder, the new one decides alone, so only its `ledger_path` is protected; a ledger only the old file names is not (docs/kit-json.md "Moving the machine config folder"; tests/guard/test_config_move.py).
- **write-jail with a git top at the home folder or above:** such a checkout holds the machine config folders, so the session gets no checkout root ("No root on a machine config folder") and the alternative a refusal names writes to temp instead (`jail.destination`).
- **machine-config and git in another checkout:** git's pathspec into `.pm-kit/` is judged only in the PM repository's work tree (`delegfile.git_config`); in another checkout, `git checkout -- .pm-kit`, `git rm -r .pm-kit` and the like are not this rule's. Such a change reaches a remote only through a commit and a push, where the pre-push machine config secrets stage refuses the secrets ("Pre-push").
- **machine-config and a program's own writes:** a script, build tool or `python -c` that writes into a machine config folder is not judged; only a file tool and the shell write targets the line names are.
- **machine-config and code on the line:** python or node code given on the line (`-c`, `-e`, standard input) that names `.pm-kit` is not read as a write (`rules.NAME_RE` is unchanged).
- **machine-config and a wildcard above the folder:** a wildcard whose literal folder is above `.pm-kit` is refused when its parts can match, on disk, an existing path that is or lies in the folder (`delegfile.glob_config_below`: `rm -r .pm*`, `Remove-Item <pointer>\*`, and PowerShell's top-level `Remove-Item *` in a checkout that has a `.pm-kit`, whose wildcards match a leading dot; in bash a part that starts with `*`, `?` or `[` skips dot-names, as bash without dotglob does, so `rm -rf *` is not this rule's). A path that does not exist is not judged (`rm -rf */__pycache__`), nor is one that matches no existing `.pm-kit`. A wildcard whose match reads more than `delegfile.WALK_LIMIT` folder entries is refused (fail closed), with its own text (`delegfile.walk_limit_refusal`): the word was too wide to check, so narrow it or name the files; it does not give the machine config folder's wording or say to ask the owner. `owner-delegations` still refuses one that can match the delegation list, and is checked first.
- **machine-config and the folder's parent:** a delete or move of a folder that only holds a `.pm-kit` (the checkout itself, the PM repository) is not this rule's; the write jail and `main-checkout` judge it as they judge any folder.
- **machine-config and pipelines:** a pipeline or `xargs` writer (`ls | xargs rm`, `Get-ChildItem | Remove-Item`) is judged for the delegation list only ("Owner delegation list"), not for a machine config folder.
- **machine-config by name:** a `.pm-kit` at the top of a checkout other than the pointer's is held for literal targets only; a wildcard there is held when its literal folder is that `.pm-kit`, or when its parts after the literal folder, folder parts included, match an existing path in that `.pm-kit` on disk (`delegfile.glob_config`, `glob_config_below`), and git there is not judged (above).
- **What the Dev Drive bound does not see:** writes the line does not name, so they land off the drive unjudged: tool caches under the user profile (pip, npm, NuGet, `.godot`, `%APPDATA%`; the owner moves them, docs/machine-setup.md), `git config --global` (`~/.gitconfig`), and writes made inside python or node code or any program the line runs ("write-jail reads the line, not the program").
- **write-jail temp is shared:** every session's temp root is the same folder, so one agent session may write another's scratch folder.
- **write-jail copy into an add-only folder:** only cp, mv, ln, install, `Copy-Item`, `Move-Item` and cmd copy and move are judged by the source's name. `robocopy`, `xcopy` and `rsync` into the existing folder, a source that is not literal, holds a wildcard or is drive-qualified (`D:name`), `-T`, and any option off the list in "Write jail" are judged as the folder itself, so they are denied.
- **write-jail and options that are not literal:** cp, mv, ln and install read a word that is not literal (`"$F"`) as an operand, though the shell may expand it to an option such as `-t<dir>`.
- **write-jail and a lander in the main checkout:** a lander whose `cwd` is the main checkout gets the whole checkout as its root, so the jail adds nothing there; the `main-checkout` rule and `roles.lander` decide what it may write.
- **The lander's agent type:** the exception for landing verbs matches the payload's `agent_type` `pm-kit:lander`, the kit's own lander, which the coordinator dispatches by that name (skill land-branch), and `lander`, a repo's own `.claude/agents/lander.md` (docs/ROSTER.md); nothing else does ("Agent names"), so a lander another plugin registers is held like any subagent. The `<plugin>:<name>` form is INFERRED from Claude Code's plugin naming, not observed; check one real payload after the plugin install.
- **write-jail and a session's working directory:** the roots follow the payload's `cwd`. An agent started in another repository's checkout (a subagent of a session that runs there) gets that checkout, not the worktree it was told to work in, and is denied there.
- **Backlog roles and code:** `backlog-raw-write` reads code given on the line (`-c`, standard input, `-m`); a script file that imports `kitlib.backlog` is not read. A main session's python importing it is not judged either: only the tool's own check holds a main session.
- **Backlog roles by name:** any script named `backlog.py` a subagent runs is judged as the kit's tool, wherever it lives.
- **Backlog roles and a computed script:** a script path the line computes (`python $p close X-1`, `python $env:K/tools/backlog.py close X-1`) is not judged by `backlog-role`: `rules.tool_run` gives no run for a computed script word. The tool's own check then holds it, by the session mark, which a subagent shares with its main session.
- **Backlog roles on Codex:** Codex's hooks send no subagent identity, so its subagents carry their session's mark and meet only the tool's own check ("Backlog roles"). The kit-tool broker (`hosts/codex/adapter/runtime.py`) holds a root binding the same way, as its marked session; only a child binding, whose role the broker checked, meets `backlog-role`.
- **Gate allow on Codex:** Codex's hooks send no subagent identity (`kitlib.host.hookmain.UNIDENTIFIED`), so a Codex subagent carries its session's mark, and one under a coordinator's or the PM's session is judged as that session: `gate-allow` lets its `gate.py allow` run (`gaterole.session_mark`; tests/guard/test_gaterole.py `test_an_unidentified_call_is_judged_by_its_mark`). The kit-tool broker's child binding names its thread and is refused as a subagent.
- **Linux paths:** a symlink swapped between the guard's check and the write is not seen (a race no command-line guard closes). The per-folder casefold of ext4 and f2fs (`chattr +F`) is not read: such a folder is judged case-sensitive. An fstype the guard does not list, nfs, nfs4 and zfs among them (they fold or not by the server or dataset, which the guard does not read), or a mount table it cannot read, folds case only for what the guard refuses, never to widen what it allows ("Write jail" "Paths"; `rules._in_temp` and `rules._under_temp`, which lift checks, compare as the allow side does). A mount made after the hook process read the table is not seen (the table is read once per process). A ledger glob (`rules.ledger_glob`) folds each part of its pattern by the mount its literal path names, so a wildcard part that matches into a mount of another kind below it (`/media/usb/**` reaching an ext4 mount) compares by the pattern's mount, not the matched path's. A `CDPATH`, `SHELLOPTS`, `BASHOPTS` or `cdable_vars` the shell inherits from its environment or a host's shell snapshot is not on the line, so the guard cannot see it and reads bash's cd as without it.
- **A failed cd is still tracked:** the folder a cd names is kept whether the cd succeeds or not, on Windows and Linux alike, so `cd missing; echo x > ../f` is judged as written from `missing`, though the shell writes from the folder before it.
- **A cd in eval or source:** a cd inside an `eval` text or a script run by `source` (or `.`) moves the outer shell, but the guard does not carry it to the commands after it.
- **Wildcard targets:** a write target with a wildcard (`d*/f`) is judged as written: links and junctions are not resolved through the wildcard part (on Windows as on Linux).
- **Backlog roles and a reason:** the map's `NEEDS_WHY` (a HIGH write must say why) is not built; the owner's ruling a write carries is the only reason the tool records.

## Lock MCP

The lock MCP server ships read-only (docs/lock-mcp.md "No write tools"); its owner-only write names are retired (`kitlib.lockmcp.OWNER_ONLY`) and stay refused here, for a server started from an older release.

- **Which tools:** a tool named `<prefix><owner-only tool>` is caught, so is any `mcp__*__<owner-only tool>`, and so is any full name listed in the user config `guard_mcp_tools`.
- **Prefix:** the default is the asking host's: its `hosts.json` profile `mcp_tool_format` with the kit plugin (`kitlib.lockmcp.PLUGIN_NAME`) and the lock server's name filled in (`rules.host_mcp_prefix`; the same text as `kitlib.lockmcp.tool_prefix()`), and "any other server name" is the tail after the format's server separator (`__`). The Claude one is INFERRED from Claude Code's plugin MCP naming; no real PreToolUse payload has been captured, as the server is not installed.   - `subagent`, or any mark (pm, coordinator): deny.

## Session mark

`kitlib/sessionmark.py`. The launcher that starts an agent session sets `PM_KIT_ROLE` to its kind (`tools/launch.py`, docs/launcher.md "The window": `pm`, `coordinator`, `deep-worker`, `consultant`, `plain`, or another agent's name); a subagent is told apart by the hook payload's `agent_id` (`Action.agent`). `kitlib/guard/context.py` `default_session_role` gives `subagent`, else the mark, else `owner`. The mark is the hook's own environment's, unless the host's adapter hands it over as `Action.role` (Claude's does not: the hook inherits the session's environment).

- **Unmarked is the owner:** a main session nothing marks is the owner's own, exempt from `owner-tool`, `lock-mcp`, the hub rules (`hub-mcp`, `hub-browser`, `hub-owner-verb`, `hub-secrets`), `owner-identity`, `owner-delegations`, `git-push-pmdata`, `kill-by-name`, `git-stash-shared`, `git-plain-commit`, `interpreter-git`, `lock-state`, `kit-json` and `write-jail`. Until the kit launcher is live, sessions the old launcher starts are unmarked and count as the owner ("Go-live", step 4).
- **Reserved values:** a mark of `owner` or `subagent` reads as `marked-<value>`, never as that standing.
- **The plugin prefix:** a mark is read without the kit plugin's agent prefix, before the reserved check ("Agent names"): `<plugin>:coordinator` is held as `coordinator`, `<plugin>:owner` reads as `marked-owner`. The launcher writes bare marks (docs/launcher.md "The window").
- **Agent sessions:** `kill-by-name`, `git-stash-shared`, `git-plain-commit`, `interpreter-git`, `lock-state`, `kit-json` and `write-jail` hold subagents and the marks in the user config `guard_agent_marks` (default `kitlib/guard/rules.py` `AGENT_MARKS`: `coordinator`, `deep-worker`, `consultant` and `pm`; compared without case); other marks (`plain`, another agent's name) are not held to them. Setting `guard_agent_marks` replaces the default list rather than adding to it, so a value must also list every default mark it keeps holding (`ctx.user().get('guard_agent_marks') or AGENT_MARKS`). `owner-tool`, `lock-mcp`, the hub rules, `owner-identity` and `owner-delegations` hold every marked session.
- **The PM's mark:** only the session the kit launcher resumes carries `pm` (docs/launcher.md "The window"); a PM session opened by hand or in the desktop app is unmarked and counts as the owner's own. The jailed PM keeps the folders it writes outside its checkout through `guard_mark_roots` ("Write jail"), which the owner sets.
- **Where it is read:** only where the session cannot change it once started: the guard hook, started with the session's environment (INFERRED; not yet observed live). The lock CLI and the lock MCP server do not read it: the server ships read-only (docs/lock-mcp.md "No write tools"), and an agent sets the environment of every command it runs.
- **Limits:** a session the launcher did not start is unmarked and counts as the owner. The lock's holds and tree roles do not read the mark.
- **Tests:** tests/guard/test_session.py.

## Owner lock tools

Owner-only lock tools are run by the owner, not agents: `reserve_ui.pyw` and the lock CLI's owner writes. The lock's own owner check (`kitlib/lock/api.py` `who`, `default_owner_check`: no Claude ancestor) can be forged by a detached process, so the guard stops agents from starting them at all. That check stays as a second layer.

- **The rule:** `owner-tool` (`kitlib/guard/rules.py` `owner_tool`, `owner_tool_run`) reads the file a command runs as `rules.tool_run` reads it: the program's base name (any case, any path, without `.exe`); the script of `python`, `pythonw`, `py` or `pyw` (their own options skipped), or its `-m` module as `<last dotted part>.py`; a `.ps1` given to a PowerShell shell; the file an opener runs (`Invoke-Item`/`ii`, `explorer`, Git Bash's or cmd's `start` with its `/b` and other options skipped, a `Start-Process -FilePath`, and a `Start-Process -ArgumentList` string, split at its spaces). Wrappers the parser unwraps (`nohup`, `cmd /c`, a nested `bash -c`) are read as the command they run.
- **The kit command:** a run of the kit command reads as the tool it names (`rules.kit_run`, `commands.kit_tool`), so every rule that keys on a kit tool's name judges `kit X` exactly as `python <kit>/tools/X.py`: the program `kit` (`kit.cmd`, `kit.exe`, `kit.bat`, `kit.com`, any case, any path), `python <kit>/tools/kit.py X` and `python -m tools.kit X` (or `-m runpy tools.kit X`, `rules.script_run`) all read as `X.py` with the words after `X`. The first token after the kit names the tool, lower-cased: the words are split at blanks and double quotes and empty tokens skipped, and the rest of the word that holds the name is split the same way into words of its own. Windows PowerShell 5.1 passes a word holding a double quote on unescaped and drops an empty word, so `kit 'hub" answer EX-1'`, `kit '""hub' answer EX-1` and `kit '' hub answer EX-1` all read as `hub.py answer EX-1`: every token the program may see is read as the tool or an argument (it fails closed). The fallback's names (`fallback.KIT_WORD`) take the same quotes and empty words before the tool's name, and each suffix `commands.base_name` takes off a program. A computed tool word (`kit $t ...`) gives no run, as a computed script does ("Known limits"), and the bare kit command with it is refused as `cmd-reparse` ("Batch files and cmd.exe"), while `python <kit>/tools/kit.py $t ...` gives no run and no refusal; a kit run naming no tool (`kit`, `kit --help`) is the kit command itself. `commands.tool_at` gives the same reading with the word's place, for `commands.wrapper`, `rules.lock_run_help`, `rules.gate_runs_nothing` and `rules.bare_wrapper`. Tests: tests/guard/test_kit_command_forms.py (every rule in each spelling), tests/guard/test_kit_tool_forms.py (parity with the script forms).
- **reserve_ui:** denied when that file is `reserve_ui` (with or without `.pyw`): `pythonw reserve_ui.pyw`, `start pythonw reserve_ui.pyw`, `& "<lock>/reserve_ui"`, `ii reserve_ui.pyw`, `python -m reserve_ui`. Reading it and git on it stay open: `cat`, `type`, `Get-Content`, `rg`, `grep`, `git add`, `diff`, `show`, `log`, `commit`, and so does any other `-m` module (`python -m py_compile reserve_ui.pyw`, `python -m pytest -k reserve_ui`), so work on the UI's own code is not blocked.
- **Lock CLI owner writes:** a run of `machine_lock.py`, read as above, whose words before `--` hold (`rules.lock_owner_write`):
  - the installed lock CLI: `reserve`, `release`, `stop --force`, `unbook --force`;
  - the kit CLI (`tools/machine_lock.py`): `hold whole|half|slots`, `division --set|--default`, `game on|off|set`, `top` (move a waiting run to the front), `stop --force`.
- **Still open:** `status`, `run`, `background`, `book`, `unbook` and `stop` without `--force`, `hold agent|list|end|edit`, bare `division` and `game`/`game show`. Ending one's own hold or run is an agent's right (`kitlib.lock.api.authorize`); the text cannot tell whose hold an id names, so the lock decides.
- **Who:** every session but the owner's own (unmarked; see "Session mark"), with no ask. A process the owner's session starts still has an agent host above it, so the lock CLI's own check refuses it there.
- **Limits:** not read, as the guard reads what a line runs, not what it builds (the guard catches honest mistakes, not evasion): `python -c` code, python's standard input (a pipe, `<`, a heredoc or here-string), a program or script named by a variable, a glob (`pythonw reserve_u*.pyw`), a program the guard does not know as a launcher (a `.py` script that runs the UI), copy-then-run under another name, `[Diagnostics.Process]::Start(...)` and other .NET process calls (git that such code runs is `interpreter-git`'s, "Rules").
- **Unreadable lines:** `kitlib/guard/fallback.py` runs this rule first when it re-reads a text-pattern match (`PARSED_RULES`). An unreadable line whose text names the lock CLI (`machine_lock.py`, `tools.machine_lock`, `-m machine_lock`, `kit machine_lock`) is refused as `owner-tool` whatever its verb, in every session but the owner's own ("Fallback", "The owner's tools by name"); reserve_ui has no name pattern, so an unreadable line reaches the rule for it only when another rule's text pattern (machine setup, wrapped gate, git, root search, heavy) matches.
- **Tests:** tests/guard/test_rules.py `OwnerLockTools`.

## Owner machine setup

Machine setup's `--apply` writes the machine config, and its `owner_email` decides which commits count as the owner's (owner-only paths, `owner-identity`; docs/machine-setup.md "Owner email"). An agent that ran it could store its own address as the owner's, so the `owner-tool` rule (`kitlib/guard/rules.py` `owner_tool`, `owner_tool_run`) denies it to every session but the owner's own:

- a run, as `rules.tool_run` reads it ("Owner lock tools"), of `machine_setup.py`, `machine-setup.ps1`, `new-repo.ps1` or the Linux `installer/machine-setup.sh` (`SETUP_SCRIPTS`; the program, python's script, `python -m <...>machine_setup`, `powershell -File`, `sh` or `bash` running the script, directly or after a `sudo` or `env` prefix, `&`, a `Start-Process -ArgumentList` string), followed by `--apply` or a prefix argparse takes for it (`--ap`, `--app`, `--appl`), or for a `.ps1` a prefix of `-Apply` (`-a`, `-App`, `-Apply:$true`), any case; words after `--` are not read.

The dry run (no `--apply`), `--help`, reads and git on its files stay open. The `--repo` mode is held the same way: it writes `.kit.json` "owner".email. An agent session's file edit or shell write of the home machine config folders is the write jail's: they are never a write root ("Write jail"). An unreadable line that names an entry point with a `-a...` word is matched by the fallback's own pattern and re-read through this rule; the owner's own session skips it.

**The machine config in a checkout** (rule `machine-config`, `kitlib/guard/rules.py` `machine_config`, `machine_config_folder`). The machine config is moving into the PM repository, as `<pointer>/.pm-kit` (docs/machine-setup.md), and a branch of any repository could carry a `.pm-kit` folder of its own. Every session but the owner's own (subagents and every mark, `plain` included, as `owner-tool`; "Session mark") is denied:

- a file tool edit or a literal shell write target (`rules.edit_target`) in the PM repository's folder, `<pointer>/.pm-kit` (`jail.pointer_config_dir`, compared as `jail.real` resolves both), whether or not git places it; and one in a folder named `.pm-kit` (case ignored) right at the top of a main checkout or a linked worktree (`Ctx.place`), whatever the pointer names. A `.pm-kit` deeper in a checkout, a folder that only holds one (a delete or move of the checkout) and one outside git are not this rule's; the home folders are the write jail's.
- a wildcard write target whose literal folder is, or lies in, such a folder (`delegfile.glob_config`: `rm <pointer>/.pm-kit/*.json`, `Remove-Item .pm-kit\*` at a checkout's top), or whose parts after its literal folder match on disk an existing path that is or lies in one (`delegfile.glob_config_below`: each part, folder parts and the last, matched as FindFirstFile matches, long or 8.3 short name, case folded; for bash a leading `*`, `?` or `[` skips dot-names and `[^` negates: `rm .pm-k*t/config.json`, `Remove-Item .pm-k?t\local.json`, `Remove-Item */config.json`, `rm -rf .pm-k*`; past `delegfile.WALK_LIMIT` folder entries read, refused, fail closed), judged after the delegation list's own wildcard check (tests/guard/test_delegfile.py `FolderWildcards`, `WalkLimitText`).
- git whose work tree is the PM repository (as "Owner delegation list" reads it): `rm`, `mv` and `checkout-index` of a pathspec that lands in `<pointer>/.pm-kit`, `restore` of one unless it only unstages (`--staged` without `--worktree`, as `git-restore` reads it), `checkout` of one after `--`, and `clean` of one without `-n` (`delegfile.git_config`, `delegfile.lands_in`: a glob by its literal folder; other magic and a computed word fail closed; an exclusion never lands). The delegation list's own git check runs first.

The reason names the folder and why (`rules.MACHINE_CONFIG_WHY`), and the `Instead:` lists it: `Get-ChildItem -Force "<folder>"`. The one exception is a wildcard whose walk passed `delegfile.WALK_LIMIT`: its reason (`delegfile.walk_limit_refusal`) says the word was too wide to check and to narrow it or name the files, with no `rules.MACHINE_CONFIG_WHY` and no ask-the-owner, and its `Instead:` is `Get-ChildItem -Force -Name "<folder>"`. Reads stay open. Precedence: a target the delegation list's rule can reach (the list itself, a wildcard that can match it) is refused as `owner-delegations`, and one in `<pointer>/.pm-kit/hub` as `hub-secrets` (its second token folder, "Hub secrets"); `machine-config` takes the rest of the folder. Pre-push refuses a push that sends a checkout's `.pm-kit/hub/` or `.pm-kit/local.json` ("Pre-push", "Machine config secrets").

- **Limits:** not caught (the guard catches honest mistakes, not evasion): `python -c` code or python's standard input importing `kitlib.machinesetup`, an entry point or its words named by a variable, a script of the agent's own that writes the machine config file (`python my.py`), a copy of the tool under another name, `[Diagnostics.Process]::Start(...)`. The write jail and `machine-config` stop a file tool or a shell write target into a machine config folder, not a program's own writes. For `machine-config` also ("Known limits"): python or node code on the line that names `.pm-kit`; a wildcard whose literal folder is above `.pm-kit`; a pipeline or `xargs` writer; git in another checkout than the pointer's; a git pathspec in the forms not listed above.
- **Tests:** tests/guard/test_rules.py `OwnerSetup`; tests/guard/test_machine_config.py (`PointerFolder`, `ByName`, `Wildcards`, `PointerGit`, `PrePushSecrets`); tests/guard/test_config_move.py `ConfigMove`.

## Owner delegation list

The owner's delegation list says which owner operations an agent may run for the owner (docs/delegations.md), so an agent that could change it could grant itself any of them. The `owner-delegations` rule (`kitlib/guard/delegfile.py`, wired in `kitlib/guard/rules.py` `owner_delegations` and `delegations_edit`) denies a write, move or delete of it to every session but the owner's own: every subagent and every marked main session, `plain` included ("Session mark"). Two copies are held: the home one the loader reads (`kitlib.delegations.delegations_file`, `~/.pm-kit/owner-delegations.json`), and the PM repository's (`<pointer>/.pm-kit/owner-delegations.json`, the PM-repo pointer's value as stored, `kitlib.config.pointer.read_raw`; a value the pointer check refuses is still held). With no pointer only the home copy is.

- a file tool edit of either copy, or a shell write target the shell rules place (`rules.edit_target`) that is either copy or a folder holding one (a delete or move of `~/.pm-kit` or the PM repository). Paths are read with the home folder's spellings and after a cd home, as `hub-secrets` reads them, and compared as the filesystem reaches them (case, links and junctions).
- a wildcard write target that can match either copy or a folder above it (`delegfile.glob_reaches`: `rm ~/.pm-kit/*.json`, `Remove-Item .pm-kit\*` in the PM repository, `rm -rf ~/*`). Each part after the literal folder is matched against the copy's path below that folder, case folded and with a leading dot matched like any other character (bash would skip it: fail closed); `**` or `..` after the wildcard matches any copy below the folder. The DOS wildcards `<`, `>` and `"` count as `*` (`rm -r .pm-ki\<`; the path is also read as the literal name, `delegfile.word_reaches`), and a part also matches the copy's 8.3 short name (`rm .pm-kit/OWNER-~?.JSO`, `rules.glob_part`), as FindFirstFile matches.
- the folder a program that writes there runs in (a stand-in target, `rules.here`: `tar -x`, `unzip`, `curl -O`, `ln`, `Copy-Item` with no `-Destination`), when it is a copy's folder or a folder above it (home, the PM repository): `git archive HEAD~3 | tar -x` in the PM repository, `cd ~ && tar -xf backup.tar`. A stand-in whose writes the guard does not read (`rules.unread_write`: python, node, ruby or perl code, a .NET call) counts only as the file: python run in the PM repository is not a write of the list.
- a writer that takes its paths from the pipeline (a cmdlet's `-Path` from `|`) or from `xargs`, judged by the commands before the `|` (`delegfile.upstream`): a path-like word of theirs (a separator, a wildcard, a leading `.`, `~` or `$`) that reaches a copy, read as git reads a pathspec when the command is git; a command that names `owner-delegations` or `.pm-kit` (fail closed); and, with no path-like literal word, the folder the first of them runs in when a copy is in it or below it (`git ls-files | xargs rm` and `Get-ChildItem | Remove-Item` in the PM repository).
- python or node code on the line (`rules.inline_code`: `-c`, `-e`, a heredoc or here-string) that names the list (`owner-delegations`, `delegations_file`) and writes, moves or deletes a file (`delegfile.WRITE_RE`); code that names the list and writes another file is refused too.
- git whose work tree is the PM repository (`-C`, a cd, or a folder below it): `rm`, `mv`, `restore` (unless it only unstages) and `checkout-index` of a pathspec that can reach the file (the file, a folder above it, a glob whose literal folder is above it, `:/` and `:(top)` from the top, other magic and a computed word fail closed, an exclusion never), `checkout-index -a`, `checkout` with no `--` or a reaching path after it, `switch`, `reset --hard`/`--merge`/`--keep`, `read-tree -u`, `clean` (not `-n`) of a reaching path or of no path, `stash` (not `list` or `show`), `sparse-checkout` (not `list` or `check-rules`) and `bisect` (not `log`, `visualize`, `view`, `terms` or `help`); and `worktree remove` or `move` of the PM repository's work tree from any place.

Reads stay open: a Read or Grep, `cat`, `Get-Content`, `git show`, python that only reads, a copy of the list to somewhere else. An unreadable line that names the list is refused even for a read ("Fallback"); the owner's own session skips every check here.

- **Limits:** not caught (the guard catches honest mistakes, not evasion): `merge`, `pull`, `rebase`, `cherry-pick`, `revert`, `am` and `apply` in the PM repository are left to the owner-only commit check ("Owner-only commits"); a script file python or node runs (`python my.py`) is not read; when the guard cannot tell which repository git acts on (`-C` with a computed path, `--git-dir` or `--work-tree`, `GIT_DIR` or the like, an alias it cannot expand, a computed subcommand) the git check is skipped; a path-like word before a `|` that reaches no copy lets the piped writer through, whatever the command makes of it; the inline check reads names, not data flow (a path built from parts that never spell the list passes).
- **The machine config folder:** `delegfile` also judges two forms for `machine-config` ("Owner machine setup"), each after this list's own check, so a target that can reach the list keeps `owner-delegations`: a wildcard write target that starts in a machine config folder, and git in the PM repository's work tree whose pathspec lands in `<pointer>/.pm-kit` (tests/guard/test_machine_config.py `Wildcards`, `PointerGit`).
- **Tests:** tests/guard/test_delegfile.py; tests/guard/test_cheap.py `KeptDenies` `test_the_owners_delegation_list_is_a_kept_deny`.

## Hub secrets

The Action Hub (`kitlib/hubsite`) keeps its tokens in a folder named `hub` beside the machine config file (`kitlib/hubsite/auth.py`); the guard also holds `<pointer>/.pm-kit/hub`, the PM repository's machine config folder's, where machine setup copies the hub's files before the hub reads them from there (`rules.hub_secret_folders`; every rule below holds each token folder; tests/guard/test_machine_config.py `test_a_hub_token_in_the_pointer_folder_is_a_hub_secret`): `owner.token` answers as the owner, `agent.token` is every agent's, and `approval.key` signs the owner's approval decisions (`kitlib/hubsite/approvals.py` `sign`) and binds strong sessions (`kitlib/hubsite/auth.py` "The approval key"). Its store is the machine config's `hub.store`, unset: `<pm_data.path>/hub` (`kitlib/hubsite/settings.py`). Agents reach the hub only through `tools/hub.py`'s agent verbs and the hub MCP server, which read `agent.token` in their own process, and the hub server's git sync writes the store; an agent's own access to those files is owner power. Four rules hold every session but the owner's own (subagents and every mark, `plain` included, as `owner-tool` does; "Session mark"). They live in `kitlib/guard/rules.py` (section "the Action Hub"), with pure helpers in `kitlib/guard/hub.py`, which copies the hub site's names rather than importing it (tests/guard/test_rules_hub.py `Plumbing` checks they match).

- **hub-secrets, edits:** a file tool edit of a path in the token folder or a store, judged by the resolved path (`jail.real`). Both stores count, an explicit `hub.store` and `<pm_data.path>/hub`, since the hub may move to the default one. The store and port are read from the machine config's `hub` object even when the strict read refuses the file for a fault elsewhere (`rules.hub_config`).
- **hub-secrets, shell:** a command (`rules.hub_secret_shell`) with:
  - a literal path (redirect targets included, `--opt=<path>` and PowerShell's `-Opt:<path>` read; `rules.hub_path_texts`) in the token folder, in the words of any program. A word that only names a token file or looks like the folder, with no path into it, passes (`echo owner.token`, `cat x/owner.token`, `cat foo.pm-kit/hub-x`); a word the shell computes is not read. A wildcard path is read as the literal folder before the separator ahead of its first wildcard (`rules.glob_folder`), so `cat ~/.pm-kit/hub/*` is refused and `cat ~/.pm-kit/h*` is not; a path holding a DOS wildcard (`<`, `>`, `"`) is read that way too, with those counted (`rules.hub_texts`: `cat ~/.pm-kit/hub/o\</../../x` is refused). The word `hub` and the store are not read (a shell write into the store is the write rules'; a file tool's edit there is still hub-secrets'). A path may start with the home folder spelled as `~`, `$HOME`, `${HOME}`, `$env:USERPROFILE`, `$env:HOME`, `%USERPROFILE%`, or the drive and path pair `$env:HOMEDRIVE$env:HOMEPATH` (`${env:...}` too) or `%HOMEDRIVE%%HOMEPATH%`, read as the guard's own home and only when nothing after it is a variable (`shell.HOME_VAR_RE`, `shell.home_text`). A relative path is read from where a `cd`, `Set-Location`, `sl`, `pushd` or `Push-Location` to such a home path moved the line, and a bash or PowerShell `cd` or `Set-Location` with no place, or PowerShell's `cd $null`, counts as a move home, as bash's and PowerShell 7's do (bash cd's own options and a `--` are passed over: `cd -- ~`, `cd -P`; a bash `builtin cd` or `command cd` is the cd itself, `shell.cd_words`). That is `shell.track`'s `cwd_home` (`shell.cd_target` with `home_vars`); every other rule still treats that line's directory as unknown, so a relative `hub` run from `~/.pm-kit` counts;
  - python or node code given on the line (`-c`, `-e`, a heredoc, a here-string, the command piped in) naming a token file or the folder literally (`hub.INLINE_RE`; `rules.inline_code`). `hub.py` and `hubsite` are not secrets, so `python "<kit>/tools/hub.py" questions --json | python -c "import json,sys; print(json.load(sys.stdin))"` passes. A parsed hub tool run of an agent verb piped into code given on the command line is that code's data, not code, so a token file's name in its words is not read (`rules.hub_run_verb`); piped into code read from standard input (`python -`) it is the code and still read, and any other program piped in is still read. A name the code builds or reaches through a library is not read.
- **hub-secrets, read tools** (`rules.hub_secret_read`, an Action of kind `read`): paths are resolved as the edit rule's are (`jail.real`), and only the token folder is held, so the store stays readable.
  - Read: a file in the token folder, or the folder itself.
  - Grep starting in the folder (its `path`, else `cwd`).
  - Grep from a parent of the folder: denied with no `glob`. With one, it is denied when any of its pieces (split on spaces and commas, braces written out at most `hub.BRACE_LIMIT` forms, case and backslashes dropped) can take in a name in the folder (the token files' names, `hub.SECRET_FILES`, and everything the folder holds, `rules.hub_secret_names`; past `rules.HUB_NAMES_LIMIT` names it counts as reaching) or name a folder on the way there (`hub.filter_reaches`); a `!` exclusion, and a brace it cannot write out, count as reaching. A Grep from anywhere else passes: it cannot reach the folder.
  - Glob is not hooked (a names search lists names and reads no token's text), so it passes anywhere, the token folder included.
- **hub-owner-verb:** a parsed hub tool run, at any depth of the line (`rules.hub_run_args`, `rules.hub_owner_run`): python with a script whose last part is `hub.py`, or with `-m tools.hub` (`-m hub`, a flag cluster ending in `m`, `-m runpy tools.hub`), its arguments read as `tools/hub.py`'s argparse parser reads them (`hub.owner_verb`). An owner verb in the Rules table (`hub.OWNER_VERBS`, `hub.OWNER_SUBS`, `todos add --owner`) is denied; a word the guard cannot read where the verb could be counts as one, and so does a PowerShell word holding a double quote. Only a run counts: text that names the hub tool without running it (a search pattern, a file a reader reads, a quoted argument of another program, a note written with `echo`) passes, and so does an agent verb whatever follows its pipe (`python "<kit>/tools/hub.py" todos --json | ConvertFrom-Json`). On a line the parser cannot read, the fallback refuses any text naming the hub tool, read verbs included ("Fallback", "The owner's tools by name"). A script or module word the guard cannot read is no run, and a launcher that runs the tool some other way is not read. The agent verbs stay open: `questions` (list, `show`, `add`, `log`, `done`, `file`, `bind`, `edit`, `withdraw`), `todos` (list, `add`, `ack`, `edit`, `withdraw`), `stories` (list, `set`), `to-pm` (list, `reply`), `inbox` (list, `add`), `pages` (list, `publish`, `show`), `approvals` (list, `show`, `add`, `withdraw`), `pending`, `wait`, `status`, `validate`, `serve`, `setup`. `approvals approve`/`deny` is held though `tools/hub.py` has no such verb. The owner's token is no protection here, since `kitlib/hubsite/client.py` reads `owner.token` itself (tests/guard/test_rules_hub.py `OwnerVerbs`, `ParsedRuns`).
- **hub-mcp:** an MCP tool whose last part (after the host's server separator, `__` on Claude) is in `hub.OWNER_MCP_TOOLS`, under any server name, or a hub tool (named `hub_*`, or served by a server named `hub`) whose name holds `decide` or `approve`. The list is the hub MCP server's `kitlib.hubmcp.OWNER_ONLY`, imported (`kitlib/hubmcp/__init__.py` imports nothing, so the guard never loads the server: `test_the_guard_does_not_load_the_server`).
- **hub-browser:** an MCP call to a server whose name holds `chrome`, `browser`, `playwright`, `puppeteer` or `computer-use` whose input (`Action.params`, every string up to 8 levels deep) holds `host:port` with a loopback host on a hub port (`hub.hub_origins`): 8790 and 8791 and the configured `hub.port` and `hub.tunnel_port`. Loopback is `localhost`, `*.localhost`, 127/8, `0.0.0.0`, `[::1]`, IPv4-mapped IPv6, and IPv4 in a browser's other spellings (`127.1`, `2130706433`, `0x7f.0.0.1`, percent-encoded). `Action.params` is the tool's input, which the Claude and Codex adapters pass (`hosts/*/adapter/events.py`); it takes no part in an Action's equality or hash (`kitlib/host/__init__.py`).

- **Limits:** not caught:
  - Read and Grep in an account whose PreToolUse matcher is older than the one in "Go-live", step 1: Claude Code does not send them to the guard (the settings are the owner's to change);
  - Glob, which is not hooked (a names search reads no token's text): it can list the token folder's names, never their text;
  - a link or junction below a search's start that leads into the token folder: only the start and the folder are resolved, not what the search walks through;
  - Grep's other ways to pick files (`type`) are not read: a Grep from a parent with a `type` and no `glob` is denied (over-reach), not judged by its type;
  - a script the agent wrote and then runs, or any program that reads the files itself (as the write jail: "Known limits");
  - python or node code on the line that never spells a name `hub.INLINE_RE` knows: a wildcard (`glob.glob(...)`), a name built from pieces (`'own' + 'er.token'`, `chr(...)`) or read from elsewhere (an environment variable, a file). `INLINE_RE` matches the code's text, not what it does;
  - a recursive read of a parent folder (`grep -r x ~/.pm-kit`, `Copy-Item -Recurse ~\.pm-kit`), a wildcard at or above the folder (`cat ~/.pm-kit/h*/owner.token`), and `Join-Path` pieces (`Join-Path $d 'owner.token'`);
  - a token file's name in a word with no literal path into the token folder (`cat $d/owner.token`; docs/guard-v2.md A2);
  - a shell command's read of the store, which is not held (its writes are the write rules'), and a relative path after a `cd` the text cannot place;
  - the home folder computed rather than spelled, which no reading of the text closes: `[Environment]::GetFolderPath('UserProfile')`, `Join-Path $HOME ...`, `$HOME + '\...'`, a variable set from it (`H=$HOME; cat $H/...`), a substitution or subshell whose output is the home folder (`$(echo ~)`, `"$(cd; pwd)"/...`); and a return home the guard does not follow: `cd -`, `popd` and `Pop-Location` (the directory after them is unknown);
  - hub-owner-verb, which reads only a parsed run: a launcher that runs the tool another way (`python -c "import tools.hub ..."`, a script the agent wrote, a copy of the tool under another name), and a name built at run time (string concatenation, an encoding, a variable's value: `python -m $m answer Q-1`). The rule catches mistakes and is not an adversary boundary;
  - a machine config the guard cannot read as JSON at all: an explicit `hub.store` and configured ports are then unknown, so only `<pm_data.path>/hub` (when the guard can tell `pm_data`) and the default ports are held;
  - text the parser never reads: the hub rules run on what the parser did read of an unclean line (tests/guard/test_rules_hub.py `test_unclean_lines_are_judged_on_what_was_read`), and the fallback refuses such a line that names the hub tool ("Fallback", "The owner's tools by name"); a line that never spells the name, such as an encoded command (`powershell -EncodedCommand <base64>`, which is not decoded), is not held by it, so a subagent is only warned (`unreadable`) and a marked session in a worktree passes;
  - hub-browser: a click, key or form input on a hub tab already open (its input names no origin), raw screen pixels, a host that resolves to loopback (`nip.io`, the machine's own name, a LAN address), a port the config does not name (`serve --port 0`, a one-off `--port`), an origin with no port (port 80 implied), obfuscated script text, and the tunnel's public hostname.
- **Over-reach:** denied though nothing secret is read:
  - hub-browser: a browser MCP call to a loopback origin on 8790 or 8791 (or the configured hub ports) when something other than the hub serves there;
  - a word of any program, git's commit message included, that is itself a path into the token folder (`git commit -m "~/.pm-kit/hub"`), as paths are read in every word;
  - from `~/.pm-kit`, a bare `hub` as any word, search patterns included (`grep -n hub x`), because there it names the token folder;
  - hub-owner-verb: an agent verb whose value is a variable (`--title "$t"`) or, on PowerShell, a word holding a double quote, since either may split into `--owner`;
  - a Windows PowerShell 5.1 `cd` with no place or `cd $null`, which stays where it is;
  - read tools: a Grep with no `glob` from any parent of a token folder (home, or the drive root); the PM repository (the pointer) is the parent of `<pointer>/.pm-kit/hub`, so a held session's Grep over its root with no `glob` is denied.
- **Tests:** tests/guard/test_rules_hub.py (each rule, every held session, the owner's allowed, and the agent verbs passing); tests/guard/test_rules_hub_read.py (the read tools); tests/guard/test_entry.py `test_a_subagent_read_of_the_hub_owner_token_is_denied` (end to end through `boot/hook.py`).

## Pre-push

`githooks/pre-push` calls `kitlib.guard.prepush.main` with git's two arguments (the remote's name, or the URL for a push by URL, and the URL). Whoever pushes, the PM data stage below judges every ref line first, then the machine config secrets stage judges every ref line; the checks after them are on a ref whose remote ref is `refs/heads/<main>`.

**PM data branch** (`prepush.leak_refusal`; docs/pm-data-branch.md "Pre-push guard"). It runs only when the git common dir of the work tree pushed from holds `kit-pm-data.json` (`kitlib.pmdata.read`: data branch, private remote, root commit); with no file nothing changes. Each ref line is judged, whatever its remote ref, and the first refusal ends the push (`--all`, `--mirror` and `--tags` included).
- **Fail closed:** a record that cannot be read or is malformed, a git common dir git cannot name, the recorded root commit missing from this clone (`cat-file -e`), or remotes that cannot be read refuse every push, the record's path or the cause named.
- **Which remote is private** (`prepush._remote_urls`, `_private`): the URL git hands the hook (its second argument, after `insteadOf` and `pushInsteadOf`) decides, not the remote's name. The push goes to the private remote only when that URL is one of the recorded remote's push URLs as git computes them (`git remote get-url --push --all <remote>`: `pushurl`, else `url`, rewritten) and no other remote has it among its URLs (push and fetch URLs as git rewrites them, and the raw `url` and `pushurl` values). Every remote URL is read with `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_<n>` and `GIT_CONFIG_VALUE_<n>` dropped from git's environment, so `git -c remote.<private>.pushurl=<public URL> push <private>` is judged as public. URLs are compared by `prepush._norm_url`: a trailing `/`, then `.git`, dropped; a remote URL (`https://`, `ssh://`, scp-like `user@host:path`) has its scheme and host case folded and keeps its path's case, so two repositories whose paths differ only in case stay two; a local path (drive, UNC, `file://`) has backslashes as slashes and is case folded whole. Everything else is public: a URL the private remote does not push to, a URL another remote also has. A remote whose URLs `get-url` cannot give for any reason but "No such remote" (then its raw config values count) refuses every push, as do remotes `git config` cannot read.
- **Public remote, by name:** the local or remote ref is `refs/heads/<data branch>`: refused, naming the one push that is allowed (`git push <private> refs/heads/<branch>:refs/heads/<branch>`).
- **Public remote, by history:** the pushed sha holds the recorded root (`refs.is_ancestor`), or git cannot tell: refused. This catches the data branch merged into any branch, and a tag (light or annotated) on a data commit.
- **Public remote, by objects:** otherwise, the objects the push may send (`rev-list --objects <local sha> --not <remote sha, when this clone has it> --remotes=<name>`) are compared with every object reachable from the root, the local data branch and `<private>/<data branch>`, less the empty tree and blob. Any shared object refuses the push, one path named. This catches a cherry-picked data commit. A file whose content is identical to a data file matches too and is refused (fail closed; the message says so); a copy changed by even one byte is not caught. The `--remotes=<name>` subtraction trusts this clone's remote-tracking refs; it is left out (nothing subtracted) when another remote's name starts with `<name>/`, whose tracking refs the pattern would also match, or the name holds a pattern character.
- **Public remote, deletions:** a deleting line sends nothing and is not judged here, so deleting a leaked `refs/heads/<data branch>` from a public remote is allowed (the main-branch rules still refuse deleting main).
- **Private remote:** it receives only `refs/heads/<data branch>`, with the root in its history. Any other ref (main, another branch, a tag), a sha without the root, and any deletion there are refused.
- **The rules after this stage** run as before for each line. For a push to the private remote their base config is the replaced remote commit's, so the data branch's own committed `.kit.json` (its `main_branch` and `push_block`) when that remote already has it; for a first push, the default branch's.
- **Not caught:** `--no-verify` skips the hook; the guard rule `git-push-pmdata` denies it outside the owner's own session ("Rules").

**Machine config secrets** (`prepush.secrets_refusal`; "Owner machine setup"). In every repository, for every remote and every ref line: a commit the push sends that adds or changes `.pm-kit/local.json` or a file under `.pm-kit/hub/` at the checkout's top (`prepush.is_secret_path`, case ignored) refuses the push, naming the file and the commit; a file a later commit deletes still counts, since the earlier commit carries it. The commits are read with `git log -m --no-renames --name-only --diff-filter=ACMRT <local sha> --not <what the remote has> --`.
- **What the remote has** (`prepush._remote_has`): the remote sha the line replaces, when this clone has it, and the tips of the remote's tracking refs (`refs/remotes/<name>/`, read by `for-each-ref`, up to `MAX_TRACKING_ARGS`; past that `--remotes=<name>`), left out as the PM data stage leaves them out (`prepush._tracking_counts`). A commit the remote already tracks is not judged again.
- **Sends nothing:** a deleting line, and a local sha this clone lacks (git hands the hook only shas it has).
- **Fail closed:** remotes `git config` cannot read, or a log or `for-each-ref` that fails, refuse the push.
- **Not caught:** a `.pm-kit` deeper than the checkout's top; a secret already on a tracking ref of the remote (the subtraction trusts this clone's tracking refs); `--no-verify`.

- **Fast-forward only, in every repo:** a push that is not a fast-forward of the remote's main is refused, and so is deleting main. A remote main sha this clone lacks cannot be an ancestor of the pushed commit, so that push is refused too ("cannot tell"; fetch first). Git hands the hook such a ref only on a forced push (`--force`, `+`, `--force-with-lease`). A branch other than main may still be rewritten.
- **Gate-OK record:** the pushed sha must have one, read as in "State" (`prepush.verify_record`): with a `dev_drive` a `.git` copy alone does not count. Only when `repo.push_block` is set; checked after the fast-forward rule.
- **Owner-only paths:** after the gate-OK check, and also only under `repo.push_block`, a push to main is refused when a commit it adds fails "Owner-only commits" below, record or not. A branch gate records its own tip, so without this a gated agent branch could go straight to main. "Adds" means not in the remote main it replaces when this clone has it, else not in `<remote>/<main>` as last fetched, else the whole history. Other remote-tracking refs are never subtracted: a pushed agent branch would hide its own commits.
- **Order:** the PM data stage for every line (tests/guard/test_prepush_pmdata_private.py `PmDataPrivateTest.test_leak_stage_runs_before_main_rules`), then the machine config secrets stage for every line, then per line delete or fast-forward, then gate-OK, then owner-only paths; the first that refuses is the one reported (`test_the_rules_refuse_in_order`).
- **Base config:** `push_block` and the main branch's name are read from the remote main commit being replaced when this clone has it, else from the default branch's committed `.kit.json` (the first of `<remote>/HEAD`, `<remote>/main`, `<remote>/master`, local `main`, local `master`). The working tree is never the base, and a pushed commit cannot turn the block off.
- **Broken config:** a `.kit.json` that does not load refuses the push.
- **Tests:** tests/guard/test_prepush.py pushes to a bare scratch remote with `core.hooksPath` set to the kit's githooks; tests/guard/test_prepush_pmdata.py and test_prepush_pmdata_private.py add a second bare remote as the private one, `PrivateTest` covers `_private` and `_norm_url`; tests/guard/test_machine_config.py `PrePushSecrets` covers the machine config secrets stage, on real git.

## Owner-only commits

`kitlib/guard/ownercommits.py` `violations()` judges the net change, then the commits. For each owner-only path (`kitlib/config/owner.py` `is_locked`) that the net change touches, it names every commit that changes the path and whose author email (`%ae`, never mailmapped, replace refs off) is not `"owner".email` (`is_owner`). `gate land` (docs/gate.md "Landing", step 4) and pre-push run it, so a plain `git commit` to an owner-only path does not reach main past either.

- **Net change:** a path counts only when landing the tip on the target main would change it: the target differs for it from the clean merge of the target and the tip (`git merge-tree --write-tree`; the tip itself for a fast-forward), or that merge conflicts on it (`net_change`). The target is the landing's base for `gate land` and `land.py` (`<remote>/<main>` as fetched at its turn; docs/gate.md "Landing", step 4), the remote main being replaced for pre-push. So an agent change a later commit undoes, a rename away and back, and an owner change the branch brought in by merging main do not count. With no target (pre-push with no remote main known), every changed path counts.
- **Rules:** the base's merged with the pushed or landed commit's (`owner.merge`): paths are the union, exceptions the intersection, the owner email the base's only. An unset owner email, or one also in `agent_emails`, refuses every owner-only change.
- **What a commit changes:** a commit with one parent or none, its diff. A two-parent merge, what differs from the clean merge of its parents (`git merge-tree --write-tree`) plus every path that merge conflicts on: a merge that only joins histories changes nothing, and an edit or conflict resolution inside a merge is judged by the merge's author. More parents: the union of the diffs against each. Renames count as a delete and an add.
- **Trailers** play no part here but one (an owner approval, below): the author email decides. `tools/commit.py` writes the `Owner-Approved` trailer and refuses an owner-only path without `--owner-authored` (docs/commit.md).
- **An owner approval** is the one exception (`HubApprovals`; docs/commit.md "Owner approval"): a non-owner commit that carries exactly one `Owner-Approval: hub:A-<n>`, has one parent, changes exactly the approval's files to their approved blobs as regular files, and the hub verifies as consumed by that commit. The parent is the approval's base or a descendant of it that holds every approved path as the base does (`kitlib.hubsite.approvals.same_content_error`, then `Verifier.verify_on` asks the hub for the signed base), so an approved branch whose base main moved past still lands.
- **Git failure:** refuses (the landing or the push).
- **Tests:** tests/guard/test_ownercommits.py, tests/gate/test_land_owner.py, tests/guard/test_prepush_owner.py `OwnerTest`.

Known limits:

- **The author email is what the committer says** (`git commit --author`, `GIT_AUTHOR_EMAIL`). The guard's `owner-identity` rule denies a session other than the owner's setting the owner's email on the command line; an identity in the environment the session started with is not seen. Signed commits would close it; not built.
- **Only main is checked at push**, and only under `repo.push_block`, like the gate-OK check. A push to another branch, or a merge made on the server (a pull request merged in the web UI), is not seen.
- **One net change per push:** a push to main that carries the owner's unpushed main commits together with a branch is judged as a whole. When an owner commit in it changes a path, an agent commit that touched that path and was undone counts too, and the push is refused (fail closed). Pushing the owner's commits first avoids it.

## Self-test

`hosts.claude.adapter.guard_selftest.agent_id_check(projects_dir, since)` scans subagent transcripts (`<project>/<session>/subagents/agent-*.jsonl`) for guard tags.

- **What counts:** only tags in tool results marked `is_error` (INFERRED to be where a hook deny lands).
- **Results:**
  - `role=main` in a subagent transcript is an alarm: `agent_id` has disappeared;
  - only subagent roles pass;
  - no tags is inconclusive.
- **Not live:** it is not wired to a session-start hook.

## Refusal patterns pre-empted

The guard denies these with the command to use before the auto-mode classifier sees them (the PM repository's docs/refusals.md):

- **P16:** a gate wrapped as `cd <wt> && python tools/gate.py 2>&1 | tail`. Rule: `wrapped-gate`, whose alternative is `python "<kit>/tools/gate.py" -C "<wt>"` run bare in the background.
- **A repo's wrapped lander command** (same family as P16). Rule: `wrapped-gate`.
- **git_guard's main-checkout patterns:** the git rules and the fallback cover them.
- **Root searches:** rule `root-search`.
