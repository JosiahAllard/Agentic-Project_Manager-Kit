# Machine setup

One reviewed command sets a machine up for the kit (plan decision 27, docs/multi-host-plan.md section 7). It writes nothing into any repository (the one exception is opt-in: the `--pm-settings` file you name, a local settings file the PM repository keeps out of its commits): a repository works with the kit with nothing committed in it, and the kit's first use there writes only local git settings (docs/install.md "What first use writes"). Three repositories land through `gate.py land` on the owner's machine: this kit and two others.

```
powershell -NoProfile -File installer\machine-setup.ps1 [-OwnerEmail <email>] [-PmSettings <file>] [-ConfigDir <folder>,<folder>] [-AgentTemp <folder>] [-NoSweepTask] [-Shortcut] [-Procwatch [-ProcwatchKill]] [-Apply]
powershell -NoProfile -File installer\machine-setup.ps1 -OldKit <old kit clone> [-OwnerEmail <email>] [-ConfigDir <folder>,<folder>] [-AgentTemp <folder>] [-NoSweepTask] [-Procwatch [-ProcwatchKill]] [-Apply]
python tools/machine_setup.py [--old-kit DIR] [--owner-email EMAIL] [--pm-settings FILE] [--config-dir DIR]... [--agent-temp DIR] [--no-sweep-task] [--no-worktree-sweep] [--shortcut] [--procwatch [--procwatch-kill]] [--kit DIR] [--home DIR] [--desktop DIR] [--apply]
python tools/machine_setup.py --repo PATH --owner-email EMAIL --agent-email EMAIL [...] [--apply]
python tools/machine_setup.py --managed-settings [--kit DIR] [--home DIR] [--apply]
python tools/machine_setup.py --pm-repo PATH [--kit DIR] [--apply]
python tools/machine_setup.py --delegation [--kit DIR] [--apply]
```

Six modes:

- **The default** ("Default mode" below): the guard's entry in each Claude account's `settings.json`, the kit plugin on each host machine setup installs, the owner's email in the machine config ("Owner email") and the agents' temp folder ("Extras"). `--fresh` (`-Fresh`) is its old name and is still accepted.
- **`--old-kit DIR`** (`-OldKit`): switches a machine's Claude config folders from an older kit clone to this kit checkout: each account's `settings.json` (with every link the clone's setup left reported, "Links"), the owner's email and the machine extras (the schedule shortcut, the agents' temp folder with its sweep, and `KIT_MACHINE_LOCK`).
- **`--repo PATH`**: the committed repo setup, for a repository that wants its kit settings committed: `.kit.json`, the ignore lines, a starter `docs/INDEX.md`, and with `--stack` its files ("Committed repo setup (--repo)" below; docs/install.md "Committed setup (--repo)"). `installer/new-repo.ps1` is its PowerShell front end.
- **`--managed-settings`** (`-ManagedSettings`): writes Claude Code's machine-wide managed settings file from the kit's template, and nothing else ("Managed settings" below). `--apply` needs an elevated terminal.
- **`--pm-repo PATH`**: sets the PM-repo pointer in the registry to the PM repository's work tree PATH, and nothing else ("PM repo pointer" below). `--apply` needs an elevated terminal. The PowerShell wrapper's switch is `-PmRepo PATH` (`installer/machine-setup.ps1`): a mode of its own that takes only `-Python` and `-Apply` (docs/install.md step 1).
- **`--delegation`**: Linux only, the one root step that gives strong containment, and nothing else ("Linux" below). `--apply` runs as root, through sudo.

Run it from the kit's main checkout, not a worktree: `--kit` defaults to the checkout the tool is in, and every hook path and shortcut names that folder. Run from a plugin export (`<export root>/<sha12>`, docs/plugin-source.md "Layout"), in every mode `--kit` defaults to the main checkout the export's `.pm-kit-export` marker records (`kitlib.pluginsource` `default_kit`), since every plugin refresh replaces the export folder; when that checkout has moved or gone, the tool prints `REFUSED: <export>: this is an export; pass --kit <kit checkout>` and exits 1.

- **Dry run by default.** It prints every change, with each `settings.json` change as a unified diff, and changes nothing. `--apply` (`-Apply`) makes the same changes, in the printed order.
- **Config folders.** The default mode uses the account folders `tools/plugin_refresh.py` runs in (`account_folders`, `kitlib/pluginsource/claude.py`): `~/.claude`, every `~/.claude-*` folder except the machine config's own, current and retired (`kitlib.config.user.DIR_NAME`, `kitlib.config.migration.OLD_DIR_NAME`), and each existing folder the launcher config names; the dry run notes that a backup copy such as `~/.claude-backup` is among them unless `--config-dir` leaves it out. `--old-kit` uses the first two only. `--config-dir` (repeatable) names them instead; the wrapper's `-ConfigDir a,b` is split on commas, so a folder name with a comma cannot be passed there. A folder that is a link to one already listed is read once. With no config folder at all, both modes refuse.
- **Idempotent.** A second run prints `nothing to do` in every section and exits 0.
- **Refusals.** Any refusal stops the run before anything changes: an old-kit path in a settings file that this step neither removes nor re-points, a hook path it cannot resolve, a settings file it cannot read or must not replace, a machine config it cannot read, a kit file a path would need, a missing config folder, or `--kit` equal to `--old-kit`. Each refusal names the file and path.
- **Part-way failure.** If a change fails under `--apply`, whatever the error, it stops there. It prints the change, the error, how to restore that change by hand, and the changes already made. Every line is printed as it is produced.

Exit codes: 0 done, dry run printed or nothing to do; 1 refused or stopped; 2 usage: both `--old-kit` and `--fresh`, `--pm-settings` with `--old-kit`, a `--repo` option without `--repo` or a machine option with it, `--managed-settings` with any option but `--kit`, `--home` and `--apply`, `--pm-repo` or `--delegation` with any option but `--kit` and `--apply`, two modes at once (the wrapper also exits 2 for `-OldKit` with `-Fresh`, `-ManagedSettings` with `-OldKit` or `-Fresh`, `-PmSettings` with `-OldKit`, a `-Python` that is not a file, or, without `-Python`, with no `python` on PATH). `--repo` has its own codes (docs/install.md).

The wrapper runs the tool under `-Python <python.exe>` when given, else under the `python` on PATH.

## Links

`kitlib/machinesetup/links.py`. Machine setup makes no link, in either mode. The kit runs from its own folder (the plugin root), so an account needs no `tools`, `knowledge` or `skills` entry pointing into it. This step only reports the links an earlier setup left, and adds no change, so a second run still prints `nothing to do`.

Each leftover is one note, with the command that removes the link only, never its target (never `/s`; `links.remove_cmd`, `links.leftover`):

```
leftover link <path> -> <target>: remove it with: cmd /c rmdir "<path>"
```

Remove the `hooks` link only once `settings.json` no longer calls a guard through `~/.claude/hooks`. Skill links left after the plugin install make each skill appear twice.

That is the command for a junction or a directory symlink. A file symlink (one without the directory attribute) gets `cmd /c del "<path>"` instead, since `rmdir` fails on it; `del` removes the link and leaves its target. A relative symlink target is read against the link's own folder, not the current directory (`common.link_target`).

In each config folder it checks `tools`, `knowledge` and `skills`. A link counts when its target is in this kit or, with `--old-kit`, in the older kit clone:

- A container that is itself such a link: one leftover note for the container. For `skills`, each skill under its target that the kit has no folder for in `content/skills` is named too: a repo-local skill moves to its repo before the link goes.
- A link whose target is outside this kit (and, with `--old-kit`, the older clone) is left alone but never silently: a container that is a link elsewhere, for example an account folder following `~/.claude`, or an entry of a real `tools`, `knowledge` or `skills` folder that is, gets one note (`links.skipped`). In the default mode a link an earlier setup made into a kit clone that has moved since is one of these, so the note carries the same remove command:

  ```
  skipped link <path> -> <target>: its target is outside this kit, left as is; if an earlier setup made it, remove it with: cmd /c rmdir "<path>"
  ```

  An absent container is left alone with no note.
- In a real `tools` or `knowledge` folder, each entry that is such a link is a leftover. Earlier setups linked `machine_lock` -> `<kit>/tools`, `kitlib` -> `<kit>/kitlib`, `comfy`, `procwatch`, `usage`, `agenttemp` -> `<kit>/optional/<name>` (`links.TOOL_LINKS`) and `knowledge/asset-generation` (`links.KNOWLEDGE_LINKS`). A real folder at one of those names is noted ("a real folder, left as it is") with the kit's own copy; nothing is renamed or deleted.
- In a real `skills` folder, a link at the name of a kit skill is a leftover, including one into a folder the skills have left (`links.MOVED_SKILLS_DIRS`: `<kit>/claude/skills`, `<kit>/hosts/claude/shell/skills`); the plugin loads those skills. A link at another name is noted and left: the kit has no such skill.
- With `--old-kit`, any other entry of the config folder (`agents`, `hooks`) that links into the older kit clone is noted and left ("Not done here").

A settings path that runs through one of these links is re-pointed to the kit's own file in the same run ("Settings"), so the owner can remove the links once that change is applied.

## Settings

`kitlib/machinesetup/settings.py`. In each config folder's `settings.json`, it reads every path in a hook's `command` and `args` and in `statusLine.command`. `~`, `%USERPROFILE%`, `$env:USERPROFILE`, `$HOME`, `${HOME}`, `$env:HOME`, `%HOMEDRIVE%%HOMEPATH%` and `%HOMEPATH%` are read as the home folder.

A path it cannot resolve to an absolute one (a relative path, a script name, another variable) is refused, since it cannot tell whether it is the old kit's. Words, switches such as `/c`, URLs and paths under `$CLAUDE_PROJECT_DIR` or `$CLAUDE_PLUGIN_ROOT` are not refused. A `hooks` value, event or group of a shape Claude Code does not use is refused too.

A path that resolves into the old kit, into `<kit>/hooks` or to `<kit>/tools/guard.py` gets one of three outcomes:
- **Removed.** `no_root_search.py` and `main_checkout_redirect_guard.py`: the hook goes. A group or event that removal empties goes too; one that was already empty stays.
- **Re-pointed.** The file is rewritten to the kit's copy with forward slashes, quotes kept:
  - `pm_session_start.py` and `coordinator_session_start.py` become the kit's hook entry: `boot/hook.py claude SessionStart pm` and `boot/hook.py claude SessionStart coordinator` (the words follow the path in a command line, or are added to `args` after it).
  - `statusline-usage.ps1` and `write-usage-status.ps1` go to `optional/usage/`.
- **Refused.** Any other old-kit path, named.

### Moved hook paths

Before any other step, in every mode and in the `--pm-settings` file, a hook path to a retired script in `<kit>/claude/hooks/` or `<kit>/hosts/claude/shell/hooks/` is re-pointed to the kit's one hook entry with the host and the script's words (`settings.repoint_moved`, `settings.RETIRED`): `guard.py` becomes `boot/hook.py claude PreToolUse`, `pm_session_start.py` `boot/hook.py claude SessionStart pm`, `coordinator_session_start.py` `boot/hook.py claude SessionStart coordinator` (in a command line the words follow the path; in `args` they are added after it). Any other script name in those folders, or a kit with no `boot/hook.py`, is refused. The kit keeps no stub at the retired paths, so an account whose settings still name a removed hook script has every guarded tool call blocked until the owner re-runs machine setup, which must happen from a terminal outside any Claude session (its Bash calls are blocked until then), then restarts open sessions, which read hooks at start. A PM repo's settings file is re-pointed only with `--pm-settings FILE` (the default mode); under `--old-kit` one that still runs `pm_session_start.py` is edited by hand to the hook in docs/pm-start.md.

A path through `<config>/tools/<name>`, a name in `links.TOOL_LINKS`, is re-pointed to the kit file that link reached, forward slashes, quotes kept (an unquoted path that gains a space is quoted): `<config>/tools/usage/statusline-usage.ps1` becomes `<kit>/optional/usage/statusline-usage.ps1` (`settings.repoint_links`). `<config>` is any config folder of the run or of the home, since a status line can name another account's folder. This runs in every mode, in hooks (`command` and `args`) and `statusLine.command`, and in the `--pm-settings` file. It is refused, named, when the kit has no such file.

When no PreToolUse hook names `<kit>/boot/hook.py`, the entry `boot/hook.py claude --settings-entry` prints is appended (docs/guard.md; on Linux a rerun also adds `onFailure "block"` to a guard entry written without it, `settings._guard_on_failure`; hook entries with absolute paths and `python3` or `python3.N` interpreters are recognised, so a rerun adds no duplicate), unless the managed settings file runs a kit's guard ("Managed settings": with this kit's guard there, none is appended and one already in the account is noted as running twice; with another kit's, it is noted and none is appended). The host, `claude`, is hosts.json's default host, whose account settings these are.

A SessionStart hook in shell form whose command is a Python interpreter (`python`, `python.exe`, `pythonw`, `pythonw.exe`, by base name), then `<kit>/boot/hook.py` and its words (at most three plain words; a redirect or a pipe keeps the hook in shell form), is written in exec form: `command` becomes the interpreter of the guard entry `boot/hook.py claude --settings-entry` prints, and `args` holds the script with forward slashes, then its words. Exec form starts no shell. Any other command, a hook that already has `args`, and every other event are left as they are.

When the kit's `.claude-plugin/plugin.json` names a `hooks` file, a settings hook that runs the same script with the same words as one of that file's hooks, for the same event, is noted (`${CLAUDE_PLUGIN_ROOT}` read as the kit): once the plugin is enabled the hook runs twice, so the settings entry is removed in the same step as the plugin install (docs/install.md "Plugin install"). The note changes nothing. In the default mode a SessionStart one gets no note in a folder whose plugin the plugin step owns (in the refresh set, the entry absent or `true`; `owns_settings`, `kitlib/machinesetup/plugin.py`): that step removes it ("Default mode", "Plugin: Claude").

`statusLine` stays in shell form. Claude Code gives it no `args` field: "The `command` field runs in a shell", and "On Windows, Claude Code runs status line commands through Git Bash when Git Bash is installed, or through PowerShell when Git Bash is absent" (https://code.claude.com/docs/en/statusline).

Each of these is a planned change or a note: a dry run writes nothing, and `--apply` writes through the backup below.

The file is edited as JSON and written back in its own layout: indent, ASCII escaping, CRLF, BOM and final newline. Only the changed lines differ. A layout `json.dumps` cannot reproduce is noted, and the diff then shows the whole rewrite.

A `settings.json` that is a symbolic link or has more than one hard link is refused when it needs a change: writing through a temp file would split it from the file it shares.

`--apply` refuses if the file changed since the survey or has become a link. It then copies the file to `settings.json.machine-setup-<yyyymmdd>.bak` and writes through a temp file, which it removes if the write or the rename fails.

## Extras

`kitlib/machinesetup/extras.py`. Each extra is read first and planned only when it differs.

- **Machine schedule shortcut.** `Machine schedule.lnk` on the desktop (or `--desktop`) runs `pythonw "<kit>\reserve_ui.pyw"`. With `--old-kit` always; in the default mode only with `--shortcut` (`-Shortcut`), and the plan notes it otherwise.
  - Other desktop shortcuts that still run the old kit or `reserve_shortcut.ps1` are noted, not removed.
- **Agent temp init.** `kitlib/machinesetup/agenttemp.py`. The folder is `--agent-temp`, else the machine config's `agent_temp_sweep.dir` (docs/kit-json.md), else the user environment's `AGENT_TEMP`, else `kit-temp` (`kitlib.config.user.TEMP_DIR_NAME`) at the root of the kit's drive (`default_agent_temp`; a kit on a UNC path gets a note and no folder). A folder that is not absolute, or is a link or a file, is refused. So is every folder the sweep refuses, through the one function both use (`unsafe_dir`): a drive root; the home folder, a folder in it or one holding it; the kit or a folder that holds the machine config (`kitlib.config.user.keep_clear_dirs`: the PM repository's `.pm-kit` when the config is there, the home folder's when the config is still there, unmoved or left over; for a config that cannot be read, the PM repository's when the pointer is good; none when there is no config), a folder in one or one holding one; a folder inside a git checkout or worktree (a `.git` in it or above it). Each check is made on the path as written and on its real path, so a junction onto one of these is refused too.
  - `python tools/agent_temp_init.py [--agent-temp DIR] [--kit DIR] [--home DIR] [--no-sweep-task] [--apply]` runs only these temp-folder steps (the folder, `AGENT_TEMP`, the config key, the sweep task and the permissions below), dry run by default (`run_agent_temp`, `kitlib/machinesetup/__init__.py`). Exit codes: 0 done, dry run printed or nothing to do; 1 refused or stopped; 2 usage.
  - The folder is made when it is missing; the permissions step below then plans its grant without reading `icacls`.
  - The user environment variable `AGENT_TEMP` is set to the folder when it is unset. Set to another folder, it is set only when `--agent-temp` was given; otherwise the plan notes it and leaves it.
  - The machine config gets `agent_temp_sweep = {"dir": <folder>, "max_age_days": 3}` when it has no such key, the file's other keys and layout kept (`write_sweep_key`). The write refuses a file that changed since the survey, and puts the file back when the config cannot be read after it. An existing key is noted and never overwritten. A machine config still only in the home folder (`UNMOVED`) is refused (`kitlib.config.user.writable_file`), and so is a machine with no PM repo pointer: there is no file to write, so `--apply` refuses, nothing changed, naming the `--pm-repo` step ("PM repo pointer").
- **Agent temp sweep task.** The scheduled task `agent-temp-sweep` runs `python "<kit>\optional\agenttemp\agent_temp_sweep.py" --apply` daily at 04:00 as the registering user (`-RunLevel Limited`, `-StartWhenAvailable`; `task_line`). It opens no console window: the task's program is the `pythonw.exe` of this interpreter's base install (`kitlib.launcher.pythonw.base_pythonw`, written into the line as a literal path, never a `Get-Command pythonw` lookup, which finds the Store alias first), with the arguments `"<kit>\tools\no_window.py" python "<kit>\optional\agenttemp\agent_temp_sweep.py" --apply` (the carrier, docs/daily-full.md "The schedule"), and the line throws, registering nothing, when that `pythonw` is not a file or is under `WindowsApps` (the Microsoft Store alias). `--apply` registers it by default (the owner runs `--apply`; the guard denies it to every other session, "Owner email"). The sweep task is two planned changes, in order. The first runs the sweep once without `--apply` (`python "<kit>\optional\agenttemp\agent_temp_sweep.py" --home <home>`, under machine setup's own interpreter, 120 s limit; `sweep_dry_run`; `--home DIR` is the sweep's option naming the home whose machine config it reads, so it reads the config of the home being set up; its output is read as UTF-8; it is planned after the folder's ACL step, `task_step` from `extras.acl_step`, so a refusing dry run cannot skip the hardening) and prints each line of its report, prefixed `sweep dry run (nothing removed):`, so the run shows what the task's first run would remove; the config key is written earlier in the same run, so the dry run reads it. A dry run that refuses (exit 2: no key, a bad config, an unsafe folder) or fails any other way but exit 3 stops the run there, registering nothing; the report is printed before the second change registers the task, so a failed registration does not lose it. `--no-sweep-task` (`-NoSweepTask`) leaves the task unregistered and the plan notes the PowerShell line that would register it; with the task already registered it notes how to unregister it. `--register-sweep-task` (`-RegisterSweepTask`), the old opt-in, is still accepted and changes nothing; given with `--no-sweep-task` it is a usage error. A task already registered is left as is (a second run plans nothing for it), so one registered before the carrier keeps running `python` with a window until the owner undoes it (below) and registers it again; a `schtasks` query that fails or takes over 30 s is a note (`task_registered`). Undo with `Unregister-ScheduledTask -TaskName agent-temp-sweep -Confirm:$false`.
  - What the sweep removes (its docstring, `optional/agenttemp/agent_temp_sweep.py`, holds the rules and exit codes): top-level entries of the folder, and under `claude/` each `claude/<project>/<session>` folder, once the newest time in it is older than `max_age_days` and it can be renamed aside (an entry with an open file or a working folder in it cannot). `agent_temp_sweep.keep` lists entries it never removes (`claude/<project>/<session>`, `*` and `?` within one name; case-insensitive; a keep entry deeper than the swept entry keeps that whole entry (`is_kept`)); `BUILT_IN_KEEP` adds `*-coordinator`, `*-consultant` and `shared`.
  - The user temp's session folders. Sessions the kit's launcher did not start (the desktop app's Code tab) keep their scratch under the user's own TEMP, `<user temp>\claude\<project>\<session>`. With `"user_temp": true` in `agent_temp_sweep` the daily run also sweeps that folder (HKCU\Environment TEMP, else TMP, `%VAR%` expanded), its `claude` units only and under the same rules; it is skipped with one `user temp: skipped:` line when the value is missing or not absolute, the folder is absent, it is `dir`, in it or holds it, or `second_root_unsafe` refuses it (a link in its path; every `unsafe_dir` refusal, except that `%LOCALAPPDATA%\Temp\claude` exactly may lie in the home folder). After moving the user's TEMP off the default, drain the old folder once: end every session and the desktop app started before the change, then run `python <kit>\optional\agenttemp\agent_temp_sweep.py --drain-old-user-temp` (a dry run) and the same with `--apply`. It sweeps only `%LOCALAPPDATA%\Temp\claude` and exits 4, removing nothing, while any `claude.exe` started before HKCU\Environment was last written, or when that cannot be told (an empty process list, or an HKCU\Environment TEMP, else TMP, that is missing, not absolute or holds an unexpanded `%VAR%`); the dry run exits 4 too while that gate is shut.
  - Remaining risk: a session idle, with no open handle in its folder, for longer than `max_age_days` loses its scratch; the keep-list is the remedy. An empty folder some tool left (a dotnet build's, say) goes like any other old entry.
  - The default `max_age_days` stays 3: the age, the claim and the keep-list carry the safety, and the dry run printed before registering is the list to read. To read it before any task exists, apply with `--no-sweep-task`, run `python <kit>\optional\agenttemp\agent_temp_sweep.py` by hand, then apply again without the flag.
- **Worktree sweep tasks** (the owner's choice: on by default, as the agent temp sweep task is). `kitlib/machinesetup/worktreesweep.py`, planned after the other extras in both modes. Each repository in the machine config's `launcher.repos` gets the scheduled task `<repo name>-worktree-sweep` (the name is the repository's `.kit.json` `repo.name`, else the last part of its remote's URL (`kitlib/git/defaults.py` `repo_name`), else its main checkout's folder name), the task docs/worktree-remove.md describes: daily at 03:00 as the registering user (`-RunLevel Limited`, `-StartWhenAvailable`), the base install's `pythonw.exe` running the carrier and `tools\worktree_remove.py -C <main checkout> --sweep-merged --apply`; the line throws, registering nothing, for a `pythonw` that is not a file or is under `WindowsApps` (`task_line`). The tool is the kit's live main checkout (`tool_root`): `pluginsource.live_root`, else the checkout a plugin export's marker records, else the kit itself when it is no export. A kit in a branch worktree plans no task and notes why; so does a plugin export with neither a live root nor a marker checkout that is there, since a task naming the export runs a folder a later prune removes: the note says to pass `--kit <kit main checkout>`. Two repositories whose names give one task name (different main checkouts) get no task, and a note names both and asks for a `repo.name` of its own in each `.kit.json`; two labels on one main checkout are one repository and get one task. `--apply` registers a missing task by default, after one run of the sweep without `--apply` (under machine setup's own interpreter, 600 s limit, its output prefixed `worktree sweep dry run (nothing removed):`); a dry run that exits any way but 0 stops the run there, registering nothing. A task already registered is left as is unless a path its action runs is in a plugin export folder (a 12-hex folder under `plugin.export_dir`) that holds no export marker any more: that task is registered again with `-Force`. A repository folder that is not there, a task list that cannot be read or a bad `launcher.repos` is a note. `--no-worktree-sweep` turns each change into a note carrying the line. pm-start flags a repository whose task is missing or runs a removed export, and repositories that share one task name (`kitlib.pmstart.worktree_sweep_lines`). Undo with `Unregister-ScheduledTask -TaskName '<repo name>-worktree-sweep' -Confirm:$false`.
- **The kit command:** writes `kit.cmd` in `<plugin.export_dir>\bin` (running the main checkout's `tools\kit.py` with every argument) and appends that folder to the user PATH, keeping the other entries and the value type. Open a new terminal after --apply. In Git Bash type `kit.cmd`. cmd reads `^`, `%VAR%`, `&` and quotes in the arguments again. A kit.cmd that machine setup did not write is left alone (`kitlib/machinesetup/kitcommand.py`).
- **Procwatch task** (opt-in). `kitlib/machinesetup/procwatch.py`. `--procwatch` (`-Procwatch`) registers the scheduled task `Claude procwatch` (`task_line`): every 15 minutes as the registering user (`-RunLevel Limited`, `-StartWhenAvailable`, one run at a time, ended after 10 minutes) it runs `python "<kit>\optional\procwatch\procwatch.py" --log "<agent temp>\procwatch.log"` through the carrier and the base install's `pythonw.exe`, as the sweep task above does, so it opens no window and names no home-folder link. The log is `procwatch.log` in the agents' temp folder the run chose ("Agent temp init"), so the task is skipped with a note when there is none. The task only reports: killing is a second choice, `--procwatch-kill` (`-ProcwatchKill`; a usage error without `--procwatch`), which appends `--kill --only msys-follow,msys-filter,msys-sleep,root-search,msbuild-node,test-host` (`SAFE` in `kitlib/machinesetup/procwatch.py`, the kill-allowlisted rules of `optional/procwatch/procwatch.py`). Each kill class needs its suspect rule plus its own gate (`KILL_GATE` and `LIVE_PARENT_KILL` in `optional/procwatch/procwatch.py`, which hold the ages and conditions); every kill also needs a suspect that is not protected and a creation time re-checked before TerminateProcess. The line is `Register-ScheduledTask -Force`, so a task already there (one made by hand, or before this, running through a home link) is replaced by the kit's definition: the plan says `update`, and a second run with the flag updates it again rather than printing `nothing to do`. `SAFE` is every rule that can kill today, so `--procwatch-kill` does not narrow what a plain `--kill` would end; it only keeps a future kill rule from joining the task without a change here. That includes `root-search`, which `procwatch.py` ends after 10 minutes even when its parent is alive (`LIVE_PARENT_KILL`). A hand `--log` with no file writes `<agent temp>\procwatch.log` too (`default_log`, `optional/procwatch/procwatch.py`), falling back to `~/.claude/logs/procwatch.log` only when no agent temp is set. The line throws, registering nothing, for a `pythonw` that is not a file or is under `WindowsApps`. Undo with `Unregister-ScheduledTask -TaskName 'Claude procwatch' -Confirm:$false`; to keep the old definition, `Export-ScheduledTask` it first.
- **Automatic tasks task.** `auto_task_step`, `kitlib/machinesetup/extras.py`, planned after the procwatch task in both modes. The scheduled task `kit-automatic-tasks` runs `python "<kit main checkout>\tools\auto_tasks.py" tick` every 15 minutes as the registering user (`-RunLevel Limited`, `-StartWhenAvailable`, one run at a time, ended after 10 minutes; `auto_task_line`), through the carrier and the base install's `pythonw.exe` as the sweep task above does; the line throws, registering nothing, for a `pythonw` that is not a file or is under `WindowsApps`. Each tick reads the hub's schedules and starts each due one (`tools/auto_tasks.py`, `kitlib/autotasks`). The tool is the kit's live main checkout (`tool_root`, as for the worktree sweep tasks); a kit that is no main checkout, or one with no `tools/auto_tasks.py`, plans no task and notes why. `--apply` registers it with `-Force`; a task already there with the same program and arguments is left as is. Undo with `Unregister-ScheduledTask -TaskName 'kit-automatic-tasks' -Confirm:$false`.
  - Known limits: it is not verified whether Task Scheduler ends a finished task's child processes, so a started task could be cut short when the tick exits. The launch asks for `CREATE_BREAKAWAY_FROM_JOB` first and starts without it only when that is refused.
- **Agent temp permissions.** On the folder above.
  - The command is `icacls <dir> /inheritance:r /grant:r *S-1-5-18:(OI)(CI)F *S-1-5-32-544:(OI)(CI)F <DOMAIN\user>:(OI)(CI)F`. That leaves other explicit entries, so each one (and any deny entry) is then removed with `icacls <dir> /remove:g <who>` (`/remove:d` for a deny); the plan names them.
  - It runs unless the folder already has no inherited entries, no deny entries, and only SYSTEM, Administrators and the user with full control. Undo with `icacls <dir> /reset`.
  - An empty `USERDOMAIN` or `USERNAME` is refused. The parse reads English `icacls` output.
- **Comfy lock tool.** The user environment variable `KIT_MACHINE_LOCK` = `<kit>\tools\machine_lock.py`.
  - `optional/comfy/comfy_gen.py` otherwise looks for `tools/machine_lock.py` two folders above itself (`MACHINE_LOCK_TOOL`). Run from the kit that is the kit's own; run through a leftover `<config>/tools/comfy` link it is `<config>/tools/machine_lock.py`, which does not exist.

## Default mode

The default (no `--old-kit`; `--fresh` and `-Fresh` say the same) is for any machine with no older kit clone, a new one or one set up before. It only appends: no entry is rewritten into exec form, the only rewrites are a hook path to a retired kit hook script ("Settings") and a path through a tools link ("Settings"), and the only entries removed are the kit SessionStart hooks the kit plugin also runs, by the plugin step once the plugin is enabled ("Plugin: Claude"). The dry run prints the sections links, settings, plugin, owner, extras (`Plan.FRESH_SECTIONS`, `kitlib/machinesetup/common.py`). `--apply` makes the changes in the order the survey adds them (`survey`, `kitlib/machinesetup/__init__.py`): the settings writes, the PM hook, the plugin, the owner's email, the extras.

- **Links.** None are made; each leftover link into the kit is reported as in "Links".
- **Settings: the guard's entry.** In each config folder's `settings.json`, the guard entry `boot/hook.py claude --settings-entry` prints (`boot/hook.py claude PreToolUse`) is appended when no PreToolUse hook names `<kit>/boot/hook.py` and the managed settings file runs no kit's guard ("Managed settings"). It stays there until the plugin carries the guard (docs/guard.md "Go-live"). A missing `settings.json` is created, with indent 2, LF and a final newline; the dry run shows it as a diff from nothing, and `--apply` refuses to replace a file that appeared since the survey. An existing file keeps its layout and gets the `.bak` described in "Settings".
- **PM SessionStart hook** (opt-in). It is written only to the file `--pm-settings` (`-PmSettings`) names: the settings the PM session loads, for example `<PM repo>/.claude/settings.local.json` (docs/pm-start.md "Hook (settings.json)"), a file that repository's `.gitignore` or `info/exclude` keeps out of its commits. The hook runs `boot/hook.py claude SessionStart pm` in exec form with the guard entry's interpreter and the matcher `startup|resume|compact`. Without `--pm-settings` it is a note, not a change. It refuses a file that is an account's `settings.json`, a missing folder, and a file whose SessionStart hook already runs a `pm_session_start.py` other than this kit's. It also refuses when a `pm_session_start.py` hook, under any event, is already in the other file of the pair `settings.json` and `settings.local.json` next to it, or in any config folder's `settings.json`: the PM checklist would run twice (`_pm_hook_elsewhere`, `kitlib/machinesetup/settings.py`).
- **Plugin**, per host (`survey_hosts`, `kitlib/machinesetup/plugin.py`). For each host in `hosts.json`, in order, the host's install step, or a note for a host machine setup does not install. Claude has one (below). Codex has none: `hosts/codex/README.md` says nothing of it is installed or activated on any machine, and its agents and skills are review templates, not installed, so the plan notes `codex: not installed` and names that README. A host gains a step in `installer` once a live install of its plugin is verified.
- **Plugin: Claude.** The plugin is installed from the export of the kit's pushed main, never from the checkout (docs/plugin-source.md), the way `tools/plugin_refresh.py --migrate --apply` does it (`survey`, `kitlib/machinesetup/plugin.py`). A config folder needs it when its `settings.json` has no `enabledPlugins["pm-kit@pm-kit"]`, or has `true` but the export's `state.json` does not record the folder as migrated (an install from the checkout, which `plugin_refresh.py --apply` refuses); the second case is noted. One change makes the export (`ensure_export`, `kitlib/pluginsource/__init__.py`; it runs no `claude` and refuses when the kit checkout has not fetched its remote's main). Then one change per folder runs `refresh` with migrate for that folder: `claude plugin marketplace remove pm-kit` (its failure tolerated), `marketplace add <export root>` and `install pm-kit@pm-kit -s user` through `Runner` (`kitlib/pluginsource/claude.py`), which removes `CLAUDE_CONFIG_DIR` for `~/.claude` and sets it to any other folder. `machine_setup.py --apply` gives `Runner` `run_tree` (`kitlib/machinesetup/extras.py`), which starts `claude` in a job object so a timeout ends its children too. The CLI also rewrites other keys of `settings.json`, so the change first copies it to `settings.json.machine-setup-<yyyymmdd>-plugin.bak`, and afterwards checks the entry is `true`; if a step fails or the entry is not `true`, the run stops there, and the undo text gives the folder's `--migrate --folder` command to run it again. An entry that is `false` or any other value is noted and left. With no `claude` on PATH each folder is a note giving that command. A `--config-dir` folder outside `account_folders` is never installed: `plugin_refresh.py` and `pm_start` would never update it, so it is a note giving the same three `claude` commands and the two update commands to run there by hand, and the export change is still made for it (`_split`, `_outside_note`, `kitlib/machinesetup/plugin.py`). It runs after the settings writes, so the `.bak` holds the guard entry. The export folder comes from the machine config's `plugin` key, by default under `%LOCALAPPDATA%`, on Linux under `<profile>/.local/share` (docs/plugin-source.md).
- **Plugin: Claude, the settings after it.** After the installs, one more change per refresh-set folder whose entry is `true` already or is set by this run's install (`_plan_settings`, `edit_settings`, `kitlib/machinesetup/plugin.py`; the edit is `plugin_edit`, `kitlib/machinesetup/settings.py`):
  - It appends to `permissions.allow` each of `LOCK_ALLOW` (`kitlib/machinesetup/settings.py`) it lacks, exactly `mcp__plugin_pm-kit_machine-lock__lock_snapshot`, `..._lock_run` and `..._lock_hold` (`permissions` and `allow` are made when absent; a `permissions` that is no object or an `allow` that is no list is refused).
  - It removes from `hooks.SessionStart` each `type: command` entry that runs exactly one of the plugin's own SessionStart hooks: the first file it runs that is not a Python interpreter is `<kit>/boot/hook.py` (normalised: slashes and drive case do not matter; `~` and the home variables read as the home folder), the words after it are the same as that hook's, and the plugin's hooks file (`.claude-plugin/plugin.json` `hooks`, `${CLAUDE_PLUGIN_ROOT}` read as the kit) holds it. Today that is `boot/hook.py claude SessionStart` and `boot/hook.py claude SessionStart coordinator`. Such an entry goes only when the plugin's groups running that hook have matchers that, joined, cover every session source (`startup`, `resume`, `clear`, `compact`) its own group's matcher covers (`matcher_sources`, `plugin_sources`, `kitlib/machinesetup/settings.py`): a matcher that is absent, empty or `*` covers all four, plain words joined by `|` cover those words, and any other matcher (a regular expression) is never taken as covered. Otherwise the entry stays and the plan notes it, its matcher and the sources the plugin's does not cover: on a source both cover the hook runs twice, so the owner narrows that matcher by hand (`_kept_note`, `kitlib/machinesetup/plugin.py`). The plugin runs the coordinator hook on `startup|resume|compact`, so a coordinator entry whose group has no matcher, or one with `clear`, stays. The PM hook (`... SessionStart pm`, not in the plugin), another kit's `hook.py`, an entry with other words, an entry written with `${CLAUDE_PLUGIN_ROOT}` and every other event stay; a group or `SessionStart` this removal empties goes, one that was already empty stays. No other hook or allow rule is touched.
  - The dry run shows it as a diff on the file as it is; `--apply` re-reads the file after the CLI's rewrite, refuses (nothing written) unless the entry is `true`, recomputes the edit, and writes nothing when there is nothing left to do. Otherwise it copies the file to `settings.json.machine-setup-<yyyymmdd>-plugin-settings.bak` and writes through a temp file, as in "Settings". A folder whose entry is `false`, a folder outside the refresh set and a folder with no `claude` on PATH whose entry is absent get no change (the last one's note says the edit waits for the install); a `settings.json` that is a link is a note giving the edit to make by hand. A second run plans nothing.
- **Managed settings.** Read, never written: the step notes whether the managed settings file is in sync with the kit's template and, when it is not, names the `--managed-settings --apply` command ("Managed settings").
- **Owner email.** "Owner email" below.
- **Extras.** The agent temp init, the sweep task (unless `--no-sweep-task`), the agent temp permissions and the worktree sweep tasks (unless `--no-worktree-sweep`) run as in "Extras"; the shortcut only with `--shortcut`. `KIT_MACHINE_LOCK` is not set: the plugin's lock tool is used, and the plan notes it.

## Owner email

`kitlib/machinesetup/owner.py`, in both machine modes. The machine config's `owner_email` (docs/kit-json.md "Machine config keys") is the owner's identity for every repository whose `.kit.json` sets no `"owner".email`; with neither, no commit can be proven to be the owner's and every owner-only path refuses every edit (docs/kit-json.md "With no file").

- `--owner-email` (`-OwnerEmail`): stored when the machine config holds another value or none; the change names the value it replaces, and its undo text sets it back.
- None given and one stored: kept, nothing to do.
- None given and none stored: a note, and nothing is stored on its own. `git config user.email`, read in the kit checkout (the user's global value unless the kit checkout sets its own; `Host.git_email`, `kitlib/machinesetup/extras.py`), is only suggested: the note names it and says to confirm it with `--owner-email <it>`. A git identity can be any address, an agent's among them, so it is never stored unconfirmed. With `--apply` in a console (stdin and stdout a terminal), `tools/machine_setup.py` asks first (`needs_prompt`, `suggestion`): `y` stores the suggested address, a typed address stores that, and an empty answer or `n` stores nothing. With no console (a redirected run), nothing is asked and nothing stored.
- A value that is not an email address is refused when given, and a note when found in git config.
- Only the owner runs it to act: the guard's `owner-tool` rule denies `machine_setup.py --apply` (and its front ends' `-Apply`) to every other session, and the write jail denies an agent session's edit of the machine config (docs/guard.md "Owner machine setup").

The write keeps the machine config's other keys and its layout (`kitlib/machinesetup/machineconfig.py`, shared with the sweep key below): it refuses a file that changed since the survey, and puts the file back when the machine config cannot be read after it. The two keys planned in one run both land: each write moves the run's snapshot of the file on to what it wrote. A machine config still only in the home folder (`UNMOVED`) is refused (`kitlib.config.user.writable_file`). With no PM repo pointer there is no file to write: a given `--owner-email` refuses, nothing changed, naming the `--pm-repo` step ("PM repo pointer"), and `--apply` in a console asks nothing (`needs_prompt`).

## Managed settings

`kitlib/machinesetup/managed.py`. Claude Code loads `%ProgramFiles%\ClaudeCode\managed-settings.json` (on Linux `/etc/claude-code/managed-settings.json`, written as root or with sudo) for every account on the machine, above each account's own `settings.json`. The path is the default host's: its adapter's optional `managed_settings_path()`, which `Host.managed_path` asks for with getattr; a host without it has no managed file, and this mode notes nothing to install. The shared settings (the guard's hook, the status line, the plugin's marketplace, permissions, auto mode) live there, so an account's `settings.json` needs none of the kit's. The template holds the marketplace (`extraKnownMarketplaces`) and `enabledPlugins` for the plugin. `tools/plugin_refresh.py` refresh and migrate read each account's own `settings.json` and the export's `state.json` record of migrated folders (`kitlib/pluginsource`), never the managed file: the plugin step installs and migrates each account whether or not that file enables the plugin.

- **The template.** `hosts/<default host>/managed-settings.json` in the kit (`source()`; `hosts/claude/managed-settings.json` today), a JSON object the kit commits. The kit is the main checkout, never a plugin export (`managed.stable_kit`): each plugin refresh replaces the export folder, so a guard hook or status line naming it would go stale. A `--kit` that is an export stands for the checkout its `.pm-kit-export` marker records, whose template is read; one whose checkout has moved or gone is refused (`this is an export; pass --kit <kit checkout>`). A managed file rendered from an export is still this kit's guard ("In the other modes") and is re-rendered. When the owner moves the checkout, the next export records the new path, and `--managed-settings --apply` is run again; until then the hook names a missing file and Claude Code blocks every guarded tool call (as in "Settings"). In every string, `{kit}` becomes the kit folder (forward slashes), `{pythonw}` the interpreter of the guard entry `boot/hook.py claude --settings-entry` prints (the interpreter that ran setup: under sudo on Linux, root's `python3`, such as `/usr/bin/python3`), and `{plugin_export}` the plugin export root (the machine config's `plugin` key, docs/plugin-source.md). A path through `<config>/tools/<link>` is then re-pointed to the kit's own file, as in "Settings". A kit with no template is a note and nothing to do. Off Windows the `WINDOWS_ONLY` keys (`statusLine`, a PowerShell command) are dropped from the template, though an overlay may add one. A hook running this kit's guard with no `onFailure` gets the guard entry's, from the same source as the account entry (`hookmain.ON_FAILURE`): on Linux `"block"`, so the guard blocks a call when its interpreter cannot start.
- **The overlay.** `<config-dir>/managed-settings.json` (`OVERLAY`, in the machine config folder, the PM repository's `.pm-kit`, git-ignored; absent by default) holds what the committed template must not: the agents' git identity and the auto-mode lines that name the owner, accounts or home paths. It is merged over the rendered template: an object key by key, anything else (a list, a string) replaced. It must be a JSON object, and its `env`, when there, an object of strings; otherwise the run is refused. The machine config's own reader never reads it.
- **`--managed-settings`** (`run_managed`, `survey`). A dry run prints the diff from the file as it is to the rendered template; `--apply` writes it. The run is refused under `--apply` unless the process is elevated (`Host.is_admin`): the file is under Program Files, and nothing elevates itself. A new file is made, folder too, in indent 2 and LF; an existing one keeps its layout and is replaced whole, so it is refused when it is no JSON object or holds a key at any depth that neither the template nor the overlay has (the refusal names each by its dotted path: add them to the template; values inside lists are not walked), except a retired key: `managed.RETIRED` lists the top-level keys the template dropped on purpose (`effortLevel` and `modelSettings`, dropped in the commit "Managed settings: drop effortLevel and modelSettings"), which the replace drops, the plan line naming them (`drops the retired key(s) ...`) and the diff showing them removed; a key is added to that tuple in the commit that drops it from the template. The file is copied to `managed-settings.json.machine-setup-<yyyymmdd>.bak` first, and is refused when it changed since the survey or is a link (hard or symbolic). The write keeps the existing file's key order, so the diff shows only real changes. A missing overlay prints a `WARNING` line naming the file looked for; with no usable PM-repo pointer there is none to name (`managed.overlay_path` is None, the home folder holds no overlay) and the line says `<PM repo>/.pm-kit/managed-settings.json` and the `--pm-repo` step. The file sits in `ClaudeCode` under `%ProgramW6432%`, else `%ProgramFiles%`. A template without this kit's guard entry is noted: each account then keeps its own. A second run prints `nothing to do`.
- **In the other modes** (`survey_live`, `note_sync`). The managed file is read as it is, never written. It decides the guard ("Settings") above; the plugin step does not read it. One that is there but no JSON object is refused: machine setup cannot tell whether it carries the guard. The default and `--old-kit` runs note whether it is in sync with the template.

## PM repo pointer

`kitlib/machinesetup/pointer.py`; `tools/machine_setup.py --pm-repo PATH [--kit DIR] [--apply]` (`run_pointer`, `survey`). It sets the PM-repo pointer, `HKLM\SOFTWARE\pm-kit` value `pm_repo` (REG_SZ, 64-bit view), to PATH, and nothing else. What the value means and how it is read is docs/kit-json.md "The PM repo pointer".

- **Checked first.** PATH is normalised and checked as the reader checks it (`kitlib.config.pointer.check`): absolute, an existing folder, the top of a git work tree, on the PM data branch when the repository records one (else the main checkout). Any failure is refused with the reason, before anything else, so the pointer is never set to a value the reader would call `BAD`.
- **Elevation.** The value is under HKLM, so `--apply` is refused unless the process is elevated (`Host.is_admin`); the refusal names the command and the `reg add` that does the same by hand. Nothing elevates itself. A dry run notes that `--apply` would be refused.
- **The plan.** One change: set the value, or replace the one there (named). Its detail line is the `reg add` that does the same by hand; the restore line is `reg delete "HKLM\SOFTWARE\pm-kit" /v pm_repo /f /reg:64` for a new value, or the `reg add` of the old one. A value already equal to PATH is nothing to do. A value there that cannot be read (for example a REG_EXPAND_SZ) is noted and replaced, with no restore line: it is not absent, so `reg delete` would be wrong, and the note says to record it first (`reg query`).
- **Under the kit's tests** the registry is never written: `Registry.write` raises when `kitlib.config.user.fenced()`.

## Linux

`installer/machine-setup.sh` is the Linux front end (it refuses on any other system), run with `sh`. It takes the default mode's `--owner-email`, `--pm-settings`, `--config-dir`, `--agent-temp`, `--no-sweep-task`, `--shortcut` and `--apply`, or one of two root modes, run with sudo, that take only `--python` and `--apply`; it runs the tool under `--python FILE`, else the `python3` on PATH. Ubuntu 24.04 is the reference box; git, python3 and tmux are needed (docs/linux-support-plan.md section 6). Stock Ubuntu has `python3` only, so on Linux read every `python tools/machine_setup.py ...` in this file as `python3 tools/machine_setup.py ...`.

1. `sudo sh installer/machine-setup.sh --pm-repo PATH --apply`: the pointer is the root-owned file `/etc/pm-kit/pointer` ("PM repo pointer"). Declining sudo, the dry run prints the line that writes the user's own pointer file, `~/.config/pm-kit/pointer`, instead.
2. `sudo sh installer/machine-setup.sh --delegation --apply` (`kitlib/machinesetup/delegation.py`): the one root step. It writes `/etc/systemd/system/user@.service.d/pm-kit-delegate.conf` (`Delegate=cpuset cpu io memory pids`), runs `systemctl daemon-reload`, and writes `/etc/pm-kit/kit-user`, the box's one kit user (`<uid> <name>`, the user who ran sudo). Sign out and in once: the user manager takes the delegation when it starts again. It may be declined: the box then runs at the lower tier it allows, shown as such. With no systemd it is a boot hook instead, when the box has cgroup v2 and either OpenRC's `local` service (`/run/openrc` and `/etc/local.d`) or `/etc/cron.d` (runit and s6 are refused; root's own crontab is never touched): it writes `/etc/pm-kit/cgroup-boot` (0755), a fixed sh script with the kit user's uid, gid and home written in, which makes the cgroup `/pm-kit` with the leaf `/pm-kit/anchor`, turns on the cpuset, cpu, memory and pids controllers, gives the two folders and their delegatable files to the kit user, moves itself into the anchor and, dropped to the kit user (no supplementary groups), starts the kit's tmux server (`tmux -L pm-kit`) there with the session `pm-kit-anchor`, whose one window is a small python3 that only waits (no shell to `exit`), and the server option `exit-empty off`, so the server outlives its sessions; a server already answering on the kit's socket from outside the anchor is refused, never used. Then its entry, `/etc/local.d/pm-kit-cgroup.start` (0755; with `rc-update add local default` when `local` is in no runlevel) or `/etc/cron.d/pm-kit` (0644, `@reboot root`); then it runs the script once, so no reboot is needed. Every binary the script runs, and every path it writes, must be root's alone and no link, or it is refused; a tmux older than 3.2, or one whose `tmux -V` names no version, is refused too (the launcher opens its windows in the kit's server with `new-session -e`, which 3.2 added; Debian 11 and Devuan 4 ship 3.1c). Work started from the kit's tmux server (`tmux -L pm-kit attach -t pm-kit-anchor \; new-window`: attach never starts a server, and the work gets a window of its own; the launcher opens its windows there) gets strong containment, its jobs made in `/pm-kit`; work started from any other shell stays at the lower tier and says why. Only root starts the kit's server in the anchor: when it has ended (`kill-server`, or a crash), a run of this step with the hook in place runs the script again, when `/sys/fs/cgroup/pm-kit/anchor/cgroup.events` says `populated 0`, when no tmux runs in the anchor, or when no `pm-kit-anchor` window holds it; the script starts only what is missing. The other way back is a reboot. Never start `tmux -L pm-kit` from a shell yourself: it is not contained, and the script then refuses to start the kit's server until it is ended. Undo: `sudo rm -f /etc/local.d/pm-kit-cgroup.start /etc/cron.d/pm-kit /etc/pm-kit/cgroup-boot` (and `sudo rc-update del local default` when it enabled `local`); the cgroup goes at the next reboot. After this step the kit never asks for root or credentials and never runs sudo. It is refused with no systemd and no such route, in WSL, from root's own login (no `SUDO_UID`), and when the marker names another user.
3. `sh installer/machine-setup.sh --agent-temp DIR --apply`, as the kit user (it refuses root): the default mode. Linux has no default agent temp folder (it must be outside the home folder and every checkout), so without `--agent-temp` that step is a note. The box checks come first, in the `box` section (`kitlib/machinesetup/linuxbox.py`): WSL is refused; a marker naming another user is refused, and without the marker another user's kit state is a warning; a container is a warning (never strong containment there); a missing git or tmux is a note; the containment tier is probed, and below S1 the delegation step is offered. The Windows-only steps have Linux forms: the user environment is `~/.config/environment.d/pm-kit.conf`, the agents' temp folder is made mode 0700, the shortcut is `~/.local/share/applications/pm-kit-machine-schedule.desktop`, the kit command is `~/.local/bin/kit` (mode 0755, `exec python3 '<kit>/tools/kit.py' "$@"`; a note when that folder is not on PATH), and a leftover link's removal command is `rm -- '<path>'`.

`tools/kit.py` runs on Linux; it refuses WSL (the kernel release names Microsoft) and every other system, darwin among them.

## Dev Drive (owner steps)

Machine setup does none of these: each is a hand step for the owner, done once per machine.

- **Set `dev_drive`** in the machine config (docs/kit-json.md "Machine config keys") to the Dev Drive's root folder, once the kit, repositories, worktrees, `AGENT_TEMP` and every `guard.data_roots` and `guard_mark_roots` folder are on it. From then on the guard holds every agent write to the drive (docs/guard.md "Write jail", "Outer bound"); until then every session start warns that the bound is off.
- **Move the tool caches onto the drive.** The guard does not see a program's own writes ("Known limits"), so a cache left on the system drive keeps growing there. Set each as a user environment variable to a folder on the Dev Drive, then open new terminals and sessions:
  - `PIP_CACHE_DIR` (pip);
  - `npm_config_cache` (npm);
  - `NUGET_PACKAGES` (NuGet's global packages folder);
  - `DOTNET_CLI_HOME` (the .NET CLI's home folder: tools, first-run files);
  - `UV_CACHE_DIR` (uv), `CARGO_HOME` (cargo) and `GRADLE_USER_HOME` (Gradle), where used;
  - Godot's editor data and cache (`%APPDATA%\Godot`): run Godot in self-contained mode (a `._sc_` file beside the editor binary on the Dev Drive), where used.
- **Not moved by a variable:** `git config --global` writes `~/.gitconfig`, and other tools write `%APPDATA%` and `%LOCALAPPDATA%`; these stay on the system drive.

## Not done here

- **Removing links.** Every leftover link is reported with its removal command ("Links") and left for the owner to remove. Other links into the older kit clone, for example `agents` and `hooks`, are noted and left: the plugin replaces agents, and the launcher starts the agent `launcher.coordinator_agent` names (docs/launcher.md "Settings").
- **The plugin install, with `--old-kit`.** `machine_setup.py --old-kit` installs no plugin (the default mode does, in "Default mode"). `tools/plugin_refresh.py --migrate --apply` adds the export of pushed kit main as the `pm-kit` marketplace in every account folder and installs the plugin from it; `--folder DIR` migrates one folder first (docs/plugin-source.md "Migrating").
- **Scheduled tasks.** Ones that run old-kit scripts are not scanned. Only `agent-temp-sweep` (not with `--no-sweep-task`) and each launcher repository's `<repo name>-worktree-sweep` (not with `--no-worktree-sweep`) and `kit-automatic-tasks` are registered by default with `--apply`, and, in the default mode and the old-kit mode alike, the procwatch task when `--procwatch` is given ("Procwatch task" in Extras).
- **Skills as a plugin.** The plugin loads the kit's skills; a leftover skill link loads each one a second time, so it goes once the plugin is enabled (docs/install.md "Existing installs").
