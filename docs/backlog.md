# backlog.py

The backlog's reads and writes: `tools/backlog.py` (entry) over `kitlib/backlog` (library). docs/backlog-store.md is the design; this page is the behaviour. Not live until reviewed.

A program opens the configured store the way the tool does with kitlib/backlog/opener.py `open_store(root, fetch=True, session=None, branch=None)`, which returns the plan Context (its `store.load()` reads), and maps a write verb to its plan with `planner` (a verb that is no write is `USAGE:`, raised before any plan runs); opener.py `retarget_dry` returns the Change a `retarget` without `--apply` would write. `kitlib.backlog.open_store` is the same function: kitlib/backlog/__init__.py `__getattr__` imports it from opener.py on first use, so importing another backlog module does not also load the config and plan code.

## Stores

`.kit.json` `"backlog".store` picks the backend (kitlib/backlog/store.py `open_backend`):

| Value | Records live in |
|---|---|
| `ref` | `backlog/<ID>.md` on `refs/backlog/main`, which shares no history with main |
| absent | the same `ref` store, read-only |
| `branch` | the same tree on a `backlog` branch |
| `main` | `docs/backlog/<ID>.md` in the checkout; any other value is that folder |

The `ref` store reached by the default alone (neither `.kit.json` nor `migrate --to` names a store: `Config.written`) reads as usual, and every write to it is REFUSED, exit 2, before anything is built (`RefBackend.publish`, `implicit`). A repository could otherwise write records to a ref nobody reads, beside its live store: the kit's own records were once written to a stale `refs/backlog/main` while its live store was the PM data worktree's folder. The refusal (`store.default_store_refusal`) names the PM data worktree and its store to write to with `-C` when the repository has one whose `.kit.json` names a store (`store.pm_data_live_store`); one that names none reads the same ref, so the refusal says it names none and a write there is refused too; the checkout itself is never offered; a PM data worktree not found, or whose `.kit.json` cannot be read, is named as the reason. It always says to set `"backlog": {"store": "ref"}` to write the ref store. `tools/machine_setup.py` writes that setting into a repository it sets up (`kitlib.machinesetup.repo`). A landing never writes the default store (`at_landing._close_in` only reads it), so a refused close at a landing keeps the store's plain command (`at_landing._refused_advice`). Tests: `tests/backlog/test_store_default_ref.py`.

A ref or branch write (`Store.write`) loops: fetch, plan against that snapshot, validate, build the tree in a temporary index, `commit-tree` on the fetched tip, then `push --force-with-lease=<ref>:<tip>`. With no remote it runs `update-ref <ref> <new> <tip>`. A lost race (including `cannot lock ref`, read from both of the push's output streams) reruns the whole attempt, plan included, up to `ATTEMPTS` (5); after that it is ERROR and nothing was written. A push that exits non-zero yet left the remote at or past the new commit (kitlib/git/refs.py `is_ancestor`) succeeded and is not re-planned; one rejected with the remote unmoved is ERROR. When the remote or the fetch that would tell cannot be read after a failed push, the ERROR says the write may have landed: read the store (`check` fetches it) before retrying (`RefBackend._maybe_landed`). Without a remote, an `update-ref` that fails or times out after the ref already moved to the new commit succeeded. After a push the local copy of the ref moves only as a fast-forward (`RefBackend._advance_cache`). A write is refused only for what it adds: a FAIL `check` would report (`check.fail_findings`), or an `item:` blocker naming no record (`check_change`), so a store that is already broken can still be repaired. Writes never touch the checkout. A fetching read adds the store's fetch refspec (`+refs/backlog/main:refs/backlog/main` for `ref`) to the remote once (`RefBackend.ensure_refspec`), and refuses when the remote has no store but the local ref holds one. The commit body carries `Session:` and, when the write cites one, `Ruling: PM R-nnnn`.

No remote means `git remote get-url <remote>` exits 2 and the repository lists no remote at all (`find_remote`); a missing remote beside others, or a lookup that fails any other way, is ERROR.

The `main` backend writes files. It has no compare-and-swap on the files: a write checks that each record it rewrites still holds the bytes it read, then writes. So it writes only in a linked worktree and refuses in a main checkout (`MainBackend.publish`). Outside the PM data branch's worktree it commits nothing (landing carries the files).

In the worktree that has the PM data branch checked out (`MainBackend.commit_branch`: kitlib/pmdata `read` names the branch and HEAD is that branch), each write commits its own record paths and nothing else (`MainBackend._commit`). Each such write first takes git's own lock on that worktree's index, `<index>.lock` made exclusively as git makes it (`MainBackend._lock_index`, `store._IndexLock`), before it reads HEAD's commit or checks the files, and holds it until its index update: meanwhile a `git commit`, `git add` or `git reset` there fails with git's "index.lock': File exists", so none commits an index that does not yet hold the write (which would revert it), and another `backlog.py` write there waits for it. A lock still held after `INDEX_WAIT` (2 s) is ERROR, `errors.Busy`, with nothing written; that lock file is another command's and is never removed. A commit that moves HEAD without the lock (by plumbing alone, `update-ref`) is the one other commit a write can still meet, and the compare below stops it. The blobs are hashed before any file is written; each file is written whole or not at all (`store._replace_file`, below; `MainBackend._write_files`), and a file that fails to write is left as it was, puts the others back (the same way, `MainBackend._restore`) and is ERROR naming its path and any file that could not be put back. A temporary index then takes HEAD's tree plus those paths, `commit-tree` parents it on HEAD, and `update-ref HEAD <new> <old>` moves the branch, retried on a moved or locked HEAD up to `ATTEMPTS` (5). Every attempt, the first included, stops, ERROR and uncommitted (`errors.Overtaken`, an `Uncommitted`), when a commit changed any of the write's paths on HEAD since the write began: `MainBackend.publish` reads HEAD before it checks the files against what it read, and `MainBackend._publish_commit` compares the paths at that HEAD and at the one it builds on. So a write never commits over another session's commit of the same record that landed after `publish` read HEAD. A commit that landed before that read is not seen by the compare: only the files check stops it, when the file on disk differs from what the write read. The refused write then puts each file it wrote back (`MainBackend._put_back`): a path the other commit changed (`Overtaken.changed`) to what that HEAD holds, removing one HEAD lacks, so a read and the next write see the other commit's record; any other path of the write to the bytes it held before the write, a deleted file included, so a record that was uncommitted stays as it was and `catch-up` still lists it. Between the write and the put back a reader of the folder sees the refused content. It touches a file only while the file still holds exactly the bytes the write wrote, and fetches HEAD's content first so that no git call sits between that check and the write; the folder has no compare-and-swap, so a change to the file between the check and the write is still overwritten (a stated residual). The content goes in whole or not at all (`store._replace_file`: a file beside it in the store folder, `<ID>.md.<random>.put-back`, which no reader takes for a record, then `os.replace`, retried for `REPLACE_WAIT` while Windows refuses it because another process has the record open; a temp file it cannot remove is named in the error), so a put back that fails leaves the file as the write wrote it, never a part. Any other file is left, the message names it with `git -C "<worktree>" diff HEAD -- "<path>"...` to compare first (`Overtaken.left`, `Overtaken.compare`), and it gives no ready-made `catch-up --apply` command. A write that read another session's file before that session committed it is refused the same way, though it would have overwritten nothing: that false refusal is accepted, and the write is repeated. When `publish` cannot read HEAD at all the ERROR says nothing was written. The real index then takes those paths only, so other staged or pending work is left as it was: a copy of it in the lock file, its mtime kept, is updated (`GIT_INDEX_FILE`) and moved over the index (`MainBackend._sync_index`, `_IndexLock.install`), which gives the lock up; a move Windows refuses (a reader has the index open) is retried for `REPLACE_WAIT` (1 s). A write that leaves the tree unchanged commits nothing. The commit message is the one a ref write uses (`Session:`, `Ruling:`). A commit that fails after the files are written is ERROR (`errors.Uncommitted`) naming the paths and `catch-up`. A commit that lands with the real index not updated (that update or that move failed; the lock file is then removed) is `errors.IndexStale`: HEAD has the commit, a plain `git commit` in that worktree would revert it, and the message gives the repair, `git -C "<worktree>" reset -q -- "<path>"...`, or `git -C "<worktree>" reset -q` for the whole index when that worktree has no index file (a reset of some paths would build an index of those alone, every other file then a staged deletion). tools/backlog.py reports that write as written: the `WROTE` line (`CAUGHT UP` for `catch-up --apply`), then a `WARNING:` line carrying the message and the repair, exit 0 (`do_write`, `do_catch_up`). Every path in a printed command is in double quotes (`store.quoted`). These git calls drop an inherited `GIT_INDEX_FILE`, `GIT_DIR` and `GIT_WORK_TREE` (`store._store_env`), so a hook's environment never redirects them. A backend opened with `clean` (`open_backend(..., clean=True)`, which only a landing's close uses: `at_landing.pm_data_store`) first requires each path the write would change to match HEAD in that worktree and its index (`MainBackend._require_clean`, after it reads HEAD and before it checks or writes any file): a hand edit, a staged change or a record file never committed there is ERROR, `errors.Dirty`, with nothing written, naming those paths and `git -C "<worktree>" diff HEAD -- "<path>"...` to compare (`git status --short` instead when one is not in HEAD). When the worktree holds HEAD's content for each such path and only the index differs (an `IndexStale` left unrepaired, or HEAD moved by plumbing; `MainBackend._index_only`), the `Dirty` gives the index repair instead of a compare (`Dirty.repair`: `git -C "<worktree>" reset -q -- "<path>"...`, or `git -C "<worktree>" reset -q` when there is no index file). A `backlog.py` write is not `clean` and still writes over such a change. Tests: `tests/backlog/test_pmdata_commit.py`.

A pulled record holds its current `scope:` lines, never its branch's diff, so narrowing them with `set ID --scope P` frees the rest (`tests/backlog/test_pull_holder.py`). Taking scope a live pull holds is the PM's call: a `pull` over one, a dead-pull takeover over one, and a `set --scope` that widens a pulled record into one each need `--ruling R-nnnn` (Owner gates).

### The fold-in guard

A finding is fixed on the branch that found it unless it cannot be, so `add` names where it came from and why it was not folded (kitlib/backlog/plan.py `plan_add`, `_fold_arguments`, `_fold_overlap`; `tests/backlog/test_add_found_on.py`). `--found-on` is the branch the finding was made on, or `none` when no branch found it or the branch that found it was removed, landed or not (then `--why-not-folded` names that branch). A removed branch that landed may instead be named: its landing merge on the code main is the proof that lets it stand in for `none` (below); one removed without landing has no such proof and is written as `none`. `--why-not-folded` is at least 12 characters with no machine path. Both are appended to the summary, `S (found on BRANCH; not folded: T)` (`no branch (or on a branch since landed)` for `none`), and the commit subject is `backlog: add ID, found on BRANCH`.

- USAGE: either flag missing, a short reason or one holding a machine path, a malformed branch name, `--found-on` naming the code main (`backlog.code_main`, default `repo.main_branch`) in any letter case or ref spelling: a finding on main has no branch, so write `none`; or `--found-on` spelt as a ref (`refs/heads/<x>`, `heads/<x>`, `refs/remotes/<remote>/<x>`, `remotes/<remote>/<x>`, `<remote>/<x>`, the prefix in any letter case): write the local branch name (`kitlib/backlog/plan.py` `_bare_branch`).
- REFUSED: a scope member that overlaps (`kitlib/backlog/scope.py` `members_collide`) a path the branch changed since its merge base with the code main (`git diff --no-renames --name-only`), or the scope of a record the branch holds pulled (`pulled_by` compared in any letter case). A member that cannot be compared counts as an overlap. The refusal lists each pair and says: fold it into the branch, or file it after the branch lands. There is no override flag.
- REFUSED: a `--found-on` branch that is neither a local branch, nor a branch of any remote as last fetched (kitlib/backlog/plan.py `_remotes_with`; every remote is asked, no network), nor a branch with a `Merge B` merge made on the code main (`landing_merge`: `git log --merges --first-parent`, so a `Merge B` merge brought in inside another branch is no proof). The refusal says to pass an existing branch, or `none` for one removed without landing, with the branch named in `--why-not-folded`. A git that cannot list the refs or remotes or read a ref is ERROR, never this refusal.
- A branch only remotes have is diffed at each remote's tip, labelled `R/B`, and prints `NOTE: branch B is not a local branch; its diff was compared as last fetched from R` (`_branch_tips`). A landed branch prints `NOTE: branch B landed on M as SHA SUBJECT; its diff was not compared`. Either way the scopes of records it holds pulled are still checked.
- Ref names are matched in any letter case against git's own list (`_ref_names`, `_spelling`), so a packed ref is found as a loose one is. USAGE: two refs that differ only in letter case, which this file system cannot tell apart: rename one.
- ERROR: a code main that does not resolve (also for a branch found nowhere, whose landing merge then cannot be looked for), no merge base with it, a git that does not answer, or an unreadable record. The ERROR for a missing base names `backlog.code_main` (docs/kit-json.md).
- `--found-on none` skips the overlap check.
- The code main is read as `<code remote>/<code_main>` as last fetched, else the local branch (`kitlib/backlog/plan.py` `_code_main`, by `refs.default_base`; `plan.Context.code_remote`), so a local main that lags its remote gives no false overlap and misses no landing merge. The code remote is `repo.remote`, except in the PM data worktree (`kitlib/backlog/pull_branch.py` `code_config`), where it is the main checkout's `repo.remote` and an unset `backlog.code_main` is the main checkout's `repo.main_branch` (`kitlib/backlog/opener.py` `open_store`; `tests/backlog/test_add_found_on.py` `FoundOnInThePmDataWorktree`). The same code main serves `pull`'s guard below.

`pull` runs the same guard against the other live pulls (kitlib/backlog/plan.py `_pull_fold_hits`, called by `plan_pull`, `_plan_takeover` and `plan_set`; `tests/backlog/test_pull_fold_guard.py`). So does `set ID --scope` on a pulled record, for the members it adds only (the record's own branch is never compared): an overlap is REFUSED unless the call carries `--ruling R-nnnn`, and a write with one prints the fold (`folds into the work of B on R-nnnn: ...`); an open record is not checked. It fails closed as `pull` does: a git that cannot read another live branch or its merge base makes the `set` an ERROR and nothing is written, where before the guard such a widening was written. A record's declared scope can miss what its branch has actually changed, so the collision rule above cannot see that work.

- REFUSED: a scope member that overlaps a path changed since the merge base with the code main (as for `add`) on the branch of any live pull other than the caller's (`pulled_by` compared in any letter case; each branch is diffed once). A member that cannot be compared counts. The refusal lists each pair and says: fold it into that branch, or pull it after that branch lands. Overriding it takes `pull ID --reason T --ruling R-nnnn`, checked and recorded in `preempt` the way a live-pull collision is; `next` passes such a record over (`_offer_folds`), and `plan_pull` raises this refusal before the not-in-the-offer one, so the refusal names the fold. A dead-pull takeover takes `--ruling` alone.
- A code main that does not resolve in the store's git (a store whose git is not the code's) skips every diff with `NOTE: code main X does not resolve here; branch diffs not compared`. A live branch that shares no history with the code main (the code main is not that branch's history, as when `backlog.code_main` is unset in a store whose main branch is its own, docs/kit-json.md) is skipped with `NOTE: code main X shares no history with B; set backlog.code_main; branch diffs not compared`. A live branch only remotes have is diffed as for `add`, with its NOTE; one neither here nor on a remote is noted and not compared. Unlike `add`, which ERRORs on a code main that does not resolve or shares no history, these never block a pull.
- ERROR: a git that cannot read the code main or a branch, cannot answer the merge-base question (any failure other than a confirmed "no common history", `kitlib/git/refs.py` `merge_base`), or cannot diff. `next` turns the same failure into a pass-over, never an ERROR (`_live_changes` reports it per branch; `_offer_folds`).

### Stopping a pull

`block ID --on M --reason T` and `release ID --reason T` stop a pull (kitlib/backlog/plan.py `stop_pull`; `tests/backlog/test_block_stopped.py`). Its holder (the caller's branch) may stop it. Anyone may when the pull is dead (no branch or worktree by its `pulled_by`), or when `Context.liveness` finds the worktree on that branch dead: tools/backlog.py's opener passes kitlib/worktree/classify.py `branch_liveness`, `--classify`'s L rule for that one tree (docs/worktree-remove.md "Classify"). Otherwise it is REFUSED, naming why the tree is live; a branch no worktree is on, or one the probe cannot read, counts as live.

- One store commit clears `pulled_by`, `pulled_at` and the pre-emption keys, which frees the scope. `block` sets `state: blocked`, `release` sets `state: open`.
- While the branch exists, a body line `Stopped on branch B at <tip>, branch kept.` goes on its own line, before the `Blocked on M (date): T` or `Released (date): T` line, so a ruling cited in the reason still counts for `check`'s hold citations (`record.hold_citations` reads lines that start `Blocked on`). The output names the branch and tip on a `branch kept:` line. A part landing's release (`at_landing._release_plan`, `kept=False`) writes no Stopped line and reads no branch: the landing's cleanup deletes it. The branch and its worktree are never touched.
- `block` of a pulled record without `--reason` is USAGE.

### Retarget

`retarget OLD NEW` follows a moved file or folder through the store (kitlib/backlog/retarget.py `plan_retarget`; `tests/backlog/test_retarget.py`). OLD and NEW are plain repo-relative paths. USAGE: a glob in either, `none` in any case (`NONE` too), a control character (a line break would split a record line), a machine path, OLD equal to NEW, or one under the other (`a` to `a/b`; retarget through a path outside both). Matching is case-sensitive and by whole path components, so OLD `docs/guide` never touches `docs/guidebook.md`.

- `scope:` lines. A member equal to OLD becomes NEW. A member under OLD has that prefix replaced, the trailing `/**` included: with OLD a folder, `OLD/a.md` becomes `NEW/a.md` and `OLD/**` becomes `NEW/**`. A rewritten member the record already holds is dropped, not written twice. Listed as `not rewritten` and left alone: a member that covers OLD from above (`docs/**` or `docs` when OLD is `docs/guide`), since narrowing it is a judgement for `set ID --scope`; and one that matches OLD only when case is ignored (`Docs/Guide/a.md`), which the store's casefolded collision checks treat as the same path but a rename never guesses.
- `ref:` and `summary:` lines. OLD is replaced wherever it stands as a whole path: not preceded by a path character, and followed by the end, a `/` (a path under OLD) or a character that cannot continue a path (a sentence's full stop counts). An OLD with no `/` (`tools`) is replaced only where a `/` follows it; a line where it stands as a bare word is listed as `not rewritten`.
- Nothing else changes: `area`, `files` and the body are left as they are.
- A pulled record whose `scope:` lines it would rewrite is REFUSED while its branch is live (its holder releases it, or retarget after it lands; one refusal names every live record the retarget touches), and ERROR when git cannot say whether the branch is live; nothing is written. A dead pull's scope is rewritten, and a live pull whose only change is a `ref:` or `summary:` line is not checked (kitlib/backlog/plan.py `_refuse_live_pulls`; `tests/backlog/test_retarget.py` `LivePulls`).

The dry run plans against a fresh read and runs the same checks a write does. `--apply` writes every changed record in one store commit, `backlog: retarget OLD -> NEW in N record(s)`; with nothing to change it writes nothing.

## Owner gates

An owner price (`--priority-by owner|pm`), an owner hold (`blocked_on: owner`, `priority: -1`), and closing, retiring or deleting such a record take `--ruling R-nnnn`; for a retirement or a deletion the ruling alone satisfies the owner check and nothing of the owner's is written into the record. A cited id is taken on its word: no write and no `check` reads the rulings ledger, whatever the machine config names (`_check_ruling` in kitlib/backlog/plan.py, `check_store` in kitlib/backlog/check.py). A ruling is refused only for its shape (USAGE), for the id the record already carries as `priority_ruling` (one ruling, one change), for an id the record already spent on a hold release, or, on a price change, for the record's own `hold_ruling`. A `close` citing the record's own live `hold_ruling` is not checked at all (`plan_close`). An out-of-order `pull --ruling` records the ruling as `(PM R-nnnn)` after its reason (`plan_pull`). A pull of a held record (`priority: -1`) is the `pull-held` row, which no role may take (Roles), so a `--ruling` on the pull never releases the hold: release it first with `set ID --priority N --ruling R-nnnn` (the `set-hold` row: the owner or the PM), then pull.

A collision with a live pull - a pulled record whose `pulled_by` branch git still finds; a failed probe holds every pull - on another branch takes the PM's ruling, never `--reason` alone (kitlib/backlog/plan.py `live_hits`; `tests/backlog/test_pull_collision_ruling.py`). A colliding pull is REFUSED without `--ruling` and the refusal names each pair and its holder; with one it records `(PM R-nnnn)` after its reason. A held record that collides is still `pull-held`: its hold is released first (above). A dead-pull takeover that collides takes `--ruling` (and still no `--reason`; a `--ruling` on one that collides with nothing is USAGE). A `set --scope` on a pulled record checks only the members it adds (`widened_members`: a member is covered by an equal one or by an old `X/**` above it; `none` covers only `none`): with any of them colliding it is REFUSED without `--ruling`, and that ruling cannot also move a price or release a hold (USAGE, one ruling, one change). Narrowing, and widening into free scope, need nothing. A `--ruling` given on a free widening is still checked and recorded (`widened on R-nnnn: no live pull collides now`), since the collision a refusal named can clear before the retry; one on a narrowing or an unchanged scope is USAGE. Each of these messages names the form `set ID --scope <path> [--scope <path> ...] --ruling R-nnnn` (`plan.WIDEN_FORM`). A live pull on the same branch is no collision: the caller's branch for a pull or a takeover, the record's own `pulled_by` for a `set` (overlapping records bundled onto one branch; `live_hits` `branch=`). The ruling is checked as a hold release's, and the commit carries its `Ruling:` line. A collision with a record that is not pulled (another session's, or one higher in the offer) still needs only `--reason`. `unpark`'s ruling is checked as a hold release's and sets `resume` (`plan_unpark`).

## Roles

Every write first meets the session's role, before it plans (kitlib/backlog/policy.py `check`, against the owner's map kitlib/backlog/roles.py, which nothing here widens). The command is sorted into the map's ACTIONS rows: a `set` by the fields it gives and the record's price (a price on an owner-priced or held record is the owner's or the PM's row), a `pull` by `--ruling`, and a `pull` of a held record as `pull-held`, which no role may take (release the hold first, Owner gates), a `block` or `unblock` by an `owner` member or `--owner-ask`, a `close`, `retire` or `delete` of a held record as `close-held`, and `retarget --apply` and `migrate` without `--dry-run` as `retarget`. The narrowest rows are kept (a row's `over`), and a row the role may not take is REFUSED (exit 2), naming the row, its risk, who may take it and the session's role; nothing is written. The tool's role is its session mark (PM_KIT_ROLE, kitlib/sessionmark.py): unmarked is the owner, and a mark roles.py does not list is unlisted, which may only read. A builder's text edit, release or block of a record counts as its own pull when the record's `pulled_by` is the branch the write acts as (`--as`, else the checkout's). Reads, dry runs and `catch-up` (no row names it) are never refused. A command can set its own environment, so this check holds only an honest session to its role. For a subagent the guard applies the same map before the tool runs, by the role its hook payload names rather than the mark, and refuses a write that skips the tool: a subagent's python code importing the library, and any agent session's git write of the store's ref or edit of a folder store's records (docs/guard.md "Backlog roles"). Tests: `tests/backlog/test_policy.py`.

## Audit log

After a write whose rows carry a MEDIUM or HIGH risk (`roles.AUDITED`; Roles) is published, the tool appends one JSON line to `<pm_data>/audit/backlog.jsonl`, `<pm_data>` being the machine config's `pm_data.path` (kitlib/backlog/audit.py). The line holds `verb`, `id`, `role` (the session's role as the tool's own check reads it, `policy.cli_role`), `session` (`--session`, else the launcher's `PM_KIT_SESSION_NAME`), `utc` and `store_sha` (the store commit the write published), never the command's text; a value that is missing, and a role the map does not list, is `-`. `migrate` is logged with id `-`. A write that changes nothing, a LOW write, a read and a dry run add no line. The tool makes the folder on its first such write. With no `pm_data` in the machine config there is no line, and a NOTE on standard error; a log that cannot be written (or a machine config that cannot be read) is a WARNING on standard error after the write, which stands: the log never refuses a write. Only the tool writes there: the guard refuses every other session's but the owner's write in the folder (docs/guard.md `pm-data-audit`). Tests: `tests/backlog/test_audit.py`.

Known limit: the log is untracked. Nothing commits it, adds a `.gitignore` for it, or copies it anywhere, and nothing may count on its being committed later; a PM data worktree's `git status` shows the folder as untracked.

## Records

The existing record format, unchanged (every record of the first repository ported parses). A header key or value is one line: every write refuses a line break or other control character in one with USAGE, whatever the verb (kitlib/backlog/record.py `render`; `tests/backlog/test_scope_shape.py`); the body is not checked. A tab is let through, since it splits no line and a record that already holds one (a pasted summary) must still take writes; a tab in a scope or files path is still refused when a write adds it, as a new `check` finding, while a tab a scope member already holds is an ordinary character to `next` and the collision test (kitlib/backlog/scope.py `path_shape_error` `tab_ok`). Keys cut in the rewrite are unknown keys: `keys`, `class`, `small_fix_*`, `migrated`, `artefact`, `anchor`, `hold_spent`, `value*`.

The review mark, `review: <source> <YYYY-MM-DD>` (the source lower-case `[a-z][a-z0-9-]*`, at most one line; kitlib/backlog/record.py `_review`), says a record was added without a coordinator reading it: the Action Hub's `add` writes it through the library (`plan_add(..., review=)`); tools/backlog.py's `add` has no such flag, and `set` neither writes nor unsets it (REFUSED, kitlib/backlog/plan.py `WRITTEN_BY`). While it stands, `pull` is REFUSED, `--reason` and `--ruling` included (`plan_pull`), as is this session's takeover of a dead pull of the record (`_plan_takeover`; a live pull still refuses `already in flight`), and `next` never offers the record, priced or not: it sits in the banner's `to review` bucket, counted only when non-zero, and the pass-over line says to run `clear-review` (kitlib/backlog/offer.py `classify`, `not_offered_why`). An open marked record at `priority: -1` counts as open in the banner's `N at priority -1 (M of them open)` and is listed by `list --needs-priority` (offer.py `Banner.lines`, tools/backlog.py `do_list`). It can still be priced (`set`), blocked, parked or deleted. `clear-review ID --reason T` drops it (Commands). Rollout: a kit older than this one reads `review:` as an unknown key (a SCHEMA FAIL, so its `check` is RED; its writes to the record still go through, since a finding the store already had blocks no write, store.py `check_change`) and does not honour the mark: its `next` offers the record and its `pull` takes it. So the hub writes the mark only once every kit reading the store knows it. Tests: `tests/backlog/test_review_mark.py`, `tests/backlog/test_cli_review_delete.py`.
