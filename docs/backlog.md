# backlog.py

The backlog's reads and writes: `tools/backlog.py` (entry) over `kitlib/backlog` (library). docs/backlog-store.md is the design; this page is the behaviour.

A program opens the configured store the way the tool does with kitlib/backlog/opener.py `open_store(root, fetch=True, session=None, branch=None)`, which returns the plan Context (its `store.load()` reads), and maps a write verb to its plan with `planner` (a verb that is no write is `USAGE:`, raised before any plan runs); opener.py `retarget_dry` returns the Change a `retarget` without `--apply` would write, and `uncite_dry(ctx)` the one an `uncite` without `--apply` would. `kitlib.backlog.open_store` is the same function: kitlib/backlog/__init__.py `__getattr__` imports it from opener.py on first use, so importing another backlog module does not also load the config and plan code.

## Stores

`.kit.json` `"backlog".store` picks the backend (kitlib/backlog/store.py `open_backend`):

| Value | Records live in |
|---|---|
| `ref` | `backlog/<ID>.md` on `refs/backlog/main`, which shares no history with main |
| absent | the same `ref` store, read-only |
| `branch` | the same tree on a `backlog` branch |
| `main` | `docs/backlog/<ID>.md` in the checkout; any other value is that folder |

The `ref` store reached by the default alone (`.kit.json` names no store: `Config.written`) reads as usual, and every write to it is REFUSED, exit 2, before anything is built (`RefBackend.publish`, `implicit`). A repository could otherwise write records to a ref nobody reads, beside its live store. The refusal (`store.default_store_refusal`) names the PM data worktree and its store to write to with `-C` when the repository has one whose `.kit.json` names a store (`store.pm_data_live_store`); one that names none reads the same ref, so the refusal says it names none and a write there is refused too; the checkout itself is never offered; a PM data worktree not found, or whose `.kit.json` cannot be read, is named as the reason. It always says to set `"backlog": {"store": "ref"}` to write the ref store. `tools/machine_setup.py` writes that setting into a repository it sets up (`kitlib.machinesetup.repo`). A landing never writes the default store (`at_landing._close_in` only reads it), so a refused close at a landing keeps the store's plain command (`at_landing._refused_advice`).

A ref or branch write (`Store.write`) loops: fetch, plan against that snapshot, validate, build the tree in a temporary index, `commit-tree` on the fetched tip, then `push --force-with-lease=<ref>:<tip>`. With no remote it runs `update-ref <ref> <new> <tip>`. A lost race (including `cannot lock ref`, read from both of the push's output streams) reruns the whole attempt, plan included, up to `ATTEMPTS` (5); after that it is ERROR and nothing was written. A push that exits non-zero yet left the remote at or past the new commit (kitlib/git/refs.py `is_ancestor`) succeeded and is not re-planned; one rejected with the remote unmoved is ERROR. When the remote or the fetch that would tell cannot be read after a failed push, the ERROR says the write may have landed: read the store (`check` fetches it) before retrying (`RefBackend._maybe_landed`). Without a remote, an `update-ref` that fails or times out after the ref already moved to the new commit succeeded. After a push the local copy of the ref moves only as a fast-forward (`RefBackend._advance_cache`). A write is refused only for what it adds: a FAIL `check` would report (`check.fail_findings`), or an `item:` blocker naming no record (`check_change`), so a store that is already broken can still be repaired. Writes never touch the checkout. A fetching read adds the store's fetch refspec (`+refs/backlog/main:refs/backlog/main` for `ref`) to the remote once (`RefBackend.ensure_refspec`), and refuses when the remote has no store but the local ref holds one. The commit body carries `Session:` and, when the write cites one, `Ruling: PM R-nnnn`.

No remote means `git remote get-url <remote>` exits 2 and the repository lists no remote at all (`find_remote`); a missing remote beside others, or a lookup that fails any other way, is ERROR.

The `main` backend writes files. It has no compare-and-swap on the files: a write checks that each record it rewrites still holds the bytes it read, then writes. So it writes only in a linked worktree and refuses in a main checkout (`MainBackend.publish`). Outside the PM data branch's worktree it commits nothing (landing carries the files).

In the worktree that has the PM data branch checked out (`MainBackend.commit_branch`: kitlib/pmdata `read` names the branch and HEAD is that branch), each write commits its own record paths and nothing else (`MainBackend._commit`). Each such write first takes git's own lock on that worktree's index, `<index>.lock` made exclusively as git makes it (`MainBackend._lock_index`, `store._IndexLock`), before it reads HEAD's commit or checks the files, and holds it until its index update: meanwhile a `git commit`, `git add` or `git reset` there fails with git's "index.lock': File exists", so none commits an index that does not yet hold the write (which would revert it), and another `backlog.py` write there waits for it. A lock still held after `INDEX_WAIT` (2 s) is ERROR, `errors.Busy`, with nothing written; that lock file is another command's and is never removed. A commit that moves HEAD without the lock (by plumbing alone, `update-ref`) is the one other commit a write can still meet, and the compare below stops it. The blobs are hashed before any file is written; each file is written whole or not at all (`store._replace_file`, below; `MainBackend._write_files`), and a file that fails to write is left as it was, puts the others back (the same way, `MainBackend._restore`) and is ERROR naming its path and any file that could not be put back. A temporary index then takes HEAD's tree plus those paths, `commit-tree` parents it on HEAD, and `update-ref HEAD <new> <old>` moves the branch, retried on a moved or locked HEAD up to `ATTEMPTS` (5). Every attempt, the first included, stops, ERROR and uncommitted (`errors.Overtaken`, an `Uncommitted`), when a commit changed any of the write's paths on HEAD since the write began: `MainBackend.publish` reads HEAD before it checks the files against what it read, and `MainBackend._publish_commit` compares the paths at that HEAD and at the one it builds on. So a write never commits over another session's commit of the same record that landed after `publish` read HEAD. A commit that landed before that read is not seen by the compare: only the files check stops it, when the file on disk differs from what the write read. The refused write then puts each file it wrote back (`MainBackend._put_back`): a path the other commit changed (`Overtaken.changed`) to what that HEAD holds, removing one HEAD lacks, so a read and the next write see the other commit's record; any other path of the write to the bytes it held before the write, a deleted file included, so a record that was uncommitted stays as it was and `catch-up` still lists it. Between the write and the put back a reader of the folder sees the refused content. It touches a file only while the file still holds exactly the bytes the write wrote, and fetches HEAD's content first so that no git call sits between that check and the write; the folder has no compare-and-swap, so a change to the file between the check and the write is still overwritten (a stated residual). The content goes in whole or not at all (`store._replace_file`: a file beside it in the store folder, `<ID>.md.<random>.put-back`, which no reader takes for a record, then `os.replace`, retried for `REPLACE_WAIT` while Windows refuses it because another process has the record open; a temp file it cannot remove is named in the error), so a put back that fails leaves the file as the write wrote it, never a part. Any other file is left, the message names it with `git -C "<worktree>" diff HEAD -- "<path>"...` to compare first (`Overtaken.left`, `Overtaken.compare`), and it gives no ready-made `catch-up --apply` command. A write that read another session's file before that session committed it is refused the same way, though it would have overwritten nothing: that false refusal is accepted, and the write is repeated. When `publish` cannot read HEAD at all the ERROR says nothing was written. The real index then takes those paths only, so other staged or pending work is left as it was: a copy of it in the lock file, its mtime kept, is updated (`GIT_INDEX_FILE`) and moved over the index (`MainBackend._sync_index`, `_IndexLock.install`), which gives the lock up; a move Windows refuses (a reader has the index open) is retried for `REPLACE_WAIT` (1 s). A write that leaves the tree unchanged commits nothing. The commit message is the one a ref write uses (`Session:`, `Ruling:`). A commit that fails after the files are written is ERROR (`errors.Uncommitted`) naming the paths and `catch-up`. A commit that lands with the real index not updated (that update or that move failed; the lock file is then removed) is `errors.IndexStale`: HEAD has the commit, a plain `git commit` in that worktree would revert it, and the message gives the repair, `git -C "<worktree>" reset -q -- "<path>"...`, or `git -C "<worktree>" reset -q` for the whole index when that worktree has no index file (a reset of some paths would build an index of those alone, every other file then a staged deletion). tools/backlog.py reports that write as written: the `WROTE` line (`CAUGHT UP` for `catch-up --apply`), then a `WARNING:` line carrying the message and the repair, exit 0 (`do_write`, `do_catch_up`). Every path in a printed command is in double quotes (`store.quoted`). These git calls drop an inherited `GIT_INDEX_FILE`, `GIT_DIR` and `GIT_WORK_TREE` (`store._store_env`), so a hook's environment never redirects them. A backend opened with `clean` (`open_backend(..., clean=True)`, which only a landing's close uses: `at_landing.pm_data_store`) first requires each path the write would change to match HEAD in that worktree and its index (`MainBackend._require_clean`, after it reads HEAD and before it checks or writes any file): a hand edit, a staged change or a record file never committed there is ERROR, `errors.Dirty`, with nothing written, naming those paths and `git -C "<worktree>" diff HEAD -- "<path>"...` to compare (`git status --short` instead when one is not in HEAD). When the worktree holds HEAD's content for each such path and only the index differs (an `IndexStale` left unrepaired, or HEAD moved by plumbing; `MainBackend._index_only`), the `Dirty` gives the index repair instead of a compare (`Dirty.repair`: `git -C "<worktree>" reset -q -- "<path>"...`, or `git -C "<worktree>" reset -q` when there is no index file). A `backlog.py` write is not `clean` and still writes over such a change.

Exit codes (kitlib/backlog/errors.py): 0 OK, also `show` of a closed, retired or deleted id (`ENDED:`) and an empty store's `next` and `list`; 1 `NOT FOUND:`, `ERROR:`, a RED check; 2 `USAGE:`, `REFUSED:`, or bad arguments. Every write refusal leaves the store untouched. By kind: `Usage` 2, `Refusal` 2, `NotFound` 1, `Ended` (a `NotFound` that exits 0) 0, `Failure` 1, except `IndexStale`, whose write is committed and which tools/backlog.py reports as written with a `WARNING:` line, exit 0 ("Stores"); a bad id shape and an unblock of a record that is not blocked are `USAGE:`, an id already taken is `REFUSED:`.

A record passed over on a scope collision (in `next`, and in a `pull` refused as out of order) names both colliding paths and the holder: `already taken by ID (in flight on BRANCH)` for a live pull, `by ID (session S)` for another session's record, `by ID (offered above)` for one already in the offer (kitlib/backlog/offer.py `next_offer`). A pulled record holds its current `scope:` lines, never its branch's diff, so narrowing them with `set ID --scope P` frees the rest. Taking scope a live pull holds is a lead's call: a `pull` over one and a dead-pull takeover over one are the `pull-collision` row, and a `set --scope` that widens a pulled record into one the `set-widen-collision` row, each one the owner and the lead roles may take (roles.py `LEADS`; Owner gates).

### The fold-in guard

A finding is fixed on the branch that found it unless it cannot be, so `add` names where it came from and why it was not folded (kitlib/backlog/plan.py `plan_add`, `_fold_arguments`, `_fold_overlap`). `--found-on` is the branch the finding was made on, or `none` when no branch found it or the branch that found it was removed, landed or not (then `--why-not-folded` names that branch). A removed branch that landed may instead be named: its landing merge on the code main is the proof that lets it stand in for `none` (below); one removed without landing has no such proof and is written as `none`. `--why-not-folded` is at least 12 characters with no machine path. Both go into the body's `## Found` section, `Found on BRANCH; not folded: T` (`no branch (or on a branch since landed)` for `none`), never the summary, and the commit subject is `backlog: add ID, found on BRANCH`.

- USAGE: either flag missing, a short reason or one holding a machine path, a malformed branch name, `--found-on` naming the code main (`backlog.code_main`, default `repo.main_branch`) in any letter case or ref spelling: a finding on main has no branch, so write `none`; or `--found-on` spelt as a ref (`refs/heads/<x>`, `heads/<x>`, `refs/remotes/<remote>/<x>`, `remotes/<remote>/<x>`, `<remote>/<x>`, the prefix in any letter case): write the local branch name (`kitlib/backlog/plan.py` `_bare_branch`).
- REFUSED: a scope member that overlaps (`kitlib/backlog/scope.py` `members_collide`) a path the branch changed since its merge base with the code main (`git diff --no-renames --name-only`), or the scope of a record the branch holds pulled (`pulled_by` compared in any letter case). A member that cannot be compared counts as an overlap. The refusal lists each pair and says: fold it into the branch, or file it after the branch lands. There is no override flag.
- REFUSED: a `--found-on` branch that is neither a local branch, nor a branch of any remote as last fetched (kitlib/backlog/plan.py `_remotes_with`; every remote is asked, no network), nor a branch with a `Merge B` merge made on the code main (`landing_merge`: `git log --merges --first-parent`, so a `Merge B` merge brought in inside another branch is no proof). The refusal says to pass an existing branch, or `none` for one removed without landing, with the branch named in `--why-not-folded`. A git that cannot list the refs or remotes or read a ref is ERROR, never this refusal.
- A branch only remotes have is diffed at each remote's tip, labelled `R/B`, and prints `NOTE: branch B is not a local branch; its diff was compared as last fetched from R` (`_branch_tips`). A landed branch prints `NOTE: branch B landed on M as SHA SUBJECT; its diff was not compared`. Either way the scopes of records it holds pulled are still checked.
- Ref names are matched in any letter case against git's own list (`_ref_names`, `_spelling`), so a packed ref is found as a loose one is. USAGE: two refs that differ only in letter case, which this file system cannot tell apart: rename one.
- ERROR: a code main that does not resolve (also for a branch found nowhere, whose landing merge then cannot be looked for), no merge base with it, a git that does not answer, or an unreadable record. The ERROR for a missing base names `backlog.code_main` (docs/kit-json.md).
- `--found-on none` skips the overlap check.
- The code main is read as `<code remote>/<code_main>` as last fetched, else the local branch (`kitlib/backlog/plan.py` `_code_main`, by `refs.default_base`; `plan.Context.code_remote`), so a local main that lags its remote gives no false overlap and misses no landing merge. The code remote is `repo.remote`, except in the PM data worktree (`kitlib/backlog/pull_branch.py` `code_config`), where it is the main checkout's `repo.remote` and an unset `backlog.code_main` is the main checkout's `repo.main_branch` (`kitlib/backlog/opener.py` `open_store`). The same code main serves `pull`'s guard below.

`pull` runs the same guard against the other live pulls (kitlib/backlog/plan.py `_pull_fold_hits`, called by `plan_pull`, `_plan_takeover` and `plan_set`). So does `set ID --scope` on a pulled record, for the members it adds only (the record's own branch is never compared): an overlap is the `set-widen-collision` row, REFUSED unless the caller's role may take it, and a write that takes it prints the fold (`folds into the work of B: ...`); an open record is not checked. It fails closed as `pull` does: a git that cannot read another live branch or its merge base makes the `set` an ERROR and nothing is written. A record's declared scope can miss what its branch has actually changed, so the collision rule above cannot see that work.

- REFUSED: a scope member that overlaps a path changed since the merge base with the code main (as for `add`) on the branch of any live pull other than the caller's (`pulled_by` compared in any letter case; each branch is diffed once). A member that cannot be compared counts. The refusal lists each pair and says: fold it into that branch, or pull it after that branch lands. Overriding it is the `pull-collision` row, with `pull ID --reason T`, the reason recorded in `preempt` the way a live-pull collision's is; `next` passes such a record over (`_offer_folds`), and `plan_pull` raises this refusal before the not-in-the-offer one, so the refusal names the fold. A dead-pull takeover takes the row with no flag.
- A code main that does not resolve in the store's git (a store whose git is not the code's) skips every diff with `NOTE: code main X does not resolve here; branch diffs not compared`. A live branch that shares no history with the code main (the code main is not that branch's history, as when `backlog.code_main` is unset in a store whose main branch is its own, docs/kit-json.md) is skipped with `NOTE: code main X shares no history with B; set backlog.code_main; branch diffs not compared`. A live branch only remotes have is diffed as for `add`, with its NOTE; one neither here nor on a remote is noted and not compared. Unlike `add`, which ERRORs on a code main that does not resolve or shares no history, these never block a pull.
- ERROR: a git that cannot read the code main or a branch, cannot answer the merge-base question (any failure other than a confirmed "no common history", `kitlib/git/refs.py` `merge_base`), or cannot diff. `next` turns the same failure into a pass-over, never an ERROR (`_live_changes` reports it per branch; `_offer_folds`).

### Stopping a pull

`block ID --on M --reason T` and `release ID --reason T` stop a pull (kitlib/backlog/plan.py `stop_pull`). Its holder (the caller's branch) may stop it. Anyone may when the pull is dead (no branch or worktree by its `pulled_by`), or when `Context.liveness` finds the worktree on that branch dead: tools/backlog.py's opener passes kitlib/worktree/classify.py `branch_liveness`, `--classify`'s L rule for that one tree (docs/worktree-remove.md "Classify"). Otherwise it is REFUSED, naming why the tree is live; a branch no worktree is on, or one the probe cannot read, counts as live.

- One store commit clears `pulled_by`, `pulled_at` and the pre-emption keys, which frees the scope. `block` sets `state: blocked`, `release` sets `state: open`.
- While the branch exists, a body line `Stopped on branch B at <tip>, branch kept.` goes on its own line, before the `Blocked on M (date): T` or `Released (date): T` line, so a ruling cited in the reason still counts for `check`'s hold citations (`record.hold_citations` reads lines that start `Blocked on`). The output names the branch and tip on a `branch kept:` line. A part landing's release (`at_landing._release_plan`, `kept=False`) writes no Stopped line and reads no branch: the landing's cleanup deletes it. The branch and its worktree are never touched.
- `block` of a pulled record without `--reason` is USAGE.

### Retarget

`retarget OLD NEW` follows a moved file or folder through the store (kitlib/backlog/retarget.py `plan_retarget`). OLD and NEW are plain repo-relative paths. USAGE: a glob in either, `none` in any case (`NONE` too), a control character (a line break would split a record line), a machine path, OLD equal to NEW, or one under the other (`a` to `a/b`; retarget through a path outside both). Matching is case-sensitive and by whole path components, so OLD `docs/guide` never touches `docs/guidebook.md`.

- `scope:` lines. A member equal to OLD becomes NEW. A member under OLD has that prefix replaced, the trailing `/**` included: with OLD a folder, `OLD/a.md` becomes `NEW/a.md` and `OLD/**` becomes `NEW/**`. A rewritten member the record already holds is dropped, not written twice. Listed as `not rewritten` and left alone: a member that covers OLD from above (`docs/**` or `docs` when OLD is `docs/guide`), since narrowing it is a judgement for `set ID --scope`; and one that matches OLD only when case is ignored (`Docs/Guide/a.md`), which the store's casefolded collision checks treat as the same path but a rename never guesses.
- `ref:` and `summary:` lines. OLD is replaced wherever it stands as a whole path: not preceded by a path character, and followed by the end, a `/` (a path under OLD) or a character that cannot continue a path (a sentence's full stop counts). An OLD with no `/` (`tools`) is replaced only where a `/` follows it; a line where it stands as a bare word is listed as `not rewritten`.
- Nothing else changes: `area`, `files` and the body are left as they are.
- A pulled record whose `scope:` lines it would rewrite is REFUSED while its branch is live (its holder releases it, or retarget after it lands; one refusal names every live record the retarget touches), and ERROR when git cannot say whether the branch is live; nothing is written. A dead pull's scope is rewritten, and a live pull whose only change is a `ref:` or `summary:` line is not checked (kitlib/backlog/plan.py `_refuse_live_pulls`).

The dry run plans against a fresh read and runs the same checks a write does. `--apply` writes every changed record in one store commit, `backlog: retarget OLD -> NEW in N record(s)`; with nothing to change it writes nothing.

### Uncite

`uncite` takes the owner's ruling and question ids out of the store's records: a gate is a role now (Owner gates), not a cited id (kitlib/backlog/plan.py `plan_uncite`, `uncite_line`). A cited id is `R-` and four or more digits or `Q-` and three or more, not glued to a word after it (one glued to a word before it by a hyphen, `pre-ID`, is left for a hand edit, below), so a `T-` id, an `item:` member and an `R-` id of fewer than four digits are left alone (`CITE_ID`).

- Body lines. Each line with a cited id is rewritten by rules run in order (`_uncite_rules`). Where the id is a tag on the sentence it goes, with the key or lead word that goes with it (`PM`, `owner`, `ref:`, `see`, a `snake_key`) and a part it names (`O2`, `b`, `(c)`): a parenthesis holding only ids; `(ID: rest`, `rest; ID)` and `rest, ID, more`; a trailing `, ID` or `, key ID`; a leading `ID: ` or `ID, ` after a bullet and a short label; a `See ID.` sentence; and one id after a noun that already says it, with an article, `this`, `that`, `its` or a possessive (`owner's`, `PM's`) before the noun (`the ruling ID`, `an owner question ID`, `its owner's ruling ID`; `_DET`). A comma after an id joins a run of ids, never a tag, so the run stays whole (`by ID, ID` reads `by owner rulings`). Where the id is a word of the sentence it reads `an owner ruling` (`an owner question` for a `Q-` id; `owner rulings` for a run of them): as an object after a preposition or one of a few verbs (`per ID`, `answered by ID`, `overrides ID`; `_PREP`), before a noun after any of those words (`under ID ruling`), and before a date label opening a line (`ID (yyyy-mm-dd):`, an `R-` id only). A `Q-` id as an object reads `an owner question` only after `on`, `in`, `of`, `see`, `citing` or `cites` (`_Q_PREPS`), where it still names the question. A phrase that starts a sentence is capitalised. A line left with only a bullet goes; a line left opening on a mark (`, not this record's.` once a parenthesis went) gives the mark to the line above, or drops it where that line is blank, a heading or already ends on one, and starts with a capital after a blank line, a heading or a finished sentence. A `Blocked on M (date): T` line (`block --reason`) has only its reason `T` worded, the prefix kept; one whose reason would be left empty or opening on a mark is left for a hand edit. A `Blocked on` line that is a hold's only citation is kept as it is and listed under NEEDS HAND EDIT, marked `(the hold's only citation)`, so `check`'s hold citations still read it: the record is blocked on `deliberate` or `owner`, nothing in `q`, `owner_ask` or `blocked_on` cites one, and no `Blocked on` line would once worded (`_hold_needs_block_lines`).
- Lines left for a hand edit. No rewrite says `the owner` or `the owner's`. A line no rule words cleanly is left exactly as it was and listed under NEEDS HAND EDIT: an id no rule places (`One ID debug run`, `the drain and ID are done`), one after a verb or with its verb lost (`ruled ID`, `supersedes ... via ID`, `ID the details`), an id that is a subject or a possessive (`ID says`, `PM ID does not settle`, `ID's build order`: `an owner ruling` there says some ruling where the line meant one), an id after a bare noun (`Owner ruling ID wants`), more than one id after a noun (`the ruling ID and Q-nnn say`), a `Q-` id that stands for its answer (`done per Q-nnn`, `Q-nnn (yyyy-mm-dd): keep the cap`), a leading id before a semicolon (`- ID; keep it`), a leading id list whose removal would leave a joining word first (`(ID and ID, and the rule)`, `ID, which sets`), a run of ids no object rule takes, a run mixing rulings and questions, more than one id put into words in a line (distinct rulings would read as one), an id glued to a word by a hyphen (`pre-ID`), a dated label at the start of a line that continues the sentence before it, odd punctuation or indentation the rewrite would leave, and the line after one left that would have given it its mark. The list names the store, the record and the line in the written record; a second run still lists them.
- Header lines. `priority_ruling` and `hold_ruling` hold only an id, so they are dropped (`UNCITED_KEYS`). `summary` and `ref` values are worded by the body-line rules, as a line that opens a sentence (`UNCITED_FIELDS`, `_uncite_fields`); a `ref` of only ids is dropped, and a value no rule words cleanly, a `summary` of only ids (it is required) or a value left opening on a mark is kept and listed under NEEDS HAND EDIT as `line N (summary)` or `line N (ref)`. `owner_ask`, `q`, `resume`, `priority_per` and `requires` are kept: the offer ranks by `resume`, and a park reads `q`.
- The dry run prints `UNCITE: N cite(s) in M record(s): ... body line(s) rewritten, ... field(s) rewritten, ... header line(s) dropped, ... line(s) left for a hand edit`, then each record with its `- KEY: VALUE`/`+ KEY: VALUE` field pairs (`+ ref: (dropped)` for a `ref` that goes), its `-`/`+` line pairs (`+ (line removed)` for a line that goes) and `dropped KEY: VALUE` lines, then NEEDS HAND EDIT. It plans against a fresh read and writes nothing (`opener.uncite_dry`); `--apply` prints the same lines. The owner or the PM reads it before `--apply`. `--apply` writes every changed record in one store commit, `backlog: uncite N cite(s) in M record(s)`, which names no id and carries no `Ruling:` line; a second run finds nothing to write. It is the `retarget` row (Roles).

### block --until

`block ID --on M --until "<condition>"` blocks as `block` does and writes the header line `until: M <condition>`, the condition that ends hold M (kitlib/backlog/plan.py `plan_block`; the forms are kitlib/backlog/conditions.py's). The Action Hub's `unblock-conditions` job reads it every 300 s and, when the condition is met, clears M as `unblock --on M --reason "condition met: <condition>"` would, in one store commit under `Session: hub-condition`, then pushes `unblocked` to the PM (docs/action-hub.md "Timed jobs"; kitlib/hubsite/recordwrite.py `condition_met`). The conditions it reads:

- `todo:T-n done`: the hub to-do T-n is done.
- `question:Q-n answered`: the hub question Q-n is answered, filed, logged or done.
- `record:<repo>:<ID> closed`: record ID is gone from the store of `<repo>` (a `launcher.repos` name), removed by a commit (close, retire or delete); a record file missing with no commit is not closed.
- `path:<path> exists|absent`: the file or folder is there, or not. `<path>` is absolute or starts with a `%VAR%`, filled from the hub server's environment when the job reads it; it may hold spaces. A machine path (a user profile, a `machine_path_folders` folder) is USAGE, as in any record line, and the job skips one it finds in a hand-written line. Only a path on a local drive (a drive letter, a colon and a slash) after the `%VAR%` is filled is read: a UNC path (`\\host\share`) or a `..` part cannot be told, and the job never probes it.
- `plugin:<folder> absent`: the plugin export folder is gone from the export root (`pluginsource` `export_dir`).

Any other text is free text: it is written, the output says no program acts on it, and it is cleared by hand (`unblock --on M`). A condition that cannot be read (a hub document, a store or the export root that cannot be read, a `%VAR%` that is not set) is not met; the job tries again next pass.

- `owner` ends only on an owner event: `--on owner --until` takes a `todo:` or `question:` condition (with the usual cited `--owner-ask` or `--reason`, "Commands"); any other form on `owner` is USAGE, and a hand-written one is a SCHEMA finding the job skips. The `until` line is not a citation for an `owner` or `deliberate` hold.
- `--until` on `owner` schedules the owner's hold to end, so it is also the `unblock-owner` row (kitlib/backlog/policy.py `sort`), the owner's and the PM's: a coordinator may block on the owner but its `--until` there is REFUSED by the role check. A plan made without the role check (a library caller) refuses it too (`plan.refuse_top`).
- `--until` takes exactly one `--on`, a member with no space in it; an empty condition is USAGE. Each refusal writes nothing.
- One line per member: a re-block of M with `--until` replaces M's line and keeps the others, and a block of a member already there with `--until` adds or replaces its line. A block that adds M without `--until` drops any line for M an older plugin left behind, so it never comes live again.
- Every write that clears M from `blocked_on` drops M's line (`unblock`, the owner's answer, an `item:` blocker closing, a `set` of `blocked_on`; `plan._text`, `record.prune_until`), so the job's own commit leaves nothing to act on and a second pass is a skip. The job writes nothing for a line a write since its read has removed.
- `until` is a header key: a plugin older than this one reports it as an unknown key in `check`, but its writes still pass (a write refuses only a finding it adds), and a line it leaves behind on a cleared member is dropped by the next write of a current plugin.

## Owner gates

An owner gate is a row of the role map (Roles) only the owner and the PM may take (roles.py `TOP`), and the role check decides it: no verb takes a cited id (`--ruling`, `--hold-ruling` and `--owner-said` are gone, and given, each is USAGE), and nothing of the owner's is written into a record. The rows: a price of 1, a price on an owner- or PM-priced record or on one blocked on the owner, and a `priority_by` of `owner` or `pm` (`set-price-owner`); clearing `owner` from `blocked_on`, by `unblock` or by a `set` of `blocked_on` (`unblock-owner`); closing, retiring or deleting an owner-held record (`close-held`); retiring or deleting an owner- or PM-priced record (`retire-priced`); and clearing `resume`, which ranks the record in the offer (`set ID --unset resume`, `set-price-owner`, `policy.OWNER_CLEARS`) (kitlib/backlog/policy.py `sort`). The plan takes these rows only when its caller says the role check ran (`role_checked`: kitlib/backlog/opener.py for the tool, kitlib/hubsite/recordwrite.py for the owner's Action Hub routes); any other caller is REFUSED, naming the row and tools/backlog.py, whose role check decides it (`plan.refuse_top`). A landing's close runs no role check, so it never closes an owner-held record: it prints the plain `close ID --reason "landed <sha>"` for the owner or the PM to run (docs/backlog-store.md "Lifecycle changes"). An owner-held record's priority changes only with `--priority-by owner|pm`. `priority_ruling`, `hold_ruling`, `resume` and `priority_per` are no longer written (`plan.UNWRITTEN`): a `set` of one is REFUSED and `set ID --unset K` clears it (clearing `priority_ruling` or `hold_ruling` changes no rank, so it is `set-other`; clearing `priority_per` is `set-other` too, or `set-price-owner` on an owner- or PM-priced record, `policy.PRICE_FIELDS`); a record that carries one keeps it until then, and `uncite` drops the first two everywhere (Uncite), except that a price move, or a result of `priority_by: agent`, drops `priority_ruling` (it named the old price), and the output says so. The daily full run's pricing (kitlib/dailyfull/file.py `file`) records no ruling either: it always prices its red record at 2, `priority_by: agent`, with no role check and no `priority_ruling` or `Ruling:` line; the PM or the owner promotes it. No write and no `check` reads the rulings ledger, whatever the machine config names (`check_store` in kitlib/backlog/check.py). `blocked_on: owner` is the only owner hold: `priority: -1` is retired, so `set` refuses it with USAGE naming `block ID --on owner --owner-ask "<the question>"` and `check` reports a stored one (kitlib/backlog/record.py `RETIRED_PRIORITY`). A pull of a held record (blocked on the owner) is the `pull-held` row, which no role may take (Roles), so a pull never releases the hold: the owner or the PM unblocks it first (the `unblock-owner` row), then it is pulled.

A collision with a live pull - a pulled record whose `pulled_by` branch git still finds; a failed probe holds every pull - on another branch is a lead's call, never `--reason` alone (kitlib/backlog/plan.py `live_hits`). The plan finds it, not the command's words, so the role check's sort never names it: the tool's opener asks the role map whether the session may take the collision row (`policy.may`) and passes the answer as `may_collide`, and without it the plan refuses, naming each pair, its holder and the row. A colliding `pull` is the `pull-collision` row and still needs `--reason`, recorded in `preempt`; a dead-pull takeover that collides takes the row with no flag. A held record that collides is still `pull-held`: its hold is released first (above). A `set --scope` on a pulled record checks only the members it adds (`widened_members`: a member is covered by an equal one or by an old `X/**` above it; `none` covers only `none`): with any of them colliding, or folding into another live pull's work (the fold-in guard), it is the `set-widen-collision` row, its refusal names the form `set ID --scope <path> [--scope <path> ...]` (the whole new list), and the write prints each collision (`widened into a live pull: ...`, `folds into the work of B: ...`). Narrowing, and widening into free scope, need nothing. Both rows are MEDIUM and the owner's and the lead roles' (roles.py `LEADS`). A write that takes one names the row for the audit log (`Change.rows`) and ends its commit subject with ` (over a live pull)` (`policy.COLLISION_MARK`), which the audit check reads back (Audit log). A live pull on the same branch is no collision: the caller's branch for a pull or a takeover, the record's own `pulled_by` for a `set` (overlapping records bundled onto one branch; `live_hits` `branch=`). A collision with a record that is not pulled (another session's, or one higher in the offer) still needs only `--reason`.

## Roles

Every write first meets the session's role, before it plans (kitlib/backlog/policy.py `check`, against the owner's map kitlib/backlog/roles.py, which nothing here widens). The command is sorted into the map's ACTIONS rows: a `set` by the fields it gives and the record's price (a price on an owner-priced or held record is the owner's or the PM's row, and a `set` of `blocked_on` that drops `owner` is `unblock-owner`), a `pull` of a held record as `pull-held`, which no role may take (release the hold first, Owner gates), a `block` or `unblock` by an `owner` member or `--owner-ask`, a `close`, `retire` or `delete` of a held record as `close-held`, a `retire` or `delete` of an owner- or PM-priced record as `retire-priced`, and `retarget --apply` and `uncite --apply` as `retarget` (roles.py's `retarget` row names `uncite`, so the owner and the PM may apply it). The narrowest rows are kept (a row's `over`), and a row the role may not take is REFUSED (exit 2), naming the row, its risk, who may take it and the session's role; nothing is written. The tool's role is its session mark (PM_KIT_ROLE, kitlib/sessionmark.py): unmarked is the owner, and a mark roles.py does not list is unlisted, which may only read. A builder's text edit, release or block of a record counts as its own pull when the record's `pulled_by` is the branch the write acts as (`--as`, else the checkout's). Reads, dry runs and `catch-up` (no row names it) are never refused. A command can set its own environment, so this check holds only an honest session to its role. For a subagent the guard applies the same map before the tool runs, by the role its hook payload names rather than the mark, and refuses a write that skips the tool: a subagent's python code importing the library, and any agent session's git write of the store's ref or edit of a folder store's records (docs/guard.md "Backlog roles").

## Audit log

After a write whose rows carry a MEDIUM or HIGH risk (`roles.AUDITED`; Roles) is published, the tool appends one JSON line to `<pm_data>/audit/backlog.jsonl`, `<pm_data>` being the machine config's `pm_data.path` (kitlib/backlog/audit.py). The line holds `verb`, `id`, `role` (the session's role as the tool's own check reads it, `policy.cli_role`), `session` (`--session`, else the launcher's `PM_KIT_SESSION_NAME`), `utc` and `store_sha` (the store commit the write published), never the command's text; a value that is missing, and a role the map does not list, is `-`. A write that changes nothing, a LOW write, a read and a dry run add no line. The tool makes the folder on its first such write. With no `pm_data` in the machine config there is no line, and a NOTE on standard error; a log that cannot be written (or a machine config that cannot be read) is a WARNING on standard error after the write, which stands: the log never refuses a write. Only the tool and the guard's hook write there. The hook appends `refusals.jsonl`, one line per deny it answers (docs/guard-v2.md "Refusal log"). The guard refuses every other session's write in the folder, except the owner's (docs/guard.md `pm-data-audit`).

Known limit: the log is untracked. Nothing commits it, adds a `.gitignore` for it, or copies it anywhere, and nothing may count on its being committed later; a PM data worktree's `git status` shows the folder as untracked. Known limit: only `tools/backlog.py` writes are logged; the record close at landing (gate and land, `at_landing.pm_data_store`), the hub's writes (the `unblock-conditions` job's under session `hub-condition`), the daily full run's pricing (`kitlib/dailyfull/file.py`, session `daily-full`) and a direct write to the store add no line. Known limit: `catch-up --apply` commits under a MEDIUM row but writes no line today.

`tools/backlog_audit.py [-C DIR] [--days N] [--no-fetch] [--all]` (kitlib/backlog/audit_check.py) reads the store's commits of the last N days (default 1) against the log, for the PM's digest. It writes no record, no log line and no checkout file. By default a ref or branch store is fetched first: that rewrites the local store ref, and the first time it may add the store's fetch refspec to the remote in `.git/config`. `--no-fetch` skips both. Each commit's command is rebuilt from its subject (a collision row from the subject's `policy.COLLISION_MARK`, Owner gates) and the record before and after it, and sorted by `policy.sort`, so roles.py alone says which need a line. Findings: UNAUDITED (an AUDITED change no line's `store_sha` names), UNKNOWN (a store commit no verb's subject reads) and UNMAPPED (a line in the window whose role is `-` or not in the map). The writes of sessions `gate-land`, `owner-hub`, `daily-full` and `hub-condition` add no line by design (`audit_check.BY_DESIGN`): they are counted in the NOT LOGGED BY DESIGN line, with a count per session, and never flagged. A `catch-up --apply` commit has no line, so it shows as UNAUDITED. The log is the machine's, so a line naming no commit of this store flags nothing, and a `-` sha is only counted. A folder store outside the PM data worktree commits nothing per write: NOT CHECKED. So is a log or store that cannot be read, with the error named. Exit 0 OK, 1 findings, 2 USAGE or NOT CHECKED. By inference a `set` that gave a field its unchanged value is not seen, so the check can miss one but never flags a change wrongly.

The check also reads every `answer:` line a store change in the window adds or changes, whatever its session, covered and by-design changes included (`audit_check.answer_lines`). A line passes only when the commit's `Session:` is `owner-hub` (the Action Hub's filing, `kitlib.hubsite.recordwrite.answer`) or its subject is a `backlog: catch up ` commit (a line a failed hub write left in a folder store, docs/action-hub.md "Filing the answer"), and the hub store holds a question with that id, bound to that record id, whose `answer.at` equals the line's, or is later (a re-answer replaces the line, so an earlier answer's line still passes; `audit_check.held`), and whose status is `answered`, `filed`, `logged` or `done` (`audit_check.ANSWERED`). Anything else is UNVERIFIED, naming the commit, the line and why. The hub store is read only, through the hub's client with the agent token (`audit_check.hub_questions`, the read `kitlib/maintlint/backlog.py` makes), and only when the window holds an answer change the hub wrote. The window's records are read once, in one git process (`audit_check.records_of`), and shared with the command rebuild, so the answer check starts no git process of its own. A hub that cannot be read checks none of the hub's answer lines: a NOTE `answers NOT CHECKED` names the error, never a finding, and the exit stays as the other findings make it (a line no hub writer wrote is still UNVERIFIED). So that a marked session cannot use a by-design writer's name, `tools/backlog.py` refuses a `--session` of `gate-land`, `owner-hub`, `daily-full` or `hub-condition` (any case) from a marked session (kitlib/sessionmark.py), before the store is opened; the owner's unmarked shell may still use them.

Known limits: the line's record is matched by id alone, not by the hub's repository name (`record.repo`), which no backlog reader can map to the audited checkout. An answer line that is removed is not flagged. The library writers (`at_landing`, `recordwrite`, the `unblock-conditions` job through it, `kitlib/dailyfull/file.py`) open the store directly, so the `--session` refusal does not reach them, nor a direct commit to the store: the answer check is what catches such a commit. The `--session` refusal reads the session mark, which every command's own environment carries, so a command can clear it (`PM_KIT_ROLE= python ...`, kitlib/sessionmark.py): it stops a slip, not a session set on passing as a by-design writer. A line dated before a later hub answer to the same question on the same record passes, though the hub never held its `at`.

## Records

A header key or value is one line: every write refuses a line break or other control character in one with USAGE, whatever the verb (kitlib/backlog/record.py `render`); the body is not checked. A tab is let through, since it splits no line and a record that already holds one (a pasted summary) must still take writes; a tab in a scope or files path is still refused when a write adds it, as a new `check` finding, while a tab a scope member already holds is an ordinary character to `next` and the collision test (kitlib/backlog/scope.py `path_shape_error` `tab_ok`). An unknown key is a SCHEMA finding.

The review mark, `review: <source> <YYYY-MM-DD>` (the source lower-case `[a-z][a-z0-9-]*`, at most one line; kitlib/backlog/record.py `_review`), says a record was added without a coordinator reading it: the Action Hub's `add` writes it through the library (`plan_add(..., review=)`); tools/backlog.py's `add` has no such flag, and `set` neither writes nor unsets it (REFUSED, kitlib/backlog/plan.py `WRITTEN_BY`). While it stands, `pull` is REFUSED, `--reason` included (`plan_pull`), as is this session's takeover of a dead pull of the record (`_plan_takeover`; a live pull still refuses `already in flight`), and `next` never offers the record, priced or not: it sits in the banner's `to review` bucket, counted only when non-zero, and the pass-over line says to run `clear-review` (kitlib/backlog/offer.py `classify`, `not_offered_why`). An open unpriced marked record is listed by `list --needs-priority` (tools/backlog.py `do_list`). It can still be priced (`set`), blocked, parked or deleted. `clear-review ID --reason T` drops it (Commands).
The owner's answer, `answer: <Q-nnn> <at>` (`at` the Action Hub's timestamp with its UTC offset, exactly `YYYY-MM-DDTHH:MM:SS+HH:MM`: a `Z`, fractional seconds or the compact form are refused, so one answer has one spelling; kitlib/backlog/record.py `_answer`, `ANSWER_AT_RE`), says the owner answered that question, bound to the record, at that time. There is one line per question, so a record can hold several; two lines for one question are a SCHEMA finding (`_cross_field`), and a re-answer replaces its question's line. Only the library's `plan_answer` writes it (kitlib/backlog/plan.py), which the Action Hub's filing calls; `set` neither writes nor unsets it (REFUSED, `WRITTEN_BY`), and tools/backlog.py has no verb for it. One `plan_answer` write, one commit `backlog: owner answer <ID> on <Q>`, sets the line and appends a body section `## Owner answer (Action Hub, <at>)` with the question's id and title, the choice label and note verbatim and `via`; a machine path in any of them is USAGE. The wait ends only on the last answer: when no other question bound to the record is still open (the caller's `waiting`) and every question the record's wait names has an answer line (`q` of a parked record, the `Q-` ids `owner_ask` cites on one blocked on `owner`; `_waits_on`), a parked record is unparked as `unpark` does, and the `owner` blocker is cleared as `unblock` does (other blockers stay; `owner_ask` goes). Clearing the owner is the `unblock-owner` row, so a caller without the role check is REFUSED, the text saying the owner's or the PM's role clears an owner blocker (the hub's owner route passes `role_checked`). Otherwise the answer is written and the state stays: a pulled or open record, a record parked or blocked on another question, and a wait that names no question. A free-text Other answer (`other`) also writes the review mark `review: owner-answer <date>` unless a mark stands, so `pull` refuses the record and `next` lists it to review until a coordinator runs `clear-review` (above). The same question and `at` again changes nothing, and so does an `at` older than the record's line for that question: a stale re-file never overwrites a newer answer. A record that is gone is NOT FOUND.
A hold's end condition, `until: <member> <condition>` (kitlib/backlog/record.py `_until`), names a `blocked_on` member and, after one space, the condition that ends it; there is at most one line per member, so a record can hold several. Only `block --until` writes it ("block --until"); `set` neither writes nor unsets it (REFUSED, `WRITTEN_BY`). SCHEMA findings (`_cross_field`): a line whose member the record is not blocked on (every current write drops one), two lines for one member, and an `owner` line on a condition other than a to-do or a question.

### Umbrella records

An umbrella record (a redesign or other work built from a mockup or proposal, cut into slice records whose branches write `Part-of:`) carries an element checklist taken from the mockups by walking them, not from file sizes: one line per element (sidebar entry, view, control, state), each naming the slice record that owns it. A slice list cut by file size leaves elements owned by no slice (the Triage redesign lost its Schedule view that way). The umbrella closes when every element is ticked against a landed slice, not when every slice has landed; an element with no owner gets a slice before the umbrella closes.
